# Plan-Then-Execute プランモード

[English](README.md) · [中文](README.zh.md) · **日本語** · [한국어](README.ko.md)

セッションは実行の前に設計できます：エージェントは**プランモード**に入り、読み取り専用ツールだけで作業し、計画を提出し、ユーザーの承認があるまで一切ファイルを書きません。多ファイル変更へいきなり突っ込むのが一番ずれやすい道であり、ユーザーには軌道修正の機会がありません。

事実の出典：`agent/tools/plan_mode/`（2 つのツール + 共有状態ヘルパー）、`agent/middlewares/tool_selection/core.py`（ホワイトリスト）、`workspace/prompt_builder.py::_build_plan_mode_block`（システムリマインダー）、`config/features/agent_side/plan_mode.py`（調整値）。

## 流れ

```
                  enter_plan_mode
   needs_planning ────────────────► planning ──────────────► ready
        ▲                              │  ▲                   │
        │        reject (no message)   │  │ reject (message)  │ enter_plan_mode(replan=True)
        └──────────────────────────────┘  └─── revise ────────┘
                                                               │
                                            needs_replan ◄─────┘
                                                  │  (exit_plan_mode + 承認)
                                                  └──────────► ready
```

1. `enter_plan_mode(reason)` — 計画に値するとエージェントが判断した場合（多ファイル変更、アーキテクチャ判断、要件が不明確、複数の有効な案）。セッションの状態は `planning` になり、ツール面は読み取り専用ホワイトリストに絞られます。
2. エージェントは探索し（`read_file`、`search_files`、`message_search`、スキルビューア）、曖昧な点は `question` でユーザーに尋ね、設計します。プランモードのターンは `question` か `exit_plan_mode` の呼び出しでしか終われません。
3. `exit_plan_mode(plan)` — 計画を `workspace/sessions/<session_id>/plans/plan-<revision>.md` に保存し、承認のためにグラフを中断します（チャットには **承認** と **修正を依頼** を備えたカードが出ます）。
4. **承認** → 状態 `ready`。計画はセッションの参照として残り（システムプロンプトが毎ターンそのファイルを名指しします）、書き込みツールが戻ります。**修正を依頼**（reject + フィードバック）→ フィードバックがエージェントへ返り、修正して再提出します。**拒否**（メッセージ無し）→ 計画は破棄され、再計画するかはエージェントが決めます。

## 読み取り専用の保証

状態が `planning` / `needs_replan` の間、`ToolSelectionMiddleware` は既存のセッション別ツール選択とまったく同じ二段構えでホワイトリストを適用します：モデルにはホワイトリストだけが**提示**され、それでも届いた呼び出し（古い checkpoint、幻覚の名前）は実行時に**拒否**され、"Plan mode is active" が返ります。既定のホワイトリストは `config/features/agent_side/plan_mode.py::PLAN_MODE["allowed_tools"]` です。セッション自身の選択にも縛られますが、2 つの計画ツールだけは常に到達可能です——出られないモードは罠になります。

サブエージェントという唯一の穴は意図的に塞いでいます：`sessions_spawn` はホワイトリストに**ありません**。子は自分のセッション状態で動くため、承認前に書き込めてしまうからです。

## ガード

* **変更予算** — `PLAN_MODE["max_mutations"]`（5）：1 つの計画につき「修正を依頼」は 5 回まで。超えると `exit_plan_mode` は再提出を拒否し、ユーザーに承認か拒否かを求めさせます。
* **リビジョン結び付け** — 承認は `sha256(plan)[:16]` に結び付きます。承認待ちの間に保存されたリビジョンや計画**ファイル**が変われば、承認は破棄され再提出が必要です。
* **サイズ上限** — `PLAN_MODE["max_plan_chars"]`（20000）。超える計画は「短くして」と拒否され、切り詰められません。
* **機能オフ** — `PLAN_MODE["enabled"] = false` で両ツールが登録されず、他は変わりません。

## ユーザーに見えるもの

計画は入力スロットに承認カードとして現れます（HITL が使うのと同じ面）：計画本文、フィードバック欄、**修正を依頼**、**承認**。承認すると実行ツールが有効なままターンが再開し、修正依頼ならフィードバック付きで再開してエージェントが計画を直します。

## 他のゲートとの関係

プランモードは「実行前の承認」、HITL は「実行中の承認」（実行が始まれば従来どおり対象操作を止めます）。TaskFlow は「承認後の実行」：計画の番号付き手順を flow ステップや todo として登録し、完了ゲートが結果を判定します。

## 🎯 概要

すべてのファイルツールはすべてのサブ Agent と同じプロセスを共有し、ツールはプロセス単位のシングルトンです——つまり「同じパスに 2 人の書き手」は例外ではなく日常です。保護がなければ障害は静かです：後から書いた者が先の編集を上書きし、どちらも成功を報告する。読み手は書きかけのファイルを掴む。書き込み途中のクラッシュは対象を切り詰める。

6 つの仕組みが、書き込みが出会う順にこれへ答えます：

1. `file_write_lock`——パス単位の `threading.Lock`、続いてプロセス間 `flock`。
2. `atomic_write_text_no_follow`——同一ディレクトリの一時ファイル、`fsync`、モード保持、`os.replace`。
3. `patch_file` の二層 CAS——読み取り時のフィンガープリントと、`replace` 直前に再表明される `expected_revision`。
4. `write_file` の読み取り先行ライセンス——既存ファイルを上書きできるのは、それを読んだセッションだけ（後述の専用節）。
5. `sweep_stale_temp_files`——`kill -9` の置き土産は、そのディレクトリへの次の書き込みが掃除する。
6. 隔離サブエージェントワークスペース——任意参加の私有コピー。変更はロックの下でマージされ、衝突は報告される。

## 🧱 各レイヤー

### 1. アトミック書き込み

`atomic_write_text_no_follow`（およびその下のバイト版 `atomic_write_bytes_no_follow`）は、対象と同じディレクトリの `.sherry-tmp-*.swp` に書き込み、`fsync` し、対象のモードを写し——スクリプトの実行ビットは生き残らねばなりません——`os.replace` で据えます。したがって読み手が見るのは古い内容か新しい内容だけで、破れたファイルは決して見えず、書き込み途中のクラッシュでも対象は切り詰められません。

意図的な 2 つの端：

- 最終構成要素がシンボリックリンクなら拒否（`ELOOP`、`_open_no_follow` 経由）。よってこのヘルパーは `pub/func/atomic_replace.py` を再利用できません——あちらは意図的にリンクを辿ります。
- ファイルシステムが rename を拒む場合、ヘルパーはその場書き込みへ降格します——可用性を原子性より優先し、WARNING で記録します。

### 2. 二層 CAS

`patch_file` はファイルを読み、あいまい一致を行い、それから二度検証します：読み取り時のフィンガープリント（`mtime_ns` + `size`、内容ハッシュの免除付きなので無意味な `touch` は衝突になりません）と、アトミック書き込みが `os.replace` の直前に再表明する `expected_revision`（`mtime:<整数ミリ秒>:size:<バイト>`）。他の誰かによる変更は上書きされず、「読み直して再試行」エラーとして拒否されます。

検証から書き込みまでの窓はゼロではなく、本書もそう主張しません。ファイルシステム水準のトランザクションを前提にせず縮められる最小の間隔まで狭めてあります。

### 3. パス単位ロック

`path_lock.py` は参照カウントされた `threading.Lock` のレジストリ——解決済みパスごとに 1 つ——を保ち、読み・変更・書きのサイクル全体を包みます。これによりこのプロセス内の 2 体の Agent は競合せず直列化します。`file_lock.py` が続けてプロセス間の半分を加えます：`src/data/locks/` 配下の sidecar ファイルへの勧告的 `flock`、タイムアウトは `FileBusyError`（ハングではなく、対処可能なエラー）を返します。

人を驚かせる規則が 1 つ：**ロックファイルは決して削除しない。** ロックは inode に載っているため、sidecar を `unlink` すると——古びて見えても——次の書き手は新しいファイルを作り、誰も排除していないロックを取ります。実測では両方の保持者が同時に臨界区間へ入りました。0 バイトの sidecar は不活性で、保持者が死ねばカーネルが `flock` を解放するので、実装すべき死の持ち主プロトコルは存在しません。

`terminal`、`python_repl`、ast-grep の書き換えはサブプロセスで動き、いかなるロックも取りません：それらを捕まえるのは CAS であり、この境界は意図的です。

### 4. 残留ファイルの掃除

一時ファイルの作成から replace の間にハードキルされた場合だけ、`.sherry-tmp-*.swp` が残り得ます。他のすべての失敗経路はそれを unlink します。同じディレクトリへの次の書き込みが 1 時間を超えた残留を掃除します（`sweep_stale_temp_files`）：生きた書き手の一時ファイルは数秒の寿命しかなく、年齢しきい値はまさにそれと距離を取るためのものです。掃除は決して例外を投げません——ディレクトリを読めない走査が、それが先行する書き込みを失敗させてはならないからです。

## 📖 読み取り先行ライセンス

`write_file` は盲目の上書きです：対象を読まないため、CAS へ持ち込める revision がなく、このセッションが一度も見ていない内容を破壊し得ました。`read_state.py` が欠けていた前提条件を供給します——プロセス内の `(セッション, 解決済みパス) → revision` 写像で、餌は次の 2 つの事象だけです：

- **完全**な `read_file`（先頭ページ、切り詰めなし。部分読みは何も許諾しません）。revision は開いたディスクリプタの `fstat` から取るため、読み取り中に差し替えられたパスが、セッションの見ていないバイトを許諾することはありません。
- セッション自身によるファイル全体の `write_file`。その内容はセッションが書いたものだからです。

セッション自身の `append` や `patch_file` は、すでに保持しているライセンスを**前進**させるだけであり、決して新設しません——差分はファイル全体の知識ではありません。ライセンスは `expected_revision` としてアトミック書き込みへ渡り、したがって：

- セッションが一度も読んでいない既存ファイルは、`read_file`/`patch_file` を促すヒント付きの「まず読む」エラーで即座に拒否されます；
- 読み取り後に変わったファイルは、同時書き込みを捕まえるのと同じ表明で拒否されます；
- まだ存在しないパスは `absent` として許諾され、他の書き手に先を越された作成は上書きではなく拒否されます；
- ディレクトリやシンボリックリンクの対象はゲートを素通りします——それ自身のエラーが正しい答えであり、「まず読む」は無意味だからです。

レジストリには上限があり（4096 件、LRU）、**永続化されません**：再起動でライセンスは忘れられ、既存ファイルへの次の上書きは「まず読む」を返します——代償は再読 1 回で、失う編集は決してありません。追い出しは保護を落とすだけで、与えはしません。

## 🌱 隔離サブエージェントワークスペース

`sessions_spawn(isolation=True)` は子にプロジェクトディレクトリの私有コピーを与えます（実装は `agent/tools/subagent/isolation/`、ワークスペースは `src/data/isolated/` 配下、子の cwd は `<workspace>/tree`）。子はコピーの中で端から端まで働き——自らのツール、`terminal`、テスト——実行が終端に達したとき、完了メッセージの配達の前に announce フローがコピーをマージします（静かな子の仕事も同様にマージされます）。

マージは他の場所と同一の規則を逆向きに適用するもので、親ルート単位の `flock` の下で行います：

- コピーはマニフェスト（`snapshot.json`）を携え、コピー時点の通常ファイルごとの revision を記録します；
- 子が変更したファイルは、親がまだスナップショット revision を保つ間だけ適用されます——そうでなければ**衝突**で、親のファイルは手つかずのままです；
- 新規ファイルは空きにのみ作成されます；削除は親が依然一致することを要します；シンボリックリンクは決して貫通マージされません（スキップして報告）；
- キャッシュ（`node_modules`、`.git`、`.venv`、`__pycache__`、`dist`、`build` など）はコピーもマージもされません。

きれいなマージはワークスペースを削除します。衝突のあるマージは `<workspace>/tree` を検査用に残し、マニフェストを消費します——これにより同じツリーが二度マージされることは決してありません。親が読む完了返信には報告が添えられ（`applied`、`created`、`deleted`、そしてパスごとの全衝突）、マージされたパスは親の証跡台帳で古いものとして印されます。

## ⚖️ 代替案と実測

**行ハッシュ編集（omo の hashline）**は実装していません：ファイル全体の CAS より細かく——編集が触れた行だけを比較します——read ツール自身の出力形式の変更を要しますが、上の 4 層が対象の静かな消失故障をすでに消しています。

**rename 後のディレクトリ `fsync`** は有効化していません。本機（f2fs）での実測：書き込み 1 回はディレクトリ `fsync` 付きで 1.34 ms、なしで 0.52 ms——書き込み経路の 2.6 倍、絶対値で 1 ファイルあたり約 0.8 ms。買えるものは狭い：ファイルのデータはすでに `fsync` 済みなので、電源断が破れたファイルを残すことはなく——起き得るのは編集が以前の内容へ静かに戻ることだけで、これは主流のエディタも同じです。プロセスクラッシュには何も要りません：ページキャッシュが残ります。どこかの配備が「確認された書き込みは電源断を生き延びる」と約束するなら、フラグの後ろの 1 行です。

## 🚧 境界

- プロセス間ロックは勧告的です：外部エディタは取りません。そこでの答えは CAS の各層です。
- `terminal`、`python_repl`、ast-grep の書き換えはロックもライセンスも完全に迂回します（サブプロセス）。シェルコマンドでファイルを書く Agent は、ここの保証の外側です。
- ネットワークファイルシステム：`flock` の意味論は NFS で信頼できません。ローカルディスクが対象です。
- ハードリンクは設計上切れます：`os.replace` は inode を交換するため、古い内容へのハードリンクは古い内容を保ちます。

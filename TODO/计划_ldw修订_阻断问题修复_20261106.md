## 阻断 1：DagNode.run 丢弃上游结果 + journal key 不含变体输入

### 修复 A：DagNode.run 必须把 deps 结果拼进下游 prompt

```python
# 修复前（断链）：
run=lambda d, p=prompt, a=agent_type: ctx.agent(prompt=p, agent_type=a)  # d 没用

# 修复后（deps 结果传给下游）：
run=lambda d, p=prompt, a=agent_type: ctx.agent(
    prompt=f"{p}\n[前驱 step 结果]\n{json.dumps(d, ensure_ascii=False)}",
    agent_type=a)
```

下游 step 的 prompt 含前驱结果，agent 拿到上游输出继续工作。journal key 含此 prompt（含前驱结果），所以前驱结果不同 → 下游 key 不同 → 正确缓存。

### 修复 B：journal key 必须含变体输入（不能只用静态 task 文本）

**根因**：原编译 `prompt = s["task"]`（静态文本），所有变体哈希到同一 key → 缓存污染。

**修复**：orchestrate 接收 `args`（变体输入），注入每个 step 的 prompt。编译产物是**结构化 step 元数据**（JSON 可持久化），replay 时用 step 元数据 + 当前变体输入**重新生成 orchestrate**（不持久化闭包）：

```python
def compile_plan_to_workflow(plan_knowledge: dict) -> dict:
    """编译产物 = 结构化 step 元数据（JSON 可持久化），不是闭包。"""
    return {
        "steps": [
            {
                "step_id": s["step_id"],
                "task_template": s["task"],          # 静态模板
                "agent_type": role_agent_type(s["functional_role"], s.get("extra_tools")),
                "deps": s.get("depends_on", []),
                "hard_constraints": plan_knowledge.get("hard_constraints", []),
            }
            for s in plan_knowledge["steps"]
        ],
        "plan_key": plan_knowledge["plan_key"],
    }

def build_orchestrate(workflow_meta: dict, variant_input: str):
    """replay 时：step 元数据 + 变体输入 → orchestrate（含变体的 prompt → journal key 区分变体）。"""
    steps = workflow_meta["steps"]

    async def orchestrate(ctx, args):
        vi = args.get("variant_input", variant_input)  # 变体输入
        nodes = []
        for s in steps:
            # prompt = 静态 task + 变体输入（让 journal key 含变体）
            prompt = f"{s['task_template']}\n[当前任务输入]\n{vi}"
            nodes.append(DagNode(
                id=s["step_id"],
                deps=s["deps"],
                # deps 结果也拼进 prompt（修复 A）
                run=lambda d, p=prompt, a=s["agent_type"]: ctx.agent(
                    prompt=f"{p}\n[前驱结果]\n{json.dumps(d, ensure_ascii=False)}",
                    agent_type=a),
            ))
        return await ctx.dag(nodes)

    return orchestrate
```

**journal key 现在含**：`(task_template + variant_input + 前驱结果, agent_type, model, schema)`。不同变体 → 不同 prompt → 不同 key → 不污染。同变体重跑 → 命中 → 零调用。

**持久化**：存 `workflow_meta`（结构化 JSON），不存闭包。replay 时 `build_orchestrate(meta, variant_input)` 重新生成。

## 阻断 3：Roster builder 缓存 vs session_id 注入

### 修复：leaf 图 session-agnostic + 运行时设 contextvar

**根因**：sherry 工具按 session 构建，Roster 按 agent_type 缓存 builder → 首个 session 烘进共享图。

**修复**：leaf agent 图**不烘焙 session**——工具在执行时从 contextvar 读 session（sherry 工具已是进程级单例 + session-scoped state，session 本就在 contextvar 里）。Roster 缓存的图是 session-agnostic 的；每次 leaf 调用前设 contextvar：

```python
def make_leaf_agent(functional_role, tools, model_profile) -> Runnable:
    """造 session-agnostic 的 agent 图。工具从 contextvar 读 session，不烘焙。"""
    # sherry 工具已是进程级单例，session 从 runtime contextvar 读
    # （agent/tools 的 session-scoped state 机制）
    return built_agent(tools=tools, model=build_model(model_profile), ...)

# leaf 调用包装：设 contextvar 再 ainvoke
def wrap_leaf_with_session(agent_graph, session_id):
    """每次 leaf 调用前设 session contextvar。"""
    async def wrapped(input):
        with set_session_contextvar(session_id):  # 设当前 leaf 的 session
            return await agent_graph.ainvoke(input)
    return RunnableLambda(func=wrapped)

def register_roster(steps, session_id):
    roster = Roster()
    for s in steps:
        agent_type = role_agent_type(s["functional_role"], s.get("extra_tools"))
        tools = step_tools(s["functional_role"], s.get("extra_tools"))
        graph = make_leaf_agent(s["functional_role"], tools, step_model(...))
        # 注册的是 wrapped runnable（session 在 wrapper 里设），不是 builder
        roster.register(name=agent_type, runnable=wrap_leaf_with_session(graph, session_id))
    return roster
```

**关键变化**：
- 用 `roster.register(name, runnable=...)`（预编译 runnable）而非 `builder=`（builder 缓存图）——每次 replay 按 session 注册 wrapped runnable。
- `wrap_leaf_with_session` 在 ainvoke 前设 contextvar，工具执行时读到的 session 正确。
- 图本身 session-agnostic（工具从 contextvar 读），可被同 session 的多个 leaf 复用。

**代价**：每次 replay 重新注册 Roster（per session）。可接受（replay 不是高频操作）。

**前提验证**：sherry 工具的 session-scoped state 确实通过 contextvar 传递（不是构造时捕获）。fork Phase 0 时核实 `agent/tools` 的 session 读取机制。

## 阻断 4：PTC 脚本是 LLM 来源却绕过 AST gate

### 修复：success_steps 作 DATA 喂给固定 runner，不拼可执行源码

**根因**：`f"r{i} = {s['tool']}({s['params']})"` 把 LLM 文本原样拼进 eval 的源码。

**修复**：不生成可执行源码。生成**结构化调用列表**（data），用固定可信 runner 执行：

```python
def compile_step_ptc_script(step: dict, hard_constraints, failed_branches) -> dict:
    """编译产物 = 结构化调用列表（data），不是源码。runner 固定可信。"""
    return {
        "step_id": step["step_id"],
        "calls": [
            {"tool": s["tool"], "params": parse_params(s["params"]), "expected_outcome": s["outcome"]}
            for s in step["success_steps"] if s.get("tool")
        ],
        "hard_constraints": hard_constraints,
        "failed_branches": failed_branches,
    }

# 固定可信 runner（不是 LLM 生成，不 eval 源码）
async def ptc_runner(call_list: dict, tool_dispatch: dict):
    """按 call_list 顺序调工具。tool_dispatch 是白名单 {tool_name: tool_callable}。"""
    results = []
    for call in call_list["calls"]:
        tool_name = call["tool"]
        if tool_name not in tool_dispatch:
            raise ValueError(f"tool {tool_name} not in whitelist")  # 白名单校验
        tool_fn = tool_dispatch[tool_name]
        params = call["params"]
        # params 是 dict（parse_params 解析），不是字符串拼接
        if not isinstance(params, dict):
            raise ValueError(f"params must be dict, got {type(params)}")
        result = await tool_fn.ainvoke(params)
        results.append(result)
    return results
```

**关键变化**：
- `success_steps` 的 `params` 必须是 **dict**（结构化），不是字符串。handoff 计划 H1 的 `success_steps` 字段 schema 改 `params: dict`（而非 `str`）。
- runner 是固定可信代码（白名单 dispatch），LLM 文本只作 data 喂入，不 eval。
- 不绕过 AST gate——根本不生成源码，不走 `run_script`/eval。
- `tool_dispatch` 是白名单（只允许 step_tools 里的工具），防注入。

**与 PTC（execute_code）的关系**：不用 execute_code 执行 LLM 生成脚本。用固定 runner 按 call_list 调工具。PTC 工具本身不参与（leaf 子 agent 直接调 runner，不走 execute_code）。或把 runner 注册为一个内部工具。

## 中级修复

### L2 重跑无状态变化 → 删除 L2

L2「重跑 dag」不引入新信息，确定性失败。**删除 L2**：L1（leaf 内 PTC→ReAct）失败 → 直接判定阈值 → L3（降级 TaskFlow）或接受 partial（叶子 step 失败）。

降级链简化为：
```
L0 journal 命中 → 零调用
L1 leaf：PTC → 失败 → ReAct → 成功/失败
   ↓ step 失败（ReAct 也失败）
L2（原 L3）降级 TaskFlow：根 step 失败 / >50% 失败 → TaskFlow 重跑
   成功 step 查 journal 跳过；失败 step TaskFlow retry/judge；结果写回 journal
```

### degrade_to_taskflow 忽略数据依赖 → 传上游结果

```python
async def degrade_to_taskflow(plan_flow_def, journal_store, plan_key, succeeded, variant_input):
    for step in plan_flow_def.steps_in_topo_order():
        cached = await journal_store.get(compute_journal_key(step, variant_input))
        if cached is not None:
            continue  # 成功 step 跳过
        # 失败 step → TaskFlow spawn，传入上游成功结果作 context
        upstream_results = {dep: succeeded[dep] for dep in step.depends_on if dep in succeeded}
        result = await taskflow_spawn_step(
            step,
            context=f"[前驱结果]\n{json.dumps(upstream_results)}\n[变体输入]\n{variant_input}")
        if result.success:
            await journal_store.put(compute_journal_key(step, variant_input), result)
    return taskflow_collect_results(plan_flow_def)
```

### extra_tools 类型混淆 → 按工具名处理

```python
def step_tools(functional_role: str, extra_tool_names: list[str] | None = None) -> list:
    """extra_tool_names 是 list[str]（工具名），不是工具对象。"""
    base = role_base_tools(functional_role)  # list[Tool]
    base_names = {t.name for t in base}
    extra_names = extra_tool_names or []
    # 按名查工具对象（从工具注册表）
    extra = [tool_registry[name] for name in extra_names if name in tool_registry]
    merged = list(base) + [t for t in extra if t.name not in base_names]
    return merged
```

`role_base_tools`/`role_agent_type`/`step_model` 需实现（从 functional_role 的配置查）——标为实现待办，不是假设存在。

### orchestrate 持久化 → 存结构化元数据（已在阻断 1 修复 B 解决）

存 `workflow_meta`（JSON），replay 时 `build_orchestrate(meta, variant_input)` 重新生成。不存闭包/源码/eval。

### knowledge vs journal 关系 → 厘清

| 存储 | 内容 | 更新时机 | 用途 |
|---|---|---|---|
| **plan knowledge**（knowledge 目录） | success_steps / failed_branches / hard_constraints / step 结构 | 首次 TaskFlow 抽取 + 修补抽取合并 | 编译输入（编译 PTC call_list + workflow_meta） |
| **journal**（SqliteWorkflowStore） | 每个 leaf 的成功结果（按 prompt+agent_type+model+schema 哈希） | leaf 成功后 put | 运行时缓存（replay 命中零调用） |

- 重编译 PTC/workflow 用 **knowledge**（编译时）。
- replay 命中用 **journal**（运行时）。
- 修补抽取更新 **knowledge**（合并原 + 修补）；journal 在修补执行时自动 put（leaf 成功）。
- 二者不混：knowledge 是「该怎么做」的步骤知识；journal 是「做过什么」的结果缓存。

### 变体 fingerprint → 定义

variant_input = 当前任务的具体输入文本（用户/调用方传入，如「帮我给项目 X 加 WAL 并发测试」）。fingerprint = variant_input 本身（直接拼进 prompt，进 journal key）。不需单独哈希——prompt 含 variant_input 文本，journal key 自然区分。

### C 场景成本 → 加 breakeven 判定

ldw replay 只在**高 replay 频率**的 plan 上值得：
- knowledge 记录 plan 的 replay 次数（`knowledge(action="read")` 时计数）。
- 只在 replay 次数 ≥ 阈值（如 3 次）的 plan 上编译 ldw workflow。
- 首次/二次 replay 走 TaskFlow（直接跑）；第三次起编译 ldw workflow + journal 缓存。
- 避免低频 plan 的 ldw 开销（fork + 编译 + leaf 注册）> 直接 TaskFlow。

### PTC 失败判定靠 LLM 自觉 → 加硬 gate

不靠 system prompt 软指令。加**硬判定**：
- `execute_code`/runner 返回 error → 硬失败，强制切 ReAct。
- runner 结果经 response_schema 校验 → 不过 → 硬失败，切 ReAct。
- 只有 schema 过但 LLM 判断不充分 → 软切换（靠 prompt，可接受）。

硬 gate 在 leaf wrapper 里（runner 后校验），不依赖 LLM 自觉。

### 并发 replay 同 plan_key → 加锁

同 plan_key 的 replay 串行化（per plan_key 锁）。journal store 的 put 用 SQLite 事务（天然原子）。Roster per replay 实例独立（不共享）。

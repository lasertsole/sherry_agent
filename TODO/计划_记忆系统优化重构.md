# 记忆系统优化重构方案

> **日期**: 2026-11-03
> **目标**: 将 sherry 的记忆系统从「三个扁平 Markdown 文件 + 全量冻结注入 + 无用量追踪」升级为「SQLite 结构化条目 + 渐进式披露 + 用量反馈环 + 语义召回（config 开关）+ 增强整理器」，使其在大规模长期使用中更加优秀耐用。

---

## 一、现状分析

### 1.1 现有架构

sherry 的记忆系统由两层组成：

| 层 | 实现 | 说明 |
|---|---|---|
| 持久记忆 | `workspace/memory/{MEMORY,USER,FACTS}.md` 三个 Markdown 文件 | `MemoryStore` (`agent/tools/memory.py`) 管理，`§` 分隔条目，字符上限 2200/1375/1375 |
| 消息回忆 | `context_engine/` MesMemory SQLite + FTS5 + bge-m3 embedding | 对话级回忆，与持久记忆分离 |

**注入方式**: 三个文件的全量内容在 session 启动时冻结为快照，注入 system prompt。Mid-session 写入落盘但不更新快照（保护 prefix cache）。

**整理机制**: 压缩时 `_nudge_memory` 用 main model fork 读被丢弃的消息切片，通过 `memory` 工具写入条目。Session 删除时两波 salvage。Plan 完成时 plan extraction。无去重、无合并、无矛盾消解。

**已有但闲置的基础设施**:
- `bge-m3` embedding (1024 维) 仅用于 `messages` 表，未覆盖记忆条目
- `bge-reranker-v2-m3` cross-encoder 仅用于 code-intel，未接入 message/memory 召回
- `context_epoch` 表已存在但未用于记忆 staleness 校验

### 1.2 核心问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 容量瓶颈 | 三文件共 ~5000 字符，oldest-first 或 reject-on-overflow | 长期运行丢失重要记忆 |
| 全量注入 | 整个记忆每次都进 system prompt，无相关性过滤 | 浪费 context token，无法扩容 |
| 无用量追踪 | 不知道哪些记忆真正有用 | 无法智能淘汰 |
| 无来源追溯 | 无 origin session / 创建时间 / 修改时间 | 无法审计、无法按新鲜度排序 |
| reranker 闲置 | bge-reranker-v2-m3 仅服务 code-intel | 记忆/message 召回精度不足 |
| 无整理/去重 | curator 只提取不合并 | 记忆退化、矛盾累积 |
| 无 compaction 感知 | 压缩后检索无 epoch 校验 | 可能注入失效上下文 |

### 1.3 四项目对比启示

| 启示来源 | 借鉴点 |
|---|---|
| **codex** | 用量反馈环（usage_count/last_usage → 淘汰排序）；渐进式披露（summary→handbook→raw）；启动时自动两阶段流水线 |
| **ZCode** | originSessionId stamping；semantic-recall 完整实现但 `false` 常量关闭；Dream 4 阶段整理 |
| **omo** | compaction-aware staleness（epoch 校验）；git 版本化；Memorian gate（LLM judge 过滤召回） |
| **claudecode** | typed frontmatter；on-demand MemoryRead 工具 |

## 二、架构决策（已确认）

- **存储**: 纯 SQLite，废弃 Markdown 文件作为主存储；前端提供查看/编辑页面弥补可读性
- **语义召回**: 完整实现但 config 开关控制，默认关闭（ZCode 式渐进上线）

### 路线决策：全量 SQLite vs 双区 Markdown

> **与 `TODO/luanyujia-workbench-refactor-ref.md` 的"记忆双区模式"对齐**

| 路线 | 改动量 | 收益 | 适合场景 |
|---|---|---|---|
| **Route A — 全量 SQLite 迁移**（本计划） | 17 文件，新建 6 文件 | 结构化条目 + 用量追踪 + 语义召回 + 自动整理 + 来源追溯 | 长期大规模使用、多 session 积累大量记忆 |
| **Route B — 双区 Markdown**（luanyujia 评估） | ~3 文件，改 ~20 行 | §₀ 覆盖式交接 + §五 追加式长期，结构化但不改存储 | 记忆量不大、优先低成本 |

**推荐**：先做 Route B（1 天工作量，立即收益），观察记忆膨胀速度。如果 3 个月内
MEMORY.md 频繁触达容量上限且整理质量下降，再做 Route A。本计划保留为 Route A 的
完整设计，Route B 的落地见 `TODO/luanyujia-workbench-refactor-ref.md` 第 3 项。

**如果选择 Route B，以下 Phase 1-6 不执行。如果选择 Route A，Phase 1-3 是 MVP，
Phase 4-6 是进阶，Phase 5 可独立于 Phase 6。**

## 三、Phase 1: SQLite 记忆条目存储 + 迁移

### 3.1 新建 `memory_entries` 表

在 `context_engine/store/db.py::build_schema_v1` 中新增：

```sql
CREATE TABLE IF NOT EXISTS memory_entries (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    target TEXT NOT NULL,               -- 'memory' | 'user' | 'facts'
    content TEXT NOT NULL,              -- 记忆正文
    entry_type TEXT,                    -- 'user' | 'feedback' | 'project' | 'reference' | 'system'
    origin_session TEXT,                -- 创建该条目的 session_id
    created_at INTEGER NOT NULL,        -- epoch ms
    updated_at INTEGER,                 -- 最后修改时间
    last_used INTEGER,                  -- 最后被检索/引用的时间
    usage_count INTEGER NOT NULL DEFAULT 0,
    char_count INTEGER NOT NULL,
    archived INTEGER NOT NULL DEFAULT 0,
    archived_at INTEGER,
    archived_reason TEXT,               -- 'evicted' | 'contradicted' | 'manual' | 'consolidated' | 'superseded'
    compaction_epoch INTEGER DEFAULT 0, -- 创建时的 compaction epoch（staleness 校验）
    embedding BLOB,                     -- bge-m3 向量（lazy 生成）
    embedding_model TEXT,
    embedding_dim INTEGER
);
CREATE INDEX idx_memory_target ON memory_entries(target) WHERE archived = 0;
CREATE INDEX idx_memory_usage ON memory_entries(last_used) WHERE archived = 0;
CREATE INDEX idx_memory_origin ON memory_entries(origin_session);
```

### 3.2 新建 MemoryEntryRepository

**新文件**: `context_engine/store/memory_entry_repository.py`

```python
class MemoryEntryRepository:
    def list_entries(target=None, include_archived=False, sort="created", limit=100, offset=0) -> list[dict]
    def get_entry(id) -> dict | None
    def add_entry(target, content, entry_type=None, origin_session=None) -> dict
    def update_entry(id, content=None, entry_type=None) -> dict    # 更新正文时 embedding 置 NULL
    def archive_entry(id, reason) -> dict                          # 软删除
    def restore_entry(id) -> dict
    def increment_usage(id) -> None                                # usage_count += 1, last_used = now
    def get_entries_by_ids(ids) -> list[dict]
    def total_char_count(target) -> int                            # 按 target 统计未归档条目总字符数
    def prune_unused(max_unused_days, batch_size=200) -> int       # codex 式老化
```

复用现有的 `_SerializedConnection` 和 `get_db()` 基础设施（`context_engine/store/db.py`）。

### 3.3 迁移：Markdown 文件 → SQLite

**新文件**: `context_engine/store/memory_migration.py`

- `migrate_legacy_memory_files() -> int` — 扫描 `workspace/memory/{MEMORY,USER,FACTS}.md`，按 `§` 拆分条目逐条导入
- 每条: `origin_session=None`（遗留）、`created_at` 取文件 mtime、`entry_type` 按 target 推断
- 幂等: `memory_entries` 表已有非归档条目则跳过
- 迁移后原文件重命名为 `*.md.bak`（不删除，人工回退）
- 在 `agent/core.py::init()` 中 `load_from_store()` 调用点之后触发一次性迁移

**部分失败恢复**：
- 迁移函数在单个 SQLite 事务内执行——要么全部导入成功，要么全部回滚
- 如果事务失败：原 `.md` 文件不重命名（保持原状），日志记录错误，下次启动重试
- 如果事务成功但 `.md.bak` 重命名失败（权限/磁盘满）：SQLite 已有数据，下次启动
  检测到 `memory_entries` 非空则跳过迁移（幂等），`.md` 文件保留但不读
- 迁移完成后在 `index_meta_summary`（或 KV）记录 `migration_done=True` 标记

**Prefix cache 确定性保证**：
- `format_for_system_prompt(target)` 从 SQLite 查询活跃条目时，**按 `created_at ASC, id ASC` 排序**
  （和原文件从上到下的顺序一致），保证相同数据 → 相同 prompt → prefix cache 稳定
- 迁移时按文件内 `§` 分隔符顺序导入，`created_at` 取文件 mtime（同一文件的条目 mtime 相同），
  `id` 自增保证顺序——迁移后的 prompt 内容和顺序与原文件一致

### 3.4 重构 MemoryStore

改造 `agent/tools/memory.py::MemoryStore`:

| 方法 | 现状 | 改造后 |
|---|---|---|
| `load_from_disk()` | 从文件读取 + 冻结快照 | 改名 `load_from_store()`，从 SQLite 读取活跃条目生成快照 |
| `add(target, content)` | 写文件 + 容量检查 | `repo.add_entry(...)`，容量检查改为 `repo.total_char_count() + len(content) > limit` |
| `replace(target, old, new)` | 文件子串替换 | 匹配条目 content 子串后 `repo.update_entry(...)` |
| `remove(target, old)` | 文件子串删除 | `repo.archive_entry(id, reason='manual')` |
| `append_entries(new_entries)` | 批量写文件 | 批量 `repo.add_entry(...)`，路由逻辑不变 |
| `format_for_system_prompt(target)` | 返回冻结快照 | 不变（数据源改为 SQLite） |
| `format_live_content(target)` | 读文件 | 从 SQLite 实时查询 |
| `save_to_disk(target)` | 原子写文件 | 废弃，SQLite 写入即持久化 |

文件锁 → 不再需要（SQLite WAL + serialized connection 保证并发安全）。

## 五、Phase 3: 来源追踪（Provenance）

### 5.1 写入时自动戳入 origin_session

所有 `MemoryEntryRepository.add_entry(...)` 调用点传入 `origin_session`:

| 调用点 | session_id 来源 |
|---|---|
| `memory` 工具 (`agent/tools/memory.py`) | `runtime/session/` 获取当前 session_id |
| curator review (`nudges.py::_nudge_memory`) | 被压缩 session 的 session_id |
| session-end salvage | 即将删除的 session_id |
| plan extraction | 当前 session_id |

### 5.2 条目渲染时显示来源

`_render_block` 渲染每条记忆时，正文后追加来源标记（仅当 origin_session 存在时）:

```
§
<记忆正文>
[origin: sess_xxx, created: 2026-11-03, used: 3x]
```

让模型在 system prompt 中看到每条记忆的来源和新鲜度，自行判断可靠性。

## 六、Phase 4: 用量追踪与淘汰

### 6.1 检索时记录用量

**路径 A — memory 工具新增 read 动作**:

```
memory(action="read", target="memory")               → 返回该 target 所有活跃条目
memory(action="read", target="memory", query="关键词") → 子串匹配返回相关条目
```

每次返回的条目调用 `repo.increment_usage(id)`。

**路径 B — 语义召回**（Phase 5）: 语义召回返回的条目也调用 `repo.increment_usage(id)`。

### 6.2 用量驱动的老化淘汰

`MemoryEntryRepository.prune_unused(max_unused_days)`:
- 查询 `archived=0 AND COALESCE(last_used, created_at) < now - max_unused_days*86400000`
- 批量归档（`archived=1, archived_reason='evicted', archived_at=now`），不硬删除
- 在 curator consolidation 流程中调用（Phase 6）

### 6.3 facts target 的 oldest-first 改为 usage-aware

`MemoryStore.add(target="facts")` 溢出时:
- 不再简单归档最旧条目
- 按 `COALESCE(last_used, created_at) ASC, usage_count ASC` 排序，归档最不活跃的
- 所有条目都高使用率则拒绝添加并提示模型

## 七、Phase 5: 语义召回（config 开关，默认关闭）

### 7.1 记忆条目 Embedding 生成

**新文件**: `context_engine/store/memory_embeddings.py`

```python
def index_pending_memory_entries() -> int     # LEFT JOIN 找 embedding IS NULL 的活跃条目，批量 bge-m3
def load_memory_embeddings(target=None) -> list[dict]  # 加载 embedding + content + metadata
```

复用 `context_engine/embeddings/indexer.py` 的 `_get_embed_fn()` 和批量逻辑。触发时机: 语义召回查询前 lazy 生成。

### 7.2 语义召回路径

**新文件**: `context_engine/store/memory_recall.py`

```python
async def semantic_recall(
    query: str,
    target: str | None = None,
    limit: int = 5,
    char_budget: int = 4000,
) -> list[dict]:
```

流程:
1. `index_pending_memory_entries()` 自愈索引
2. `load_memory_embeddings(target)` 加载候选
3. embed query，cosine 排序（复用 `context_engine/embeddings/search.py` 的 numpy 逻辑）
4. 取 top-N（N = limit * 3，给 reranker 留余量）
5. **Reranker 精排**: 调用 `models/reranker_model/core.py` 的 `RerankerProtocol.rank(query, documents, top_k=limit)` — 现有基础设施的关键复用
6. 截断到 char_budget
7. 对返回的每条调用 `repo.increment_usage(id)` — 用量反馈环
8. 返回 `[{id, target, content, entry_type, score, usage_count, created_at}]`

### 7.3 注入路径：双模式

在 `workspace/prompt_builder.py::build_system_prompt` 中，根据 `MEMORY_TOOL["semantic_recall_enabled"]`:

**模式 A — 全量注入（默认，现有行为）**:
- 从 SQLite 读取所有活跃条目，渲染为冻结快照注入 system prompt
- 行为与当前一致，数据源从文件改为 SQLite

**模式 B — 语义召回（开关开启时）**:
- system prompt 中只注入**紧凑索引**: 各 target 条目数 + 最新 N 条（每条仅首行 + usage 标记）
- 新增 reminder source `memory_recall`（注册到 `agent/middlewares/reminder_catalog/sources.py`），priority 88（高于 plan_mode 85），budget = `semantic_recall_char_budget`
- builder 在每 turn 首次 model call 时取最近 user message 作为 query，调用 `semantic_recall`，结果作为 `<system-reminder source="memory_recall">` 注入
- `cooldown_turns = 3`（避免每 turn 都跑 embedding + reranker）
- 只在语义召回开关开启时注册该 source

**Reminder budget 交互评估**：

现有 reminder 总 budget = 30000 字符，8 个 source 竞争（优先级 85→50）。
`memory_recall` 在 priority 88（最高），budget = 4000 字符。

| 场景 | 30000 budget 分配 | memory_recall 占比 |
|---|---|---|
| 全部 source 激活 | plan_mode(85) + todo(80) + taskflow(75) + boulder(70) + continuity(65) + proj_instr(62) + proj_dir(60) + knowledge(50) ≈ 26000 → memory_recall 4000 挤掉 knowledge(50) | 13% |
| plan_mode 关闭 | ~22000 → memory_recall 4000 不挤掉任何 source | 13% |

**结论**：memory_recall 优先级最高，会**挤掉最低优先级的 knowledge_index(50)**。
这是可接受的——语义召回比静态知识索引更相关。如果 knowledge_index 和 memory_recall
都需要，调低 `semantic_recall_char_budget` 到 2000，或调高 knowledge_index 优先级到 55。

**与压缩过滤的交互**：`memory_recall` source 注册时需设
`compress_exclude=True`（默认值；语义召回结果每轮重新派生，压缩后无价值）。
该字段已于 2026-11-03 落地：`ReminderSource.compress_exclude` 默认 True，
`continuity_context` 显式设 False，`_filter_summary_messages` 在构建摘要
prompt 前丢弃被排除的 reminder。

### 7.4 memory 工具增强

当 `semantic_recall_enabled = True` 时新增 action:

```
memory(action="recall", query="...") → 调用 semantic_recall，返回按相关性排序的记忆条目
```

## 八、Phase 6: 增强整理器（Consolidation Curator）

### 8.1 新增 consolidation pass

在 `agent/middlewares/summarization/nudges.py` 的 memory review 流程中，在提取 review 之后追加 consolidation 阶段。

**触发时机与运行模式**：

| 触发源 | 运行模式 | 说明 |
|---|---|---|
| 压缩时（compression-time） | **异步**，不阻塞压缩 | compression 完成后在 NUDGE lane 起 consolidation task；压缩不等它完成。失败 fail-open（记日志，不影响压缩） |
| session-end salvage | 同步，在 salvage 流程内 | session 删除前的两波 salvage 中追加 consolidation，max_turns=5（比压缩时的 15 少，因为 salvage 上下文简单） |
| 前端「立即整理」按钮 | 异步，通过 API 触发 | `POST /memory/consolidate` 返回 task_id，前端轮询状态 |

**与现有 `_nudge_memory` 的关系**：追加而非替代。`_nudge_memory` 先跑（提取新条目），
consolidation 后跑（整理已有条目）。两者共享 NUDGE lane lock，串行执行不并发。

**consolidation agent 构建**:
- 复用 `_create_memory_review_agent` 的 fork 模式（main model, session prompt, nudge-gated tools）
- 新 prompt `_MEMORY_CONSOLIDATION_PROMPT`:
  - Phase 1 审视: 读取当前所有活跃记忆条目（`memory(action="read")`）
  - Phase 2 去重合并: 合并描述同一事实的条目，保留信息最完整版本
  - Phase 3 矛盾消解: 识别矛盾记忆，`replace` 更新或 `remove` 归档过时版本
  - Phase 4 老化清理: 归档 `usage_count=0` 且超 max_unused_days 的条目
  - Phase 5 格式化: 确保每条简洁无冗余
- max turns = 15（比 extraction 的 5 多，比 ZCode Dream 的 50 少）
- 在 NUDGE lane 下运行，与 extraction 共享 lock

**成本控制**：
- consolidation 只在**压缩事件**或**手动触发**时运行，不是每 turn
- 单次 consolidation 的 LLM 调用 ≈ 15 turns × main model，约 $0.05-0.15（取决于条目数）
- 如果条目数 < 10，跳过 LLM 整理，只做系统级老化（`prune_unused`）
- 配置项 `consolidation_min_entries`（默认 10），条目不足时不花 LLM 调用

### 8.2 老化淘汰集成

consolidation pass 中调用 `repo.prune_unused(max_unused_days)`:
- 在 LLM 整理之前先做一轮系统级老化
- LLM 整理时能看到哪些已被老化，避免重复处理

### 8.3 compaction-aware staleness

`MemoryEntryRepository.staleness_check(entry, current_epoch) -> bool`:
- 比较条目的 `compaction_epoch` 与当前 session 的 `context_epoch`
- 条目创建于更早 epoch 且 `last_used` 也早于当前 epoch → 标记 stale
- 语义召回时跳过 stale 条目，或在结果中加 staleness 警告（类 ZCode 48h 警告）
- 全量注入模式下不检查（冻结快照是 session 开始时的状态）

`compaction_epoch` 从 `context_epoch` 表读取当前 session 的 epoch。

## 九、实施顺序与依赖

> **每个 Phase 可独立执行，前序 Phase 验收通过后才开始后序。**
> **每个 Phase 有独立的回归测试门控。**

### 独立执行单元

| 单元 | 包含 | 前置依赖 | 可独立 ship？ | 回归门控 |
|---|---|---|---|---|
| **MVP-1** | Phase 1 (SQLite+迁移) + Phase 3 (Provenance) + API 兼容层 | 无 | ✅ — 存储从 Markdown 切到 SQLite，行为透明 | `test_memory_store.py` + `test_memory_injection_guard.py` 全绿 |
| **MVP-2** | Phase 2 (前端管理页面) | MVP-1 的 API | ✅ — 前端从文件视图改为 CRUD 列表 | `MemoryPanel.integration.test.ts` |
| **进阶-1** | Phase 4 (用量追踪+淘汰) | MVP-1 | ✅ — 新增 read action + 老化逻辑 | `test_memory_usage_tracking.py` |
| **进阶-2** | Phase 6 (增强整理器) | 进阶-1（用量数据） | ✅ — 新增 consolidation pass | `test_memory_consolidation.py` |
| **增强** | Phase 5 (语义召回) | MVP-1 + 进阶-1 | ✅ — config 开关默认关闭 | `test_memory_recall.py` |

```
MVP-1 (Phase 1+3+API)          ← 基础，无外部依赖
    ↓
MVP-2 (Phase 2 前端)            ← 依赖 MVP-1 API
    ↓ (可并行)

    ↓

    ↓ (可并行)
增强 (Phase 5 语义召回)          ← 依赖 MVP-1 + 进阶-1
```

**MVP = MVP-1 + MVP-2**（结构化存储 + 前端管理）
**进阶 = 进阶-1 + 进阶-2**（智能淘汰 + 整理）

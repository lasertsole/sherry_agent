**ZCode 的对照做法**（本次核验，供语义对齐）：执行器里两处打点——`startTime`（handler 执行前）与 `totalStartedAt`（入口），分别得到 **`durationMs`（handler 主执行段）** 与 **`totalMs`（含 registry/校验/Hook/权限等待/序列化/PostToolUse 的用户感知全程）**；权限等待单独记 `permissionWaitMs`；handler 可自报细分（如 `write` 的 `fsReadMs/fsWriteMs`）；结果对象带 `startedAt/completedAt`，并落 `tool_usage` 表（含 `time_to_first_output_ms/exit_code/output_bytes/...`），日志与事件各带一份。TUI 用 `formatDuration`（`<1s→ms`、`<10s→x.x s`、否则整秒）显示——但只用在网络请求行上。

**ZCode 的时钟选择（本次核验，与本计划相反且更弱）**：**全部打点用 `Date.now()` 墙钟**，`durationMs` / `totalMs` 都是裸减法。全仓 408 处 `Date.now` vs 12 处 `performance.now`，墙钟是压倒性选择。四处减法里**只有一处加了负值防护**——`permission-flow.ts:295` 的 `Math.max(0, Math.round(...))`；`call-runner.ts:451/494/561` 三处都没有。因此 **NTP 校时或用户改系统时间时，`durationMs` 可为负值并原样落库**。那 12 处 `performance.now()` 用法反而**全部**带 `Math.max(0, ...)`（monotonic 本就不会负，钳制是习惯）——缺口精确地落在「用墙钟算差值又不钳制」这三处。唯一把 monotonic 转墙钟的地方是 `turn.ts:185` 的 `performance.timeOrigin + performance.now()`，但只用于 turn 级 trace，工具级打点没用它。本计划取 monotonic 差值正是为了避开这个已实证的缺口（见 §1.3）。

**ZCode 的耗时归属边界（本次核验，与「只做前端」的假设相反）**：ZCode **后端完整、前端零展示**——数据真的落了 SQLite，却没有任何界面显示它。

### 1.3 设计约束

- **时钟：两个时钟各司其职，不许用一个兼两职**。这是本计划与 ZCode 的**唯一实质分歧**，也是最容易被后来者"顺手简化"掉的地方，因此写成硬约束：

  | 用途 | 时钟 | 存法 | 理由 |
  | --- | --- | --- | --- |
  | `duration_ms`（花了多久） | `time.monotonic()` 差值 | 整数毫秒 | 单调只增不减，**恒 ≥ 0**，不受 NTP 校时 / 用户改系统时间 / 夏令时影响 |
  | `started_at`（什么时候开始） | `time.time()` 墙钟 | 整数毫秒（或 ISO 文本，与 `messages.created_at` 同口径） | 单调时钟读出来是「进程启动后 8500ms」这种无意义数字，**无法落库当时间戳**；而墙钟可能被调时，只能用于「给人看 / 与消息行排序对齐」，**绝不参与耗时差值** |

  两者**不可互换**：墙钟算差值可能为负（ZCode 的实证缺陷），单调值不能当日期。**禁止**用一个 `time.time()` 同时充当 `started_at` 与 duration 起点——那正是 ZCode 出负值的根因。若将来要加 `started_at` 列，必须同时引入 `time.monotonic()` 打点，两个值分别落两个列。

  > 顺带说明 JS 侧的 `performance.timeOrigin + performance.now()`（ZCode `turn.ts:185` 用法）：它等于「进程启动那一刻的墙钟快照 + 单调增量」，既单调又不丢日历语义。但它保证单调而**不保证与真实日历一致**——进程运行期间若NTP 把墙钟拨了 5 分钟，之后所有推导值永久偏 5 分钟。故适合日志时间戳，**不适合**需要跨进程对齐的权威列。Sherry 是长驻进程且要与 `messages.created_at` 对齐，因此不用这个手法。

- **负值一律钳 0**：即使改用 monotonic 也不放弃钳制——`max(0, ...)` 是零成本的防御，让下游不必判断符号（ZCode 只在一处钳、另三处不钳的不一致正是缺陷来源）。
- **HITL 拒绝不产生耗时**：被拒绝的调用没有执行段（`tool_result` 帧来自"未执行"路径），显示为未知而不是 0——避免"0ms 的工具"这种假信息。
- **并发会话隔离**：开始时间必须按 `[session_id][tool_call_id]` 存放（现有 `_pending_args` 的 bare-id 约定已经这么做，直接沿用）。
- **状态键契约**：若选择把开始时间放进 `state_register_mem`（便于跨帧读取），必须按仓库约定在 `runtime/session/state_keys.py` 的 StateKey 契约中登记（有契约测试守着）。
- **单调时钟的跨进程性质**：`time.monotonic()` 的基准是**未定义的**（CPython 中通常是进程启动，但也可能是系统启动）。因此**绝不跨进程传递或落库单调原值**——只落它与起点相减后的差值。跨进程要传的是 `duration_ms` 这个已经算好的整数。

## 2. 技术方案

### 2.1 计时点（R1）— `server/service/stream_dispatch.py`

与 `_pending_args` 同构，新增一个按会话隔离的开始时间表，在 `tool_start` 落点、`tool_result` 取点：

```python
# 键 = [bare session id][tool_call_id]，值 = time.monotonic()
_tool_started_at: dict[str, dict[str, float]] = {}

def _note_tool_start(self, tool_name: str) -> None:   # 现有副作用点
    ...                                                # 原有逻辑（转录注记）
    # 新增：记录开始时间（tool_call_id 从当次 chunk 的 meta 取，与 args 同一来源）

def _consume_tool_duration(session_id: str, tool_id: str) -> int | None:
    started = _tool_started_at.get(session_id, {}).pop(tool_id, None)
    return None if started is None else max(0, int((time.monotonic() - started) * 1000))
```

`tool_result` 帧增加一个字段（**加法**，老客户端忽略未知字段）：

```python
yield {
    "type": "tool_result",
    "content": _normalize_text(tm.content),
    "tool_id": tool_id,
    "tool_name": name,
    "args": args,
    "error": bool(getattr(tm, "status", None) == "error"),
    "duration_ms": _consume_tool_duration(self.session_id, tool_id),   # 新增
}
```

### 2.2 落库（R3）— `context_engine` 消息表 + 写入路径

- 迁移：`messages` 表新增 `tool_duration_ms INTEGER`（走既有 `_migrations` 机制，旧库补列为 NULL）。
- 写入：工具行在 `context_engine/store/core.py` 构造（`tool_name/tool_status` 附近，:253-255）时带上耗时。耗时来源取 **`message_persistence.wrap_tool_call` 的计时**（该中间件就是"工具返回那一刻"的落点，见其模块 docstring 的 Timing contract），把它写进 `ToolMessage.additional_kwargs["tool_duration_ms"]` 再随行落库——这样权威值在后端，流式帧只是同一个数的一份拷贝。

> 两条路要一致：帧里的值与落库的值都来自同一个 `_consume_tool_duration`/中间件计时；若两者不一致（例如补帧路径），以落库值为准。

**`started_at` 列：v1 不加，但预留口径**。当前 `messages` 表已有 `created_at`，且它由 MesMemory 的落库时刻给出，语义上已是「该行写入时刻」——与工具真正开始的时刻相差一次落库延迟（毫秒级，本用途不可感知）。因此 **v1 不新增 `tool_started_at` 列**，避免为一个不可感知的差异付出一列的迁移与兼容成本。

若将来慢工具分析真的需要精确起点（例如要按「工具开始时刻」而非「消息落库时刻」做并发窗口分析），再加列，**并且必须同时**：

1. 在 `tool_start` 落点用 `time.time()` 记 `started_at`（墙钟，与 `created_at` 同为可读时间戳）；
2. `duration_ms` 继续由 `time.monotonic()` 差值产出，**两者不共用起点**；
3. 在 AGENTS.md 明确标注两列的时钟来源不同，防止后来者拿 `started_at` 去重算 duration。

### 2.3 前端读取（R2/R3/R4/R7/R8）— 客户端

**核验结论（本次）**：客户端**只有一个工具卡渲染点**，思考流与对话流共用它。因此不存在「两处都要改」的重复接线问题。

| 内容 | 组件 | 渲染位置 | 是否渲染工具调用 |
| --- | --- | --- | --- |
| 思考/推理文本 | `ChatThinkingBlock.vue` | `ChatBox.vue:102-108` | **否**（只出 reasoning 文字） |
| 工具调用 | `ChatToolCard.vue` | `ChatBox.vue:110-120` | **是，且全客户端仅此一处** |

`ChatBox.vue:110-120` 把整个 `message: MessageItem` 传给卡片，因此卡片一旦消费该字段，两条流同时生效。**真正要防的是「将来新增第二个渲染点」**——加一条守卫测试（见 §4「渲染点唯一性」）。

**R8：归行修复 —— ✅ 已完成，本次先行落地**

修复前的匹配是位置启发式：`findSameTurnToolIdx`（`use-stream-chunks.ts:104-111`）从数组尾部反扫、返回**本轮最后一个** TOOL 行，`tool_end`/`tool_result` 都用它定位，`tool_result` 另有「倒扫任意 `running`/`failed` 行」的兜底（本是为 HITL resume 跨轮补位而加的）。**在并发工具调用下这是错的**，且**已可执行复现**（非理论推断）：

```
A.start → B.start → A.end
  findSameTurnToolIdx 指向 B  →  B 被标成 done，A 永远停在 running
  A 的结果文本被写进 B 的行
```

实测（修复前，断言正确行为）：`['running','done']`（期望 `['done','running']`）、A 的 `toolResult` 为 `undefined`、行上无 `toolId`。可达性由后端帧序保证——一条 assistant 消息的 N 个 `tool_start` 在该消息自身流式期发完（`stream_dispatch.py:566`，messages 模式），`tool_end`/`tool_result` 才在执行后发（updates 模式 `:393-406`），且 `repeat_flag` 在每个新 `tool_id` 到达时复位（`:518`），故该顺序是**必然**而非罕见竞态。

| 缺口 | 修复前 | 状态 |

## 5. 风险与回滚

- **时钟语义（唯一高危项）**：必须用 `monotonic` 算差值，否则 NTP 校时 / 用户改系统时间会给出负值或跳变；负值统一钳 0。**这不是理论风险——ZCode 已实证**：`call-runner.ts:451/494/561` 三处 `Date.now()` 裸减法均无钳制（仅 `permission-flow.ts:295` 有），故其 `duration_ms` 在系统时间回拨时会为负并原样落库。**ZCode 是反例，本计划不得回归到它的做法。**
- **被"顺手简化"成单时钟**：本计划最可能被后来者破坏的地方。典型误改是「反正只要一个时间，把 `time.monotonic()` 换成 `time.time()` 省事」——这会让耗时重新变得可为负，且因为测试通常不模拟时钟拨回而**静默通过**。§4 的「格式化」「计时正确性」用例须显式注入一个**回拨的墙钟序列**并断言结果仍 ≥ 0（见 §4 新增行）。
- **中断的调用**：`tool_start` 后流中断（用户停止/网络断）没有 `tool_result`——开始时间表会留残留项；按会话上限清理（或 `tool_end`/会话结束时丢弃该会话的整张表）。
- **补帧路径**：resume/HITL 拒绝的 `tool_result` 来自另一条路径，没有开始时间 → 字段为 `null`（前端不显示），不要伪造 0。
- **展示抖动**：`tool_end` 立刻到达时，运行中计时可能只闪一下——接受（与 ZCode 的完成值一致），不需要最小显示时长。
- **回滚**：帧字段与列都是加法，回滚=前端不读、后端不写，无需数据迁移回退。

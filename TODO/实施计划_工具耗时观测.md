# Sherry Agent 工具耗时观测 — 实施计划

> **状态**: 待实施
> **创建日期**: 2026-10-04
> **依据**: 本次对 ZCode 源码的核验（`/home/honor/Desktop/project/ZCode/apps/zcode-cli`，工具执行器打点 + 分层语义 + 用量表）与 Sherry 现状核验（工具调用帧、消息落库、工具卡）
> **目标**: 每次工具调用都有可观测的执行耗时——流式期间实时可见、完成后落在工具卡上、随消息持久化（历史回放也在）
> **非目标**: 审批等待 / 排队时长的单独分层、独立的 `tool_usage` 明细表、"可暂停 deadline"超时重构

---

## 1. 需求概述

### 1.1 现状（核验证据）

| 能力 | Sherry 现状 | 位置 |
| --- | --- | --- |
| 工具开始/结束信号 | 已有：`tool_start`（带 args）→ `tool_result`（带 `tool_id/tool_name/args/error`）→ `tool_end` | `server/service/stream_dispatch.py:238,393-406` |
| 每次调用的开始时间 | **未记录**（`_pending_args` 只暂存参数；`state_register_mem` 只存 `current_tool_name/current_tool_id`） | `server/service/stream_dispatch.py:49-56` |
| 耗时字段 | **无**（帧里没有、消息行没有、工具卡不显示） | `client/app/composables/use-stream-chunks.ts:13-29` |
| 工具行落库字段 | `tool_calls` / `tool_status` / `tool_name`，**无耗时列** | `context_engine/store/core.py:253-255` |
| 工具卡展示 | 运行中只有 spinner + `runningLabel`；完成后无耗时 | `client/app/components/chat/ChatToolCard.vue:13,46-48` |
| 可复用的显示件 | `formatElapsed(startedAtMs, nowMs)`（mm:ss，TasksPanel 的 1s ticker 在用） | `client/app/common/utils.ts:19` |

**ZCode 的对照做法**（本次核验，供语义对齐）：执行器里两处打点——`startTime`（handler 执行前）与 `totalStartedAt`（入口），分别得到 **`durationMs`（handler 主执行段）** 与 **`totalMs`（含 registry/校验/Hook/权限等待/序列化/PostToolUse 的用户感知全程）**；权限等待单独记 `permissionWaitMs`；handler 可自报细分（如 `write` 的 `fsReadMs/fsWriteMs`）；结果对象带 `startedAt/completedAt`，并落 `tool_usage` 表（含 `time_to_first_output_ms/exit_code/output_bytes/...`），日志与事件各带一份。TUI 用 `formatDuration`（`<1s→ms`、`<10s→x.x s`、否则整秒）显示——但只用在网络请求行上。

### 1.2 需求条目

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | **执行段耗时** | 每次工具调用记录"从开始执行到返回结果"的墙钟耗时；**审批等待与排队不计入**（与 ZCode 的 `durationMs` 同义，避免把"等人工批准"读成"工具慢"） |
| R2 | **流式可见** | `tool_result` 帧带上 `duration_ms`，前端工具卡完成后立即显示（无需等历史回放） |
| R3 | **持久化** | 工具消息行新增 `tool_duration_ms` 列，历史加载后同样显示（刷新/换设备一致） |
| R4 | **运行中计时** | 工具卡在 `running` 状态显示实时递增计时（复用已有的 1s ticker 惯例），完成时定格为最终值 |
| R5 | **展示一致** | 一个格式化函数：`<1s → "850ms"`、`<10s → "1.2s"`、`≥10s → "12s"`（与 ZCode `formatDuration` 同款规则），四语下无需翻译数字，仅 tooltip/aria 文案走 i18n |
| R6 | **不改变对外契约** | 工具调用/结果本身的语义、帧类型、消息 schema 只做**加法**（新字段可缺省）；旧库（无该列）读回为 `NULL` 不报错，前端按"未知"处理 |

### 1.3 设计约束

- **时钟**：耗时用 `time.monotonic()` 差值（不受系统时间调整影响）；落库仍存整数毫秒。
- **HITL 拒绝不产生耗时**：被拒绝的调用没有执行段（`tool_result` 帧来自"未执行"路径），显示为未知而不是 0——避免"0ms 的工具"这种假信息。
- **并发会话隔离**：开始时间必须按 `[session_id][tool_call_id]` 存放（现有 `_pending_args` 的 bare-id 约定已经这么做，直接沿用）。
- **状态键契约**：若选择把开始时间放进 `state_register_mem`（便于跨帧读取），必须按仓库约定在 `runtime/session/state_keys.py` 的 StateKey 契约中登记（有契约测试守着）。

## 2. 技术方案

### 2.1 计时点（R1）— `server/service/stream_dispatch.py`

与 `_pending_args` 同构，新增一个按会话隔离的开始时间表，在 `tool_start` 落点、`tool_result` 取点：

```python
# 键 = [bare session id][tool_call_id]，值 = time.monotonic()
_tool_started_at: dict[str, dict[str, float]] = {}

def _note_tool_start(self, tool_name: str) -> None:   # 现有副作用点
    ...                                                # 原有逻辑（转录注记）
    # 新增：记录开始时间（tool_call_id 从当次 chunk 的 meta 取，与 args 同一来源）

def _consume_tool_duration(session_id: str, tool_id: str) -> int | None:
    started = _tool_started_at.get(session_id, {}).pop(tool_id, None)
    return None if started is None else max(0, int((time.monotonic() - started) * 1000))
```

`tool_result` 帧增加一个字段（**加法**，老客户端忽略未知字段）：

```python
yield {
    "type": "tool_result",
    "content": _normalize_text(tm.content),
    "tool_id": tool_id,
    "tool_name": name,
    "args": args,
    "error": bool(getattr(tm, "status", None) == "error"),
    "duration_ms": _consume_tool_duration(self.session_id, tool_id),   # 新增
}
```

### 2.2 落库（R3）— `context_engine` 消息表 + 写入路径

- 迁移：`messages` 表新增 `tool_duration_ms INTEGER`（走既有 `_migrations` 机制，旧库补列为 NULL）。
- 写入：工具行在 `context_engine/store/core.py` 构造（`tool_name/tool_status` 附近，:253-255）时带上耗时。耗时来源取 **`message_persistence.wrap_tool_call` 的计时**（该中间件就是"工具返回那一刻"的落点，见其模块 docstring 的 Timing contract），把它写进 `ToolMessage.additional_kwargs["tool_duration_ms"]` 再随行落库——这样权威值在后端，流式帧只是同一个数的一份拷贝。

> 两条路要一致：帧里的值与落库的值都来自同一个 `_consume_tool_duration`/中间件计时；若两者不一致（例如补帧路径），以落库值为准。

### 2.3 前端读取（R2/R3/R4）— 客户端

- `use-stream-chunks.ts`：`tool_result` 的 meta 增加 `duration_ms` → 写入 `MessageItem.toolDurationMs`（历史映射 `toMessageItems` 同步该字段）。
- `ChatToolCard.vue`：
  - `running`：显示 `formatElapsed(startedAtMs, now)`（1s ticker，仅在 running 时运行——与 TasksPanel 同款惯例）；
  - 完成：显示 `formatToolDuration(durationMs)`；
  - 未知（HITL 拒绝/老数据）：不显示，而不是显示 0。
- `formatToolDuration`：放 `client/app/common/utils.ts`，规则与 R5 一致；数字本身语言无关。

### 2.4 明确不做 / 备选

| 项 | 结论 | 理由 |
| --- | --- | --- |
| `totalMs`（含审批等待/排队）分层 | **备选** | ZCode 的价值在"区分慢与等"。Sherry 的等待发生在 HITL 挂起与输入排队，二者已有独立可见性（审批卡、排队徽标）；要做时再加 `permission_wait_ms` 列 |
| `tool_usage` 明细表 | **备选** | 现无"慢工具分析"需求；真要上，形态照 ZCode：一行一次调用，含 `started_at/completed_at/duration_ms/time_to_first_output_ms/exit_code/output_bytes/status` |
| 可暂停 deadline | **不做** | ZCode 的 `ToolDeadline` 是为"进程级准入闸门"服务的（排队不计超时）；Sherry 的 `tools_timeouts` 是固定墙钟超时，改动面与收益都不同，单列议题 |
| handler 自报细分耗时 | **备选** | 如 `patch_file` 的 `fsReadMs/fsWriteMs`、`terminal` 的 spawn/等待拆分；需要时用 `additional_kwargs` 同款加法扩展 |

## 4. 测试计划

| 用例 | 断言 |
| --- | --- |
| 计时正确性 | 注入 `time.monotonic` 序列 → `duration_ms` 精确等于差值（毫秒取整、负值钳 0） |
| 并发隔离 | 两个 session 各自的 `tool_call_id` 交错 start/result → 各自拿到自己的耗时 |
| 缺失路径 | `tool_id` 为空 / 只有 `tool_start` 没有 `tool_result`（中断）→ 字段为 `null`，不抛异常 |
| 落库往返 | 写入后按 `(session_id, turn_num)` 读出 `tool_duration_ms`；旧库列缺失时读取兜底 |
| 前端 | running 时计时递增（fake timers 推进 3s → 显示 00:03），完成后定格；未知不显示 |
| 格式化 | 850 → "850ms"、1234 → "1.2s"、12345 → "12s"、null → 不渲染 |
| 回归 | 既有 `tool_start/tool_result/tool_end` 帧消费方（`use-stream-chunks` 及其测试）不受新增字段影响 |

## 5. 风险与回滚

- **时钟语义**：必须用 `monotonic`，否则 NTP 校时会给出负值或跳变；负值统一钳 0。
- **中断的调用**：`tool_start` 后流中断（用户停止/网络断）没有 `tool_result`——开始时间表会留残留项；按会话上限清理（或 `tool_end`/会话结束时丢弃该会话的整张表）。
- **补帧路径**：resume/HITL 拒绝的 `tool_result` 来自另一条路径，没有开始时间 → 字段为 `null`（前端不显示），不要伪造 0。
- **展示抖动**：`tool_end` 立刻到达时，运行中计时可能只闪一下——接受（与 ZCode 的完成值一致），不需要最小显示时长。
- **回滚**：帧字段与列都是加法，回滚=前端不读、后端不写，无需数据迁移回退。

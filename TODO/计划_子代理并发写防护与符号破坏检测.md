# 子代理并发写防护与符号破坏检测

> 结论先行:
> 1. **同文件前后修改:文件工具路径有真防护**(锁 + 读许可 + revision CAS + 隔离合并 CAS);
>    **shell 写路径(terminal/python_repl)完全绕过这一切**,只留沙箱。
> 2. **符号破坏:改名有"弱防护"(仅隔离合并时的公告,且只认函数/方法/类);
>    同名函数改参数、改返回值、模块级变量改名**零防护**;**没有任何机制反查谁在 import**,
>    公告只是提示父代理,纯 import 用户的证据也不会被失效。
> 3. **无限触发/死循环:当前接线不存在无界自动循环**——每条自动链都有一次性/幂等/上限;
>    真正的软循环是"父代理看到公告后行为性反复重派",只有资源上限兜底。另有两个
>    一次性写盲区(回放门的 formatter 直写、shell 写)。
> 4. P0 四项对着符号破坏与一次性写盲区(检测/验证,不产生参与式协调开销);P1 三项引入
>    前置协调(opt-in / 按并发子代理数门控 / 默认 advisory)——见 §四。

## 一、现状:同文件前后修改

### 1.1 并发(两个子代理同时写)

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 进程内 | `path_write_lock` 每规范路径互斥,读共享 | `agent/tools/pub_base/path_lock.py:129` |
| 跨进程 | `flock` LOCK_EX/LOCK_SH,锁文件 inode 永不删除 | `agent/tools/pub_base/file_lock.py:85` |
| 批内调度 | SafeToolNode 按资源分组:同文件组按模型顺序串行,非文件不安全工具全批屏障 | `agent/safe_tool_node.py`(AGENTS.md「Tool Parallel Safety」) |
| 隔离合并 | 每父根一把 `merge-<sha>.lock` flock,60s 超时,两个子代理同时合并串行 | `agent/tools/subagent/isolation/merge.py:48,87,184` |

**判定:并发同文件写有防护。** 锁只取单一路径、无嵌套获取 → 无循环等待 → 无死锁;
所有等待都有超时。

### 1.2 串行(B 在 A 之后覆盖同一文件)

- **读后写许可(write license)**:覆盖要求本会话"完整读过当前修订"或"自己写的";
  许可按 session 记录(write_file.py:96-118)。B 拿着 A 写之前的旧许可覆盖 → 原子写
  的 `expected_revision` CAS 失配 → `StaleWriteError` 拒绝,B 必须重读(write_file.py:333-366)。
- **原子写**:临时文件 + 原子替换,无半写状态。
- **隔离合并 CAS**:父树该路径仍等于子代理开工快照的 revision 才落;否则记 CONFLICT、
  父树不动、工作区保留供检视,且 manifest 被消费(SNAPSHOT→MERGED 改名,
  merge.py:203-213)——**同一次运行不可能被合并两次**;新建路径只写入"空位",
  父树已出现同名文件即拒绝(merge.py:254-259)。

**判定:串行前后修改有防护**(B 无法盲覆 A 的改动;隔离模式下 A 的父树改动与 B 的
合并冲突会被显式报告而非静默丢失)。

### 1.3 盲区(必须知道)

1. **隔离默认关闭**:`sessions_spawn(isolation=False)` 是默认(sessions_spawn.py 的
   Field 默认 False)。默认形态是共享同一工作树,只有 1.1/1.2 的锁与许可。
2. **shell 写完全绕过**:terminal / python_repl / ptc 写文件不经文件工具——无许可、
   无 CAS、无 path_lock;证据记账的 `invalidates_evidence` 装饰器只挂在
   write_file/patch_file(evidence_recorder.py:114;write_file.py:164;patch_file.py:136),
   **shell 写既不被记账也不会失效别人的证据**(它的 evidence 行 `modified_files` 恒空,
   别人改了文件它也不会被标 stale)。
3. **回放子进程直写**:finish 回放门允许 `black`/`prettier`/`ruff` 等可写 formatter
   (regression_gate.py:43-74 白名单),`_run` 直接 subprocess——**绕过许可体系**,
   一次性覆盖并发编辑(不会循环,见三)。

## 二、现状:符号破坏(函数名/参数/返回值/变量名 → 顺着 import 破坏别人)

场景:A 改 `utils.py` 的 `foo`(改名/改签名),B 的 `b.py` `from utils import foo`。

### 2.1 现有覆盖(经代码核实)

- **改名/增/删符号——仅隔离合并时有公告**:`symbol_diff.py`(tree-sitter)在合并落盘
  前对每文件算 `InterfaceDelta`(added/removed/renamed;改名=同 (kind, parent) 组内
  Levenshtein≤2 配对,subagent_isolation.py 的 `interface_diff_rename_levenshtein=2`),
  渲染进完成公告的 "**Interface changes** (renamed/added/removed symbols — another
  subagent may still call an OLD name)" 区(workspace_merge.py:132-163,cap 10 文件/
  每类 20 条)。
- **路径级证据失效**:A 的 write_file/patch_file → `mark_evidence_stale` → 自己 + 跨会话
  广播(evidence_ledger.py:457 `mark_stale_for_path_all_sessions`,cap 扫 200 会话);
  隔离合并的 applied/created/deleted 路径同样广播(workspace_merge.py:57-68)。
  但匹配键是**路径**:命中条件是对方 evidence 行的 `modified_files`(或 legacy 命令串)
  **包含被写路径**。
- **兜底重验**:flow finish 回放门把该 flow 记录过的 passed 验证命令重放一遍
  (regression_gate.py:317;白名单验证器、无 shell、cap 10、60s/条、一次),失败记
  `broken`;TaskFlow Gate C 见 FAIL/stale/broken 拒绝 finish。如果 B 的验证命令恰好
  执行到那个 import(如 pytest 跑了 b.py),破坏会在 finish 时被确认。

### 2.2 缺口(直接回答"有无保护措施")

1. **同名签名变化完全不可见**:符号身份是 `(kind, name, parent)`(symbol_diff.py:137-139)。
   `foo(a, b)` → `foo(a, b, *, timeout)` 或返回值语义变化,**合并零冲突、公告零条目**。
2. **变量名不可见**:提取器的 kind 只有 function/method/class(extract.py:304,559),
   模块级常量/变量改名(常被 `from utils import MAX_N` 引用)不进 diff。
3. **无反向 import 索引**:公告只说"foo 改名了",**没有任何机制指出谁在 import foo**;
   是否检查全凭父代理自觉。
4. **纯 import 用户收不到失效**:B 只是 import `utils.foo`、从未改过/验证过 utils.py →
   B 的 evidence 不含该路径 → 跨会话广播不命中 → B 的"通过"证据保持绿灯。
5. **非隔离运行连公告都没有**:symbol_diff 只在隔离合并路径上运行;默认共享树模式下,
   A 直接 write_file 改名,除了路径级 stale,没有任何符号层信号。
6. **公告是 advisory**:不阻断、不自动重验、不自动通知正在跑的 B(合并公告只到父代理)。
7. **证据行只带 session key**(无 flow/图键),Gate 只能靠"新鲜度"兜(已知缺口,
   见记忆 evidence-ledger-key-binding-gap)。

**判定:改名=弱防护(仅隔离、仅公告、靠父代理反应);参数/返回值/变量名=零防护;
import 面的自动定位与失效=没有。** 现有体系是"路径世界",问题发生在"符号世界"。

## 三、死循环审查(逐链路)

| 自动链路 | 触发→动作 | 界限 | 判定 |
| --- | --- | --- | --- |
| 证据 stale 标记 | 文件写/合并 → 追加 stale 行(**派生态**:读取时才折算) | 只标记,**不触发任何执行**;事件行本身不会再触发广播 | 无环 |
| finish 回放门 | flow finish → 重放 ≤10 条白名单命令 → 追加 broken/unmark | 每 flow finish **一次**;追加的事件不触发回放;flow finish 是终态不重启 | 无环 |
| announce→合并 | 子代理完成 → 合并一次 | manifest 消费/工作区丢弃(merge.py:203-213)+ announce 幂等(announce/idempotency.py)→ **不可能二次合并** | 无环 |
| announce→auto_resume | 完成 → `_try_auto_resume_taskflow`(delivery.py:385)→ resume 步骤 → auto_dispatch 解锁的 newly-ready 步骤 | 步骤按 DAG 推进(环在 progress 层被标记);步数/spawn 天花板、每会话 spawn≤50、run_timeout 600-7200s | 有界 |
| continuation 门 | 回合结束注入续跑指令 | `max_continuation_turns=15` + 会话闩,只有未被注入的真实用户回合重置;busy 应答不计入(2026-10-15 修复,否则 stop 丢失) | 有界 |
| CompletionJudge / StepJudge / LLMRetry / InvalidToolCallRepair | 各种自动重试 | goal_max_turns / max_retries / 11 次尝试+熔断 / resend_max_retries | 有界 |
| 文件锁 / 合并锁 | 阻塞等待 | 单锁不嵌套(无循环等待);全部带超时(合并 60s) | 无死锁 |
| 跨会话 stale 广播 | 写 → 给 ≤200 个会话各追加一行 | 广播只写行;接收方无自动动作 | 无环 |

**判定:现有接线没有无限触发 bug、没有死循环。** 每条自动化要么一次性+幂等,要么显式上限。
两个真实的边角(非循环、但值得知道):

1. **回放门的 formatter 直写**:`black foo.py`(不带 `--check`)作为被记录的验证命令,
   会在回放时**绕过许可直写文件**——一次性、能覆盖并发编辑,且写完不计账。
2. **行为性软循环**:父代理读到"Interface changes"公告 → 重派修复步骤 → 新合并又产生
   接口变化 → 新公告……语义上无检测,只有资源上限(spawn≤50、步数、超时)兜底。P0-3
   (合并即定向重验)要消的浪费来源。

## 四、实现计划

**同文件写(文件工具路径)已有防护;符号破坏(参数/返回值/变量名、import 面)是真空;
自动链路无死循环但有两个一次性写盲区(shell 写不记账、回放门 formatter 直写)。**
P0 对着符号破坏与一次性写盲区,P1 引入前置协调,P2 观望。

- **P0 四项不受影响**(它们是检测与验证,不需要每个工人额外交互一块共享黑板);
- **P1 的参与式协调(CLAIM 板、发现板、mid-turn 通知)一律 opt-in / 按并发子代理数门控 /
  默认 advisory**,并各带"关掉之后行为与今天完全一致"的开关。

### P0-1 symbol_diff v2:签名面 + 模块级变量(关掉最大盲区)

- **现状**:`symbol_diff.py:137` 符号身份 = `(kind, name, parent)`,kind 只有
  function/method/class——**同名函数改参数/改返回值、模块级变量改名,合并公告完全看不见**。
- **改动**:`extract.py` 的 SymbolDef 增加 `signature`(参数名序列+是否仅关键字、参数个数、
  返回注记有无,不比较类型细节,只比"形状字符串");diff 时同名同 parent 但 signature 变化
  → 新增 `changed: list[SignatureChange]`;tree-sitter 捕获模块级赋值(kind=`variable`,
  仅顶层,函数体内的局部变量不进面)。`InterfaceDelta` 增字段;`_interface_lines`
  渲染 `changed: foo(a, b) → foo(a, b, *, timeout)`。
- **边界**:失败一律 fail-open(现状已是);大小上限沿用 `interface_diff_max_file_bytes`。
- **测试**:`tests/agent/tools/code_intel/` 增签名变化/模块变量改名用例;merge 公告渲染快照。

### P0-2 反向 import 索引:公告点名受影响文件(把 advisory 变得可执行)

- **现状**:合并公告只说"renamed foo→bar",**没有任何机制指出谁在 import foo**;
  跨会话失效广播按路径交集匹配(`evidence_ledger.py:457`),纯 import 用户(没改过、
  没验证过该文件)收不到 stale 行。
- **改动**:sherry 已有 code-intel 索引(`.sherry/codeintel/index.db`,`indexer.py:67`
  的 `import_edges` 表带 `idx_imports_name` 索引)。在 `workspace_merge.py` 的公告阶段:
  对 `interface_changes` 里的每个 removed/renamed/changed 符号,用索引反查引用文件
  (`SELECT importer FROM import_edges WHERE imported_name=?`),在 Interface changes 区
  追加 `affected importers: path3.py, path4.ts`;同时把这些引用文件作为路径调用
  `mark_evidence_stale_for_paths`(writer=父会话)——**让"纯 import 用户"的证据也失效**,
  使 finish 回放门/Gate C 能兜住。**索引缺失时 fail-open 不做反查**(不造第二条 ast 扫描
  路径——索引已在 `.sherry/codeintel/index.db`,缺索引就跳过,不维护两套反查逻辑)。
- **边界**:反查只读、有 cap、fail-open;不阻断合并(维持 CAS 只管文本冲突的定位)。
- **测试**:双 worktree 集成用例——A 改名、B 引用,B 的 evidence 变 stale,finish 回放
  产生 broken。

### P0-3 合并即定向重验

- **现状**:重验只在 `taskflow_finish` 的回放门(regression_gate.py,一次性、cap 10、
  白名单),合并当下不跑任何东西。
- **改动**:隔离合并产生了 interface_changes 且反查到受影响 importers 时,立即对这些
  importer 关联的已记录 passed 命令跑一轮**定向**回放(复用 `_safe_argv`/`_run`,
  独立小 cap=5、开关默认关),结果 broken/unmark 直接进账本。即"接口变化合并 ⇒ 马上
  知道有没有打断同伴",不等 flow finish。
- **防循环红线**:重验只消费账本行、只追加事件,**事件追加绝不触发新的重验或新的合并**
  (维持"账本读取/写入不触发执行"的现有不变量);每个 run 的合并只发生一次(manifest
  消费,merge.py:212)。
- **测试**:合并→broken 出现→auto_resume 把失败带回父代理。

### P0-4 shell 写记账:命令后 shadow-git diff → record_file_edit

- **现状(经代码核实)**:`terminal`/`python_repl` 执行前**已经**调 `ensure_checkpoint`
  (terminal.py:541 / python_repl.py:286,同步异步都拍),shadow git 快照把项目树存进
  `.sherry/shadow-git`——**回滚安全网已有**。真正的缺口是记账与失效传播:shell 写后没人调
  `record_file_edit`/`mark_evidence_stale`(装饰器只挂 write_file/patch_file,
  evidence_recorder.py:119),会话的 `changed_paths` 不含 shell 写的路径 → 它的 evidence 行
  `modified_files` 恒空 → 跨会话 stale 广播(按 `modified_files` 路径匹配)不命中 → 纯 import
  用户的证据永远不被标 stale。回放门的 `black`/`prettier`(不带 `--check`)作为被记录验证命令,
  finish 回放时还会**绕过许可直写文件**(regression_gate.py:43-72 白名单)。
- **改动**:命令跑完后,shadow store 已持有「命令前」状态
  (`ensure_checkpoint` 拍的),工作树是「命令后」状态——一次 `run_shadow(root,
  ["diff","--name-only",SHADOW_REF])` 给出命令期间变更路径(cap 200,fail-open 返回空),
  逐条调 `record_file_edit(path, session_id)`(已有的 `mark_evidence_stale` + 跨会话广播在
  里面,与 write_file/patch_file 走同一条管子)。shadow_git.py 加一个 `diff_changed_paths`
  helper(~15 行);terminal/python_repl 各在 `_record_verification` 后加 ~5 行调用。**不用
  mtime 扫描**:shadow store 已有命令前状态(不重复造轮子),内容比对不被 `touch -d` 骗,
  复用 `run_shadow` 的 env/GIT_DIR 设置。
- **边界**:(1) `ensure_checkpoint` 每会话每回合 dedup——若同回合 write_file 已拍快照,
  terminal 的快照是 no-op,diff 比的是「回合开始 vs 命令后」,含 write_file 已记过的路径;
  重复 stale 行无害,第一版可不管(要干净就 diff 结果减去 `changed_paths` 已有项)。
  (2) `python_repl` 的 restricted builtins 禁了 `open`/`__import__`,但类内省逃逸
  (`().__class__.__base__.__subclasses__()` 找到 `os`)仍可能写——shadow diff 看工作树
  实际变更,不管怎么写的,照样捕获。(3) `run_in_background` 的命令在工具返回时还在写——
  mtime-diff 在返回点会漏,shadow diff 挂在 watcher 退出回调(terminal.py:679
  `start_watcher`)即可。
- **独立小修复(可先做)**:regression_gate `_safe_argv`(line 97)对 `black`/`prettier`/
  `ruff format` 强制要求 argv 含 `--check`/`--diff`,否则返回 `None`(跳过回放,记 skipped)。
  ~5 行,与记账补丁完全独立。
- **不要做**:给 shell 写加 path_lock(写路径无法从命令字符串静态推断,
  `python -c "open(...)"` 看不出目标);建 mtime 扫描子系统(shadow store 已有前态,重复且
  被 touch 骗);上 fanotify/FSEvents(需特权、平台差异大、复杂度远超威胁模型)。
- **测试**:`sed -i` 后账本出现该路径 + 跨会话 stale 命中纯 import 用户;背景任务退出后 diff
  出文件;`python_repl` 类内省写文件被捕获;`black foo.py`(无 `--check`)作为证据命令不被回放。

### P1-1 CLAIM 认领板(写前声明,防患于写前)

- 每项目一张 append-only claims 表(复用 `BaseSQLiteRepository` 三件套套路),新工具
  `claim_scope(paths[], note)` + 完成时自动释放;`write_file`/`patch_file` 在目标路径与
  **其他活跃会话**的 claim 重叠时,结果里附一行提醒(**永远 advisory,不做拒绝路径**——
  拒绝路径会让一次 write_file 的判定变成 claim→许可→CAS 三层叠加,且 claim 过期 TTL/
  并发 claim 仲裁的复杂度不值得;advisory 提醒已能让父代理反应)。
- 与现有件的关系:这是锁之上的**意图层**(锁管字节,CAS 管版本,claim 管语义);对齐
  WorkspaceNotice 的"通知注入人类消息"手法,不动中间件链。
- **防循环**:claim 检查是纯读,不自动发消息、不自动 spawn;提醒每回合至多一次。
- **测试**:双会话并发 claim 同文件;claim 过期(TTL)自动失效。

### P1-2 发现板查询面(FAIL/FACT 跨子代理可读)

- 把合并公告从自由文本升级为结构化条目(files/idea/evidence/interface),连同子代理的
  `FAIL`(试过不行)与 `FACT`(已确认)写进一张 per-project 发现表;新只读工具
  `peers_findings(query)`(AND/OR 语义)给**子代理**用——现在兄弟之间只有父代理转述,
  让同伴直接复用发现,省的是每个子代理的重复试错预算。
- **防循环**:只读查询;写入只发生在 announce/merge 既有钩子内。
- **前缀缓存红线**:发现板内容**绝不写进 system prompt**——system prompt 只持稳定内容
  (persona + memory + skills index),发现板是 live 数据(每有新 FAIL/FACT/PATCH_SUMMARY
  即变),写进 prompt 会让整个前缀缓存失效。不沿用任何"渲染进 prompt"的设计。
  落地方式:(1) `peers_findings(query)` 只读工具——子代理主动查询,不自动注入;
  (2) 如需自动提示,走 DynamicReminderMiddleware 的 reminder 消息(末尾追加,历史前缀不变,
  缓存可命中稳定部分)。

## 五、防循环设计红线(所有新增件必须遵守)

1. **事件幂等**:一切广播/注入带唯一事件 id,重复投递被 announce idempotency 同款机制吞掉;
2. **账本只标记不执行**:唯一允许的自动执行仍是"一次性、白名单、有 cap"的回放(现状
   regression_gate,新增 P0-3 同规格);
3. **注入上限**:mid-turn 通知每会话每回合 ≤1 条,且只由文件写触发;
4. **锁不嵌套**:任何新逻辑不得在持有一个路径锁时再取另一个(维持无死锁论证);
5. **资源上限兜底**:行为性循环(父代理反复重派)由 max_total_spawns_per_session=50、
   step 天花板、run_timeout_seconds 兜底——这是现有最后防线,新件不得绕过。

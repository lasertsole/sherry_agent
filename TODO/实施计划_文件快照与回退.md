**ZCode 对照（本次核验）**：写前快照是**每次 Write/Edit 调用**存一份改前全文（实测 `fileCount` 恒为 1）；`snapshotRef == diffRef` 是**同一个** artifact，内含 `beforeContent` + `afterContent` + `structuredPatch` **三份冗余**；回退时**整文件覆盖**（`structuredPatch` 只用来推导 afterContent 做陈旧检测，不参与还原）；新建文件靠 `existedBefore = originalFile !== null` 判定删除。实测 4 个会话目录最大一个 753 文件 / 16MB。**无保留策略**（`retention` 枚举声明了但 store 从不读，storage catalog 还标 `cleanability: "none"`）。两套引擎并存：新的有 plan 时 sha256 CAS + journal 逆序补偿，旧的全无保护。`branchGeneration` fencing **只拦迟到通知/子 agent 消息，不拦文件写**。

**OMO 有三样可直接借鉴的东西**：

1. **冲突降级语义**（`isolation-core/src/merge/index.ts:20-23`）：`apply: false` 时保留全部 artifacts 且**不动父树**。这是「诚实」与「谎报成功」的分界，本计划 §2.4 采纳为第二降级层。
2. **proven-dead 锁身份**（`memory-core/src/locks/`）：`{pid, process_start, hostname, nonce}`（`lock-record.ts:6-14`），`kill(pid,0)` 的 `ESRCH`/`EPERM` 区分死/活（`process-identity.ts:116-126`），`link()` 原子发布（`acquire.ts:135-156`），nonce 匹配才 unlink（`:329-339`），**从不按年龄抢锁**。本计划 §2.5 的 GC 采纳 pid + `process_start` 身份判定，见 R9。
3. **fencing 语义先例（已随设计修正失效）**：thread mailbox 的 `message_seq` 单调序列 + `expected_turn_id` CAS（`omo-senpi/.../thread/mailbox.ts:129-135`）与 reader 的内容 `revision` → `cursor_stale`（`thread/reader.ts:184-200,322-328`）曾作为原 §2.6 rewind 栅栏的参照；rewind 弃用后**没有任何代码采用这套语义**，此条仅存为调研记录。

**OMO 已持久化的前置数据（省掉一半工作量）**：`hashline-edit-diff-enhancer/hook.ts:84-90` 已把 `filediff = {file, path, before, after, additions, deletions}` 写进 tool part 元数据，按 `sessionID:callID` 索引（`tool-metadata-store/store.ts:28`）。即**「改前内容」已在为 diff 渲染流入会话存储**——本计划的 per-turn manifest 是延长其生命周期与保留策略，不是从零造。

### 1.2 需求条目

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | **写前快照** | `write_file` 三个分支与 `patch_file` 写入前，把目标文件旧内容按**内容寻址**落盘（`<sha256>.blob`）；不存在则记 `existed_before=0` 不建 blob。快照为**原始字节**，不假设 UTF-8 |
| R2 | **捕获点在临界区内、写入之前** | 复用各工具已有的 `read_bytes_no_follow`（同 fd `fstat`，`:91-109`）取旧字节与指纹——`patch_file` 本来就读了，**零额外读**；`write_file` 非 append 分支新增一次读（先 `lstat`，文件不存在则完全不读） |
| R3 | **归因到具体工具调用** | 快照行必须带 `tool_call_id`，否则无法回答「第 N 轮改了哪些文件」。用 `Annotated[str, InjectedToolCallId]`（`langchain_core.tools` / `langchain.tools` 均导出，langgraph 侧只有 `InjectedState`/`InjectedStore`/`InjectedToolArg`）。**实施第一步须先用最小用例验证该注解在本仓 langchain 1.3.9 / langgraph 1.2.5 组合下确实被注入**（现有代码只用过 `InjectedState`）；不成立则退到 middleware `wrap_tool_call` 归因 |
| R4 | **陈旧拒绝** | 每行同时记 `after_revision`（写后 `file_revision`）与 `after_sha256`（**由已持有的待写字节算出，零额外 I/O**）。回退时先比 `after_revision` 快速通道，再退到 `sha256(当前字节)` 兜底；任一文件不匹配 → **整批拒绝**并逐文件报告原因（沿用 ZCode `canApply` 的诚实语义） |
| R5 | **新建文件回退 = 删除** | 直接依据快照的 `existed_before`，**不**从工具返回值里的字符串推断——顺带修掉 ZCode 的缺陷：`Edit` 用 `old_string:""` 创建文件时 `originalFile` 为 `""`，被 `!== null` 判为「原本存在」，回退留下 0 字节文件而非删除 |
| R6 | **回退工具** | `file_changes_revert(paths=[], to_tool_call_id="", dry_run=False)`：按路径回退到最近一次快照，或回退到指定工具调用之前的全部改动（每路径取范围内**最早**一条快照 = 恢复到该路径最初状态）。始终返回完整 plan（动作 + 逐文件结果 + 拒绝原因） |
| R7 | **一次性、不做 redo** | 成功回退后删除对应快照行与 blob（同一事务），使二次回退自然失败。**不做 redo/roll-forward**（与 ZCode 一致：其 `chat.changeSummary.reapply` i18n key 全仓无引用，是死字符串） |
| R8 | **失败不阻塞写入** | 快照捕获任何异常一律 `logger.warning` 后**继续写入**（fail-open）。agent 写文件是主路径，快照是增强 |
| R9 | **保留期 + 磁盘 GC** | 内容寻址天然去重；再叠加每会话 `max_bytes` / `max_files` / `retention_days` 三重上限，按 `captured_at` LRU 清。**Sherry 无磁盘 GC 先例，自建**：仿 `start_blacklist_cleanup` 的 daemon 线程形态，在 `server/__main__.py:195` 同一装配点注册。**清理判据取「年龄 + 占用身份」双条件**（见 R13） |
| R10 | **回退公告**（原「对话 rewind」，已弃用） | 回退**不改动对话**：成功后向会话图状态追加一条 `<revert>user had revert editing …</revert>` AIMessage（`graph.aupdate_state`，与「项目目录已切换」通知同一机制），持久化层把它镜像进消息库，agent 下一轮自然读到。成功才追加；失败只 warning，绝不让回退本身失败 |
| R11 | **推送与前端入口** | 新增 `file_changes_updated` WS 帧（照抄 `progress_push.py:86` 范式）+ `server/trigger/core.py` 的 `file_changes_refresh_processor` 供重连取快照；新增 Pinia store；`ChatBox.vue` 在 `ChatCopyButton` 旁挂载撤销 chip + 两步确认对话框（先预览逐文件计划，再确认破坏性操作） |

| R14 | **拒绝时给可执行的恢复路径** | 抄 OMO `isolation-core/src/merge/index.ts:20-23` 的诚实语义。陈旧拒绝**不止于**返回 `external_modified`：若被改文件位于某个 git 工作树内，plan 阶段额外计算「以快照前内容为 theirs、以当前内容为 ours」的三方合并可行性，并产出 `git apply --3way` 命令 + 冲突文件列表交给用户手工收尾，**磁盘零变更**。整批拒绝仍是默认（无 `force`），此为**补充信息而非替代**——Sherry 不自动执行合并 |
| R15 | **存储语义显式选择** | OMO 的两个后端语义相反且各自有代价：opencode 后端**可变**（`patchPart`/`deletePart` 走 HTTP，`shared/opencode-http-api.ts:88-137`；甚至直接 `UPDATE message SET data = json_set(...)`，`plugin/ultrawork-db-model-override.ts:80-82`），senpi 后端**append-only JSONL**（`omo-senpi/.../thread/reader.ts:3-6`）。本计划取 **append-only**：`context_engine` 消息永不删除或原地改写（回退公告也只是**追加**一条），快照行只插入/消费。执行中这条纪律的最终形态更强：连「隐藏」都不做，历史原样保留 |

### 1.3 设计约束

- **单进程假设**：所有 agent（主/子/嵌套）在同一 server 进程内，工具 `_core` 是同步代码、由 `asyncio.to_thread` 调度，临界区内不得 await —— 快照落盘是同步 I/O，符合约束。
- **临界区预算**：`file_write_lock` 的跨进程超时是 10s（`file_lock.py:53`）。内容寻址 + `O_EXCL` 使「blob 已存在」时**零写入**，重复写同一文件不增加临界区耗时。
- **快照不落在用户项目里**：blob 与索引都放 `SESSIONS_DIR` / `src/data`，遵循既有「锁文件不散落」的纪律（`file_lock.py:11-25`）。
- **不绕过安全边界**：快照只对已经通过 `PathGuard` / `resolve_workspace_path` / `resolve_external_path`（HITL）解析成功的路径采集；外部路径审批语义不变。
- **config 层依赖自由**：`config/features/**` 不得 import `agent/`、`server/`、`models/`（import-linter 强制），新配置块必须零依赖。
- **回退不改动对话**（设计修正后的硬约束）：回退只还原文件并**追加**一条公告，不隐藏、不删除、不重排任何消息；因此不需要轮次边界校验，也不存在「在途工具调用与 rewind 竞态」这一类问题。
- **project dir 会漂移**：`session_workspace_root(session_id)` 可在轮次边界切换（park/promote），故快照行**同时存绝对路径与捕获时的 root**，回退按记录 root 解释，避免用新 root 重新解析旧路径。

### 2.3 捕获钩子（R1/R2/R3/R8）— `agent/tools/file_tools/snapshot.py`（新增）

```python
@dataclass(slots=True)
class Capture:
    """一次写入前的旧内容捕获结果，落库前不得跨临界区使用。"""
    path: Path
    root: Path
    existed_before: bool
    before_size: int
    before_revision: str
    blob_sha256: str | None


def capture_pre_write(resolved: Path, root: Path) -> Capture:
    """在 file_write_lock 临界区内、写入之前调用。缺失文件不读内容，只记 existed_before=0。"""
    try:
        before_revision = file_revision(resolved)
    except OSError:
        before_revision = "absent"
    if before_revision == "absent":
        return Capture(resolved, root, False, 0, before_revision, None)
    raw, _stat = read_bytes_no_follow(resolved)      # 同 fd fstat，与 CAS 口径一致
    return Capture(resolved, root, True, len(raw), before_revision, hashlib.sha256(raw).hexdigest())


def finalize(capture: Capture, session_id: str, tool_call_id: str, written: bytes) -> None:
    """写入成功后记账。after_sha256 取自待写字节——零额外 I/O，这是比 ZCode 更省的关键点。"""
    store_blob(capture, written)                    # 仅记录旧内容；新内容不进快照
    snapshot_store.insert(
        session_id=session_id,
        path=str(capture.path),
        root=str(capture.root),
        blob_sha256=capture.blob_sha256,
        before_size=capture.before_size,
        before_revision=capture.before_revision,
        after_revision=file_revision(capture.path),
        after_sha256=hashlib.sha256(written).hexdigest(),
        existed_before=int(capture.existed_before),
        tool_call_id=tool_call_id,
        captured_at=time.time(),
    )
```

**插入点**（两处，都在 `file_write_lock` 内）：

- `patch_file.py`：`_core` 已在 `:167` 读出 `read_raw` 与 `read_stat`。把 `capture` 从这次读构造（**不重复读**），落库放在 `:248` `mark_evidence_stale` 附近。
- `write_file.py`：`:107` 进入临界区后、`:111` 分支之前，先 `file_revision(resolved)` 判存在性；非 append 且存在 → `read_bytes_no_follow` 一次构造 `capture`；append 与 `.py`+append 分支同样捕获（append 的旧内容就是回退目标）。落库放在 `:142` 附近。

**失败处理（R8）**：`capture_pre_write` / `finalize` / `store_blob` 全部包在 `try/except Exception` 里 `logger.warning` 后放行；写入失败时已存的 blob 是无索引孤儿，由 GC 回收（内容寻址使其无害）。

### 2.4 回退工具（R4/R5/R6/R7/R14）— `agent/tools/file_tools/revert.py`（新增）

注册：`@tool("file_changes_revert")` + `build_file_changes_revert_tool()`，加入 `_MAIN_TOOLS_BUILDERS`（`agent/tools/__init__.py:41-60`）。参数 schema 沿用 `ReadFileInput`（`read_file.py:24-39`）的 `SessionId` 写法并追加 `ToolCallId`。

```python

    session_id: SessionId = ""
    tool_call_id: ToolCallId = ""
    paths: list[str] = []          # 空 = 该 scope 内全部有快照的路径
    to_tool_call_id: str = ""      # 非空 = 回退到该调用之前（含）的全部改动
    dry_run: bool = False
```

**计划阶段**（纯读，与 ZCode 的 plan-then-apply 同构）：

1. 按 `(session_id, paths?, to_tool_call_id 之前的时间边界)` 取行；`to_tool_call_id` 非空时先解析出它的 `captured_at` 作为上界。
2. 每条路径**取范围内 `captured_at` 最小的一行**（恢复到该路径最初的旧内容），而不是最新一行。
3. 逐文件判安全性：

| 磁盘现状 | 动作 | 说明 |
| --- | --- | --- |
| `file_revision == after_revision` | 允许 | 快速通道，零读 |
| 否则 `sha256(read_bytes_no_follow) == after_sha256` | 允许 | 兜底通道（`hash_guard_max_bytes` 内才做） |
| `existed_before == 0` 且文件已不存在 | 允许 | 目标状态已达成，幂等通过 |
| 文件已不存在（`existed_before == 1`） | `missing` → 拒绝 | 已被外部删除，不擅自重建 |
| 都不匹配 | `external_modified` → 拒绝 | 不覆盖别人的改动 |
| blob 缺失 / 行已过期 | `snapshot_expired` → 拒绝 | 如实报「快照已过期」，不静默跳过 |

4. **任一文件不安全 → 整批拒绝**（`safe == len(rows)` 才 apply），逐文件返回原因。这是 ZCode `canApply: safeFiles.length > 0 && unsafeFiles.length === 0` 的语义，且**默认无 `force`**：宁可让用户重跑，也不要一个「部分覆盖了别人改动」的结果。
5. `dry_run=True` 时只返回 plan。

**应用阶段**：按 `delete` / `restore` 执行；`restore` 走 `atomic_write_text_no_follow`（沿用既有原子写与软链拒绝），`delete` 用 `missing_ok=True`。先写一份 journal（`SESSIONS_DIR/<sid>/file_snapshots/last_journal.json`）再改。

**部分失败的取舍（R7 相关）**：v1 **不做**向前补偿。原因是 ZCode 的补偿依赖永久保存 `afterContent`，代价是磁盘双份常驻；我们只存 `after_sha256`，无法反向恢复。改为：journal 记录已完成项，异常时**如实返回逐文件结果**（哪些已还原、哪些未动），并保留未消费的行让用户可以重试。这是刻意取舍，不是遗漏。

**拒绝时的降级链（R14，本次对标 OMO 后新增）**：单纯「整批拒绝 + 报 `external_modified`」不够——ZCode 的失败模式是**静默覆盖用户的并行改动然后报告「已回滚」**，而纯拒绝虽然不破坏，但只告诉用户「不行」，不给他路。分三层：

| 层 | 触发 | 磁盘 | 产出 |
| --- | --- | --- | --- |
| L1 直接回退 | 全部行安全 | 改 | 逐文件 `restored` / `deleted` |
| L2 **整批拒绝**（默认终局） | 任一行不匹配 | **零变更** | 逐文件拒绝原因 + （若在 git 工作树内）三方合并可行性 + `git apply --3way` 命令 + 冲突文件列表 |
| L3 手工收尾 | 用户自己执行 L2 给的命令 | 用户控制 | 不在本工具职责内 |

L2 的合并可行性检查**只读**，用两条命令，且**各自的安全标志是强制的**（缺一个就退化为写操作）：

| 命令 | 强制标志 | 为什么 | 局限 |
| --- | --- | --- | --- |
| `git merge-file -p <当前> <快照前> <其他>` | **`-p` 必带** | `-p` 输出到 stdout、**不落盘**；不带 `-p` 时 git 会把合并结果**写回第一个文件**（= 改动用户工作树，正是本层禁止的） | 纯文本三方合并，不理解 git 的 rename/mode 变更；对二进制文件无效 |
| `git apply --3way --check <patch>` | **`--check` 必带** | `--check` 只校验不落盘 | `--3way` 要求「快照前内容」在对象库里存在；未提交过的文件会失败（`repository lacks the necessary blob`） |

两者都只作用于 **plan 阶段的临时目录副本**，输入是三份临时文件（当前内容 / 快照前内容 / 用户后续编辑），不是工作树里的真实文件。**本工具永不自动执行合并**——自动三方合并的失败模式比整文件覆盖更难预测。这一层是纯增量信息，不改变「默认无 `force`」的立场。

**先试 `merge-file -p`，失败再降级为纯提示**：`merge-file` 不依赖对象库，对「未提交过的文件」也能给出可行性结论；`apply --3way --check` 只在前者不可用（如需要理解 rename）时作为补充，且其失败**只影响提示文案**，不得让 L2 变成错误信息或额外拒绝。两条命令都不可用时（L1‑L2 层无 git、非文本文件、超时）→ 只返回原始拒绝原因 + 建议命令，**不报错**。

**为什么 ZCode 模式在 Sherry 会更糟**：ZCode 的 `originalFile !== null` 判据把 `old_string:""` 创建的文件误判为「原本存在」（见 R5），回退留下 0 字节文件；而它又没有任何陈旧检测，所以「agent 写完 → 用户改同一文件 → 用户点撤销」这条最常见的路径上，ZCode 会**用旧内容盖掉用户的改动并报告成功**。本计划 L1 的两道 CAS（R4）+ L2 的诚实降级就是为了堵这两条。

**幂等（R7）**：全部成功后，在**同一事务**内删除这些行并把对应 blob 标为待 GC。删除后二次回退因无行而返回「无可回退内容」，天然不可 redo。

### 2.5 磁盘 GC（R9/R13）

新增 `start_file_snapshot_gc(interval_seconds)`，形态照抄 `auth_service.start_blacklist_cleanup`（`server/service/auth_service.py:388-406`）：daemon 线程、每 tick 一个短命 `asyncio.run`、`time.sleep` 间隔、宽 `except` 绝不致命。在 `server/__main__.py:195` 同一装配点与 `auth_service.start_blacklist_cleanup()` 一并注册。

每轮按顺序：① 删 `captured_at < now - retention_days` 的行与其 blob；② 若行数超 `max_files_per_session`，按 `captured_at` 升序删到限额；③ 字节数超 `max_bytes_per_session` 同法；④ 扫无行引用的孤儿 blob。单轮删除数受 `gc_batch_limit` 限制，长事务会拖慢 SQLite。

**删除判据是双条件，不是纯年龄（R13）**：①～③ 循环里对每个候选行先做**占用身份判定**，四种情形互斥（对应 `snapshot_owner_state` 的四态）：

| # | 探测结果 | 判定 | 动作 |
| --- | --- | --- | --- |
| 1 | `os.kill(pid, 0)` 抛 **`ESRCH`** | 该 pid 上**没有任何进程** → 持有者已死 | **可删** |
| 2 | `kill(pid, 0)` **成功** 且当前 `process_start` **与记录一致** | 持有者**活着且正在使用** | **跳过，无论多旧** |
| 3 | `kill(pid, 0)` **成功** 但当前 `process_start` **与记录不符** | **pid 被新进程复用**（原持有者已死） | **可删** |
| 4 | `kill(pid, 0)` 抛 **`EPERM`** | 进程存在但非本用户 → **活着**（可能读不到 `/proc`） | **跳过**（不当作「未知」） |
| — | 判不出（`hostname` 不符的跨主机行、平台读不到 start） | `unknown` | 年龄超 `orphan_grace_days` 才删 |

**两个必须写清的实现陷阱**：

- **`ESRCH` 分支不做 `process_start` 比对**。`ESRCH` 的含义就是「该 pid 无对应进程」，此时 `/proc/<pid>/stat` **不存在**，拿不到可比对的值。若写成「抛 `ESRCH` **且** start 身份一致 → 确认死亡」，这个条件**永远为假**，该分支变成死代码，判据静默退化成「从不删」。**pid 复用（情形 3）的前提是 `kill(pid, 0)` 成功、但进程换了人**——`ESRCH` 时根本谈不上「复用」。
- **`EPERM` 不等于「未知」**。它证明进程**存在**（只是 uid 不同），因此按「活着」跳过。若归入 unknown，短寿命但属于其他用户的进程会在 `orphan_grace_days` 后被误删，而它可能仍在写文件。

抄 OMO 的 proven-dead 语义（`locks/acquire.ts:191-200`）：**死只在有证据时成立**，不按年龄推断。这一条是纯年龄 LRU 的必要修正——否则一次长轮次进行到第 6 小时时，它自己两小时前的快照会被 GC 掉，回退随即返回 `snapshot_expired`。

已知竞态（写进风险章节）：GC 与 revert 并发时，被 GC 掉的行会让 revert 在 plan 阶段读到更少的目标——表现为「少还原了文件」，而非错误还原。

## 5. 风险与回滚

- **快照捕获拖慢写入**：每次写入多一次读（`write_file`）+ 一次 blob 写。缓解：内容寻址命中即零写、文件不存在零读、`enabled` 可关。若实测 hot path 受损，把 `finalize` 的落库挪到 `after_model` 批量做（代价是崩溃时丢最后一批快照）。
- **临界区变长 vs 10s 锁超时**：`finalize` 含一次 SQLite 写。内容寻址使重复写不增加耗时，但首次写大文件会拉长临界区；超时是 `FileBusyError` 而非数据损坏，可接受。
- **磁盘增长**：内容寻址 + 三重限额已封顶，但**上限之内**仍是持续占用。`max_bytes_per_session=64MB` × 会话数是理论上界；若嫌大先降 `retention_days`。
- **`tool_call_id` 注入不成立**：`InjectedToolCallId` 在本仓从未使用过（langgraph 侧只导出 `InjectedState`/`InjectedStore`/`InjectedToolArg`；`InjectedToolCallId` 在 `langchain_core.tools` 与 `langchain.tools` 均可见）。阶段一必须先验证，不成立则退到 `wrap_tool_call` 归因——**那时 `tool_call_id` 的可得性取决于消息落库时序**，需要额外评估，故列为阶段一的门禁。
- **部分回退无补偿**：见 §2.4。表现为「少还原」，用户重试即可；不会错误覆盖。
- **GC 与 revert 竞态**：同上，最坏少还原。
- **公告的时序**：公告写进图状态后由持久化层在下一轮刷进消息库，所以**聊天历史里它会晚一轮出现**（模型的可见性是即时的）。若要求聊天里也立即出现，需显式补一次库写入——当前未做，属已知取舍。
- **回滚**：五个阶段互相独立，可单独 revert。关 `FILE_SNAPSHOT["enabled"]=False` 即让工具回到原行为（快照不再写；已存的 blob 由 GC 清）。索引表与 blob 是纯新增产物，回滚后是孤儿数据，不影响任何既有路径。
- **`clear_session` 漏清索引行**：阶段五补 `delete_snapshots_by_session`；在此之前删除会话会在 `file-snapshots.db` 留下孤儿行（不影响正确性，只占空间）。
- **身份判定依赖平台 API（R13）**：`/proc/<pid>/stat` 是 Linux 专有；macOS 需 `ps -o lstart=`，Windows 需 `CreationFileTime`。若某平台取不到 start 身份，该平台的 GC 退化为「纯年龄 + `orphan_grace_days`」，并接受「长轮次快照可能被清理」的已知行为——**不要**为此引入 psutil 依赖，`/proc` + `ps` + 明确降级已足够。
- **R14 的三方合并检查可能给出误导性「可行」**：L2 只做 `merge-file -p` / `--3way --check` 这类探测，它通过不等于用户执行后无冲突（工作树在检查与执行之间会变；且 `merge-file` 不理解 rename/mode、`--3way` 要求前像在对象库内）。**文案必须写明「基于检查时刻的工作树状态」**，不得承诺结果。探测失败也不得升级为拒绝理由（见 §2.4 降级链末句）。
- **R15 append-only 的代价**：每次回退会多出一条公告行（一条消息换一次「agent 知情」，可接受）；被消费前的快照行由 `retention_days` + GC 清理。任何情况下都**不要**改成原地删除或改写消息——那会与既有的「消息不删」纪律和并发读冲突。

| 问题 | ZCode | OMO | 本计划 |
| --- | --- | --- | --- |
| 主 agent 原地写能否回退 | 能（整文件覆盖） | **不能**（只覆盖 delegated task） | 能，且带两道 CAS |
| 并行编辑被覆盖 | **静默覆盖并报成功** | 结构上不可能（父树不被触碰） | 检测到即整批拒绝 + 给可执行恢复命令 |

三个模型里**只有本计划同时覆盖「主 agent 原地写」与「并行编辑不被静默覆盖」**——ZCode 有前者无后者，OMO 有后者但靠「换一个工作树」这个 Sherry 不能接受的代价实现。

## 0. ZCode 行为 — 两条 PDF 路径

ZCode 并不总是将 PDF 转为图片。路径取决于模型的 `supportsPdf` 能力（由 `modalities.input` 包含 `"pdf"` 推导）：

### 路径 1：原生 PDF（模型 `supportsPdf == true`，无页面范围）

PDF 二进制数据作为原生内容块发送 — provider 内部处理渲染：

- **Anthropic**：`{type:"document", source:{type:"base64", media_type:"application/pdf", data:<base64>}, title:...}`（偏移 4162368）
- **OpenAI Responses API**：`{type:"file", file:{filename:..., file_data:"data:application/pdf;base64,..."}}`（偏移 749480）

无需 `pdftoppm`，无需图片转换，无需 `prepareForModel`。PDF 字节直接进入消息。

### 路径 2：PDF→图片（模型不支持 PDF，或请求了页面范围）

使用 `pdfDocumentPort.renderPages`（偏移 9870569）：
1. `getPageCount` 启动 `pdfinfo` 统计页数
2. `renderPages` 启动 `pdftoppm`，参数为 `["-jpeg", "-r", "100", "-f", firstPage, "-l", lastPage, filePath, "<tmp>/page"]` — 100 DPI，JPEG，120 秒超时
3. 每张渲染出的 JPEG → `prepareForModel` 压缩（相同预算：G1/i4/Cde）
4. 每张压缩后的页面 → `data:image/jpeg;base64,...` `image_url` 块

### 路径选择逻辑

```
if supportsPdf AND no page range → Path 1 (native PDF block)
elif supportsPdf AND page range AND supportsImages → Path 2 (render to images)
elif supportsPdf AND page range AND NOT supportsImages → error PDF_PAGES_IMAGES_UNSUPPORTED
elif NOT supportsPdf AND supportsImages → Path 2 (render to images, fallback)
else → cannot handle PDF
```

**错误分类**（ZCode `Eu` 码）：
- `PDF_TOO_LARGE`（>20MB）、`PDF_TOO_MANY_PAGES`（>10 页强制使用页面范围）、`PDF_PAGE_RANGE_TOO_LARGE`（每次请求 >20 页）、`PDF_PAGES_IMAGES_UNSUPPORTED`（支持 PDF 但不支持图片 + 页面范围）、`PDF_PASSWORD_PROTECTED`、`PDF_INVALID`、`PDF_TIMEOUT`（120 秒）、`PDF_IO_ERROR`、`PDF_PROCESS_FAILED`

## 1. Sherry 当前状态

**Sherry 完全没有服务端 PDF 处理。** PDF 仅在客户端处理：
- `FileViewerPanel.vue` 通过 pdf.js 渲染 PDF（浏览器查看器，200 页上限）
- PDF **从不发送给 LLM** — 流水线中没有 PDF 内容块，也没有 PDF 媒体类型
- `read_file` 不处理 PDF（编码嗅探将其作为二进制拒绝）

## 2. 设计

### 2.1 路径 1：原生 PDF 内容块

在 `read_file` 中新增 PDF 分支，当模型支持时将 PDF 作为原生内容块发送：

```python
def _read_pdf_native(file_path: str, provider: str, model: str) -> dict:
    raw = Path(file_path).read_bytes()
    if len(raw) > PDF_MAX_FILE_BYTES:  # 20MB, aligns with ZCode
        return {"error": "pdf_too_large", ...}
    mime = "application/pdf"
    # Build provider-specific content block
    if provider == "anthropic":
        block = {"type": "document", "source": {"type": "base64",
                  "media_type": "application/pdf", "data": base64.b64encode(raw).decode()}}
    else:  # OpenAI-compatible
        block = {"type": "file", "file": {"filename": Path(file_path).name,
                  "file_data": f"data:application/pdf;base64,{base64.b64encode(raw).decode()}"}}
    return {"content": [block], "file_size": len(raw), "total_pages": None}
```

def render_pdf_pages(file_path, *, first_page=1, last_page=None, dpi=100, timeout_s=120) -> list[PdfPage]:

### 2.3 `read_file` 中的路径选择

```python
if suffix == ".pdf":
    caps = get_declared_capability(provider, model, "pdf")
    if caps == "supported" and not page_range_requested:
        return _read_pdf_native(file_path, provider, model)      # Path 1
    elif caps != "supported" and get_declared_capability(provider, model, "vision") == "supported":
        return _read_pdf_to_images(file_path, ...)               # Path 2
    elif caps == "supported" and page_range_requested:
        if get_declared_capability(provider, model, "vision") == "supported":
            return _read_pdf_to_images(file_path, ...)           # Path 2 (page range)
        else:
            return {"error": "pdf_pages_images_unsupported"}     # error
    else:
        return {"error": "pdf_not_supported"}                    # can't handle
```

### 2.4 在媒体流水线中新增 `"pdf"`

- `media_handlers.py` 中的 `MEDIA_TYPE_BY_ITEM`：新增 `"pdf"` 家族
- `_MEDIA_HANDLERS`：新增一个 `PdfHandler`，透传原生 PDF 块（原生路径无需解码/重存）
- `scrub.py` 的 `_FAMILY_SKILL`：`"pdf": None`（无 skill 回退 — 如果模型无法处理 PDF 或图片，则拒绝）

### 2.5 依赖：poppler 或 PyMuPDF（仅路径 2）

路径 1 不需要外部依赖 — 仅需 base64 编码。路径 2 需要：
- **poppler**（`pdftoppm` + `pdfinfo`）：与 ZCode 完全对齐，但增加 Windows 打包复杂度
- **PyMuPDF**（`fitz`）：纯 Python wheel，打包更简单，偏离 ZCode 实现

建议：打包时用 PyMuPDF；路径 1 仍是主路径（大多数现代模型支持原生 PDF）。

## 5. 备注

- **路径 1（原生 PDF）是主路径** — 大多数现代模型（Claude 3.5+、Gemini、GPT-4o）支持原生 PDF。路径 2 是旧模型的回退。
- **路径 1 不需要外部依赖** — 仅需 base64 编码 + provider 特定的块构造。这是最容易实现的部分。
- **路径 2 是成本较高的部分** — 外部依赖（poppler/PyMuPDF）+ 子进程启动 + 图片压缩。但仅对不支持原生 PDF 的模型才需要。
- `supportsPdf` 能力检查来自 Vision 能力门控计划的 JSON 目录。
- ZCode 的 `PDF_PAGES_IMAGES_UNSUPPORTED` 错误含义：模型支持原生 PDF 但不支持图片，且有人请求了页面渲染（需要图片）。修复方式是使用不带页面范围的原生 PDF。

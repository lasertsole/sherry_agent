# 计划：中间件约束机制更新指南

- 日期：2026-11-11
- 状态：**待评审**
- 来源：梳理 Sherry 的 main/subagent 中间件必需约束机制，给出维护和更新操作指南
- 风险等级：**高** —— 必需中间件是安全基线，改错会导致 agent 构建失败或安全中间件被静默移除

---

## 0. 机制全景

### 0.1 三层架构

```
specs.py (声明层)
  └── MIDDLEWARE_SPECS 表，每行一个 MiddlewareSpec
      └── required_in: frozenset[Profile]  →  MAIN / CHILD / _BOTH / 空
  └── required_entries(profile)  →  从表派生出必需集合
  └── _validate_table()  →  导入时检查：required_in 标了的必须有对应 binding

scaffolding.py (派生+执行层)
  └── _MAIN_REQUIRED = required_entries(MAIN)      ← 自动派生，无第二份真相
  └── _SUBAGENT_REQUIRED = required_entries(CHILD)
  └── validate_required_middleware(list, chain, entries)  ← 构建时检查
  └── ScaffoldingViolationError  ← 缺了就报错

core.py / child_agent_factory.py (调用层)
  └── agent_middleware = _build_middlewares(...)
  └── validate_required_middleware(agent_middleware, chain="main", entries=_MAIN_REQUIRED)
      ↑ 在 create_agent() 之前执行，缺必需中间件 → 构建中止
```

## 1. 图片功能计划对中间件约束的影响

### 1.1 已有改动：不需要改 `required_in`

图片功能计划涉及的改动全部在**已有必需中间件内部**或**非中间件模块**：

| 计划 | 改动位置 | 是否新中间件 | 影响 required_in？ |
|---|---|---|---|
| 压缩级联 | `pub/func/media/image_compress.py`（工具模块） | 否 | 无 |
| Read 读图 | `agent/tools/file_tools/read_file.py`（工具） | 否 | 无 |
| PDF 处理 | `agent/tools/pub_base/pdf_render.py`（工具模块） | 否 | 无 |
| Vision 门控 | `config/model_capabilities.py`（配置模块） | 否 | 无 |
| Artifact 存储 | `agent/tools/pub_base/artifact_store.py`（工具模块） | 否 | 无 |
| 历史剥离预算化 | `MultimodalProcessor._project_history_media_budget`（**已有中间件内部**） | 否 | 无 |
| Markdown 画廊 | `client/app/` 前端 | 否 | 无 |
| 图片生成 | `agent/tools/image_gen.py`（新工具） | 否 | 无 |
| 上传流水线 | `server/trigger/http/` + `client/app/` | 否 | 无 |

`MultimodalProcessor` 已经在 `required_in=frozenset({MAIN})` 里——历史剥离预算化只是改它内部的方法，不改类名、不改必需状态。

### 1.2 需要新增：子代理图片历史剥离中间件

**问题**：子代理能碰到图片（`read_file` 没标记 `main_only`，子代理继承基础工具集），但 `MultimodalProcessor` 没有 child binding——子代理链里完全没有图片历史剥离。

**风险**：子代理 N 轮调 N 次 `read_file` 读图 → N 个 `image_url` block 全留 context → 没有预算剥离 → 累积溢出。

**工具层已覆盖的保护**（不需要中间件）：
- ✅ 压缩 — `read_file._read_image` → `prepare_for_model` 在工具层做
- ✅ 能力检查 — `native_image_content` → `_native_allowed(session_id)` 在工具层做
- ✅ 技能回退 — `native_image_content` 返回纯文本在工具层做

**缺失的保护**（需要中间件）：
- ❌ 历史剥离 — `MultimodalProcessor._project_history_media_budget` 只在 main 链

### 1.3 方案：抽独立中间件加到 BOTH

把预算剥离逻辑从 `MultimodalProcessor` 内部抽成一个独立的轻量中间件 `MediaBudgetProjection`，加到 main 和 child 两条链，`required_in=_BOTH`。

**不抽 `MultimodalProcessor` 整体到 BOTH**——它还有用户上传处理、`_persist_media_kwargs`、`_scrub_request` 等 main 专属逻辑，子代理不需要。

**不加 scrub 到子代理**——`native_image_content` 在工具层已做能力门控，子代理不会把不支持的图片发给模型。

### 1.2 未来可能需要改 `required_in` 的场景

| 场景 | 操作 |
|---|---|
| 新增一个安全关键中间件（如 SafetyFilter） | 在 `MIDDLEWARE_SPECS` 加一行，设 `required_in=frozenset({MAIN})` 或 `_BOTH` |
| 把某个可选中间件提升为必需 | 改它的 `required_in` 从空到 `frozenset({MAIN})` |
| 把某个必需中间件降为可选 | 改它的 `required_in` 从 `frozenset({MAIN})` 到空（**慎重**） |
| 重命名一个必需中间件 | 改 spec name + 加 `names` 别名到 `RequiredMiddlewareEntry`（见 §2.4） |

## 2. `MediaBudgetProjection` 中间件设计

### 2.1 职责

单一职责：**对消息列表中的 `image_url` / `audio_url` / `video_url` block 做字节预算投影**——从新到旧贪心保留，最新用户消息的媒体受保护，超预算的替换为文本占位符。

这是从 `MultimodalProcessor._project_history_media_budget` 抽出来的独立逻辑，main 和 child 都需要。

### 2.2 新中间件类

新文件：`agent/middlewares/media_pipeline/budget_projection.py`

```python
class MediaBudgetProjectionMiddleware(AgentMiddleware):
    """预算式媒体历史剥离（对齐 ZCode Oui）。

    每轮 wrap_model_call 前对消息列表做字节预算投影：
    - 收集所有 image_url / audio_url / video_url block，按 message 位置 + 字节大小标记
    - 最新 user message 的媒体标记为 protected（永远不剥）
    - 非保护 block 按从新到旧贪心保留，直到预算耗尽
    - 超预算的 block 替换为文本占位符
    """

    def awrap_model_call(self, request, call_next):
        messages = request.messages
        budget = MEDIA_PIPELINE.get("history_media_budget_bytes", 75 * 1024 * 1024)
        projected = _project_media_budget(messages, budget)
        return call_next(request.override(messages=projected))
```

`_project_media_budget` 是从 `MultimodalProcessor._project_history_media_budget` 提取的纯函数（不依赖 `self`），main 和 child 共用。

### 2.3 从 `MultimodalProcessor` 提取

当前 `_project_history_media_budget` 是 `MultimodalProcessor` 的方法（`core.py:221`）。提取步骤：

1. 把 `_project_history_media_budget` 和辅助函数 `_estimate_block_bytes` 移到 `budget_projection.py` 作为独立函数
2. `MultimodalProcessor` 改为调用 `MediaBudgetProjectionMiddleware`（或保留自己的调用作为 main 链的双重保险——main 链的 `MultimodalProcessor` 在 `before_agent` 做一次，`MediaBudgetProjection` 在 `wrap_model_call` 再做一次，幂等）
3. 推荐：`MultimodalProcessor` 删除自己的 `_project_history_media_budget` 调用，只保留 `before_agent` 的上传处理/persist/scrub 逻辑；预算剥离统一由 `MediaBudgetProjection` 在 `wrap_model_call` 做

### 2.4 注册到 `MIDDLEWARE_SPECS`

```python
MiddlewareSpec(
    name="MediaBudgetProjection",
    cls=MediaBudgetProjectionMiddleware,
    main=ProfileBinding(10, lambda _ctx: MediaBudgetProjectionMiddleware()),
    child=ProfileBinding(5, lambda _ctx: MediaBudgetProjectionMiddleware()),
    required_in=_BOTH,
),
```

- main position 10：在 `ToolGuardrails`(8) / `ToolResourceLockMiddleware`(9) 之后，`ContextEvictionMiddleware`(11) 之前——预算剥离在工具护栏之后、上下文驱逐之前
- child position 5：在 `OutputRepetitionGuard`(child 5) 之前或之后——child 链位置需要根据现有 child 链顺序调整

**`required_in=_BOTH`** —— main 和 child 都必需。缺了就报 `ScaffoldingViolationError`。

### 2.5 为什么不直接加 `MultimodalProcessor` 到 BOTH

| `MultimodalProcessor` 的功能 | 子代理需要？ |
|---|---|
| `_project_history_media_budget`（预算剥离） | ✅ 需要 |
| `before_agent`：处理用户上传的 `image_base64_list` | ❌ 子代理不接收用户上传 |
| `_persist_media_kwargs`（写 `additional_kwargs["images"]`） | ❌ 子代理不需要 |
| `_scrub_request`（按能力剥离不支持媒体） | ❌ 工具层 `native_image_content` 已覆盖 |
| `_apply_skill_path`（技能回退） | ❌ 工具层已覆盖 |
| `_strip_history_images`（已废弃，被预算投影替代） | ❌ 已移除 |

只剥离这一个功能需要共享，其余都是 main 专属。加整个 `MultimodalProcessor` 到 child 会引入不必要的复杂度和副作用。

## 3. 更新操作指南

### 2.1 新增必需中间件

**场景**：新增一个 `SafetyFilterMiddleware`，要求 main agent 必须带。

**步骤**：

1. **`specs.py` — 加 spec 行**：
```python
MiddlewareSpec(
    name="SafetyFilterMiddleware",
    main=ProfileBinding(30, lambda ctx: SafetyFilterMiddleware()),  # position 接在最后
    required_in=frozenset({MAIN}),
),
```

2. **无需手动改 `scaffolding.py`** —— `_MAIN_REQUIRED = required_entries(MAIN)` 自动派生，新行会被自动包含。

3. **无需手动改 `core.py`** —— 调用点 `_MAIN_REQUIRED` 是引用，自动更新。

4. **加测试** —— `tests/agent/middlewares/test_scaffolding.py` 加一条：移除 `SafetyFilterMiddleware` → 报 `ScaffoldingViolationError`。

### 2.2 新增 BOTH 必需中间件（main + subagent）

```python
MiddlewareSpec(
    name="NewSafetyMiddleware",
    main=ProfileBinding(31, lambda ctx: NewSafetyMiddleware()),
    child=ProfileBinding(10, lambda ctx: NewSafetyMiddleware()),
    required_in=_BOTH,
),
```

`_MAIN_REQUIRED` 和 `_SUBAGENT_REQUIRED` 都会自动包含。

### 2.3 修改现有中间件的必需状态

**场景**：把 `TokenBudget` 从可选提升为必需。

```python
# 改前
MiddlewareSpec(
    name="TokenBudget",
    main=ProfileBinding(6, lambda _ctx: TokenBudget()),
    child=ProfileBinding(2, lambda _ctx: ChildTokenBudget()),
    # 无 required_in
),
# 改后
MiddlewareSpec(
    name="TokenBudget",
    main=ProfileBinding(6, lambda _ctx: TokenBudget()),
    child=ProfileBinding(2, lambda _ctx: ChildTokenBudget()),
    required_in=_BOTH,
),
```

派生集合自动更新。测试里加一条验证。

### 2.4 重命名必需中间件

**场景**：`HeartbeatStaleness` 改名为 `HeartbeatMonitor`。

```python
# specs.py — 改 name
MiddlewareSpec(
    name="HeartbeatMonitor",  # 改了
    main=ProfileBinding(22, lambda _ctx: HeartbeatMonitor()),  # 类名也改了
    child=ProfileBinding(8, lambda _ctx: HeartbeatMonitor()),
    required_in=_BOTH,
),
```

`scaffolding.py` 的派生集合会自动用新类名。但如果有测试或配置硬编码了旧名 `"HeartbeatStaleness"`，需要同步更新。

如果类改名但想保持向后兼容（旧测试/配置仍用旧名），在 `RequiredMiddlewareEntry` 的 `names` 字段加别名——但目前 `required_entries()` 不支持自定义 names，它是 `RequiredMiddlewareEntry(spec.class_for(profile), ())`，第二个参数（别名）始终为空。如果要支持别名，需要改 `required_entries()` 和 `MiddlewareSpec` 加一个 `aliases` 字段。

### 2.5 降级必需中间件为可选（慎重）

**场景**：`ContextEvictionMiddleware` 不再必需（改为按需加载）。

```python
# 改前
required_in=frozenset({MAIN}),
# 改后
# 删除 required_in 行（默认 frozenset()）
```

**风险**：如果该中间件确实是安全关键的，降级后可能被意外移除而不报错。必须：
1. 确认移除后 agent 仍能安全运行
2. 更新 `_format_rejection()` 的错误消息引用（如果它被当作示例提到）
3. 更新测试：从"缺失报错"改为"缺失不报错"
4. 在 AGENTS.md 记录降级原因

## 5. 不需要改的部分

| 组件 | 为什么不用改 |
|---|---|
| `scaffolding.py` 的派生逻辑 | `_MAIN_REQUIRED = required_entries(MAIN)` 是自动的——改 specs 表就够 |
| `core.py` / `child_agent_factory.py` 的调用点 | 它们引用 `_MAIN_REQUIRED` / `_SUBAGENT_REQUIRED`，自动跟随 |
| `validate_required_middleware()` 函数本身 | 检查逻辑不依赖具体中间件名——它只比对 entries 和实际列表 |
| `ScaffoldingViolationError` | 异常类不绑定具体中间件 |

**唯一的"第二份真相"风险**是有人手动在 `scaffolding.py` 里硬编码了中间件名——但当前代码没有这样做，`_MAIN_REQUIRED` 和 `_SUBAGENT_REQUIRED` 完全从 `specs.py` 派生。

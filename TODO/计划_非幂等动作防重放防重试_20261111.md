# 计划：非幂等高危动作防重放（不改首次执行 / 不破坏流程）

- 日期：2026-11-11（r3 重写）
- 状态：**待评审**
- 来源：r2 被否（HITL 门 + wrap_tool_call 阻塞会改首次执行、断 executor 子代）；r3 改用"首次不动 + 重放降级 + 自动账本提醒"路线，融合用户思路（高危记录 session 注册 + system-reminder 提醒 + PTC 降级）
- 风险等级：**中** —— 不改首次执行、不加门、不破坏现有流程；硬机制只在 Sherry 自有重放层；残留 retry 风险靠软机制降低不消除（诚实）

---

## 0. 设计原则（r3 核心）

| 原则 | 含义 |
|---|---|
| **首次执行神圣不可变** | 不加 HITL 门、不加阻塞守卫、不改 wrap_tool_call 拦截首次。agent 的工具调用首次执行行为字节级不变 |
| **硬机制只在重放/重复路径** | PTC pre-run / LDW journal / boot recovery / regression gate 这些 Sherry 自有优化层可以改（它们不是 agent 的"原有动作"，是重放优化）。改它们不破坏原有流程 |
| **软机制靠自动账本 + 提醒** | 高危调用执行时**被动自动入账**（不依赖 agent 主动注册——这硬化了用户思路里的"agent 发现并注册"），system-reminder 每轮提醒 agent 幂等事件项和键，agent 自治避免重复或换键绕过 |
| **不破坏 executor 子代** | 无 HITL 门 → 无 headless 自动拒绝问题 → executor 子代的 terminal/python_repl/write_file 首次执行不受影响 |

**与 r2 的根本区别**：r2 在 wrap_tool_call 最内层加阻塞守卫 + HITL 门（改首次执行、断子代）；r3 撤掉所有首次阻塞，硬机制只改重放层，软机制靠被动账本 + 非阻塞提醒。

---

## 1. 高危幂等记录账本（session 级，被动自动记录）

### 1.1 核心思路（融合用户想法 + 硬化）

用户原意："agent 发现需要做幂等高危操作、或者有高危 metadata 的工具，给 session_id 注册高危幂等记录，本 session agent 可见，会话/子代理结束删除，留痕排查。"

r3 硬化点：**不依赖 agent 主动发现并注册**（那是自觉）。改成工具执行时**被动自动入账**——带 `side_effect=non_idempotent` metadata 的工具，执行时自动写一条高危记录到 session 账本。agent 不需要做任何事，账本自动完整。

### 1.2 账本结构

```
high_risk_idempotency_ledger（session 级，内存 + SQLite mirror）
  idempotency_key  = hash(tool_name + args_canonical)   -- 用于识别"同动作"
  tool_name        TEXT
  args_canonical   TEXT        -- 规范化参数（排序 key/去空格）
  call_id          TEXT        -- LangChain tool_call id（溯源）
  status           TEXT        -- committed | failed
  result_digest    TEXT        -- 结果摘要（不存全量，隐私+体积）
  turn_id / step_id / plan_key TEXT  -- 溯源
  executed_at      INTEGER
  session_id       TEXT
```

- **session 级**：只本 session（含其子代）可见；会话删除 / 子代理结束时删除 live 记录
- **留痕**：删除前写一条到 append-only 审计日志（`audit/high_risk_actions.log`，持久，仅溯源用，不进上下文）—— 满足用户"留痕方便后期排查"
- **被动自动**：工具执行（首次/重试/任何路径）后，若该工具标 `side_effect=non_idempotent`，自动写账本。agent 无需主动调注册工具
- **args_canonical**：用于"同动作不同 call_id"识别（LLMRetry 重发会用新 call_id，但 args 相同 → 同 key）

### 1.3 账本只读注入上下文（不阻塞）

账本不拦截任何调用，只**被动观察 + 注入提醒**。它是只读视图，不是门。

## 2. 软机制：system-reminder 提醒 + 调用点即时 notice（非阻塞）

### 2.1 每轮 system-reminder（用户核心想法）

DynamicReminderMiddleware 增加 `high_risk_idempotency` source（低优先级，budget 内）：每轮首次 model call 前，把账本里的高危事件项注入：

```
<system-reminder source="high_risk_idempotency">
本会话已记录的高危幂等动作：
- [committed] terminal "stripe refund ch_xxx" (key: a3f...)  — 已执行，重发会重复退款
- [committed] mcp__payment charge order=123 (key: b7e...)     — 已执行，重发会重复扣款
- [failed]    python_repl "requests.post(...)" (key: c2d...)   — 上次未确认，可重试但确认前勿重复
如需重做同类动作，使用不同的幂等键（如换 order id / 换 refund 目标）。
</system-reminder>
```

- agent 看到后自治：避免重发同动作，或换键（用户原意："防重输入同样 id，换个 id 就行"）
- **非阻塞**：提醒只是信息，不阻止 agent 做任何事

### 2.2 调用点即时 notice（硬化提醒，仍非阻塞）

仅靠每轮提醒，agent 在同一 turn 内重发时来不及反应（提醒在 turn 首，重发在 turn 中）。加一道**调用点即时 notice**：

当工具即将执行 + 该 (tool, args_canonical) 已在账本为 committed → 在工具**返回结果前**注入一条 notice（作为 tool_result 前缀，非单独消息）：

```
[⚠️ idempotency notice: this action was already committed with key a3f... 
 on turn N. Re-execution may duplicate. If unintended, use a different key.]
<actual tool result>
```

- **非阻塞**：工具照常执行（不改首次/任何执行行为），notice 只是结果前缀
- 比每轮提醒更精准（命中即提示，不靠 agent 记住全局提醒）
- agent 在下一轮看到 notice，可纠正（反向、联系、换键）

### 2.3 软机制的边界（诚实）

软机制**降低重复概率，不消除**。retry 在同一 turn 重发时，即时 notice 作为结果前缀，agent 来不及在同一 turn 中途取消——重复仍可能发生。这是"不加门"的代价。硬机制（第 3 节）堵重放路径，retry 路径靠软机制 + 残留风险接受。

## 3. 硬机制：重放路径降级（只在 Sherry 自有重放层，不改首次执行）

这是唯一的"阻断"——且只阻断**自动重放**，不阻断 agent 主动调用。agent 主动调用永远照常执行。

### 3.1 PTC 工具白名单排除 + 编译门控（主防线，r3 补）

> 用户指出：有高危幂等 metadata 的 MCP 工具必然不能使用 PTC。这是 PTC 的**主防线**，比 pre-run 降级更靠前——non_idempotent 工具根本不该进 PTC 的可调用集，也不该被编译进脚本。

**两层排除**：

**(a) `ptc_allowed_tools` 白名单排除（config 级）**
- `config/features/agent_side/ptc.py` 的 `ptc_allowed_tools`（当前含 terminal/write_file/patch_file 等）必须**排除所有 `side_effect=non_idempotent` 工具**
- non_idempotent MCP 工具**不在白名单内** → PTC 脚本运行时的工具集（`ptc_allowed_tools` ∩ spawn policy）不含它们 → 脚本即使引用也调不到
- 这是 config 级硬排除，不依赖运行时判断

**(b) PTC 编译器静态门控（compile 级）**
- `agent/tools/ptc/compiler.py` 编译 step 脚本时（已有"source is validated statically"），增加一道：检查 step 的 calls_log / 源码引用的工具名，若含 `side_effect=non_idempotent` 工具（含 non_idempotent MCP）：
  - **拒绝编译该 step 的 PTC 脚本**（不生成 `ptc__<plan>__<step>.py`）→ 该 step 永远不走 PTC 重放，每次走 agent 模式
  - 或编译但标 `high_risk=true`（仅当 pre-run 降级作为兜底时才用此选项；默认拒编更安全）
- 默认拒编（a + b 双保险）：non_idempotent 工具既不在白名单、也不会被编进脚本

**为什么默认拒编而非标 high_risk**：
- 拒编 = 该 step 永远 agent 执行（agent 看到账本提醒自治）
- 标 high_risk + pre-run 降级 = 脚本存在但不重放（脚本文件本身可能被误用/误执行）
- 脚本不存在比"存在但不执行"更安全（无脚本可误跑）

**与现有 PTC 机制衔接**：
- PTC 编译发生在 skill review 通过后（`compiler.py`）—— skill review 已能读工具 metadata，编译时过滤 non_idempotent
- `ptc_allowed_tools` 白名单变更应触发 side_effect 复审（r2 已知局限第 6 条）—— 确保新增白名单工具不引入 non_idempotent
- non_idempotent MCP 工具的 manifest 声明（第 4 节）→ 编译器读 manifest 判定 MCP 工具 side_effect → 拒编

### 3.2 PTC pre-run 高危步骤 → 降级 agent 模式（defense-in-depth）

> "涉及到高危幂等记录的 重放 taskflow 的特定 step 必须从 PTC 方式降级到 agent 方式执行。"

这是 3.1 的**兜底**——即使 3.1 漏过（白名单误配 / 编译器 bug 导致高危脚本生成），pre-run 仍拦：

- step 的 calls_log 含 `side_effect=non_idempotent` 调用 → 标记该 step 为 high-risk
- PTC pre-run 遇 high-risk step → **不重放脚本**，降级为正常 React（建 child agent 走 LLM 决策）
- agent 模式执行时：agent 看到账本提醒（第 2 节），自治决定是否重做 / 换键
- **非 high-risk step 照常 PTC pre-run**（用户原意："其他不涉及高危的 step 照常按 PTC 运行"）

这不改首次执行——首次执行本就不走 PTC pre-run（pre-run 是重复任务的重放优化）。改的是重放：高危步骤的重放从"脚本自动重放"降级为"agent 重新决策"。

**3.1 + 3.2 关系**：3.1 主防线让高危 step 根本没 PTC 脚本（拒编）；3.2 兜底处理万一有脚本的漏网情况（pre-run 不重放）。正常情况下 3.1 生效，3.2 不触发。

### 3.3 LDW journal 高危调用标记不可重放

- LDW journal 记录高危调用的结果，但标 `replayable=false`
- LDW replay 遇 `replayable=false` 的调用 → **不用 journal 缓存**，回退为实际执行（经 agent 决策，因为 LDW leaf 执行也是 agent 驱动）
- 非 high-risk 调用照常 journal 命中零调用重放

### 3.4 boot recovery 高危 dangling 调用 → skip + surface

- 当前 boot recovery：dangling call 做 skip/rerun 决策
- r3：dangling call 若是高危（账本有记录或 metadata 标 non_idempotent）→ **skip 不 rerun** + 在 resume 时 surface 为 system-reminder："你有一个未确认的高危动作（key X），自行决定是否重发或查状态"
- 不盲重跑高危 dangling call（防重启后双付）

### 3.5 regression gate 高危命令 skip

- regression gate 已有 `_ALLOWED_EXECUTABLES` 白名单（basedpyright/mypy/tsc/pytest…），支付工具不在内
- r3 加一道：reverify 时若命令匹配账本高危记录 → skip 不回放（双保险）

### 3.6 硬机制的边界

硬机制只覆盖**自动重放路径**（PTC pre-run / LDW journal / boot recovery / regression gate）。这些是 Sherry 的优化层，不是 agent 的"原有动作"。改它们不破坏原有流程——最坏情况是重放优化失效（降级为 agent 执行），不是流程断裂。

**不覆盖 retry**（LLMRetry/InvalidToolCallRepair/MaxTokensBoost 重发）——retry 重发是 agent turn 内的执行路径，改它会动首次执行语义。retry 只靠软机制（第 2 节）。

## 4. 工具高危标记（用于自动入账识别）

### 4.1 side_effect metadata（声明式，从 r2 保留分类，但用途变了）

r2 用 metadata 做 HITL 门控（被否）；r3 只用它**识别哪些工具执行后自动入账**，不做门控。

| 类别 | 工具 | 自动入账？ | 行为变化？ |
|---|---|---|---|
| `pure` | read_file/grep/lsp_*/web_search/browser(snapshot,screenshot,scroll)/... | 否 | 无 |
| `idempotent` | memory(replace,remove)/todowrite(replace,patch)/taskflow(create,plan)/... | 否 | 无 |
| `non_idempotent`（图灵完备任意副作用） | terminal / python_repl / execute_code(PTC) / browser_evaluate / browser(click,type,press,navigate) / mcp__* | **是（被动自动入账）** | **无（入账是观察，不阻塞）** |
| `non_idempotent`（本地状态损坏） | patch_file/write_file/ast_grep_rewrite/lsp_rename/lsp_format/skill_manage/... | 是（可选，默认不入账——本地状态损坏非支付类，靠 git 回滚） | 无 |

### 4.2 不盲信现有 metadata（r2 核实结论保留）

- `memory(action=add)` 标 `idempotent=True` 但 add 无去重 → 入账分类按 non_idempotent（防重放插重复条目）
- `terminal_bg(action=kill)` 在 `READ_ONLY_TOOLS` 但 kill 有副作用 → 不依赖该集合

### 4.3 新工具默认

- 未声明 `side_effect` 的工具 → 默认 non_idempotent → 自动入账（fail-safe：未知动作默认观察记录）
- MCP 工具无 metadata → 默认 non_idempotent → 自动入账
- **不阻塞、不加 HITL**——默认入账只是"多观察"，不改执行

## 5. 可选强模式：重发命中已提交 → 返回缓存（toggle，默认关）

这是 r2 的幂等表缓存机制，r3 降级为**可选 toggle**，默认关：

- `IDEMPOTENCY_CACHE_MODE = "off" | "on"`
- off（默认）：账本只观察 + 提醒，重发照常执行（不改首次/重试行为）
- on（可选启用）：重发（retry/replay）命中账本 committed 记录 → 返回缓存结果不重执行（r2 行为，堵 retry 双付）

**为什么默认关**：on 模式会改 retry 执行语义（返回缓存而非执行），可能影响合法重发（agent 想查状态、args 恰好匹配）。默认关保"不改原有动作"；用户/场景确需硬堵 retry 双付时再开 on。

这样 r2 的硬堵能力保留为可选项，不强制施加。

## 6. 行为影响分析（评审重点：是否破坏原有）

| 路径 | r3 行为 | 是否改变原有？ |
|---|---|---|
| agent 首次调用任何工具 | 照常执行，无门、无阻塞 | **不变** |
| pure 工具任何调用 | 照常，不入账、不提醒 | **不变** |
| non_idempotent 工具首次调用 | 照常执行 + 执行后被动入账（观察）+ 下轮提醒 | 执行行为**不变**；多了观察记录（additive） |
| executor 子代 terminal/python_repl | 照常执行（无 HITL 自动拒绝问题） | **不变**（解决 r2 最大破坏点） |
| retry 重发（LLMRetry 等） | 照常执行（默认 off 模式）+ 即时 notice 结果前缀 | 执行**不变**；结果多 notice 前缀（additive，agent 下一轮可见） |
| PTC pre-run high-risk step | 降级 agent 模式（不脚本重放） | 改重放优化（Sherry 自有层），不改 agent 原有动作 |
| LDW journal high-risk call | 标不可重放，回退执行 | 改重放优化，不改首次 |
| boot recovery 高危 dangling | skip + surface（不盲重跑） | 改恢复层（更安全），不改 agent 动作 |
| regression gate 高危命令 | skip | 改 gate（已有白名单基础），不改 agent 动作 |

**结论**：agent 的所有原有动作（首次/重试调用工具）字节级不变。改的全是 Sherry 自有重放/恢复优化层（降级为 agent 执行或 skip），最坏情况是重放优化失效而非流程断裂。executor 子代不再受 HITL 自动拒绝影响（r2 的致命破坏点消除）。

**additive 部分**：被动入账 + system-reminder + 即时 notice——这些是新增观察/信息，不改执行，只让 agent 多看到信息自治。

## 7. 全场景推演（r3 机制覆盖验证）

逐一在 r3 机制下走每个场景，标覆盖度。**r3 机制**：自动账本（被动 after 钩子）+ system-reminder + 调用点 notice（非阻塞）+ PTC 白名单排除 + PTC 编译拒编 + pre-run 降级（兜底）+ LDW 标不可重放 + boot skip+surface + gate skip + 可选 on 模式（默认关）。

### 7.1 重放路径（r3 硬防完整）

| 场景 | r3 机制 | 覆盖 |
|---|---|---|
| 1 PTC pre-run 重执行支付(terminal) | 3.1(a) terminal 不在 ptc_allowed_tools + 3.1(b) 编译器拒编含 terminal 的 step → 无脚本；3.2 pre-run 降级兜底 | ✅ 硬防 |
| 5 LDW journal 重放高危 | 3.3 高危调用标 replayable=false → 不缓存重放，回退执行 | ✅ 硬防（回退 agent，agent 见账本自治） |
| 7 browser click 支付按钮重放 | browser 动作 non_idempotent → 3.1(a) 不在白名单 + 3.1(b) 拒编 | ✅ 硬防 |
| 8 MCP 支付工具重放 | MCP 默认 non_idempotent → 3.1(a)+(b) 排除拒编 | ✅ 硬防 |
| 11 boot recovery 重跑高危 dangling | 3.4 skip + surface（不盲重跑） | ✅ 硬防 |
| 12 gate 重放含支付 | 3.5 skip + 现有白名单双保险 | ✅ 硬防 |
| 13 PTC execute_code 重放支付 | execute_code non_idempotent → 3.1(b) 拒编含它的 step | ✅ 硬防 |
| 14 browser_evaluate fetch 支付重放 | browser_evaluate non_idempotent → 3.1(a)+(b) 排除拒编 | ✅ 硬防 |

**重放路径全部硬防**——高危工具根本不进 PTC 脚本（白名单排除 + 编译拒编），即使漏网 pre-run 降级兜底。LDW/boot/gate 各自硬防。

### 7.2 retry 路径（r3 软防，残留风险）

| 场景 | r3 机制 | 覆盖 |
|---|---|---|
| 2 LLMRetry 新 id 重发支付 | 首次执行（无门）+ 自动入账；retry 重发**照常执行**（默认 off）→ 可能双付；命中 committed → 结果前缀 notice（事后，agent 下一轮见） | ⚠️ 软防（降低概率不消除） |
| 3 Repair 原 id 重派 | 同 2——执行 + notice 事后 | ⚠️ 软防 |
| 4 MaxTokensBoost 重发 | 同 2 | ⚠️ 软防 |
| 10 跨 turn 并发同动作 | 账本 session 级跨 turn 可见 + notice；但第二 turn 仍执行（无门） | ⚠️ 软防 |

**retry 路径只能软防**——这是"不加门、不改首次执行"的根本代价。notice 是结果前缀（事后），agent 来不及同 turn 取消重发。开第 5 节 on 模式可硬堵（命中 committed 返回缓存不重执行），但 on 模式改 retry 语义（合法重发也被缓存），默认关。

### 7.3 spawn / LDW leaf 路径

| 场景 | r3 机制 | 覆盖 |
|---|---|---|
| 6 子代重复 spawn | spawn non_idempotent → 自动入账 + 提醒；现有 step 状态机（DISPATCHED 检查）部分挡；r3 不硬阻 spawn | ⚠️ 部分（spawn 不硬阻，但子代副作用受 r3 保护） |
| LDW leaf 重放高危 | 3.3 leaf 调用标 replayable=false → leaf 回退 agent 执行 → agent 见账本自治 | ⚠️ 软防（回退 agent 后靠自治） |

### 7.4 r3 新暴露的设计矛盾（需解决）

推演中发现一个 r3 的真实矛盾——**PTC 白名单排除 vs 编码步骤合法重放**：

**问题**：核实发现 `ptc_allowed_tools` 当前**含 terminal / write_file / patch_file**（`config/features/agent_side/ptc.py:44-51`）。r3 步骤 6 说"白名单排除 non_idempotent"——但：
- terminal / python_repl 是 non_idempotent（图灵完备）→ 排除 → PTC 脚本不能跑 `pytest`/`tsc`/`git diff`（这些是编码步骤的合法验证）
- write_file / patch_file 是 non_idempotent（本地状态损坏类）→ 排除 → PTC 脚本不能重放文件写入 → 编码步骤 PTC 失效

**若全排除**：PTC 对编码任务失效（编码步骤几乎都含 write_file/terminal），PTC 优化层废掉。
**若全保留**：terminal 里 `curl` 支付漏进 PTC → 重放双付。

**这不是同类风险**：
- 外部不可逆（支付/邮件/下单）→ 必须 PTC 排除
- 本地状态损坏（write_file/patch_file）→ 可 PTC 重放，前提是 worktree 基线重置（CAS + worktree isolation 已保证文件回到 step 前状态，重放 write_file 是幂等的）
- terminal/python_repl 图灵完备 → 无法静态区分网络 vs 本地

**解法（细化 r3 步骤 6）**：PTC 白名单排除分两档：
- **外部不可逆类（terminal/python_repl/execute_code/browser_evaluate/browser 动作/non_idempotent MCP）**：从 ptc_allowed_tools 排除 + 编译拒编。这些不该 PTC 重放
- **本地状态类（write_file/patch_file/ast_grep_rewrite/lsp_rename/lsp_format）**：保留在 ptc_allowed_tools，PTC 可重放（worktree 基线重置保证幂等）。编译器对这类**不拒编**，但要求 step 有 worktree 隔离基线（无基线则拒编——重放会损坏）
- terminal/python_repl 的"编码验证"子命令（pytest/tsc/git）→ 若要 PTC 重放，需编译时静态检测命令为安全白名单子集（复用 `_ALLOWED_EXECUTABLES`），否则该 step 不含 terminal 的 PTC 脚本

**简化方案（推荐 r3 初始版）**：
- terminal/python_repl/execute_code/browser_evaluate/browser 动作/non_idempotent MCP → 排除 + 拒编（外部不可逆，硬排除）
- write_file/patch_file 等本地类 → 保留 PTC（基线重置保证）
- 编码步骤的 terminal 验证命令（pytest 等）→ step 有 terminal 就不 PTC（保守，编码步骤降级 agent 执行），等静态分析增强后再放行

简化方案接受"含 terminal 的编码步骤不走 PTC"的性能损失换安全。这比"全排除废掉 PTC"好——纯文件操作步骤仍能 PTC 重放。

### 7.5 全场景覆盖汇总

| 路径类 | 场景数 | r3 硬防 | r3 软防 | 不防 |
|---|---|---|---|---|
| 重放（PTC/LDW/boot/gate） | 8 | 8 | 0 | 0 |
| retry（LLMRetry/Repair/MaxTokens） | 4 | 0（默认 off） | 4 | 0（on 模式可硬堵） |
| spawn/LDW leaf | 2 | 0 | 2 | 0 |
| 跨 session | — | — | — | 不在范围（业务层 idempotency-key） |

**结论**：重放路径 r3 硬防完整（8/8）。retry 路径软防（4/4 软，on 模式可升硬）。spawn/LDW leaf 软防。r3 用"不改首次执行"换了 retry 软防局限——这是设计选择不是缺陷。**新矛盾（7.4 PTC 白名单分档）必须解决，否则要么废 PTC 要么漏支付**。

| 风险 | r3 能否防 | 说明 |
|---|---|---|
| PTC pre-run 重放高危步骤双付 | ✅ 硬防（降级 agent） | 第 3.1 |
| LDW journal 重放高危双付 | ✅ 硬防（不缓存回退） | 第 3.2 |
| boot recovery 重启后重跑高危 | ✅ 硬防（skip+surface） | 第 3.3 |
| regression gate 重放高危 | ✅ 硬防（skip） | 第 3.4 |
| **LLMRetry 重发高危双付** | ⚠️ 软防（提醒+notice降低概率，不消除） | retry 在 turn 内执行，notice 是结果前缀，agent 来不及同 turn 取消。默认 off 模式下重发照常执行。开 on 模式可硬堵（第 5 节，但改 retry 语义） |
| **agent 无视提醒坚持重发** | ❌ 不防 | 软机制本质局限。开 on 模式可硬堵 |
| 子代隔离 worktree 内高危动作 | ✅ 账本 session 级（含子代可见） | 子代账本冒泡到父 session |
| 跨 session 同动作 | ❌ 不防 | 账本 session 级，跨 session 需业务层 idempotency-key（支付 API header） |

**核心诚实**：r3 用"不改首次执行"换来了 retry 路径的软防局限。重放路径硬防完整，retry 路径靠软机制降低概率。若场景要求 retry 也硬防，开第 5 节 on 模式（接受改 retry 语义的代价）。

## 9. Kill criteria

- 若 system-reminder 注入账本导致上下文膨胀（高危动作多的 session）→ 账本注入设上限（如最近 N 条 + 计数）+ 仅 committed 不含 failed
- 若即时 notice 作为结果前缀干扰 agent 解析工具结果 → notice 改为单独 tool_message（仍非阻塞）
- 若 PTC 降级导致 high-risk step 重放成本过高（每次都 agent 执行）→ 接受（安全优先于重放性能）；或对该 step 标记"不重放"（PTC 直接 skip，不降级 agent 也不重放，留给主 agent 决定是否重跑）
- 若 on 模式 toggle 在实测中误堵合法重发（agent 查状态、args 恰好匹配）→ 保持默认 off，仅特定场景（支付类任务）显式开 on

## 10. 验收

### 10.1 首次执行不变（核心）
- agent 首次调用 terminal/python_repl/MCP/browser 动作 → 照常执行，无门、无阻塞
- executor 子代 terminal/python_repl/write_file → 照常执行（无 HITL 自动拒绝）
- pure 工具全路径字节级不变

### 10.2 自动入账（被动观察）
- non_idempotent 工具执行后 → 账本自动有条目（agent 无需主动注册）
- 账本 session 级可见，子代可见父 session 记录
- session/子代结束 → live 记录删除 + 审计日志留痕

### 10.3 软机制
- 每轮 system-reminder 含高危事件项 + 幂等键
- 高危调用执行后若命中 committed → 结果前缀 notice
- 非阻塞（执行照常）

### 10.4 硬机制（重放降级）
- **PTC `ptc_allowed_tools` 不含 non_idempotent 工具**（含 non_idempotent MCP）—— config 级排除验证
- **PTC 编译器拒编含 non_idempotent 调用的 step**—— 不生成 `ptc__<plan>__<step>.py`（主防线）
- PTC pre-run high-risk step（万一漏网）→ 不脚本重放，降级 agent 模式（兜底）
- LDW journal high-risk call → 不缓存重放，回退执行
- boot recovery 高危 dangling → skip + surface（不盲重跑）
- regression gate 高危命令 → skip
- 非 high-risk step → 照常 PTC/LDW 重放
- **non_idempotent MCP 工具既不在 ptc_allowed_tools，也不会被编进 PTC 脚本**

### 10.5 可选 on 模式
- off（默认）：retry 重发照常执行 + notice
- on：retry 重发命中 committed → 返回缓存不重执行

### 10.6 回归
- 现有工具行为不变（pure 路径字节级一致）
- executor 子代编码工作流不破（terminal/python_repl 可用）
- `uv run pytest tests/agent/tools -q` 全过
- HITL/PTC/LDW 现有测试不破

## 11. 与 r2 的对比（为什么 r3 合格而 r2 不合格）

| 维度 | r2（被否） | r3 |
|---|---|---|
| 首次执行 | 加 HITL 门 + wrap_tool_call 阻塞 | **不变**（无门、无阻塞） |
| executor 子代 | HITL 自动拒绝 → 断编码工作流 | **不受影响**（无 HITL） |
| 重放路径 | 幂等表缓存拦截 | 降级 agent 模式（不脚本重放） |
| retry 路径 | 幂等表缓存硬堵（改 retry 语义） | 软防（提醒+notice），可选 on 模式硬堵 |
| 账本 | agent 不主动注册就漏 | **被动自动入账**（硬化用户思路） |
| 提醒 | 无 | system-reminder + 调用点 notice |
| 改原有行为 | 是（多处） | 否（仅改 Sherry 自有重放层） |

r3 满足"不改变原有动作、不破坏原有流程"——首次执行和现有流程字节级不变，硬机制只在重放优化层，软机制靠被动账本 + 非阻塞提醒。残留 retry 风险靠软机制降低，需硬堵时开可选 on 模式。

## 二、设计(四点怎么做)

### ① 末尾自动插入 verify todo + main_agent 感知

**触发时机(post-mutation 归一化,不只是 replace)。** 不能只挂在 `replace` —— 模型可能用 `add` 逐条构建计划(todo1→todo2→todo3),从不 `replace`,verify 永远不出现。正确做法:**任何变更(replace/add/patch/remove)落库后,跑一次 verify 归一化**:
- 若 work todo(非 verify、非 cancelled)≥2 且**无 active verify**(无 verify,或现有 verify 已 terminal=completed/cancelled)→ append 一个系统 verify 到末尾
- 若 work todo <2 且存在 active(pending/in_progress)verify → 移除该 verify(琐碎/已结束计划不值得验收)
- 若 verify 存在但不在末尾 → 移到末尾(见 ①b)

**⚠ 归一化的 active 判定(G2 修正)。** 一个 completed/cancelled 的 verify 是"旧计划的遗留",不算 active。否则模型完成第一个 plan(verify completed)后用 `add` 开始第二个 plan,归一化看见"有 verify"就不 append 新的 → 新计划没验收。判定:verify 的 status 是 pending/in_progress 才算 active;completed/cancelled 的 verify 在归一化时视为"不存在"(若 work≥2 则 append 新的,旧 terminal verify 留在列表但不阻新 verify)。

**⚠ 归一化 main-agent-only(G3 修正)。** 归一化在所有 session 跑会让 subagent/side-chat 的 todo list 也被插 verify → 子代理再 spawn reviewer → 嵌套无底。`_normalize_verify` 必须像 DelegationPressureGate 一样拒绝 `:subagent:`/`:swarm:` session(检查 session_id 前缀或 session 类型)。子代理的 todo list 不插 verify —— 子代理的工作由父代理的 verify 覆盖。

**⚠ 移除 verify 时 kill 链接的 subagent(G4)。** 归一化移除 active verify(work<2 触发)时,若该 verify 有 running 的 `subagent_id` → 调 subagent suppress/kill(复用现有 cascade kill 路径),避免 reviewer 孤立运行。

这是幂等归一化,不依赖"计划创建"这个模糊判定。阈值 ≥2 是因为单 todo 的小任务不值得开验收。

**verify todo 的形状。**

```json
{
  "content": "[VERIFY] 对整个 plan 跑验收:spawn reviewer subagent 执行所有 todo 的 acceptance criteria,失败项定向回退",
  "status": "pending",
  "priority": "high",
  "category": "deep",
  "delegation": "subagent",
  "metadata": {"kind": "verify", "auto_inserted": true}
}
```

`metadata.kind="verify"` 是后续 barrier 强制和 prompt 指引的判定依据。`auto_inserted=true` 让前端能渲染成特殊样式(可选)。

**⚠ 判定只认 `metadata.kind`,不认 content 文本。** 模型可以在 content 里写"[VERIFY]..." —— 那是一个普通 work todo,不触发 barrier、不享受末尾不变量保护,无害。只有 `metadata.kind="verify"` 才是系统 verify todo,而模型到不了这个字段(见下"结构性防伪造")。

### ①a 结构性防伪造:模型到不了标记字段

**不是靠运行时检查"剥离模型传入的 kind=verify",而是结构性阻断 —— 模型根本没有写入标记的通道。三层:**

1. **工具输入 schema 不暴露 metadata。** `TodoWriteInput`(`agent/tools/todolist/tools/todowrite.py`)的 pydantic 字段只有 `action, todos, todo_id, after_todo_id, content, status, priority, category, plan_ref, flow_id, session_id` —— 没有 `metadata` 字段。模型在工具调用里无法表达 `metadata={"kind":"verify"}`。

2. **`_normalize_rows` 只取白名单字段。** `store_sqlite.py:141` 用 `todo.get()` 只读这 11 个字段构造 INSERT 元组:
   ```
   (session_id, content, status, priority, position, category,
    delegation, subagent_id, flow_id, step_id, plan_ref)
   ```
   模型在 dict 里塞的 `metadata` / `kind` / 任何额外 key —— **逐字节丢弃**,永远到不了 INSERT 语句。

3. **表 schema 现在没有 metadata 列 —— 需要加法迁移。** 现状 todos 表是固定 13 列,无 `metadata`/`kind` 列。所以 verify 标记需要先补一个列:
   ```sql
   ALTER TABLE todos ADD COLUMN metadata TEXT;  -- JSON, nullable
   ```
   - `_normalize_rows` 扩展**系统专用入口**:`_normalize_rows(session_id, todos, *, system_metadata_map=None)`,系统 append verify todo 时传 `system_metadata_map={todo_id: '{"kind":"verify"}'}`;模型走的路径不传这个参数 → 模型 dict 里的 metadata key 仍被丢弃。
   - `_row_to_todo` 读回 metadata,barrier / reminder 据此识别 verify。
   - 关键:**metadata 列只通过系统专用入口写入,`_normalize_rows` 的模型路径(默认参数)不读 input dict 的 metadata key**。即使将来误把 metadata 加进 pydantic schema,模型的 dict 仍然到不了列。

### ①b 末尾不变量:插入其他 todo 时 verify 一定在末尾(靠程序移位)

**主层:service 在调 store 前拦截 `add` 的插入点。** `add` 的 `after_todo_id` 决定新 todo 落在哪:

| 模型调用 | service 拦截后实际落位 |
| :--- | :--- |
| `add(after_todo_id=None)`(append 到尾) | 重写成插到 verify **前面**(新 todo 取 verify 的旧 position,verify 顺移到 position+1,仍是末尾) |
| `add(after_todo_id=<verify_id>)` | 拒绝 `TodoStoreError("Cannot insert after the verify todo; it must remain last")` |
| `add(after_todo_id=<某个 work todo>)` | 正常插入,verify 天然仍在末尾 |

**兜底层:每次变更落库后跑末尾不变量检查。** 不管走哪条路(service 的 add、replace、TaskFlow 直接调 store),提交前/后校验:若 verify 存在但不在 max position,UPDATE 它的 position 到 max。这是防御绕过 service 的路径(见下"泄漏点")。

**`replace` 不需要移位。** service 先剥离模型传入的 verify(若有,虽到不了 metadata 但 content 里可能有 —— 剥离的是系统标记的 verify,模型写的 content 像 verify 的普通 todo 不剥离),再把系统 verify append 到列表末尾,按 index 分配 position —— verify 的 position 天然是 max,by construction。

**⚠ `replace` 时模型抄入 verify-content 项的处理(P3 修正)。** 模型从 reminder 看见 verify todo,做 `replace` 时可能把它抄进新列表。模型抄的那个到不了 `metadata.kind`(结构性阻断),会落库为普通 work todo,content 是 "[VERIFY]...",然后归一化又 append 真 verify → 列表里两个 verify-ish 项。**确定性地剥离**:service 对 replace 的输入列表,按**精确的系统 verify content 模板**(系统控制该模板字符串,可字节精确匹配,不做模糊匹配)剥离任何 content 等于模板的项,再走归一化。配合工具描述告知模型"replace 时不要包含 verify todo,系统会管理它"。

**`patch` / `remove` 不影响排序。** patch 不改 position;remove 一个 work todo 后 verify 仍是剩余里的 max;remove verify 受保护(work 未结束时拒绝,见 ④)。

**⚠ 泄漏点:TaskFlow 的 `append_flow_root_todo` 直接调 `store.add_todo`,绕过 service。** 主层 `add` 拦截抓不到它。两个选择:
1. 把 `append_flow_root_todo` 改走 `service.add_todo`(单一 chokepoint,推荐 —— 一次到位,无 position 抖动)
2. 靠兜底层(末尾不变量 UPDATE)兜住

倾向 1。

### ③ 验收不通过 → 定向回退失败 todo + 改代码,不重跑整表

**这是核心。分两步:reviewer 报告 → 主代理 patch 失败 todo 回 pending → 继续修。**

**reviewer 报告 schema。** reviewer subagent 的最终答复必须是结构化 JSON(在 spawn brief 里要求),形如:

```json
{
  "verified": false,
  "results": [
    {"todo_id": 3, "passed": true, "evidence": "..."},
    {"todo_id": 5, "passed": false, "evidence": "test_foo assert X == Y failed at line 42", "suggested_fix": "..."},
    {"todo_id": 7, "passed": false, "evidence": "...", "suggested_fix": "..."}
  ]
}
```

`todo_id` 是回退的定位键。reviewer 跑的测试按 todo 的 acceptance criteria 分组,每个 todo 一个 pass/fail 判定。

**主代理收到报告后的动作(prompt 强制 + 现有 patch action)。**

```
- On reviewer report {"verified": false}:
  1. For each todo_id with passed=false: todowrite(action="patch", todo_id=N,
     status="pending"). This re-opens ONLY the failing todos; all passed
     todos stay completed.
  2. Attach the evidence to the todo: patch its content or a notes field with
     the reviewer's evidence + suggested_fix.
  3. Do NOT re-run the whole todolist. PlanContinuationEnforcer will inject a
     directive naming only the re-opened todos — fix those, re-spawn the
     reviewer on just those (or the whole list again if cheap), repeat.
  4. Only when reviewer reports {"verified": true} may you patch the verify
     todo itself to completed.
```

**为什么不重跑整表。** `patch(action="patch", status="pending")` 只翻失败的几条,passed 的保持 `completed`。PlanContinuationEnforcer 的 directive 是"列出 pending/in_progress 的 todo"—— 只会点名那几条失败项。主代理只修那几条,不重做已通过的。

**失败 todo 的 evidence 注入(P4 已定)。** 加一个**模型可写的 `notes` 列**(与系统托管的 `metadata` 分开,见 ①a 的 schema 迁移)。evidence 进 `notes`,原 `content` 不动(保留原始任务描述)。`patch(action="patch", notes="...")` 追加;`_row_to_todo` 读回 notes;reminder 渲染时若 notes 非空附在 todo 末尾。`metadata` 是系统字段(模型不可写),`notes` 是模型字段 —— 两者职责分开。

- [ ] `notes` 列随 ①a 迁移一起加;`patch` 支持 notes 字段;reminder 渲染 notes
- [ ] prompt 加"失败定向 patch 回 pending + notes 写 evidence,不重跑整表"强制条款
- [ ] 单测:模拟 reviewer 报告 2 fail → 主代理 patch 那 2 条 status=pending + notes=evidence → 其余保持 completed → PlanContinuationEnforcer directive 只点名那 2 条

### ④ verify todo 的"必须先跑 reviewer"强制(复用 transition barrier)

**⚠ 前置:patch 必须扩展支持 `subagent_id`(G1,致命)。** 现状 `patch_todo_by_id`(`store_sqlite.py:362`)只接受 content/status/priority/category,**不支持 subagent_id**;`TodoWriteInput` 的 patch 字段也没暴露 subagent_id。这意味着模型无法把 reviewer 返回的 `child_session_key` 挂到 verify todo → ④ 的 barrier"verify 必须有 subagent_id"永远不满足 → verify 永远无法 completed → plan 永久卡住。**必须先扩展**:
- `patch_todo_by_id` 加 `subagent_id: str | None = None` 参数(UPDATE 该列)
- `TodoWriteInput` 加 `subagent_id: str | None = Field(default=None, description="patch field: link a subagent child_session_key to this todo.")`(仅 patch 用)
- 这是 verify 流程走通的前置条件,不补则全盘失效

**不造新 gate,复用现有 transition barrier。** `_assert_transition_allowed` 已经检查 `subagent_id` 是否还 running。给 verify todo 设 `subagent_id=<reviewer的child_session_key>` 后,主代理想标 verify todo completed 时,barrier 会拒绝("subagent X is still running")—— 直到 reviewer 跑完。

**补一层:verify todo 必须有 subagent_id。** 现有 barrier 只检查"有 subagent_id 时它是否 running",不检查"必须有"。在 `_assert_transition_allowed` 里加一个分支:若 `todo.metadata.kind=="verify"` 且 `todo.subagent_id` 为空,raise `TodoStoreError("Verify todo requires a reviewer subagent: spawn one and patch its subagent_id first")`。这强制主代理不能跳过 reviewer 直接标 verify 完成。

**⚠ barrier 必须同时管 `cancelled`,不只是 `completed`(防逃避)。** 现状 `_assert_transition_allowed` 只 gate `completed`,模型可以 `patch(todo_id=<verify>, status="cancelled")` 直接跳过验收 —— 整个 verify 机制被绕过。修法:verify todo 的 status 变更 `completed` 和 `cancelled` 都走 barrier。verify 标 `cancelled` 只允许在两条合法路径:
1. **re-spawn 耗尽**:enforcer 注入 `[VERIFY BUDGET EXHAUSTED]` 时 set 一个 `StateKey.VERIFY_BUDGET_EXHAUSTED`(mem + DB 双写,类似 resumable_breakpoint);barrier 检查到这个 flag 才允许 verify cancel;cancel 后 clear flag。
2. **计划整体放弃**:barrier 检查 verify 的 cancel 请求时,读列表确认其余 work todo 全 `cancelled` → 允许(整个计划放弃了,verify 一起 cancel 合理)。

不满足这两条 → `TodoStoreError("Verify todo cannot be cancelled directly; complete it via reviewer, or cancel the whole plan")`。

- [ ] `_assert_transition_allowed` 扩展:verify todo 的 `completed` 和 `cancelled` 都受管
- [ ] **前置(G1):`patch_todo_by_id` 加 `subagent_id` 参数;`TodoWriteInput` 加 `subagent_id` patch 字段** —— 不补则 verify 流程全盘失效
- [ ] 加 `StateKey.VERIFY_BUDGET_EXHAUSTED`(mem + DB 双写),enforcer 注入耗尽 directive 时 set,verify cancel 后 clear
- [ ] verify cancel 的 barrier 逻辑:flag set 或 其余 work todo 全 cancelled → 允许;否则拒

### ⑤ verify todo 等待 reviewer 的状态语义(P2 修正,硬伤)

**问题。** 主代理 spawn reviewer + patch verify.subagent_id 后,verify 仍 `pending` → PlanContinuationEnforcer 看见 pending → 不停注入 directive 驱动"继续做 verify"。但 reviewer 跑完前主代理无事可做,会撞 barrier(标 completed 被拒,subagent running)或浪费地再 spawn 一个 reviewer。

**修法:enforcer 对"verify + subagent running"判为等待中,不驱动。** 在 `PlanContinuationEnforcer` 的 plan 扫描里加一条:若当前唯一 pending/in_progress 项是 verify todo 且它的 `subagent_id` 对应的子代理仍 running → **不注入 continuation directive**,让 turn 自然结束。subagent 完成时,现有 announce pipeline 投递完成通知 → 触发 auto-turn resume(主代理已有的"subagent completion resets continuation latch"机制)→ 主代理读 reviewer 报告并行动。

**状态机:**
```
verify pending, 无 subagent_id → enforcer 驱动(主代理该 spawn reviewer 了)
verify pending, subagent_id running → enforcer 不驱动,turn 结束,等 completion notice
verify pending, subagent_id finished → enforcer 驱动(主代理该读报告了)
verify pending, 无 subagent_id 且 reviewer 从未 spawn → enforcer 驱动(prompt 提醒 spawn)
```

**为何不引入新 status。** 不加 `waiting` 状态(避免改 status 枚举 + reminder 渲染 + 前端)。用"`pending` + subagent_id running"的组合语义,由 enforcer 读取判断。

**报告丢失兜底(reviewer 卡死 / completion notice 丢失)。** continuation counter 在 subagent completion 时重置,但若 reviewer 被卡死/kill 而无 completion notice → counter 不重置 → 15 次后续跑预算耗尽 → enforcer latch 静默 → verify 永远卡在状态③(subagent running 但实际已死)。两条兜底:
1. **liveness 兜底**:enforcer 状态③判定"subagent running"时,顺带读 subagent registry 的 liveness(现有 `_is_subagent_running` 已是 registry 查询)。若 registry 显示该 run 已 terminal(TIMEOUT/KILLED)但 verify 仍 pending → 当作状态④(subagent finished)处理,注入 directive 驱动主代理读报告。
2. **报告不可读兜底**:状态④(subagent finished)注入的 directive 里,若主代理尝试读 reviewer 报告失败(child checkpoint 已清 / `sessions_messages` 不可读 / 结果 caps 截断丢内容)→ directive 文案明确提示"reviewer 报告丢失,重新 spawn reviewer 跑验收"。主代理 re-spawn → 新 subagent_id → patch 覆盖旧 id → 回到状态③。这把"卡死"变成"重跑一次",而非 plan 永久卡死。

注意:re-spawn 不能无限循环。若同一 verify todo 的 subagent_id 被覆盖 N 次(N=`TODOLIST_INFRA` 的一个新配置,默认 2)仍拿不到报告 → enforcer 注入 `[SYSTEM DIRECTIVE: VERIFY BUDGET EXHAUSTED]`,允许主代理用**自己跑目标测试**作为降级路径(回退到 evals修复 ③ 的最低配闭环),并标记 verify 为 cancelled(而非 completed)——计划未通过验收但允许收尾,不卡死。

- [ ] `PlanContinuationEnforcer` plan 扫描加"verify + subagent running → 跳过 directive"分支
- [ ] enforcer 状态③判定时读 subagent registry liveness:run 已 terminal 则当状态④处理(报告丢失兜底 1)
- [ ] 状态④ directive 文案:报告不可读时提示"重新 spawn reviewer"(报告丢失兜底 2)
- [ ] re-spawn 次数上限(默认 2)耗尽 → 注入 `[VERIFY BUDGET EXHAUSTED]` + 允许降级到主代理自跑测试 + verify 标 cancelled
- [ ] 单测:verify pending + subagent running → 无 directive;subagent finished → 有 directive;无 subagent_id → 有 directive(spawn 提醒)
- [ ] 单测:subagent 被 KILLED 但 verify 仍 pending → enforcer 当状态④,注入 directive(兜底 1)
- [ ] 单测:re-spawn 2 次仍报告不可读 → 注入 VERIFY BUDGET EXHAUSTED + verify 可标 cancelled(不卡死)

## 三、闭环时序

```
主代理 todowrite(replace, [todo1, todo2, todo3])
  └─ service 自动 append [VERIFY] todo4(末尾,pending,kind=verify)
主代理做 todo1→todo2→todo3,逐个 patch completed(各自走自己的 transition barrier)
  └─ todo1/2/3 的 acceptance criteria 在 content 里预先写好
主代理 reach todo4(VERIFY)
  └─ prompt 指引:读 todo1-3 的 acceptance → sessions_spawn(reviewer, brief=[todo_id+criteria+cmd])
  └─ patch todo4.subagent_id = reviewer_key
  └─ verify pending + subagent running → enforcer 不驱动,turn 结束(P2 修正)
reviewer 跑完 → announce pipeline 投递完成通知 → auto-turn resume 主代理
reviewer 返回 {verified:false, results:[{todo_id:2, passed:false, ...}]}
  └─ 主代理 patch todo2 status=pending + notes=<evidence>(P4:notes 列,不覆盖 content)
  └─ todo1/todo3 保持 completed,todo2 回 pending,todo4 仍 pending(subagent 已 finished,但 todo2 没修)
  └─ enforcer 驱动:directive 点名 todo2(verify 的 subagent 已 finished,但 todo2 pending)→ 主代理只修 todo2
  └─ 修完 todo2 → patch completed → 再次 reach todo4 → 再 spawn reviewer(可只跑 todo2 或全跑)
reviewer 返回 {verified:true}
  └─ 主代理 patch todo4 completed(此时 barrier:subagent_id 已 finished → 放行)
  └─ plan 完成 → 触发现有 skill_review(独立路径,review skill 文件)
```

**关键不变量:**
- verify todo 永远是最后一个,`kind=verify` 标记
- verify todo 标 completed 前 barrier 强制 subagent_id 已 finished
- 失败只回退被点名的 todo_id,passed 的保持 completed
- PlanContinuationEnforcer 的 directive 天然只列 pending 项 → 不重跑整表

## 六、风险与不做的事

**风险:**
- verify todo 自动 append 可能在不该出现的场景出现(单 todo 小任务、对话式任务)。阈值 ≥2 work todo 降低概率;另可加 `delegation` 字段判定(只有含 `delegation="subagent"` 的计划才插,纯 self 小任务不插)。
- reviewer subagent 跑测试可能很慢/很贵(全量测试)。brief 里允许 reviewer 只跑 acceptance criteria 指定的测试,不跑全量。
- 失败回退若 reviewer 报告的 todo_id 错(幻觉),会翻错 todo。reviewer 报告必须带 evidence,主代理 patch 前应核对 todo_id 在当前列表里存在(`TodoIdNotFoundError` 已有)。**更大的风险:主代理在 spawn brief 里写错 todo_id**(reviewer 只是 echo),mitigation 是主代理从 reminder 读 todo 列表拿正确 id。
- **⑤ 的 enforcer 等待语义是新增耦合**:PlanContinuationEnforcer 现在要读 verify todo 的 subagent_id 状态。若 enforcer 逻辑改坏,verify 可能永远不驱动(plan 卡死)或不停驱动(撞 barrier)。必须有单测覆盖四种状态组合(已列)。
- **reviewer 跑完但主代理 turn 没被 resume**:依赖现有 announce pipeline + auto-turn trigger。若 subagent completion notice 丢失,verify 永远 pending + subagent finished → enforcer 驱动主代理读报告,但报告可能已不可读(child checkpoint 被清理)。mitigation:主代理被驱动时若报告不可读,重新 spawn reviewer。
- **归一化的性能**:`_normalize_verify` 在每次 todowrite 落库后跑(SELECT verify position + 可能 UPDATE)。todo 列表通常 <50 项,开销可忽略,但需确认不在热路径上造成可测延迟。
- **G5(patch verify content 允许)**:模型可 patch verify 的 content(content 是 patchable 字段)。无害 —— barrier/enforcer 用 `metadata.kind` 不用 content 判定。允许,不额外限制。
- **G6(模型伪造 subagent_id)**:patch 支持 subagent_id 后,模型可填一个假 key。`_is_subagent_running(假key)` 返回 False → barrier 可能放行 completed。这是所有 todo 的既有信任模型(work todo 经 replace 也一样,假 subagent_id 不被校验)。verify 同样信任模型用 sessions_spawn 返回的真 key。**接受此风险,不为 verify 单独造 registry 校验**(若未来要堵,barrier 可加"subagent_id 必须对应 registry 里一个真实 terminal run")。
- **G7(续跑预算与 verify 循环)**:subagent completion 重置 continuation counter,但主代理在两次 spawn 之间若做多次 fix turn 会烧 continuations。可接受 —— prompt 驱动每次 fix 后立即 re-spawn reviewer,每个 cycle 一个 completion 重置一次。若 fix 轮过多撞 15 上限,enforcer latch 静默,需用户介入(可接受:复杂计划本就需要人工)。

**不做:**
- 不加 hard "tests must pass before finish" 全局 gate(同 `计划_evals修复_20261109.md` 四的立场)—— 本计划的 barrier 只在 verify todo 这一个特殊 todo 上生效,不强制所有 todo。
- 不让 reviewer subagent 自己改代码(只读 + 报告),改代码永远是主代理的职责。
- 不自动解析 reviewer 报告并 auto-patch(主代理读报告后手动 patch)—— 自动化那一层风险高(报告幻觉),先做半自动。

## 第一批

## 1. H5 局域网手机访问

### 1.1 目标能力

手机浏览器在同局域网访问桌面会话续聊：H5 静态网关 + token 鉴权，手机扫码或输 token 连接，复用桌面会话的 WS 协议。

### 1.2 Sherry 现状

Tauri 桌面单端，Robyn 后端绑 `127.0.0.1:8080`，WS 无 auth（桌面 Tauri 直连 loopback）。消息流/HITL/流式 chunk 都已经是 WS frame。

### 1.3 前置可行性确认（必须先做）

> **这是本特性的门控步骤。不通过则不启动。**

Sherry 当前 WS 握手无 auth（loopback 信任）。bind 到 `0.0.0.0` 后，**同 WiFi 任何人知道端口即可连**。必须确认：

- WS 握手协议能否加**可选 auth**（桌面 Tauri client 本地豁免或带 token；H5 client 强制 token）
- 加 auth 是否需要改桌面 client 的 WS 连接逻辑（若需要，成本从"小"上调为"中"）
- Robyn 的 WS 实现是否支持连接级鉴权

**确认结果决定成本量级与是否推进。**

### 1.4 目标架构（可行性通过后）

```
桌面端（Robyn）
  ├─ 127.0.0.1（默认本地，无 auth）
  └─ 0.0.0.0（H5 开启，WS 握手强制 token）
        ├─ /h5/*（静态移动端页）
        ├─ /h5/auth（token 签发，扫码/密码）
        └─ ws（H5 client 带 token，桌面 client 本地豁免）

手机浏览器 → http://<桌面IP>:8080/h5 → token → 连 ws
```

### 1.5 实施步骤（可行性通过后）

1. 后端 host 可配 + WS 握手可选 auth 中间件（`server/service/h5_access_service.py`）
2. 移动端精简页 `client/app/pages/h5/`（复用 `use-chat-stream.ts` WS composable，仅对话 + HITL 简化卡）
3. 设置面板 H5 开关 + 局域网二维码

### 1.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 局域网暴露后端 | 默认关闭；开启强制 token；绑定局域网段 |
| WS auth 改握手影响桌面 client | 前置可行性确认；本地豁免路径 |
| 桌面 + 手机并发操作 | 复用现有 turn busy 检测，同 session 同时一个 turn |

### 1.7 Kill criteria

- 若 WS 握手无法加可选 auth（Robyn 限制或桌面 client 改动过大），H5 **搁置**，记原因

### 1.8 验收

- 手机连桌面收发消息 + HITL approve/deny
- token 失效拒绝连接
- 关闭 H5 后回 loopback，外部不可达
- 桌面端原有功能不受影响

## 2. TTS 语音输出

### 2.1 目标能力

agent 回复可语音朗读：本地 TTS 合成 + 流式回复按句切分送合成 + 播放队列。配合角色扮演场景的角色音色一致性。

### 2.2 Sherry 现状

只有 STT 输入（FunASR daemon，`127.0.0.1:9011`，按需 spawn / loopback HTTP）。无 TTS 输出。

### 2.3 与 STT 的关键差异（非同构）

> **不能当 STT 的同构镜像处理。**

| 维度 | STT | TTS（本特性） |
|---|---|---|
| 调用形态 | 一次性请求-响应 | 流式回复需连续合成 + 播放队列 |
| 背压 | 不涉及 | 回复产出速度可能快于合成速度，需队列/背压 |
| 断句 | 不涉及 | 四语言断句（日韩无明确标点，比中文/英文难） |
| 音色一致性 | 不涉及 | 角色扮演需跨会话固定角色音色 |

### 2.4 目标架构

```
主进程（HTTP client）            TTS daemon 子进程（按需 spawn）
  synthesize(text) ──HTTP──▶ /synthesize   本地 TTS 引擎常驻
                                返回音频流

前端
  流式 chunk → 断句 → 入合成队列 → 逐句合成 → <audio> 播放队列
  背压：合成跟不上时丢弃中间句保留首尾 + 当前句
  自动/手动朗读开关
  角色音色配置（speaker 持久化到 session/角色档案）
```

### 2.5 实施步骤

**步骤 1：TTS daemon 脚本**
- `skills/builtin/core/text_to_speech/scripts/server.py`（参照 STT 结构，但接口形态不同）
- 端口 9015，pid 文件 `.tts_daemon.pid`，复用 daemon 公共骨架

**步骤 2：主进程 TTS 服务**
- `server/service/audio_synthesize_service.py`：HTTP proxy，按需 spawn，`GET /audio/synthesize/status`

**步骤 3：前端朗读控件（含队列 + 背压）**
- 断句：中文/英文标点为主；**日韩单独子任务**（用 ICU 分句或语言检测库，不能只靠标点）
- 合成队列：逐句调 `/synthesize`，顺序播放
- 背压：队列长度超阈值（如 5 句）时丢弃中间句保留首尾 + 当前句，避免积压
- 角色音色：speaker 选择持久化到 session 设置 / 角色档案（**音色身份方案待定**：固定 speaker vs 声纹克隆，先做固定 speaker）

### 2.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 流式产出快于合成 → 积压 | 背压策略（丢中间保首尾） |
| 日韩断句不准 | 单独子任务，ICU/语言检测库 |
| 角色音色跨会话不一致 | speaker 持久化；先固定 speaker，克隆后置 |
| daemon 模型缺失 | 按钮 disabled + toast（同 STT） |

### 2.7 Kill criteria

- 若四语言断句质量无法达到可接受（日韩频繁断错），先只支持中/英 TTS，日韩后置
- 若合成延迟导致背压策略频繁丢句、朗读不可听，回退为"整段回复完成后一次性合成"（牺牲流式体验）

### 2.8 验收

- 中/英流式回复朗读连贯
- 背压策略在长回复下不积压
- 自动/手动朗读开关
- daemon 不可达降级（不阻塞对话）
- 角色音色跨会话一致
- STT 输入不受影响

## 3. 记忆关联层

### 3.1 目标能力

记忆四层处理理念（观察→片段→抽象→关联）中的**关联层**：记忆间跨链接，召回时顺关联跳到相关记忆。

### 3.2 Sherry 现状

MesMemory 扁平 entry 列表（memory/user/facts，带 embedding + 语义召回 + reranker），有 consolidation（去重/消歧/重路由），无 entry 间关联图，召回单跳。entry 有 `archived` 软删除。

### 3.3 简化采纳

不搬四层管道，只引入**关联层**：entry 间加关联边，consolidation 时 LLM 推导关联，召回时图扩展 1-2 跳。

### 3.4 实施步骤

**步骤 1：关联表 schema**
- **复用 `计划_声明性知识提炼层` 的 `memory_relations` 表**（不重建——两计划共用一张表，relation_type 区分）
- 关联层用 `relation_type`：`causes` / `refines` / `contradicts` / `temporal`
- 知识提炼层用 `relation_type='evidence'`（已在该计划定义）
- `source_kind` 列：关联层的 entry↔entry 边 `source_kind=NULL`（或 `'memory_entry'`）；知识提炼层的 abstraction→source 边 `source_kind='memory_entry'/'message_turn'/'handoff_run'`
- **archived 处理**：关联边查询时过滤 `target_id` 已 archived 的行（级联软删：source archived 时其出边也标记失效）

**步骤 2：consolidation 推导关联**
- `run_memory_consolidation` 增加关联推导步骤（仅对新/改 entry）
- fail-open

**步骤 3：召回图扩展**
- `memory_recall.py` 向量召回 top-N → 查关联表 1-2 跳 → 合并去重 → reranker 重排
- **预算交互设计**：向量召回 top-N 与图扩展结果合并后总条目数封顶（如 2×N），再过 reranker 取最终 top-K，避免图扩展爆炸
- 扩展条目标注来源（向量命中 / 关联跳转 + 类型）

**步骤 4：噪声离线评估（上线前必须做）**
- 取一批历史 entry，让 LLM 推导关联，人工标注准确率
- 准确率达标（如 >70%）才上线；不达标则调 prompt 或降权图扩展

### 3.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 推导关联噪声大 | **上线前离线评估**（硬门控）；权重阈值；reranker 重排；fail-open |
| 图扩展爆炸 | 预算封顶（2×N）再 reranker |
| archived entry 关联悬空 | 查询过滤 + 级联软删 |
| consolidation 成本增加 | 仅对新/改 entry 推导 |

### 3.6 Kill criteria

- 若离线评估准确率 <70% 且调 prompt 后无法达标，**关联推导不上线**，关联表保留但仅手动维护
- 若图扩展上线后召回质量（人工评估）下降，关闭图扩展，保留向量召回

### 3.7 验收

- 离线评估准确率 ≥70%
- 召回结果含关联跳转且相关
- archived 关联正确过滤
- 噪声不顶替高质量向量命中
- 回归：现有语义召回测试全过

## 4. 交互式 PTY 终端

### 4.1 目标能力

真正的 PTY（PowerShell/Bash/Zsh + xterm.js），交互式全屏，常驻 shell，agent 和用户都能用。

### 4.2 Sherry 现状

工具箱终端是一次性 console（`POST /terminal/run` 跑一行返回 exit code），agent 的 `terminal` 工具单次执行 + HITL。无法跑 vim/top/ipython。

### 4.3 技术方案（明确）

- **Windows**：conpty（Tauri 侧 Rust 用 `portable-pty` 或 windows crate）
- **Unix**：ptmx（同库跨平台）
- 不用 Python pexpect（Windows 兼容性差）
- PTY 是**用户工具箱 tab**，agent `terminal` 工具保持单次执行 + HITL 不变

### 4.4 实施步骤

1. Tauri 侧 Rust PTY session manager（`portable-pty` 跨平台）
2. WS frame：`pty_input`/`pty_output`/`pty_resize`/`pty_exit`
3. 前端 `TerminalPanel.vue`（xterm.js + addon-fit）
4. 生命周期 + 并发上限（见 4.5）

### 4.5 并发与资源管理

> Sherry 是 KeepAlive 多会话模型，每个活跃会话一个 PTY 会累积。

- **并发上限**：同时活跃 PTY 数封顶（如 8），超限 LRU 淘汰最久未用的（kill 其 shell，tab 提示已结束）
- 会话关闭 / deactivate 时 kill PTY
- 空闲超时（如 30 分钟无输入）自动 kill

### 4.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| PTY 进程泄漏 | 并发上限 + LRU 淘汰 + 空闲超时 + 会话关闭 kill |
| Windows conpty 兼容 | Tauri 侧 Rust `portable-pty`，不用 Python |
| 与 agent terminal 工具混淆 | 明确分离，agent 工具不改 |

### 4.7 Kill criteria

- 若 Windows conpty 在目标系统不稳定（频繁崩溃/乱码），Windows 暂只支持一次性 console 模式，Unix 上 PTY

### 4.8 验收

- vim/top/ipython 正常
- 多会话并发 PTY 不超上限
- 会话关闭 / LRU 淘汰时 PTY 清理
- agent terminal 工具不受影响

## 5. 会议模式 / 多智能体审议 — 决定不采用

**决定：不采用会议模式（多角色审议→质询→投票裁决）。**

理由：
1. **Sherry 已有多专家并行执行**（subagent spawn + TaskFlow DAG + lane 并发 + 角色隔离），覆盖了"可分解执行"场景，比同类工具的派工模型更深。会议模式解决的是"开放性决策"，不是执行。
2. **价值存疑**：LLM"开会"仍是同一模型用不同 persona 自说自话，多样性是人造的。N 个 persona 调用是否真比同模型 N 轮自反思（self-reflection）强，经验上存疑——会议模式成本（N×M 调用）可能数倍于主 agent 深度推理，而无对照评估证明质量更优。
3. **Sherry 已有替代**：主 agent 深度推理（多轮 self-reflection）+ CompletionJudge 判定已覆盖决策场景，成本更低。开放性决策可走这条路，不需引入会议编排。
4. **参考实现不可验证**：同类工具的会议模式实现不可见（插件源码不在仓库）、有已知 bug（工作/会议模式记忆只写不读），照搬风险高。

**结论**：不引入会议模式。本计划移除该条目。开放性决策由主 agent 深度推理 + CompletionJudge 承担。

## 第三批

## 6. 进程插件通道 — 待论证必要性（与 Python 三通道计划主题重叠）

### 6.1 与 Python 三通道计划的关系

`计划_Python版三通道插件体系` 已经回答了本节的部分问题：
- 事件总线 → 三通道方向三（`runtime/event_bus.py`，可选/后置）
- Process 通道 → 默认 MCP stdio（三通道方向一已落地设计）
- 权限 → OS 级隔离 + PathGuard（三通道 §1.9）
- 生命周期 → daemon 骨架 + lazy spawn + atexit kill（三通道 §1.7）

**本节的"待论证"问题应转向三通道计划未覆盖的维度**（如 MCP 的细粒度权限 vs Sherry 自定义权限、lane 集成限流），而非重复三通道已答的问题。如三通道方向三（事件总线）落地，本节的进程插件通道论证可关闭——三通道已是完整方案。

### 6.2 待论证问题（仅限三通道未覆盖的）

1. **MCP 细粒度权限**：MCP 是否支持文件/网络授权？Sherry 是否需要比 OS 隔离更细的权限（如路径级 allow/deny）？→ 宿主能力授权计划（D5）部分覆盖
2. **lane 集成限流**：插件工具调用是否走 lane 限流（SUBAGENT/MAIN）？三通道未涉及
4. **复用 lane 经验**：Sherry 的 lane 隔离经验能否直接作用于 MCP 子进程？若能，是否不需要新通道？

### 6.3 决策

- 若上述问题能给出 MCP 不可替代的清晰答案 → 推进，单独立实施计划
- 若不能 → **砍掉，用 MCP 替代**，把精力放在 MCP 的生命周期/权限增强上（而非新协议）

### 6.4 Kill criteria

- 论证无法给出不可替代价值 → 砍掉，不进实施

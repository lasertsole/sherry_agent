## 0. 背景（已核实）

### 0.1 sherry 现状：后台命令基础设施搭了 80%，缺 kill 入口与前端

sherry **已有**完整的后台命令"启动 + 查询 + 退出通知"链路：

- `terminal(run_in_background=True)` → `_run_background`（`terminal.py:600-719`）：spawn 子进程（用 `_process_group_kwargs()` 做进程组隔离，`:668/681/690`），立即返回 task_id，输出写保留文件（`terminal-bg-*.log`），在 `background_registry` 注册 `BackgroundTask`（记录 `pid`/`pgid`/`status`/`output_path`，`:645-704`），起独立 watcher 监听退出。
- watcher（`terminal_bg_registry.py:141-167`）：`await proc.wait()` → 更新状态 → `_push_exit_notification`（广播 WS `terminal_bg_exit` 帧，`:169-185`）+ `_trigger_auto_turn`（用退出报告唤醒 agent，`:187-211`）。
- 查询工具 `terminal_bg(action='list'|'output')`（`terminal_bg_tools.py:90-111`）。
- session 删除时 `kill_session_tasks(session_id)`（`:103-129`）批量杀进程树：`kill_process_tree(SimpleNamespace(pid=task.pid), pgid=task.pgid or task.pid, grace=1.0)`——**进程树杀逻辑已完整**。

**缺的三块**：
1. registry 无单任务 kill 方法（只有批量 `kill_session_tasks`）。
2. `terminal_bg` 工具无 `kill` action（只有 list/output，`terminal_bg_tools.py:111` 未知 action 报错）；无 WS/HTTP kill 端点。
3. **前端完全不渲染后台任务**——grep `terminal_bg_exit`/`terminal_bg`/`run_in_background` 在 `client/app/` 零命中；watcher 推的 `terminal_bg_exit` 帧前端不处理。

### 0.2 取消粒度：sherry 是 turn 级，ZCode 是命令级

- **sherry**：WS `stop` 帧 → `_cancel_session` 对整个 turn 的 asyncio task 调 `task.cancel()`（`messages.py:144-163`）。后台 watcher 是独立 asyncio task（`create_task`，`terminal_bg_registry.py:137`），**turn stop 不杀后台命令**——它们要么自然退出、要么等 session 删除被批量杀。前台命令随 turn 死（CancelledError 顺带 `akill_process_tree`）。**没有"保 turn、停单条命令"的入口**。
- **ZCode**：命令级取消是独立路径——前端 `CancelButton`（`ConversationBackgroundWorks.tsx:64`）经 v4 `cancelBackgroundWork {workId}` → `runtime.cancelBackgroundTask` → `executionPort.cancelBackgroundTask` → `AbortController.abort()` → `terminateProcessTree`（`background.ts:206-292`）。后台命令在 `commitBackground` 时 `removeExternalAbort`（`lifecycle.ts:199`）主动脱离 turn abort，所以 turn stop 不误杀后台命令，两者互不干扰。

### 0.3 关键结论

sherry 的后台命令进程树杀逻辑（`kill_session_tasks`）**已经存在并经过验证**，单任务 kill 只是把它从"遍历 session 全部 running 任务"收敛到"按 task_id 取一条"。前端面板参考 ZCode 的 `ConversationBackgroundWorks.tsx`。**整体是补齐已有链路，不是从零搭建**。

## 1. ⚠️ 硬约束

| 约束 | 含义 | 验收方式 |
|---|---|---|
| **F1**：registry 进程级单例不变 | 后台任务是本进程子进程，不持久化；重启无残留（OS 回收孤儿） | 不引入 DB/磁盘持久化 |
| **F2**：现有 list/output 向后兼容 | `terminal_bg` 加 `kill` action 是新增；老 action 行为不变 | list/output 测试不变 |
| **F3**：WS 协议追加 | `terminal_bg_kill`/`terminal_bg_started` 是新帧；老前端忽略未知帧不崩 | 老前端收新帧走旧行为 |
| **F4**：kill 是命令级 | kill 单条后台命令不影响当前 turn / 其它后台命令 | kill 期间对话不中断 |
| **F5**：fail-open | kill 失败（任务已死/task_id 不存在/非本 session）提示错误，不崩 | 后端拒绝时前端提示 |
| **F6**：session 归属校验 | 只能 kill 本 session 的后台任务（task_id 绑定 session_id） | 跨 session kill 被拒 |

## 2. 任务一：MVP —— 后台命令前端可终止（必做）

### 2.1 目标

agent 起了一条后台命令 → 前端聊天区出现"后台命令"面板（显示 command/status/pid）→ 用户点"终止"按钮 → 该命令进程树被 kill，面板状态更新为"已终止"，对话不受影响。agent 也能用 `terminal_bg(action='kill', task_id=...)` 自己终止。

### 2.2 核心思路：复用 `kill_session_tasks` 的进程树杀逻辑

`kill_session_tasks`（`terminal_bg_registry.py:103-129`）的核心是：
```python
kill_process_tree(SimpleNamespace(pid=task.pid), pgid=task.pgid or task.pid, grace=1.0)
self.update(task.task_id, status="killed")
```
单任务 kill 就是把这段从循环里抽出来，按 task_id 取一条执行。kill 后 watcher 的 `proc.wait()` 会返回（进程已死），自然触发 exit 通知——但需处理 watcher 覆盖 "killed" 状态的竞争（见 2.4）。

### 2.3 后端改动清单

#### (a) registry 加单任务 kill 方法

- [ ] **2.3.1** `agent/tools/terminal_bg_registry.py` 新增 `kill_task(task_id, session_id=None) -> bool`：
  ```python
  def kill_task(self, task_id: str, session_id: str | None = None) -> bool:
      """Kill ONE background task's process tree (command-level cancel).

      Reuses kill_session_tasks' tree-kill logic, scoped to a single task_id.
      Returns False if the task is missing / already dead / not this session's.
      """
      from types import SimpleNamespace
      from agent.tools.pub_base.process_reap import kill_process_tree

      task = self._tasks.get(task_id)
      if task is None:
          return False
      if session_id is not None and task.session_id != session_id:
          return False  # F6: cross-session kill refused
      if task.status != "running" or task.pid is None:
          return False  # already dead
      try:
          kill_process_tree(
              SimpleNamespace(pid=task.pid),
              pgid=task.pgid or task.pid,
              grace=1.0,
          )
      except (OSError, ProcessLookupError):
          pass  # already dead: the watcher will record that
      self.update(task_id, status="killed")
      return True
  ```

### 2.5 风险与约束

- **watcher 覆盖 killed 状态**：`_watch` 的 `update`（`:153-157`）无条件覆盖 status。kill 后 proc.wait() 返回，watcher 会把 "killed" 改成 "failed"（非零退出码）。**必须**按 2.3.2 加 `task.status == "killed"` 守卫，否则前端面板状态闪烁（kill→killed→failed）。
- **kill 与 watcher 的退出通知重复**：kill 后 `terminal_bg_kill_ack`（即时）和 `terminal_bg_exit`（watcher 检测到退出后）都会到前端。前端以 exit 帧为终态权威，ack 只是"已发 kill 信号"的即时反馈（按钮禁用），exit 帧确认 status。参考 ZCode 的 `cancelRequestedAt`（`background.ts:217-228`）即时禁用按钮 + `BackgroundTaskCompleted` 确认终态。
- **进程组杀的跨平台**：`kill_process_tree` 已处理 POSIX（`start_new_session` → 进程组 SIGTERM/SIGKILL）和 Windows（`CREATE_NEW_PROCESS_GROUP` → taskkill /T /F）。单任务 kill 复用同一路径，无需新写平台分支。
- **agent 自动终止 vs 用户终止**：两条路径（`terminal_bg(action='kill')` 工具 / WS `terminal_bg_kill` 帧）都调同一个 `registry.kill_task`。agent 终止走工具返回文本；用户终止走 WS ack + exit 帧。两者都触发同一个 exit 通知（2.3.3 区分 reason）。
- **输出查看**：MVP 面板只显示 command/status/pid，不嵌入输出尾查看（避免面板复杂度）。用户要看输出可让 agent 调 `terminal_bg(action='output')`。阶段二可加行内展开。

**验收**：F1–F6。新建 `tests/agent/tools/test_terminal_bg_kill.py`（kill_task 单任务 / watcher 不覆盖 killed / 跨 session 拒绝）+ `tests/server/test_ws_terminal_bg_kill.py`（WS 帧 handler）+ 前端组件测试。

## 3. 任务二：前台超时自动转后台（可选）

### 3.1 目标

借鉴 ZCode 的 `auto_on_timeout`（`node-execution-adapter-lifecycle.ts:217-222`）：前台命令超时**不直接 kill**，而是转成后台命令（detach + 注册 + watcher）。转后台后天然获得"可单独终止"能力——用户能在面板上 kill 它，而不是只能停整个 turn。

### 3.2 思路

- `agent/tools/terminal.py` 前台超时分支（`:481-494` sync / `:832-846` async）：当前是 `TimeoutExpired` → `kill_process_tree`。改成：超时 → 调 `_run_background` 的 detach 逻辑（复用 `:600-719`）→ 返回"命令超时，已转后台，task_id=..."。
- 需保留前台已产生的输出（前台是管道/文件直写，转后台要衔接输出文件）。
- 转后台后推送 `terminal_bg_started` 帧（2.3.6），前端面板显示，用户可终止。
- 配置开关 `TERMINAL_BG["auto_on_timeout"]`（默认 off，保持现有 kill 行为；on 才转后台）。

### 3.3 不做的原因（阶段一）

- 前台超时转后台要处理输出衔接（前台管道 → 后台文件）、turn 的阻塞 await → 立即返回的语义切换、模型看到"超时转后台"而非"超时被杀"的 prompt 影响。
- 阶段一先让"显式 `run_in_background=True`"的命令可终止（这是用户最直接感知的场景：agent 起了后台任务，用户想停）。前台超时转后台是体验优化，观察阶段一使用后再定。

## 6. 不做的事

| 项 | 不做的原因 |
|---|---|
| 后台任务持久化（DB/磁盘） | 进程是本进程子进程，重启无残留（OS 回收孤儿）；ZCode 也不持久化进程句柄 |
| 前台命令"保 turn、停命令"（不转后台） | 前台命令阻塞在 turn task 内的 `proc.wait()`，单独停需把执行与 turn 解耦——ZCode 用 auto_on_timeout 转后台解决，阶段二对齐，不另造路径 |
| 后台任务输出嵌入面板查看 | MVP 只显示状态；输出查看让 agent 调 `terminal_bg(action='output')`，阶段二加行内展开 |
| 后台任务跨 session 管理 | task_id 绑定 session_id，只能管本 session 的（F6） |
| PTY / 交互式后台 shell | sherry 的后台命令是 spawn + 文件直写（非 PTY），交互式程序无意义；用户交互式终端是独立的 taskbar console（`/terminal/run`，one-shot） |
| turn stop 杀后台命令 | 保持现有语义：turn stop 不杀后台（watcher 独立 task）；后台命令靠本方案的 kill 入口单独终止 |

## 一、基线事实: 现在能测什么、不能测什么

### 1.1 外部基准: 集成为零（确信的否定）

对全仓库做大小写不敏感搜索，关键词覆盖 `swe-bench|swebench|terminal-bench|terminalbench|webarena|browsergym|agentbench|tau-bench|tau2|osworld|bfcl|lm-eval|opencompass|holodeck|corebench|swe-gym|mle-bench|deep-research-bench|gaia`，返回**零命中**；中文 `榜单` 也从未出现。因此当前**没有**外部基准的适配器、harness 入口、结果格式映射或榜单输出。`[源码确认]`

结论: 要谈外部基准，得**从零建 harness**，这不是「接一下」的事。

### 1.2 内部 `evals/`: 5 个自设计套件，不是基准

注册表是 `evals/evals.py:21-27` 的硬编码 dict，运行器 `uv run python evals/evals.py [suite ...]` 顺序执行。逐套件事实（均 `[实测]`）:

| 套件 | 评什么 | 阈值 / 退出语义 | 成本 |
| --- | --- | --- | --- |
| `graph_rag` | RAGAS（Faithfulness / AnswerRelevancy / LLMContextRecall / ContextPrecision） | **无任何 pass 判据**，只打印指标 | 需活体辅 LLM（提取器兼裁判）+ embedding（默认本地 `bge-m3` GGUF，首次自动下载） |
| `subagent` | 真实 `spawn_subagent_direct` 跑 3 个确定性微任务 | 算 `success_rate`，**无阈值、不影响退出码** | 真实 LLM |
| `long_running_task` | TaskFlow create→run→dispatch→wait→resume，3 步依赖链 | 算 `step_success_rate`；**唯一能退出非零**，但仅在**流程 stalled** 时 `SystemExit(1)`，低成功率不触发 | 真实 LLM 子代理 |
| `session_memory` | 6 项检查（cooldown 重启存活、compaction 锁互斥、checkpoint 往返、幂等重放、上下文资格过滤、语义检索排序） | 无阈值 | 6 项中 5 项用 stub 模型（无 token 成本），第 6 项需真实本地 embedding。**基本 hermetic，最便宜** |
| `nudge_extraction` | 辅 LLM 裁判计划抽取 | **全框架唯一硬编码阈值**：`skill_created AND grounded_in_run AND quality >= 6`（`evals/nudge_extraction/suite.py:456`） | 需 `MAIN_LLM_API_KEY` + `AUXILIARY_LLM_API_KEY`，读**套件内** `evals/nudge_extraction/.env`（非仓库根）；缺失时写 `skipped` 报告并**退 0**（静默跳过） |

### 1.3 结构性缺陷（均 `[实测]`）

- **无基线、无历史、无趋势文件**：结果只落 `evals/results/<suite>/<run_id>/eval_report.json`，而 `evals/results/` 被 `.gitignore:11-12` 忽略，每次运行是孤儿。
- **不进 CI**：`.github/workflows/ci.yml` 与 `scripts/verify_feature.sh` 都不调 `evals/evals.py`；`ci.yml:76-79` 只是 bandit SAST 步骤里的一段注释，说明 `evals` 与 tests 被排除在那次扫描之外（该 step 的 `uvx bandit -r agent server config ...` 从不包含 `evals`），没有任何 job 调用 `evals.py`。
- **结果陈旧且集中在一次批量失败**：五套**都出过结果**，但每套最新一次都停在 2026-09-13/14（约三周前）。其中 4 套的最新一次属同一批 `2026-09-14 21:10-21:12` 的连续运行，且**全部 0.0 / 全 error**；只有 `graph_rag` 最新一次（`20260913_070724`）在这批之外。`[实测]`
- **这批 0.0 的成因分两种，不可一概而论**（`[实测]`，逐个报告核对）：
  - `session_memory/20260914_211038` 与 `nudge_extraction/20260914_211104` 的报告**字面**含 `RateLimitError 429 ... 余额不足或无可用资源包` → 可判为**额度故障**，应标 `invalid_run`。
  - `subagent/20260914_211133` 与 `long_running_task/20260914_211252` 的报告**没有**这段文字，只记录 `outcome: "error"` + `result_text` 为空 + 每例约 18-22 秒（快速失败）。与同批错误**同形但未被证实**为额度问题 → 属**待查故障**，不得按额度故障抹平。
- **报告相对代码过期**：报告列 7 个 `session_memory` 检查，当前代码只有 6 个（`facts_extraction_llm` 检查已在 commit `e9cb198f` 移除）。
- **不可复现，且原因未归因**：历史结果 `session_memory` 0.57 / 0.71 / 1.0 / 0.86；`subagent` 1.0 / 1.0 / **0.0**；`long_running_task` 1.0 / **0.0**；`nudge_extraction` 0.2 / 1.0 / 0.2。其中 2 份可归因额度（见上），另 2 份（`subagent` / `long_running_task` 的 0.0）**原因未记录**，因此当前无法区分「能力不足」与「环境故障」。
- **dispatcher 无失败退出码**：`main()` 返回 None，套件失败或跳过时仍退 0。
- `evals/sandbox.py` 是隔离模式（把全部 SQLite store / checkpoint 重定向到 per-run 目录；child agent 工具收窄到 `{read_file, search_files, question}`，`terminal` / `python_repl` 不进该白名单；设置 `SANDBOX_POLICY`），可复用于基准隔离。

### 1.4 现有真实 LLM 验证资产

`llm_e2e` marker 出现在 22 个文件中，其中 **19 个是测试文件**（另 3 个是 `tests/conftest.py`、`tests/agent/tools/subagent/conftest.py`、`tests/run_tests_split.py` 等基础设施，不含测试函数）；其中 **12 个文件在 `tests/full/`**。这三个计数于 2026-10-06 复测仍成立 `[实测]`。但**函数数已从原文的「约 76」降为 60**：`uv run --no-sync pytest tests/ -m llm_e2e --collect-only -q` 实测 `60/6885 tests collected (6825 deselected)` `[实测]`。经 `uv run python tests/run_tests_split.py --with-llm-e2e` 运行，默认被排除。

注意口径差异：仓库 README 统计的是 `tests/agent/tools/subagent/` 子集加 RAG 一例，即「**8 个测试 / 5 个文件**」（原文写的「7 个测试 / 4 个文件」已于 2026-10-06 更正）；AGENTS.md 的「约 47 用例」是 `tests/full/` 一次实测的净用例数。这些口径与上面的 22/19/12 文件计数、60 函数计数**互不相同**，引用时须写明范围，不可混用。AGENTS.md 记录实测：约 47 用例 ≈ 10.8 分钟净测试时间，但批量时墙钟 **≈ 73.7 分钟**，因此规定「一个文件一个进程 + 外部看门狗」。

### 1.5 基线结论

**当前不存在任何可复现的成熟度数字。** 可复现的最小单位只是「单次运行的原始报告」，其中一部分还被额度故障污染。这是本方案的出发点。

## 三、SWE-bench 类 spike（本轮重点）

### 3.1 为什么代码类最匹配

- **工具面**: harness 驱动 MAIN agent（depth 0），拿到完整工具集（`build_main_tools()` 约 38 个固定工具 + MCP；MCP 默认空配置即 0）。角色门控（MAIN / ORCHESTRATOR / LEAF + `main_only`）**只作用于 subagent**（depth ≥ 1），不是 harness 的阻塞。`[源码确认]`
- **强项**: 代码智能是真实优势（关键词 + 符号索引 + ast-grep + LSP + 语义检索）；对标文档记录另一产品**无**内置索引。
- **取 diff 便宜**: SWE-bench 类任务仓库是 **git checkout at base commit**，patch 可由 `git -C <task_repo> diff <base_sha>` 直接取，无需从模型输出里解析 diff。`[行为推断]`
- **独立审计轨迹: 已消失，此路不通。** 原文称 `fa8b7d0b` 按写入记录前/后字节 + revision + 归属工具调用，是「模型无关的审计轨迹」，且配套 `revert.py` 已注册为 MAIN 工具（`agent/tools/__init__.py` 的 `build_file_changes_revert_tool`）。**这两项均已在 `36a6ad0a`（refactor: delete the file-snapshot & revert machinery, P5 taken early）被整体删除** `[实测]`：当前 HEAD 的 `agent/tools/__init__.py` 已无 `build_file_changes_revert_tool`，`SHERRY_FILE_SNAPSHOTS_DB` 在 `config/` `server/` `agent/` 全域零命中。因此 **harness 不再能拿写入前后的字节做独立交叉验证**，diff 判定只能依赖 `git -C <repo> diff <base_sha>` 本身（或子代理 worktree 的合并结果，见 §八末行）。
- **仍然存在的写入侧约束**（不是审计轨迹，只是并发保护）：`write_file` / `patch_file` 走 `file_write_lock`（`agent/tools/pub_base/file_lock.py`：进程内 per-path `threading.Lock` → 跨进程 `flock`）+ `atomic_write_text_no_follow`（`atomic_write.py`）；`patch_file` 另有两层 CAS（读时指纹 + `expected_revision` 在 `os.replace` 前复断言）；`write_file` 需 READ-BEFORE-WRITE 许可（`agent/tools/pub_base/read_state.py`），其 revision 作为 `expected_revision` 随原子写入落下。`terminal` / `python_repl` **绕过全部这些**（子进程不取锁），这是刻意边界。`[源码确认]` **注意**: 对话 rewind 曾由 `60497a77` 引入、再由 `5958b17e` **刻意移除**；随后文件级回退本身也被 `36a6ad0a` 删除 —— 故当前**既无会话级重写、也无文件级回退**，harness 若依赖任何回退能力需自行实现。
- **注意**: `terminal` 能跑会改状态的 git 命令，diff 必须相对 **pinned base SHA**，且禁止任务仓库内 commit。

### 3.3 人格处理：选定 A（隔离进程 + 中性 workspace）

**决策: 采用 A。** 目标是让数字可与公开基准对比，代价是必须自建中性人格（见下）。

| 选项 | 做法 | 得到什么 | 代价 / 风险 |
| --- | --- | --- | --- |
| **A. 隔离进程 + 中性 workspace（仍为选定路线）** | 每实例独立进程 + 独立 `WORKSPACE_DIR`，其中预置**自建**中性 persona | 唯一能与公开基准对比的臂 | 仍需自建中性 `AGENTS.md` + 一个 `SHERRY_WORKSPACE_DIR` 覆盖；必须进程级隔离。**成本较原文下降**：SOUL/USER/ROLE 三份已可合法置空（见下「预设」小节），不必自建 |
| B. 保留人格作自变量 | 不动 workspace，跑两臂（人格开 / 中性近似） | 真实产品表现 + 人格影响量级 | 数值不能与公开榜对比；**且当前无可用中性臂**（模板本身即人格，见下），B 实际退化为「只跑人格臂」 |
| C. 走受支持接口部分中性化（**前提已变，见下**） | 原文设想「只改 `SOUL.md` / `USER.md`，`AGENTS.md` 不动」 | 可维护、可复用的控制臂 | **原文代价「`AGENTS.md` 不可控」已不成立**：该文件现经 `/system_prompt` 可写。但 C 仍只覆盖 3 份文件、仍留 `AGENTS.md` 全人格，且无进程级隔离，并行实例会互相覆盖 |

#### 预设：已能置空 role-play，但不等于「中性臂已就绪」

2026-10-06 实测的前端「预设」（`预设` 面板）确实提供了受支持的人格中性化通道 `[实测]`：

- **可置空且零成本**：内置「编程助手」预设（`client/app/composables/persona-catalog.ts:143-153`，`BuiltinPresetId = 'sherry' | 'coding'`）对 `coding` 分支写入 `'SOUL.md': ''`、`'USER.md': ''`，`ROLE.md` 由 `composeRoleFile()`（`:109-116`）在两个角色名皆空时返回 `''`。`build_system_prompt()` 末尾 `"\n\n".join(p for p in parts if p)`（`workspace/prompt_builder.py:367`）**丢弃空段**，后端 `_WorkplaceFileStore.allow_empty = True`（`server/service/workplace.py:33`，注释明写「编程助手内置预设出厂即空 soul / user profile」）故空文件是合法状态而非错误。**结论：SOUL/USER/ROLE 三份 role-play 载体可经受支持接口清零。**
- **不可置空的是 `AGENTS.md`**：同一分支保留 `'AGENTS.md': template['AGENTS.md']`（`persona-catalog.ts:153`），而该模板**含 6 处 `Tachibana Sherry` 且带强制编排教条**：`en/AGENTS.md:15,17,19,33,64,70` 的 `### Orchestrator Doctrine (MANDATORY)` / `YOU ARE AN ORCHESTRATOR. NEVER THE IMPLEMENTER.` / `You DO NOT write code. You DO NOT edit product files.` / `DELEGATE every sub-task via task tool` / 把「自己写代码」列为失败模式 / `FAILURE TO FOLLOW ORCHESTRATOR DOCTRINE = INCOMPLETE WORK.`。
- **`AGENTS.md` 取自「当前 UI 语言」的模板，故污染随 locale 变**：内置 preset 的 payload 由 `readSystemPromptTemplate(locale)` 取模板后合成（`persona-catalog.ts:166,172,176`），非固定英文。`zh`（`:15,17,20-21,33,60,66`）与 `ja`（`:17,60,66`）模板**同样带该教条**，但行号与措辞均不同 —— `ja` 写的是 `決して実装者（IMPLEMENTER）ではありません`，**不含英文字面 `NEVER THE IMPLEMENTER`**。因此 harness 若以英文关键字做「已中性」扫描，会在非英文 UI 语言下**漏判**；P2a 的中性 `AGENTS.md` 校验必须按全语言清单核对，或固定为单一 locale。`[实测]`
- **这是新的头号错法**：内置预设名叫「编程助手」、是**默认项**（`6b05f4e1` 让它成为默认并以预设选择 gate 住建会话），极易被当成现成中性臂直接使用；但它保留的 `AGENTS.md` 会**主动教模型不写代码**，对编码基准是**负向污染而非中性**。任何对外编码数字若用它做「中性臂」，结论无效。`[实测]`
- 因此 `AGENTS.md` 仍**必须自建**（A 臂前置不变）；预设的净收益是把 SOUL/USER/ROLE 三份从「自建」降为「置空」，并让 `AGENTS.md` 可经 `/system_prompt` 写入而非被 API 挡住。

#### A 的真实前置工作（原方案低估）

**陷阱 1（原文已有，仍然成立）: 仓库里不存在中性模板。** `workspace/template/` 是「首次启动时复制进 workspace 的一次性副本」，不是中性基线；2026-10-06 复测：`en/AGENTS.md` 与 `zh/AGENTS.md` 各含 6 处 `橘雪莉`/`Sherry`、`ja/AGENTS.md` 6 处，`zh/USER.md` 5 处、`zh/SOUL.md` 1 处，与 live workspace 人格浓度**相同**；唯一例外是 `ko/AGENTS.md`（0 处）。`rg -il 'neutral|中性' workspace/template/` 零命中。
因此 A **必须先自建**中性 `AGENTS.md`（`ALL_SYSTEM_FILE_NAMES` = CORE `AGENTS.md` + COMMUNITY `SOUL.md` / `USER.md` / `ROLE.md`，共 4 个文件，见 `workspace/__init__.py:3-26`；`IDENTITY.md` 已从该集合移除）。直接复制模板、或改用内置「编程助手」预设，都会得到一个「看似中性实则全人格、且教模型不写代码」的 workspace，并据此报数 —— 这是本方案最坏的一种错法，必须显式排除。

**A 的落地条件**（均 `[实测]`）:
- `WORKSPACE_DIR` 目前硬编码为 `ROOT_DIR / "workspace"`（`config/path.py:36`），**不可用环境变量覆盖**。需新增 `SHERRY_WORKSPACE_DIR` 覆盖 —— 同文件已有 4 处仍有效的 `SHERRY_*` 先例（`config/path.py:274` `SHERRY_PROJECT_DIR`、`:307` `SHERRY_APPROVAL_STORE_PATH`、`:323` `SHERRY_FILE_LOCKS_DIR`、`:338` `SHERRY_ISOLATED_WORKSPACES_DIR`），照既有模式改动，不破坏配置约定。**注意原文列举的 `:320 SHERRY_FILE_SNAPSHOTS_DB` 已随 `36a6ad0a` 删除，不再是有效先例。**
- **可落地**: `file_sync.py:80-81` 为 `if target.exists(): continue` —— 启动同步**只补缺失文件、不覆盖**。因此预置的中性 persona 不会被启动时的模板同步冲掉，无需额外保护。
- 覆盖 `WORKSPACE_DIR` 会一并移动 `SESSIONS_DIR` / `MEMORY_DIR` / `KNOWLEDGE_DIR` / `HEARTBEAT_PATH`（`config/path.py:37-50`），正好达成每实例状态隔离，**但这是隐式副作用而非设计意图，必须显式验证 checkpoint 与 MesMemory 确实落在实例目录内** `[未验证]`。

**注意**：原文称 `AGENTS.md` 的 API 排除是「面向运行时 agent 自改人格的纵深防御」，并据此论证 harness 预置不削弱产品防御。**该排除已于 `6ab42480`（2026-10-05，恢复 `AGENTS.md` 标签页）移除**，`server/service/workplace.py:9-19` 的注释改为说明：现在受保护的是 **agent 侧**（`agent/tools/memory.py` 的 memory 写守卫、`agent/security/threat_patterns.py` 的威胁扫描仍拒绝「overwrite/modify AGENTS.md」内容），人机 UI 侧不设限。威胁扫描的对应规则可复核：`agent/security/threat_patterns.py:121-122` 的 `(?:modify|overwrite|replace)\s+.{0,60}(?:AGENTS|CLAUDE)\.md` → `injection_modify_agents_md`。同一段注释 `:18-19` 另记载 `IDENTITY.md` **已完全移除**（同时退出 `ALL_SYSTEM_FILE_NAMES` 与模板），故它既不在注入链也不在此白名单内。因此 harness 经 `/system_prompt` 写入中性 `AGENTS.md` **不触碰任何现存防御** —— 存活的 agent 侧守卫拦的是不可信文本，不能让 agent 改自己的规则，与本方案无冲突。

无论哪种臂，人格污染都是编码基准数字可信度的**最大威胁**；任何对外数字都必须声明用的是中性臂，且必须说明中性 persona 是自建的。

### 3.4 spike 范围

- **5 到 10 个** SWE-bench 类实例（不是全量 2000+）。优先依赖少、测试可离线跑、单文件或小范围修改的实例。
- 固定主/辅模型与 provider，确认额度充足（第六节）。
- 每实例: fresh `session_id`（**无 session-create 端点**，用客户端生成、经 `pub/func/validator/session_id.py` 校验的安全路径段）；pinned base SHA；结束后可选 purge（`DELETE /sessions` → `server/DAO/messages.py:17` `clear_session` 会清该 session 的 MesMemory、todos、taskflow flows、LangGraph checkpoint、`sessions/<id>/` 目录、plan knowledge、内存 register、state_register 变量、file-snapshot 行）。
- 产物: 每实例的 diff、判定结果、token、墙钟、失败分类。

### 3.5 三条必须验证的退出判据

1. **端到端可判定**: 至少 5 个实例完成「任务描述 → agent 改仓 → 自动取 diff → 自动判定」，**无人工介入**；且失败实例能区分「模型没改对」与「harness 没跑通」。任一实例无法判定即该判据不通过。`[待实测]`
2. **人格中性臂可判定**: 中性臂（3.3 的 A 臂）产出的 prompt 中**不含人格内容** —— 需给出注入 system prompt 的实际抽样证据（自建 persona 全文 + `build_system_prompt` 输出片段），而非仅声称已配置。若同时跑人格臂作对照，则给出两臂 diff 差异与人格影响方向；只跑人格臂而无法证明中性者不算通过。`[待实测]` **2026-10-06 追加具体判据**：抽样证据必须明证中性臂 prompt 中 (a) 无角色名（`Tachibana Sherry` / `橘雪莉` 零命中）、(b) 无 `ORCHESTRATOR` / `NEVER THE IMPLEMENTER` 等编排教条 —— 内置「编程助手」预设恰好在这两条上失败，仅凭「已套用预设」不构成本判据通过。
3. **成本与噪声可复现**: 全程记录模型 id、provider、token、墙钟；**无 `429 余额不足` 污染**；同一实例重跑结果方向一致，或明确记录不稳定并给出原因分类。出现额度故障即该批作废。`[待实测]`

### 3.6 本轮不做什么

- 不提交任何榜单 / leaderboard。
- 不跑全量 SWE-bench（2000+ 实例）。
- 不改 `workspace/prompt_builder.py` 或 `server/service/workplace.py` 的 persona 接口（3.3 明确不采用选项 C）。
- 不让 harness 复用 live `workspace/`：每实例必须用独立 `WORKSPACE_DIR`（A 臂），避免污染用户真实人格。
- 不为 spike 改 `agent/` 业务逻辑；harness 放 `evals/` 或独立目录。
- **不把复制 `workspace/template/` 当作「中性化」**：模板本身即人格（3.3），必须自建中性 persona。
- **不把内置「编程助手」预设当作中性臂**（2026-10-06 新增）：它只置空 SOUL/USER/ROLE，保留的 `AGENTS.md` 含 `ORCHESTRATOR. NEVER THE IMPLEMENTER`，会主动教模型不写代码。可借其置空动作，但 `AGENTS.md` 必须自建（3.3）。
- 不把 spike 结果写成「编码能力 X%」。
- 不把 spike 纳入 CI 默认分组。

## 四、内部 evals 的最小改进（与 spike 并行、低风险）

前提: 不改套件语义，只加测量骨架。每项给验收判据。

### 4.1 加基线与趋势

- 做法: 在 `evals/` 放一个**受版本管理**的 baseline 文件（不是 gitignored 的 `results/`），记录每套件上一版关键指标与模型 id；runner 每次与 baseline 对比并打印 delta。
- 验收: 同一 suite 连跑两次，第二次能打印与 baseline 的 delta；baseline 已入 git。
- 注: `evals/results/` 可维持 gitignored（`.gitignore:11-12`），baseline 是另一份显式文件。

### 4.2 加阈值 + 失败退出码

- 做法: 给每套件定义明确 pass 阈值；让 `evals.py` 的 `main()` 在任一 suite 低于阈值时返回非零。
- 验收: 人为把某阈值抬到不可能通过，运行后进程退出码非零。
- 注: 现仅 `nudge_extraction` 有硬阈值（`suite.py:456`），`long_running_task` 仅在 stalled 时 `SystemExit(1)`，其余无阈值。

### 4.3 纳入 CI

- 做法: 至少把最便宜、基本 hermetic 的 `session_memory`（6 检查中 5 个用 stub 模型）纳入常规 gate；需真实 LLM 的套件放独立 job，默认不并行。
- 验收: CI 常规运行能跑到 `session_memory` 并因其失败而红。
- 注: 当前 `ci.yml:76-79` 只是 bandit SAST 步骤内说明 `evals` / tests 被排除于该次扫描，没有任何 job 调 `evals.py`。

### 4.4 消除不可复现

- 做法: (a) 固定模型/provider 并记录；(b) 确保额度充足，429 一律标为 `invalid_run` 而非计入失败率；(c) 每次运行写模型版本与配置快照；(d) 每实例/每 suite 用 fresh sandbox。
- 验收: 同配置连跑两次差异可解释；报告不再出现被当成质量失败的额度故障。
- 注: 1.3 列出的历史结果中，0.0 / 0.2 含 `RateLimitError 429 ... 余额不足或无可用资源包`。

### 4.5 修正过期与静默

- 做法: 更新相对代码过期的报告口径（报告 7 个 `session_memory` 检查 vs 当前 6 个，`facts_extraction_llm` 已在 `e9cb198f` 移除）；让 `nudge_extraction` 缺 key 时不再**静默退 0**（当前写 `skipped` 报告并退 0）。
- 验收: 报告检查数与当前代码一致；缺 key 时明确标 skipped，且「跳过」按 4.2 语义不算通过。

### 4.6 复用 sandbox 隔离

- 做法: spike harness 复用 `evals/sandbox.py` 的隔离模式（SQLite store / checkpoint 重定向 per-run，child 工具收窄，`SANDBOX_POLICY`）。
- 注意: 这是 **child agent** 的隔离；harness 实际驱动的 MAIN（depth 0）仍有完整工具集，**不能据此认为 harness 安全**（见 3.2 第 4 点）。

## 五、无法自动化的盲区

- STT 路径（`models/STT_model/`、`speech_to_text` skill）与 MinerU 文档摄取**零测试覆盖**，因为需要模型权重。现有门禁**无法证明**这些已交付路径没有回归。安全处置记录在 transformers 4→5 迁移问题上得到同一结论。
- **结论表述约束**: 任何「成熟度」「无回归」「已覆盖」的表述都必须显式带上这条盲区；不得由其余套件的通过推断 STT / MinerU 健康。
- 这类路径只能**人工验证**（真实权重 + 真实音频/文档样例），本方案不为它们承诺自动化。

## 六、度量口径与防自欺

- **固定模型与额度**: 主/辅模型、provider、`MAIN_LLM_MAX_TOKEN` 与 `AUXILIARY_LLM_MAX_TOKEN`（均须 ≥ 131072；未设辅模型上限会回退 121072 并**中止启动**）全部固定并记录。额度不足会重演历史 429 污染。
- **样本量与噪声**: 5 到 10 实例的 pass rate **不是**成熟度。小样本置信区间宽且受任务抽样影响；报告只写「本例集上 X/N」，不写百分比能力值。
- **人格对照组必须设**: 没有中性臂，任何编码数字都混杂人格贡献，无法与其他系统比较。**中性 = 自建 + 可证**，而非「套用了某个预设」：置空 SOUL/USER/ROLE 只解决三份 role-play 载体，`AGENTS.md` 的编排教条须由自建内容剔除（见 3.3 预设小节与 3.5 判据 2）。
- **不允许下的结论**:
  - 由 spike 推「Sherry 编码能力 = X%」。
  - 由**无阈值**的自设计套件推任何通过率（`graph_rag`、`subagent`、`session_memory` 目前均无阈值）。
  - 把 429 额度故障计入失败率。
  - 跨模型版本 / 跨窗口大小的直接对比（未控制变量）。
  - 由内部套件通过推「外部基准等价」。
- **口径固定**: 判定用 `git -C <repo> diff <base_sha>`（相对 pinned base，而非工作区 HEAD）；禁止任务仓库内 commit。

# 计划：WorkMode 子机制 — 意图路由 + 任务级可靠性 + 计划模板

- 日期：2026-11-12
- 状态：**待评审**
- 来源：借鉴同类工具 WorkMode 的子机制；补 Sherry 专家团模式（Mode 2）没覆盖的"任务级可靠性与协调"维度
- 风险等级：**中** —— 部分复用现有 TaskFlow（计划模板/渐进展开），部分新增（意图路由/死循环检测/看门狗）
- 关系：补专家团模式计划——专家团解决"谁做"，本计划解决"怎么可靠地做"

---

## 0. 借鉴什么（5 个子机制，不抄整体架构）

Madorin WorkMode 是"三层组织 + 持久化计划 + 意图路由"长任务体系。整体和专家团有概念重叠（不抄整体三层），但 **5 个子机制 Sherry 没有**，补的是任务级可靠性：

| 子机制 | 解决什么 | Sherry 现状 |
|---|---|---|
| 意图分类器输入路由 | 长任务被用户中途打断怎么路由 | 无（打断当普通消息进 turn） |
| 看门狗 + 死循环检测 | 任务卡死/循环无进展 | 有调用级（InvalidToolCallRepair/LLMRetry），无任务级 |
| 自评重做循环 | 步骤质量不够自动重做 | 有 StepJudge/CompletionJudge，但无"自评打分+重做上限" |
| 计划模板复用 + 渐进式展开 | "再做一份"+ 大计划按需展开 | 有 PTC/LDW replay（编译脚本），无"计划模板"层 |
| plan/environment 双文件 | 任务事实固化进文件 | 有 TaskFlow flow store，无 environment.yaml 式事实文件 |

---

## 1. 意图分类器输入路由

### 1.1 问题

Sherry 长任务（TaskFlow 跑着）被用户中途发消息——现在是当普通消息进 turn，可能打断正在跑的任务流，或被 busy 排队（queued input）。没有"用户意图分类→不同路由"。

### 1.2 设计

用户中途输入分类（rules-only，参照 Sherry TaskIntent 的 rules-only 四语言模式，不调 LLM）：

| 意图 | 触发 | 路由 |
|---|---|---|
| **NewTask** | 用户开新话题（与当前 TaskFlow 无关） | 挂起当前 flow / 排队新任务 |
| **ContinueTask** | 用户补充当前任务信息 | 注入当前 flow 上下文 |
| **SoftPreemption** | 用户插话要调整方向 | 入队 pending 提示，下一 turn 注入主持人/主 agent，不直接打断执行中的 step |
| **CancelTask** | "停下"/"取消"/"别做了" | 取消当前 TaskFlow flow（taskflow_flow action=cancel） |
| **ResumeTask** | HITL 挂起后回答 | 现有 HITL resume（已有） |

优先级：CancelTask > SoftPreemption > ResumeTask > ContinueTask > NewTask。

### 1.3 实施

- 新建 `agent/middlewares/task_intent_router/`：before_agent 节点，长任务运行时（检测 TaskFlow flow active），对用户输入分类
- 复用 TaskIntent 的 rules-only 四语言关键词模式（不调 LLM）
- SoftPreemption 走现有 queued input 机制（入队 pending，下 turn 注入）
- CancelTask 调 taskflow cancel
- **不影响短任务**（无 active TaskFlow 时走现有路径）

## 2. 看门狗 + 死循环检测（任务级可靠性）

### 2.1 问题

Sherry 有调用级可靠性（InvalidToolCallRepair 修 JSON、LLMRetry 重试 429/500、MaxTokensBoost 续写）。但没有**任务级**：一个 TaskFlow flow 跑了很久没进展、同一步骤反复失败、自评不通过循环——没有检测和兜底。

### 2.2 看门狗（Watchdog）

- 新建 `agent/tools/taskflow/watchdog.py`：后台定时扫描（参照 Sherry lane 的 BACKGROUND_REVIEW 模式）
- 检测：TaskFlow flow `OrchestratorState=running` 且 `HeartbeatAt < now - threshold`（如 10 分钟无心跳更新）→ 标记 stale + 通知
- 心跳：TaskFlow step dispatch/finish 时更新 `HeartbeatAt`（flow 级时间戳）
- 兜底：stale flow 通知主 agent/主持人（system.notice 或 reminder）"任务可能卡住"

### 2.3 死循环检测（DeadlockDetector）

三类（参照 Madorin 的 DeadlockDetector）：
1. **同参数同工具连续失败 ≥3**：同一 step 同一工具调用连续失败 3 次（args 相同）→ 标记循环，step 失败
2. **CompletionJudge 连续不通过 ≥5**：同一 flow 的 completion judge 连续 5 次判 retry → 标记循环，flow 失败（不无限重试）
3. **无进展超时**：flow running 30 分钟无 step 状态变化 → 标记 stale

命中后：
- 写循环检测日志
- 通知主 agent（system.notice "系统检测到任务可能陷入循环"）
- 不自动强制失败——fail-open 提示，让 agent/用户决定（取消 or 继续）

### 2.4 实施

- `taskflow/watchdog.py`：看门狗扫描 + 心跳更新
- `taskflow/deadlock_detector.py`：三类检测
- 复用 TaskFlow 现有 step/flow 状态（step retry count、judge retry count、flow updated_at）
- 配置项：`TASKFLOW_INFRA["heartbeat_timeout_s"]`、`["deadlock_tool_fail_count"]`、`["deadlock_judge_fail_count"]`、`["deadlock_no_progress_s"]`

## 3. 自评重做循环

### 3.1 问题

Sherry 有 StepJudge（criteria-bearing step 的 judge：pass/retry/block）和 CompletionJudge（goal loop）。但都是"判通过/不通过"二值。Madorin 的自评是"打分 1-10，≥7 通过，<7 重做，最多 5 次强制通过"——给了更细的质量梯度 + 强制上限防无限重做。

### 3.2 设计

给 StepJudge 加可选的**自评模式**（step 配 `self_evaluate: true` + `min_score: 7` + `max_retries: 5`）：
- step 完成后，调 LLM 打分（1-10，基于 step 的 judge_criteria）
- ≥ min_score → pass
- < min_score → retry（带"上次打分+原因"反馈），最多 max_retries 次
- 超过 max_retries → **强制通过**（记 `forced_pass: true`），不无限循环

### 3.3 实施

- StepJudge 扩展：`step_judge.py` 加 self-evaluate 分支
- step 配置 schema 加 `self_evaluate`/`min_score`/`max_retries`（可选，缺省=现有二值 judge）
- 复用现有 judge 的 LLM 调用框架
- 与死循环检测的"judge 连续不通过≥5"联动（自评 max_retries 到了强制通过，不死循环）

## 4. 计划模板复用 + 渐进式展开

### 4.1 计划模板

Sherry 有 PTC/LDW replay（编译成功 flow 为脚本，零调用重放）。但这是"执行层复用"——重放的是具体步骤调用序列。Madorin 的计划模板是"规划层复用"——重用的是**任务分解结构**（步骤列表 + 角色 + 依赖），不是具体调用。

设计：
- TaskFlow flow 完成后，可选 `save_as_template`（保存步骤结构：id/title/role/depends_on/judge_criteria，不含具体执行结果）
- 下次类似任务 `load_from_template` → 用模板步骤结构创建新 flow（步骤是空壳，重新执行）
- 模板存 `APP_HOME/taskflow_templates/<name>.json`
- 与 PTC/LDW 互补：模板复用"分解结构"，PTC/LDW 复用"执行序列"。一个任务可先 load_template（复用分解）再让 PTC pre-run（复用执行）

### 4.2 渐进式展开 — 不需要（嵌套 TaskFlow 已覆盖，核实结论）

**决定不采用 expandable step 机制。** Sherry 的嵌套 TaskFlow 已覆盖渐进式展开需求：

- ORCHESTRATOR 深度子 run 能内部 `taskflow_create` 自己的子 flow（已核实：taskflow 工具不在 subagent 屏蔽表）——顶层只建粗粒度步骤，执行时子 agent 自己分解为细粒度子步骤
- 这是"渐进式展开"的另一种形态：顶层 flow 只有粗步骤，子步骤在 child 的独立 flow 里

**嵌套 TaskFlow vs expandable step 对比**：

| | expandable step（Madorin） | 嵌套 TaskFlow（Sherry 已有） |
|---|---|---|
| 展开在哪 | 同一 plan（子步骤写进父 plan） | child 独立 flow |
| 父看得到子步骤 | 是（进度可见可调） | 否（父只看 child 最终结果） |
| 上下文压缩 | 大 plan 不预定义子步骤 | 顶层 flow 只有粗步骤 |
| 状态机复杂度 | step 加 expandable→expanded 转换 + 部分展开 finish 门 | 不加（child flow 独立状态机） |

**唯一差距——父级进度可见性——用更轻的解法**：
- child 通过 system.notice 或 taskflow progress_push 帧上报进度（Sherry 已有 `progress_push.py`）
- 父编排者看到"专家内部 2/3 步完成"，不需要把子步骤写进父 flow
- 比给 TaskFlow 状态机加 expandable→expanded 转换 + 部分展开 finish 门简单得多

**不采用的理由**：
1. 嵌套 TaskFlow 已覆盖渐进分解（不需要新机制）
2. TaskFlow step 存 SQLite 不存对话上下文（Madorin 压上下文的动机不成立）
3. expandable step 给状态机加复杂度（部分展开的 finish 门、跨展开层级环检测）不值得
4. 父级进度可见性用上报机制（progress_push / system.notice）更轻

### 4.3 实施

- `taskflow/template_store.py`：模板 CRUD（save/load/list）
- `taskflow/tools/taskflow_merged.py` 加 `save_as_template`/`load_from_template` action
- ~~step schema 加 expandable/expander~~（不采用，见 §4.2）
- ~~taskflow execute 到 expandable step 时调 LLM 展开~~（不采用）

## 5. plan/environment 双文件

### 5.1 问题

Sherry 的任务事实（项目路径/规格/凭证引用）散在对话历史或 TaskFlow flow description 里。Madorin 用 `environment.yaml` 固化任务事实，dispatch 时自动注入执行者 system prompt。

### 5.2 设计

- TaskFlow flow 创建时可选附 `environment`（JSON：项目路径/技术栈/约束/凭证引用 `credential_ref: keychain://...`）
- `environment` 存 flow store（和 flow 元数据一起）
- step dispatch 时自动注入 step 子 agent 的 system prompt（"## Task Environment" 块）
- 凭证引用不存真值（`credential_ref: keychain://xxx`），执行时解析注入

### 5.3 实施

- TaskFlow flow schema 加 `environment` 字段（可选 JSON）
- taskflow_create 接受 environment
- step spawn 时注入 environment 块到子 agent system prompt
- 与 Sherry 现有 project_dir / AGENTS.md 注入正交（environment 是任务级，project_dir 是会话级）

## 6. 实施顺序

| 阶段 | 内容 | 依赖 | 价值 |
|---|---|---|---|
| 1 | 意图分类器输入路由 | 无 | 长任务打断路由（通用痛点） |
| 2 | 看门狗 + 死循环检测 | TaskFlow 状态（现有） | 任务级可靠性 |
| 3 | 自评重做循环 | StepJudge（现有） | 质量梯度 + 重做上限 |
| 4 | 计划模板复用 | TaskFlow（现有） | 规划层复用（渐进式展开不采用，嵌套 TaskFlow 已覆盖） |
| 5 | plan/environment 双文件 | TaskFlow flow schema | 任务事实固化 |

阶段 1-2 最先（通用痛点 + 可靠性）；3-5 渐进。

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 意图分类误判（SoftPreemption 当 NewTask） | rules-only fail-open（分不清当 ContinueTask，不丢消息） |
| 看门狗误报（长 step 正常跑超阈值） | 阈值可配 + fail-open 提示（不强制失败） |
| 自评打分主观（LLM 打分不稳） | min_score/max_retries 可调 + 强制通过上限防死循环 |
| 计划模板与 PTC/LDW 概念混淆 | 明确分工：模板=分解结构复用，PTC/LDW=执行序列复用 |
| environment 凭证引用泄露 | 只存 ref 不存真值，解析时注入 |

### Kill criteria

- 意图路由若 rules-only 误判率高（用户反馈打断体验差），降级为"全部走 SoftPreemption 入队"（不分类，统一排队）
- 死循环检测若误报频繁，调阈值或关闭（fail-open 不阻塞）
- 自评若 LLM 打分不稳定导致强制通过率高，回退为二值 judge（现有）
- 计划模板若使用率低（用户倾向 PTC/LDW replay），模板后置

## 8. 验收

### 意图路由
- 长任务运行时用户发"停下"→ CancelTask → flow cancel
- 用户发补充信息 → ContinueTask → 注入当前 flow
- 用户发无关新话题 → NewTask → 排队
- 短任务（无 active flow）→ 走现有路径，不分类

### 看门狗 + 死循环
- flow 10 分钟无心跳 → stale 标记 + 通知
- 同 step 同工具失败 ≥3 → 循环标记 + step 失败
- judge 连续 retry ≥5 → 循环标记 + flow 失败
- 30 分钟无进展 → stale

### 自评
- self_evaluate step 完成后打分 ≥ min_score → pass
- < min_score → retry 带反馈
- 超过 max_retries → 强制通过（forced_pass=true）

### 模板
- flow 完成后 save_as_template → 存 JSON
- load_from_template → 用模板步骤创建新 flow

### ~~渐进式展开~~（不采用，嵌套 TaskFlow 已覆盖，见 §4.2）

### environment
- flow 带 environment → step dispatch 时子 agent system prompt 含 environment 块
- 凭证引用不存真值

### 回归
- 现有 TaskFlow / StepJudge / CompletionJudge 行为不变（自评/模板/environment 全可选）
- `uv run pytest tests/agent/tools/taskflow -q` 全过

## 9. 与专家团模式计划的关系

专家团模式（Mode 2）解决"谁做"（主持人 + 全底座专家）。本计划解决"怎么可靠地做"：
- 意图路由 → 主持人长任务被打断时路由用户输入
- 看门狗/死循环 → 专家团 flow 跑久不进展的兜底
- 自评 → 专家 step 质量梯度
- 模板/展开 → 专家团协调模式复用（save 团队分解结构为模板）
- environment → 专家 step 的事实验入

两者正交叠加：专家团用本计划的子机制增强任务级可靠性。

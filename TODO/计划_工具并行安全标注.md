## 0. 结论先行

这份计划管的是**单个 agent 在同一次模型回复里返回的一批 tool calls**，不是多 agent 调度。

v1 只做静态标注 + warning，不阻断。v3 分两层：

1. **批次层**：安全调用并发；文件读写按 canonical path 分组，**同一 path 按模型 `tool_calls` 顺序串行，不同 path 并发**；非文件类不安全工具（terminal / memory / session 写等）仍是整批 barrier。
2. **资源层**：不重建已有的文件/记忆/存储锁；给文件补一个共享读锁，并补两个真实缺口——进程级 `system` 锁（terminal / python_repl / execute_code / ptc）和按 session 的 `user_interaction` 锁（question / exit_plan_mode）。

多 agent 的并发仍由 `runtime/lane`、spawn admission、`file_write_lock`/CAS 负责；`system` 锁是唯一有意跨 session 的锁，用来阻止两个 agent 同时跑 shell。跨批次/跨 agent 的同一文件读写不承诺调用顺序，只保证互斥。

不直接合并 `xp_graph` 的 `SmartToolNode`：它现在的实现对当前 LangGraph 1.3.9 不兼容，且只按 `idempotent` 判定。保留的是它的**批次级分类思路**，代码按当前版本重写。

## 0.1 现有资源锁盘点（不要重复实现）

| 资源 | 现有机制 | 覆盖范围 | 缺口 |
|---|---|---|---|
| 文件写入 | `agent/tools/pub_base/file_lock.py`：按规范化路径的进程内 `path_lock` + 跨进程 `flock`；`patch_file` 另有 CAS | `write_file` / `patch_file` 的同文件写入 | `read_file` 不拿锁；`terminal` / `python_repl` / `execute_code` / `ptc` 不经过它 |
| 记忆文件 | `agent/tools/memory.py::_file_lock`：对 `MEMORY.md` / `USER.md` / `FACTS.md` 的 read-modify-write 加 `flock` | memory 工具的 add / replace / remove | 无（已有资源锁） |
| TaskFlow / todolist / subagent 注册表 | SQLite WAL + busy timeout；TaskFlow 用 `expected_revision` 乐观锁 + 冲突重试 | 数据库写入的一致性 | 不是工具级锁；不覆盖跨资源的复合操作 |
| MesMemory / state register | 共享连接上的 `RLock` / `_stmt_lock`，单条语句串行 | 单次读/写 | 不覆盖多步工具逻辑，但这是存储层职责 |
| 浏览器 | `server/service/browser_manager.py` 的 per-page `nav_lock` | 同一页面的导航 | 不是所有 browser 操作的全局互斥 |
| lane | `runtime/lane` 的 MAIN / SUBAGENT / NUDGE / NESTED | 并发数量与排队 | 不是资源互斥 |

因此资源层只做两件事：

- **`system` 锁**：进程级独占，包住 `terminal`、`python_repl`、`execute_code`、`ptc`；可选开关，默认关闭，避免正常并行命令被全部串行。
- **`user_interaction` 锁**：按 session 独占，包住 `question` 和 `exit_plan_mode`，避免同一会话同时出现两个 HITL 交互。

`workspace` / `session` 不新增通用锁：文件用 `file_write_lock`，记忆用 memory 自有锁，SQLite 用 WAL + revision；批次层只需要把它们标成不安全以保证顺序。

## 1. 参考实现评估

### 1.1 它做对了什么

`origin/xp_graph:agent/smart_tool_node.py` 的核心很小：

```python
def _should_parallelize(tool_calls, tools_by_name) -> bool:
    if len(tool_calls) <= 1:
        return False
    return all(tool.metadata.get("idempotent", False) for ...)
```

`SmartToolNode` 覆写 `_afunc` / `_func`：

- `_should_parallelize` 为真 → `asyncio.gather` / `executor.map`。
- 否则 → 按 `tool_calls` 列表顺序逐个 `await self._arun_one` / `self._run_one`。

这正是需要的批次级语义：**全安全才并发，否则整批顺序执行**。批次上下文和 `tools_by_name` 都在 ToolNode 里，不需要从 middleware 猜兄弟调用。

具体效果（按分支的 `idempotent` 规则）：

| 模型返回的批次 | 参考实现行为 | 是否符合安全语义 |
|---|---|---|
| `read_file` + `read_file` | 并发 | ✅ |
| `write_file` + `read_file` | 整批串行 | ✅ 保守但正确 |
| `memory` + `memory` | 并发（两个都 `idempotent=True`） | ❌ 漏放，memory 会写文件 |
| `sessions_spawn` + `sessions_spawn` | 整批串行（`idempotent=False`） | ❌ 过度串行，spawn 本身可并行 |

所以它的价值在**批次级决策点**，不在判定规则；判定规则必须换成 `destructive` / `concurrent_safe` / `side_effect_scope`。

## 2. 最终设计

### 2.1 静态标注字段

在工具 metadata 中新增三个字段（`agent/tools/parallel_safety.py` 定义 `TypedDict`）：

```python
class ToolSafetyMeta(TypedDict, total=False):
    destructive: bool          # True = 永远不并行
    concurrent_safe: bool      # True = 显式声明可并行（即使有副作用）
    side_effect_scope: Literal[
        "none", "workspace", "git", "network", "system", "session", "user_interaction"
    ]
```

判定顺序：

```python
def tool_is_parallel_safe(name: str, tool: BaseTool | None) -> bool:
    if name in READ_ONLY_TOOLS:
        return True
    meta = getattr(tool, "metadata", None)
    if not isinstance(meta, dict):
        return False
    if meta.get("destructive"):
        return False
    if meta.get("concurrent_safe"):
        return True
    return meta.get("side_effect_scope") == "none"
```

规则：

- 显式 `destructive` 优先，任何声明都不能翻案。
- 未知工具、缺 metadata、缺 `idempotent` 都按**不安全**处理。
- **不再用 `idempotent` 推导并行安全**。`idempotent` 只服务 ToolGuardrails 的重复调用检测；并行安全是独立语义。
- `READ_ONLY_TOOLS` 是名单兜底，不要求每个只读工具都改 metadata。

### 2.2 批次分类与文件资源

除了“安全 / 不安全”，文件工具需要第三种分类：**同一个 canonical path 上的读写互相冲突，不同 path 不冲突**。

```python
FILE_READ_TOOLS = frozenset({"read_file"})
FILE_WRITE_TOOLS = frozenset({"write_file", "patch_file"})

def file_resource_key(call, state) -> tuple[str, str] | None:
    """(canonical_path, "read"|"write")；无法解析时返回 None（按 barrier 处理）。"""
```

- `read_file` 虽然也在 `READ_ONLY_TOOLS`，调度器必须**先**看 `FILE_READ_TOOLS`，不能把它当普通只读工具。
- path 通过 `resolve_tool_path` / `session_workspace_root` 解析到与 `file_write_lock` 相同的 canonical path；解析失败（外部路径审批前、非法参数）→ 该调用按 barrier 处理。
- 同一个 path：`read_file` 与 `write_file` / `patch_file` 冲突，组内只要有一个写，整组按 `tool_calls` 顺序串行；组内**全是读**时按共享锁并发。
- 不同 path：互不冲突，可并发。

**批次调度规则**：

1. 批次里有任何 **非文件类不安全工具**（`terminal` / `python_repl` / `execute_code` / `ptc` / `memory` / `session` 写操作等）→ 整批顺序，行为与 v2 的保守策略一致；这些工具的资源无法从参数可靠推断。
2. 批次只含安全工具 + 文件工具：
   - 文件工具按 `canonical_path` 分组；
   - **组内只要有一个写，按 `tool_calls` 原始顺序串行；组内全是读则共享并发**；
   - 不同组之间、以及普通安全工具之间并发；
   - 输出按原始 index 回填，再交给 `_combine_tool_outputs`。
3. 单调用、空批次照常走直接执行/并发路径。

**同读写同时发生时的顺序（明确规则）**：

- 同一批内，以模型返回的 `tool_calls` 顺序为准。
- `read_file(A)` 在 `write_file(A)` 之前 → 读旧内容，读完后再写；如果 `write_file(A)` 需要 read-before-write license，这次读正好提供。
- `write_file(A)` 在 `read_file(A)` 之前 → 先写，后读看到新内容；如果这是覆盖已有文件的写且没有 license，写会按现有规则拒绝，后面的读仍按原顺序执行。
- 两个读同一文件 → 共享并发，不互相等待。
- 两个写同一文件 → 按调用顺序执行，最后一个生效；`file_write_lock` 仍负责跨进程/跨 agent 的互斥。
- 不同 path 的读写 → 并发，谁也不等谁。
- 跨批次/跨 agent → **不承诺调用顺序**；只有 `file_write_lock` / 新的 read lock 的互斥，谁先拿到锁谁先执行。

### 2.3 `SafeToolNode`（对标 SmartToolNode，适配当前版本）

新增 `agent/safe_tool_node.py`：

- `class SafeToolNode(ToolNode)`：只覆写 `_afunc` / `_func`，其余行为继承。
- `_plan_batch(tool_calls, tools_by_name, state)` 按 2.2 生成执行计划：barrier 整批顺序，或“文件 path 组 + 安全调用”的并发组。
- `TOOL_PARALLEL["enforce"] = False` 时 `_plan_batch` 只用于记录冲突，执行仍走原生并发；`True` 时按计划执行。
- 异步分支：每个 path 组是一个顺序执行的协程，组间与安全调用用 `asyncio.gather`；结果按原 index 回填。
- 同步分支：用 `get_executor_for_config(config)` 的线程池提交各 path 组；组内仍按原顺序逐个 `_run_one`；结果 `_combine_tool_outputs`。
- 结果统一交给 `_combine_tool_outputs(outputs, input_type)`，`Command` / `return_direct` 等行为不变。
- 分类/日志放在 `_plan_batch` 内，每个批次只执行一次，天然不会为每个 tool call 重复打日志。

关键点：**不要**从分支复制 `_get_config_list` / `_build_tool_runtimes`；它们不存在。按当前 `ToolNode._afunc` / `_func` 的内联写法重写，并在兼容性测试里 pin 住所依赖的私有方法。

### 2.4 安装方式

`create_agent` 不暴露 `tool_node` 参数；`langchain.agents.factory` 在构造时读取模块级 `ToolNode`。因此：

```python
def install_safe_tool_node() -> None:
    import langchain.agents.factory as factory
    factory.ToolNode = SafeToolNode
```

调用位置：`agent/core.py` 模块导入时、`built_agent()` 之前执行一次（子代理的 `create_agent` 也走同一个 factory 全局，自动生效）。分支里被注释掉的 `patch_tool_node()` 改为受配置控制：

- `TOOL_PARALLEL["enabled"] = False` → 不 patch，行为与今天完全一致。
- `TOOL_PARALLEL["enabled"] = True` → patch 一次；进程内所有 `create_agent`（main / child / auxiliary）都用 `SafeToolNode`。
- `TOOL_PARALLEL["enforce"] = False` → `SafeToolNode` 仍走原生并发，只记录不安全批次，用于观察误报。
- `TOOL_PARALLEL["enforce"] = True` → 不安全批次整批串行。

保留全局 patch 的理由：这是唯一能在不改 `create_agent` 源码的情况下拿到完整批次的位置。风险由“pin LangGraph 版本 + 兼容性测试”兜底；上游若改私有方法，测试会先红。

### 2.5 配置

新增 `config/features/agent_side/tool_parallel.py`：

```python
class ToolParallelConfig(TypedDict):
    enabled: bool              # install SafeToolNode
    enforce: bool              # False = observe only
    log_unsafe_batches: bool   # one warning per unsafe batch
    system_lock: bool          # process-wide terminal/code-execution mutex
    interaction_lock: bool     # per-session question/exit_plan_mode mutex

TOOL_PARALLEL: ToolParallelConfig = {
    "enabled": True,
    "enforce": True,
    "log_unsafe_batches": True,
    "system_lock": False,
    "interaction_lock": True,
}
```

下面是**收尾后的默认值**；Phase 1 先设 `enforce=False` 观察日志，Phase 2 再切到 `True`。`enabled=False` 是总开关；`enforce=False` 是灰度观察；`log_unsafe_batches` 只影响日志，不改变执行。`system_lock` 默认关闭（启用后所有 agent 的 shell/代码执行串行，可能明显变慢，先观察再开）；`interaction_lock` 默认开启（同一会话的 HITL 交互本来就不应该并发）。

### 2.6 与现有多 agent 机制的关系

- 本计划只约束**一个 agent 的一次 ToolNode 批次**。
- 每个子 agent 在自己的图中执行，`SafeToolNode` 也会作用于它的批次（因为全局 patch），但父/子之间没有共享批次锁。
- 两个 agent 同时写同一个文件仍由 `file_write_lock` + `patch_file` 的 CAS 保护。
- 同一子代理的并发数量、排队与超时仍由 `runtime/lane` 的 SUBAGENT lane 和 spawn admission 控制。
- 唯一有意跨 session 的互斥是 `system` 锁：启用后两个 agent 的 `terminal` / `python_repl` / `execute_code` / `ptc` 不会同时执行。除此之外不做通用的跨 session 全局锁；那会把不同会话的独立写操作无谓串行化。

```python
READ_ONLY_TOOLS = frozenset({

    "agents_list", "subagents_list", "sessions_messages",

```

`code_intel_*` 的只读查询也加入；如果该组工具是动态注册的，在工厂里按实际名字补。

`question` **不在** READ_ONLY_TOOLS：它虽然不写磁盘，但会占用 HITL 交互通道，属于 `user_interaction` 资源，不能和同批工具并行。

### 3.2 显式 `concurrent_safe`

| 工具 | 标注 | 理由 |
|---|---|---|
| `sessions_spawn` | `concurrent_safe: True` | spawn 本身是登记新 child，不共享可变状态；真正的并发由 SUBAGENT lane 控制 |
| 其他 | 不标 | 默认不安全 |

### 3.3 必须标 `side_effect_scope` 的写工具

| 工具 | scope | 说明 |
|---|---|---|
| `write_file`, `patch_file` | `workspace` | 同文件读写由 path 组调度 + `file_write_lock` / `file_read_lock` 协调；不同文件可并发 |
| `terminal`, `python_repl`, `execute_code`, `ptc` | `system` | 可能写文件 / 改环境 |
| `memory` | `session` | 写 MesMemory；**即使 idempotent=True 也不可并行** |
| `todolist_write` | `session` | 写 SQLite todo |
| `taskflow_*` 的写操作 | `session` | 写 SQLite / dispatch |
| `skill_manage`, `enter_plan_mode` | `session` | 改技能 / state register |
| `exit_plan_mode`, `question` | `user_interaction` | HITL 交互通道，同一会话同一时刻只允许一个 |
| `sessions_send`, `sessions_steer`, `sessions_kill`, `sessions_yield` | `session` | 改子代理状态 / 等待 |
| `browser_*` | `network` | 浏览器操作有副作用；已有 per-page `nav_lock`，不另加全局锁 |
| `cron_*` | `session` | 写 cron_jobs.json |

不要求给所有工具都加 scope；没有 scope 且不在 READ_ONLY_TOOLS 的工具默认不安全，行为是保守的。测试要保证 `TOOL_GROUPS` 里的每个名字要么在 READ_ONLY_TOOLS，要么在测试的“已知不安全”名单里，防止新增工具漏标。

`read_file` 同时在 `READ_ONLY_TOOLS` 和 `FILE_READ_TOOLS`：前者说明它没有普通副作用，后者让调度器按 path 分组；两者不冲突，文件调度优先。
### 3.4 资源锁补缺（文件读锁 + 两个缺口）

**文件读写锁（补 `read_file` 的缺口）**

- `agent/tools/pub_base/path_lock.py` 增加进程内 per-path 读写门：`path_read_lock`（共享）与 `path_write_lock`（独占，现有 `path_lock` 改名/保留别名）。写者优先：已有等待中的写者时，新读者排队，避免写者饥饿。
- `agent/tools/pub_base/file_lock.py` 的 `flock_path` 增加 `shared=False` 参数：读用 `LOCK_SH`，写用 `LOCK_EX`；新增 `file_read_lock`，保持“进程内门 → 跨进程 flock”的固定顺序。
- `read_file._core` 在读文件时包一层 `file_read_lock(resolved)`；`write_file` / `patch_file` 继续用 `file_write_lock(resolved)`。
- 同 path 的读写在**同一批内**由 2.2 的调度器按 `tool_calls` 顺序串行；跨 agent / 跨进程由读写锁互斥，谁先拿到锁谁先执行，不承诺调用顺序。
- 两个读同一文件可共享；读与写、两个写互斥。不同 path 完全并发。
- 不覆盖 `terminal` / `python_repl` / `execute_code` / `ptc` 对文件的写入：它们的目标路径无法从参数可靠推断，仍由各自的 `system` 锁/批处理约束。

**`system` / `user_interaction`（工具层锁）**

新增 `agent/middlewares/tool_resource_lock.py`（主链和子链都注册为 required）：

- 读取 `request.tool.metadata["side_effect_scope"]`。
- `system`：进程级独占锁，包住 handler。异步路径用 per-loop `asyncio.Lock`，同步路径用 `threading.Lock`；`TOOL_PARALLEL["system_lock"] = False` 时只透传。
- `user_interaction`：按 `session_id` 独占锁；`interaction_lock=False` 时只透传。
- 其他 scope（`workspace` / `session` / `network`）：**不加锁**，直接透传。文件、memory、SQLite、browser 的现有锁已经各自负责；在工具层再加一把只会重复串行。
- 锁必须用 `async with` / `with` 包住整个 `handler(request)`，异常和取消路径自动释放；不要手工 acquire/release。

这个 middleware 与 `SafeToolNode` 是两层独立机制：关掉 `SafeToolNode`（`enabled=False`）不会关掉资源锁；关掉资源锁开关也不会让批次并发。文件读写锁在工具 `_core` 内获取，不属于这个 middleware，因为 canonical path 在那里才解析。

## 4. 实施顺序

### Phase 0：分类基础设施（不改行为）

1. 新增 `agent/tools/parallel_safety.py`：`ToolSafetyMeta`、`READ_ONLY_TOOLS`、`FILE_READ_TOOLS` / `FILE_WRITE_TOOLS`、`tool_is_parallel_safe`、`file_resource_key`、`plan_batch`。
2. 新增 `config/features/agent_side/tool_parallel.py` + 导出。
3. 单测：`read_file` / `memory` / `write_file` / `sessions_spawn` / 未知工具；同一 path 与不同 path 的 `file_resource_key`。

### Phase 1：SafeToolNode + 安装

1. 新增 `agent/safe_tool_node.py`，按 1.3.9 的 `ToolNode._afunc` / `_func` 重写（不要复制分支的缺失 helper）；执行 `plan_batch` 的“path 组串行 + 组间并发”计划。
2. `agent/core.py` 导入时按 `TOOL_PARALLEL["enabled"]` 调用 `install_safe_tool_node()`。
3. 先跑 `enforce=False`（观察模式），确认日志里的不安全批次与文件冲突组符合预期。
4. 兼容性测试：`ToolNode` 上仍存在 `_parse_input` / `_extract_state` / `_arun_one` / `_run_one` / `_combine_tool_outputs` / `tools_by_name`；不存在时测试失败并提示升级适配。
5. 子代理集成测试：父子 agent 的 `create_agent` 都使用 `SafeToolNode`（可断言 factory 已被替换）；同一 path 的读写在父/子各自批次内保序。

### Phase 2：标注 + 强制

1. 给 `sessions_spawn` 加 `concurrent_safe`；给写工具加 `side_effect_scope`；给 `memory` 明确不可并行。
2. 把 `enforce` 切到 `True`。
3. 全量测试门 + 文档同步（AGENTS 的 middleware / tools 说明）。

### Phase 3：资源锁补缺

1. 新增 `agent/middlewares/tool_resource_lock.py`，并在 `scaffolding._MAIN_REQUIRED` / `_SUBAGENT_REQUIRED` 与 `MIDDLEWARE_ORDER` 注册。
2. `path_lock.py` 增加共享读门（写者优先），`file_lock.py` 增加 `file_read_lock` / `flock_path(shared=True)`；`read_file._core` 用 `file_read_lock`，`write_file` / `patch_file` 保持 `file_write_lock`。
3. 给 `terminal` / `python_repl` / `execute_code` / `ptc` 标 `side_effect_scope: "system"`；启用 `system_lock` 后，跨 agent 的 shell/代码执行串行。
4. 给 `question` / `exit_plan_mode` 标 `side_effect_scope: "user_interaction"`；同一会话的 HITL 交互串行。
5. `workspace` / `memory` / SQLite / browser 不新增工具层锁；测试确认它们在 `system_lock` / `interaction_lock` 之外仍按各自现有机制工作。

### Phase 4：观察与收尾

1. 用真实会话观察 `unsafe batch` 日志，确认没有把只读/独立工具误判为不安全；发现漏标就补 metadata 或 READ_ONLY_TOOLS。
2. 先开 `system_lock` 观察 terminal / code execution 的跨 agent 串行是否造成明显延迟；如果代价过高，保留 `SafeToolNode` 的批内串行，`system_lock` 继续默认关闭。
3. 检查同一会话两个 `question` 的历史行为，确认 `interaction_lock` 没有引入等待死锁；HITL resume 后锁必须释放。
4. 观察同一 path 读写锁的等待日志；如果读锁导致明显延迟，确认是跨 agent 竞争还是写者优先策略，再决定是否改成更细的 path 分段。

## 5. 测试

新增 `tests/agent/tools/test_parallel_safety.py`：

- `read_file` + `web_search` → safe。
- `memory` → unsafe（即使 `idempotent=True`）。
- `write_file` / `patch_file` / `terminal` / `question` → unsafe。
- `sessions_spawn` → safe。
- 未知工具 / 缺 metadata → unsafe。
- `destructive=True` 覆盖 `concurrent_safe=True`。
- `file_resource_key("read_file", path)` / `file_resource_key("write_file", path)` 得到同一 canonical path、不同 mode；不同 path 不同 key；非法/超界 path 返回 `None`。

新增 `tests/agent/middlewares/test_tool_resource_lock.py`：

- 两个不同 session 的 `terminal` 在 `system_lock=True` 时互斥；`system_lock=False` 时重叠。
- 同一 session 的两个 `question` 在 `interaction_lock=True` 时互斥；不同 session 可并发。
- 取消 / 异常路径释放锁；超时不会永久占锁。
- `workspace` / `session` / `network` scope 不经过这层锁。

新增 `tests/agent/tools/file_tools/test_file_rw_lock.py` 与扩展 `test_file_lock_cross_process.py`：

- 同一 path 两个 `read_file` 可以重叠（共享锁）。
- 同一 path 的 `read_file` 与 `write_file` 互斥；读先则读旧值，写后生效。
- 同一 path 两个 `write_file` 互斥；后一个写入为最终值。
- 不同 path 的读写可以重叠。
- 跨进程：读用 `LOCK_SH`、写用 `LOCK_EX`；写者等待现有读者，后续读者等待写者（写者优先，不饥饿）。
- 取消 / 抛异常路径释放 in-process 门和 flock。

新增 `tests/agent/test_safe_tool_node.py`：

- 两个 safe 工具并发：用 `asyncio.Event` / `barrier` 证明重叠。
- 同一 path：两个 `read_file` 可以重叠（共享）。
- 同一 path：`read_file(A)` + `write_file(A)` 不重叠；正序（读在前）读旧值，逆序（写在前）读新值；`write_file` 的 license 行为与顺序一致。
- 不同 path：`read_file(A)` + `write_file(B)` 可以重叠。
- 同一 path 两个写：顺序与 `tool_calls` 一致，最后一个生效。
- 一个 barrier 工具（如 `terminal`）+ 文件工具：整批不重叠，顺序与 `tool_calls` 一致。
- `enforce=False`：仍按原生并发（同 path 文件读写也不保序），只记录冲突组 warning。
- `enabled=False`：factory 未被 patch。
- 结果顺序与 `tool_calls` 对齐；`Command` / `return_direct` 输出不被破坏。
- 同步 `_func` 与异步 `_afunc` 各覆盖一次。

兼容性测试：

- `SafeToolNode` 依赖的 `ToolNode` 私有方法存在；LangGraph 升级后先在这里失败。
- 使用真实 `create_agent` 构建一个两工具 agent，确认 `factory.ToolNode is SafeToolNode`。

回归：

- `tests/agent/middlewares/` 全量；ToolGuardrails、HITL、MessagePersistence 的 tool-call 包装链不因替换 ToolNode 改变。
- 全量 split gate（A/B/C）。

## 6. 风险与非目标

| 风险 | 对策 |
|---|---|
| LangGraph 私有方法漂移 | pin 版本 + 兼容性测试；升级时按 `ToolNode._afunc` / `_func` 重新对齐。 |
| 全局 patch 影响所有 `create_agent` | `TOOL_PARALLEL["enabled"]` 总开关；`enforce=False` 可先观察；测试断言 patch 生效与关闭。 |
| 标注错误导致过度串行 | 默认不安全只是性能损失；观察日志 + 补 READ_ONLY / `concurrent_safe`，不阻断正确性。 |
| 串行批次中的长工具阻塞同批其它调用 | 这是安全语义，不是缺陷；依赖顺序或长任务的调用本来就不应该放在同一批。 |
| `system_lock` 让所有 agent 的 shell 串行 | 默认关闭；先观察；真正需要并行命令的部署可以保持关闭，靠批次层保证单 agent 内的顺序。 |
| `interaction_lock` 在 HITL 挂起时占锁 | 用 `async with` 包住 handler；中断/取消路径会释放。测试覆盖两个 question、resume 和异常。 |
| 同一文件跨 agent 读写 | `file_read_lock`（共享）/ `file_write_lock`（独占）负责互斥；顺序是锁获取顺序，不是调用顺序。 |
| 写者优先导致读者等待 | 读操作通常短；写者优先避免写饥饿。若长读造成明显延迟，改用公平队列或 path 分段，先用测试/日志验证。 |
| path 解析失败导致误并发 | `file_resource_key` 返回 `None` 时按 barrier 整批串行；只对能解析到 canonical path 的调用做细粒度调度。 |
| 子代理不同工具集 | 分类按 `tools_by_name` 的 metadata 走；每个 child 的 `SafeToolNode` 独立分类。 |

非目标：

- 不做通用的跨 session 全工具锁；只有显式的 `system` 锁跨 session。
- 不重建 `workspace` / `memory` / SQLite / browser 已有的锁。
- 不做通用的工具依赖 DAG：只对文件工具按 canonical path 做冲突分组；`terminal` / 其他非文件工具仍是 barrier。
- 不做按任意参数推断资源；只有 `file_path` 能可靠解析到 canonical path 时才细粒度调度，解析失败就退回 barrier。
- 不把 `idempotent` 当作并行安全的唯一依据。
- 不把 `smart_tool_node.py` 原样合入 `dev`。

## 一、完整成功路径——第 5 字段 success_steps（LLM 自报）+ 压缩 carry-forward

> **决策（方案 A）**：不挖 trajectory（方案 B 会挖到 agent 探索型工具调用噪音——agent 试探性地调用工具，这些不是真正成功路径的一部分）。改为让子 agent 在 handoff 里**自报**第 5 个字段 `success_steps`：它执行结束后，**自己梳理出直达成功的路径的有序步骤**，排除探索型噪音。
>
> **目标**：plan 抽取能拿到完整、可重放的成功路径（步骤序 + 工具 + 参数 + 结果），而非从 locked_decisions 高层推断。success_steps 是子 agent 主动 curate 的直达成功的路径，不是 trajectory 的原始工具调用流水。

### H1. 第 5 字段 success_steps

`success_steps` 加入 handoff，LLM 填（与 task_understanding/discovered_hard_constraints/locked_decisions/failed_branches 同层，LLM 现在填 **5 个**字段）：

| 字段 | 类型 | 含义 |
|---|---|---|
| `success_steps` | `list[{step: str, tool: str, params: str, outcome: str}]` | **直达成功的路径**——子 agent 完成任务后，自己梳理出「从开始到成功**直达**的那条路」的有序步骤。**只含直接导致任务完成的工具调用步骤**（含直接服务于成功路径的前置理解步骤如 read_file 探查；不含调试/探索/失败重试/被放弃的分支，那些进 failed_branches）。每步：步骤描述、用的工具、关键参数、结果。任务失败则空列表。**与 locked_decisions 分工**：locked_decisions = 高层方案选择+理由（决策级）；success_steps = 决策落地的有序操作（执行级）；不要在 success_steps 里重复 locked_decisions 的决策理由。 |

**为什么 LLM 自报而非 trajectory 挖**：
- trajectory 记录所有工具调用（含探索型试探、调试调用、被放弃的子方案调用）——机械挖出的是**超集噪音**，分不清哪步是直达成功的路径、哪步是探索。
- 子 agent 自己知道「最终走通的是哪条路」——它执行完后 curate 出直达成功的步骤，天然排除探索噪音。
- 代价：+1 字段 LLM 填（token 开销 ~200-800）；可靠性依赖子 agent 自觉填写（系统提示给模板）。

`HANDOFF_SCHEMA`（Phase 2 合入 output_schema 的）加 `success_steps`；`failed_paths` 同步改为 `failed_branches`（见「二」，两项一起落地）：

### H2. SummaryDoc carry-forward（避免压缩丢失）

子 agent 的 success_steps 在执行中逐步明确（先探索，最终确定成功路径）。若对话被压缩，已明确的成功步骤必须靠 SummaryDoc carry-forward 保留，否则最终 handoff 的 success_steps 会丢中途的步骤。

#### SummaryDoc 新增 `success_steps` 字段

```python
success_steps: list[str] = Field(default_factory=list,
    description='The DIRECT path to success — only the minimal ordered steps that '
    "led straight to task completion, each as '<step> (<tool>, <params>): <outcome>'. "
    "MUST EXCLUDE any exploratory/groping/tentative/abandoned branches (those go to "
    "failed_branches). Carry existing entries forward verbatim; replace with the final "
    "curated DIRECT path once the approach settles. Empty if task failed.")
```

- `_LIST_FIELDS` / `_FIELD_CAPS`（`SUCCESS_STEPS_MAX_ITEMS`）/ `_ITEM_TOKEN_BUDGETS` / `render_summary_markdown` 条件段同步。
- carry-forward prompt：`_SUMMARY_JSON_RULES` 加 `success_steps` 行（carry forward verbatim；approach settles 后用直达路径替换）；`_SUMMARY_UPDATE_INSTRUCTIONS_STRUCTURED` 加 carry-forward 规则。

> **格式断层（已知，接受）**：SummaryDoc.success_steps 是 `list[str]`（每条 `'<step> (<tool>, <params>): <outcome>'` 摘要文本，与现有 failed_branches/constraints 的 list[str] 惯例一致），handoff 的 success_steps 是 `list[{step, tool, params, outcome}]` 结构体。carry-forward 只保摘要文本；最终 handoff 的结构体由子 agent LLM 从 SummaryDoc 摘要 + 压缩后近期消息**重建**（解析字符串成字段）。**代价**：params 含括号/冒号时格式可能歧义，重建有损；params 是 LLM 摘要（可能简化/省略），非精确 tool args。**接受**：与 failed_branches 同模式（既有遗留）；success_steps 的 params 本就是 curated 摘要（非 trajectory 精确 args），「近似可重放」是 success_steps 的固有特性（见 H7）。

### H3. 压缩对成功/失败分支连续性的影响（关键分析）

**问题**：压缩把对话消息扁平化成 SummaryDoc 的列表字段。success_steps 和 failed_branches 是**两个独立列表**。压缩会不会破坏成功与失败分支的连续性（时序交织、因果链）？

#### 连续性的三个层次

| 连续性层次 | 压缩后是否保留 | 说明 |
|---|---|---|
| **success_steps 内部顺序**（成功路径步骤的先后） | ✅ 保留 | success_steps 是有序列表，carry-forward 保持顺序。直达成功的路径的步骤序不丢。 |
| **failed_branches 内部**（失败列表） | ✅ 保留 | failed_branches 列表，carry-forward 保持。失败条目不丢。 |
| **成功与失败的跨分支时序交织**（「先试 A 失败 → 再试 B 成功」的时序/因果） | ⚠️ 部分丢失 | 两个独立列表，跨列表的时序关系（哪次失败紧接着哪次成功）不显式保留。 |

#### 跨分支时序丢失的影响评估

关键点：**success_steps 是「直达成功的路径」而非「所有成功调用的流水」**。子 agent 在 handoff 里只填**直达成功的那条路**（一条有序路径），探索型/被放弃的尝试进 failed_branches。所以：

- 成功分支只有**一条**（直达路径），不是多次成功的交织。
- 失败分支是**多条**（所有试过的失败路径）。
- 跨分支时序 = 「这些失败了 → 最终这条成功了」。这个关系**可从两个字段推断**：failed_branches 列出失败，success_steps 列出最终成功。因果链（「A 失败所以改试 B」）隐含在内容里——B 是直达成功的路径，A 在 failed_branches，读者/LLM 能推出「B 是在 A 失败后采用的」。

**所以跨分支时序的丢失是可接受的**：success_steps 是单条直达路径，不需要和失败交织排序。plan 抽取 LLM 拿到 failed_branches（失败清单）+ success_steps（直达成功的路径），能 reconstruct「试过这些失败 → 最终这条路成功」。

#### 真正的连续性风险：压缩发生在探索中途

**风险场景**：子 agent 还在探索（没确定直达成功的路径）时对话被压缩。此时 success_steps 是**部分/暂定**的（可能含后来被放弃的子方案的步骤）。SummaryDoc carry-forward 把这些暂定步骤保留。子 agent 继续探索，最终确定真正的成功路径，**在最终 handoff 里用直达路径覆盖 success_steps**。

**缓解**：SummaryDoc.success_steps 的 carry-forward prompt 明确「approach settles 后用最终 curated 路径替换，不要保留被放弃的中间暂定步骤」。子 agent 在 handoff 填 success_steps 时，从 SummaryDoc（carry-forward 的暂定）+ 压缩后近期消息（最终确定）重新 curate，**填直达路径而非 SummaryDoc 的暂定值**。SummaryDoc.success_steps 是中途保命，最终 handoff 是 curated 覆盖。

**残留风险（未消除，靠 prompt 缓解，不保证）**：若子 agent 在压缩后没意识到 SummaryDoc.success_steps 含暂定步骤，可能直接复制进 handoff（带噪音）。缓解仅是 prompt：系统提示明确「success_steps 必须是直达成功的路径，重新梳理，不要照抄压缩摘要里的暂定步骤」。这是纯 LLM 自觉依赖，无机械保障（如压缩时标记暂定 vs 最终）。若观察期（H8 步骤 3）发现污染率高，需回退或加机械保障（如 success_steps 条目带 `settled: bool`，压缩时只 carry settled=True 的——增加复杂度，非 MVP）。

#### 结论

- **success_steps 内部顺序、failed_branches 内部**：压缩保留。✅
- **跨分支时序**：丢失但可接受（success_steps 是单条直达路径，不需和失败交织；因果可从两字段推断）。✅
- **压缩中途的暂定 success_steps**：靠 carry-forward prompt（「settles 后替换」）+ 系统提示（「最终 curated，不照抄摘要」）缓解——**未消除的残留风险，靠 LLM 自觉，不保证**。观察期监控污染率。⚠️
- **不破坏成功/失败分支的连续性**——因为 success_steps 是 curated 直达路径（单条有序），不是和失败交织的流水日志。扁平化成两个列表不丢关键连续性。

## 二、failed_paths → failed_branches 术语修正

### 问题

handoff 第 4 字段 `failed_paths`（条目 `{path, failure_reason}`）命名是「失败路径」，但实际语义是**失败分支**——每个条目代表一个被放弃的**尝试方向/方案**（如「用 ProcessPoolExecutor 并行编译」），不是步骤序列。示例一直是分支级（方向），只是字段名/key 叫了 path。与 success_steps（成功步骤序列）不对称，术语该区分。

### 改动范围

**文档层**（`计划_子agent派生上下文交接.md`）：
- `failed_paths` → `failed_branches`（字段名，所有出现处）
- `{path, failure_reason}` → `{branch, failure_reason}`（条目 key）

### 兼容性

- 旧 checkpoint 的 `run.completion.handoff` 里存的 JSON key 是 `failed_paths`——改名后读旧数据时 key 不匹配。缓解：`_extract_handoff_json`/`_read_subagent_runs` 读 handoff 时兼容旧 key（`handoff.get("failed_branches") or handoff.get("failed_paths")`），过渡期双读。新写入用 `failed_branches`。

### 选项

- **A. 全改（字段名+key+描述，文档+代码）**：语义彻底清晰，触已实现代码 + 旧数据兼容。推荐。**注意：纯术语改动，无功能收益，成本是 8 处代码 churn + 旧数据双读兼容 + 别名迁移 + 测试**——为术语偏好付的 churn，justified by 用户明确要区分失败分支 vs 成功步骤的不对称。

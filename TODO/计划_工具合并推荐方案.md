## 3. 判断标准

### 3.1 为什么省 1 个工具的配对合并不值得

plan_mode / web / todo 都是只省 1 个 schema，却要改负载代码 + 客户端 + 模型面文本：
- 模型能轻松处理 2 个配对工具（如 `web_search` + `web_fetch`），合并的 token 节省微乎其微
- 改动负载代码的风险（中间件按名匹配、安全包装按名、配置 tuple 按名）远大于省 1 个 schema 的收益
- 客户端耦合（WS 事件源匹配、HITL 卡片类型检测）需要前后端同步改，引入跨层协调成本

### 3.2 为什么省 7+ 个工具的大家族合并值得

browser(-7) 和 taskflow(-15) 的 token 节省大，且影响面可控：
- browser：8 个动词都是同一个 `BrowserManager` 薄封装，只需修 1 个 redaction prefix
- taskflow：16 个工具全部操作同一张 SQLite 表，负载点少（catalog + parallel_safety + tool_output_prune + delivery.py），模块函数本体不改

### 3.3 为什么 file 和 sessions 不做

- file：12+ 负载点触碰 parallel_safety 调度器核心——文件锁调度器按工具名分组，改为按 action 判断是核心架构改动。文件工具是每轮必用的 REQUIRED 工具，bug 风险致命
- sessions：递归防护（防子代理无限 spawn）按名阻止 `sessions_spawn`/`sessions_yield`，合并后要重做。scope 从分工具变为整个工具是行为变更（子代理失去 yield/send）

## 4. 根因判断（分层）

### 4.1 主因：`resume` 无法引用子代已存结果，父只能用自己写出的摘要

`agent/tools/taskflow/tools/taskflow_resume.py`：

- `:243` `result = result or ""` —— 缺省是**空字符串**，不是子代的 `completion.result_text`；
- `:294-310` 去重键是 `(child_session_key, result)`，所以每次改写摘要都算"新 resume"；
- `:317` 用 `child_session_key` 匹配 step；对不上就以 `step_id=None` 记一条 flow-level result（不判）；
- 全程没有任何"调用方传的 result 明显短于子代已存结果"的检查。

父上下文里只有 4k 交付载体，模型要做 resume 只能自己重写 —— 于是 452 字符摘要被当成 step 结果。**这是唯一直接决定本题成败的环节。**

### 4.2 放大因素

1. **重试没有存活窗口**：`wait_all` 的 timeout 是调用方参数（本题第二次传 60 秒），而同类调研首跑用了 507 秒；父在 61 秒后判定"等不到"，转而再次注入摘要。
2. **HALT 在子代仍 RUNNING 时结束回合**：第一次 HALT 距重试 1 起跑仅 36 秒。回合结束后 harness 给了 1 次 continuation（上限 3，因 no-progress 提前停止），随后进程被杀，两条 replacement 一起死。
3. **允许对 RUNNING 子代注入结果**：`resume` 只看 child key，不检查该 run 是否 TERMINAL，父因此可以在子代还在跑时替它"交卷"。

### 4.3 潜在因素（即使修好传递也会撞上）

1. **判官只取前 8,000 字符**；报告的"实现计划"在结尾。
2. **交付载体 4,000 字符**；父没有任何"完整结果可用"的提示。
3. **存储 24,000 B**；本题落盘 23,838 字符（原文 29,999 字节，尾部带截断标记）。对 8k 判官视图没有额外影响，但报告越长，P1-A 的 head+tail 越重要。

### 4.4 症状层（不是根因，但值得加固）

1. `no-progress` 只在重复 4 次后阻断，且只提示"换方法"，没有强制策略切换；`already resumed` 与"子代仍在跑"被混为一谈。
2. HALT 的终止消息不含"仍有子代在运行"的信息，父与 harness 都不知道该等。
3. evaluator 的 no-progress 规则本身是对的（`_MAX_PLAN_CONTINUATIONS=3`；有 `in_flight` 时**不会**停止，会继续给 wait continuation）。本题命中停止，是因为上游 HALT 先把 live child 变成了 blocked，flow 随即不再 in_flight——**修 evaluator 不解决问题，修 HALT 才解决**。

### 4.5 不是根因（更正 r1）

- 不是 verifier / 容器 / GOLD 自检：P2P 165/165，`gold_self_check=checked`。
- 不是超时：`timeout=false`，`no_progress_stop=true`；子 agent 的 507 秒远低于 `run_timeout_seconds=5400`。
- 不是 StepJudge 标准过严：判据被同一份报告满足；judge 没看到它。
- 不是经验抽取：开关已写入，未触发是 todo 未完成的下游现象。

## 5. 修复计划（按因果优先级，替换 r1 的 P0/P1）

### P0-A：`resume` 能使用子代已存结果，并拒绝"摘要替代"

**目标**：让"把子代结果交给 TaskFlow"成为默认行为，而不是让模型复述。

**实现**（`agent/tools/taskflow/tools/taskflow_resume.py`）：

1. `result` **缺省时**（空串）且 `child_session_key` 命中某个 step：用 `agent.tools.subagent.registry.memory.find_by_child_session_key(child_session_key)` 找到该 run，读 `completion.result_text` 作为本次 result，并在返回文本里注明 `result_source=child_completion (N chars)`。读不到（无 completion）才退回现状。
2. 调用方传了 `result`、但子代已存 `completion.result_text` **≥ 2 倍长度且 ≥ 2,000 字符**时：
   - `step_outcome` 为 `success`/缺省 → **拒绝**，错误文本给出两边长度并提示"省略 `result` 即可使用子代原始结果"；
   - 新增 `force_result: bool = False` 作为显式逃生（合法摘要/人工裁剪场景）。
3. 子代的 `execution.outcome` 是 `blocked` / `budget_exhausted` 而调用方声明 `success` 时，返回文本必须点名子代终态；配合 (2) 不允许用摘要静默覆盖。

**验收**（新增 `tests/agent/tools/taskflow/test_resume_result_source.py`）：

- 省略 `result` → 判官/StepJudge 收到子代存储文本（长度断言）；
- 传 452 字符摘要 + 子代 23k → 拒绝且状态不变；加 `force_result=true` → 放行；
- 子代无 completion → 现状不变（空 result 允许，兼容旧路径）。

**风险**：子代存储结果（24k）进入判官后会被 8k 截断 → 见 P1-A。

### P0-B：给重试一个真实的存活窗口，并禁止替运行中的子代交卷

**目标**：重试要么被等到，要么明确失败；不能出现"父在子代 RUNNING 时注入摘要"。

**实现**：

1. `taskflow_resume`：用 `find_by_child_session_key` 取 run，若不是 `TERMINAL`（PENDING/RUNNING/INTERRUPTED）且没有 `force_result` → **拒绝**并返回该 run 的 `status/started_at/elapsed`，提示改调 `wait_all`。这一条单独就能阻止本题 21:47:20 的第一次摘要覆盖。
2. `wait_all`：调用方 `timeout_seconds` 低于下限（建议 `TASKFLOW_INFRA["wait_all_min_timeout_seconds"]`，默认 ≥ 120）且目标子代仍在 RUNNING 时，**抬到下限**并在输出里说明；或返回"仍在运行，已等待 N 秒，预计上限 M 秒"，让模型继续等而不是交卷。
3. `ToolGuardrails` HALT：若本回合曾对某 step 子代 resume 造成 no-progress，而该子代的 run 仍 RUNNING，HALT 消息必须带上 `child_session_key` 与 `elapsed`，并提示"子代仍在运行，结束本回合前先 wait_all"；同时把"对 RUNNING 子代 resume"从 no-progress 计数里排除（它现在会被 P0-B-1 直接拒绝）。
4. **evaluator 不改**：`_flow_in_flight` 的豁免已经存在（有 in-flight step 时会继续给 wait continuation），本题的停止是 HALT 先把 in-flight 变没导致的下游结果。这一条列为"确认无需修改"，避免再出现 r1/r2 初稿式的错误归因。

**验收**：

- 单测：对 RUNNING 子代 resume → 拒绝；`wait_all` 下限抬升有断言；
- 回放本题：HALT 不再发生在重试起跑 36 秒时；至少一次 replacement 走到 TERMINAL（`outcome=ok` 或新的 RETRY 有真实产物）。

### P1-A：长报告与判官视野对齐

**目标**：judge 能看到判据真正要求的内容（尤其结尾的实现计划）。

**实现（二选一，建议 a）**：

- a) `step_judge.py` 的截断改为 **head+tail**：如 5,600 头 + 2,400 尾，尾部保证包含"依赖排序实现计划"；配 `_clip_for_judge()` helper 与单测；
- b) 在 step 的 `judge_criteria`/任务模板里要求"报告 ≤ 7,000 字符，实现计划放在前 1/4"，把上限写进契约。

**验收**：单测断言 24k 输入下尾部段落出现在判官 prompt；回放本题时判官评语不再出现"缺实现计划"（前提是 P0-A 已生效）。

### P1-B：研究型 step 的 GATE 通道

**目标**：无 verification evidence 的研究型 completion 不再把父逼进"自己编 result"。

**实现**：

1. `subagent_completion_drain` 对 `functional_role in {researcher, librarian}`（或 step 无 `file_deps`/判据为文档型）的 completion 放行，或降级为"delivered with a research-note"；
2. GATE 拒绝文本追加一句可执行提示："子代结果已存，省略 `result` 调 `taskflow_step(resume)` 即可使用"（与 P0-A 配合，把死路变成下一步）。

**验收**：单测覆盖研究型 completion 不被 GATE 拦；回放本题时 `[GATE]` 不再出现在 step-1 的 resume 之前。

### P2-A：no-progress 强制换策略（r1 P0-2，降级）

保留 r1 的"第二次 no-progress 起强制提示停止 resume"。注意与 P0-B-1 的交互：对 RUNNING 子代的 resume 由 P0-B-1 直接拒绝，不应计入 no-progress 次数。

### P2-B：RUNNING 过渡持久化

`mark_run_running` 只写内存，导致崩溃后落盘的是 PENDING（本题两条 replacement 即如此），boot 会把它当 pending orphan 处理。改为 `set_run_durable`（同 delivery 过渡的做法），让 `started_at` 在拿槽时落盘。**影响范围小，但决定事后复盘与重启语义的可信度。**

### P2-C：经验抽取验证与解题验证解耦（r1 P1-3，保留）

- 经验抽取用已完成度高的 L1 已测题验证（如 `actionlint-action-pinning-lint`、`abs-module-cache-flags`）；
- 新增未测题只验证"是否产生 patch、F2P 是否 > 0"；
- 报告区分 `task 失败导致 fired=false` 与 `抽取机制失败导致 fired=false`。

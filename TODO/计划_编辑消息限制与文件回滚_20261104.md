# 计划_编辑消息限制与文件回滚_20261104

两项改动：
1. 限制编辑消息只能编辑最新一条用户消息，清理因此变为多余的逻辑/漂移
2. 编辑时使用 shadow-git 回滚被编辑 turn 产生的文件修改，对齐 ZCode 的 rewind 行为

## 一、限制编辑为最新用户消息

### 现状

`ChatBox.vue:498` 的 `canEditMessage` 允许编辑**任意**已持久化用户消息：

```ts
const canEditMessage = (message: MessageItem): boolean =>
  props.canEdit && props.selectionEnabled && message.role === CHAT_ROLE.USER
  && message.id > 0 && message.turn_num > 0;
```

无 `isLast`/`isLatest` 限制。服务端 `_handle_edit_message`（`messages.py:432`）
也不拒绝非最新消息——唯一拒绝原因是 `compacted`。

### 改动

#### 1.1 前端：`canEditMessage` 增加"最新用户消息"判断

`ChatBox.vue:489-499`：

```ts
// 新增：判断是否为消息列表中最后一条用户消息
const isLatestUserMessage = (message: MessageItem): boolean => {
  for (let i = chatMessages.value.length - 1; i >= 0; i--) {
    if (chatMessages.value[i].role === CHAT_ROLE.USER) {
      return chatMessages.value[i].id === message.id;
    }
  }
  return false;
};

const canEditMessage = (message: MessageItem): boolean =>
  props.canEdit && props.selectionEnabled && message.role === CHAT_ROLE.USER
  && message.id > 0 && message.turn_num > 0
  && isLatestUserMessage(message);  // 新增
```

> **注意虚拟列表窗口**：`chatMessages` 是当前加载的窗口（最多 400 行）。
> 如果最新用户消息在窗口外（用户滚到了历史区），铅笔不会显示——这是正确行为，
> 因为编辑历史消息本身就被禁止了。用户滚到底部即可看到最新消息的编辑按钮。

#### 1.2 服务端：`_handle_edit_message` 增加 latest 校验

`server/trigger/ws/messages.py:432`，在 `find_user_turn_cut`（line 497）之后、
`truncate_messages_after_turn`（line 499）之前，增加：

```python
# 查询当前 session 的最大用户 turn_num
max_user_turn = await asyncio.to_thread(
    _get_max_user_turn_num, session_id
)
if cut_turn_num != max_user_turn:
    await _send_edit_ack(ws, session_id, ok=False, reason="not_latest")
    return
```

新建 helper `_get_max_user_turn_num(session_id)` 在 `context_engine/store/core.py`：
```python
def get_max_user_turn_num(session_id: str) -> int:
    """The highest turn_num among persisted user (non-internal) messages."""
    row = _query_one(
        "SELECT MAX(turn_num) FROM messages WHERE session_id=? AND role='human' "
        "AND (origin IS NULL OR origin='user')",
        (session_id,)
    )
    return int(row[0]) if row and row[0] is not None else 0
```

新增 ack reason `"not_latest"`，前端处理：
- `use-chat-stream.ts::onEditAck`（lines 657-675）加 `not_latest` case →
  toast 提示"只能编辑最新一条消息" + 重新加载历史。

#### 1.3 清理多余逻辑/漂移

限制为最新消息后，以下逻辑可能产生漂移或冗余，需检查和清理：

**a. `find_user_turn_cut` 的 row_id 可选参数**

`edit_message` 帧接受可选 `row_id`（`agent-socket.ts:283`），用于精确定位
同一 turn_num 下的某一行。限制为最新消息后，`row_id` 仍可用于区分同一 turn 的
多个用户行（如排队消息），**保留**。

**b. 客户端乐观 UI 的 truncate 逻辑**

`use-chat-stream.ts::handleEdit`（lines 712-748）执行
`chatMessages.filter(row => row.turn_num < turnNum)`——截断编辑 turn 及之后的所有行。
限制为最新消息后，被截断的只有最新用户消息及其后的 AI 回复（无更多用户 turn），
逻辑仍正确但**截断范围缩小**。不需改动，但行为更简单了。

**c. `clearCachedMessagesFromTurn` 的 Dexie 清理**

`db.ts:525-537` 清理 `turn_num >= fromTurnNum` 的 Dexie 缓存。限制后清理范围
同上缩小，逻辑正确，不需改动。

**d. 非 compacted 的旧消息编辑尝试**

前端 `canEditMessage` 已阻止非最新消息的铅笔显示，但服务端仍需 `not_latest` 校验
作为安全网（前端可被绕过）。**这是必要的防漂移措施，不是冗余**。

## 二、编辑时使用 shadow-git 回滚文件修改

### 现状

编辑流程（`messages.py:432-530`）只操作对话状态（checkpoint + SQLite），
**不触碰磁盘文件**。被编辑 turn 产生的文件修改保留在磁盘上。

shadow-git 存在（`agent/tools/pub_base/shadow_git.py`），在每次文件写入工具调用时
创建快照（`ensure_checkpoint`），快照 commit message 含 `turn=N` 标识。
但 `restore_checkpoint` 只按 commit hash 恢复，无"恢复到 turn N"API。

ZCode 的做法：编辑时可选 `workspaceMode: "rewind"`，用 per-tool-call 的
`beforeContent` 快照回滚文件，有安全门控（hash 校验），先恢复文件再截断对话。

### 改动

#### 2.0 快照保留策略：当前轮永不被剪（新增，先于回滚实现）

**冲突**：`_prune_snapshots()`（`shadow_git.py:237-254`）每次快照后把
`SHADOW_REF` 重指到 `rev-list --skip=<total - max_snapshots> -n1`，即只保留最新
`SHADOW_GIT["max_snapshots"]`（100）个提交。快照链是**按项目根共享**的
（主会话 + 所有子代理、多个会话并发）：`ensure_checkpoint` 虽按
`(session, root, turn)` 去重（每个会话每轮最多一条），但一次 fan-out 起出上百个
子代理、或多个会话并发写同一项目时，单轮累计提交很容易超过 100；`pre_restore`
直接快照也计入。此时"被编辑 turn 之前的最后一个快照"（回滚边界）会被剪掉：
`restore_to_turn` 只能找到 turn 内部或更晚的候选 → `no_checkpoint` →
fail-open → 对话已截断但文件没有回滚，正是本计划要避免的结果。

**100 的源码位置（本仓库内唯一权威来源，无 env / sherry.jsonc 覆盖）**：

| 位置 | 作用 |
|------|------|
| `config/features/agent_side/shadow_git.py:29` | `"max_snapshots": 100` —— `SHADOW_GIT` TypedDict 的代码默认值，即"100"本身。上面几行注释解释了按项目根共享、`ensure_checkpoint` 每会话每轮去重的取舍。 |
| `agent/tools/pub_base/shadow_git.py:237-254` | `_prune_snapshots()`：第 243 行 `keep = int(SHADOW_GIT["max_snapshots"])`，`rev-list --skip=<total - keep> -n1` 计算切点并 `update-ref`（由 `_take_snapshot_locked` 每次快照后调用）。这就是 §2.0 要改造的剪枝点。 |
| `tests/agent/tools/pub_base/test_shadow_git.py:163` | `test_the_shipped_cap_is_one_hundred` 钉住默认值 100（不随机制改变）；同文件 170/179 行把 cap monkeypatch 成 3 验证"只保留 N 条"，新增 floor 测试沿用这个 fixture。 |
| `AGENTS.md:2374`；`wiki/file-safety/README.{md,zh,ja,ko}.md:73` | 文档写明 100 及其共享/并发背景；机制落地后改为"历史部分软上限，当前轮不受 100 限制"。 |

`SHADOW_GIT` 只有 `store_dir` 有 `SHERRY_SHADOW_GIT_DIR` 回退；`enabled` 与 `max_snapshots`
都是静态默认值，`evals/coding_capability/suite.py`、`evals/swebench/suite.py` 也只改
`store_dir`（把 store 指到 results 目录），**不碰 100**。

**机制（只有"超过 100 且不在最后一轮范围内"的提交才允许被丢弃）**：

1. **记录 turn floor（轮次边界）**：`_take_snapshot_locked()` 在写 commit 前
   已经读取了 `parent`（当前 `SHADOW_REF` 的 tip）。若该 `(session_id, root)` 在
   本轮还没有 floor，就把 `parent` 记为这一轮的 floor——它恰好是"本轮第一个
   快照之前的链尖"，也正是编辑本轮消息时要恢复到的边界。轮次取
   `_current_turn(session_id)`；floor 连同轮次写入内存 + store 内
   `state.json`（写盘 fail-open，失败只影响本次保留）。`new_turn()` 不落盘：
   它把该会话的 turn counter 推高一格，旧 floor 因**轮次不匹配**自然失效；
   **没有快照的 turn 没有 floor**，编辑它时不会误回滚到上一轮。
   `floor_for()` 只返回**轮次等于该会话当前轮**的 tip，且 state.json 带
   **boot id**（进程级）——重启后 turn counter 从 0 重新计数，可能与上一进程的
   轮次数字撞车（都从 1 开始），boot id 才是真正的判据：宁可回滚降级
   （`no_checkpoint`，fail-open），也不拿旧 floor 误回滚更早的轮次。
2. **剪枝尊重 floor，并修正了方向**：原来的 `_prune_snapshots()` 把
   `SHADOW_REF` 重指到"第 total-keep 新"的提交，而 ref 只能保留它和它的祖先
   ——这实际 **丢弃最新**的快照、保留最旧的 N 个（超过 100 后链尖永远冻结在
   第 100 个提交上）。现在改为保留**最新**的 `max_snapshots` 个：取第
   `keep` 新的提交作为"最老保留"，再从 `state.json` + 内存收集该 root 上所有
   活跃会话的 floor，取两者中**更老**的一个作为边界；对边界执行
   `git replace --graft <boundary>`（无父提交的替换对象），`rev-list`/`log`
   就在此截断，而**边界及更新提交的哈希全部不变**（链尖、隔离 worktree 基线、
   code-intel 的 `shadow_head` 都不受影响）。floor 已不在当前链上时忽略它。
3. **保留量上限**：实际保留 = `max(max_snapshots, 最老 floor 之后的提交数)`。
   多出来的只有各会话的当前轮；下一轮开始时 floor 前移，多保留的部分在下一次
   剪枝释放，不会无限增长。`max_snapshots` 因此成为"历史部分"的软上限
   （配置注释同步更新）。
4. **回滚只认 floor**：`restore_to_turn()` 用
   `floor_for(session_id)`（= 本会话当前轮开始前的链尖）作为唯一恢复目标；
   没有 floor（本轮没有任何快照 / 无项目根 / 重启导致轮次不匹配）直接返回
   `no_checkpoint`，**不做 `turn < before_turn` 的历史扫描**——上一进程的
   turn 数字与 `cut_turn_num` 没有可比性，退扫只会误回滚更早的轮次。这同时
   消掉了 2.3 的三重 turn 编号映射问题：floor 就是"本轮之前"，不需要
   `ordinal` / `cut_turn_num` 与 shadow-git `turn=` 的换算。
5. **回滚后重锚链尖**：checkout 到 floor 之后，工作树是旧状态而链尖仍指向
   回滚前的树；若不处理，重跑轮的 floor 会变成"回滚前"的状态，下次编辑会
   把刚删掉的文件复活。因此回滚成功后再拍一条 `post_restore` 快照，让链尖
   描述**已恢复**的树。（`pre_restore` 仍保留，作为撤销的撤销点。）

#### 2.1 shadow-git 新增 `restore_to_turn` API

`agent/tools/pub_base/shadow_git.py` 新增：

```python
def restore_to_turn(
    session_id: str,
    before_turn: int,
    *,
    project_root: Path | None = None,
) -> dict[str, Any]:
    """恢复工作树到本会话当前轮开始前的状态（编辑消息的文件回滚）。

    唯一目标：2.0 记录的 turn floor（当前轮的第一个快照替换掉的链尖，剪枝
    不会越过它）。没有 floor 时返回 {"restored": False, "reason": "no_checkpoint"}
    ——不做历史扫描（重启后上一进程的 turn 数字不可信）。
    """
    target = floor_for(session_id, project_root=root)
    if target is None:
        return {"restored": False, "reason": "no_checkpoint"}

    # 撤销的撤销点
    pre_restore_snapshot(root, session_id, before_turn)

    # 恢复文件（checkout 不删除新建文件，另做清理）
    git_checkout(root, target, ".")
    removed = _delete_new_files_since(root, target)  # ls-files vs ls-tree + untracked

    # 重锚链尖：让下一轮 floor 描述“已恢复”的树，而不是回滚前的
    post_restore_snapshot(root, session_id, before_turn)

    return {"restored": True, "commit": target, "removed": removed}
```

**关键问题：`git checkout <commit> -- .` 不删除快照后新建的文件。**
采用方案 A：`git ls-tree -r --name-only <target>` 得到目标文件集合，
`git ls-files`（索引 = 最后一次快照）与 `git ls-files --others --exclude-standard`
（最后快照之后新建、尚未入索引的文件）的都是“目标里没有”的文件，逐个删除并
`update-index --force-remove`；git 自己的 exclude 规则天然排除 `.git`、
`.sherry/shadow-git` 与 deny patterns。上限 500 个，路径 resolve 后必须仍在
项目根内，删除后顺带 rmdir 空目录。不用 `git reset --hard` / `git clean`：
那会重置整个工作树，破坏 shadow-git 的非破坏性原则。

#### 2.2 编辑流程集成 shadow-git 回滚

`server/trigger/ws/messages.py::_handle_edit_message` 的顺序（实现时按此落地）：

1. busy 检查 → `find_user_turn_cut` → **latest 校验**；
2. `truncate_messages_after_turn`（唯一还会拒绝的一步：compacted）——
   **在任何文件操作之前**，否则被拒绝的编辑会留下一个已回滚的工作区；
3. `shadow_git.restore_to_turn(session_id, cut_turn_num)`（失败/无 floor →
   fail-open，仅记录 `rollback_skipped`）；
4. `delete_messages_from_turn` → `clear_breakpoint` → （若跳过回滚则先发
   `ok: true, rollback_skipped: true` 的 warning ack）→ `submit_user_input`。

> 计划原文把"先文件、后对话"对齐 ZCode 的 `commitAfterApply`。落地时改成
> 对话截断先行：ZCode 的本地截断不会失败，而这里的 checkpoint 截断可能因
> compacted 拒绝——先回滚文件再拒绝编辑会留下不一致状态，反过来则与"没有
> 回滚"的旧行为一致，是更安全的一侧。

#### 2.3 Turn 映射问题

shadow-git 的 `turn=N` 是 session 级 turn counter（`_turn_counts[session_id]`，
每次 `new_turn()` 递增），而编辑流程的 `ordinal` 是 user turn 序数（非内部
HumanMessage 计数），`cut_turn_num` 是 SQLite batch number。三者不同。

**需要确认映射关系**：
- `new_turn(session_id)` 在 `workspace_notice/core.py:120-122` 每个新 turn 开始时调用。
- `ensure_checkpoint` 在文件写入时调用，读取 `_current_turn(session_id)`。
- 因此 shadow-git 的 `turn=N` 对应 session 的第 N 个 turn（不分 user/assistant）。
- `ordinal` 是 user turn 序数——如果每个 user turn 后跟一个 assistant turn，
  shadow-git turn ≈ `ordinal * 2`（或 `ordinal * 2 - 1`，取决于 turn 定义）。

**落地方式（2.0 的 floor 已经给出答案）**：不用 ordinal/cut_turn_num 映射。
编辑只能编辑最新用户消息，而该消息所属轮次的 floor 在 2.0 里按
`(session_id, root)` 记录为"本轮第一个快照之前的链尖"——直接恢复到这里即可。
下面的 `turn < N` 扫描只作为没有 floor 时的回退，不再是主路径。

回退路径（没有 floor 时）才使用扫描：取 `turn < before_turn` 的最新一条快照。
它依赖 `before_turn` 的正确映射，因此只作为冷路径，主路径永远是 floor。

#### 2.4 前端：ack 处理回滚状态

`use-chat-stream.ts::onEditAck`（lines 657-675）扩展：
- `ok: true, rollback_skipped: true` → toast 提示"文件未回滚（无快照或无项目目录）"
- `ok: true, rollback_skipped: false`（或无此字段）→ 正常流程

## 三、对齐 ZCode 的安全门控（可选增强）

ZCode 在回滚前做安全检查：当前磁盘文件 hash 与快照 afterContent hash 比对，
不一致则 `external_modified`，阻止回滚并弹冲突对话框。

sherry 的 shadow-git 目前无此检查。可作为第二期增强：

1. **回滚前检查**：对每个快照涉及文件，读取当前磁盘内容，与快照 commit 的
   blob hash 比对。
2. **不一致时**：fail-open（跳过该文件，继续回滚其他文件）或 fail-closed
   （拒绝回滚，提示用户手动处理）。
3. **冲突 UI**：前端弹对话框，显示冲突文件列表，让用户选"仅截断对话"或"取消"。

第一期不做安全门控，只做基本回滚 + fail-open。后续增强。

## 四、风险与边界（快照保留）

| 风险 | 说明 / 缓解 |
|------|-------------|
| 单轮远超 100 个快照 | 2.0 全量保留当前轮（+ 边界 floor），保留量临时上涨；下一轮释放。提交对象本身去重 + delta 压缩，磁盘成本可控。 |
| 并发会话互相抬高下限 | 取**最老**的当前轮 floor，多保留的只是各会话当前轮，数量受 lane 并发上限约束。 |
| 重启后 floor 过期 | 安全优先：state.json 带 **boot id**，重启后旧 floor 一律作废（`no_checkpoint` fail-open），绝不回滚到更早的轮次。要做到跨重启回滚，需把 turn counter 一并持久化（后续增强，本计划不做）。 |
| floor 指向已被替换的链 | 剪枝前用 `merge-base --is-ancestor` 校验可达性，不可达则忽略；回滚只认 floor，不做历史扫描。 |
| state.json 增长 | 每个 session 只存一条（最近一轮），覆盖写；写入用 tmp + replace，失败 fail-open。 |
| 子代理同轮写入被一起回滚 | 快照链按项目根共享且线性，恢复到边界会连同该轮子代理的写入一起回退——与本计划"回滚本轮工作区"的语义一致；跨轮历史不受影响。 |
| `git replace --graft` 的兼容性 | 只影响 `rev-list`/`log` 的遍历；存活提交哈希不变，`checkout <hash>`、隔离 worktree、`shadow_head` 均不受影响。每次剪枝新增一个替换对象/ref，体量可忽略。 |
| 被删文件是用户手写的 | 第一版按计划不做 hash 安全门控（§三），`_delete_new_files_since` 只删"目标树里没有"的文件；删除前 resolve 校验仍在项目根内。 |

## 验证

- 非最新用户消息不显示编辑铅笔。
- 服务端拒绝非最新编辑（`not_latest` ack）。
- 编辑最新用户消息时，该 turn 产生的文件修改被 shadow-git 回滚
  （文件恢复到编辑前的状态）。
- 无快照时（纯对话 turn 无文件修改）编辑正常进行（`rollback_skipped`）。
- 无项目目录时编辑正常进行（`rollback_skipped`）。
- **单轮产生 >100 个快照（含子代理 fan-out）后，编辑最新用户消息仍能回滚**：
  边界 floor 与整轮快照都保留；实际保留量临时超过 `max_snapshots`，下一轮
  floor 前移后回落。
- 普通历史（非当前轮）仍按 `max_snapshots` 截断，存储不随轮数增长。
- 进程重启后：重启后新跑的轮次 floor 照常生效；重启前那一轮编辑时回滚降级为
  `rollback_skipped`（不误回滚更早的轮次）。
- 全文搜索 `canEditMessage` 确认 latest 限制已生效。

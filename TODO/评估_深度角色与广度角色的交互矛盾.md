- 建档日期：2026-10-15
- 状态：**评估完成，待决策**
- 关联代码：
  - `agent/tools/subagent/spawn/system_prompt.py`（系统 prompt 构建）
  - `agent/tools/subagent/spawn/core.py::_resolve_child_tool_policy`（工具策略）
  - `agent/tools/subagent/roles/definitions/*/AGENTS.md`（五个广度角色定义）
  - `agent/tools/subagent/capabilities/core.py`（深度角色解析）

## 0. 两个维度

子代理的完整身份由两个正交维度决定：

| 维度 | 决定因素 | 取值 | 管什么 |
|------|---------|------|--------|
| 深度角色（depth role） | 嵌套 depth vs `max_spawn_depth` | MAIN / ORCHESTRATOR / LEAF | 能否 spawn、spawn 工具可用性、spawn 相关 prompt 段注入 |
| 广度角色（functional role） | `functional_role` 参数 | general / researcher / executor / reviewer / librarian | 工具白名单、model_tier、`## Role Instructions` body |

**关键设计原则**：深度角色是硬门控（三层：tool policy + call-time privilege + depth validation），广度角色是软约束（工具白名单 + prompt body）。两者独立运作，深度角色不读广度角色的 body 内容。

## 1. 系统 prompt 的拼装顺序

`build_subagent_system_prompt`（`system_prompt.py:8-190`）按固定顺序拼装：

| 段 | 注入条件 | LEAF 时 | ORCHESTRATOR 时 |
|----|---------|---------|-----------------|
| `## Your Role` | 总是注入 | "You are a LEAF worker… You CANNOT spawn" | "You are an ORCHESTRATOR… You MAY spawn" |
| `## Role Instructions` | `role_prompt_body` 非空时 | **注入**（body 原文） | **注入**（body 原文） |
| `## Rules` | 总是注入；spawn 指导（第 6 条）仅 `can_spawn=True` | 无 spawn 指导 | 有 spawn 指导 |
| `## Output Format` | 总是注入 | ✓ | ✓ |
| `## What You DON'T Do` | 总是注入；含 "do NOT spawn unless you are an ORCHESTRATOR" | ✓（LEAF 不是 ORCHESTRATOR，一致） | ✓（ORCHESTRATOR 就是 ORCHESTRATOR，一致） |
| `## Sub-Agent Spawning` | 仅 `can_spawn=True` | **不注入** | **注入**（spawn 操作指南） |
| `## Session Context` | 总是注入 | depth=N/max | depth=N/max |

`can_spawn` 在 `core.py:342` 写死：`can_spawn = role == SubagentSessionRole.ORCHESTRATOR`。

**要点**：`## Role Instructions`（广度角色的 AGENTS.md body）是**无条件注入**的——不管深度角色是 LEAF 还是 ORCHESTRATOR，body 原文都会出现在 prompt 里。

## 2. 工具策略矩阵

`_resolve_child_tool_policy`（`core.py:253-285`）的输出：

| 广度角色 | tools 字段 | 白名单模式？ | ORCHESTRATOR 时 | LEAF 时 |
|---------|-----------|-------------|----------------|---------|
| general | `inherit` | 否（继承模式） | deny-list 移除 spawn/yield → 有 spawn 工具 | deny-list 保留 spawn/yield → 无 spawn 工具 |
| researcher | `[read_file, search_files, terminal, web_search]` | 是 | spawn/yield **追加到** allow-list → 有 spawn 工具 | spawn/yield 从 allow-list **剥离** → 无 |
| executor | `[read_file, write_file, patch_file, terminal, python_repl]` | 是 | spawn/yield 追加到 allow-list → 有 spawn 工具 | spawn/yield 剥离 → 无 |
| reviewer | `[read_file, terminal]` | 是 | spawn/yield 追加 → 有 | 剥离 → 无 |
| librarian | `[read_file, search_files, terminal, web_search]` | 是 | spawn/yield 追加 → 有 | 剥离 → 无 |

**结论**：ORCHESTRATOR 深度下，**所有五个广度角色都能拿到 `sessions_spawn` 工具**——深度角色是硬门控，广度角色不影响 spawn 能力。

**子代理的工具来源**：`_assemble_child_tools` 调 `build_main_tools(session_id=...)` 构建**完整的**主 agent 工具集，再按子代理自己的白名单/deny-list 过滤。父代理的工具集**不限制**子代理——一个 read-only 的 researcher 可以 spawn 一个 write-capable 的 executor 子代理，executor 子代理从完整工具集里拿到自己的 `write_file` / `patch_file`。

## 3. 五个广度角色 × 两个深度角色的矛盾矩阵

逐个检查每个广度角色的 AGENTS.md body 是否包含与深度角色矛盾的内容：

### 3.1 general

**body 内容**："Full tool access (inherited from parent). Can read, write, modify, execute terminal, web search."
**spawn 相关声明**：无

| 深度 | 矛盾？ | 说明 |
|------|--------|------|
| ORCHESTRATOR | ✅ 无矛盾 | depth prompt 说 "MAY spawn"，body 没说不能 |
| LEAF | ✅ 无矛盾 | depth prompt 说 "CANNOT spawn"，body 没说能 |

### 3.2 researcher

**body 内容**："Read-only: you CANNOT modify, create, or delete files."
**spawn 相关声明**：无

| 深度 | 矛盾？ | 说明 |
|------|--------|------|
| ORCHESTRATOR | ✅ 无矛盾 | body 不提 spawn，depth prompt 说 "MAY spawn" |
| LEAF | ✅ 无矛盾 | body 不提 spawn，depth prompt 说 "CANNOT spawn" |

**但有一个语义张力**：researcher 是 read-only，但在 ORCHESTRATOR 时有 spawn 工具。它 spawn 的子代理可以是有写权限的 executor——read-only 的 researcher 指挥 write-capable 的 executor 干活。这不是矛盾（子代理的工具不继承父代理的限制），但需要调用者理解这一点。

### 3.3 executor ← **唯一有矛盾**

**body 内容**：包含 "Do NOT spawn further subagents (you are a LEAF executor)"
**spawn 相关声明**：**有**——硬编码 "you are a LEAF executor"

| 深度 | 矛盾？ | 说明 |
|------|--------|------|
| ORCHESTRATOR | ❌ **矛盾** | depth prompt 说 "You are an ORCHESTRATOR, you MAY spawn"；body 说 "Do NOT spawn, you are a LEAF executor" |
| LEAF | ✅ 无矛盾 | depth prompt 说 "CANNOT spawn"；body 说 "Do NOT spawn, you are a LEAF executor"——一致 |

**ORCHESTRATOR executor 的完整 prompt 矛盾清单**：

| 段 | 内容 | 倾向 |
|----|------|------|
| `## Your Role` | "You are an ORCHESTRATOR… You MAY spawn further subagents" | 允许 spawn |
| `## Role Instructions` | "Do NOT spawn further subagents (you are a LEAF executor)" | **禁止 spawn** |
| `## Rules` 第 6 条 | "When spawning child subagents, keep their tasks brief…" | 允许 spawn |
| `## Sub-Agent Spawning` | "You may spawn child subagents via sessions_spawn. Guidelines…" | 允许 spawn |
| `## What You DON'T Do` | "do NOT spawn subagents unless you are an ORCHESTRATOR" | 允许 spawn（你就是） |
| 工具集 | `sessions_spawn` 在白名单里 | 允许 spawn |

四条说"可以 spawn"，一条说"不可以 spawn"。模型大概率会 spawn（多数 + 工具可用），但 body 里那句 "you are a LEAF executor" 会让模型困惑。

### 3.4 reviewer

**body 内容**："Read-only: you CANNOT modify, create, or delete files."
**spawn 相关声明**：无

| 深度 | 矛盾？ | 说明 |
|------|--------|------|
| ORCHESTRATOR | ✅ 无矛盾 | body 不提 spawn |
| LEAF | ✅ 无矛盾 | body 不提 spawn |

**语义张力**：同 researcher——read-only 的 reviewer 在 ORCHESTRATOR 时可以 spawn write-capable 子代理。

### 3.5 librarian

**body 内容**："Read-only: never modify files in the target repo."
**spawn 相关声明**：无

| 深度 | 矛盾？ | 说明 |
|------|--------|------|
| ORCHESTRATOR | ✅ 无矛盾 | body 不提 spawn |
| LEAF | ✅ 无矛盾 | body 不提 spawn |

## 5. LEAF 节点的工具与 prompt 分析

### 5.1 工具：加载了，spawn 工具被剥离

LEAF 子代理的工具来自 `build_main_tools()` 构建的完整主 agent 工具集，按广度角色白名单 + LEAF 的 deny-list 过滤：

| 广度角色 | LEAF 工具集 | spawn 工具？ |
|---------|------------|------------|
| general | 全部工具 - DEFAULT_SUBAGENT_BLOCKED_TOOLS(spawn/yield) | 无 |
| researcher | [read_file, search_files, terminal, web_search] | 无（不在白名单 + 被剥离） |
| executor | [read_file, write_file, patch_file, terminal, python_repl] | 无（不在白名单 + 被剥离） |
| reviewer | [read_file, terminal] | 无 |
| librarian | [read_file, search_files, terminal, web_search] | 无 |

**结论**：LEAF 子代理正常加载自己的功能性工具，spawn/yield 被三层剥离：
1. 白名单模式：不在广度角色的 tools 列表里
2. deny-list：`DEFAULT_SUBAGENT_BLOCKED_TOOLS` 保留 spawn/yield
3. `can_spawn_children(role)` 返回 False：从 allow-list 剥离

### 5.2 Prompt：spawn 相关段被正确剥离

| prompt 段 | LEAF 时 | 正确？ |
|----------|---------|--------|
| `## Your Role` | "You are a LEAF worker… You CANNOT spawn" | ✅ |
| `## Rules` 第 6 条（spawn 指导） | 不注入（`can_spawn=False`） | ✅ |
| `## Sub-Agent Spawning` 段 | 不注入（`can_spawn=False`） | ✅ |
| `## What You DON'T Do` | "do NOT spawn unless you are an ORCHESTRATOR" | ✅（LEAF 不是 ORCHESTRATOR） |
| `## Role Instructions`（body） | **注入** | ⚠️ 见下 |

**`## Role Instructions`（body）是无条件注入的**——LEAF 也会拿到广度角色的 body 原文。对 executor 的 LEAF 来说，body 说 "Do NOT spawn (you are a LEAF executor)"——和 LEAF 的 depth prompt 一致，不矛盾。其他角色 body 不提 spawn，也无矛盾。

**结论**：LEAF 节点的工具和 prompt 都正确。spawn 工具被剥离，spawn 相关 prompt 段被跳过，body 原文注入但不与 LEAF 矛盾。

## 6. 其他发现

### 6.1 read-only 广度角色在 ORCHESTRATOR 时可 spawn write-capable 子代理

researcher / reviewer / librarian 是 read-only 角色，但在 ORCHESTRATOR 深度时拿到 `sessions_spawn` 工具。它们 spawn 的子代理从**完整主 agent 工具集**获取工具（`build_main_tools`），不受父代理工具限制。所以一个 read-only researcher 可以 spawn 一个 write-capable executor 子代理。

这不是矛盾——子代理的能力由自己的广度角色决定，不继承父代理的限制。但调用者需要理解：read-only 不意味着"不能指挥别人写代码"。

### 6.2 `## What You DON'T Do` 段的条件措辞

`system_prompt.py:110` 写的是 "do NOT spawn subagents unless you are an ORCHESTRATOR"——这是一个**条件句**，对 LEAF 和 ORCHESTRATOR 都正确：
- LEAF：你不是 ORCHESTRATOR → 不要 spawn ✓
- ORCHESTRATOR：你是 ORCHESTRATOR → 可以 spawn ✓

这个段总是注入，措辞自洽，不产生矛盾。

## 7. 修复建议

### 7.1 executor AGENTS.md：删除硬编码 LEAF 声明

**当前**：
```markdown
## When NOT to use
- Do NOT use for research-only tasks (use researcher)
- Do NOT use for code review (use reviewer)
- Do NOT spawn further subagents (you are a LEAF executor)
```

**改为**：
```markdown
## When NOT to use
- Do NOT use for research-only tasks (use researcher)
- Do NOT use for code review (use reviewer)
```

**理由**：depth role 的 prompt 已经正确处理了 spawn 能力声明——LEAF 说 "You CANNOT spawn"，ORCHESTRATOR 说 "You MAY spawn"。广度角色的 body 不应该替深度角色做声明，否则在 executor@ORCHESTRATOR 时产生矛盾。删除后：
- executor@ORCHESTRATOR：depth prompt 说 "MAY spawn"，body 不矛盾 → 一致
- executor@LEAF：depth prompt 说 "CANNOT spawn"，body 不矛盾 → 一致

### 7.2 不改其他四个广度角色的 body

general / researcher / reviewer / librarian 的 body 不包含 spawn 相关声明，不产生矛盾，不需要改。

### 7.3 不改系统 prompt 构建逻辑

`build_subagent_system_prompt` 的逻辑是正确的：
- depth role 决定 `## Your Role` 的措辞
- `can_spawn` 控制 spawn 相关段的注入
- body 无条件注入（合理——广度角色的操作指南应该总是可见）

问题只在 body 内容，不在注入逻辑。

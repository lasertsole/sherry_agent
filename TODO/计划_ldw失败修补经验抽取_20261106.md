# 计划：ldw workflow 失败修补经验抽取

> **背景**：ldw workflow 重放已验证 plan 时，任意数量 step 失败（单 step PTC 失败降级 ReAct，或多 step 失败降级 TaskFlow）后，要抽「修补经验」——PTC 为什么失败、ReAct/TaskFlow 怎么修的、是否找到新成功路径。更新 plan knowledge + 重编译 PTC 脚本/workflow，让未来 replay 更鲁棒。
>
> **前置**：`计划_ldw重放已验证plan_20261106.md`（ldw 重放 + 三级降级）+ `计划_handoff成功路径与失败分支修正_20261106.md`（success_steps + failed_branches）。
>
> **日期**：2026-11-06

---

## 一、为什么要抽修补经验

ldw workflow 是「已验证成功路径」的重放。但当前任务变体可能和原 plan 不同（参数/环境/输入差异），导致：
- PTC 脚本不适用（工具调用参数对不上、环境变了）→ leaf 降级 ReAct。
- 多 step 失败 → 降级 TaskFlow（retry/judge 重新执行）。

这些「失败 + 修补」是宝贵经验：
- **PTC 失败原因**：原 success_steps 对新变体哪里不适用（输入漂移、约束变化）。
- **ReAct 修补路径**：ReAct 实际怎么解决的（可能是一条和原 success_steps 不同的新路径）。
- **TaskFlow 修补结果**：降级 TaskFlow 后，retry/judge 重新跑出的成功路径。

不抽这些 → 下次同变体 replay 还会失败（journal 未命中或 PTC 再失效）。抽了 → 更新 knowledge → 重编译 PTC 脚本/workflow → 下次同变体 replay 成功（journal 命中修补后的结果，或 PTC 脚本已适配）。

**反馈环**：replay → 失败 → 修补 → 抽修补经验 → 更新 knowledge → 重编译 → 下次 replay 更鲁棒。

---

## 二、修补经验的三种来源

| 来源 | 触发 | 修补内容 | 数据载体 |
|---|---|---|---|
| **A. 单 step PTC 失败 → ReAct 成功** | leaf 内 PTC 脚本失败，ReAct 接管成功 | ReAct 的实际执行路径（可能 ≠ 原 success_steps） | leaf 子 agent 的 handoff（success_steps/failed_branches）+ PTC 失败原因 |
| **B. 单 step PTC+ReAct 都失败 → dag 跳过** | step 完全失败，下游 skip | 失败原因 + 哪些下游受影响 | 失败 step 的 handoff（failed_branches）+ dag partial 结果 |
| **C. 多 step 失败 → 降级 TaskFlow** | L3 降级，TaskFlow 重新执行 | TaskFlow 的 retry/judge 修补路径 | TaskFlow 子 agent 的 handoff（完整 4+1 字段）+ skill review |

---

## 三、抽取流程

### A. 单 step PTC 失败 → ReAct 成功（leaf 内修补）

leaf 子 agent 在 ReAct 成功后，handoff 的 `success_steps` 记录的是 **ReAct 实际走的路径**（不是原 PTC 脚本）。`failed_branches` 应记一条「原 PTC 脚本路径失败 + 原因」。

```python
# leaf 完成后（ReAct 成功），其 handoff:
{
  "success_steps": [<ReAct 实际走的步骤>],  # 可能和原 PTC 脚本不同
  "failed_branches": [{"branch": "原 PTC 脚本路径", "failure_reason": "参数 X 对新变体不适用"}],
  ...
}
```

**抽取**：ldw replay 结束后，sherry 收集每个 leaf 的 handoff（ldw leaf 是子 agent，有 handoff）。对比原 plan knowledge 和 leaf handoff：
- success_steps 变了（ReAct 路径 ≠ 原 PTC 脚本）→ 标记为「修补后成功路径」。
- failed_branches 新增（PTC 失败原因）→ 标记为「PTC 不适用场景」。

### B. 单 step 完全失败（dag 跳过）

step 的 leaf handoff `success_steps` 为空（任务失败），`failed_branches` 记失败原因。下游 step 被 skip（无 handoff）。

**抽取**：记录失败 step 的 failed_branches + 受影响的下游 step 列表。这些是「该 step 在此变体下不可行」的经验。

### C. 多 step 失败 → 降级 TaskFlow

TaskFlow 重新执行 plan（retry/judge/schema gate）。TaskFlow 的子 agent 产出完整 handoff（4+1 字段）。TaskFlow 完成后，**走标准 skill review**（`_run_skill_review`）——但这是「修补版抽取」：

```python
# TaskFlow 降级完成后
async def repair_extraction(session_id, plan_key, original_knowledge):
    """降级 TaskFlow 完成后，抽修补经验，合并进原 knowledge。"""
    # 标准 skill review（读 TaskFlow 子 agent handoff + assemble + aggregate）
    repaired = await _run_skill_review(session_id)  # 产出修补后的 success_steps/failed_branches/hard_constraints
    
    # 合并：修补版 和 原 knowledge 的差异
    merged = merge_knowledge(original_knowledge, repaired)
    
    # 更新 knowledge 存储
    knowledge_store.update_plan(plan_key, merged)
    
    # 重编译 PTC 脚本 + ldw workflow（用修补后 knowledge）
    recompile_ptc_scripts(plan_key, merged)
    recompile_ldw_workflow(plan_key, merged)
    
    return merged
```

## 四、knowledge 合并规则（原 + 修补）

`merge_knowledge(original, repaired)`：

| 字段 | 合并规则 |
|---|---|
| `success_steps`（每 step） | **替换**：若修补版（ReAct/TaskFlow）的 success_steps 和原不同 → 用修补版替换（修补版是对当前变体实际验证的路径）。若相同 → 保留原。记录「该 step 有变体专属路径」标记。 |
| `failed_branches` | **并集**：原 failed_branches + 修补版新增（PTC 失败原因 + ReAct/TaskFlow 发现的新失败分支）。去重。 |
| `hard_constraints` | **并集**：原 + 修补版新发现的约束。去重。 |
| `locked_decisions` | **并集**：原 + 修补版新锁定的决策。 |
| `discovered_hard_constraints` | 同 hard_constraints |

**success_steps 替换而非并集的理由**：success_steps 是「最终成功路径」，一个 step 一条。修补版的 success_steps 是对当前变体实际跑通的路径——比原版（可能对当前变体不适用）更准确。替换 = 用更准确的覆盖。但若想保留「原版适用场景」信息，可记一条 failed_branch「原 success_steps 对变体 X 不适用」。

**变体感知（进阶）**：若要区分「不同变体的不同成功路径」，success_steps 可带变体标签（variant fingerprint：输入特征哈希）。原版 success_steps 适用变体 A，修补版适用变体 B。replay 时按当前变体查匹配的 success_steps 编译 PTC 脚本。MVP 先不区分变体（直接替换），进阶再按变体分叉。

## 五、重编译（修补后 knowledge → 更新 PTC 脚本 + ldw workflow）

修补经验合并进 knowledge 后，重编译：

| 产物 | 重编译 | 用修补后 knowledge 的什么 |
|---|---|---|
| PTC 脚本模板（每 step） | `compile_step_ptc_script(step, ...)` | 修补后的 success_steps（ReAct/TaskFlow 实际路径）→ 更新脚本 |
| ldw workflow（orchestrate） | `compile_plan_to_workflow(...)` | steps + dag 依赖（不变，除非 step 结构变了）+ 修补后的 hard_constraints（guard 断言更新） |
| journal | 不重编译（journal 是运行时缓存，按 key 自动命中/未命中） | — |

重编译后，**同变体下次 replay**：
- journal 命中修补后结果（若 TaskFlow 降级写回了 journal）→ 零调用。
- 或 PTC 脚本已用修补后 success_steps 重编译 → 适配新变体 → PTC 成功（不再降级 ReAct）。

## 六、抽取触发时机

| 场景 | 触发抽取 | 抽取类型 |
|---|---|---|
| workflow 完整成功（全 step journal 命中或 PTC 成功） | **不抽取**（已验证，无需修补） | — |
| 单 step PTC 失败 → ReAct 成功（step 成功） | replay 结束后抽 | A（leaf handoff 对比） |
| 单 step 完全失败（dag 跳过，接受 partial） | replay 结束后抽 | B（失败 step failed_branches） |
| 多 step 失败 → 降级 TaskFlow | TaskFlow 完成后抽 | C（标准 skill review + 合并） |

**抽取入口**：`replay_with_degradation` 返回结果后，sherry 检查结果状态，按场景触发抽取：

```python
async def replay_with_degradation_and_repair(plan_key, ...):
    results = await replay_with_degradation(plan_key, ...)
    failed_steps = [sid for sid, r in results.items() if r is None]
    react_repaired = collect_leaf_handoffs_with_ptc_failure(results)  # A: ReAct 修补的 leaf
    
    if not failed_steps and not react_repaired:
        return results  # 完整成功，不抽取
    
    if degraded_to_taskflow:
        # C: TaskFlow 降级，走标准 skill review + 合并
        await repair_extraction(session_id, plan_key, original_knowledge)
    elif failed_steps:
        # B: 有完全失败的 step
        await extract_failure_experience(failed_steps, plan_key)
    elif react_repaired:
        # A: 有 ReAct 修补（PTC 失败但 ReAct 成功）
        await extract_react_repair_experience(react_repaired, plan_key)
    
    return results
```

## 七、ReAct 级联的修补经验

单 step ReAct 成功后，下游 step 可能因输入变化也 PTC 失败 → ReAct 级联。级联中每个 ReAct 的 leaf handoff 都要收集：
- 每个 ReAct leaf 的 success_steps（实际走的路径）。
- 每个 PTC 失败的 failed_branches（为什么 PTC 不适用）。

级联的修补经验揭示：**原 plan 的 success_steps 对该变体整体不适用**（从一个 step 偏离后，整条链的 PTC 都失效）。这可能是「变体专属路径」的信号 → 考虑进阶的变体感知 success_steps（第四节）。

若级联中某个 step 的 ReAct 也失败 → 真失败 → 计入 L3 → 降级 TaskFlow → 走 C 抽取。

## 八、与现有计划的关系

- **不冲突**：修补抽取是 ldw replay 失败后的**增量**，不改 ldw workflow 执行/journal/降级逻辑。
- **依赖 handoff**：leaf 子 agent 的 handoff（success_steps + failed_branches）是修补经验的数据源——依赖 `计划_handoff成功路径与失败分支修正_20261106.md` 落地。
- **依赖 skill review**：C 场景（降级 TaskFlow）走标准 `_run_skill_review`——依赖已实现的 plan 抽取链。
- **knowledge 更新**：`knowledge_store.update_plan`（新方法，原 read-only 改为可更新）+ 重编译 PTC/workflow。

## 九、实施顺序

1. `knowledge_store.update_plan(plan_key, merged)`：knowledge 从只读改为可更新（合并原 + 修补）
2. `collect_leaf_handoffs(results)`：从 ldw replay 结果收集每个 leaf 的 handoff（ldw leaf 是子 agent，handoff 在 CompletionState）
3. `extract_react_repair_experience(react_repaired, plan_key)`：A 场景——对比原 success_steps 和 ReAct success_steps，合并进 knowledge
4. `extract_failure_experience(failed_steps, plan_key)`：B 场景——记录失败 step 的 failed_branches
5. `repair_extraction(session_id, plan_key, original_knowledge)`：C 场景——TaskFlow 降级后走标准 skill review + 合并
6. `recompile_ptc_scripts` + `recompile_ldw_workflow`：修补后 knowledge → 重编译产物
7. `replay_with_degradation_and_repair`：replay + 失败判定 + 触发抽取
8. 测试 + 端到端验证

## 十一、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| 修补经验覆盖原经验（success_steps 替换丢原路径） | 中 | 替换时把原 success_steps 记一条 failed_branch「原路径对变体 X 不适用」；进阶按变体分叉保留多版本 |
| ReAct 级联导致整条链修补（工作量大） | 中 | 级联是信号：原 plan 对该变体整体不适用 → 考虑直接 L3 降级 TaskFlow（而非逐个 ReAct 修补） |
| TaskFlow 降级抽取成本（再跑一遍 skill review） | 中 | 只在 L3 降级时触发；TaskFlow 的 handoff 已有，extraction 是机械消费 |
| knowledge 更新并发（多 replay 同时修补同 plan） | 低 | knowledge 文件覆盖写 + 原子 temp-replace；或按 plan_key 加锁 |
| 重编译后的 PTC 脚本仍不适用（修补经验不够） | 低 | 下次 replay 还会失败 → 再抽修补 → 迭代收敛；journal 兜底（同输入命中修补结果） |

# 计划：附件上传流水线（对齐 ZCode）

- 日期：2026-11-10
- 状态：**待评审**
- 来源：对齐 ZCode — ZCode 拥有分块上传流水线，`attachmentChunkMaxBytes=512KB`，带 TTL 的 preview/read/stage 缓存，以及 64MB 的暂存上传上限
- 风险等级：**中高** — 重构 client→server 上传路径；涉及 HTTP 路由、client composable 和 Dexie schema
- 依赖：无（独立的基础设施改进）

---

## 0. ZCode 行为

ZCode 的附件上传流水线：

| 常量 | 值 | 含义 |
|---|---|---|
| `attachmentMaxBytes` | 20 MB | 单个附件硬上限 |
| `attachmentChunkMaxBytes` | 512 KB | 上传分块大小 |
| `attachmentPreviewMaxBytes` | 30 MB | 预览渲染的最大字节数 |
| `attachmentPreviewMaxChunks` | 60（30MB / 512KB） | 预览最大分块数 |
| `attachmentReadCacheMaxBytes` | 30 MB | 读取缓存大小 |
| `attachmentReadCacheTtlMs` | 30 s | 读取缓存 TTL |
| `attachmentUploadMaxStagedBytes` | 64 MB | 暂存（待上传）最大字节数 |

流水线：
1. 文件被切成 ≤512KB 的分块
2. 分块被暂存（总计上限 64MB）并顺序或并行上传
3. 读取缓存（30MB，30s TTL）避免重复读取/上传相同内容
4. 预览渲染有界（最大 30MB）
5. 完成握手将分块组装为最终文件

## 1. Sherry 当前状态

**单次整包 POST，无分块、无缓存、无去重。**

### 客户端
- `composables/bridge/upload.ts::uploadBase64ToUrls()` — 顺序遍历每个 base64 字符串，解码为 `Uint8Array`，通过 `fetchApiRaw()` 以整包 body POST 原始字节。无分块、无 FormData、无重试、无进度。
- `composables/bridge/agent-socket-upload.ts` — 编排：上传 base64 → 获取 URL → 将 WS frame 改写为使用 `image_path_list` URL 而非 `image_base64_list`。

### 服务端
| 路由 | 限制 | 存储 |
|---|---|---|
| `POST /images/upload` | 25 MiB | `SRC_DIR/images/<uuid><ext>` |
| `POST /audio/upload` | 100 MiB | `SRC_DIR/audio/<uuid><ext>` |
| `POST /video/upload` | 500 MiB | `SRC_DIR/video/<uuid><ext>` |

- 整包 body POST；无 `Content-Range`、无分块组装、无上传会话。
- `uuid4().hex` 文件名 — 无内容哈希寻址（无去重）。
- 上传的 media 落入共享的顶层目录，**不**按 session 隔离。

### 无缓存
- Dexie 没有 uploads/attachments 表。每次重发都重新上传。

## 2. 设计

### 2.1 分块上传协议

**新增端点：**
```
POST /upload/chunk?session_id=<sid>&upload_id=<uid>&chunk_index=<i>&total_chunks=<n>&filename=<name>&content_type=<mime>
    Body: raw chunk bytes (≤512KB)
    Response: { ok: true, chunk_index: i, received: <bytes> }

POST /upload/complete?session_id=<sid>&upload_id=<uid>
    Response: { ok: true, url: "<http_url>", filename: "<name>", sha256: "<hash>" }
```

**服务端分块组装**（`server/trigger/http/upload_chunked.py`）：
1. 每个分块写入 `TEMP_DIR/<upload_id>/<chunk_index>`
2. 在 `complete` 时：按序拼接分块，计算 SHA256，写入最终位置（内容寻址 — 见计划 #7），清理分块目录
3. 若 SHA256 与已存在文件匹配 → 返回已有 URL（去重）

### 2.2 客户端分块上传器

新模块：`client/app/composables/bridge/upload-chunked.ts`

```typescript
const CHUNK_SIZE = 512 * 1024  // 512 KB
const MAX_STAGED_BYTES = 64 * 1024 * 1024  // 64 MB

async function uploadChunked(
  bytes: Uint8Array,
  kind: 'image' | 'audio' | 'video',
  session_id: string,
  contentType: string,
  onProgress?: (sent: number, total: number) => void,
): Promise<string> {
  const uploadId = crypto.randomUUID()
  const totalChunks = Math.ceil(bytes.length / CHUNK_SIZE)
  for (let i = 0; i < totalChunks; i++) {
    const chunk = bytes.subarray(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE)
    await fetchApiRaw({ url: `/upload/chunk?...&chunk_index=${i}&total_chunks=${totalChunks}`, body: chunk, contentType })
    onProgress?.((i + 1) * CHUNK_SIZE, bytes.length)
  }
  const result = await fetchApiJson(`/upload/complete?...&upload_id=${uploadId}`)
  return result.url
}
```

### 2.3 读取/上传缓存（Dexie）

新增 Dexie 表（schema v7）：
```typescript
uploadCache: '++id, sha256, url, session_id, created_at'
```

```typescript
async function uploadWithCache(bytes: Uint8Array, kind: string, session_id: string): Promise<string> {
  const hash = await crypto.subtle.digest('SHA-256', bytes)
  const hashHex = Array.from(new Uint8Array(hash)).map(b => b.toString(16).padStart(2, '0')).join('')
  // Check cache (30s TTL)
  const cached = await db.uploadCache.where('sha256').equals(hashHex).first()
  if (cached && Date.now() - cached.created_at < 30_000) {
    return cached.url  // dedup — same bytes → same URL
  }
  // Upload
  const url = await uploadChunked(bytes, kind, session_id, ...)
  await db.uploadCache.put({ sha256: hashHex, url, session_id, created_at: Date.now() })
  return url
}
```

### 2.4 进度上报

分块上传器按分块调用 `onProgress(sent, total)`。composer 对大于 1MB 的上传显示进度条。

### 2.5 回退到整包 POST

对于小文件（<512KB，单个分块），跳过分块协议，使用现有的 `/images/upload` 整包 POST — 单个分块本身就是一次 POST，但分块路径会多一次 `complete` 往返，对单分块上传是不必要的。

### 2.6 迁移

`upload.ts` 中现有的 `uploadBase64ToUrls()` 保留作为回退路径。新的 `uploadWithCache()` 是主路径。`agent-socket-upload.ts` 改为调用 `uploadWithCache()` 而非 `uploadBase64ToUrls()`。

## 5. 备注

- ZCode 的流水线面向所有附件（包括非 media 文档）。Sherry 的仅限 media（图片/音频/视频）。扩展到通用文件附件是独立的未来计划。
- 上传缓存中的 SHA256 去重与计划 #7（Artifact 持久化）对齐 — 两者都使用内容寻址存储。上传缓存在客户端（Dexie），artifact store 在服务端。二者互补：上传缓存避免重复上传相同字节，artifact store 避免服务端重复存储相同字节。
- 500MB 视频限制是分块的主要驱动力 — 单次 500MB POST 在不稳定连接上不可靠。
- 分块上传使进度上报和中断恢复（未来增强）成为可能。

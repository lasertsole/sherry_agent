## 0. ZCode 行为

### 0.1 上传协议

ZCode 用 WebSocket RPC（v4 gateway），分块上传是 `v4/attachment/*` 系列方法：

```
v4/attachment/begin    → 开始上传会话（返回 uploadId + nextChunkIndex=0）
v4/attachment/chunk    → 发一个分块（必须按 index 顺序）
v4/attachment/commit   → 完成（校验 SHA256 + 组装 + 去重）
v4/attachment/abort    → 取消
v4/attachment/read     → 读回
```

### 0.2 单文件内顺序

ZCode 服务端**强制分块顺序到达**：

```js
if (t.chunkIndex < n.chunks.length) throw "chunkConflict";  // 已收过 → 冲突
if (t.chunkIndex > n.chunks.length) throw "chunkGap";        // 跳过 → 间隙
// 只有 chunkIndex === n.chunks.length 才接受（追加到末尾）
```

单文件内不能并行——每个分块必须等前一个到达才能发。

### 0.3 多文件并行

```js
if (this.staged.size >= nn.attachmentUploadMaxConcurrent)  // 16
    throw "tooManyUploads";
```

最多 16 个上传会话同时进行——用户同时上传多张图，每个文件各占一个"车道"，文件之间并行。

### 0.4 常量

| 常量 | 值 | 含义 |
|---|---|---|
| `attachmentMaxBytes` | 20 MB | 单个附件硬上限 |
| `attachmentChunkMaxBytes` | 512 KB | 上传分块大小 |
| `attachmentUploadMaxChunks` | 64 | 单文件最多 64 个分块（即最大 32MB） |
| `attachmentUploadMaxConcurrent` | 16 | 最多 16 个并发上传会话 |
| `attachmentUploadMaxStagedBytes` | 64 MB | 所有暂存分块的总字节上限 |
| `attachmentReadCacheMaxBytes` | 30 MB | 读取缓存大小 |
| `attachmentReadCacheTtlMs` | 30 s | 读取缓存 TTL |

### 0.5 为什么是顺序而非并行

上传的瓶颈是**带宽**，不是连接数。一个 500MB 视频在 10Mbps 上传带宽下需要 ~400 秒，不管开 1 个连接还是 6 个——总带宽固定。并行连接只在高延迟/丢包网络下有边际收益（多 TCP 窗口），但换来的是协议、进度、续传、错误处理的**大幅简化**。

Sherry 用 HTTP POST（每个分块是独立请求），技术上可以做单文件内并行。但对齐 ZCode 的顺序模型更简单、更可靠——且实际速度差异在带宽瓶颈下可忽略。

## 1. Sherry 当前状态

**单次整包 POST，无分块、无缓存、无去重、无并行。**

### 客户端
- `composables/bridge/upload.ts::uploadBase64ToUrls()` — 顺序遍历每个 base64 字符串，解码为 `Uint8Array`，通过 `fetchApiRaw()` 以整包 body POST 原始字节。无分块、无 FormData、无重试、无进度。
- `composables/bridge/agent-socket-upload.ts` — 编排：上传 base64 → 获取 URL → 将 WS frame 改写为使用 `image_path_list` URL 而非 `image_base64_list`。

### 服务端
| 路由 | 限制 | 存储 |
|---|---|---|
| `POST /images/upload` | 25 MiB | `SRC_DIR/images/<uuid><ext>` |
| `POST /audio/upload` | 100 MiB | `SRC_DIR/audio/<uuid><ext>` |
| `POST /video/upload` | 500 MiB | `SRC_DIR/video/<uuid><ext>` |

- 整包 body POST；无 `Content-Range`、无分块组装、无上传会话。
- `uuid4().hex` 文件名 — 无内容哈希寻址（无去重）。
- 上传的 media 落入共享的顶层目录，不按 session 隔离。

### 无缓存
- Dexie 没有 uploads/attachments 表。每次重发都重新上传。

## 2. 设计

### 2.1 传输协议——HTTP POST（非 WS RPC）

ZCode 用 WS RPC，Sherry 用 HTTP POST。原因：
- Sherry 的 WS 只管聊天流（服务端→客户端推送），不管文件传输
- Sherry 已有 HTTP 基础设施（Robyn HTTP 路由），上传走 HTTP 和现有架构一致
- HTTP POST 调试友好（curl 可测），浏览器/代理兼容性好
- WS RPC 需要自定义协议层（begin/chunk/commit/abort 帧），HTTP POST 用标准路由即可

**端点：**
```
POST /upload/begin?session_id=<sid>&filename=<name>&content_type=<mime>&total_chunks=<n>&total_bytes=<size>
    Response: { ok: true, upload_id: "<uid>", next_chunk_index: 0 }

POST /upload/chunk?upload_id=<uid>&chunk_index=<i>
    Body: raw chunk bytes (≤512KB)
    Response: { ok: true, next_chunk_index: <i+1> }

POST /upload/complete?upload_id=<uid>
    Response: { ok: true, url: "<http_url>", filename: "<name>", sha256: "<hash>" }

POST /upload/abort?upload_id=<uid>
    Response: { ok: true }

GET /upload/status?upload_id=<uid>
    Response: { ok: true, received_chunks: <count>, total_chunks: <n> }
```

**服务端**（`server/trigger/http/upload_chunked.py`）：
1. `begin`：创建 `TEMP_DIR/<upload_id>/` 目录，记录 metadata（filename、content_type、total_chunks、total_bytes），返回 `upload_id` + `next_chunk_index=0`
2. `chunk`：校验 `chunk_index === 已收数量`（对齐 ZCode 顺序约束），追加到 `TEMP_DIR/<upload_id>/` 目录，返回 `next_chunk_index`
3. `complete`：校验所有分块到齐 → 按序拼接 → 计算 SHA256 → 写入最终位置（内容寻址去重，见 artifact 存储计划）→ 清理分块目录 → 返回 URL
4. `abort`：删除 `TEMP_DIR/<upload_id>/` 目录
5. `status`：返回已收分块数量（用于断点续传）

### 2.2 单文件：顺序发送分块

```typescript
async function uploadChunked(
  bytes: Uint8Array,
  kind: 'image' | 'audio' | 'video',
  session_id: string,
  contentType: string,
  onProgress?: (sent: number, total: number) => void,
): Promise<string> {
  const totalChunks = Math.ceil(bytes.length / CHUNK_SIZE)
  // 1. begin
  const { upload_id } = await fetchApiJson(`/upload/begin?...&total_chunks=${totalChunks}&total_bytes=${bytes.length}`)

  // 2. 顺序发送分块（对齐 ZCode：每个分块等前一个完成）
  for (let i = 0; i < totalChunks; i++) {
    const chunk = bytes.subarray(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE)
    await fetchApiRaw({ url: `/upload/chunk?upload_id=${upload_id}&chunk_index=${i}`, body: chunk, contentType })
    onProgress?.(i + 1, totalChunks)
  }

  // 3. complete
  const result = await fetchApiJson(`/upload/complete?upload_id=${upload_id}`)
  return result.url
}
```

**为什么顺序：** 对齐 ZCode。上传瓶颈是带宽不是连接数——顺序和并行在带宽饱和时速度差异可忽略。顺序换来的是：简单进度（连续计数）、简单续传（从第 N+1 个继续）、简单错误处理（重发当前分块）、简单服务端（追加而非随机位置写）。

### 2.3 多文件：并行发送

```typescript
const MAX_CONCURRENT_FILES = 8  // 对齐 ZCode attachmentUploadMaxConcurrent（ZCode=16，Sherry 保守取 8）

async function uploadMultipleFiles(
  files: { bytes: Uint8Array; kind: string; contentType: string }[],
  session_id: string,
  onFileProgress?: (fileIndex: number, sent: number, total: number) => void,
): Promise<string[]> {
  // 每个文件占一个"车道"，文件之间并行
  // 单文件内顺序发分块（uploadChunked 的 for 循环）
  const results: string[] = new Array(files.length)
  await runPool(files, MAX_CONCURRENT_FILES, async (file, fileIndex) => {
    results[fileIndex] = await uploadChunked(
      file.bytes, file.kind, session_id, file.contentType,
      (sent, total) => onFileProgress?.(fileIndex, sent, total),
    )
  })
  return results
}
```

**`runPool` 并发池：**
```typescript
async function runPool<T>(
  items: T[],
  concurrency: number,
  fn: (item: T, index: number) => Promise<void>,
): Promise<void> {
  let cursor = 0
  const workers = Array.from({ length: Math.min(concurrency, items.length) }, async () => {
    while (cursor < items.length) {
      const index = cursor++
      await fn(items[index], index)
    }
  })
  await Promise.all(workers)
}
```

**场景：** 用户拖入 5 张图 → 5 个 `uploadChunked()` 并行跑（最多 8 并发），每个内部顺序发分块。浏览器 6 连接限制自动让超出部分排队。

### 2.4 读取/上传缓存（Dexie）

新增 Dexie 表（schema v7）：
```typescript
uploadCache: '++id, sha256, url, session_id, created_at'
```

```typescript
async function uploadWithCache(bytes: Uint8Array, kind: string, session_id: string): Promise<string> {
  const hash = await crypto.subtle.digest('SHA-256', bytes)
  const hashHex = Array.from(new Uint8Array(hash)).map(b => b.toString(16).padStart(2, '0')).join('')
  // 检查缓存（30s TTL）
  const cached = await db.uploadCache.where('sha256').equals(hashHex).first()
  if (cached && Date.now() - cached.created_at < 30_000) {
    return cached.url  // 去重 — 相同字节 → 相同 URL，不重传
  }
  // 上传
  const url = await uploadChunked(bytes, kind, session_id, ...)
  await db.uploadCache.put({ sha256: hashHex, url, session_id, created_at: Date.now() })
  return url
}
```

多文件并行 + 缓存：
```typescript
async function uploadMultipleWithCache(
  files: { bytes: Uint8Array; kind: string; contentType: string }[],
  session_id: string,
): Promise<string[]> {
  return runPool(files, MAX_CONCURRENT_FILES, async (file) => {
    return uploadWithCache(file.bytes, file.kind, session_id)
  })
}
```

### 2.6 断点续传

顺序模型下断点续传简单——服务端记录已收分块数量，客户端从下一个继续：

```typescript
async function resumeUpload(uploadId: string, bytes: Uint8Array, kind: string, ...): Promise<string> {
  // 1. 查服务端已收几个
  const status = await fetchApiJson(`/upload/status?upload_id=${uploadId}`)
  // status.received_chunks = N（已收 N 个，顺序排列 0..N-1）

  // 2. 从第 N 个继续顺序发送
  const totalChunks = Math.ceil(bytes.length / CHUNK_SIZE)
  for (let i = status.received_chunks; i < totalChunks; i++) {
    const chunk = bytes.subarray(i * CHUNK_SIZE, (i + 1) * CHUNK_SIZE)
    await fetchApiRaw({ url: `/upload/chunk?upload_id=${uploadId}&chunk_index=${i}`, body: chunk, contentType })
    onProgress?.(i + 1, totalChunks)
  }

  // 3. complete
  return (await fetchApiJson(`/upload/complete?upload_id=${uploadId}`)).url
}
```

客户端持久化 uploadId（Dexie）：
```typescript
// uploadCache 表增加上传状态字段
uploadCache: '++id, sha256, url, session_id, created_at, upload_id, file_name, total_chunks, status'
// status: 'uploading' | 'completed' | 'failed'
```

页面刷新/崩溃后：查 Dexie 里 `status='uploading'` 的行 → 用 uploadId 调 `/upload/status` → 从 `received_chunks` 继续。

### 2.7 小文件回退

对于小文件（<512KB，单个分块），跳过分块协议，使用现有的 `/images/upload` 整包 POST — 分块路径会多一次 `begin` + `complete` 往返，对单分块上传不必要。

### 2.8 迁移

`upload.ts` 中现有的 `uploadBase64ToUrls()` 保留作为回退路径。`agent-socket-upload.ts` 改为：

```typescript
// 之前：顺序上传每个文件
const urls = await uploadBase64ToUrls('image', base64List)

// 之后：多文件并行，单文件顺序分块
const urls = await uploadMultipleWithCache(
  base64List.map(b64 => ({ bytes: decodeBase64(b64), kind: 'image', contentType: 'image/png' })),
  session_id,
)
```

`audio` 和 `video` 同理。

## 3. 与 ZCode 的对比

| | ZCode | Sherry |
|---|---|---|
| 传输协议 | WS RPC（`v4/attachment/*`） | HTTP POST（`/upload/begin` / `chunk` / `complete`） |
| 单文件内 | 顺序（服务端强制 `chunkIndex === length`） | 顺序（服务端同样校验） |
| 多文件 | 并行（≤16 并发会话） | 并行（≤8，`runPool` 并发池） |
| 分块大小 | 512KB | 512KB |
| 分块上限 | 64 个/文件（32MB） | 不设上限（Sherry 支持视频 500MB = ~1000 分块） |
| 去重 | SHA256 内容寻址 | SHA256 + Dexie 客户端缓存 + 服务端 `complete` 时去重 |
| 断点续传 | `attachmentRead` RPC | `GET /upload/status` + Dexie 持久化 uploadId |
| 缓存 | 读取缓存 30MB / 30s TTL | Dexie uploadCache 30s TTL |
| 进度 | `nextChunkIndex` 返回值 | `onProgress(sent, total)` 回调 |

## 6. 备注

- ZCode 的流水线面向所有附件（包括非 media 文档）。Sherry 的仅限 media（图片/音频/视频）。扩展到通用文件附件是独立的未来计划。
- 上传缓存中的 SHA256 去重与 Artifact 存储计划对齐 — 两者都使用内容寻址存储。上传缓存在客户端（Dexie），artifact store 在服务端。二者互补。
- 500MB 视频限制是分块的主要驱动力 — 单次 500MB POST 在不稳定连接上不可靠。
- Sherry 的 HTTP POST 分块上限不设 64（ZCode 的 `attachmentUploadMaxChunks`），因为 Sherry 支持视频 500MB = ~1000 个 512KB 分块。
- Sherry 的 `MAX_CONCURRENT_FILES = 8` 比 ZCode 的 16 保守——浏览器对同域名约 6 个并发连接，16 个文件会大量排队，8 个更合理。

# 计划：TaskFlow step 重放——PTC 优先 + React 回退 + 部分复用

> **场景**：重放稳定 plan 的 TaskFlow。每个 step = 一个 subagent。step 的 success_steps 已被 plan 抽取后的 skill review 编译成 PTC 脚本，放在 owning skill 的 `scripts/` 下：`skills/auto/<skill>/scripts/ptc__<plan_key>__<step_id>.py`。
>
> **目标**：step 的 subagent **系统级优先跑 PTC**（不靠 LLM 自觉选），PTC 失败再转 React，**React 复用 PTC 已完成的步骤**（不重做）。
>
> **日期**：2026-11-06

---

## 一、机制：PTC-prefill spawn

`_execute_subagent`（`core.py:1459`）在 `child_agent.ainvoke`（LLM React 循环）**之前**，系统级预跑 PTC：

```
spawn step subagent
  → 查 PTC 脚本（step → success_steps → 编译的 skills/auto/<skill>/scripts/ptc__<plan_key>__<step_id>.py）
  → 有脚本：
      → 系统级预跑 PTC（不经 LLM，直接调 PTC 执行路径）
      → PTC 成功（无异常 + 输出符合期望）→ step DONE，跳过 LLM 循环，返回 PTC 结果（零 LLM token）
      → PTC 失败（异常/断言失败/输出不符）→ 收集部分结果（步骤 1..N-1 done, 步骤 N failed）→ 转React（见二）
  → 无脚本 → 正常 React（当前行为）
```

**「督促」是系统级硬执行，不是 prompt 软劝**：PTC 在 LLM 循环之前跑，LLM 根本不参与「选择」。PTC 成功则 LLM 循环跳过；PTC 失败才启动 LLM。LLM 无法「忘记」用 PTC——系统替它跑了。

## 二、React 回退 + 部分复用

PTC 失败时，启动子 agent LLM React 循环，初始消息注入 **PTC 预跑进度**：

```
[PTC Pre-run Progress]
A PTC script (skills/auto/<skill>/scripts/ptc__<plan_key>__<step_id>.py) was attempted for this task.
Completed steps (side effects already applied — DO NOT redo):
  1. <step1> (<tool1>, <params1>) → <result1>
  2. <step2> (<tool2>, <params2>) → <result2>
  3. <step3> (<tool3>, <params3>) → <result3>
Failed at step 4: <step4> (<tool4>, <params4>) → <error>

Continue from step 4 using normal tools. The completed steps' side effects
(files written, etc.) are real — do not redo them. Pick up from the failure point.
```

- **复用**：React LLM 看到 1..N-1 已完成（结果 + side effects 已应用），从步骤 N 继续，不重做。
- **side effects 真实**：PTC 的工具调用走真实 RPC 桥（write_file 真写文件等），所以 1..N-1 的 side effects 已落盘。React 继续时这些状态在。
- **不重做保障**：初始消息明确「DO NOT redo completed steps」+ 列出已完成的结果。LLM 据此跳过。

### 阻断缺口 4:React 进度注入机制

PTC 进度从 `run_ptc` 返回的 `calls_log` 流到 React 初始消息,复用 `build_subagent_initial_user_message` 的**现有 `context` 参数**（那个参数从未被填充,见主计划现状分析——正好用上）:

```python
# _execute_subagent PTC 失败分支
progress_text = _render_ptc_progress(ptc_result["calls_log"])
# progress_text = "[PTC Pre-run Progress]\nCompleted (DO NOT redo):\n  1. ... \nFailed at step N: ..."
result = await child_agent.ainvoke(...)  # 正常 React
# 但初始消息要带 progress_text——通过 context 参数传入
```

- `_execute_subagent` 把 `progress_text` 作为 `context` 传给 `_assemble_child_prompts` → `build_subagent_initial_user_message(context=progress_text)`
- 初始消息渲染到现有 `[Subagent Additional Context]` 段（`initial_message.py:4-25` 的 `{context}` 占位）——**不需新渲染函数**,复用现有格式
- `_render_ptc_progress(calls_log)`:从 `calls_log` 提取 `ok=True` 前缀（completed）+ 首个 `ok=False`（failed）,渲染成上面的 `[PTC Pre-run Progress]` 文本

## 三、PTC 预跑的执行路径（探查确认）

PTC 系统级入口已存在:`run_ptc(code, tools_map, session_id, config, *, cwd=None)`(`agent/tools/ptc/runner.py:237`)是纯函数,不经 LLM。`ExecuteCodeTool._run`(`tool.py:99`)只是对它的 LangChain 包装。预跑直调 `run_ptc`,`code` 取脚本文件内容。

```python
# spawn/core.py _execute_subagent 预跑分支
from agent.tools.ptc.runner import run_ptc
script_code = skill_view_read(
    name=owning_skill, file_path=f"scripts/ptc__{plan_key}__{step_id}.py"
)
ptc_result = run_ptc(
    code=script_code,
    tools_map=build_ptc_tools_map(session_id, cwd),  # 复用 build_ptc_tool 的 tools_map 构造
    session_id=session_id,
    config=PTC,  # config/features/agent_side/ptc.py
    cwd=step_cwd,
)
# ptc_result: {status, output, error, exit_code, tool_calls_made, calls_log(NEW)}
```

- **复用** `run_ptc` 的 RPC 桥（`PtcRpcServer` localhost TCP + JSON,`rpc_server.py:55`）、子进程（`subprocess.Popen`,`runner.py:306`）、`sherry_tools` bridge module（现场生成,`stub_generator.py:157`）、预算（50 次,`rpc_server.py:220`）、超时（120s,`runner.py:320`）、白名单（`ptc.py:35-42`）。全部不变量直调路径生效。
- **绕过 EXECUTOR gate**:系统级 `run_ptc` 不经 `core.py:1904` 的 `if functional_role in PTC_ROLES` gate——任意角色 step 都能预跑（见七）。
- **hard_constraints guard**:脚本里的 `assert` 失败算 PTC 失败（异常步骤进 failed_step）。assert 由 plan 抽取 LLM 生成（非机械注入,见八）。

### 阻断缺口 1:per-step 结果捕获（现有不支持,必须加）

探查确认:`PtcRpcServer` 只计 `calls_made`（`rpc_server.py:88`），**不保留 `{tool, args, result}` 列表**。`run_ptc` 返回只有 `{status, output, error, exit_code, tool_calls_made}`（`runner.py:218-234`）。要拿「步骤 1..N-1 done + 步骤 N failed」必须新加:

| 文件 | 位置 | 改动 |
|---|---|---|
| `agent/tools/ptc/rpc_server.py` | `PtcRpcServer.__init__`（`:55` 附近） | 加 `self._calls_log: list[dict] = []` |
| `rpc_server.py` | `_dispatch`（`:208`）/ `_invoke`（`:227`） | 成功:`self._calls_log.append({"tool": name, "args": args, "result": result, "ok": True})`;失败:`append({"tool": name, "args": args, "error": str(err), "ok": False})` |
| `agent/tools/ptc/runner.py` | `_result`（`:218-234`） | 返回加 `"calls_log": server._calls_log` |

`PtcResult`（预跑消费）从 `calls_log` 提取:
- `completed_steps = [c for c in calls_log if c["ok"]]` 的前缀（失败前的连续成功）
- `failed_step = first c where not c["ok"]`（首个失败）
- `success = (no exception) and output non-empty and all(c["ok"] for c in calls_log)`

## 四、脚本查找：step → PTC 脚本（命名约定，免 mapping JSON）

plan 抽取后的 skill review 编译 success_steps → 脚本。**命名约定**（无需 mapping JSON，命名即映射；脚本直接归属 skill，减少第二套关联维护）:

```
skills/auto/<skill>/scripts/ptc__<plan_key>__<step_id>.py
```

- plan 抽取后的 skill review 写：`skill_manage(action="write_file", file_path=f"scripts/ptc__{plan_key}__{step_id}.py", file_content=<compiled_script>)`
- **目标 skill 必须先存在**：`skill_manage(write_file)` 要求 skill 已创建/已定位；顺序是先 create/patch owning skill，再写脚本。若本次 nudge 是 judge 认可的 no-op，仍需选定一个 owning skill 才有地方放脚本；没有 owning skill 就不编译 PTC，只走 React。
- **脚本必须放 `scripts/` 顶层，不能放 `scripts/ptc/...`**：`skill_view` 的 `linked_files["scripts"]` 用 `scripts/*.py` 扫描，嵌套目录里的脚本可写但不会展示。
- 重放时 step 查找：`skill_view(name=<skill>, file_path=f"scripts/ptc__{plan_key}__{step_id}.py")` 读内容 → `run_ptc(code=content, ...)`
- 未找到（skill_view 返回不存在 / step 无 success_steps / owning skill 已被 archive/delete）→ 无 PTC，正常 React。
- `plan_key` 来自 `resolve_plan_identity`，`step_id` 来自 TaskFlow step；文件名是唯一映射，不维护 mapping 表。
- **脚本随 skill 生命周期走**：skill rename 时脚本随目录移动；skill archive/delete 时脚本一起消失。PTC 查找必须 fail-open，脚本丢失只降级 React，不阻塞 step。

查找链路：`step_id + plan_key → skill_view(scripts/ptc__<plan_key>__<step_id>.py) → run_ptc(code)`。两步，无中间 mapping 表。

## 五、PTC 成功判定 + 伪造子 agent 结果

### 成功判定

PTC 预跑「成功」= 跳过 LLM 的条件:
- **无异常**:脚本跑完不抛异常（含 assert 全过 + 所有 calls_log ok=True）
- **stdout 非空**:最终 `print(...)` 输出非空

MVP:**无异常 + stdout 非空即成功**（信任脚本 + hard_constraints assert 兜底）。不校验输出 schema（后续增强）。

### 阻断缺口 2:PTC 成功 → 伪造子 agent 结果（否则 complete_run 断）

PTC 成功跳过 LLM,但 `_execute_subagent` 后续 `complete_run` 要 `result_text` + `handoff`。必须伪造等价返回:

```python
# _execute_subagent PTC 成功分支
from langchain_core.messages import AIMessage
fake_result = {"messages": [AIMessage(content=ptc_result["output"])]}
# 跳过 child_agent.ainvoke，直接用 fake_result 作 agent_result
result_text = ptc_result["output"]   # 脚本 stdout 作 result_text
handoff = None                        # 无 LLM 填 handoff
# 传给 complete_run（result_text + handoff=None）
```

- `result_text = ptc_output`（脚本 stdout）——父 agent / plan 抽取 LLM 读这个
- `handoff = None`——无 LLM 填 handoff。`_read_subagent_runs` 读 `run.completion.handoff=None` → fail-open 回退 result_text（原行为,不破坏聚合）
- 不 build child agent（见七,预跑在 build 前）——PTC 成功零 LLM token + 零 agent build 开销

## 六、触发条件：仅重放

PTC-prefill 只在**重放稳定 plan**时触发：
- 首次执行 plan：step 无 success_steps（还没跑过）→ 无 PTC 脚本 → 正常 React
- 重放（plan 已抽取 + success_steps 已编译成脚本）→ PTC-prefill

判定：spawn 时查该 step 是否有编译好的 PTC 脚本。有 → prefill；无 → React。

## 七、与 TaskFlow 调度的关系 + EXECUTOR gate 绕过

TaskFlow 调度 step（dispatch subagent）时不变——仍 spawn subagent。PTC-prefill 在 **subagent 内部**（`_execute_subagent` 的入口），对 TaskFlow 调度透明：
- TaskFlow 派发 step → spawn subagent → `_execute_subagent` 预跑 PTC → 成功跳过 LLM / 失败转 React → subagent 完成 → TaskFlow resume 下游

TaskFlow 不感知 subagent 是 PTC 完成的还是 React 完成的——结果一样进 resume。

### EXECUTOR gate 绕过（重要）

系统级 `run_ptc` 绕过 `core.py:1904` 的 `if functional_role in PTC_ROLES`（EXECUTOR-only）gate——**任意角色 step 都能预跑 PTC**。但 PTC 失败转 React 后,React LLM 调 `execute_code` 仍受 EXECUTOR-only 限制:

| step 角色 | PTC 预跑 | PTC 失败后 React |
|---|---|---|
| executor | ✅ 系统级预跑 | ✅ React 可调 execute_code 重试/继续 |
| researcher/reviewer/librarian | ✅ 系统级预跑（绕过 gate） | ❌ React 不能调 execute_code,只能用各自正常工具继续 |

**非 executor step PTC 失败后**:React 用该角色的正常工具继续（不能重试 PTC）。PTC 进度（completed steps）仍注入初始消息,React 从 failed step 继续。

### 预跑时机（重要 7）：在 agent build 之前

`_execute_subagent` 里 agent 通过 `create_agent` build。预跑应尽量早——**在 `create_agent` 之前**（拿到 step_context + script 后立即 `run_ptc`）:
- PTC 成功 → 不 build agent（省 build 开销 + 零 LLM token）
- PTC 失败 → 才 build agent + 转 React（初始消息带 progress）

## 十、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| PTC 脚本 params 是 LLM 摘要（success_steps 审视重要 7）→ 预跑失败率高 | 中 | 失败转 React（本机制核心）；React 复用已完成步骤不重做；观察期统计 PTC 预跑成功率，低则不 prefill |
| side effect 冲突（PTC 写了文件，React 重试同步骤覆盖） | 中 | 初始消息「DO NOT redo completed steps」；React 从 failed step 继续，不回退 |
| PTC 成功但结果错（无异常但逻辑错） | 中 | hard_constraints assert 兜底；MVP 信任脚本；后续加输出 schema 校验 |
| 脚本查找错（step → 错脚本） | 低 | plan_key+step_id 精确文件名；task 文本模糊匹配仅作 fallback |
| owning skill 被 archive/delete 后脚本一起消失 | 中 | PTC 查找 fail-open 回退 React；含 PTC 脚本的 skill 由 curator 保护或接受降级 |
| 每个 plan 的脚本堆积在 skill `scripts/` | 中 | 文件名用 plan_key 精确键；脚本只保留可执行流程/guard，不塞完整 JSON；后续可加清理策略 |
| PTC 预跑超时阻塞 spawn | 低 | 120s 超时；超时算失败转 React |
| 首次执行无脚本 → 正常 React（无 PTC 收益） | 无 | 设计如此：PTC-prefill 只在重放触发 |

## 十一、实施顺序

1. `agent/tools/ptc/rpc_server.py` + `runner.py` — `_calls_log` 捕获 + `run_ptc` 返回暴露 calls_log（阻断缺口 1，可独立测）
2. `background_reviews.py` + `skill_manage` — plan 抽取后的 skill review 编译 success_steps → owning skill 的 `scripts/ptc__<plan_key>__<step_id>.py`（顶层；依赖 success_steps 计划 H5/H7 与 skill review 计划）
3. `spawn/core.py` `_execute_subagent` — `create_agent` 前查脚本 → `run_ptc` 预跑 → 成功跳过 build+ainvoke（伪造 AIMessage + handoff=None）/ 失败 build+ainvoke（context=progress_text）+ 新增 `_render_ptc_progress(calls_log)`
4. `spawn/initial_message.py` — 复用现有 `context` 参数渲染 progress（阻断缺口 4，不需新渲染函数）
5. 测试 + 验证
6. **观察期（重要 6）**：统计 PTC 预跑成功率（无异常 + stdout 非空）+ 人工抽检脚本质量（params 准确性、assert 有效性）。低成功率则禁 prefill（始终 React，回退成本 = PTC 预跑白跑的延迟）；达标后再信任跳过 LLM

依赖：success_steps 的 handoff/aggregate 已落地（H5 部分）；PTC 编译由 `已落地的技能评审实现` 的 skill review 承接，本计划只消费 `scripts/ptc__<plan_key>__<step_id>.py`。

## 十二、与 ldw 的关系（不冲突）

ldw（若有朝一日 fork 落地）在 **step/subagent 级**重放（整个 subagent 作 leaf，journal 零调用重放）。本机制在 **subagent 内部**（工具调用级）PTC 预跑。两者层次不同：
- ldw：step 级编排 + journal 重放整个 subagent（粗粒度）
- PTC-prefill：subagent 内部工具调用级脚本预跑（细粒度）

若 ldw 落地，step 级重放由 ldw journal 处理（零调用）；PTC-prefill 作为 subagent 内部的细粒度优化（ldw leaf 内部仍可 prefill PTC）。互补，不冲突。本计划独立于 ldw，先落地。

两类产物共用 owning skill 的 `scripts/` 顶层，用类型前缀区分：

```text
skills/auto/<owning-skill>/scripts/ptc__<plan_key>__<step_id>.py
skills/auto/<owning-skill>/scripts/ldw__<plan_key>.py
```

ldw 的元数据写在 `ldw__<plan_key>.py` 的模块常量里，不再使用 `workflow.json` sidecar。

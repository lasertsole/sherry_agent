## 1. 触发与集成点（精确到行）

### 1.1 唯一触发：consolidation 之后（后台评审协程内，与压缩并发）

**先厘清 Sherry 现有的两个不同操作**（核实自 `background_reviews.py` + `compression.py`）：

| 操作 | 名称 | 干什么 | 时机 |
|---|---|---|---|
| A | memory review（抽取/salvage） | fork 无 checkpointer 的独立 agent，从被压缩丢弃的前缀 `messages_to_summarize=current_messages[:cutoff]` 抢救 MEMORY/USER/FACTS | 压缩派发时 fire-and-forget（`compression.py:331` 派发，`:338` 才正式压缩，**并发不 await**） |
| B | consolidation（清理） | `prune_unused` aging + LLM merge/dedupe 已有条目 | A 完成后（同一后台协程 `:1357` 在 `:1349` 抽取之后），**仍与压缩并发** |

A 产新条目，B 整理已有条目，B 等 A 跑完。两者都在压缩派发的后台评审协程里（`LaneType.BACKGROUND_REVIEW`），**不是"压缩完成后"**——是"压缩派发的后台链里，与压缩并发"。

**abstraction pass 挂在 B（consolidation）末尾**：在 `run_memory_consolidation`（`:1394-1464`）的 LLM 合并 pass 完成、`memory_store.refresh_live()`（`:1456`）之后调用。位置在 B 的尾部、后台协程内，不阻塞压缩主流程。

```python
# background_reviews.py，run_memory_consolidation 末尾（行 1456 后）：
memory_store.refresh_live()
# 【新增】声明性知识提炼（consolidation 末尾附加，后台协程内，不阻塞压缩）
if MES_MEMORY.get("abstraction_pass_enabled", False) and consolidation_ran_llm:
    try:
        from context_engine.store.abstraction_pass import run_abstraction_pass
        await run_abstraction_pass(session_id, memory_store.repo)
    except Exception:
        logger.exception("abstraction pass failed (fail-open)")
entries_after = memory_store.repo.count()
```

> `consolidation_ran_llm`：`run_memory_consolidation` 当前只返回 entries_after count，需加一个 `ran_llm: bool` 标志（成本门控 <10 条 active 时 ran_llm=False，跳过提炼，避免 aging-only 时白跑）。

- **触发链**：压缩派发后台协程（memory review 抽取 → consolidation 清理 → **abstraction pass**）；session-end salvage 同链（wave1+wave2 抽取 → `:1625` consolidation → abstraction pass）；手动 `POST /memory/consolidate` 直接触发 consolidation → abstraction pass
- 三路径都经 `run_memory_consolidation`，abstraction pass 挂在其末尾，**零新增触发机制**
- fail-open：提炼失败不阻塞 consolidation / 压缩 / 会话删除
- 独立开关 `abstraction_pass_enabled`（默认 false 观察，验证后开）

### 1.2 成本（诚实口径）

- **新增 1 个 LLM 调用 / consolidation 触发**（三任务合并一次调用，不是三个）
- 非 per-turn；consolidation 本就批量触发
- r3 说的"并入同一 LLM 批次不新增调用类型"修正为：**新增一个 LLM 调用**（consolidation 的 agent-turn 用 memory 工具做去重；提炼 pass 是其后独立的 programmatic+LLM 步，因为聚类需程序化先做，不适合 agent-turn 内）

### 2.3 查询过滤改造（7 处上下文可见查询）

`memory_entry_repository.py` 中 7 处 `archived = 0` → `archived = 0 AND lifecycle = 'active'`：

`prune_unused`(:419) 加 `AND lifecycle = 'active'`：只老化 active，PROPOSED/contested 不受 aging。PROPOSED 清理：连续 N 次 pass 未转 active → retire。

## 3. 共同机制

### 3.1 lifecycle 状态机

```
proposed ──judge 通过──▶ active
proposed ──N 次未过──▶ retired
active ──新证据反证≥支持──▶ contested
contested ──复评通过──▶ active
contested ──复评未过──▶ retired
任意态 ──archived──▶ (软删除，不进任何视图)
```

### 3.2 重复不增信

置信度基于证据**多样性**（独立来源数）非数量。同一来源重复不增信。

### 3.3 TMS 简化版

源条目 archived 时：
```sql
SELECT DISTINCT source_id FROM memory_relations
WHERE target_id = ? AND relation_type = 'evidence' AND source_kind = 'memory_entry';
```
依赖抽象证据边减一；剩余 < 2 → contested/retired。单跳，不传播。

### 4.2 执行流程

```python
async def run_abstraction_pass(session_id, repo):
    # 1. 收集原料
    memory_entries = repo.active_entries_ordered("memory")     # 领域规律 + 概念抽象原料
    facts_entries   = repo.active_entries_ordered("facts")     # 领域规律原料
    user_entries    = repo.active_entries_ordered("user")      # 用户画像已有
    recent_msgs     = _recent_user_messages(session_id, n=20)  # 用户画像新原料（MessageRepository）
    clusters        = _cluster_memory(memory_entries)          # 概念抽象聚类（bge-m3 embedding 已有）

    # 2. 一次 LLM 调用，三任务
    llm_result = await _llm_synthesize(
        memory_entries, facts_entries, user_entries, recent_msgs, clusters)

    # 3. 写 PROPOSED + 证据边（事务）
    for item in llm_result.abstractions:
        repo.add_abstraction(
            target=item.target, content=item.content,
            abstraction_kind=item.abstraction_kind,
            origin_session=session_id,
            evidence_sources=item.evidence)

    # 4. judge 每条（同 LLM 或规则前置过滤 + LLM 判定）
    for entry in repo.list_by_lifecycle("proposed", target=None):
        judgment = await _judge(entry, repo)
        if judgment.passed:
            repo.promote_lifecycle(entry["id"], "active")

    return AbstractionPassResult(...)
```

## 5. LLM 调用设计

### 5.1 综合调用 prompt 结构（三任务合并）

```
你是记忆提炼器。从以下记忆条目和用户消息中提炼声明性知识。
所有产物必须标注证据来源（哪几条 entry / 哪些 turn）。

## 任务 A：用户画像（写 user 目标）
从 user 条目 + 近期用户消息归纳用户偏好/习惯/工作方式。
约束：
- 仅用于表达调整和注意力倾斜，不改变事实/授权
- 不做人格预测/道德/价值判断
- 必须跨≥2 条证据
- 标注 evidence（turn_id 或 entry_id）

## 任务 B：领域规律（写 facts 或 memory 目标）
从 memory + facts 条目跨条目综合共性规律/坑。
- 跨项目规律→facts；项目级约定→memory
- 必须跨≥2 条源 或 聚类≥3 条
- 标注 evidence（entry_id）

## 任务 C：概念抽象（写 memory 目标）
对给定聚类簇，提炼一句抽象约定（conditions/conclusions/applicability）。
- 标注 evidence（簇内 entry_id）

## 输入
[user 条目] / [memory 条目] / [facts 条目] / [近期用户消息] / [聚类簇]
## 输出 JSON
{"abstractions": [{"target","content","abstraction_kind","evidence":[["id","kind"],...]}]}
```

### 5.2 judge prompt

```
判定以下抽象条目是否可晋升 ACTIVE。四标准：
- grounded：证据边指向的源存在且未 archived
- non_trivial：跨≥2 源 或 聚类≥3 条（非单条复述）
- non_redundant：不与现有 active 条目语义重复
- calibrated：置信度合理（证据多样性，非重复数量）
输出 {"passed": bool, "reason": "..."}。
```

grounded 可程序化前置校验（查 memory_relations 证据边源是否存在），其余三项 LLM 判定。

## 6. MemoryEntryRepository 接口扩展（含 SQL）

```python
def add_abstraction(self, target, content, *, abstraction_kind,
                    origin_session=None, evidence_sources: list[tuple[str,str]]) -> dict:
    """事务：INSERT memory_entries(lifecycle='proposed', abstraction_kind) + 批量 INSERT memory_relations(evidence)"""
    with self.transaction():
        entry = self.add_entry(target, content, origin_session=origin_session)
        eid = str(entry["id"])
        now = _now_ms()
        for src_id, src_kind in evidence_sources:
            self._write(
                "INSERT OR IGNORE INTO memory_relations(source_id,target_id,relation_type,source_kind,created_at) VALUES(?,?,'evidence',?,?)",
                (eid, src_id, src_kind, now))
        # 回填 lifecycle/abstraction_kind（add_entry 不写这两列）
        self._write("UPDATE memory_entries SET lifecycle='proposed', abstraction_kind=? WHERE id=?",
                    (abstraction_kind, entry["id"]))
        return self.get_entry(entry["id"])

def list_by_lifecycle(self, lifecycle: str, target=None) -> list[dict]:
    sql = "SELECT * FROM memory_entries WHERE archived=0 AND lifecycle=?"
    params = [lifecycle]
    if target: sql += " AND target=?"; params.append(target)
    sql += " ORDER BY created_at ASC"
    return [dict(r) for r in self.db.execute(sql, params)]

def promote_lifecycle(self, entry_id: int, new_lifecycle: str) -> dict | None:
    # 校验 new_lifecycle ∈ {active, contested, retired}
    self._write("UPDATE memory_entries SET lifecycle=? WHERE id=? AND archived=0",
                (new_lifecycle, entry_id))
    return self.get_entry(entry_id)

def dependents_of(self, source_id: str) -> list[dict]:
    rows = self.db.execute(
        "SELECT DISTINCT source_id FROM memory_relations WHERE target_id=? AND relation_type='evidence'",
        (source_id,))
    return [dict(r) for r in rows]
```

`prune_unused` 加 `AND lifecycle='active'`；`list_entries` 加 `lifecycle` 可选参数。现有方法签名不改。

### TMS 挂载

## 11. 风险与 Kill criteria

| 风险 | 缓解 |
|---|---|
| schema ALTER 失败 | PRAGMA 守卫幂等（side_chats.db 范式） |
| 抽象噪声污染上下文 | PROPOSED 不进 snapshot/召回；judge；max_proposed 上限；离线评估 |
| 用户画像幻觉 | 证据绑定 + 仅 expression/attention + 不做人格预测 |
| consolidation 后 +1 LLM 调用成本 | 三任务合并一次；开关可关；非 per-turn |
| PROPOSED 泄漏进上下文 | 7 处过滤集中改 + 测试断言 |
| memory_relations 与关联层冲突 | 共用一张表，relation_type 区分 |
| agent 不写硬约束 → 领域规律原料不足 | 提示词强化；不跨边界捞 handoff |

**Kill criteria**：
- 离线评估准确率 <70% 且调 prompt 后无法达标 → 不投递 ACTIVE（PROPOSED 仍写但不进上下文）
- 用户画像 accommodation 频繁 → 缩小到 preference
- TMS 误伤 → 加人工确认再降级
- +1 LLM 调用致 consolidation 成本超预算 → 子 pass 分批（压缩只做领域规律，session-end 做全部）

## 附录 A：继承对照（借鉴同类记忆引擎机制）

### 继承（机制层面）

| 机制 | Sherry 对应 |
|---|---|
| candidate→active 生命周期 | lifecycle proposed/active/contested/retired |

| schema_discovery 聚类→候选 | 概念抽象 pass（bge-m3 替 Jaccard） |
| schema_evolution 同化/顺应/冲突 | 反证机制（assimilation/accommodation/conflict→contested） |
| "重复不增信" | 置信度基于证据多样性非数量 |

### 未继承（太重或不适用）

| 机制 | 不继承原因 |
|---|---|
| 四记忆类型（working/episodic/semantic/procedural） | Sherry 三目标 memory/user/facts |
| 58 表全 schema | Sherry 加 2 列 + 1 表 |
| cognitive_schemas 独立实体 + schema_versions | 折叠进 memory_entries |
| schema_network 拆分/合并/影响图 | 过重，关联层只做 1-2 跳 |
| 完整 TMS（AND/OR + SCC + 预算传播） | 只做单跳 |
| Domain Pack 声明式本体 + 领域门控 | 领域知识从 memory/facts 条目来 |
| emotion-behavior 共现扫描 | 超范围 |
| strategy 学习闭环 | Sherry 有 PTC/LDW 做过程性固化 |
| cognitive_task_runs + validation_suites | 过重，judge 用轻四标准 |
| AB 测试 | 不适用 |
| hashed_embedding（blake2b） | Sherry 用 bge-m3 |
| RRF + 时空/情绪重排 | Sherry 用 bge-m3 + reranker |
| 6 memory banks/spaces | Sherry 三目标 |
| 20+ RelationKind | Sherry ~5 种 |
| capability permissions 全治理 | 本地单用户 |
| judgment_traces/fault_cases/value_soft_prefs/identity_principals | 超范围 |

**原则**：借设计原则和轻机制，不借重基础设施。Sherry 已有 MesMemory + bge-m3 + reranker + skill review judge，复用这些比搬重基础设施划算。

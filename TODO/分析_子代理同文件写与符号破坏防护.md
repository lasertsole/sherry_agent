# 分析:子代理同文件写与符号破坏的现有防护(含无限触发/死循环审查,对照 Agensh)

> 结论先行:
> 1. **同文件前后修改:文件工具路径有真防护**(锁 + 读许可 + revision CAS + 隔离合并 CAS);
>    **shell 写路径(terminal/python_repl)完全绕过这一切**,只留沙箱。
> 2. **符号破坏:改名有"弱防护"(仅隔离合并时的公告,且只认函数/方法/类);
>    同名函数改参数、改返回值、模块级变量改名**零防护**;**没有任何机制反查谁在 import**,
>    公告只是提示父代理,纯 import 用户的证据也不会被失效。
> 3. **无限触发/死循环:当前接线不存在无界自动循环**——每条自动链都有一次性/幂等/上限;
>    真正的软循环是"父代理看到公告后行为性反复重派",只有资源上限兜底。另有两个
>    一次性写盲区(回放门的 formatter 直写、shell 写)。
> 4. 论文可解点:CLAIM 写前认领、PATCH_SUMMARY 类型化公告 + 共享发现板、mid-turn 直接
>    消息、"吸收最新进度→重验→再合"协议、反向引用由同伴评审定位——见
>    [计划_借鉴Agensh自组织多代理机制.md](计划_借鉴Agensh自组织多代理机制.md) 的 P0/P1。

## 一、同文件前后修改:现有防护

### 1.1 并发(两个子代理同时写)

| 层 | 机制 | 位置 |
| --- | --- | --- |
| 进程内 | `path_write_lock` 每规范路径互斥,读共享 | `agent/tools/pub_base/path_lock.py:129` |
| 跨进程 | `flock` LOCK_EX/LOCK_SH,锁文件 inode 永不删除 | `agent/tools/pub_base/file_lock.py:85` |
| 批内调度 | SafeToolNode 按资源分组:同文件组按模型顺序串行,非文件不安全工具全批屏障 | `agent/safe_tool_node.py`(AGENTS.md「Tool Parallel Safety」) |
| 隔离合并 | 每父根一把 `merge-<sha>.lock` flock,60s 超时,两个子代理同时合并串行 | `agent/tools/subagent/isolation/merge.py:48,87,184` |

**判定:并发同文件写有防护。** 锁只取单一路径、无嵌套获取 → 无循环等待 → 无死锁;
所有等待都有超时。

### 1.2 串行(B 在 A 之后覆盖同一文件)

- **读后写许可(write license)**:覆盖要求本会话"完整读过当前修订"或"自己写的";
  许可按 session 记录(write_file.py:96-118)。B 拿着 A 写之前的旧许可覆盖 → 原子写
  的 `expected_revision` CAS 失配 → `StaleWriteError` 拒绝,B 必须重读(write_file.py:333-366)。
- **原子写**:临时文件 + 原子替换,无半写状态。
- **隔离合并 CAS**:父树该路径仍等于子代理开工快照的 revision 才落;否则记 CONFLICT、
  父树不动、工作区保留供检视,且 manifest 被消费(SNAPSHOT→MERGED 改名,
  merge.py:203-213)——**同一次运行不可能被合并两次**;新建路径只写入"空位",
  父树已出现同名文件即拒绝(merge.py:254-259)。

**判定:串行前后修改有防护**(B 无法盲覆 A 的改动;隔离模式下 A 的父树改动与 B 的
合并冲突会被显式报告而非静默丢失)。

### 1.3 盲区(必须知道)

1. **隔离默认关闭**:`sessions_spawn(isolation=False)` 是默认(sessions_spawn.py 的
   Field 默认 False)。默认形态是共享同一工作树,只有 1.1/1.2 的锁与许可。
2. **shell 写完全绕过**:terminal / python_repl / ptc 写文件不经文件工具——无许可、
   无 CAS、无 path_lock;证据记账的 `invalidates_evidence` 装饰器只挂在
   write_file/patch_file(evidence_recorder.py:114;write_file.py:164;patch_file.py:136),
   **shell 写既不被记账也不会失效别人的证据**(它的 evidence 行 `modified_files` 恒空,
   别人改了文件它也不会被标 stale)。
3. **回放子进程直写**:finish 回放门允许 `black`/`prettier`/`ruff` 等可写 formatter
   (regression_gate.py:43-74 白名单),`_run` 直接 subprocess——**绕过许可体系**,
   一次性覆盖并发编辑(不会循环,见三)。

## 二、符号破坏(函数名/参数/返回值/变量名 → 顺着 import 破坏别人)

场景:A 改 `utils.py` 的 `foo`(改名/改签名),B 的 `b.py` `from utils import foo`。

### 2.1 现有覆盖(经代码核实)

- **改名/增/删符号——仅隔离合并时有公告**:`symbol_diff.py`(tree-sitter)在合并落盘
  前对每文件算 `InterfaceDelta`(added/removed/renamed;改名=同 (kind, parent) 组内
  Levenshtein≤2 配对,subagent_isolation.py 的 `interface_diff_rename_levenshtein=2`),
  渲染进完成公告的 "**Interface changes** (renamed/added/removed symbols — another
  subagent may still call an OLD name)" 区(workspace_merge.py:132-163,cap 10 文件/
  每类 20 条)。
- **路径级证据失效**:A 的 write_file/patch_file → `mark_evidence_stale` → 自己 + 跨会话
  广播(evidence_ledger.py:457 `mark_stale_for_path_all_sessions`,cap 扫 200 会话);
  隔离合并的 applied/created/deleted 路径同样广播(workspace_merge.py:57-68)。
  但匹配键是**路径**:命中条件是对方 evidence 行的 `modified_files`(或 legacy 命令串)
  **包含被写路径**。
- **兜底重验**:flow finish 回放门把该 flow 记录过的 passed 验证命令重放一遍
  (regression_gate.py:317;白名单验证器、无 shell、cap 10、60s/条、一次),失败记
  `broken`;TaskFlow Gate C 见 FAIL/stale/broken 拒绝 finish。如果 B 的验证命令恰好
  执行到那个 import(如 pytest 跑了 b.py),破坏会在 finish 时被确认。

### 2.2 缺口(直接回答"有无保护措施")

1. **同名签名变化完全不可见**:符号身份是 `(kind, name, parent)`(symbol_diff.py:137-139)。
   `foo(a, b)` → `foo(a, b, *, timeout)` 或返回值语义变化,**合并零冲突、公告零条目**。
2. **变量名不可见**:提取器的 kind 只有 function/method/class(extract.py:304,559),
   模块级常量/变量改名(常被 `from utils import MAX_N` 引用)不进 diff。
3. **无反向 import 索引**:公告只说"foo 改名了",**没有任何机制指出谁在 import foo**;
   是否检查全凭父代理自觉。
4. **纯 import 用户收不到失效**:B 只是 import `utils.foo`、从未改过/验证过 utils.py →
   B 的 evidence 不含该路径 → 跨会话广播不命中 → B 的"通过"证据保持绿灯。
5. **非隔离运行连公告都没有**:symbol_diff 只在隔离合并路径上运行;默认共享树模式下,
   A 直接 write_file 改名,除了路径级 stale,没有任何符号层信号。
6. **公告是 advisory**:不阻断、不自动重验、不自动通知正在跑的 B(合并公告只到父代理)。
7. **证据行只带 session key**(无 flow/图键),Gate 只能靠"新鲜度"兜(已知缺口,
   见记忆 evidence-ledger-key-binding-gap)。

**判定:改名=弱防护(仅隔离、仅公告、靠父代理反应);参数/返回值/变量名=零防护;
import 面的自动定位与失效=没有。** 现有体系是"路径世界",问题发生在"符号世界"。

## 三、无限触发 / 死循环审查(逐链路)

| 自动链路 | 触发→动作 | 界限 | 判定 |
| --- | --- | --- | --- |
| 证据 stale 标记 | 文件写/合并 → 追加 stale 行(**派生态**:读取时才折算) | 只标记,**不触发任何执行**;事件行本身不会再触发广播 | 无环 |
| finish 回放门 | flow finish → 重放 ≤10 条白名单命令 → 追加 broken/unmark | 每 flow finish **一次**;追加的事件不触发回放;flow finish 是终态不重启 | 无环 |
| announce→合并 | 子代理完成 → 合并一次 | manifest 消费/工作区丢弃(merge.py:203-213)+ announce 幂等(announce/idempotency.py)→ **不可能二次合并** | 无环 |
| announce→auto_resume | 完成 → `_try_auto_resume_taskflow`(delivery.py:385)→ resume 步骤 → auto_dispatch 下一波 | 步骤按 DAG 推进(环在 progress 层被标记);步数/spawn 天花板、每会话 spawn≤50、run_timeout 600-7200s | 有界 |
| continuation 门 | 回合结束注入续跑指令 | `max_continuation_turns=15` + 会话闩,只有未被注入的真实用户回合重置;busy 应答不计入(2026-10-15 修复,否则 stop 丢失) | 有界 |
| CompletionJudge / StepJudge / LLMRetry / InvalidToolCallRepair | 各种自动重试 | goal_max_turns / max_retries / 11 次尝试+熔断 / resend_max_retries | 有界 |
| 文件锁 / 合并锁 | 阻塞等待 | 单锁不嵌套(无循环等待);全部带超时(合并 60s) | 无死锁 |
| 跨会话 stale 广播 | 写 → 给 ≤200 个会话各追加一行 | 广播只写行;接收方无自动动作 | 无环 |

**判定:现有接线没有无限触发 bug、没有死循环。** 每条自动化要么一次性+幂等,要么显式上限。
两个真实的边角(非循环、但值得知道):

1. **回放门的 formatter 直写**:`black foo.py`(不带 `--check`)作为被记录的验证命令,
   会在回放时**绕过许可直写文件**——一次性、能覆盖并发编辑,且写完不计账。
2. **行为性软循环**:父代理读到"Interface changes"公告 → 重派修复步骤 → 新合并又产生
   接口变化 → 新公告……语义上无检测,只有资源上限(spawn≤50、步数、超时)兜底。这是
   论文场景里"吸收最新进度后重验再合"要消的浪费来源。

## 四、论文(Agensh)哪些点能解决这些问题

| 问题 | 论文机制 | 为什么能解 | 落地(计划编号) |
| --- | --- | --- | --- |
| 同文件撞车只能"写时发现" | **CLAIM 写前认领** + 撞车用直接消息当场解决 | 把冲突从"CAS 拒绝/事后冲突树"提前到意图层,省掉整轮返工 | P1-1 |
| 签名/变量/import 面零防护 | **PATCH_SUMMARY 类型化公告** + 共享上下文板可查询(board_grep) | 接口变化成为一等数据,兄弟子代理可直接检索而不等父代理转述;FAIL 条目阻止重复踩坑 | P0-1/P0-2/P1-2 |
| 破坏发现太晚(finish 才兜) | **mid-turn 高优先级注入**(DM/新板条目随下一个工具调用返回) | A 合并改名的瞬间,B 正在跑的回合就能得知并改引用,而不是等 flow 收尾回放炸出来 | P1-3 |
| 合并不重验 | **"合并被拒→吸收最新 main→重验→再合"协议** + 同伴先验证再合并(32+ 代理的评审协议) | 论文把"吸收同伴进度后必须重验"写进 worker 协议;sherry 对应"接口变化合并 ⇒ 定向回放受影响 importer" | P0-3 |
| 接口靠事后 diff | **工人事先公告接口约定**(8 代理阶段:谈定接口各自实现) | 事先约定 + 声明导出面,比事后 tree-sitter diff 更根本;sherry 可用"声明导出契约 + 合并时校验"承接 | P0-2(反向索引为基座) |
| 行为性重派浪费 | 标准化合并协议、常驻集成者、T−45/T−5 收口纪律 | 把合并权集中到验证过的流程,截止前停止派新功能,防止预算烧在互相打断上 | P2(观望) |

**论文的循环安全范式**(事件唯一 id 去重、持久队列、回合结束才确认、退避重试)与 sherry
现有 announce 幂等/delivery_state 同构——新增机制必须保持同一红线(见计划文档第四节),
尤其:**mid-turn 注入绝不能由消息事件再触发**,否则就造出 A↔B 互踢的死循环。

### 四.1 图上的三条证据(文字版论文看不出来的部分)

**(1) 图 3 的读写箭头 = mid-turn 注入该落在哪一步。** 循环五步与基础设施的关系在图上用
两类箭头标出:**异步读**(绿)发生在 Gather context / Take action / Verify results;
**并发写**(红)发生在 Claim sub-task / Take action / Merge progress。Take action 是唯一
读写兼备的一步。这直接给出 sherry 的设计约束:**注入点应挂在"读"的三处**(即下一次模型
调用前 / 下一次工具结果后),而**幂等与限流必须覆盖"写"的三处**。论文附录 B.2 说
mid-turn 注入"包在任意基础设施工具调用外层"——同一条约束的实现版。

**(2) 图 5/图 6 证明小规模加协调可能净亏——这条直接决定 sherry 该不该做 P1。**
分任务读数(正文只给均值):gromacs 19.49(1)→ 19.37(8)→ 19.17(32)→ 22.12(128),
**前三次递减**;ctags 25.82(1)→ **18.77(8)** → 44.50(32)→ 45.62(128),**8 代理跑输
单代理 7 分**;图 6 的时间曲线进一步显示 ctags 的 8 代理线全程垫底、gromacs 的 1 代理线
长期压在 8/32 之上。**"不大不小"的 8 代理是最难看的配置。** 对 sherry 的含义:sherry 的
子代理典型并发是 2~10 个,正落在这个"协调开销 > 并行收益"的区间边缘——所以 CLAIM 板、
共享发现板这类**主动协调机制必须是 opt-in / 按并发数门控 / 默认 advisory**,不能默认开启
强制流程;而 P0 三项(签名面检测、反向索引、合并即重验)属于**检测/验证**,不是参与式协调
协议,不产生"每个工人都要额外读写一块共享黑板"的开销,所以不受这条证据约束。

**(3) 图 2 的拓扑说明"中心化能不能借"——能。** 左侧"编排者组织工人"与右侧 Agensh 的
拓扑**都是星形**;区别只在中心节点里装的是"一个有智能的编排者"还是"共享工作区+消息接口+
共享上下文这套被动设施"。所以可迁移的是**"把中心基础设施化"**,而不是"取消中心"。这与
sherry 的形态吻合:保留父代理作为派发/判定中心,把"兄弟之间共享发现与接口变更"下沉到
哑设施(账本/板/注入),正是图 2 右侧那个形状。

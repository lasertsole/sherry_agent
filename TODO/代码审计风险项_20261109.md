## 一、严重（High）

### H3. Windows 平台无 OS 沙箱后端，terminal/python_repl 在默认 AUTO 下静默降级为无沙箱执行
- **严重性**：HIGH
- **位置**：`agent/tools/pub_base/sandbox.py:270-306`、`agent/tools/terminal/core.py`、`agent/tools/python_repl.py`
- **问题**：`get_backend` 仅在 Linux(bwrap)/Darwin(seatbelt) 返回后端，Windows 一律返回 `None`；AUTO 策略下 `None` 仅打印一条 loguru 警告即降级为裸 `subprocess`/`create_subprocess_shell`。此时唯一屏障是 `DANGEROUS_COMMAND_REGEX` 与 `_SENSITIVE_FILE_PATTERNS` 的字面正则——代码注释自承这些是 mitigation 而非 barrier：`sed`/`dd`/`python -c "open('.env').read()"`/变量/通配/heredoc 均可绕过。
- **影响**：在 Windows（当前部署环境为 win32）上，agent 可经 terminal 读取 `.env`、`~/.ssh/`、任意系统文件并执行任意命令，无任何 OS 级隔离。
- **建议**：Windows 下 `SANDBOX_POLICY=auto` 且后端不可用时，应 fail-closed 或强制 HITL，而非静默降级。

## 二、中等（Medium）

### M2. `/system/dirs` 允许枚举全盘目录结构，无范围限制
- **位置**：`server/service/system_folders_service.py:44-81`
- **问题**：`list_subdirectories` 接受任意绝对路径并返回子目录名，仅"必须绝对路径 + 数量上限"，可对 `C:\Windows\System32\config`、`/etc`、`~/.aws` 等逐级枚举。结合默认 loopback 免登录/免 token，同源注入脚本可遍历整个文件系统目录树做侦察。
- **建议**：限制可枚举根范围或要求额外授权。

### M6. `restore_runs_from_disk` 在恢复主体运行前将 `_restore_done` 翻转为 `True`
- **位置**：`agent/tools/subagent/registry/state.py:53-90`
- **问题**：`_restore_done = True` 在 `try:` 块之前设置。若加载或重定基抛出异常，循环失败被吞没，内存部分填充且标志位永不重试。这同时导致 `server/service/effects/restart_table.py` 的 `apply_subagent_terminals` 变为 no-op。重启后的 RUNNING 残留和单调时钟重定基只能尝试一次且 fail-open。
- **建议**：将标志位移到主体成功完成后，或循环内部用独立"已尝试"标志 + 重试上限。

### M7. `requeue_claimed_inputs` 等修复仅覆盖前 50 个最新会话
- **位置**：`server/service/boot_recovery.py:34,62-63,178-195`
- **问题**：`_MAX_SESSIONS = 50` 上限 + 跳过无活动 checkpoint 的目录，任何不在前 50 名内且持有 `CLAIMED` 输入队列行的会话不会被重新排队。这些行保持 `CLAIMED` 直到 24 小时 `expires_at` 过期，用户消息会在近一天内消失。`rebuild_hitl_pending` 和 `heal_dangling_turns` 共享此上限——繁忙多会话安装中这些修复仅 best-effort。
- **建议**：移除或大幅提高上限；或按"有未完成队列行/HITL 中断"过滤候选而非按活跃度排序。

### M8. `lane.set_max` 在车道持续饱和时静默丢弃配置更改
- **位置**：`runtime/lane/core.py:155-198`
- **问题**：热更新将 `_rebind_pending = True` 推迟，仅在 `_queued == 0` 时应用。持续 MAIN/SUBAGENT 负载下队列永不排空，挂起 rebind 永不触发，新 `max_concurrent` 静默丢失。`_rebind` 本身用 `max(1, self._max - self._active)` 作底，`_active` 超过降低后限制时新信号量仍会发出 1 个许可，允许超限准入。
- **建议**：rebind 应用不依赖 `_queued==0`；或在准入点检查"当前 active 是否已超新上限"做拒绝。

### M9. `effects` 工作线程在异步循环中执行同步 `sqlite3` 调用
- **位置**：`runtime/effects/worker.py:70-113` → `runtime/effects/intent_log.py:152-209`
- **问题**：每个 `_tick` 从运行中事件循环直接调用 `fetch_pending`/`mark_in_flight`/`mark_done`/`mark_retry`（同步阻塞 `sqlite3.connect`+`commit`）。磁盘争用下会停滞整个循环——包括所有回合调度和 WS 帧发送。阻塞无界（`busy_timeout=5s` × 每批多次调用）。
- **建议**：通过 `asyncio.to_thread` 分派，匹配 `context_engine/store/db.py` 的模式。

### M11. `taskflow mark_flow_superseded` 在没有 CAS 的情况下提升 `expected_revision`
- **位置**：`agent/tools/taskflow/registry/store_sqlite.py:318-352`
- **问题**：该更新没有 `expected_revision = ?` 谓词——无条件 `expected_revision + 1`。两个并发 `mark_flow_superseded`（重新规划竞争 vs 取消竞争）都会成功并各提升一次，版本号跳两步，随后持有实际 revision 的 `update_flow` CAS 会以 `FlowConflictError` 失败，即使无真正并发修改。
- **建议**：supersede 使用 `WHERE expected_revision = ?` 使两并发调用者线性化。

### M12. `ContextEviction` 工具结果截断是 fail-open，且子代理会话根本不注册该中间件
- **位置**：`agent/middlewares/context_eviction/core.py:366-368`、`agent/middlewares/specs.py:367-370`
- **问题**：截断失败时直接返回**原始超大结果**（fail-open），OOM 风险未消除。更严重的是子代理完全不安装此中间件（spec 只有 `required_in=frozenset({MAIN})`，没有 child binding）——子代理 `read_file`/`sessions_messages`/任何工具的巨量输出原样留在子代理上下文与 checkpoint，长任务子代理可 OOM。`human_evict_threshold_chars=200_000`/`evict_threshold_chars=20_000` 对子代理无效。
- **建议**：子代理安装精简版 context eviction；截断失败应 fail-closed 或 fallback 到硬字节截断而非返回原始结果。

### M13. LLM 内容审核在不可达时 fail-open 放行
- **位置**：`agent/middlewares/safety_filter/middlewares.py:180-233`
- **问题**：`LLMModerationMiddleware` 在审核模型不可达/无法解析时返回 None，中间件 fail-open 让该轮继续进入主 LLM。这是关键安全输入路径上的 fail-open：provider 故障或审核服务被 DoS 即可绕过内容过滤。设计注释自述"a safety check that stalls the turn is worse than none"，但语义上等于安全门失效。
- **建议**：至少在 `safety_filter.llm_moderation_strategy == "always"` 模式下 fail-closed 或要求人工确认。

### M14. TaskFlow `_evidence_gate` 全链路 fail-open，可放过未验证完成
- **位置**：`agent/tools/taskflow/tools/taskflow_finish.py:132-200`
- **问题**：证据门用于判定 flow 是否真正达成目标。回归 replay 出错 → skip；`collect_evidence_summary` 异常 → `return None`（通过）；ledger 任何读失败 → 通过。失败/陈旧/损坏的证据都会被当作"无证据即放行"，可能导致未经验证的工作被标记完成。
- **建议**：安全/质量门禁不应 fail-open，至少记录为"证据不可用，需人工确认"而非直接放行。

### M15. LDW replay 对 auto-skill 脚本执行 `exec_module`（全权限主进程执行）
- **位置**：`agent/tools/ldw/scripts.py:103-112`
- **问题**：`load_ldw_script` 用 `importlib` 执行磁盘上的 `.py`，无沙箱、无 builtins 限制（与 PTC 不同）。`write_ldw_script` 自己只写常量（`repr` 渲染），但文件落在操作者可写的 `AUTO_SKILLS_DIR/ldw-replay/scripts/`。任何能写入该目录的进程/恶意 skill 即可注入任意 Python 在主进程执行。`plan_key` 有正则约束防路径穿越，但不防内容篡改。
- **建议**：LDW 脚本执行应走与 PTC 相同的沙箱与受限 builtins；或对脚本做 AST 白名单校验。

### M16. `mes_memory` 在一个全局 `RLock` 上序列化所有语句
- **位置**：`context_engine/store/db.py:23-57`
- **问题**：`_stmt_lock` 是保护唯一共享连接的模块级 `threading.RLock`。每个 `execute`/`commit`（跨所有会话的每条消息持久化、嵌入写入、压缩等）都获取它。会话 A 的工具结果持久化会阻塞会话 B 的读取，容量天花板是单 `RLock` 持有时间而非 SQLite 能力。高并发下表现为每回合尾部延迟。
- **建议**：若部署扩展到超过每进程几个并发会话，应改用连接池或 per-session 连接。

## 三、低（Low）

### L1. `DANGEROUS_COMMAND_REGEX` 黑名单可被多种方式绕过
- **位置**：`agent/tools/terminal/core.py:220-232`
- **问题**：正则只覆盖 `rm -rf`/`mkfs`/`shutdown`/`reboot` 的有限形态，且对 `&&/||/;` 后接危险词才匹配。`find / -delete`、`dd if=/dev/zero of=/dev/sda`、`chmod -R 777 /`、`:(){ :|:& };:`、`python -c "import os;os.system('...')"` 等均不命中。OS 沙箱可用时这是可接受的第二层 mitigation；在 Windows(H3) 或 `sandbox=False` 被绕过时它成为唯一屏障即失效。

### L2. 路径解析的中间目录符号链接替换存在残余 TOCTOU
- **位置**：`agent/tools/pub_base/path_utils.py:96-128,82-93`
- **问题**：`resolve_workspace_path` 先 `.resolve()`（跟随所有符号链接）再 `is_relative_to(root)`，`_open_no_follow` 仅对**最后一段**做 `O_NOFOLLOW`。若 `resolve()` 之后、`open()` 之前某个**中间父目录**被替换为指向 root 外的符号链接，存在理论 TOCTOU 窗口。实际利用需竞态且需在 root 内有可写中间目录，风险低，但与 `_open_no_follow` 注释声称的"closes the TOCTOU window"不完全一致（它只关闭末端组件窗口）。

### L3. `_rebase_restored_clock` 为预先终止的已恢复运行重置 `archive_at`
- **位置**：`agent/tools/subagent/registry/state.py:52-97`
- **问题**：每次恢复的运行都被重定基，包括重启前已 TERMINAL 的运行。对有非空 `archive_at` 的终止运行，它获得 `now + window`，延迟归档/驱逐一个完整 `archive_after_minutes` 窗口。含许多预重启终止运行的注册表会驻留更久。非正确性问题，是内存/磁盘膨胀 + 延迟驱逐。

### L4. `complete_subagent_run` 在终端锁上存在 TOCTOU
- **位置**：`agent/tools/subagent/registry/lifecycle.py:113-118`
- **问题**：`if lock.locked(): return get_run(run_id)` 后跟 `async with lock:` 是 check-then-act 窗口。生成跟踪器（`is_callback_current`）和 `_arbitrate_kill_vs_completion` 涵盖重复终结，影响是双重终结尝试的冗余日志/通知而非状态损坏。该检查是快路径快捷方式，移除仅增加一次等待。

### L5. `_terminal_locks`/`_cleanup_generations`/`_deferred_cleanup_timers` 针对每个 `run_id` 无界增长
- **位置**：`agent/tools/subagent/registry/lifecycle.py:40-49,52-80`
- **问题**：`sweep_stale_lifecycle_state` 修剪运行已从注册表消失的条目，但仅由清理器触发；无逐出时自修剪。若清理器停滞或未注册，这些字典随每个生成运行增长。依赖关闭路径 `shutdown_deferred_cleanup` 清空。

### L8. `memory_entries` 仅按"未使用天数"清理，活跃条目无上限
- **位置**：`config/features/agent_side/memory_tool.py:24,38`、`server/service/memory_entries.py:259`
- **问题**：只有 90 天未用条目被剪枝；活跃/被引用 memory 条目无最大条数、无总体积上限。consolidation 只合并不强制封顶。长期会话 memory 表可无限增长。

### L9. 子代理 wall-clock 超时是 per-child，不覆盖整个子树
- **位置**：`agent/tools/subagent/config.py:28,19,23`、`completion_judge.py:35`
- **问题**：单子代理 600s 上限，但 fan-out 是 main→5 orchestrator→各 5 leaf = 25 leaf，加上 `max_total_spawns_per_session=50`。深度已被 `MAX_SPAWN_DEPTH_CAP=2` 与角色 allow-list（LEAF 无 CHILDREN scope）正确限制——fan-out 不会无限。但并发子树最坏耗时 ≈ 50 × 600s，且父超时不强制 kill 已分离孙辈（依赖 orphan sweeper 120s 延迟回收）。

### L10. LLM 重试预算叠加可能放大调用次数
- **位置**：`config/features/agent_side/llm_retry.py:34`、`llm_client_defaults.py:32-58`、`invalid_tool_call.py:22`、`max_tokens_boost.py:26`、`step_judge.py:24`
- **问题**：各层独立计数。最坏路径：goal loop 5 turn × (LLM retry 10 + invalid_tool resend 2 + max_tokens_boost 3)。但主 LLM `main_max_retries=0`/`fallback_max_retries=0` 限制了主路径爆炸；`llm_retry.max_retries=10` 主要作用于 aux 通道；`completion_judge` fail-open 防止 judge 死循环。
- **建议**：对"同一条消息上的累计 LLM 调用"设全局上限。

## 五、优先处置建议

6. **L2/L3/L4/L5/L8/L9/L10**：其余 Low 项可批量排期或纳入对应模块的常规加固。

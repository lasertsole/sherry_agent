# 项目代码审计风险项报告

> 审计日期：2026-11-09
> 审计范围：`D:\selfProj\sherry_agent` 全量代码（Python 后端 Robyn + LangGraph + SQLite；前端 Nuxt 4 / Tauri 2）
> 审计域：安全（认证/路径/沙箱/注入）、并发与状态机、资源管理与外部交互

总体评价：该项目安全设计成熟度较高——路径解析有"字符串级 `..` 拒绝 → `resolve()` → `is_relative_to` → 符号链接环检测 + `O_NOFOLLOW`"四道门；HTTP 层有 Origin 白名单 + 网关 token + CSRF(Sec-Fetch-Site) + 用户登录四层中间件全局生效且无路由可绕过；前端 `v-safe-html` + DOMPurify 且 eslint 禁用 `v-html`；env scrub 优先级正确（hijack > keep > deny > substring），`PYTHONPATH`/`BASH_ENV` 等启动钩子恒被剥离；CAS 竞态（effects `(id,generation,status)`、input_queue `claim_next` `UPDATE...RETURNING` + `BEGIN IMMEDIATE`）实现正确；子代理 fan-out 深度/广度/总数都有界且 role allow-list 有效。

但仍存在若干真实风险，按严重性分级如下。

## 一、严重（Critical / High）

### H1. HTTP 项目文件浏览器可读取 `.env`/`.models` 等凭据文件
- **严重性**：HIGH
- **位置**：`server/service/project_files_service.py:82-94,161-191`、`server/trigger/http/project_files.py:105-137`
- **问题**：`/project/file` 与 `/project/file/blob` 仅用 `resolve_within(session_project_dir, rel)` 做越界校验，**未应用** agent 侧的 `self_path_policy` 敏感文件拒绝清单（`_ROOT_SENSITIVE_FILES` = `.env/.models/.network/sherry.jsonc`，见 `agent/tools/pub_base/self_path_policy.py:56-63`，只覆盖 agent 工具）。当一个会话**未绑定外部项目目录**（`project_dir_source == "default"`）时，`current_project_dir` 回落到 `ROOT_DIR`（仓库本身），于是 `GET /project/file?session_id=<unbound>&path=.env` 直接返回 `.env` 明文（含 `MAIN_LLM_API_KEY` 等）。
- **放大因素**：默认 `SHERRY_GATEWAY_REQUIRE_TOKEN` 为空（`server/trigger/gateway.py:56`）、loopback 免登录（`auth_user.py:126`），任意本地进程或同源注入脚本即可读取全部模型 API key。
- **建议**：在 `resolve_within` 之后追加 `_ROOT_SENSITIVE_FILES` 名单校验（与 agent 工具同一策略）；未绑定项目目录的会话拒绝 `/project/file*` 端点。

### H2. 沙箱 `sandbox` 参数对模型可见，主会话 `sandbox=False` 在 AUTO 策略下无审批直接放行
- **严重性**：HIGH
- **位置**：`agent/tools/pub_base/sandbox_guard.py:15-36`、`agent/tools/terminal/core.py:284-291`（`sandbox` 在 `SafeShellInput` schema 中）、`agent/tools/python_repl.py:276-282`
- **问题**：`_deny_sandbox_bypass` 仅在 `caller_scope != "main"` 或 `SANDBOX_POLICY=required` 时拒绝 `sandbox=False`。默认策略为 `AUTO`（`sandbox.py:139`），主会话调用 `sandbox=False` **直接通过、无 HITL**——代码注释自承 "main-session human approval wiring arrives — no `interrupt()` here"。`sandbox` 字段在模型可见的 `args_schema` 中，LLM 可主动设为 false 关闭自己的沙箱。
- **建议**：主会话首次 `sandbox=False` 仍应走 HITL 审批；或从模型可见 schema 中移除 `sandbox` 字段，由服务端按策略决定。

### H3. Windows 平台无 OS 沙箱后端，terminal/python_repl 在默认 AUTO 下静默降级为无沙箱执行
- **严重性**：HIGH
- **位置**：`agent/tools/pub_base/sandbox.py:222-265`、`agent/tools/terminal/core.py:454-467`、`agent/tools/python_repl.py:171-187`
- **问题**：`get_backend` 仅在 Linux(bwrap)/Darwin(seatbelt) 返回后端，Windows 一律返回 `None`；AUTO 策略下 `None` 仅打印一条 loguru 警告即降级为裸 `subprocess`/`create_subprocess_shell`。此时唯一屏障是 `DANGEROUS_COMMAND_REGEX` 与 `_SENSITIVE_FILE_PATTERNS` 的字面正则——代码注释自承这些是 mitigation 而非 barrier：`sed`/`dd`/`python -c "open('.env').read()"`/变量/通配/heredoc 均可绕过。
- **影响**：在 Windows（当前部署环境为 win32）上，agent 可经 terminal 读取 `.env`、`~/.ssh/`、任意系统文件并执行任意命令，无任何 OS 级隔离。
- **建议**：Windows 下 `SANDBOX_POLICY=auto` 且后端不可用时，应 fail-closed 或强制 HITL，而非静默降级。

### H4. `python_repl` / PTC 受限 builtins 可经类自省逃逸到 `os`/`subprocess`
- **严重性**：HIGH
- **位置**：`agent/tools/python_repl.py:81-118`、`agent/tools/ptc/runner.py:96-103,138`、`agent/tools/ptc/builtins.py:25-95`
- **问题**：`__builtins__` 白名单删除了 `open`/`__import__`，但保留了 `getattr`/`type`/`dir`/`vars`/`hasattr`/`isinstance`/`id`。经典逃逸 `().__class__.__base__.__subclasses__()` 可定位 `subprocess.Popen`/`os.system`。代码注释自承 "class introspection can still reach `os`"（`python_repl.py:302-304`），将真正屏障完全推给 OS 沙箱后端——而该后端在 Windows 不存在（H3），在 Linux 也可被 H2 的 `sandbox=False` 绕过。PTC 编译器对"禁止 os/subprocess"仅是 prompt 指令，无 AST 强校验。
- **建议**：受限 builtins 应进一步移除 `getattr`/`type`/`vars`/`dir`，或对 `__class__`/`__subclasses__` 等属性访问做拦截；OS 沙箱不可用时拒绝执行。

### H5. `browser_navigate` 无 SSRF 防护 — 内网/元数据/本地文件可被模型访问
- **严重性**：HIGH
- **位置**：`agent/tools/browser/tools/browser_navigate.py:28-35`、`server/service/browser_manager.py:847,940`
- **问题**：`browser_navigate` 接受任意绝对 URL，未调用 `is_public_url`/`is_local_url`/scheme 白名单。模型可让真实 Chrome 打开 `http://127.0.0.1:port`、`http://169.254.169.254`（云元数据）、内网管理面、`file://` 等，再通过 `browser_snapshot`/`browser_screenshot` 把页面内容读回，构成 SSRF + 数据泄露。`web_fetch` 有完整 SSRF 守卫（`public_url.py` fail-closed DNS 解析 + `safe_fetch.py` 逐跳 re-pin），但浏览器路径完全没有对齐。CDP devtools 端点本身也监听 `127.0.0.1`，可被反向利用。
- **建议**：`browser_navigate` 复用 `web_fetch` 的 SSRF 守卫；至少校验 scheme 白名单 + 私网地址 + 元数据地址拒绝。

## 二、中等（Medium）

### M1. `.models` 配置路由向前端明文返回 API key
- **位置**：`server/service/models_config.py:111-166`、`server/trigger/http/models_config.py:9-41`
- **问题**：`read_models_config` 用 `_display_value` 渲染每行值，仅处理 bool/dict/JSON 解析，**不对 `*_API_KEY` 做掩码**。`GET /models-config` 将 `MAIN_LLM_API_KEY`/`AUXILIARY_LLM_API_KEY`/`TAVILY_API_KEY` 等真实密钥以明文下发到前端 JS。
- **建议**：对 `*_API_KEY` 类键做掩码（如 `sk-****1234`），仅在显式写入时接收新值。

### M2. `/system/dirs` 允许枚举全盘目录结构，无范围限制
- **位置**：`server/service/system_folders_service.py:44-81,54-71`
- **问题**：`list_subdirectories` 接受任意绝对路径并返回子目录名，仅"必须绝对路径 + 数量上限"，可对 `C:\Windows\System32\config`、`/etc`、`~/.aws` 等逐级枚举。结合默认 loopback 免登录/免 token，同源注入脚本可遍历整个文件系统目录树做侦察。
- **建议**：限制可枚举根范围或要求额外授权。

### M3. 网关 token 写入每个响应的全局响应头
- **位置**：`server/trigger/core.py:30-31`
- **问题**：`app.set_response_header(auth.TOKEN_HEADER, auth.gateway_token())` 对所有响应（含静态资源/错误）都附加 token。一旦 webview 内出现脚本注入（DOMPurify 0day、被篡改的 dev-server 资产、mermaid/KaTeX 解析缺陷），同源脚本即可读出 token 并以合法凭据驱动全部 API。`csrf.py` 注释也承认同源注入是 residual gap。
- **建议**：token 仅通过受信通道（如 `POST /auth/token` 一次性）下发，不写入全局响应头。

### M4. `/auth/token` 向任意白名单 Origin 的 token-less 调用方发放网关 token
- **位置**：`server/trigger/auth.py:58,90-112`、`server/trigger/core.py:34-41`
- **问题**：`BOOTSTRAP_PATH=/auth/token` 在 strict 模式下也豁免 token 校验，仅靠 Origin 白名单。Origin 白名单默认含 `http://localhost:3000`/`127.0.0.1:3000`——本机任何监听这些端口的进程或被攻陷的本地 dev 服务器页面都能取走 token。
- **建议**：dev-server 劫持场景值得收紧；至少在生产构建中移除 `localhost:3000` 白名单或要求额外绑定。

### M5. `trajectory_store` 每次操作的连接忽略 `busy_timeout`，读取静默失败
- **严重性**：MEDIUM（数据完整性）
- **位置**：`server/service/trajectory_store.py:226,308,340,360`
- **问题**：每次 `aiosqlite.connect(self._db_path)` 都直接执行 SQL 而无 `PRAGMA busy_timeout`（只有 `_ensure` 初始化连接第 194 行设置了）。`busy_timeout` 是 per-connection 的，默认 0，任何与写入者冲突的读取会立即收到 `SQLITE_BUSY`，而每个调用点都包裹在 `except Exception: ... return []`，读取静默失败返回空数据。`read()` 也没有获取 `self._lock`，读取者在无序列化、无退避下与写入者竞争。仓库中其他所有存储都正确设置了 per-connection `busy_timeout`，此模块是特例。
- **建议**：在 `_connect`/每次 `aiosqlite.connect` 后立即 `PRAGMA busy_timeout=...`；`read()` 获取 `self._lock` 或使用独立读连接池。

### M6. `restore_runs_from_disk` 在恢复主体运行前将 `_restore_done` 翻转为 `True`
- **位置**：`agent/tools/subagent/registry/state.py:137-140`
- **问题**：`_restore_done = True` 在 `try:` 块之前设置。若加载或重定基抛出异常，循环在第 171 行失败被吞没，内存部分填充且标志位永不重试。这同时导致 `server/service/effects/restart_table.py:49` 的 `apply_subagent_terminals` 变为 no-op。重启后的 RUNNING 残留和单调时钟重定基只能尝试一次且 fail-open。
- **建议**：将标志位移到主体成功完成后，或循环内部用独立"已尝试"标志 + 重试上限。

### M7. `requeue_claimed_inputs` 等修复仅覆盖前 50 个最新会话
- **位置**：`server/service/boot_recovery.py:34,178-195`、`candidate_session_ids:62-63`
- **问题**：`_MAX_SESSIONS = 50` 上限 + 跳过无活动 checkpoint 的目录，任何不在前 50 名内且持有 `CLAIMED` 输入队列行的会话不会被重新排队。这些行保持 `CLAIMED` 直到 24 小时 `expires_at` 过期，用户消息会在近一天内消失。`rebuild_hitl_pending` 和 `heal_dangling_turns` 共享此上限——繁忙多会话安装中这些修复仅 best-effort。
- **建议**：移除或大幅提高上限；或按"有未完成队列行/HITL 中断"过滤候选而非按活跃度排序。

### M8. `lane.set_max` 在车道持续饱和时静默丢弃配置更改
- **位置**：`runtime/lane/core.py:155-198`
- **问题**：热更新将 `_rebind_pending = True` 推迟，仅在 `_queued == 0` 时应用。持续 MAIN/SUBAGENT 负载下队列永不排空，挂起 rebind 永不触发，新 `max_concurrent` 静默丢失。`_rebind` 本身用 `max(1, self._max - self._active)` 作底，`_active` 超过降低后限制时新信号量仍会发出 1 个许可，允许超限准入。
- **建议**：rebind 应用不依赖 `_queued==0`；或在准入点检查"当前 active 是否已超新上限"做拒绝。

### M9. `effects` 工作线程在异步循环中执行同步 `sqlite3` 调用
- **位置**：`runtime/effects/worker.py:70-113` → `runtime/effects/intent_log.py:152-209`
- **问题**：每个 `_tick` 从运行中事件循环直接调用 `fetch_pending`/`mark_in_flight`/`mark_done`/`mark_retry`（同步阻塞 `sqlite3.connect`+`commit`）。磁盘争用下会停滞整个循环——包括所有回合调度和 WS 帧发送。阻塞无界（`busy_timeout=5s` × 每批多次调用）。
- **建议**：通过 `asyncio.to_thread` 分派，匹配 `context_engine/store/db.py` 的模式。

### M10. `side_chat_store` 未启用 WAL 且每次打开连接运行 DDL
- **位置**：`server/DAO/side_chat_store.py:72-85`
- **问题**：`_connect` 打开 `sqlite3.connect(..., timeout=30)` 并 `PRAGMA busy_timeout=30000`，但**从未设置 `journal_mode=WAL`**。文件保持 rollback journal 模式，写者完全序列化读者。更糟的是每次连接打开都运行 `_DDL` + `_add_missing_columns`（每次 `PRAGMA table_info` + `ALTER TABLE` 循环）+ 索引 DDL——每次读/写都付出 DDL 成本并强制写锁路径。仓库中其他所有存储都通过锁保护的 per-process-once 初始化运行一次 DDL，此模块是特例。
- **建议**：启用 WAL；DDL 移到 per-process-once 初始化。

### M11. `taskflow mark_flow_superseded` 在没有 CAS 的情况下提升 `expected_revision`
- **位置**：`agent/tools/taskflow/registry/store_sqlite.py:318-352`
- **问题**：该更新没有 `expected_revision = ?` 谓词——无条件 `expected_revision + 1`。两个并发 `mark_flow_superseded`（重新规划竞争 vs 取消竞争）都会成功并各提升一次，版本号跳两步，随后持有实际 revision 的 `update_flow` CAS 会以 `FlowConflictError` 失败，即使无真正并发修改。
- **建议**：supersede 使用 `WHERE expected_revision = ?` 使两并发调用者线性化。

### M12. `ContextEviction` 工具结果截断是 fail-open，且子代理会话根本不注册该中间件
- **位置**：`agent/middlewares/context_eviction/core.py:366-368`、core.py:46-47
- **问题**：截断失败时直接返回**原始超大结果**（fail-open），OOM 风险未消除。更严重的是子代理完全不安装此中间件——子代理 `read_file`/`sessions_messages`/任何工具的巨量输出原样留在子代理上下文与 checkpoint，长任务子代理可 OOM。`human_evict_threshold_chars=200_000`/`evict_threshold_chars=20_000` 对子代理无效。
- **建议**：子代理安装精简版 context eviction；截断失败应 fail-closed 或 fallback 到硬字节截断而非返回原始结果。

### M13. LLM 内容审核在不可达时 fail-open 放行
- **位置**：`agent/middlewares/safety_filter/middlewares.py:142-146`
- **问题**：`LLMModerationMiddleware` 在审核模型不可达/无法解析时返回 None，中间件 fail-open 让该轮继续进入主 LLM。这是关键安全输入路径上的 fail-open：provider 故障或审核服务被 DoS 即可绕过内容过滤。设计注释自述"a safety check that stalls the turn is worse than none"，但语义上等于安全门失效。
- **建议**：至少在 `safety_filter.llm_moderation_strategy == "always"` 模式下 fail-closed 或要求人工确认。

### M14. TaskFlow `_evidence_gate` 全链路 fail-open，可放过未验证完成
- **位置**：`agent/tools/taskflow/tools/taskflow_finish.py:144-191`
- **问题**：证据门用于判定 flow 是否真正达成目标。回归 replay 出错 → skip；`collect_evidence_summary` 异常 → `return None`（通过）；ledger 任何读失败 → 通过。失败/陈旧/损坏的证据都会被当作"无证据即放行"，可能导致未经验证的工作被标记完成。
- **建议**：安全/质量门禁不应 fail-open，至少记录为"证据不可用，需人工确认"而非直接放行。

### M15. LDW replay 对 auto-skill 脚本执行 `exec_module`（全权限主进程执行）
- **位置**：`agent/tools/ldw/scripts.py:108-112`、`scripts.py:73-99`
- **问题**：`load_ldw_script` 用 `importlib` 执行磁盘上的 `.py`，无沙箱、无 builtins 限制（与 PTC 不同）。`write_ldw_script` 自己只写常量（`repr` 渲染），但文件落在操作者可写的 `AUTO_SKILLS_DIR/ldw-replay/scripts/`。任何能写入该目录的进程/恶意 skill 即可注入任意 Python 在主进程执行。`plan_key` 有正则约束防路径穿越，但不防内容篡改。
- **建议**：LDW 脚本执行应走与 PTC 相同的沙箱与受限 builtins；或对脚本做 AST 白名单校验。

### M16. `mes_memory` 在一个全局 `RLock` 上序列化所有语句
- **位置**：`context_engine/store/db.py:23,39-57`

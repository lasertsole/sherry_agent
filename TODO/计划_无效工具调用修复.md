## 0. 问题与证据

### 0.1 现象

模型发出的 tool call 若 `arguments` 不是合法 JSON，`langchain_core` 的 `default_tool_parser`
（`.venv/.../langchain_core/messages/tool.py:355-384`）把它归入 `invalid_tool_calls`
（**args = 原始字符串、error=None**），`tool_calls` 保持为空。`create_agent` 的模型→工具
路由只看 `tool_calls`，于是这条 AI 消息被当作「无调用的终答」**直接结束回合**——
模型不知道（它以为还要继续）、用户不知道、日志里没有一行记录。

该 parser 只对 **JSONDecodeError** 产生 invalid 条目（工具名不存在不在其中——那种走
ToolNode 的 tool-error 路径回给模型，不是静默丢弃）。

### 0.2 真实样本（与截断不同）

django__django-17051 的 14.7s 回合里，模型两次发出 `terminal` 调用，arguments 全部非法：

1. `{"commands": cd $(pwd) && pwd && git log --oneline -3 && ls}` —— 命令值缺引号；
2. `{"commands": cd /repo 2>/dev/null || cd .; git log --oneline -3; python -c "import django; print(django.__version__)"}`
   —— 值缺引号且含**未转义的内层双引号**。

结果：第二次调用让消息变成「零调用」，回合在 0.6s 内结束；**零改动**、FAIL_TO_PASS 5 全败
（PASS_TO_PASS 全过——没有任何东西被弄坏，只是活没干）。同一条消息里合法的
`search_files` 兄弟调用正常执行——丢弃是**逐调用**的：部分合法 + 部分非法时，非法的那条
被静默扔掉。

证据落点（均可复核）：

- checkpoint（`evals/results/swebench/20261017_003529/sandbox/src/checkpoints/sqlite.db`）：
  两条消息的 `invalid_tool_calls` 原文（`args` 即上面的串、`error` 为 nil）；
- MesMemory（同目录 `src/store/mes_memory/mes_memory.db`）：最后一条 AI 消息 `tool_calls=[]`，
  正文却是「…Let me check the git log…」；
- 运行日志：两次 `stream: tool start name=terminal` 之后**既无 `tool executed` 也无结果帧**。

### 0.3 与已有机制的边界

- **截断**（`finish_reason=length`）：流式聚合用 `parse_partial_json` 能给出部分对象 →
  `tool_calls` 非空 → `MaxTokensBoostMiddleware` 已兜底（boost 重发）。
- **本问题**：即使输出完整也解析不了的**语法错误**（值缺引号是 deepseek-flash 的实测形态），
  全链路无人处理——这是修复对象。
- 现有对 `invalid_tool_calls` 的唯一消费点是 `pub/func/transcript_repair.py`（重放/配对路径上
  **清空**它以免序列化成 OpenAI tool_calls），运行时循环（before_model / after_model /
  wrap_model_call）**没有任何一层检查它**。

## 1. 设计

### 1.1 P0-A：语法修复 `InvalidToolCallRepairMiddleware`

**落点**：`awrap_model_call` / `wrap_model_call`（与 `OutputRepetitionGuard`、
`MaxTokensBoostMiddleware` 同一接缝），注册为 `_build_middlewares` 的**最后一项**——即
wrap 链的最内层、贴着模型调用。这一位置是刻意的：

- 返回给图状态的是修复后的消息 → **ToolNode 路由、MessagePersistence 落库、checkpoint
  三处一致**（DB 里存的是修复后的 tool_calls，不会 state 有 DB 没有）；
- 所有外层重试（LLMRetry / Summarization 的 T4/T5）重调 handler 时都会再经过本层，
  且本层幂等（严格解析成功即原样返回）。

**触发条件**：handler 返回的 AIMessage 满足全部——

1. `invalid_tool_calls` 非空；
2. `finish_reason` **不是** `length` / `max_tokens`（截断是 MaxTokensBoost 的领地，
   本层必须让路，否则可能把截断的残片"补"成一个能解析的坏参数）。

**修复算法**（纯函数，逐条调用，保守到只做语法补全）：

1. 取原始 args 字符串，候选 A：去掉结尾多余逗号后 `json.loads`；
2. 候选 B（实测形态）：顶层 `"键":` 之后出现**未加引号的值** → 从值起点取到对象结尾的
   原文，转义其中的 `\` 与 `"`，整体加引号，再 `json.loads`；
3. **接受条件**（全部满足才修）：解析成功、结果是 `dict`、且修复后的值与原文**逐字节一致**
   （纯 quote-only 变换，不做任何语义重解释）；多键且中间值缺引号（边界歧义）→ **不修**；
4. 修复后的调用以 `message.model_copy(update={...})` 重建：`tool_calls` = 原有合法调用 +
   修复调用（**保持原顺序、原 name、原 id**），`invalid_tool_calls` 清空。

**id 必须保留**：客户端那张工具卡是 `stream_dispatch` 从原始 delta 投影出的
`tool_start`（先于本层发生）；修复后执行产出的结果帧带同一个 id 才能配对，悬空卡片自愈。

**安全性**：修复后的调用照常经过 `wrap_tool_call` 全链（ToolGuardrails / PathGuard /
HITL 审批 / sandbox writable-roots）——**修复不绕过任何门**；quote-only 且逐字节相等，
是纯语法补全而非替模型改主意。

**同一消息含兄弟调用**（0.2 的第 1 个样本）：合法的保留、非法的修复，全部一起走
ToolNode——今天非法的那条是被静默丢掉的。

### 1.2 P0-B：可见性

- **日志**：修复成功 info（工具名、id、原 args 预览）；无法修复 warning（同字段，
  预览长度上限 `INVALID_TOOL_CALL["log_args_chars"]`）。
- **trajectory**：经 `runtime.hooks.RECORD_TRAJECTORY_EVENT` 记一条错误事件
  （`code=invalid_tool_call`，字段对齐 ledger 现有 error 事件），让「这条调用没进去」
  在时间线上可见——而不是像今天这样留下一条**没有结果的 tool_start**。

### 1.3 P1：无法修复时的重发（复用已证模式）

`MaxTokensBoostMiddleware` 已证明这套动作在本仓库可行：在 wrap 内**重调 handler**、
重调前**剥离 LangChain callbacks**（第一轮 token 已上线，不重复推流）、Agent 循环只见
最终结果（`agent/middlewares/max_tokens_boost/core.py` 文件头）。本层同法：

- 条件：P0 处理后仍 `invalid_tool_calls` 非空 **且** `tool_calls` 为空——即「回合将被
  终止」这一唯一需要挽救的情形（有合法调用可跑时不必重发）；
- 重发时把一条纠正 SystemMessage 追加进**本次重发的请求**
  （`request.override(messages=[*request.messages, SystemMessage(...)])`，支持项已核对；
  **不进 state、不落库**），内容含：解析错误、原始 args 片段、「重新发出该调用，参数必须是
  合法 JSON（字符串加引号、内部引号转义）」；
- 重试上限 `INVALID_TOOL_CALL["resend_max_retries"]`（默认 2）；仍失败 → 保留今天的行为
  （回合结束）+ warning；
- **验收观察点**：客户端视图一致性——第一轮 token 已流、重发不推流（与截断场景同一
  行为）；需实测确认文本/工具卡表现可接受，必要时由 P2 处理。

### 1.4 P2（可选）：用户可见提示

放弃修复（进入终答）时，把一行 `[marker]` 文本注入终答内容——沿用
`OutputRepetitionGuard` 的前端已识别标记先例，用户与模型下一轮都能看到「有一个工具调用
因 JSON 非法被丢弃」。

## 5. 边界与不做的事

- **不做通用 JSON 容错库**：不加依赖；quote-only 保守修复，含糊即拒绝。
- **不重解释语义**：修复值与原文逐字节一致是硬条件；任何"猜"一律走 P1 重发或放弃。
- **不改 ToolNode/路由**：无效调用在到达图之前被处理；路由语义保持 langgraph 原样。
- **unknown 工具名不在此列**：它不进 `invalid_tool_calls`，已走工具错误路径回给模型。
- **P2 之外的 UI**：不做专门的聊天卡片/通知面板（消息内 marker 已满足"可见"）。

# 计划：对齐 openclaw 多用户模型 + 一用户多 cell 切换

- 日期：2026-11-17（r2，加 openclaw 对齐）
- 状态：**待评审**
- 定位：两步升级——(1) 一个 cell 服务多个用户（openclaw 信任域模型），(2) 一个用户切换多个 cell。从 1:1:1 升级为 N:N。
- 风险等级：**低→中** — 步骤 1 改 1 行 schema（~1 小时），步骤 2 加关联表 + 前端 switcher
- 依赖：P2 已落地（Ingress + Fleet manager + per-user cell）
- 参考：openclaw `docs/gateway/multi-tenant-hosting.md`——"one Gateway = one trust domain, multiple named operators, shared workspace"

---

## 0. 两步升级

| 步骤 | 改什么 | 代价 | 效果 |
|------|--------|------|------|
| **步骤 1：多用户共享 cell** | `users.tenant_id` 去掉 `UNIQUE`（1 行 DDL） | ~1 小时 | alice 和 bob 登录不同账号，路由到同一个 cell，共享 sessions/memory/skills |
| **步骤 2：一用户多 cell 切换** | 加 `user_tenants` 关联表 + active tenant cookie + 前端 switcher | ~3 天 | alice 关联 cell-A 和 cell-B，前端下拉切换 |

步骤 1 是步骤 2 的基础——先支持多用户共享一个 cell，再支持一个用户访问多个 cell。两步独立可验收。

## 1. 步骤 1：多用户共享 cell（openclaw 对齐）

### 1.1 改动

**文件**：`fleet/store.py:26`

```sql
-- 修复前
tenant_id TEXT NOT NULL UNIQUE,

-- 修复后
tenant_id TEXT NOT NULL,
```

去掉 `UNIQUE`。`username` 保持 `UNIQUE`（登录仍按 username 查）。

**SQLite 迁移**：SQLite 不能直接 DROP column constraint，需 table-swap：
```sql
CREATE TABLE users_new (...同上但不带 UNIQUE on tenant_id...);
INSERT INTO users_new SELECT * FROM users;
DROP TABLE users;
ALTER TABLE users_new RENAME TO users;
CREATE INDEX idx_users_username ON users(username);
```

**文件**：`fleet/store.py:140` — 更新错误消息

```python
# 修复前
raise ValueError("username or tenant_id already exists")
# 修复后
raise ValueError("username already exists")  # tenant_id 不再 UNIQUE，不会冲突
```

### 1.2 为什么不需要改 cell

cell（Sherry server）已经是"一个信任域，共享数据"的盒子：
- `auth_account CHECK(id=1)`——单账户，loopback 调用豁免
- 所有 session/memory/todo 表按 `session_id` 分（无 `user_id` 列）——共享是默认行为
- Ingress 通过 loopback + gateway_token 连接 cell，cell 不知道也不关心是哪个用户

这和 openclaw 完全一致——openclaw 文档明确说"one Gateway = one trusted operator domain, shared workspace, collaboration guardrails rather than tenant isolation"。

### 1.3 改后的行为

```
Ingress users 表：
  alice → tenant_id="team-a"
  bob   → tenant_id="team-a"   ← 同一个 cell
  carol → tenant_id="team-b"   ← 另一个 cell

alice 和 bob 登录不同账号 → JWT 都带 tenant_id="team-a" → 路由到同一个 cell
  → 共享 sessions / memory / todos / skills / persona / project_dir
  → 不共享 Ingress 登录凭据（各自的 username/password）
```

### 1.4 Admin CLI

```bash
# 创建 cell
python -m fleet create --tenant team-a

# 创建两个用户关联同一个 cell
python -m fleet user-add --username alice --password *** --tenant team-a
python -m fleet user-add --username bob   --password *** --tenant team-a   ← 现在可以了
```

### 1.5 验收

- alice 和 bob 用各自账号登录 → 都路由到 team-a cell
- alice 创建的 session，bob 能看到并继续（共享）
- alice 改密码不影响 bob（凭据独立）
- carol 登录 → 路由到 team-b cell → 看不到 team-a 的数据

## 2. 步骤 2：一用户多 cell 切换

### 2.1 Schema：加 `user_tenants` 关联表

**文件**：`fleet/store.py`

```sql
-- users 表去掉 tenant_id 列（或保留为 nullable 做 back-compat）
CREATE TABLE users (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    username TEXT NOT NULL UNIQUE COLLATE NOCASE,
    password_hash TEXT NOT NULL,
    role TEXT NOT NULL DEFAULT 'user',
    created_at INTEGER NOT NULL
    -- tenant_id 列删除
);

-- 新增多对多关联
CREATE TABLE user_tenants (
    user_id INTEGER NOT NULL,
    tenant_id TEXT NOT NULL,
    role TEXT NOT NULL DEFAULT 'owner',  -- owner / member
    is_default INTEGER NOT NULL DEFAULT 0, -- 用户的默认 cell
    created_at INTEGER NOT NULL,
    PRIMARY KEY (user_id, tenant_id),
    FOREIGN KEY (user_id) REFERENCES users(id)
);
CREATE INDEX idx_user_tenants_tenant ON user_tenants(tenant_id);
```

`store` 新增方法：
- `list_user_tenants(user_id) -> list[dict]` — 返回用户关联的所有 cell（含 role / is_default）
- `add_user_tenant(user_id, tenant_id, role, is_default)` — admin 授权用户访问一个 cell
- `remove_user_tenant(user_id, tenant_id)` — 撤销访问
- `get_user_by_username(username)` — 返回 user row（不含 tenant_id，tenant 列表单独查）

### 2.2 active tenant 用独立 cookie

不在 JWT 里放 active tenant（避免每次切换都重签 token + 断 WS）。用一个独立的短期 cookie：

**文件**：`fleet/security.py`

```python
ACTIVE_TENANT_COOKIE = "sherry_tenant"

def set_active_tenant_cookie(response, tenant_id: str):
    response.set_cookie(
        ACTIVE_TENANT_COOKIE, tenant_id,
        httponly=True, samesite="Lax",
        max_age=86400 * 30,  # 30 天
        path="/"
    )
```

JWT claims 改为携带**可用 tenant 列表**（不是单个）：
```python
def _claims(user, tenants: list[str], *, kind, ttl, issuer):
    return {
        "sub": str(user["id"]),
        "username": user["username"],
        "tenants": tenants,       # 列表，不是标量
        "role": user.get("role", "user"),
        ...
    }
```

### 2.3 proxy 按 active tenant cookie 路由

**文件**：`fleet/ingress.py:proxy`

```python
async def proxy(request):
    claims = request.get(CLAIMS_KEY) or {}
    available_tenants = claims.get("tenants", [])

    # 从 cookie 读 active tenant
    active = request.cookies.get(ACTIVE_TENANT_COOKIE, "")
    if not active:
        # fallback：用户的默认 tenant
        active = await store.get_default_tenant(claims["sub"])

    # 验证 active tenant 在可用列表中
    if active not in available_tenants:
        return _json(403, {"error": "tenant_not_authorized"})

    cell = await store.get_cell(active)
    if cell is None:
        return _json(503, {"error": "cell_unavailable"})

    # 反代到 cell（同现有逻辑）
```

WS proxy 同理——从 cookie 读 active tenant。

### 2.4 切换 tenant 的 API

**文件**：`fleet/ingress.py`

新增端点：
```
POST /auth/tenant  body: {"tenant_id": "alice"}  → 设 active tenant cookie
GET  /auth/tenants  → 返回用户的可用 cell 列表
```

`POST /auth/tenant` 逻辑：
1. 验证 `tenant_id` 在 JWT 的 `tenants` 列表中
2. `set_active_tenant_cookie(response, tenant_id)`
3. 返回 `{ok: true, tenant_id: "alice"}`

`GET /auth/tenants` 逻辑：
1. 从 JWT 读 `tenants` 列表
2. 对每个 tenant 查 `get_cell(tenant)` 获取 cell 状态（running/stopped）
3. 返回 `[{tenant_id, role, cell_status, is_default}, ...]`

### 2.5 登录时设默认 tenant

**文件**：`fleet/ingress.py` `login` handler

登录成功后：
1. 查 `list_user_tenants(user_id)` 获取可用 cell 列表
2. 如果只有一个 → 直接设为 active tenant
3. 如果有多个 → 设 `is_default=True` 的为 active tenant
4. 如果没有 → 返回错误（用户未关联任何 cell）
5. JWT 里放 `tenants` 列表 + active tenant cookie

const tenants = ref<TenantInfo[]>([])

async function switchTenant(tenantId: string) {

## 3. 迁移

### 现有数据

`users` 表当前有 `tenant_id` 列。迁移步骤：

1. 创建 `user_tenants` 表
2. 从 `users.tenant_id` 迁移数据：`INSERT INTO user_tenants (user_id, tenant_id, role, is_default) SELECT id, tenant_id, 'owner', 1 FROM users`
3. `users.tenant_id` 列保留（nullable，back-compat）或删除（如果所有代码都已改）

不需要停机——迁移脚本在 Ingress 启动时自动执行（同现有 `init_store` 的 schema 初始化）。

### JWT 兼容

旧 JWT 带单个 `tenant_id`（标量），新 JWT 带 `tenants`（列表）。`decode_token` 兼容两种：
```python
tenants = claims.get("tenants")
if tenants is None:
    # 旧 token 兼容
    single = claims.get("tenant_id")
    tenants = [single] if single else []
```

旧 token 在 refresh 时自动升级为新格式。

## 5. 测试

### 步骤 1

| 场景 | 预期 |
|------|------|
| 两个用户关联同一 cell | 都路由到同一 cell，共享 sessions/memory |
| 两个用户关联同一 cell，各自改密码 | 互不影响（凭据独立） |
| 两个用户关联不同 cell | 互相看不到对方数据 |

### 步骤 2

| 场景 | 预期 |
|------|------|
| 用户关联 1 个 cell | 登录后自动设为 active，不显示 switcher |
| 用户关联 2 个 cell | 登录后设默认 cell，顶栏显示 switcher |
| 切换 cell | `POST /auth/tenant` → cookie 更新 → 页面 reload → 数据变为新 cell |
| 切换到未授权 cell | `POST /auth/tenant` → 403 |
| 旧 JWT（单个 tenant_id） | 兼容，refresh 后升级为列表 |
| cell 停止后切换 | `GET /auth/tenants` 显示 cell_status=stopped，切换后 503 |
| admin 撤销 cell 访问 | 下次请求时 JWT 验证失败（tenant 不在列表）→ 需重新登录 |

## 6. 不做的事

- ❌ 不在 cell 内做 per-user session 隔离（步骤 1 的共享是 openclaw 模型——同信任域内共享 workspace）
- ❌ 不做 tenant 内的 user 角色权限（owner/member 区分只在 admin CLI 层，cell 内部不感知）
- ❌ 不做 tenant 级配额/计费（未来需求）
- ❌ 不做 self-service 注册 cell（cell 创建仍是 admin CLI）

## 7. Kill criteria

- 如果 active tenant cookie 方案在 WS 长连接场景下有问题（WS 建立后切换 tenant 不断连），改为切换时强制断开所有 WS + reload
- 如果 `user_tenants` 多对多关联在实际使用中过于复杂（大部分用户只用 1 个 cell），退化为 `users.tenant_id`（单值，步骤 1 去掉 UNIQUE 后可多用户共享）+ admin 手动改绑——不支持切换，只支持改绑
- 步骤 1 可独立落地，步骤 2 可无限 defer——步骤 1 已经实现了 openclaw 对齐

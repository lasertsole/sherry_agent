## 一、严重（High）

### H1. [Strategy/Factory Method] `reasoning_payload` 的 provider/format 分发用长 if/elif 链
- **违反模式**：Strategy / Factory Method
- **位置**：`models/LLMs/reasoning_payload.py:264-292`、`:448-489`、`:534-570`
- **问题**：`resolve_thinking_format`、`_wire_payload`、`_native_thinking_kwargs` 都用一长串 `if provider == "deepseek" / elif provider in (...) / elif == "dashscope" / elif == "openrouter" / elif == "together" / elif == "baseten"` 以及 `if thinking_format == OPENAI.value: ... elif == DEEPSEEK.value: ...` 分发同一概念（"哪个 provider 怎么编 wire payload"）。`_OPENAI_COMPATIBLE` 集合与 if/elif 必须手动保持同步。
- **应如何做**：每个 `ThinkingFormat` 是一个对象（带 `wire_payload(value)`、`level_map` 字段），新增 provider 只需注册一个对象而不是再插三条 elif。当前新增 provider 必须改三处函数，违反开闭原则。
- **严重性**：high

### H2. [Strategy] 结构化输出降级用整数等级 `strategy_level` 0/1/2 选择算法
- **违反模式**：Strategy
- **位置**：`agent/tools/subagent/spawn/core.py:2363,2372,2380,1919`（配合 `agent/tools/subagent/model_caps.py:42-43`）
- **问题**：`strategy_level` 是 int（0=LangChain 原生 structured output，1=自行发送 `response_format={"type":"json_object"}`，2=关 thinking）。行为通过散落多处的数值阈值判定：`strategy_level >= 1`（2363 绑定 response_format）、`>= 2`（2372 关 thinking）、`>= 1 ... validate_structured_output`（1919）。`level_label` 用 dict 把 int 映射回字符串名，是 Strategy 退化的典型信号。
- **应如何做**：三档降级各是一个 Strategy 对象（封装 `apply_build(llm)` 与 `validate(result)`），而非魔法整数 + `>=1`/`>=2` 阈值分散在 4 个调用点。
- **严重性**：high

### H3. [State] 子代理投递状态机用 enum + 散落 free function，无转换守卫
- **违反模式**：State
- **位置**：`agent/tools/subagent/registry/delivery_state.py:49-128`（状态枚举定义在 `types/registry.py:27`）
- **问题**：`DeliveryStatus` 有 PENDING/IN_PROGRESS/DELIVERED/FAILED/SUSPENDED/DISCARDED 等状态。转换通过 `mark_delivery_pending`/`mark_delivery_in_progress`/`mark_delivery_delivered`/`mark_delivery_failed`/`mark_delivery_suspended`/`mark_delivery_discarded` 等平级 free function 实现，每个都直接 `model_copy(update={"status": ...})` 盲写状态。转换合法性被分散到 `should_retry_delivery`(133)、`should_discard_delivery`(147)、`is_delivery_terminal`(36) 等查询函数。任意调用方可从任意状态调任意 `mark_*`（如 DISCARDED→DELIVERED 不会被阻止）。
- **应如何做**：每个状态成为 State 对象，封装自身允许的后继状态与守卫。状态机完整性不应靠调用方自律维持。
- **严重性**：high

### H4. [Builder] `spawn_subagent_direct` 用 22 个位置/关键字参数构造一次 spawn
- **违反模式**：Builder
- **位置**：`agent/tools/subagent/spawn/core.py:597-620`
- **问题**：22 个参数（task、requester_session_key、agent_id、task_name、label、thinking、cleanup、attachments、cwd、completion_owner_key、expects_completion_message、run_timeout_seconds、swarm_group_id、output_schema、model、launch_fingerprint、goal_max_turns、functional_role_hint、extra_tools、isolation、flow_id、step_id），参数之间存在强耦合的可选组（isolation 需要 cwd；output_schema 影响系统提示；flow_id/step_id 必须成对）。函数体直接按顺序喂给 12 个 `_phase` 辅助函数。调用点（`sessions_spawn.py:155`、taskflow dispatch）必须逐个对位传，新增字段要同时改签名、调用方、schema、`SpawnResult`。

- **严重性**：high

### H5. [Strategy] `_LazyReranker` 每个方法用 `if self._local:` 重新分发后端
- **违反模式**：Strategy
- **位置**：`models/reranker_model/__init__.py:59-91`

### H6. [Observer] `taskflow_wait_all` 用忙轮询等待子代理完成，而非订阅完成事件
- **违反模式**：Observer

- **问题**：`while True:` 循环，每次 `await asyncio.sleep(interval)` 后调用 `_settled(child_key)` 查注册表判断子 run 是否还活着，直到全部 settled 或超时。仓库已存在事件机制 `register_yield_event`/`wake_yield_if_all_children_settled`（`registry/yield_events.py`，被 `sessions_yield` 工具使用），该模块 docstring 自承"deliberately does NOT reuse the session-wide yield event"是因为粒度不匹配——但这恰恰说明应有一个 flow 作用域的 Observer 订阅 API，而非退化为轮询。

### H7. [上帝文件] `spawn/core.py`（2481 行，~35 个顶层函数）

## 五、优先重构建议

按"影响 × 改动收敛性"排序：

1. **H4 + H7 + L7 + M1（spawn 系列）**：`spawn_subagent_direct` 的 22 参数 → `SpawnRequest` dataclass；`spawn/core.py` 按职责拆分；`build_subagent_system_prompt` Builder 化；`SessionsSpawnTool._arun` 收敛。四者根因相通，应作为一组重构，一次性收束 spawn 调用链的可维护性。

2. **M11 + M13 + M10（middleware 双链）**：单表声明 `MiddlewareSpec(name, factory, position, profiles={main,child})`，主/子链由同一表派生，`_MAIN_REQUIRED`/`_SUBAGENT_REQUIRED`/`catalog.py` 全部从表生成。一次性消除 Shotgun Surgery + Template Method 重复 + Decorator 装配硬编码三个问题。

3. **H1 + H5 + M2 + M6（Strategy 系列）**：reasoning_payload provider 链、reranker local/cloud 分发、embedding backend 分发、thinking level kwargs——四处 if/elif 统一改为构造期注入 Strategy 对象。新增 provider/backend 时改动面最大、最易遗漏，优先处理。

4. **H3 + M9（State 系列）**：delivery 状态机与 taskflow step 状态机封装为 State 对象 + 集中转换守卫，消除"任意路径写任意状态"的完整性风险。

5. **H6 + M7 + M8（Observer 系列）**：taskflow_wait_all 忙轮询、sweeper 周期轮询、auto_turn idle 轮询——三处改为事件订阅 + 保底低频轮询，消除固定延迟与空转开销。

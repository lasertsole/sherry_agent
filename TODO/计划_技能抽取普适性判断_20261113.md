# 计划：技能抽取的任务级普适性预判断

- 日期：2026-11-13
- 状态：**待评审**
- 来源：用户要求"技能抽取时也要判断技能是否具备普适性而选择抽不抽取" → 调查发现 skill review 无预过滤 + `reusable` 判断对象错位
- 风险等级：**低** — 加轻量预判断函数 + 1 次 auxiliary LLM 调用；不动 review agent prompt、不动 judge 逻辑
- 依赖：无
- 关联：no-op 重试 bug（`reusable=False` 导致正确 no-op 被重试到耗尽）已记入 `TODO/代码审计风险项_20261109.md` M30，本计划不重复修复，仅做预判断减少不必要的 review agent 调用

---

## 0. 问题

### 0.1 无预过滤

`maybe_trigger_skill_review`（`skill_review_runner.py`）在 plan 完成时**无条件触发** skill review。唯一的 gate 是 feature flag + in-flight lock + once-per-cycle fingerprint + failure cooldown。没有任何内容/普适性检查。一个"修 README 拼写错误"的一次性任务和"搭建项目 CI/CD 流水线"的通用任务走完全相同的路径。

### 0.2 `reusable` 判断的是 skill 内容不是任务

judge prompt 的 `reusable` 定义："class-level guidance useful beyond this one plan. Reject plan IDs, session artifacts, one-off task narratives, and environment setup failures."

这判断的是**产出的 skill 内容**是否可复用，不是**原始任务**是否可泛化。判断对象错位——一个高度具体的一次性任务可能产出看似可复用的 skill 片段，但触发价值极低。

> **no-op 重试 bug**：`reusable=False` 导致正确的 no-op 被重试到耗尽（~10-20 次 LLM 调用浪费），已记入审计风险项 M30，独立修复。本计划聚焦预判断，减少一次性任务触发 review agent 的次数。

---

## 1. 设计

### 1.1 任务级普适性预判断

在 `_run_skill_review` 中，**构建 review agent 之前**，加一个轻量 LLM 预判断。

位置：`_run_skill_review` 在 `_build_plan_context` 之后、agent 创建之前（约 line 2070）。

```python
# 新增：任务级普适性预判断
plan_context = _build_plan_context(...)
if not plan_context:
    return

# 预判断：这个 plan 的任务是否有普适性，值得花 review agent 调用吗
generalizable = await _judge_task_generalizability(plan_context)
if not generalizable.should_extract:
    logger.debug(f"Skipping skill review: task judged non-generalizable — {generalizable.reason}")
    # 记录 hash 防止下轮重复预判断
    _record_skill_review_outcome(session_id, snapshot_hash, outcome="skipped_non_generalizable")
    return
```

`_judge_task_generalizability` 实现：

```python
async def _judge_task_generalizability(plan_context: dict) -> _GeneralizabilityVerdict:
    """Lightweight pre-check: is this plan worth a full skill review?
    
    One auxiliary LLM call with a short prompt — much cheaper than the full
    review agent (2-5 turns) + judge (1 call) that it replaces.
    """
    # 提取精简输入：goal + step 摘要（不含完整 evidence/handoff）
    goal = plan_context.get("plan_content", "")[:1000]
    step_summaries = [
        {"id": t.get("step_id"), "task": t.get("content", "")[:200]}
        for t in plan_context.get("todos", [])[:10]
    ]
    
    prompt = f"""Judge whether this completed plan likely contains reusable class-level knowledge
worth extracting into a skill. Answer ONLY with JSON.

## Plan goal
{goal}

## Steps
{json.dumps(step_summaries, ensure_ascii=False)}

Return: {{"should_extract": true|false, "reason": "one sentence"}}
- false: one-off fix, environment setup, project-specific config, typo fix, specific bug in specific file
- true: reusable procedure, pattern, workflow, toolchain knowledge that applies beyond this one task
"""
    llm = build_auxiliary_llm(temperature=0)
    response = await llm.ainvoke([SystemMessage(...), HumanMessage(content=prompt)])
    return _parse_verdict(response)
```

设计要点：
- **1 次 auxiliary LLM 调用**（短 prompt，无工具），远比 review agent（2-5 轮带工具）+ judge（1 轮）便宜
- **输入精简**：只给 goal + step 摘要，不给完整 evidence/handoff/feedback → token 成本低
- **判断对象是任务**，不是 skill 内容——这正是 0.3 指出的"判断对象错位"的修复
- **should_extract=false 时直接返回**，不创建 review agent，不跑 judge——省掉整个 review 循环
- **should_extract=true 时继续现有流程**——review agent + judge 照常跑，judge 的 `reusable` 仍作为 skill 内容的 post-hoc 质量门

### 1.2 预判断的 hash 记录

和现有的 `_SKILL_REVIEW_FIRED_KEY` / failure cooldown 机制对齐：

- 预判断返回 `should_extract=false` → 记录 snapshot_hash + outcome=`skipped_non_generalizable`
- 下次同一 snapshot_hash 的 plan 完成 → `_detect_todo_all_complete` 的 fingerprint 检查会跳过（已有机制）
- plan 内容变了 → fingerprint 不同 → 重新预判断

### 1.3 不做的事

- **不加纯启发式预过滤**（检查文件路径/步骤数/goal 长度）——太脆弱，误判率高，不如 1 次 LLM 调用准确
- **不改 review agent 的 prompt**——agent 的 rule 7 已经说了"不要捕获一次性任务叙事"，问题不在 agent 的指令，在于 judge 的 passed 逻辑
- **不加 `task_generalizable` 到 judge 输出**——预判断已经覆盖了任务级判断，judge 继续专注 skill 内容质量

## 3. 测试

| 场景 | 预期行为 |
|---|---|
| 一次性任务（"修 README 拼写"） | 预判断 `should_extract=false` → 不创建 review agent → 0 次 review LLM 调用 + 0 次 judge 调用 |
| 通用任务（"搭建 CI/CD 流水线"） | 预判断 `should_extract=true` → 正常跑 review agent + judge |
| 预判断 LLM 调用失败 | fail-open：`should_extract=true`（继续现有流程，不因预判断故障跳过） |
| 同一 plan 再次完成（内容不变） | fingerprint 命中 → 不重复预判断 |

## 4. 成本对比

| 场景 | 修复前 | 本计划（预判断） | 配合 M30 修复后 |
|---|---|---|---|
| 一次性任务 | `max_attempts` × (2-5 agent + 1 judge) ≈ 10-20 次 | **1 次**（预判断） | 1 次（预判断） |
| 通用任务，skill 可复用 | ~3-6 次 | ~4-7 次（+1 预判断） | ~4-7 次 |
| 通用任务，无普适 skill（no-op） | ~10-20 次（no-op 重试到耗尽） | ~4-7 次（预判断通过 + 1 轮 no-op + judge） | ~4-7 次（M30 修复消除重试） |

> M30（no-op 重试 bug）独立修复后，本计划的预判断仍值得做：一次性任务从 ~10-20 次降到 1 次（预判断直接跳过），而非 M30 修复后的 ~4-7 次（仍需跑 1 轮 review agent + judge 才能产出 no-op）。

## 6. Kill criteria

- 若预判断的准确率不足以区分一次性/通用任务（人工抽检误判率 > 30%），退化为不做预判断——M30 的 no-op 重试修复本身已消除重试浪费（从 ~10-20 次降到 ~4-7 次），预判断是进一步优化
- 若预判断的 1 次 LLM 调用成本在大多数场景下超过了它省掉的 review agent 成本（即大多数 plan 都是通用的、都会触发 review），考虑加纯启发式预过滤（检查 goal 中是否含具体文件路径/session ID）作为零成本前置层

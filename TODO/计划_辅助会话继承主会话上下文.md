# 计划：辅助会话继承主会话上下文

- 建档日期：2026-10-24
- 状态：**待评审 / 未开工**
- 触发问题：从主会话选中内容打开“辅助会话”后，辅助会话的历史是空的。它只拿到选中文本，无法回答“主会话前面聊了什么”“这个结论怎么来的”这类解释性问题。
- 目标：辅助会话仍然是一个独立的普通会话、侧栏历史仍从空开始，但**模型**在创建时继承主会话已完成的对话快照，并明确知道自己只是解释/追问，不接手主会话任务。

## 0. 结论先行

1. 当前行为不是“辅助会话”该有的语义：它只是复制了主会话的预设、角色、agent config 和项目目录，**没有复制任何对话上下文**，所以模型只能看到选中文本。
2. ZCode 的 selection side chat 不是空会话：它在创建时把父会话的已完成消息作为 **model-only / UI-hidden** 的历史复制进 child，再追加一条边界提示。child 的可见历史仍然从空开始，模型却能看到父会话。
3. 推荐 sherry 采用同样的模型：**创建时快照父会话 → 写入 child checkpoint → UI 不显示继承消息 → 加一条“仅参考、不接手任务”的边界消息**。保留 sherry 现在“辅助会话是普通可见会话”的产品选择，不改成 ZCode 的隐藏 child 类型。
4. 不要一次性把父会话全文塞进每轮用户消息；快照只做一次，后续轮次靠 child 自己的 checkpoint 保留。

## 1. ZCode 的做法（已核实）

参考代码在 `ZCode/apps/zcode-cli/packages/core/src/runtime/methods/session-fork.ts`：

- `createSelectionSideConversation()` 不是创建一个空 child，而是调用 `commitAtomicConversationFork(..., kind: "selection_side_chat")`。
- `selectionSideChatHistoryMessages()` 以父会话的 **stable persisted boundary** 截断：父会话正在生成时，只保留已提交的 real-user 输入，排除该轮尚未提交的 assistant/tool 增量。
- `commitAtomicConversationFork()` 把父消息 clone 到 child，并把每条消息标成：
  - `visibility: "model-only"`
  - `semantics.uiVisibility: "hidden"`
  - `semantics.providerVisibility: "visible"`
  所以 child 的 UI 历史为空，但模型请求里能看到父会话。
- 最后追加一条 synthetic `selection_side_chat` 边界消息：

  > The preceding conversation was inherited from the parent task for reference only.
  > Do not continue the parent's active work automatically; answer only new questions sent in this side chat.
  > Modify the workspace only when the user explicitly asks you to do so in this side chat.

- 选中文本本身走另一条路：`conversation-quotes.ts` 的 `withConversationQuotes()` 把引用格式化成 `<conversation_quote>...</conversation_quote>`，不混进 canonical 用户正文；UI 通过 `dispatchConversationSelectionAdd` 把 reference 加到 child，下一次输入时再转成模型材料。
- UI 创建命令见 `ZCode/apps/zcode-cli/packages/bootstrap/src/zcode-protocol-v4/commands/handlers/selection-side-session.ts` 和 `packages/ui/src/v4/SessionPane.tsx`。

ZCode 的 child 还是 `taskType: selection_side_chat` 的隐藏 child，不出现在普通 root session 列表；sherry 现在选择让辅助会话出现在普通会话列表里（可恢复历史），这个差异保留。

## 2. 当前 sherry 的差距

- `client/app/composables/use-side-chat.ts`：
  - `crypto.randomUUID()` 新建普通 session；
  - 只复制 preset binding、character snapshot、agent config、project directory；
  - 注释明确写着 “The conversation itself starts empty”。
- `SideChatPanel.vue` 用这个 session 自己的 socket、history、approvals 和 `useChatStream`；选中文本只进入 composer 的 quote chip。
- 后端 `pub/func/build_agent_config.py` 用 `rand_str_to_int(session_id)` 作为 `thread_id`；child 的 checkpoint 是空的，所以模型完全不知道父会话。
- 当前 message store / checkpointer 都能存 child 的消息，但没有“父上下文只在模型里可见、UI 不显示”的概念。

## 3. 推荐方案：创建时模型上下文快照

### 3.1 数据流

1. 用户在消息选择菜单点“在辅助会话中提问”。
2. 前端调用新的服务端接口（建议 `POST /sessions/side_chat`）：
   - 入参：`parent_session_id`、占位 `title`；
   - 服务端生成 child `session_id`（不再由前端 `crypto.randomUUID()` 决定）；
   - 读取父会话的**已完成对话快照**；
   - 写入 child checkpoint（只写消息，不写父会话的 plan / todo / taskflow / HITL / 权限状态）；
   - 记录 child → parent 的关联；
   - 返回 child `session_id`。
3. 前端拿到 child id 后继续现在的 Dexie 复制逻辑（preset / character / agent config / project dir），打开侧栏 tab，把 parent id 一并放进 tab payload。
4. 用户在辅助会话里发送第一句（composer 已带 quote chip）；模型请求里已经有父会话快照 + 边界消息 + 引用文本。
5. 辅助会话 UI 仍然从空历史开始；后续轮次只显示 child 自己的消息。

### 3.2 快照来源与边界

优先使用**已持久化的消息**，而不是父会话正在流式生成的内存态：

- 从父会话的 message store 读取按 turn 排序的已完成消息；或者使用 `agent/state_port.py::read_messages(parent_id)` 读取模型视图，再显式剔除未完成 turn。
- 父会话正在跑时，只保留该轮已提交的 real-user 消息之前的内容；不复制尚未完成的 assistant/tool 增量，避免把半截回答带进 child。
- 过滤掉内部提醒/注入消息（`metadata.internal`、`provenance` 为内部来源、project dir / git head notice 等）；保留 user / assistant / tool 对话本身。
- 不复制父会话的 `plan_status`、todo、TaskFlow flow、HITL interrupt、权限/yolo 状态。child 的 checkpoint 只带 `session_id` + 消息 + 边界提示。

### 3.3 写入 child checkpoint

建议在 `agent/state_port.py` 增加一个领域函数，例如：

```python
async def seed_side_chat_context(
    child_session_id: str,
    messages: list[BaseMessage],
) -> bool
```

- 用 `built_agent()` / `agent_lease()` 拿当前图，`graph.aupdate_state(build_agent_config(child), {...})` 写入初始状态。
- 每条继承消息加 `additional_kwargs["side_chat_context"] = True`，用于持久化过滤（见 3.4）。
- 最后追加一条边界消息（HumanMessage，`metadata.internal=True`，`provenance="side_chat_context"`），文本为：

  > 以上内容是主会话的历史上下文，仅供理解用户引用的内容。
  > 不要自动继续主会话正在进行的任务；只回答辅助会话里新提出的问题。
  > 除非用户明确要求，不要修改工作区。

- 如果写入失败，辅助会话仍然创建成功但上下文为空（fail-open），并在侧栏提示“未能继承主会话上下文”。

### 3.4 不让继承内容污染 UI 历史

继承消息只存在于 checkpoint，不写入 child 的 message store。为此：

- 在 `agent/middlewares/message_persistence/prepare.py::_is_persistable()` 里跳过带 `side_chat_context` 标记的消息。
- 这样 `MessagePersistence` 在 child 第一次 `after_model` 时不会把父消息写进 child 的 `messages` 表；`GET /get_history_by_turn_page` 仍然只返回 child 自己的消息，侧栏保持空白。
- 如果未来需要“查看继承上下文”的调试入口，可以另做只读接口，不要复用 chat history。

### 3.5 上下文预算

父会话可能很长。新增 `config/features/agent_side/side_chat.py`（`SIDE_CHAT`）：

- `inherit_context: bool = True`
- `context_max_tokens: int`（建议 16_000 起步）
- `context_max_messages: int`（建议 80）
- 截断时从最旧消息开始丢，保留最近一轮和选中文本所在 turn；在快照前插入一条“更早的主会话历史已省略”的提示（同样 model-only）。
- 用 `pub.func.estimate_tokens.estimate_messages_tokens` 做预算，避免把几 MB tool 输出整个复制进 checkpoint。

### 3.6 引用文本

- MVP 保留现有 quote chip → markdown blockquote；第一轮用户消息已经带引用。
- 后续可补 ZCode 式的结构化引用：发送时把 quote 作为 `<conversation_quote>` 附加材料，不进入 canonical 用户正文；这不影响本轮上下文继承方案。

## 4. UI 提示

侧栏辅助会话仍然从空历史开始，但要让用户知道“模型知道主会话”：

- `SideChatPanel` 的 header 或空状态显示一条小提示：
  - “已继承主会话上下文（创建时快照）”
  - tooltip：“只包含创建辅助会话时主会话已经完成的消息；主会话之后的内容不会自动同步。”
- tab payload 增加 `parentSessionId`（当前只有 `sessionId` / quote / source）。
- 如果继承失败，显示“未继承主会话上下文，仅使用当前引用”。
- 不需要在主会话列表里额外标记 parent；这是可选增强。

## 5. 实施步骤

### P0：后端快照与写入

- 新增 `SIDE_CHAT` feature 配置。
- 新增 `server/service/side_chat_service.py`：
  - 读父会话已完成消息（stable boundary）；
  - 过滤内部消息、裁剪预算；
  - 生成 child id、写 parent 关联；
  - 调 `agent.state_port.seed_side_chat_context()`；
  - 失败 fail-open。
- 新增 `POST /sessions/side_chat` 路由（gateway/auth 与现有 session 路由一致）。
- 在 `agent/state_port.py` 增加 seed 函数；在 `message_persistence/prepare.py` 增加 `side_chat_context` 跳过规则。

### P1：前端接入

- `client/app/composables/use-side-chat.ts`：改为调用 `POST /sessions/side_chat` 获取 child id，再执行现有 Dexie 复制。
- `[sid].vue` 的 `onSelectionSideChat` 把 `parentSessionId` 放进 sideChat tab payload。
- `SideChatPanel` 展示继承提示；失败时提示空上下文。
- 现有 `createSideChatSession` 的单元测试改为 mock 新 bridge；补 API 失败降级用例。

### P2：验证与收尾

- 后端单测：
  - 快照只含已完成 turn；
  - 内部提醒/HITL/plan/todo 不进入；
  - 预算截断与保留最近 turn；
  - `side_chat_context` 消息不被 MessagePersistence 写入 child message store；
  - 删除 child 只清自己的 checkpoint。
- 前端单测/集成：
  - 创建流程使用服务端 id；
  - 侧栏历史为空但显示继承提示；
  - quote chip 仍进入首条消息；
  - 继承失败仍能打开空辅助会话。
- E2E/真机：
  1. 主会话说一个只在历史里的事实（例如项目代号）；
  2. 选中一句打开辅助会话，问该事实；
  3. 回答正确，且侧栏历史里没有父会话气泡；
  4. 主会话继续新内容后，旧辅助会话不应自动知道；新建辅助会话应知道；
  5. 父会话正在流式生成时创建辅助会话，快照不包含半截 assistant/tool 输出。

## 6. 风险与取舍

- **上下文成本**：继承父会话会增加 child 首轮输入 token；用 `context_max_tokens` 限制，并保留最近内容。
- **快照过期**：辅助会话是创建时快照，主会话之后的内容不会同步；UI 必须说清楚。
- **隐私/安全**：父会话的 tool 输出可能含敏感内容；它只进入 child checkpoint，不出现在 child UI，不跨用户。child 仍是同一用户/同一工作区。
- **持久化副作用**：如果不加 `side_chat_context` 过滤，MessagePersistence 会把继承消息写进 child history，侧栏不再为空；这是本方案的关键测试点。
- **现有辅助会话**：不迁移，仍为空上下文；只有新建的辅助会话继承。若需要，可加“重新继承”按钮，但不属于第一版。
- **父会话删除**：child 是独立普通会话；父会话删除不应删除 child 的 checkpoint/history，只让 parent 关联悬空。
- **不要复制执行状态**：权限、plan、todo、TaskFlow、HITL 都是父会话的运行态，复制过去会导致 child 意外接手或阻塞。

## 7. 备选方案

| 方案 | 做法 | 优点 | 问题 |
|---|---|---|---|
| A. 创建时 checkpoint 快照（推荐） | 父消息 model-only 复制进 child checkpoint，UI 空 | 最接近 ZCode；后续轮次自然保留上下文 | 需要 seed/持久化过滤，改动中等 |
| B. 首轮 context pack | 第一轮用户消息前临时拼父会话摘要/转写 | 改动小，无需 checkpoint seed | 快照发生在首轮而非创建时；需要隐藏消息/持久化处理 |
| C. 父会话只读工具 | child 带 parent_session_id，模型按需读取父历史 | 不复制、适合超长历史 | 多一个工具和提示，模型不一定主动查 |
| D. 完整可见 fork | child UI 也显示父历史 | 实现直接 | 违背辅助会话“侧栏从空开始”的产品语义，且会误认为普通 fork |

推荐 A；如果只想最快验证，可先做 B，但需要同样解决“继承消息不进 UI 历史”的过滤问题。

## 8. 不做什么

- 不把辅助会话改成 subagent。
- 不复制父会话的权限、HITL、plan、todo、TaskFlow 运行态。
- 不把父会话消息写进 child 的可见 message store。
- 不做自动同步（主会话后续消息不会实时灌入已有辅助会话）。
- 不把选中文本和完整父历史混进同一段 canonical 用户正文；引用仍作为引用材料处理。

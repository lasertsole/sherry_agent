## 0. 先对齐口径，否则数字会互相打架

同一个漏洞在不同扫描器里计数不同，比较时必须先统一：

| 口径 | 数量 |
|---|---|
| GitHub 仓库告警（推送时回报） | 31（15 high / 12 moderate / 4 low） |
| `uv audit` advisory 记录数 | 17（本轮修复后） |
| **去重后唯一 CVE 数** | **9** |

差异来源有二：GitHub 按「依赖 × 告警」计数并自带自己的评级节奏；`uv audit` 把同一 CVE 在
OSV 下的两个 advisory ID（PYSEC-* 与 GHSA-*）各记一条。因此**「31」并不代表 31 个独立缺陷**，
真实独立缺陷是 9 个。

更重要的是：**9 个里有 5 个上游任何版本都没有修复版本**。这不是配置或排查不到位，
是补丁尚未发布。这类漏洞无法通过升级消除，只能记录暴露面并接受。

## 4. 复审约定

`.github/dependabot.yml` 的 `ignore` 一律使用**精确版本号**（`=x.y.z`）而非版本区间：

- 若用区间（如 `>=1.14.0,<2`），上游一旦发布修复版就会被区间吞掉，告警再也不会回来；
- 用精确版本号，则**任何一次依赖升级都会重新触发告警**，逼迫重新评估暴露面。

因此本文件第 2 节各条在对应包版本变动时必须复审，而非视为永久豁免。
`transformers` 未被 ignore，同样意味着它会在每周 Dependabot 扫描中持续出现——
这是有意为之的可见债务。

推送完成后，GitHub 仍回报「31 vulnerabilities（15 high / 12 moderate / 4 low）」，

**已确认落到 `main` 的事实**（可直接核验）：

- `origin/main:.github/dependabot.yml` 含 3 条 ignore（accelerate / diskcache / ragas）

**尚未发生、需等待的部分**：

- GitHub 的 Dependabot 数据库按自身节奏刷新，**不随 push 实时更新**，
  故其告警数在本次推送后不会立刻下降；
- `ignore` 规则要到**下一次 Dependabot 运行**才生效。

因此**当时无法验证 GitHub 侧的最终数字**，只能确认配置与 lock 已正确落地。
后续复审时应预期：`setuptools` 与三个被 ignore 的包从告警列表消失，
而 **`transformers` 仍在**——那是第 2.4 节刻意保留的可见债务，不是回归。

若下次推送时告警数**仍为 31 且 setuptools 仍在列**，那才是真问题，
应检查 ignore 规则的版本号是否已因依赖升级而失配。
（该判据的首次评估见 5.1：实际降到 30，**未触发**此告警条件。）

- 可能性一：Dependabot 数据库尚未完成整轮刷新，ignore 规则未对全部条目生效；
- 可能性二：降掉的是 `setuptools`（锁文件修复已生效），三个 ignore 包待下轮；

**判定方法**：下一次推送后若数字继续下降并趋近 27（31 − setuptools − 3 个 ignore 包），
即证实处置按预期生效；若停在 30 不动，则应改为排查 ignore 规则的**版本号是否已失配**
（精确版本锁定在依赖升级后必然失配，这是第 4 节约定的正常结果，而非配置错误）。

# 计划：宿主能力授权（Host Capability Authorization）— 插件/专家不持有模型密钥

- 日期：2026-11-12
- 状态：**待评审**
- 来源：借鉴同类工具的宿主能力授权机制；插件/专家不直接持有模型密钥，声明式申请宿主能力，运行时通过统一通道请求
- 风险等级：**中** —— 新增能力授权层 + 模型调用代理通道；不动现有 agent 主链路
- 关系：补 Python 三通道插件体系（插件调模型）+ 专家团模式（专家调模型）

---

## 0. 问题

Sherry 现状：插件/专家若要调 LLM（如文档解析插件要摘要、安全审查要判定），通常**自己配 API key**（环境变量/配置）。问题：
1. **密钥散布**——用户把模型 API Key 散进多个插件环境变量，难管理、易泄露
2. **无审计**——插件直接调模型，宿主不知道调了多少、调了什么
3. **无授权**——任何插件都能用用户的模型配额，无法按插件限制/计费
4. **无统一模型选择**——插件各自选模型，不能由宿主统一管控（如"插件只能用便宜模型"）

## 1. 设计

### 1.1 能力声明（manifest 级）

插件/专家在 manifest 声明需要的能力：

```json
// 插件 manifest
{
  "name": "my-plugin",
  "required_capabilities": [
    {
      "id": "host.llm.invoke.v1",
      "purpose": "document.summarize",
      "required": true,
      "reason": "Summarize parsed documents"
    }
  ]
}
```

```json
// 专家配置
{
  "name": "frontend-expert",
  "required_capabilities": [
    {"id": "host.llm.invoke.v1", "purpose": "code.review", "required": true}
  ]
}
```

### 1.2 运行时能力请求通道

插件/专家不直接调模型 API，通过**宿主能力通道**请求：

```python
# 插件/专家代码
result = await request_host_capability(
    capability="host.llm.invoke.v1",
    params={"messages": [...], "model": "deepseek-chat"},
    purpose="document.summarize"
)
```

宿主侧：
- `server/service/capability_service.py`：接收能力请求 → 转发到宿主模型服务 → 返回结果
- 密钥/模型选择/审计/授权全在宿主侧
- 插件/专家看不到密钥

### 1.3 授权 + 审计

- **授权分级**：
  - `host.llm.invoke.v1`：**默认批准 + 审计 + 配额**（低风险，但所有调用审计可见，配额可设）
  - `host.memory.write.v1`：**显式批准**（高敏，用户必须手动批准）
  - MVP 先做 llm.invoke（默认批准+审计+配额），memory.write 后置

### 1.4 与 Python 三通道计划的实施顺序（解决循环依赖）

D5 与三通道（A3）互相引用（manifest capabilities ↔ capability_service）。明确先后：
1. **A3 manifest 先落地 `capabilities` 字段**（声明式，空实现——插件声明但宿主不处理）
2. **D5 capability_service 后接**（宿主侧实现能力请求代理 + 审计 + 配额）
3. A3 的 PluginContext `request_capability` 方法先返回"未实现"stub，D5 落地后接入真实通道

### 1.4 能力类型（可扩展）

| 能力 ID | 作用 |
|---|---|
| `host.llm.invoke.v1` | 调 LLM（messages → response） |
| `host.llm.embed.v1` | 调 embedding（文本 → 向量） |
| `host.llm.rerank.v1` | 调 reranker |
| `host.memory.read.v1` | 读 MesMemory（受限） |
| `host.memory.write.v1` | 写 MesMemory（受限） |

MVP 先做 `host.llm.invoke.v1`（最高价值——密钥治理），其余后置。

## 2. 实施

| 步骤 | 内容 | 依赖 |
|---|---|---|
| 1 | 能力声明 schema（manifest 加 `required_capabilities`） | Python 三通道 manifest |
| 2 | `capability_service.py`：接收请求 → 转宿主模型 → 返回 | 现有 models/LLMs |
| 3 | 插件/专家 SDK：`request_host_capability()` 函数 | 步骤 2 |
| 4 | 授权 UI：设置面板批准/拒绝能力申请 | 步骤 1 |
| 5 | 审计日志：能力调用记录 | 步骤 2 |
| 6 | 配额（可选）：按插件 token/调用限制 | 步骤 5 |

## 3. 变更清单

| 文件 | 变更 |
|---|---|
| `server/service/capability_service.py` | **新建**：能力请求代理 + 审计 + 配额 |
| 插件/专家 manifest schema | 加 `required_capabilities` 字段 |
| `agent/tools/plugins/protocol.py`（三通道计划） | PluginContext 加 `request_capability` 方法 |
| 设置面板 | 能力授权管理（批准/拒绝/审计/配额） |

**不改**：agent 主链路、现有模型调用路径（主 agent 直接调模型不变，只有插件/专家走能力通道）。

---

## 4. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 能力通道增加延迟（多一跳） | loopback 本机；宿主侧直接调模型，延迟 <1ms |
| 插件不声明就偷偷调模型 | Native 信任制（文档明确）；Process 隔离（无密钥环境变量，拿不到 key） |
| 授权 UI 繁琐 | 默认批准 `host.llm.invoke.v1`（低风险）；高敏能力才显式批准 |

### Kill criteria

- 若插件生态未成规模（用户少用第三方插件），能力授权后置（主 agent 直接调模型够用）
- 若 Process 插件天然无密钥（OS 隔离拿不到 env），授权层降为审计+配额（不做显式批准）

---

## 5. 验收

- 插件声明 `host.llm.invoke.v1` → 设置面板显示申请 → 用户批准
- 插件调 `request_host_capability("host.llm.invoke.v1", ...)` → 宿主代理调模型 → 返回结果
- 插件看不到 API key（Process 隔离 + 无 env 注入）
- 审计日志记录每次调用（插件/能力/purpose/模型/token/时间）
- 配额：超限拒绝 + 通知

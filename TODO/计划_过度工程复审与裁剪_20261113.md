## 一、复审纠正：伪过度工程（不动）

以下项目在第一轮审计中被标记为过度工程，经第二轮深入验证后确认**不是**过度工程。记录纠正理由以避免未来重复质疑。

### ✅ 三重 LLM Judge（StepJudge + CompletionJudge + Gate E）——不冗余

**第一轮误判**：三个 judge 判断同一件事，代码自己承认重叠。

**复审纠正**：三个 judge 作用域、触发时机、补救动作完全不同：

| Judge | 作用域 | 问题 | 触发点 | 补救动作 |
|-------|--------|------|--------|---------|
| CompletionJudge | 单次 spawn | "子 agent 完成任务了吗？" | spawn 运行中，finalize 前 | CONTINUE → 注入 prompt，继续运行同一 agent |
| StepJudge | 单步骤结果 | "结果满足步骤的 validation_criteria 吗？" | taskflow_resume，子完成后 | RETRY → 生成替换子 agent；BLOCK |
| Gate E | 整个 flow | "所有结果汇总满足 flow 的目标吗？" | taskflow_finish，Gate A-C 通过后 | GOAL_NOT_MET → 拒绝 finish，引导 replan |

Gate E 的 `min_steps=3` 是**显式去重边界**——1-2 步骤的 flow 不跑 Gate E，因为 CompletionJudge 已覆盖。3 步以上的 flow，步骤各自通过 ≠ 目标达成（步骤可能各自正确但组合起来缺东西）。

典型 3 步 flow happy path = **4 次 judge 调用**（3 StepJudge + 1 Gate E，CompletionJudge 被 `_first_turn_self_evident` 短路跳过）。不是"每步 3×冗余"。

**结论：不裁剪。** 三个 judge 覆盖三个层级（run / step / flow），是分层质量保障，不是冗余。

### ✅ PTC replay ——半活跃 + 半分阶段启用，不是死代码

**第一轮误判**：1,484 行运行时代码从不执行。

**复审纠正**：
- **`execute_code` 手动工具是活跃的**——注册在 `child_agent_factory.py:298-304`，EXECUTOR 角色子 agent 可直接调用，是真实的 agent 工具
- **replay/compile 路线是分阶段启用的**——config 注释明确写了启用条件（观察 compile hit rate / prefill success rate / duplicate-side-effect audit）；`TODO/计划_非幂等动作防重放防重试_20261111.md` 是启用前的硬化前置
- 不是被放弃的实验，是有明确启用路线图的暂存代码

**结论：不裁剪。**

### ✅ Effects 层 ——分阶段启用，填补真实空白

**第一轮误判**：完整复制现有同步路径，4 个 flag 全 False，从不执行。

**复审纠正**：
- **填补真实空白**：`boot_recovery.py` 只恢复 *状态*（HITL flag / dangling tool call / CLAIMED row），不重新投递 *错过的异步副作用*（continuation 指令 / 完成通知 / auto-turn trigger）。进程在这些投递的间隙死掉时，同步路径丢失它们——effects 层的 durable queue 正是为此设计
- **不是纯复制**：generation CAS 去重（慢 worker 持旧 generation 不能完成新行）、durable 跨重启持久化、指数退避重试 + abandon 上限——这些都是同步路径没有的
- **三阶段 rollout 已设计**：off → shadow（观察，`scripts/verify_effects_shadow.py` 验证脚本已交付）→ execution
- handlers 通过 `_from_effects=True` seam 重入原始实现，投递 *体* 共享，调度/持久化/去重/重试 *外壳* 是新的

**结论：不裁剪。**

### ✅ Registry 25 文件——真模块化，非碎片化

**第一轮误判**：状态机被文件分片，25 文件追踪一个 registry。

**复审纠正**：
- **所有微模块都有多个生产调用者**（3-20 个），没有单调用者文件
- 5 个模块级单例（`task_refs` / `spawn_budget` / `yield_events` / `terminal_gen` / `work_admission`）正确分离——各自持有带锁的可变状态，合并会纠缠锁作用域
- "7 个状态机文件"实际是"2 个真状态机 + 5 个不同关注点"（`session_state.py` 是优先级探测器，`state.py` 是 init/persistence 被误命名，`completion.py` 是结果解析，`completion_events.py` 是 pub/sub hub，`reconciliation.py` 是推理逻辑）
- `session_keys.py` 20 个调用者，`memory.py` 40 个调用者——重度复用

**唯一弱点**：`read.py`（59 行，10 个一行委托包装）是纯 pass-through 层，无逻辑。成本可忽略。

**结论：不裁剪。** `state.py` 可重命名为 `persistence.py`（纯可读性改善，非必须）。

### ✅ Spawn 25 文件——20/24 真模块化

**第一轮误判**：17 个单函数微模块碎片化。

**复审纠正**：
- 24 个逻辑文件中 20 个是真模块化（多调用者、有内聚性）
- 0 个测试 fixture / conftest 充数——文件计数无水分
- `__init__.py` 36 行是 facade re-export，非 boilerplate

**唯一弱点**：4 个单函数微文件（`task_name.py` 18L / `accepted_note.py` 21L / `initial_message.py` 25L / `thinking.py` 30L）各有 3 个调用者但内容极小，可合并为一个 `spawn/text_helpers.py`。成本低，改善有限。

**结论：可选合并 4 个微文件，非必须。**

### ✅ 默认关闭的 flag ——保守默认值设计

8 个 `*enabled: False` flag 全部在生产代码中被 genuine gate 消费。抽样验证每个都在定义文件外被引用。这是保守默认值策略，不是死配置。

**结论：不裁剪。**

### ✅ DelegationPressureGate ——活跃但建议性

`enabled=True`，生产中运行。纯建议性（不阻止工具调用），7/12 阈值未校准。但它是一个 252 行的轻量中间件，成本可忽略。阈值未校准是"可改进"而非"过度工程"。

**结论：不裁剪。阈值校准可作为未来优化。**

### 🔴 P1：`background_reviews.py` 万能文件（2,335 行 / 7 个不相关职责）

**问题**：`agent/middlewares/summarization/background_reviews.py` 单文件 2,335 行，承载 7 个与"压缩旧消息"无关的职责：

| 职责 | 行数 | 说明 |

**量化**：summarization 包 7,494 行中，~2,670 行（36%）不是压缩逻辑。

**裁剪方案**：
1. 把 `background_reviews.py` 拆成 5-6 个内聚文件，按职责分：
   - `memory_review.py`（memory review + consolidation）
   - `session_salvage.py`（session-end salvage）
   - `handoff_aggregation.py`（handoff-tree 读取+聚合）
   - `skill_review_runner.py`（合并 `background_reviews.py` 中的 460 行 + 现有 `skill_review.py` 的 335 行 → 统一到一个文件）
   - `ptc_compile.py`（PTC 脚本编译）
   - `compression_todo.py`（压缩后 todo 对账）
   - `background_agent_scaffolding.py`（共享 scaffolding）
2. 每个文件由压缩管线通过统一的 `schedule_*` 入口调度，保持 fire-and-forget 模式
3. 不改变任何行为——纯文件重组

### 🟡 P2：SQLite quartet 碎片化（4 个可合并的全局 DB）

**问题**：以下 4 个数据库使用相同的 `BaseSQLiteRepository` 骨架、相同的 `_BUSY_TIMEOUT_S`、相同 monkeypatch 契约，从不在 SQL 中 JOIN（关联在 Python 中按 id 解析）：

`taskflow_finish.py` 的 evidence gate 跨 store 边界读 evidence 行（evidence 在一个 DB，flow 状态在另一个 DB），通过两个独立查询在 Python 中拼接。

**不合并的 DB（已验证有正当理由）**：

- `codeintel/index.db`（per-project）

**裁剪方案**：
1. 合并 4 个 DB 为一个 `registry.db`，包含 `subagent_runs` / `flows` / `steps` / `todos` / `evidence_events` 表
2. evidence_events 保持 append-only/fail-open 语义（独立表，不影响其他表的写）

### 阶段 2：SQLite quartet 合并（P2）——✅ 评估通过，可行但中等成本

**评估结论**：

| 评估项 | 结论 |
|--------|------|
| 写冲突 | **可控**。同 loop 的 async 写串行；真正的跨线程并发是 sync（evidence ledger 每次 tool call）vs aiosqlite worker（taskflow/todos），但 4 个 DB 都已用 WAL + 5s busy_timeout，正是多写者合并 DB 的标准缓解措施。父-step 期间和子-step 期间的写是顺序的，不重叠。 |
| 连接模式 | **同质，合并就绪**。全部 per-call 短连接，全部 WAL，全部 5000ms busy_timeout。evidence ledger 独立于 BaseSQLiteRepository 但行为等价。 |
| 测试契约 | **~19 个测试文件 + sandbox.py**。最省路径：保留各模块的 `_DB_PATH`/`LEDGER_PATH` 属性指向同一合并文件 → 测试零改动。sandbox.py 有预存缺陷（不 patch evidence ledger），合并时需补上。 |
| 迁移 | **无现成框架**（BaseSQLiteRepository 明确声明不做 migration）。需一次性离线迁移脚本，在 boot 时 sweeper 启动前执行。`pending_injections`/`user_input_queue` 是 subagent_registry.db 的第三方写者，必须一起搬。 |

**合并方案**：
1. 创建一个 `registry.db`，包含 5 张表：`subagent_runs` / `flows` / `steps` / `todos` / `evidence_events`
2. 四个模块保留各自的 `_DB_PATH`/`LEDGER_PATH` 属性，全部指向同一文件（测试零改动）
3. evidence_events 保持 append-only/fail-open 语义（独立表）
4. 跨表查询（evidence by flow_id）变为同 DB 操作
5. 一次性迁移脚本（boot 时执行，sweeper 启动前）：
   - 检测旧 DB 是否存在 → 复制表数据到新 DB → 重命名旧 DB 为 `.bak`
   - 必须处理 `pending_injections`/`user_input_queue` 的 co-writer
6. `evals/sandbox.py` 补上 `EvidenceLedger.LEDGER_PATH` redirect（预存缺陷修复）

**风险**：中等。写冲突靠 WAL 缓解（已验证就绪），但首次合并涉及数据迁移 + co-writer 搬迁。建议先在 staging 验证迁移脚本 + 跑 full test suite。

### 阶段 3：低优先级清理（P3-P6）——✅ 全部评估通过，低风险

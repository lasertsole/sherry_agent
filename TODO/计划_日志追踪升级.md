## 设计

三档递进，互相独立：方案一成本最低收益最大，方案二锦上添花，方案三需要配套落地。

### 方案一：`logger.contextualize()` 注入 turn_id + session_id（最低成本，最高收益）

#### 原理

loguru 原生支持 `logger.contextualize(**kwargs)`——一个 context manager，在其范围内所有日志自动带上指定字段（写入 record 的 `extra` dict），无需手动 f-string。Sherry 的 `turn_runner.py` 已有 `turn_id`（`uuid.uuid4().hex`，line 443），只差在 turn 生命周期开始处用 `with logger.contextualize(...)` 包裹整个执行。

#### 改动

**`server/service/turn_runner.py`**——在 `WsTurnExecutor.execute_batch` 或 `_execute_single` 入口处：

```python
with logger.contextualize(
    turn_id=turn_info["turn_id"],
    session_id=session_id,
):
    # ... 整个 turn 执行体 ...
```

这一行 `with` 让范围内所有 loguru 日志（中间件、工具、LLM 调用、错误、stream dispatch）自动带上 `turn_id` 和 `session_id`。包括：
- `_GenerateTurn._log_started` / `_log_completed` / `_log_failed`（已手动写 session_id，现在自动带）
- 中间件 hook 的 DEBUG 日志（`base.py` 的 `BeforeAgentHooksMixin` / `AfterAgentHooksMixin`——当前无 session_id，现在自动有）
- `MessagePersistenceMiddleware` 的持久化日志
- `LLMRetryMiddleware` 的重试日志
- `ContextEvictionMiddleware` 的驱逐日志
- Summarization 的压缩日志
- stream dispatch 的 tool_start/tool_result 帧日志（如果有）
- 异常路径的 `logger.exception`

**`agent/middlewares/base.py`**——给 hook 日志加 session_id 和 enter/exit 时序：

```python
class BeforeAgentHooksMixin:
    def abefore_model(self, state, runtime=None):
        session_id = state.get("session_id", "")
        logger.bind(middleware=self.__class__.__name__).debug(
            f"before_model enter"
        )
        # ... hook logic ...
        logger.bind(middleware=self.__class__.__name__).debug(
            f"before_model exit"
        )
```

如果方案一的 `contextualize` 已落地，`session_id` 自动带上，这里只需加 `middleware` 名和 enter/exit 标记。20 个中间件的执行链从"完全不可见"变成"可追踪"。

#### 验收

- `all_*.log` 里同一个 turn_id 的日志行包含 WS 接收 → 中间件链（enter/exit） → LLM 调用 → 工具执行 → 响应完成，按时间排序即为完整链路
- 中间件 hook 日志带 session_id（之前没有）
- `grep turn_id=xxx all_*.log` 或 `jq 'select(.extra.turn_id == "xxx")'` 能拉出完整 turn 链路
- 无需改测试（日志格式变更不影响行为）

#### 风险

- `logger.contextualize` 是 context manager，在 async 代码中需确认 contextvar 在 `await` 边界正确传播——loguru 基于 `contextvars`，与 asyncio 兼容，但子 agent 的 turn 在独立 session_id 下执行，需确认子 agent 的 `contextualize` 不泄漏回父 agent
- 性能：`contextualize` 只在 record 创建时多一次 dict merge，可忽略

### 方案二：结构化 JSON sink（让日志可程序化分析）

#### 原理

给 loguru 加一个 JSON sink（`serialize=True`），让 `all_*.log` 变成 JSONL，每行带 `turn_id`/`session_id`/`level`/`name`/`message`/`extra`。之后 `jq 'select(.extra.turn_id == "abc")' all_*.log` 就能精确过滤，可程序化分析。

#### 改动

**`logs/logger.py::init_logger`**——在现有 3 个文件 sink 之外，加一个 JSON sink：

```python
logger.add(
    LOG_DIR / "all" / f"json_{date}_{pid}.log",
    level="TRACE",
    rotation="100 MB",
    retention="30 days",
    compression="zip",
    serialize=True,  # JSONL：每行一个 JSON 对象
    enqueue=True,
)
```

保留现有的纯文本 sink（stderr + info + all + error）——它们给人看，JSON sink 给机器看。不互斥。

#### 验收

- `json_*.log` 每行是合法 JSON，带 `text`（消息体）、`record.extra`（turn_id/session_id/middleware 等上下文字段）
- `jq 'select(.record.extra.turn_id == "abc") | {time, level, name, message: .text}' json_*.log` 拉出完整链路
- 现有纯文本日志不受影响

#### 风险

- 磁盘：JSON 每行比纯文本大 ~2-3x，但 `all/` 已是全量 TRACE sink，增量可接受
- 密钥脱敏：现有 `redact_formatter` 在 patcher 层处理 `record["exception"]`，JSON sink 的 `serialize=True` 会序列化整个 record dict——需确认 redact patcher 在 serialize 之前生效（loguru patcher 在 sink 之前运行，所以是的）

### 方案四：简化版 Trajectory Ledger（离散事件表，给观测面板结构化数据）

#### 原理

前三个方案解决"文本日志可追踪"和"LLM 调用可计量"。但观测面板需要**结构化的 per-turn 事件时间线**——按轮次分页浏览、一行展示 tool 的 args+result+duration、轮次级 metrics（TTFB/总时长）、压缩事件可视化——这些是文本日志（即使 JSON 格式化）渲染不出来的。

参考 Octop 的 trajectory_events 表，但**大幅简化**：只记离散事件（6 种 kind），不记每个流式 chunk。一轮约 3-12 条事件，不是几百条。

#### 事件设计

| kind | 触发点 | payload | 每轮约几条 |
|---|---|---|---|
| `turn_start` | turn_runner 生成 turn_id 时 | `{turn_id, session_id, message_ids, source}` | 1 |
| `tool_start` | stream_dispatch 发 `tool_start` 帧时 | `{tool_call_id, tool_name, args}` | 0-5 |
| `tool_end` | stream_dispatch 发 `tool_result` 帧时（**upsert 合并到 tool_start**） | `{tool_call_id, tool_name, result_clip, duration_ms, is_error}` | 0-5 |
| `compact` | Summarization 压缩完成时 | `{messages_before, messages_after, tokens_saved, preserve_count}` | 0-1 |
| `error` | 流式失败时 | `{error_type, error_message, diag_summary}` | 0-1 |
| `turn_end` | stream_dispatch 发 `done` 帧时 | `{turn_id, total_ms, ttft_ms, tool_count, token_usage}` | 1 |

**关键设计：tool_start → tool_end upsert 合并**

用确定性 `event_id` = `{session_id}:{turn_id}:tool:{tool_call_id}` 做 upsert key。`tool_start` 创建行（args 写入），`tool_end` 用相同 event_id upsert（result + duration + is_error 合并进去）。一轮结束后每个工具调用是一行完整记录，不是两行。

#### 表结构

```sql
CREATE TABLE IF NOT EXISTS trajectory_events (
    event_id   TEXT PRIMARY KEY,   -- 确定性：{session}:{turn}:tool:{call_id} 或 {session}:{turn}:{kind}:{seq}
    session_id TEXT NOT NULL,
    turn_id    TEXT NOT NULL,
    seq        INTEGER NOT NULL,    -- 单调递增，用于时间线排序
    ts         TEXT NOT NULL,       -- ISO 时间戳
    kind       TEXT NOT NULL,      -- turn_start / tool_start / tool_end / compact / error / turn_end
    is_error   INTEGER DEFAULT 0,
    summary    TEXT,               -- 一行摘要（工具名/错误类型等，用于列表展示）
    payload_json TEXT              -- 完整 payload（args/result/duration/metrics）
);
CREATE INDEX IF NOT EXISTS idx_trajectory_session_turn ON trajectory_events(session_id, turn_id, seq);
CREATE INDEX IF NOT EXISTS idx_trajectory_turn ON trajectory_events(turn_id, seq);
```

挂在现有 SQLite store（和 messages 同库，不新建库文件）。继承 `BaseSQLiteRepository`。

#### Projector（hook 进 stream_dispatch）

不新建独立的数据采集管线——sherry 的 `StreamTurn.run()` 已经在发射 WS 帧（`tool_start`/`tool_result`/`turn_started`/`done`/`error`）。projector 是帧发射的一个**额外 sink**：

```python
# stream_dispatch.py 的帧发射点，每发一个帧额外写一条 trajectory 事件
async def _emit_frame(self, frame: dict, ...):
    yield frame  # 现有 WS 帧逻辑不变
    _try_project_trajectory(frame, self.session_id, self.turn_id)  # fail-open
```

```python
def _try_project_trajectory(frame, session_id, turn_id):
    """把 WS 帧投影成 trajectory 事件。fail-open——永不中断流。"""
    try:
        kind = _frame_kind(frame)  # turn_started→turn_start, tool_start→tool_start, ...
        if kind is None:
            return  # 帧类型不关心（reasoning/text delta 等）
        event_id = _make_event_id(session_id, turn_id, kind, frame)
        payload = _extract_payload(frame)  # 按 kind 提取 args/result/duration/metrics
        repo.upsert_event(event_id, session_id, turn_id, seq, kind, payload, ...)
    except Exception:
        logger.debug("trajectory projection failed", exc_info=True)
```

6 种 kind 各一个 `_extract_payload` case，~15 行/kind。

#### turn_id 兜底

当上游没传 turn_id（如 subagent 的 turn），自动合成 `f"{session_id}:turn:{turn_seq}"`（turn_seq 从 trajectory 表的 max(seq) + 1 取），保证关联永不断裂。

#### REST 查询

```
GET /sessions/{session_id}/trajectory?turn_id=...&limit=50&offset=0
```

返回按 seq 排序的事件列表，每个事件带 kind/summary/payload。tool_start 和 tool_end 已合并为一行。

不需要 SSE 推送——sherry 已有 `/logs/ws` 实时日志面板。trajectory 表的历史查询走 REST，实时追踪走 loguru + contextualize（方案一）。两套系统共享 turn_id。

#### 配置

```python
class TrajectoryConfig(TypedDict):
    enabled: bool          # True
    max_turns_per_session: int  # 保留最近 N 轮（默认 50），超出按最旧优先裁剪
    payload_max_chars: int     # payload_json 截断上限（默认 64000）
    result_clip_chars: int     # tool result 在 summary 里的截断（默认 2000）
```

#### 验收

- 一轮完整对话后，`trajectory_events` 表有 turn_start + N×(tool_start merged with tool_end) + turn_end，按 seq 排序即为时间线
- tool_start 和 tool_end 合并为一行（upsert 生效），payload 同时有 args 和 result+duration
- `GET /sessions/{id}/trajectory?turn_id=xxx` 返回该轮全部事件
- compact 事件在压缩后出现，带 messages_before/after/tokens_saved
- error 事件在流式失败后出现，带 diag_summary
- fail-open：projector 异常不中断流式
- 裁剪：超过 max_turns 的旧轮次被删除

#### 风险

- **写压力**：每轮 3-12 条 upsert，在 stream_dispatch 的帧发射点同步写。低——SQLite WAL + 单行 upsert。但需确认不阻塞 WS 帧发射（可在 `asyncio.to_thread` 里写，或用 batch flush）
- **payload 体积**：tool args/result 可能很大——payload_max_chars 截断 + 只存 JSON 摘要。完整 result 已在 messages 表，trajectory 只存 clip
- **和 messages 表的重复**：trajectory 不替代 messages 表——messages 存对话内容（给模型读），trajectory 存事件时间线（给面板读）。数据有重叠但用途不同

#### 成本

| 组件 | 行数 |
|---|---|
| 建表 SQL + migration | ~20 |
| Repository（继承 BaseSQLiteRepository） | ~80 |
| Projector（6 种 kind 的 frame→event 映射） | ~100 |
| REST 路由 | ~60 |
| 配置 TypedDict | ~15 |
| 测试 | ~120 |
| **合计** | **~400** |

## 不做的事

- **不换日志框架**——loguru 已够用，`contextualize` + `serialize` 就能得到结构化日志和关联，不需要引入 structlog 或 OpenTelemetry
- **不加 OpenTelemetry exporter**——sherry 是自托管单进程，OTel 的 collector/exporter 基础设施过重。LangSmith（LangChain 原生 tracing）已覆盖 LLM 调用链
- **不改现有日志格式**——纯文本 sink 保留给人看，只加 JSON sink 给机器看。现有的 `init_logger` 配置（4 sink + redact patcher + 7 天清理）不动
- **不给每个工具加 loguru 日志**——工具调用的 `tool_duration_ms` 已进 DB（`messages.tool_duration_ms`）和 WS 帧，加日志是冗余。方案一落地后，工具执行范围内的 `contextualize` 会让已有的 message_persistence 日志自动带 turn_id，已足够关联
- **不做 per-chunk trajectory**——Octop 记每个流式 delta（一轮几百条），sherry 只记离散事件（一轮 3-12 条）。粒度够面板用，成本降 80%
- **不建 SSE trajectory 推送**——sherry 已有 `/logs/ws` 实时面板。trajectory 的历史查询走 REST，实时追踪走 contextualize（方案一），不重复建实时通道

## 现有日志优化清单

### O1. 168 个 f-string logger 调用，零 `logger.bind()`（高，全仓库）

`logger.info(f"...session_id={session_id}...")` 遍布全仓库（server/trigger=106, runtime=26, server/service=19, agent/middlewares=6）。f-string 即使日志级别过滤掉了也会求值，且不产生机器可查字段。

- **现状**：0 个 `logger.bind()` / 0 个 `extra=` / 5 个 `logger.opt(exception=...)`
- **最差**：`server/trigger/core.py` 和 `ws/messages.py`——每条日志都是 f-string
- **修复**：改为 loguru placeholder 格式 `logger.info("...", session_id, ...)` 或 `logger.bind(session_id=...).info(...)`。方案一 `contextualize` 落地后 session_id/turn_id 自动带，f-string 中的手动 session_id 可以删掉

### O2. memory 工具日志缺 session_id

`agent/tools/memory.py:650,656,686,693-696`——memory 操作日志（DEBUG start+duration, ERROR failure）不含 session_id。工具收到了 session_id 参数但日志不用。

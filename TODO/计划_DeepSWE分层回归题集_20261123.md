## 1. 设计

两层题集：

| 层 | 题数 | 耗时 | token | 通过条件 | 用途 |
|----|------|------|-------|---------|------|
| L1 回归题集 | 12 | ~5h | ~4M | resolved 不退化 + near-miss 不退步 + P2P 不回归 + 未测题有产出 | 每次改动后跑 |
| L2 全量题集 | 105（117 - 12） | ~53h | ~26M | L1 通过后才跑 | 发版前全量验证 |

### L1 选题原则

1. **5 种语言全覆盖**
2. **已测 + 未测混合**——已测有基线对比，未测探路
3. **最能暴露流程 bug 的题优先**——按以下特征筛选：
   - 多文件修改 → 测试 patch_file 多文件模式 + CAS
   - 长指令多验收条款 → 测试 reviewer checklist + StepJudge + 漂移检测
   - 需要 terminal 跑测试 → 测试 evidence collector + verify 回归门
   - 复杂 API + 多导出 → 测试 agent 跨文件理解能力
   - 已知失败模式 → 验证改进效果

### 2.2 为什么这样选未测题

**koota-entity-snapshot-rollback**（#7）——最能暴露流程 bug：
- 20 行指令，7 个 API 导出 + convenience methods → reviewer checklist 能提取大量验收条款
- "Throws Error on duplicate keys"、"Throws Error for destroyed entities" → StepJudge 有明确判定依据
- 需要 snapshot + rollback + diff 三组功能 → agent 容易漂移到只做 snapshot 忘了 rollback
- Python + 大量测试 → terminal 跑测试验证 evidence collector

**returns-validated-error-accumulation**（#8）——测试多文件 CAS + 漂移：
- 17 行指令，需改 4+ 文件（新文件 + cond.py + hypothesis + pointfree）
- 指令明确说 "Beyond creating new files, you must also update..." → agent 容易漏文件
- "ValidatedLikeN cannot extend DiverseFailableN" → 复杂约束，agent 容易理解偏

**langchain-request-coalescing**（#9）——测试复杂契约理解：
- 7 行但密度极高：sync/async/stream/batch/batch-as-completed 共享一个 backend
- "Transform, atransform, and event streaming pass through transparently" → agent 容易漏
- 线程安全 + 并发 → 需要深入理解代码

**happy-dom-abort-pending-body-reads**（#10）——bugfix 精确定位：
- bugfix 题需要先理解 bug 再修，不是从零实现
- "read must reject with DOMException named AbortError" → 精确的验收条款
- TS + 浏览器 DOM → 不同领域覆盖

**csstree**（#11）+ **pest**（#12）——语言探路：
- JavaScript 和 Rust 完全没测过，必须探路
- csstree 是 lexer 改动（范围小），pest 是解析器改动（范围小），不太耗时

## 4. 迭代节奏

```
改动计划 → 实现 → L1 回归（5h）
  ├─ L1 通过 → L2 全量（53h）→ 发版
  └─ L1 不通过 → 修问题 → 重跑 L1
```

| 轮次 | 改动 | L1 预期 | 跑 L2？ |
|------|------|---------|---------|
| 1 | 叶子超时 600→1800s | #5 耗时下降 | L1 通过后跑 |
| 2 | task 压缩存活（修 8/9/10） | #4 长时任务 F2P 提升 | L1 通过后跑 |
| 3 | 子 agent 漂移检测（DRIFTED） | #2/#6 near-miss F2P 提升 + #7-9 未测题不漂移 | L1 通过后跑 |
| 4 | reviewer checklist | #7-9 验收条款多的题 F2P 提升 | L1 通过后跑 |

## 5. L1 题集维护

| 情况 | 调整 |
|------|------|
| near-miss 题推过线（resolved） | 替换为新的 near-miss 题 |
| 未测题全 0 分（模型不支持该语言） | 替换为同语言其他题或去掉 |
| L1 耗时 > 8h | 缩减到 8-10 题 |
| L1 不够敏感（改动后 F2P 不变） | 替换为对改动更敏感的题 |

## 6. 成本估算

| 层 | 题数 | 耗时 | token | 成本（≈$0.5/M token） |
|----|------|------|-------|---------------------|
| L1 | 12 | 5h | 4M | ~$2 |
| L2 | 105 | 53h | 26M | ~$13 |
| L1 + L2 | 117 | 58h | 30M | ~$15 |

每次改动只跑 L1（~$2），通过后才跑 L2（~$13）。比每次全跑（~$15）省 87%。

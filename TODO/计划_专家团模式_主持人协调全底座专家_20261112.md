# 计划：专家团模式（Mode 2）— 主持人协调全底座专家 agent

- 日期：2026-11-12（重写为 Mode 2）
- 状态：**待评审**
- 来源：Sherry 第二种产品模式——用户和主持人对话，主持人协调分配任务给多个完整底座专家 agent；汲取同类工具的 host-expert UX，每专家保 Sherry 全底座（TaskFlow + evidence + PTC/LDW）
- 风险等级：**高** —— 新产品模式（非工具）；MVP 可行（复用 TaskFlow），完整愿景需补持久专家 session + host UX 表面 + 跨 session 派工协议

---

## 0. 模式定义

**两种模式并存**：
- **Mode 1（现有）**：用户 ↔ 底座 main agent（直接对话）
- **Mode 2（新）**：用户 ↔ 主持人（协调员）↔ N 个专家（每个完整底座 main agent）

主持人是用户对话对象，只分解/派工/收口/综合，不干活。专家各自完整底座（全工具 + own TaskFlow + evidence + PTC/LDW + memory），做实际工作。

### 借鉴 / 不借

| 借 | 不借 |
|---|---|
| Octop host-expert UX（用户→主持人→专家） | Madorin 会议投票（已否决） |
| Octop host 轻量协调员（剥离工作工具） | Octop 内存任务跟踪（Sherry 有 TaskFlow 状态机） |
| 持久专家累积领域专长（Octop 每专家独立 workspace/memory） | Octop WS 房间广播（Sherry 有 announce/drain） |

### Sherry 独有差异化

- 每专家是**完整底座**（TaskFlow/evidence/PTC-LDW），不是轻量执行者
- **两层 TaskFlow + 两层 PTC/LDW 编译**（团队协调模式 + 专家内部工作流都可复用）——Octop/Madorin 没有
- evidence ledger + 回归门（专家内部 + 团队跨专家）

## 1. 核实结论：什么可行、什么要建

### 可行（MVP 基础，现有架构）

| 机制 | 证据 |
|---|---|
| 主持人用 TaskFlow dispatch 派工给专家子 run + wait_all 阻塞等完成 + resume 注入结果 | `taskflow_wait_all.py:177-225` 事件驱动阻塞等 child settle |
| 专家子 run 内部跑自己的 TaskFlow（ORCHESTRATOR 深度默认有 taskflow 工具） | `inherited_tool_policy.py:122-127`（taskflow 不在屏蔽表） |
| 两层 flow finish 各自触发 PTC/LDW 编译 | 现有 PTC/LDW（flow finish 自动编译） |
| 专家并行（SUBAGENT lane 默认 4） | `lane_system.py` SUBAGENT semaphore |
| 专家 memory 跨任务持久（MesMemory） | 现有 MesMemory SQLite |

### 不可行（完整愿景缺口，需建）

| 缺口 | 现状 | 需建 |
|---|---|---|
| **持久专家 session**（跨多次派工存活、累积专长） | run 一任务一生命周期，终态后不可再派（`control/send.py:33-37`） | 持久专家 session 模型（run 终态后 session 保留可再派） |
| **同步 request-response 跨 session** | sessions_send 工具层禁用 `wait_for_reply`（`sessions_send.py:71` 硬编码 False） | 用 TaskFlow wait_all 替代（MVP），或启用 wait_for_reply 路径（phase 2） |
| **派给已存在独立 session** | 只能派给活着的子 run（不能派 side chat / 已 terminal） | dispatch-to-existing-session 入口 |
| **host 独立 UX 表面** | host 现在只是带协调员 persona 的 session，无独立模式 UI | 模式切换 UI + host profile |

## 2. MVP Mode 2（phase 1，可行现在）

### 2.1 MVP 形态

- 用户开一个"团队 session"（带主持人 system prompt 的 Sherry session）
- 主持人是 main agent（完整底座，但 persona 指示只协调不干活）
- 主持人用 TaskFlow 编排：
  ```
  taskflow_create_flow(task)
  → taskflow_create steps（每个 step 绑定一个专家配置：persona/role/model）
  → taskflow_dispatch 每个 step（spawn ORCHESTRATOR 深度子 run = 专家）
  → 专家子 run 内部跑自己的 TaskFlow（多步 + judge + evidence + handoff）
    → 专家 flow finish → 专家 PTC/LDW 编译（领域工作流复用）
  → taskflow_wait_all（阻塞等所有专家 settle）
  → taskflow_resume（注入每个专家结果）
  → taskflow_flow(action="finish")（团队 evidence 门 + Gate E）
    → 团队 flow finish → 团队 PTC/LDW 编译（协调模式复用）
  → 主持人综合回复用户
  ```

### 2.2 MVP 的两层 TaskFlow + 两层复用

```
团队级 TaskFlow flow（主持人跑）
  step 1 → dispatch 前端专家子 run
  step 2 → dispatch 后端专家子 run（depends_on step 1）
  finish → 团队 evidence 门（跨专家回归）→ 团队 PTC/LDW 编译
                                    ↑ "前端→后端"协调模式可复用

专家级 TaskFlow flow（每个专家子 run 内部跑）
  专家自己 taskflow_create/dispatch/wait/finish
  → 专家 evidence 门 + 专家 PTC/LDW 编译
                                    ↑ 前端专家的前端工作流可复用
```

两层都是现有 TaskFlow 机制，不新造编排引擎。两层 finish 各自触发 PTC/LDW 编译——但**按可复用性判定条件触发**（见 §2.6），不是无条件编译。

### 2.3 MVP 主持人

- **完整底座 + 协调员 persona**（MVP 不做轻量剥离，phase 2 做）
- system prompt：你是团队主持人，分解任务→taskflow 派工给专家→wait_all→resume→finish→综合回复，不亲自干活
- 拥有 taskflow 工具（继承 build_main_tools）

### 2.4 专家是一等公民实体（per-expert 独立配置 + 注册库 + 跨团复用）

专家不是派工时的临时配置，是**持久注册的独立实体**，可被多个专家团复用。

**per-expert 独立配置**（每个专家各自配 prompt / skills / plugins / MCP / model）：

```json
// APP_HOME/experts/<name>.json
{
  "name": "frontend-expert",
  "description": "Frontend development specialist",
  "persona_prompt": "You are a frontend expert. You know React/Vue/CSS deeply...",
  "model": "claude-3-5-sonnet",
  "thinking": "medium",
  "functional_role": "executor",
  "depth": "ORCHESTRATOR",
  "skills": ["code_wiki", "text_to_image"],        // per-expert 技能白名单（超出角色默认）
  "plugins": ["my-frontend-plugin"],                // per-expert 插件
  "mcp_servers": ["frontend-tools-server"],         // per-expert MCP server 集
  "tools_allow": [],                                // per-expert 工具 allow/deny（可选，覆盖角色默认）
  "step_timeout_seconds": 1800
}
```

- **prompt**：per-expert persona（领域身份/专长/风格）
- **skills**：per-expert 技能白名单——对接 per-role 技能隔离计划（caller_role 过滤）之上再加一层 per-expert 白名单（专家只看到自己配的技能子集）
- **plugins**：per-expert 插件——对接 Python 三通道插件体系计划（每个专家启用自己的插件子集）
- **MCP**：per-expert MCP server 集——每个专家接自己的 MCP server（不同专家接不同工具链）
- **model/thinking**：per-expert 模型 + 思考级别（前端专家用 Claude、后端用 DeepSeek，发挥各模型强项）
- **functional_role/depth**：角色 + 深度（ORCHESTRATOR 让专家有 taskflow 工具跑内部 TaskFlow）

**专家注册库（Expert Registry）**：
- 存储在 `APP_HOME/experts/<name>.json`（持久配置，跨 session/团队）
- 一个专家定义一次，多个专家团引用
- CRUD：创建/编辑/删除/列出专家

**跨团复用**：专家团配置引用专家名（不是内联配置）：
```json
// APP_HOME/teams/<name>.json
{
  "name": "web-team",
  "host": {...},
  "members": [
    {"expert": "frontend-expert"},   // 引用注册库
    {"expert": "backend-expert"},
    {"expert": "db-expert"}
  ]
}
```
- 同一专家（如 `frontend-expert`）可同时在 `web-team` 和 `mobile-team`——一处定义、多团复用
- 专家配置改一处，所有引用该专家的团自动生效

### 2.5 MVP 不有的（诚实）

- 专家不持久（一任务一 run，完成后解散；memory 经 MesMemory 持久但 run 不持续）→ phase 2
- 无独立 host UX（就是带 persona 的 session）→ phase 3
- 主持人是完整底座（有诱惑自己干活）→ phase 2 剥离

### 2.6 可复用性判定（按实际情况决定是否编译可复用 TaskFlow）

**不是所有任务都该编译成可复用流程**。一次性任务（如"修这个特定 bug""写一次性迁移脚本"）编译了也不会重放——浪费编译资源 + 污染 skills/auto 目录。

**三层判定**：

| 判定 | 来源 | 结果 |
|---|---|---|
| **flow 级 `reusable` 标志** | 主持人创建 TaskFlow flow 时设（`taskflow_create(reusable=True/False/partial)`） | False→跳过整个 flow 的 PTC 编译；True（缺省）→正常编译；Partial→只编译标记了 `reusable_step=True` 的步骤 |
| **LDW 自然门控** | 现有 `LDW["min_replays"]=3`（同 plan 成功 3 次才编译） | 一次性任务只成功 1 次→**自然不触发 LDW 编译**，无需改 |
| **手动保存** | 用户/主持人在 flow 完成后显式 `save_as_template`（WorkMode 计划的计划模板） | 手动标记可复用，不受 auto 判定限制 |

**主持人怎么判定 reusable**：
- **可复用**（reusable=True）：重复性/流程化任务（部署、代码审查、文档生成、例行检查、同类 bug 修复模式）
- **不可复用**（reusable=False）：一次性任务（特定 bug 修复、一次性迁移、一次性数据处理、探索性研究）
- **部分可复用**（reusable=partial）：流程中有些步骤可复用（如"环境准备"步骤可复用，但"修特定 bug"步骤不可复用）

**判定方式**：
- MVP：主持人在 system prompt 里被引导创建 flow 时设 `reusable` 标志（LLM 判断任务类型）
- 进阶：基于历史 plan key 匹配（类似任务做过→可复用；全新任务→先 False，重复 3 次后 LDW 自然编译）

**PTC 编译按 `reusable` 过滤**：
- flow `reusable=False` → finish 时**跳过 PTC 编译**（不生成 `ptc__*.py` 脚本）
- flow `reusable=True` → 正常 PTC 编译（每成功 step 编译）
- flow `reusable=partial` → 只编译 `reusable_step=True` 的 step（跳过不可复用 step）
- 专家内部 flow 同理（专家创建自己的 TaskFlow 时也设 `reusable`）

**不影响**：evidence ledger / 回归门 / completion judge（这些是验证层，不是复用层，不论可复用与否都要跑）。只影响 PTC/LDW 编译（复用层）。

## 3. 完整愿景的缺口（phase 2/3）

### 3.1 持久专家 session（phase 2）

**缺口**：run 一任务一生命周期，终态后不可再派。专家不跨任务存活。

**需建**：
- "持久专家 session"模型：run 终态后 session 保留（checkpoint + MesMemory），可被再次派工（新 run 复用旧 session 的 checkpoint/memory）
- 或：专家 = 命名别名（`task_name`），每次派工 spawn 新 run 但继承同名专家的 memory/skills/auto（`sessions_spawn` cleanup=keep + memory 继承）
- 专家的 PTC/LDW 编译库按专家命名隔离（`skills/auto/<expert-name>/scripts/`）

**这是补"领域专长跨任务累积"的关键**——前端专家攒自己的前端 replay 库 + memory，不混后端。

### 3.2 host 轻量协调员 profile（phase 2）

**缺口**：MVP 主持人是完整底座，有诱惑自己干活。

**需建**：
- 主持人 profile：剥离工作工具（file/browser/terminal/code-intel 等），只留 taskflow + subagent runtime + memory + time（参照 Octop host_briefing 的轻工具集）
- `scope: host_only` 或新 profile 机制，让主持人只能协调不能执行

### 3.3 host 独立 UX 表面 + 专家库管理页面 + 模式切换（phase 3）

**缺口**：MVP host 就是带 persona 的 session，无独立模式 UI；专家配置是 JSON 文件无管理界面。

**需建**：
- 模式切换：用户选"直接对话"（Mode 1）或"团队模式"（Mode 2）
- 团队模式 UI：显示主持人 + 专家列表 + 任务进度（专家内部 TaskFlow step 进度，需专家 flow 状态上报团队）
- **专家库管理页面**（Expert Library，专门存放/管理专家）：
  - 专家列表（卡片：name / description / model / skills 数 / 插件 / MCP / 被哪些团引用）
  - 创建/编辑/删除专家（表单：persona prompt / model / thinking / functional_role / depth / skills 多选 / plugins / mcp_servers / tools_allow）
  - 技能多选：从技能索引勾选该专家可用的技能（per-expert 白名单）
  - 插件/MCP 多选：从已装插件/MCP server 勾选该专家的
  - "被引用"视图：显示该专家在哪些团队里，支持跳转到团队
  - 测试专家：发一个样例任务给专家单独跑，看产出
  - 团队管理页面：团队列表 + 创建/编辑团队（从专家库勾选成员组花名册 + 配 host）
- 专家卡片（持久专家的 memory/replay 库概览——phase 2 持久 session 后）

### 3.4 跨 session 派工协议（phase 2，可选）

**缺口**：sessions_send 工具层禁用 wait_for_reply；只能 spawn 新子 run。

**可选改进**：
- 启用 sessions_send 的 `wait_for_reply` 路径（底层已有 `_wait_for_updated_reply`，工具层没开）——给主持人同步派工+等回复的能力
- 或保持 TaskFlow wait_all 路径（MVP 够用），不建 sync RPC

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 主持人完整底座自己干活（MVP） | persona 强约束；phase 2 剥离工作工具 |
| 两层 TaskFlow 成本翻倍 | 简单任务走 Mode 1；Mode 2 仅复杂多领域任务 |
| 主持人规划封顶（分解质量） | TaskFlow 固有局限；团队配置预设常见分解模板缓解 |
| ORCHESTRATOR 专家子 run 内部 TaskFlow 深度/lane 限制 | 阶段 1 步骤 3 验证深度/lane；若不支持，专家内部 TaskFlow 降级为单步 |
| 持久专家 session（phase 2）架构改动大 | phase 2 在 MVP 验证价值后才做；不值则止步 MVP |
| 专家内部 TaskFlow 进度对主持人不可见 | MVP 接受（只看 completion）；phase 3 加进度上报 |
| **专家间 sync 互调死锁**（若加 lateral 专家互调） | 见下方专项 |

### 专家间 sync 互调死锁防范（专项）

**MVP 无风险**：派工严格树形（host→专家→grandchild），专家之间不互调，树形无环→**无循环等待可能**。wait_all 只等自己的 child（`taskflow_wait_all` docstring：不 reuse session-wide yield event，只等本 flow child）。

**风险出现在加 lateral 专家互调时**：专家 A sync 调专家 B（A 阻塞等 B），B 执行中 sync 调 A（B 阻塞等 A，但 A 已阻塞）= 经典循环等待死锁。Octop 的 `TeamJobTracker`（`jobs.py`）只追踪 host→member、不追踪 member→member、无环检测、重启即丢——**防了 async 循环没防 sync 循环**，就是这个坑。Sherry 不重蹈。

**选定的防法（B：sync 超时 + 等待图环检测）**：

若 Mode 2 完整愿景加 lateral 专家互调（专家 A 问专家 B），用等待图 + 环检测 + 超时三件套：

1. **等待图（wait graph）**：进程级 `AgentWaitGraph`，记 `waiter→waitee` 边。专家 A sync 调 B 时加边 `A→B`；B 返回时删边。
2. **环检测**：新 sync 调用前检等待图是否有环（从 waitee 回到 waiter 的路径）。有环→**拒绝调用**，返回 deadlock 错误（"circular wait detected: A→B→A"），让调用方走 host 中转或换路径。
3. **sync 超时**：所有 sync 专家互调带 deadline（`EXPERT_PEER_CALL_TIMEOUT_S`，默认 300s）。超时→调用方放棄、返回 timeout 错误、删等待边。防止无限挂死（即使环检测漏了，超时兜底）。
4. **TaskFlow DAG 环检测复用**：若专家间协作建模为 TaskFlow step 的 depends_on，现有 `validate_steps_list` 已有 DFS 环检测（创建时拒绝 cycle）——作为 DAG 建模路径的额外防线。

**不学 Octop 的半截防法**：不只防 async、不只追踪 host→member。等待图覆盖**任意专家→专家**对，sync 调用全过环检测 + 超时。

**实施时机**：MVP 不做（无 lateral 互调）。phase 2/3 若加专家互调，本防范随同落地，**不晚于 lateral 互调功能上线**。

### Kill criteria

- **阶段 1 MVP**：若主持人 TaskFlow 编排专家 + 专家内部 TaskFlow + 两层编译在验证中跑不通（深度/lane/状态机阻断），回退为"主持人单层 TaskFlow + 专家单步 subagent"（退化到 subagent 计划），两层复用降级为单层
- **阶段 1 价值**：若 MVP（含两层复用）不优于 Mode 1 main agent 直接 TaskFlow，Mode 2 止步 MVP，不推进 phase 2/3
- **阶段 2 持久专家**：若持久 session 模型架构改动过大且 MVP 已证值，持久专家后置或用"命名别名 + memory 继承"轻量替代
- **lateral 专家互调 + 死锁防范**：若等待图环检测 + 超时实施复杂度超预期且 lateral 互调非刚需，回退为防法 A（禁止专家互调，协作走 host 中转）——不引入 sync 死锁缺口

## 6. 验收

### 6.1 阶段 1 MVP
- 专家注册库：创建/编辑/删除专家配置（`APP_HOME/experts/<name>.json`），per-expert 配置含 prompt/skills/plugins/mcp/model
- 团队配置引用专家名，同一专家可被多个团引用
- 用户开团队 session → 主持人分解任务 → taskflow dispatch 派给 ORCHESTRATOR 专家（配置从注册库加载）→ 专家内部跑 TaskFlow → wait_all 等 → resume 注入 → finish 团队门 → 主持人综合回复
- 两层 flow finish 各自触发 PTC/LDW 编译（团队模式 + 专家工作流脚本）
- 专家并行（SUBAGENT lane）
- 专家内部 TaskFlow 有 evidence + judge + handoff

### 6.2 阶段 2（完整愿景）
- 持久专家跨任务存活 + 累积 memory/replay 库（按专家隔离）
- 主持人轻量 profile（无工作工具，只协调）
- per-expert 插件/MCP 独立加载（每个专家接自己的插件/MCP server）

### 6.3 阶段 3（UX）
- 模式切换（Mode 1 / Mode 2）
- 团队模式 UI（主持人 + 专家列表 + 进度）
- **专家库管理页面**（专家列表/创建/编辑/删除/技能多选/插件MCP多选/被引用视图/测试专家）
- 团队管理页面（团队列表/创建/编辑/从专家库勾选成员）
- 专家卡片（持久专家的专长概览）

### 6.4 回归
- Mode 1 行为不变
- 现有 TaskFlow / subagent / PTC-LDW 行为不变
- `uv run pytest tests/agent/tools/taskflow tests/agent/tools/subagent -q` 全过

## 7. 总结

**Mode 2 = Sherry 第二种产品模式**：用户↔主持人↔全底座专家。相对 Octop/Madorin 的差异化是每专家完整底座 + 两层 TaskFlow/PTC-LDW 复用。

**分阶段**：
- **阶段 1 MVP（可行现在）**：主持人 session + TaskFlow 编排 ORCHESTRATOR 专家 + 两层编译。复用现有机能，验证价值
- **阶段 2**：持久专家 session（跨任务累积领域专长）+ host 轻量 profile。需建新机制
- **阶段 3**：host 独立 UX + 模式切换 + 专家卡片

**硬前提已核实**：阶段 1 可行（TaskFlow dispatch/wait_all/resume + ORCHESTRATOR 专家内部 TaskFlow + 两层编译，全是现有机能）。阶段 2/3 的缺口（持久 session + host UX）明确，在 MVP 验证价值后推进。

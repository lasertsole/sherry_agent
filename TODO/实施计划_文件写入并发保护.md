# Sherry Agent 文件写入并发保护 — 实施计划

> **状态**: 待实施
> **创建日期**: 2026-10-03
> **依据**: 本次会话对 Sherry 文件工具链的核验 + 对标 omo（`/home/honor/Desktop/project/oh-my-openagent`）与 ZCode（`/home/honor/Desktop/project/ZCode`，源码核验）+ 既有 `对标计划_Zcode可借鉴能力.md`
> **目标**: 让主 agent 与并发子 agent 写同一个文件时**不静默丢改动**，并让写回**崩溃安全**
> **非目标**: 跨进程文件锁、行级哈希编辑（hashline）、工作树隔离、锁住 `terminal`/`python_repl` 的直接写入

---

## 1. 需求概述

### 1.1 现状（核验证据）

| 工具 | 现状 | 位置 |
| --- | --- | --- |
| `write_file` | 直接 `os.open(O_WRONLY\|O_CREAT\|O_TRUNC/O_APPEND)` 写目标，**无锁**、**非原子** | `agent/tools/file_tools/write_file.py:48-58` |
| `write_file`（`.py` + append） | 「append → 整文件读回 → 整文件重写」**两段写**，窗口更大 | `agent/tools/file_tools/write_file.py:102-106` |
| `patch_file` | **读 → 模糊替换 → `O_TRUNC` 整文件写回**，无锁、无版本校验（无 CAS） | `agent/tools/file_tools/patch_file.py:148-195` |
| `read_file` | 无锁；因写非原子，可能读到半写状态 | `agent/tools/file_tools/read_file.py` |
| 工具调用层 | `wrap_tool_call` 各中间件按各自职责工作，**没有按路径串行化** | `agent/middlewares/*/core.py` |

**并发是真实存在的**：

- 子 agent 拿的是与主 agent**同一批 `build_main_tools()` 单例**（同进程），默认 deny 只有 `sessions_spawn`/`sessions_yield`（`agent/tools/subagent/spawn/inherited_tool_policy.py:122`），即**子 agent 拥有读写/补丁工具**；
- `SUBAGENT` lane 默认并发 8（`config/features/infra_side/lane_system.py`），加上主 agent 与 `sessions_send` 嵌套回合，同进程内可以不只一个写者；
- 单个 agent 一次 turn 内工具调用是串行的，所以只有「单 agent 独占」场景是安全的。

**后果**：两个 agent 同时 `patch_file` 同一文件 → 后写者把前者已改内容整体覆盖，**两边都返回 success**（丢更新）；`O_TRUNC` 写大文件期间被 `read_file` 读到 → 撕裂读；进程在写中途崩溃 → 文件被截断。

**绕过路径（记录在案，不锁）**：`terminal`、`python_repl`、ast-grep 结构化重写都能直接写同一批文件，任何工具内锁都覆盖不到。

### 1.2 需求条目

| 编号 | 需求 | 说明 |
| --- | --- | --- |
| R1 | **写回原子化** | 临时文件 + `fsync` + `os.replace`，读者只会看到旧内容或新内容，不出现撕裂/截断；权限位保留；`rename` 不可用时降级为直写（warn） |
| R2 | **两层乐观并发校验（CAS）** | ① 工具层：`patch_file` 记录读取时的指纹（`mtime_ns` + `size` + 内容哈希），写前重取比对；② 写入 API 层：把 revision（`mtime:整毫秒:size`）传入原子写助手，在 `replace` 前再断言一次。任一层不一致即**拒绝**并提示重新读取，绝不静默覆盖 |
| R3 | **进程内按路径互斥** | 同一解析路径的 `write_file`/`patch_file` 临界区互斥（threading 锁），覆盖 `patch_file` 的读改写与 `write_file` 的 append+格式化两段写 |
| R4 | **错误可操作** | 冲突时返回结构化错误：`{"error": "...changed since ...", "path": ..., "hint": "重新 read_file 后再试"}`，模型据此重读重试 |
| R5 | **可观测** | 锁等待、CAS 拒绝、原子替换降级各留一条 loguru 日志（不新增埋点体系） |
| R6 | **对外契约不变** | 工具名、参数、返回结构、`PathGuard`/`_open_no_follow` 的边界与符号链接拒绝语义逐字节保持；非并发场景行为不变 |

### 1.3 设计约束

- **单进程假设**：所有 agent（主/子/嵌套）都在同一 server 进程内，`threading.Lock` 足以互斥；工具的 `_core` 是同步代码、由 `asyncio.to_thread` 调度，临界区内**不得 await**，因此不需要 asyncio 锁。
- **不破坏安全边界**：临时文件必须与目标同目录（同设备才能 `rename`）；`_open_no_follow` 的「拒绝软链终节点」语义必须保持（见 2.1 的差异说明）。
- **不引入死锁**：每个工具调用只持有一把路径锁，不做嵌套获取。
- **性能**：只在写路径加一次 `stat`/哈希与一次临时文件写入；无并发时开销可忽略（写本就比它贵）。

## 2. 技术方案

### 2.1 原子写助手（R1）— `agent/tools/pub_base/atomic_write.py`（新增）

```python
def atomic_write_text_no_follow(
    path: Path, text: str, expected_revision: str | None = None
) -> None:
    """同目录临时文件 + fsync + os.replace；拒绝软链终节点；可带写入前 revision 前置条件（CAS 的第二层）。"""
    st = path.lstat() if path.exists() else None
    if st is not None and stat.S_ISLNK(st.st_mode):
        raise OSError(errno.ELOOP, "Symbolic link not allowed")   # 保持现有语义
    if expected_revision is not None and _revision_id(st) != expected_revision:
        raise StaleWriteError(path)          # 工具层转成可操作错误（R4）
    mode = stat.S_IMODE(st.st_mode) if st is not None else 0o644  # 保留原权限（脚本执行位）
    fd, tmp = tempfile.mkstemp(dir=str(path.parent), prefix=".sherry-tmp-", suffix=".swp")
    try:
        with os.fdopen(fd, "w", encoding="utf-8", newline="") as f:
            f.write(text)
            f.flush()
            os.fsync(f.fileno())
        os.chmod(tmp, mode)
        if expected_revision is not None and _revision_id_of(path) != expected_revision:
            raise StaleWriteError(path)      # 临时文件写入期间目标又变了 → 放弃替换
        try:
            os.replace(tmp, path)            # rename 不跟随符号链接：目标此刻被换成软链也不会写到链接指向处
        except OSError:
            # 兜底：极少数文件系统/挂载不支持同目录 rename。退化为就地直写——保功能、放弃原子性
            # （ZCode 的 atomicWrite 同样是 temp+rename 失败后 fallback 到 O_TRUNC 直写）。
            _write_in_place_no_follow(path, text)
            with contextlib.suppress(OSError):
                os.unlink(tmp)
    except BaseException:
        with contextlib.suppress(OSError):
            os.unlink(tmp)
        raise


def _revision_id(st: os.stat_result | None) -> str:
    """`mtime:<整毫秒>:size:<字节>`，不存在时为 `absent`（对标 ZCode 的 revisionId）。"""
    return "absent" if st is None else f"mtime:{int(st.st_mtime_ns // 1_000_000)}:size:{st.st_size}"
```

**为什么不直接用 `pub/func/atomic_replace.py`**：它会对软链目标做 `realpath` 后**跟随写入**，而文件工具的策略是**拒绝**软链终节点（`_open_no_follow`）。两者语义相反，必须独立实现；方案里保留这个差异说明，避免后人误复用。

**append 语义**：`write_file(append=True)` 保持追加行为——非 `.py` 走 `O_APPEND`（持锁，见 2.3）；`.py` 因为要整体格式化，本就等价于「读全量 → 重写」，统一走原子写。

### 2.2 两层 CAS（R2/R4）

**第一层（工具层，指纹更细）**：在既有 `_core` 的读改写之间插入指纹校验：

```python
before = _fingerprint(resolved)          # (mtime_ns, size, sha256(bytes))
...  # 现有 读文件 → fuzzy_find_and_replace（不改）
if _fingerprint(resolved) != before:     # 写前重取；持锁下进行（2.3）
    return json.dumps({
        "error": "File changed on disk since it was read (another writer).",
        "path": display_path(resolved, root),
        "hint": "Re-read the file and re-apply the patch.",
    }, ensure_ascii=False)
atomic_write_text_no_follow(resolved, new_content, expected_revision=revision_of(before))
```

**第二层（写入 API 层，紧贴 replace）**：把 revision（`mtime:整毫秒:size`）**传进原子写助手**，由它在临时文件写完后、`rename` 前**再断言一次**。这层是 ZCode 的设计（`FileSystemPort.writeTextFile(expectedRevision)` → `assertExpectedRevision` → `stale_write`），价值是把「校验 → 替换」的空窗压到最小，且让任何调用方都拿到同一个前置条件，而不依赖工具层记得比对。

要点：

- 两层都保留：工具层的 sha256 能识别「mtime 变了但内容相同」的假冲突（ZCode 工具层同样有「完整读且内容一致则不算 stale」的豁免）；写入层的纯 revision 比对则便宜且离 `rename` 最近；
- 指纹在**同一把锁内**复取（2.3），CAS 是给「绕过锁的写者」（未来的跨进程/外部编辑器）兜底，锁是进程内主防线；
- 哈希用 `hashlib.sha256`，几 MB 文件开销在写路径可接受；`mtime_ns + size` 先比，命中再算哈希，避免白算；
- **校验 → 替换之间仍有理论空窗**（非原子 CAS）：这是与 ZCode 相同的已知边界，靠「空窗极小 + 内容哈希兜底 + 进程内锁」三重收窄，不宣称消除；
- `write_file` 是**盲覆盖**语义、不先读文件，因此默认不传 `expected_revision`（无前置条件）；若未来要给它也上 CAS，需要先引入 ZCode 式的「read-state + 先读才能写」契约（见 2.4 备选）；
- 拒绝时**返回错误而非抛异常**（`handle_tool_error` 语义：让模型看到结构化原因，可自行重读重试）。

### 2.3 进程内按路径锁（R3/R5）— `agent/tools/pub_base/path_lock.py`（新增）

```python
_locks: dict[str, _LockEntry] = {}      # key = str(resolved 绝对路径)
_guard = threading.Lock()

@contextlib.contextmanager
def path_lock(path: Path) -> Iterator[None]:
    key = str(path)
    with _guard:
        entry = _locks.get(key) or _locks.setdefault(key, _LockEntry())
        entry.users += 1
    t0 = time.monotonic()
    with entry.lock:                    # threading.Lock（临界区纯同步）
        waited = time.monotonic() - t0
        if waited > 0.05:
            logger.debug("file lock wait: {} {:.0f}ms", key, waited * 1000)
        try:
            yield
        finally:
            with _guard:
                entry.users -= 1
                if entry.users == 0:
                    _locks.pop(key, None)   # 引用计数归零即回收，字典不无界增长
```

覆盖点：`write_file._core` 与 `patch_file._core` 各自包住「读 → 改 → 写」整段（`write_file` 的 `.py` append 两次写也在同一临界区内）。

**为什么不用 subagent lane 解决**：lane 只限制并发**数量**，不保证「同一文件只被一个写者碰」；两个子 agent 写不同文件是完全正常的并行，不能为了文件安全把子 agent 串行化。

### 2.4 明确不做 / 备选

| 项 | 结论 | 理由 |
| --- | --- | --- |
| 跨进程锁 | **本期不做** | 全部 agent 在同一进程；未来要加可借鉴 omo `packages/memory-core/src/locks/acquire.ts`（pid + 进程启动身份 + nonce 的身份化锁文件、死主可证明回收、`link/rename` 原子发布、`waitTimeoutMs`） |
| read-state + 「先读才能写」契约 | **备选** | ZCode 的 Write/Edit 要求本会话先 Read 过该文件（`WRITE_NOT_READ_MESSAGE`），并把读时的 mtime/size 持久化为 read-state，恢复会话时水合。它是**盲覆盖也能 CAS 的前提**：`write_file` 目前是盲覆盖（不先读），所以本期拿不到它的前置条件。引入它需要新增一份「按会话的文件读状态」记录，且会改变现有工具契约（写新文件也可能被要求先读），改动面与收益都要单独评估 |
| hashline 行哈希编辑 | **备选** | omo 的 `hashline-core` 用 `行号#xxhash` 做编辑锚点，apply 时重读校验，别人改过的行直接 `HashlineMismatchError`（"N lines have changed since last read"）。它比整文件 CAS 精细（只对改动的行判冲突），但需要同时改造读工具的输出格式，改动面大 |
| 工作树隔离 + 加锁合并 | **远期** | omo `isolation-core`：并行任务跑在 COW 克隆/独立工作树里，改动以 patch/分支合并回主树，合并经 `<git-common-dir>/omo-isolation-merge.lock` 的身份化文件锁串行化（60s 等待，跨进程 + linked worktree 互斥）。Sherry 的子 agent 设计是直接写主树，改成隔离是架构级变更 |
| `terminal`/`python_repl` 直写 | **文档化，不锁** | 工具内锁管不到子进程；写入 AGENTS.md「Known Pitfalls」提示这一边界 |
| 目录 fsync | 可选 | 保证 rename 在掉电后也持久；本机开发场景收益低，作为阶段一的最后一个可选开关 |

> 定位说明：对标两家后，「乐观校验 + 原子写」是 ZCode（成熟 harness，**且完全没有文件写互斥锁**）与 omo（乐观哈希）的共同底座；本计划保留的三层里，ZCode 有前两层、omo 有更细的行级版本，**进程内按路径锁（阶段三）是 Sherry 相对两家的加码**——因为它与两家最大的不同是「子 agent 与主 agent 同进程、同工具单例、直接写主树」，一把进程内锁的成本极低而封堵最彻底。

## 4. 测试计划

| 用例 | 断言 |
| --- | --- |
| 并发 patch 不同片段（N=8 线程，各自持锁外读→写） | 全部片段生效；无丢更新 |
| 并发 patch 同一行片段 | 一个成功、其余返回 CAS 冲突错误（或按序列化顺序全部成功且内容一致） |
| 并发 write 同一文件 | 最终内容是某一个完整版本，绝不是两次写入的混合 |
| 读撕裂 | 大内容写入期间循环 `read_file`，每次内容 ∈ {旧, 新} |
| 第二层 CAS | 工具层校验通过后、`replace` 前目标被改 → `StaleWriteError`，文件保持外部写入的内容 |
| rename 兜底 | 注入 `os.replace` 失败 → 降级直写成功，工具仍返回成功且内容正确（记录一条 warn 日志） |
| 权限保留 | 可执行位为 0755 的文件经原子写后仍为 0755；原文件不存在时新建为 0644 |
| 非并发回归 | 现有 `test_path_hardening.py` / `test_external_access.py` / `test_virtual_paths.py` 全绿，返回文案不变 |
| 锁回收 | 压测后 `_locks` 为空；无 FD/临时文件泄漏 |
| 符号链接 | 目标为软链时仍然 `ELOOP` 拒绝（原子替换不得把软链替换成普通文件） |

## 5. 风险与回滚

- **inode 变更**：`os.replace` 换 inode → 硬链接会被断开、正在 `tail -f` 的读者句柄跟着旧 inode（记录为已知限制）；权限位在 helper 内显式保留。
- **兜底直写牺牲原子性**：`rename` 失败时退化为就地 `O_TRUNC` 写，此时撕裂读/崩溃截断的保护失效——仅作为「文件系统不支持同目录 rename」时的可用性兜底，触发时打 warn 日志（ZCode 采用同一取舍）。
- **校验 → 替换的理论空窗**：第二层 CAS 也非原子（stat 与 rename 之间），与 ZCode 的已知边界相同；不宣称消除，靠空窗极小 + 内容哈希兜底 + 进程内锁三重收窄。
- **临时文件残留**：崩溃时可能留下 `.sherry-tmp-*`；阶段一附「启动/工具入口清理超过 1 小时的残留」小逻辑。
- **锁粒度**：按路径互斥，不同文件不互相阻塞；若未来出现「成组写」需求再考虑排序加锁，当前不做嵌套锁。
- **回滚**：三段改动互相独立——CAS（阶段二）与锁（阶段三）各自可单独 revert；原子写（阶段一）退回直接写即为原行为。

## 一、问题

sherry 的 `read_file` 工具（`agent/tools/file_tools/read_file.py`）在分页**之前**
把整个文件读进内存，没有任何文件大小硬上限：

```python
# _read_bytes (read_file.py:189)
with os.fdopen(fd, "rb") as f:
    data = f.read()          # ← 整个文件，无大小守卫

# _paginate (read_file.py:268-270)
raw = decode_text(data, encoding)              # ← 整个文件解码成字符串
all_lines = raw.splitlines(keepends=True)      # ← 整个文件切成行列表
total_lines = len(all_lines)
page_lines = self._window(all_lines, offset, limit)  # ← 这才挑出 500 行
```

对一个 200 MB 的日志/minified 文件：

1. Python 读 200 MB bytes 对象进堆；
2. `decode_text` 解码成 200+ MB 字符串；
3. `splitlines` 生成全量行列表（又一个副本）；
4. `_window` 才从中挑出请求的 500 行。

**整个文件全程驻留堆上**，分页只是事后切片。最坏路径（一个 500 MB 的
minified JS bundle）会直接 OOM。下游的 ContextEviction / token 预算截断只在
**结果文本已经生成之后**才起作用——它们保护的是上下文，不是进程堆。

此外，sherry 缺少 ZCode 在 **schema 层**就拦截的二进制扩展名黑名单和设备文件
黑名单——`.exe`/`.zip`/`/dev/zero` 这些路径在 sherry 里要等到 `f.read()` 之后
的 `sniff_text_encoding` 才发现是二进制，大文件已经全量进堆了。

### 已有的保护（不够）

| 层 | 机制 | 位置 | 为什么不够 |
|---|---|---|---|
| token 预算 | `read_file_token_budget`（4000 token） | `_window` | 在**全量读进堆之后**才截断；保护上下文，不保护堆 |
| 单行硬上限 | `read_file_max_line_tokens`（4000 token） | `_window` | 同上，事后裁一行 |
| 行数窗口 | `file_tools_read_default_limit`（500 行） | schema | 只是 limit 参数默认值，不阻止全量读取 |
| 二进制检测 | `sniff_text_encoding` 返回 None | `_paginate` | **读完后**才判二进制；大文件已经进堆 |
| ContextEviction | 头尾 5 行预览 | middleware | 结果生成后才截断，堆已经爆了 |
| fd 直写 offload | `stdout_fd.py` | terminal/python_repl | **只覆盖命令输出，不覆盖 read_file** |
| PathGuard | 路径边界检查 | `resolve_tool_path` | 拦越界路径，不拦 `/dev/zero`（在 root 内）也不拦 `.exe` |

## 二、ZCode 的完整设计（参照基准）

### 2.1 双阈值 + 条件性 maxBytes

ZCode 有**两个独立阈值**：

| 常量 | 值 | 作用 |
|---|---|---|
| `READ_MAX_FILE_SIZE_BYTES` | 256 KiB | **整文件读**的拒绝阈值（仅无 offset/limit 时生效） |
| `FAST_PATH_MAX_BYTES` | 10 MiB | 快速路径（全量 readFile + slice）vs 流式路径（createReadStream）的分界 |

关键逻辑（`read-text.ts:42-49`）：

```typescript
const limitProvided = limit !== undefined;
maxBytes: limitProvided ? undefined : READ_MAX_FILE_SIZE_BYTES,
```

- **模型没传 limit（整文件读）**：`maxBytes = 256 KiB`。文件超过 → `assertWithinMaxBytes`
  抛 `too_large`，**不读一个字节**。
- **模型传了 limit（范围读）**：`maxBytes = undefined` → 直接 pass → 无论文件多大都
  进流式路径，**不拒绝**。

也就是说：**ZCode 从不在模型已经指定 offset/limit 时拒绝读取**——大文件 + 范围读 =
走流式，只有大文件 + 整文件读才拒绝。这避免了一个陷阱：模型想分段读大文件却被
拒绝、无从下手。

### 2.2 schema 级二进制扩展名黑名单 + 设备文件黑名单

```typescript
// contracts/src/tools/read.ts
const UNSUPPORTED_BINARY_EXTENSIONS = new Set([
  ".7z", ".a", ".bin", ".bz2", ".class", ".dll", ".dmg", ".dylib",
  ".exe", ".gz", ".jar", ".o", ".pyc", ".rar", ".so", ".tar", ".tgz",
  ".wasm", ".zip",
]);
const BLOCKING_DEVICE_PATHS = new Set([
  "/dev/console", "/dev/fd/0", "/dev/fd/1", "/dev/fd/2", "/dev/full",
  "/dev/random", "/dev/stderr", "/dev/stdin", "/dev/stdout", "/dev/tty",
  "/dev/urandom", "/dev/zero",
]);
```

在 **zod schema 的 superRefine** 里做——模型传 `.exe` 或 `/dev/zero` 时，schema
校验阶段就拒绝，**不开 fd、不 stat、不读**。sherry 的 `sniff_text_encoding` 是
读完整个文件后才判二进制，大文件已经全量进堆。

### 2.3 流式路径（`readRangeStreaming`）

```typescript
const stream = createReadStream(request.path);
for await (const chunk of stream) {
  const text = decoder.write(buffer);
  const parts = `${carry}${text}`.split("\n");
  carry = parts.pop() ?? "";
  for (const part of parts) {
    if (shouldSelectLine(lineIndex, offsetLine, limitLines, selectedLines.length)) {
      selectedLines.push(normalizeCompletedLine(part));
    }
    lineIndex += 1;  // ← 数到文件末尾，total_lines = lineIndex
  }
}
```

逐 chunk 读、解码、按 `\n` 切、数行号、只收集窗口内的行。**读整个文件但每次
只持有一个 chunk 在内存**。`totalLines` 是读完整个流才知道的（不从窗口结束处
seek 到 EOF——全量流式读一遍）。

编码嗅探（`detectEncodingFromHead`）：单独打开 fd 读前 4096 字节嗅探，处理 UTF-8
字符被截在中间的补字节（`getUtf8CompletionBytes`），再关掉 fd。

### 2.4 `truncatedByTokenCap` 区分截断原因

ZCode 的输出有两种 truncation：

- `truncated: true`（无 `truncatedByTokenCap`）→ 文件还有更多行（行数窗口到顶）
- `truncated: true` + `truncatedByTokenCap: true` → token 预算到顶（内容被裁了）

模型可以据此判断「加大 offset 继续」还是「缩范围」。

### 2.5 整读 vs 范围读的 token 降级

```typescript
allowPartialFallback: allowPartialFallback ?? isInitialWholeFileRead(offset, limit),
```

- **整文件读** + token 超限 → 创建 partialView（二分搜索找最大前缀，优雅降级）
- **范围读** + token 超限 → **直接 throw error**（模型要的太多了，必须缩小范围）

### 2.6 ZCode 没有而 sherry 已有的（不抄）

| sherry 已有 | ZCode 对应 | 为什么 sherry 的更好 |
|---|---|---|
| `_window` 行走时按 token 停 | 读完所有行后二分搜索裁前缀 | sherry 不读不返回的行，省内存 |
| `_LINE_TOKEN_CAP` 单行硬裁 | char 级二分搜索前缀 | sherry 的更直接，不碰超长行 |
| write license（read-before-write） | 无 | sherry 独有，保护写操作 |
| CJK 感知 token 估算 | `estimateTokens`（非 CJK 感知） | sherry 的对中日韩更准 |

## 三、改动方案

### 设计原则

1. **双阈值**：拒绝阈值（整文件读）+ 流式阈值（快速/流式分界），不混为一个。
2. **条件性拒绝**：只在模型没传 limit（整文件读）时拒绝大文件；传了 limit 就放行进流式。
3. **schema 级黑名单**：二进制扩展名 + 设备文件在 pydantic validator 里拒绝，不开 fd。
4. **流式行扫描**：超流式阈值的文件逐 chunk 读、数换行符定位窗口，不全量载入堆。
5. **`truncated_by_token_cap`**：区分「行数到顶」vs「token 预算到顶」。
6. **保留所有现有语义**：token 预算裁断、单行 clip、write license、CJK 估算、行号格式、
   hint 引导全部不变。

### 3.2 新增 schema 级黑名单（`agent/tools/file_tools/read_file.py`）

在 `ReadFileInput` 加 pydantic validator：

```python
#: 二进制扩展名黑名单——schema 级拒绝，不开 fd、不 stat、不读。
#: 对齐 ZCode 的 UNSUPPORTED_BINARY_EXTENSIONS。sherry 额外加 .db / .sqlite
#: / .lock（SQLite/锁文件是 sherry 项目里常见的大二进制文件）。
_BINARY_EXTENSIONS: frozenset[str] = frozenset({
    ".7z", ".a", ".bin", ".bz2", ".class", ".dll", ".dmg", ".dylib",
    ".exe", ".gz", ".jar", ".o", ".pyc", ".rar", ".so", ".tar", ".tgz",
    ".wasm", ".zip",
    # sherry 追加：项目里常见的大二进制/数据库文件
    ".db", ".sqlite", ".sqlite3", ".lock", ".swp", ".swo",
})

#: 设备文件黑名单——这些路径会产生无限输出或阻塞。对齐 ZCode 的
#: BLOCKING_DEVICE_PATHS。Windows 没有这些路径，但 validator 统一拦。
_BLOCKING_DEVICE_PATHS: frozenset[str] = frozenset({
    "/dev/console", "/dev/fd/0", "/dev/fd/1", "/dev/fd/2", "/dev/full",
    "/dev/random", "/dev/stderr", "/dev/stdin", "/dev/stdout", "/dev/tty",
    "/dev/urandom", "/dev/zero",
})


class ReadFileInput(BaseModel):
    file_path: str = Field(...)
    offset: int = Field(default=1, ge=1, ...)
    limit: int = Field(default=_READ_DEFAULT_LIMIT, ge=1, le=_READ_MAX_LIMIT, ...)
    session_id: SessionId = ""

    @model_validator(mode="before")
    @classmethod
    def _reject_binary_and_device_paths(cls, values: Any) -> Any:
        if not isinstance(values, dict):
            return values
        path = values.get("file_path")
        if not isinstance(path, str) or not path:
            return values
        lower = path.lower()

        # 设备文件
        if lower in _BLOCKING_DEVICE_PATHS:
            raise ValueError(
                f"Cannot read '{path}': this device file would block or "
                f"produce infinite output."
            )

        # 二进制扩展名
        ext = _file_extension(lower)
        if ext in _BINARY_EXTENSIONS:
            raise ValueError(
                f"This tool cannot read binary files. The file appears to be "
                f"a binary {ext} file. Use terminal (file/xxd/strings) to "
                f"inspect it."
            )
        return values


def _file_extension(lower_path: str) -> str | None:
    """Extract the file extension from a lowercased path."""
    # 同时处理 / 和 \（Windows）
    last_sep = max(lower_path.rfind("/"), lower_path.rfind("\\"))
    basename = lower_path[last_sep + 1:]
    dot = basename.rfind(".")
    if dot <= 0:
        return None
    return basename[dot:]
```

> **注意**：pydantic 的 `model_validator(mode="before")` 抛 `ValueError` 会被
> LangChain 的 `handle_tool_error=True` 捕获，作为 ToolException 返回给模型。
> 需要确认这个路径在现有的 `_validate_commands` validator 之上叠加不冲突——
> 现有的 validator 只处理 `commands` 字段（ShellInput 遗留），read_file 没有
> before-validator，所以是新增。

### 3.3 新增流式行扫描模块（`agent/tools/pub_base/stream_read.py`）

```python
"""Stream-based line reader for oversized files.

Used by read_file when the file exceeds ``read_file_fast_path_threshold_bytes``:
instead of ``f.read()`` the whole file, this reader scans for newlines in
fixed-size chunks via ``os.read(fd, chunk)``, yielding only the lines in the
requested [offset, offset+limit) window. The file's bytes never ride the
Python heap in full — at most one chunk + one carry string + the collected
window lines are held at any time.

The encoding is sniffed from the first chunk (same ``sniff_text_encoding``
the whole-file path uses), then the reader decodes chunk-by-chunk. A BOM is
stripped once at the head. UTF-8 multi-byte sequences split across chunk
boundaries are handled by the incremental decoder
(``codecs.getincrementaldecoder``).

Design aligned with ZCode's ``readRangeStreaming``
(``adapters/src/fs/text-range-reader.ts``): ZCode reads the entire stream
through to count ``totalLines``; this implementation does the same — it
reads chunk by chunk to EOF, selecting only the window's lines but counting
every line for an accurate total. The cost is one full sequential read of
the file (kernel-page-cache hot after the first chunk), but the peak heap
is O(chunk_size + window_lines) not O(file_size).
"""
```

核心接口：

```python
def read_line_window(
    fd: int,
    offset: int,          # 1-indexed start line
    limit: int,           # max lines to return
    encoding: str | None, # None = sniff from first chunk
    chunk_bytes: int = 65_536,
) -> tuple[list[str], int, str | None, bool]:
    """Read lines [offset, offset+limit) from an open fd without loading the
    whole file into memory.

    Reads the file sequentially from start to EOF in fixed-size chunks,
    counting every newline for an accurate ``total_lines`` and collecting
    only the lines in the requested window. Peak memory is
    O(chunk_bytes + len(window_lines)), not O(file_size).

    :returns: ``(page_lines, total_lines, encoding, is_binary)``
        - ``page_lines``: the lines in [offset, offset+limit), keepends=True
        - ``total_lines``: exact total line count (read to EOF)
        - ``encoding``: the sniffed/used encoding, or None if binary
        - ``is_binary``: True if the file was detected as binary
    """
```

实现要点：

1. **编码嗅探**：读第一个 chunk（64 KiB），`sniff_text_encoding` 判定编码。
   二进制 → 返回 `(=[], 0, None, True)`。UTF-8 BOM 剥一次。
2. **增量解码**：用 `codecs.getincrementaldecoder(encoding)(errors="replace")`
   逐 chunk 解码，处理 UTF-8 多字节序列被 chunk 边界截断的情况（对齐 ZCode 的
   `createStreamingTextDecoder` + `getUtf8CompletionBytes`）。
3. **行切分**：`carry + decoded_text` 按 `\n` 切，最后一个元素是 carry（不完整行），
   留到下一个 chunk。CRLF 的 `\r` 在行尾 `rstrip` 掉（对齐 ZCode 的
   `normalizeCompletedLine`）。
4. **行计数 + 窗口收集**：每个完整行 `line_index += 1`；当
   `offset <= line_index < offset + limit` 时收集到 `page_lines`。
5. **读到 EOF**：继续读直到文件结束，`total_lines = line_index`。窗口收集满后
   只数行不收集（不提前 break——需要精确 total_lines）。
6. **末尾 carry**：流结束后 `decoder.end()` 拿残余，如果非空且 `sawAnyBytes`，
   算最后一行。

### 3.4 修改 `read_file.py` 的 `_read_bytes` + `_paginate`

**`_core` 入口加条件性拒绝（对齐 ZCode 的 `limitProvided ? undefined : maxBytes`）：**

```python
def _core(self, file_path, offset=1, limit=_READ_DEFAULT_LIMIT, session_id=""):
    root, resolved, error = resolve_tool_path(...)
    if error is not None or resolved is None or root is None:
        return error or tool_error("Could not resolve the path")

    if not resolved.exists():
        return json.dumps({"error": f"File not found: {display_path(resolved, root)}"}, ...)
    if resolved.is_dir():
        return json.dumps({"error": f"Path is a directory: ..."}, ...)

    try:
        file_size = resolved.stat().st_size
    except OSError:
        file_size = 0

    # ★ 条件性整文件读拒绝（对齐 ZCode 的 maxBytes 条件）
    # 模型没传 limit（想读整个文件）且文件超过拒绝阈值 → 直接拒绝
    limit_was_explicit = limit != _READ_DEFAULT_LIMIT  # 模型显式传了 limit
    if (
        _MAX_WHOLE_READ > 0
        and not limit_was_explicit
        and file_size >= _MAX_WHOLE_READ
    ):
        return json.dumps({
            "error": (
                f"File is {file_size} bytes ({file_size / 1024:.1f} KiB), "
                f"exceeding the {_MAX_WHOLE_READ} byte whole-read limit. "
                f"Use offset and limit to read it in sections."
            ),
            "path": display_path(resolved, root),
            "file_size": file_size,
            "hint": (
                "This file is too large to read whole. "
                f"Use offset=1&limit={_READ_DEFAULT_LIMIT} to read the first "
                f"{_READ_DEFAULT_LIMIT} lines, or use search_files to find "
                f"specific content."
            ),
        }, ensure_ascii=False)

    # ★ 快速 vs 流式分流（对齐 ZCode 的 FAST_PATH_MAX_BYTES）
    if _FAST_PATH_THRESHOLD > 0 and file_size >= _FAST_PATH_THRESHOLD:
        return self._paginate_streaming(resolved, root, file_size, offset, limit, session_id)

    # 小文件：保持现有路径（全量读 + splitlines + window）
    with file_read_lock(resolved):
        data, read_stat, error = self._read_bytes(resolved)
        if error is not None or data is None or read_stat is None:
            return error or tool_error("Failed to read file")
        return self._paginate(resolved, root, data, read_stat, file_size, offset, limit, session_id)
```

> **`limit_was_explicit` 的判定**：pydantic schema 的 `limit` 有 default
> (`_READ_DEFAULT_LIMIT = 500`)，模型不传 limit 时 pydantic 填默认值。要区分
> 「模型传了 500」和「模型没传、默认 500」，需要在 `ReadFileInput` 的
> `limit` 字段用 `default=None` + validator 填默认值，或者在 `_run`/`_arun`
> 的签名上用 `limit: int | None = None` 判断。后者改动更小：

```python
def _run(self, file_path, offset=1, limit=None, session_id="", run_manager=None):
    limit = _READ_DEFAULT_LIMIT if limit is None else limit
    session_id = resolve_tool_session_id(session_id, run_manager)
    return self._core(file_path, offset, limit, session_id, limit_was_explicit=limit is not None)
```

实际上更干净的做法是改 `ReadFileInput.limit` 的 default 为 `None`，加
`@model_validator(mode="before")` 填默认值——这样 `_core` 直接看 `limit is None`
就知道是不是显式传的。但这会改变 schema 的 `default` 属性（模型看到的 limit
描述变），需要同步更新 description。**推荐用 `_run`/`_arun` 签名 `limit: int | None
= None` + 内部填默认值**，schema 的 `args_schema` 不变（LangChain 从 kwargs 取
值，`None` 不传给 pydantic）。

等等——LangChain 的 `BaseTool` 通过 `args_schema` 做参数校验和 schema 生成。
改 `_run` 签名不影响 schema（schema 由 `args_schema` 决定），但 LangChain 调
`_run` 时传的是 pydantic 校验后的值（limit=500），不是 None。所以
`limit_was_explicit` 无法通过 `_run` 签名判断。

**最终方案**：在 `ReadFileInput` 里加一个内部字段：

```python
class ReadFileInput(BaseModel):
    file_path: str = Field(...)
    offset: int = Field(default=1, ge=1, ...)
    limit: int = Field(default=_READ_DEFAULT_LIMIT, ge=1, le=_READ_MAX_LIMIT, ...)
    session_id: SessionId = ""

    @model_validator(mode="before")
    @classmethod
    def _tag_explicit_limit(cls, values):
        """Tag whether limit was explicitly provided (for whole-read refusal)."""
        if isinstance(values, dict):
            values["_limit_explicit"] = "limit" in values and values["limit"] is not None
        return values
```

然后在 `_run` 里从 `**kwargs` 取 `_limit_explicit`，或者改 `_run` 接收完整
`ReadFileInput` 实例。LangChain 的 `BaseTool` 默认解包参数到 kwargs，所以
`_limit_explicit` 会在 `**kwargs` 里。可行但侵入。

**更简单的替代**：不改 schema，在 `_core` 里用 `file_size` 单独判断——如果文件
小于 `_MAX_WHOLE_READ`，无论 limit 是否显式都走快速路径；如果文件大于
`_MAX_WHOLE_READ` 且 `offset == 1 and limit >= _READ_MAX_LIMIT`（模型在尝试
读很多行），才拒绝。这跟 ZCode 的「limitProvided」不完全等价但语义接近：
模型传了 limit（哪怕值很大）说明它知道文件大、在分段读，放行；模型没传 limit
（default 500）且文件大，拒绝。

```python
# 简化判定：文件大于拒绝阈值 + offset==1 + limit==default → 整文件读意图
whole_read_attempt = offset == 1 and limit == _READ_DEFAULT_LIMIT
if _MAX_WHOLE_READ > 0 and whole_read_attempt and file_size >= _MAX_WHOLE_READ:
    return refusal_json
```

这个判定有一个边界漏洞：模型传 `limit=500`（跟 default 相同）会被判为「没显式
传」。但语义上它跟 default 一样，所以拒绝是对的——模型用 default limit 读大文件
本来就应该被劝退。**采用这个简化方案**。

**新增 `_paginate_streaming`（大文件流式路径）：**

```python
def _paginate_streaming(
    self,
    resolved: Path,
    root: Path,
    file_size: int,
    offset: int,
    limit: int,
    session_id: str,
) -> str:
    """大文件流式路径：逐 chunk 行扫描，不全量载入堆。"""
    fd = _open_no_follow(resolved, os.O_RDONLY)
    try:
        page_lines, total_lines, encoding, is_binary = read_line_window(
            fd, offset, limit, encoding=None, chunk_bytes=_STREAM_CHUNK
        )
    finally:
        try:
            os.close(fd)
        except OSError:
            pass

    if is_binary or encoding is None:
        return json.dumps({
            "error": (
                f"File is binary or not UTF-8/UTF-16 text ({file_size} bytes); "
                f"read_file shows text only."
            ),
            "path": display_path(resolved, root),
            "hint": "Use terminal (file/xxd/strings, or python) to inspect.",
        }, ensure_ascii=False)

    # 喂给 _window 做 token 预算裁断（跟小文件路径一致的裁断语义）
    page_lines, spent_tokens, clipped = self._window(page_lines, 1, limit)

    end_line = offset + len(page_lines) - 1
    page_text = "".join(page_lines)
    if page_text.endswith("\n"):
        page_text = page_text[:-1]
    numbered_content = _add_line_numbers(page_text, offset) if page_text else ""

    # 大文件流式路径永远 truncated（不可能一页读完），且永远不发 write license
    truncated = True

    result = {
        "content": numbered_content,
        "total_lines": total_lines,
        "file_size": file_size,
        "truncated": truncated,
        "oversized": True,  # 新标记：走了流式路径
    }
    # hint + truncated_by_token_cap
    hint = f"Use offset={end_line + 1} to continue reading (showing {offset}-{end_line} of {total_lines} lines"
    if clipped:
        hint += (
            "; one line alone exceeded the whole budget and was clipped"
            " — read_file cannot page INSIDE a line, so for that line's"
            " remainder use search_files / terminal (head -c / tail -c) / python_repl"
        )
    if _TOKEN_BUDGET > 0:
        hint += f", ~{int(spent_tokens)} tokens of the {_TOKEN_BUDGET} budget"
    result["hint"] = hint + ")"
    return json.dumps(result, ensure_ascii=False)
```

### 3.5 新增 `truncated_by_token_cap` 字段

在小文件路径的 `_paginate` 和大文件路径的 `_paginate_streaming` 里都加：

```python
# _window 返回值已经有 clipped（单行被裁）和 spent_tokens（token 花费）
# truncated_by_token_cap: token 预算到顶（spent >= target）导致截断
# vs 纯 truncated: 行数到顶（total_lines > end_line）
truncated_by_token_cap = spent_tokens >= (_TOKEN_BUDGET * _BUDGET_RATIO) if _TOKEN_BUDGET > 0 else False

result["truncated_by_token_cap"] = truncated_by_token_cap
```

模型据此判断「加大 offset 继续」还是「缩 limit 范围」。

### 3.7 `_line_token_cost` 短路（对齐 ZCode 性能）

**问题**：`_line_token_cost`（`read_file.py:86-93`）逐字符走完整个行才算出
token 成本，不短路。它的调用方 `_window` 只需要判断「这一行是否超过
`per_line_cap`」，不需要精确值。对 500 MB 的不换行 minified 文件，它会走 5 亿次
`ord()` + `is_cjk_codepoint()`——约 50 秒，而结论在第 ~13600 个字符时就已经确定了。

ZCode 的等价场景用二分搜索（`findLargestPrefixCharsWithinTokenBudget`）O(log n)
解决；sherry 不需要二分搜索（`_window` 行走时裁是一步到位的），但需要短路来避免
O(file_size) 的全行扫描。

**改法**：给 `_line_token_cost` 加 `cap` 参数，超过 cap 立即返回：

```python
def _line_token_cost(line: str, *, cap: float | None = None) -> float:
    """One line's token cost, CJK-aware.

    With ``cap`` set, returns as soon as ``total`` exceeds it — the caller
    only needs to know "is this line over the cap", not the exact cost, so
    a 500 MB minified line short-circuits at ~13600 chars instead of walking
    500 million. Without ``cap`` the behavior is byte-identical to before.
    """
    total = 0.0
    for char in line:
        total += (
            1.0 / _CHARS_PER_TOKEN_CJK if is_cjk_codepoint(ord(char)) else 1.0 / _CHARS_PER_TOKEN
        )
        if cap is not None and total > cap:
            return total
    return total
```

`_window` 的调用处改成传 `cap=per_line_cap`：

```python
# _window 内部（read_file.py:368）
cost = _line_token_cost(line, cap=per_line_cap)
```

**效果**：不换行的 500 MB 文件从 ~50 秒降到微秒级（走到 ~13600 字符就短路）。
正常多行文件不受影响（每行都很短，走完也不会超 cap，行为不变）。

**不影响精度**：`_window` 只在 `cost > per_line_cap` 时裁断，短路返回的 `total`
已经大于 cap，判断结果与走完全行的精确值一致。`cost <= per_line_cap` 的行会
走完全行（没有短路），返回精确值，用于 `spent` 累加——这部分行为不变。

## 四、边界情况与兼容性

| 情况 | 处理 |
|---|---|
| `_MAX_WHOLE_READ = 0`（禁用拒绝） | 不拒绝整文件读；大文件仍走流式（如果 ≥ FAST_PATH_THRESHOLD） |
| `_FAST_PATH_THRESHOLD = 0`（禁用流式） | 全量读路径，byte-for-byte 历史行为 |
| 模型传 limit=500（等于 default）+ 大文件 | 判定为整文件读意图（`offset==1 and limit==default`），拒绝 |
| 模型传 limit=2000 + 大文件 | `limit != default` → 不拒绝，走流式路径 |
| 模型传 offset=2 + 大文件 | `offset != 1` → 不拒绝（模型在分段读），走流式路径 |
| 文件刚好等于拒绝阈值 | 拒绝（`>=` 判断），安全侧 |
| 文件刚好等于流式阈值 | 走流式路径 |
| 二进制大文件 + 扩展名在黑名单 | schema 级拒绝，不开 fd |
| 二进制大文件 + 扩展名不在黑名单（如 .log 实为二进制） | 流式路径的编码嗅探返回 is_binary → 报二进制错误 |
| UTF-16 大文件 | 增量解码器按 UTF-16 解码每 chunk（`codecs.getincrementaldecoder("utf-16")`） |
| UTF-8 多字节序列被 chunk 边界截断 | 增量解码器自动处理（`getincrementaldecoder` 的核心能力） |
| offset 超过总行数 | 流式 reader 读到 EOF 没找到对应行 → 返回空 page + total_lines |
| 单行超 chunk 大小 | 累积多个 chunk 直到遇换行；仍超 `_LINE_TOKEN_CAP` 则裁断 + clipped |
| write license | 大文件永远 `truncated=True`，不发 license |
| `_unchanged_since_last_read` | 大文件永远走不到 stub（它要求 license 非空） |
| revision_id | 流式路径仍从 `os.fstat` 拿 stat，`revision_id` 有效 |
| ContextEviction | 流式路径返回的 page 已被 `_window` 裁到 ≤ token 预算，ContextEviction 无需特殊处理 |
| 现有测试 `test_tool_schema_goldens.py` | schema 的 `ReadFileInput` 字段不变（limit 仍有 default 500），validator 是 before-mode 不改 schema shape |

## 七、不做的事

- **不改 `_window` 的 token 预算 / 单行 clip 逻辑**：大文件路径的 page_lines 走
  同样的 `_window` 裁断，保持一致。sherry 的行走时裁比 ZCode 的事后二分搜索更好。
- **不加 read_file 的 fd-offload 路径**：文件本身在磁盘上，模型用 offset/limit
  回去读，不需要 offload 到 `evicted/`。
- **不改 ContextEviction**：大文件路径返回的 page ≤ token 预算，无需改动。
- **不改行号格式**：sherry 用 `N|content`，ZCode 用 `N\tcontent`，各自的既有契约，
  不对齐。
- **不改 partialView 通知格式**：sherry 用 JSON `hint`，ZCode 用 `<system-reminder>`，
  不对齐。
- **不加 `allowPartialFallback` 语义**：ZCode 在范围读 token 超限时 throw、整文件读
  时 partialView。sherry 的 `_window` 行走时裁让「读完后才发现超 token」不发生，
  这个区分没有意义。
- **流式路径不 seek 到 EOF 数剩余行**：对齐 ZCode——读整个流数行，total_lines 精确。
  seek-to-EOF 方案更快但 total_lines 是近似值（窗口后的文件可能被改），不值得。

## 八、与 ZCode 的对齐度

| ZCode 机制 | 本计划 | 对齐 |
|---|---|---|
| `READ_MAX_FILE_SIZE_BYTES` 整文件读拒绝 | `read_file_max_whole_read_bytes` (256 KiB) | ✅ |
| 条件性 maxBytes（仅无 limit 时拒绝） | `offset==1 and limit==default` 判定 | ✅（语义等价） |
| `FAST_PATH_MAX_BYTES` 快速/流式分界 | `read_file_fast_path_threshold_bytes` (10 MiB) | ✅ |
| `readRangeStreaming` 逐 chunk 流式行扫描 | `read_line_window` + 增量解码器 | ✅ |
| `detectEncodingFromHead` 头部嗅探 | 第一 chunk `sniff_text_encoding` | ✅ |
| UTF-8 补字节 (`getUtf8CompletionBytes`) | `codecs.getincrementaldecoder` 自动处理 | ✅（更通用） |
| `UNSUPPORTED_BINARY_EXTENSIONS` schema 黑名单 | `_BINARY_EXTENSIONS` pydantic validator | ✅ |
| `BLOCKING_DEVICE_PATHS` 设备文件黑名单 | `_BLOCKING_DEVICE_PATHS` validator | ✅ |
| `truncatedByTokenCap` 区分截断原因 | `truncated_by_token_cap` 字段 | ✅ |
| 不换行超长行性能（ZCode 二分搜索 O(log n)） | `_line_token_cost` 短路 O(cap) | ✅（路线不同，效果对齐） |
| `READ_MAX_OUTPUT_TOKENS` token 预算 | `read_file_token_budget` (已有，4000) | ✅（sherry 更低但已有） |
| `READ_DEFAULT_MAX_LINES` 默认行数 | `file_tools_read_default_limit` (已有，500) | ✅ |
| `partialViewNotice` `<system-reminder>` | JSON `hint` | ❌ 不对齐（各有契约） |
| `allowPartialFallback` 整读/范围读降级 | 不做（`_window` 行走时裁让此问题不存在） | ❌ 不需要 |
| `file_unchanged` 独立输出类型 | `_UNCHANGED_STUB` 内容桩 | ❌ 不对齐（各有契约） |
| 行号格式 `N\tcontent` | `N|content` | ❌ 不对齐（各有契约） |
| write license | sherry 独有，ZCode 无 | sherry 多一个 |

**实质对齐**：11/14 项。3 项不对齐是各自既有契约差异（行号格式、通知格式、
unchanged 输出类型），不改——改了会破坏现有的模型行为契约和测试 golden。

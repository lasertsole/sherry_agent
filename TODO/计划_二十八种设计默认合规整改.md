# 计划：二十八种设计默认（系统设计核心概念）合规整改

- 日期：2026-10-26 · 分支：dev · 状态：待执行
- 审计依据：Alina Kovtun《28 Core System Design Concepts, Explained Through the
  Failures They Prevent》（Medium / Women in Technology，2026-06）。
  已核实锚点：1 客户端-服务器、2 IP 地址、3 DNS、4 反向代理、5 负载均衡 …
  25 WebSockets、26 Webhooks、27 幂等、28 限流；中段（6–24）按原文"请求旅程"
  三段式（发送请求 → 应用与存储 → 可靠性与异步通信）自经典体系重构，原文正文
  在付费墙后。**审计按概念名逐条对照，不依赖编号**；若后续拿到原文全表，仅
  总览表的编号列需对齐，七个整改项不受影响。
- 审计方式：逐概念在代码中找正反证据（file:line 见各节），不是按清单打勾。

## V1（P2）排队队列用伪造时间戳表达优先级

**概念 #14 消息队列。**

- 现状：`send_now`（立刻发送）把目标行 `created_at` 重排到该会话所有排队行
  最小值之下，再取消当前回合让 drain 先领它——
  `server/trigger/ws/messages.py:287-298`、
  `server/queue/user_input_queue.py::prioritize`（`_PRIORITIZE_SQL`）。
  AGENTS.md 明言"`ORDER BY created_at` 是唯一排序规则，没有优先级列"。
- 为什么不规范：时间戳不再表示时间。审计/调试时一行消息的"创建时间"是伪造
  值；任何按 `created_at` 做的新功能（过期清理窗口、UI 相对时间显示）都建立在
  被污染的数据上。这是把缺一列 schema 编码进数据值里。
- 整改：
  1. `user_input_queue` 加列 `priority INTEGER NOT NULL DEFAULT 0`（走该 store
     已有的一次性 migration 机制，`server/queue/user_input_queue.py:16`）。
  2. `claim_next` 的 `_CLAIM_NEXT_SQL` 排序改为 `ORDER BY priority DESC,
     created_at ASC`；`prioritize` 改为 `UPDATE ... SET priority = 1`，不再碰
     `created_at`。
  3. `queued_min_created_at` 辅助函数删除（只服务于重排）。
  4. WS 帧协议不变（`send_now` 语义照旧），客户端零改动。
- 验证：`tests/server/queue/` 现有 send_now 用例改断言"priority=1 且
  created_at 不变"；补一条"两行同 priority 时仍按 created_at FIFO"。
- 工作量：小（一个 migration + 两处 SQL + 测试）。

## V2（P1）web_fetch 远程分支单发无重试

**概念 #20 重试与退避。**

- 现状：`agent/tools/web_fetch.py` 远程分支（`safe_fetch`，约 160-175 行）单次
  尝试，失败直接返回错误串。瞬时网络抖动（连接重置、DNS 抖动、5xx）会作为
  工具失败暴露给模型，模型只能再花一整轮工具往返重发——重试成本从"毫秒级
  库内重试"变成"一次 LLM 决策 + 全上下文重读"。
- 对照：同项目内 LLM 侧已有完整 ZCode 对齐的重试层（11 次预算、指数退避、
  Retry-After），Tavily 也有有界重试——缺口只在 web_fetch。
- 整改：在 `safe_fetch` 外包一层有界重试——只对**分类为瞬时**的失败（连接
  错误、超时、HTTP 502/503/504）重试 1 次，固定 1s 间隔（不做指数退避，2 次
  封顶）；4xx、非公开 URL、超限类失败不重试。判定复用
  `pub/func/retry_policy.py` 的分类思路，不新造分类器。
- 验证：单测打桩 `safe_fetch` 第一次抛 `httpx.ConnectError`、第二次成功，断言
  结果 ok 且调用 2 次；4xx 断言只调 1 次。
- 工作量：小。

## V3（P1）SearXNG 无失败记忆（缺熔断/冷却）

**概念 #21 熔断器。**

- 现状：SearXNG 实例宕机/配错时，每次 `web_search` 都付全额
  `web_search_timeout_seconds`（`agent/tools/web_search_searxng.py:30,100`），
  失败后零记忆；且按设计 SearXNG 永不回退 Tavily（`agent/tools/web_search.py:15`）
  ——自持部署没有 key 是对的，但代价是死实例让每个搜索都拖着超时尾巴。
- 对照：LLM 侧有 stale-streak 熔断（连续 5 次超时中止当回合）；搜索后端没有
  任何等价物。
- 整改：进程级连续失败计数 + 冷却窗——连续 3 次失败（超时或连接错误）把
  SearXNG 标记为"冷却中"持续 60s；冷却期间 `resolve_preferred_backend` 把它
  视为未配置（现有的"显式选择仅在提供方已配置时有效"规则自然接管：切到
  可用的 Tavily 或返回桩结果），恢复后自动解冻。冷却进入/退出各推一次已有的
  `search_backend_fallback` 播报帧。计数器仿照 sticky fallback 用进程级状态，
  不进寄存器。配置进 `WEB_SEARCH_CONFIG`（`failure_threshold`、
  `cooldown_seconds`）。
- 验证：单测模拟 3 连失败后第 4 次调用不再触网（直接走 Tavily/桩）；
  60s 后（打桩时钟）恢复直连。
- 工作量：中。

## V4（P2）无进程级 /health 端点

**概念 #22 健康检查。**

- 现状：`server/trigger/http/` 有 40+ 路由模块，无任何 health/readiness 端点
  （仅 STT 的 `/audio/transcribe/status`、auth 的 `/auth/status`、sandbox 状态
  等领域级状态）。客户端连通性横幅只能拿 WS 证据当判据（记忆中
  navigator.onLine 在 webview 恒 false 的问题正是被这个缺口逼出来的）。
- 整改：新增 `server/trigger/http/health.py` 注册 `GET /health`（公开路径，走
  网关中间件），返回 `{ok, version, uptime_s, models_configured,
  live_sessions, queue_depth}`。只做进程自检（不探测下游），保证 O(1)、永不
  抛 5xx。客户端 `stores` 的连通性判定增加一个 HTTP 探测兜底（WS 没判决时），
  与现有横幅逻辑并存。
- 验证：路由单测 + 手工 `curl 127.0.0.1:8080/health`。
- 工作量：小。

## V5（P2）日志无保留策略

**概念 #23 可观测性。**

- 现状：`logs/output/json/json_<date>_<pid>.log` 按进程累积，代码库内无任何
  轮转/清扫（grep rotation/rotate 仅命中 auth 黑名单清理）。长期运行的桌面
  后端日志目录无限增长；排障时也无法用"保留 N 天"快速圈定范围。
- 整改：仿 `auth_service.start_blacklist_cleanup()` 的启动清扫 + 周期清扫：
  boot 时与每 24h 删 `logs/output/json` 下 mtime 早于 `LOGS["retention_days"]`
  （默认 14）的文件，并对目录总量设上限（超过 `LOGS["max_total_mb"]` 默认
  512 时从最旧进程文件删起）。配置进 `config/features/infra_side/` 新
  `LOGS` 键。与 per-PID 命名正交，不动 loguru 接线。
- 验证：单测造旧文件断言被删、新文件保留；上限分支同样。
- 工作量：小。

## V6（P2）POST /sessions/side_chat 创建无幂等键

**概念 #27 幂等。**

- 现状：`server/service/side_chat_service.py` 创建辅助会话是一次性 fork（复制
  父 checkpoint + 全套会话设置），无任何去重。客户端 POST 超时/断线后重发、
  或用户在网络抖动下重试点开侧聊，会产生第二个完整 fork——成本高（整份
  checkpoint 拷贝）且两个子会话都会出现在会话列表里。
- 对照：用户消息已有 `client_msg_id` 全链路去重（ACTIVE + DELIVERED 24h 窗）；
  spawn 有 plan 哈希幂等；文件写有 CAS。唯独这个高成本 POST 裸奔。
- 整改：请求体加可选 `client_request_id`；`side_chats` 表（`src/data/side_chats.db`）
  加唯一键 `(parent_session_id, client_request_id)`，命中即返回已有子会话
  （200 带 `deduplicated: true`）。客户端 `createSideChatSession` 生成并随重试
  复用同一 id（复用 client_msg_id 的生成器）。老请求不带 id 走原路径，兼容。
- 验证：服务单测同 id 二次创建返回同一 session_id；客户端集成测试重试路径。
- 工作量：中。

## V7（P3，可选加固）WS 入站帧与票据签发无速率限制

**概念 #25 WebSockets + #28 限流。**

- 现状：入站 WS 帧不做节流（`server/trigger/core.py` 的处理器表无逐连接
  限制）；`GET /auth/ws-ticket`（`server/trigger/http/auth.py:225`）签发无限。
  登录有逐地址指数锁出，是全项目唯一的限流实现。
- 为什么只算 P3：威胁模型是回环 + 网关 token + Origin 白名单——能过网关的
  都是自己人，帧风暴最坏是自我 DoS。这是纵深防御，不是堵洞。
- 整改（可选）：令牌桶逐连接限入站帧（建议突发 50、持续 10 帧/s，超限丢帧并
  回一条 `rate_limited` 帧）；`/auth/ws-ticket` 每 SOCKET 地址每分钟 30 次。
  两者都 fail-open（限流器异常放行），打点进日志即可。
- 明确不做：连接空闲回收器。agent-stream 观察 socket 在无回合时本就长时间
  静默，按空闲回收会误杀合法观察者——心跳是客户端驱动的 ping/pong
  （`server/trigger/core.py:144-161`），服务端不适合另立存活判定。
- 工作量：小（若做）。

## 合规面记录（避免未来重复审计）

以下按同一清单已逐条查证为合规，附关键证据，后续审计不必重开：

- **幂等**：`user_input_queue.claim_next` 单条 `UPDATE ... RETURNING` +
  `BEGIN IMMEDIATE` 原子领取（`server/queue/user_input_queue.py:680-692`）；
  CLAIMED 行崩溃后由 `recover()` + 24h 过期 + 启动对账回收
  （`server/service/input_queue_service.py:36-38`）。
- **重试**：LLMRetryMiddleware 完整 ZCode 对齐（11 次预算、budget_attempt 与
  物理_attempt 分离、Retry-After、stale-streak 熔断、逐事件入 ledger）。
- **超时**：全部 httpx 调用点显式超时（web_fetch 本地/远程、SearXNG
  `_TIMEOUT`、下载器 HEAD/流式）；`sessions_spawn` 超时钳制 [600, 7200]；
  三个 SQLite store 家族 + MesMemory + 队列全设 busy_timeout 首语句。
- **推送可恢复**：`todo_refresh`/`taskflow_refresh` 快照帧
  （`server/trigger/core.py:164-215`）；budget 与搜索后端有 GET 拉取对应；
  model_retry 明确"in-memory 展示 + ledger 持久"双层。
- **索引**：messages 五索引、队列 session/status/client_msg 唯一索引、
  trajectory 双索引、evidence/registry/taskflow/todolist/code-intel 齐全。
- **SSRF/Rebinding**：web_fetch 远程分支 DNS pinning + 公网 URL 判定；本地分支
  显式 opt-in（`SHERRY_WEB_FETCH_ALLOW_LOCAL`）。
- **登录限流**：逐 SOCKET 地址指数锁出 + 参数化 SQL + 假 scrypt 恒时。

## 不适用项说明

负载均衡、CDN、复制、分片、一致性哈希、CAP 对单进程本地优先应用无整改
意义；无状态（#8）是已知且文档化的架构边界（进程级单例 + mem 档寄存器），
其风险已由"resolve per call, never at construction time"规则 + 启动回填 +
双档寄存器测试覆盖，本计划不动它。

## 0. 背景（已核实）

### 0.1 关键发现：side chat 已经是会话 fork

sherry 的 side chat（辅助会话）**本质上就是一个会话 fork 机制**，不是简单的"侧边栏小窗"。`POST /sessions/side_chat`（`side_chat.py:22-41`）→ `create_side_chat`（`side_chat_service.py:257-330`）做的是：

1. **checkpoint fork**：`get_checkpoint_fork_for_turn`（`:202-254`）通过 `read_messages(parent)`（`state_port.py:65`）读父会话的 LangGraph checkpoint live state（模型看到的完整消息，**包括 browser/tool 结果等未到达 message store 的内容**），切到 fork 点，给每条消息打 `side_chat_context` 标记，在子会话**首 turn** 注入（`:219` 的 `session_has_messages` guard 保证只注入一次）。
2. **per-session settings 继承**：`_copy_parent_session_settings`（`:163-177`）复制 10 个 StateKey（model/thinking/custom mapping/search backend/budget/agent config/project dir + 两个 announced baselines/HITL 模式）。
3. **幂等创建**：`client_request_id` + `(parent, request_id)` UNIQUE 索引（`side_chat_store.py:51-54`），重试/重复点击返回同一 child。
4. **parent-scoped 生命周期**：删除父会话级联 `purge_side_chat_children`（`side_chat_service.py:393-406`）逐个 fail-open 清理子会话；关闭侧边栏 tab 只 detach socket，不删会话。
5. **link 表**：`side_chats.db`（`side_chat_store.py:33-42`）记录 `child_session_id`(PK) / `parent_session_id` / `fork_mode` / `context_text`(文本快照回退) / `client_request_id`。

**唯一的缺口**：fork 点**固定**为父会话"最后一条已完成（无 tool_calls）的 AI 回答"——`_completed_history`（`:187-199`）从末尾向前找第一条无 tool_calls 的 AIMessage。DB schema、路由 payload、service 全程**没有 turn 参数**（grep `fork_turn` 零命中）。无法指定从哪个 turn fork。

### 0.2 会话分支 vs side chat：同一 fork 基建，两个入口

| 维度 | side chat（已有） | 会话分支（本计划） |
|---|---|---|
| 入口 | 右键选中文字 → "在辅助会话中提问"（ContextMenu） | AI 消息行 hover → fork 按钮 |
| fork 点 | 固定：父会话最后一条 AI 回答 | **可指定**：该 AI 消息行所在 turn |
| 呈现 | 侧边栏面板（`SideChatPanel.vue`，与主聊天并列） | 独立会话切换（`router.push` 到新 session） |
| quote | 带选中文字 quote chip 预填 | 无 quote（纯分叉探索） |
| fork 机制 | checkpoint fork（复用） | checkpoint fork（复用，加 turn 参数） |
| settings 继承 | 10 个 StateKey（复用） | 同左（复用） |
| 级联清理 | parent 删除级联（复用） | 同左（复用） |

两者共用同一套 `side_chat_service` fork 基建，只是入口和 fork 点不同。**后端改动 = fork 点参数化（加 `fork_turn_num`），前端改动 = 新增 fork 按钮入口 + 分支导航。**

### 0.3 turn_num 到 checkpoint 消息的映射（路径 A，保真）

fork 点参数化的技术障碍：`read_messages`（`state_port.py:65`）读的是 LangGraph checkpoint live state，**消息没有 turn_num 标签**。但 checkpoint 消息按顺序排列，**HumanMessage 计数 = turn_seq**（`state_port.py:168` 的 marker id 计算已用这个逻辑）。所以：

- 第 N 条 HumanMessage 之后到第 N+1 条 HumanMessage 之前的所有消息 = turn N 的内容
- fork 到 turn N = 保留到 turn N 的最后一条 AI 回答（在该 turn 范围内找无 tool_calls 的 AIMessage）

这和 `_completed_history` 的逻辑一致，只是限定在 turn N 范围内而非全局末尾。**保真**：checkpoint fork 的核心价值是"包含 browser/tool 结果"（AGENTS.md 反复强调），路径 A 保留这个优势。

**compaction 回退**：若 fork turn 已被压缩出 checkpoint（turn_num 超出 checkpoint 的 HumanMessage 计数），回退到现有的 `context_text` 文本快照（`:245-253`，不按 turn 切，降级场景可接受）。

### 0.4 ZCode 做法

ZCode 的 `forkAssistant` 基于 checkpoint 追踪，feature id `conversation.history.branch`。fork = 从某 turn 创建分支 checkpoint，在新分支继续对话。sherry 的 side chat fork 机制与之等价，只差 turn 参数化。

## 1. ⚠️ 硬约束

| 约束 | 含义 | 验收方式 |
|---|---|---|
| **F1**：复用 checkpoint fork | 子会话继承父 checkpoint 消息视图（含 tool/browser 结果），不物理复制 message store 行 | fork 不产生全量 message 复制 |
| **F2**：分支独立写入 | fork 后子会话独立演进，写入不影响父分支 | 子分支写入不改变父 checkpoint |
| **F3**：fork 点可指定 turn | 用户点 turn N 的 AI 回答 fork → 子会话继承到 turn N | fork_turn_num 生效 |
| **F4**：不破坏 side chat | 现有 quote 场景的 side chat 行为不变（fork_turn_num=None 走原逻辑） | side chat 测试全过 |
| **F5**：fail-open | fork 失败/turn 已被压缩 → 回退文本快照或提示错误 | 后端拒绝时前端不崩 |

- [ ] **2.2.4** `server/service/side_chat_service.py:187-199` 新增 `_history_up_to_turn` 替代 `_completed_history` 的固定逻辑：
  ```python
  def _history_up_to_turn(
      messages: list[BaseMessage], turn_num: int | None
  ) -> list[BaseMessage]:
      """Cut the parent transcript at the fork point.

      turn_num=None: legacy side-chat default — the last completed (call-less)
      AI answer (a dangling tool call never replays into the child).
      turn_num=N: cut after turn N's AI answer — the branch fork point.
      Returns [] when turn N is not in the checkpoint (compacted away).
      """
      if turn_num is None:
          return _completed_history(messages)

      # Locate turn N's span: the Nth HumanMessage up to (excluding) the
      # (N+1)th HumanMessage, or end of list. HumanMessage count == turn_seq
      # (state_port.py:168 uses the same fact for the interrupt marker id).
      human_count = 0
      turn_start = None
      turn_end = len(messages)
      for index, msg in enumerate(messages):
          if msg.type == "human":
              human_count += 1
              if human_count == turn_num:
                  turn_start = index
              elif human_count == turn_num + 1:
                  turn_end = index
                  break

      if turn_start is None:
          return []  # turn N compacted away → caller falls back to context_text

      span = messages[turn_start:turn_end]
      # Within the turn's span, cut at the last call-less AI answer (stable
      # boundary — same rule as _completed_history, scoped to this turn).
      for index in range(len(span) - 1, -1, -1):
          msg = span[index]
          if isinstance(msg, AIMessage) and not getattr(msg, "tool_calls", None):
              return list(messages[: turn_start + index + 1])
      # No call-less AI in this turn (mid-tool at the fork point) → cut at
      # the turn boundary; the child starts after the user's turn-N message.
      return list(messages[:turn_end])
  ```

### 2.3 风险与约束

- **compaction 回退降级**：fork turn 被压缩出 checkpoint 时，回退到 `context_text` 全量文本快照（不按 turn 切）。这时子会话继承的是"父会话最近 N turns 的文本"而非"到 turn N 的 checkpoint"。降级场景，可接受；进阶可在 `build_parent_context`（`:92-151`）加 `turn_num` 参数按 turn 切文本。
- **fork 点是 mid-tool 的 turn**：若用户 fork 的 turn 当时正卡在 tool call 中间（AI 有 tool_calls 但无结果），`_history_up_to_turn` 的 span 内找不到无 tool_calls 的 AI → cut at turn boundary（`:turn_end`），子会话从该 turn 的下一条 HumanMessage 之前开始。这避免了回放父的未完成 tool call（与 `_completed_history` 的安全目标一致）。
- **turn_num 来源**：前端 AI 消息行携带 `turn_num`（`MessageItem` 已有，见 `计划_前端_消息编辑与重生成.md` 0.2 节）。fork 按钮传该 turn_num。注意 checkpoint 的 HumanMessage 计数与前端 turn_num 的对应：前端 turn_num 从 1 开始（第一条用户消息 = turn 1），checkpoint HumanMessage 计数同样从 1 开始。

- **fork 按钮与编辑按钮共存**：编辑按钮在**用户消息行**（`计划_前端_消息编辑与重生成.md`，编辑=原地重跑）；fork 按钮在 **AI 消息行**（fork=分叉探索）。两者在不同消息行，不冲突。
- **fork 后子会话历史为空**：side chat 的 `side_chat_context` 标记让 `MessagePersistence` 过滤继承的消息（AGENTS.md:346），子会话可见历史从空开始。这是设计如此（子会话是"新分支"，不回显父历史）。**但分支场景用户可能期望看到继承的父历史**——这是与 side chat 的一个 UX 差异点。MVP 沿用 side chat 行为（历史为空，模型仍能看到继承的 checkpoint）；进阶可加"显示继承历史"开关。**需在方案评审时确认这个 UX 取舍**。
- **turn_num 与 checkpoint HumanMessage 计数的对应**：前端 turn_num 从 1 开始；checkpoint 的 HumanMessage 计数（`_history_up_to_turn` 的 human_count）也从 1 开始。但 workspace notice 等 internal HumanMessage（`metadata.origin=project_dir/git_head`）也会被计入——需确认这些是否影响 turn_num 映射。`_completed_history` 目前不区分（它只找 AIMessage），`_history_up_to_turn` 按 `msg.type == "human"` 计数会包含 internal HumanMessage。**需校准**：计数时跳过 `metadata.internal=True` 的 HumanMessage（workspace notice），与前端 turn_num（只算用户真实消息）对齐。

**验收**：F4 + F5。前端组件测试 + fork 流程集成测试。

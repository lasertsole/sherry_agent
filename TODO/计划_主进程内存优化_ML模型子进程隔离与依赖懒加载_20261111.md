# 计划：主进程内存占用优化 — ML 模型子进程隔离 + 重依赖懒加载

- 日期：2026-11-11（修订版 r2）
- 状态：**待评审**
- 来源：Sherry 内存消耗分析；本版修订回应自审意见（基线缺失、负载差异、桥接风险、止损点）
- 风险等级：**中** —— embed/reranker/本地 LLM 是语义召回和辅助模型核心路径，隔离后走 HTTP 增加失败点；本地 LLM 的 `BaseChatModel` HTTP 桥接是高风险子任务

---

## 0. 背景与目标

### 0.1 一个总前提（评审须认清）

方向一、二的本质是**内存隔离/搬家，不是纯减少**。把权重从主进程挪到 daemon 子进程，系统总内存（主进程 + daemon）在功能全开时基本持平、甚至略增（多一份进程开销）。收益是三件事：

1. **主进程变轻**——主进程承载编排、WS、中间件链、所有 session 状态，是最不该 OOM、最该保响应的进程
2. **峰值消除**——当前 embed 每次调用 load/close GGUF，主进程峰值飙到 ~600MB–1GB 又落回，反复 alloc/free
3. **按需启停**——语义召回关了，embed daemon 不 spawn，零内存

方向三才是**真减少**（不用的依赖不进内存）。

**评审按"主进程内存"评判方向一二，按"系统总占用"评判方向三。**

### 0.2 现状（已代码核实）

Sherry 后端是**单 Python 进程**（`server/__main__.py:309` 显式 `app.config.processes = 1`）。主进程内存去向：

| 来源 | 位置 | 估计占用 | 默认 |
|---|---|---|---|
| Python + langchain 全家桶 + opencv + tree-sitter + snkv + leidenalg 等静态导入 | 顶层 import 链 | 数百 MB（**待实测**） | 必然 |
| 本地 bge-m3 embed（GGUF） | `models/embed_model/text/core.py:148-161` 每次 `Llama(...)` / `model.close()` | 峰值约 600MB–1GB（**待实测**），调用间隙释放 | **开启** |
| 本地 bge-reranker（GGUF） | `models/reranker_model/__init__.py:39-50` 每次 new 后 close；`_META_CACHE` ~16MB 常驻 | 峰值数百 MB | 关闭 |
| 本地 LLM（Qwen3.5-9B Q4 + n_ctx=40960 KV cache） | `models/LLMs/auxiliary_llm/core.py:82-93` 懒加载后常驻到 atexit | 数 GB | 关闭 |
| STT（FunASR + torch） | 独立 daemon 子进程 | 不计入主进程 | — |
| StateRegister | `runtime/session/state_register.py:44-66` `state_register_mem` | 多会话线性增长 | 内存版 |
| Checkpoint | SQLite WAL 落盘 | 不驻留 | — |

> **注意**：上表所有数字均为按权重文件大小 + 通用常识的估计，**非实测**。阶段 0 会测真实基线，收益以实测为准。

### 0.3 目标

| 指标 | 当前（待实测） | 目标 |
|---|---|---|
| 主进程峰值（语义召回活跃时） | ~600MB–1GB（估） | 主进程不含 embed 权重 |
| 主进程常驻（开本地 LLM 时） | 数 GB（估） | 重内存移到子进程 |
| 主进程静态导入占用 | 数百 MB（估） | 功能门控依赖延迟到首次使用 |

## 阶段 0：基线测量 + 基础设施（必须先做）

> **本阶段是后续一切验收的前提。没有基线就无法判定收益。**

### 0.4 基线测量清单

用 `psutil` 或平台工具记录以下指标（每项写进报告，作为前后对比基准）：

1. **冷启动 RSS**：`python -m server` 启动后空闲态（无会话）主进程 RSS
2. **空闲态 RSS**：一个会话空闲态主进程 RSS
3. **语义召回峰值**：触发语义召回（`memory(action="recall")` + 索引构建）时主进程 RSS 峰值与稳态
4. **embed load 耗时（冷 vs 热）**：`_LocalEmbeddingBackend.embed()` 的 load + 推理 + close 各段耗时，**必须区分冷启动（首次，磁盘 IO）与热启动（page cache 命中，重复第 N 次）**——这是方向一 mmap 决策门的依据（见 §1.1）
5. **开本地 LLM 时占用**：`AUXILIARY_LLM_MODEL_LOCAL=true` 触发一次 invoke 后主进程 RSS（权重 + KV cache）
6. **importtime profile**：`python -X importtime -m server` 输出，列出启动时被拉入的重依赖及其触发模块
7. **辅助 LLM 实际输入 token 分布**：采 safety moderation / 记忆整合的真实输入长度分布（用于方向二 n_ctx 决策）

### 0.5 抽 daemon 公共骨架

从 STT 的 `skills/builtin/core/speech_to_text/scripts/core.py` 抽出 `daemon_alive(port)` / `spawn_daemon(script, port, pid_file)` / `kill_daemon(pid_file)` 通用逻辑到 `models/daemon/base.py`（或 `agent/tools/pub_base/`）。STT 改为复用该骨架，行为不变，回归测试覆盖。

> **注意**：抽骨架是复用思路，不代表 STT 的负载验证能直接迁移到 embed（见方向一风险）。

## 方向三：重依赖懒加载（最低风险，先做）

### 3.1 原理

Python 顶层 `import X` 在模块加载时执行，即使 X 本次会话用不到。移到函数内则首次用到才加载，不用则永不进内存。这是真减少（非搬家）。Sherry 已有先例：`models/embed_model/code/core.py:200-211` 的 onnxruntime `_ensure_loaded`。

### 3.2 实施步骤

**步骤 1**：基于阶段 0 的 importtime profile，列出启动时被拉入但功能门控的重依赖及触发模块。
**步骤 2**：逐个把顶层 import 移到实际调用函数内。优先级（按体量）：
1. `mineru-vl-utils[transformers]`（拖 torch+transformers，仅文档解析）
2. `opencv-python-headless`（仅图像/多模态）
3. `leidenalg` + `snkv`（仅 graph-rag/code-intel）
4. `tree-sitter-*`（仅 code-intel）
5. `gguf`（确认无顶层强导入）
**步骤 3**：每改一个，跑一次 importtime 确认该依赖已不在启动集合，并跑相关功能测试。

### 3.3 风险与缓解

| 风险 | 缓解 |
|---|---|
| 循环依赖（顶层 import 顺序掩盖） | 逐个改、逐个验证启动 |
| 模块顶层副作用初始化（`import X; X.configure()`） | profile 时检查目标依赖是否有顶层副作用；有则副作用也需移进函数 |
| 热路径传递依赖 | profile 确认目标依赖触发点不在 LLM/持久化/TaskFlow/spawn 链上 |
| 首次使用 import 延迟 | 这些功能（文档解析/code-intel/graph-rag）非交互热路径，可接受 |

### 3.4 Kill criteria

- 若 importtime 显示目标依赖实际**未在启动时被拉入**（已被其他机制懒加载或根本没接入），则该条不改，跳过
- 若某依赖改动后启动报循环依赖且无法在 1 个工作日内解决，回退该条，记录原因，不阻塞其他

### 3.5 验收

- importtime 前后对比：目标依赖不在启动集合
- 主进程冷启动 RSS 较基线下降（实测数字）
- 触发各懒加载功能（文档解析/code-intel/graph-rag/图像）正常工作
- `uv run pytest tests/ -m "not llm_e2e"` 全过

## 方向一：本地 embed / reranker 隔离到子进程 daemon

### 1.1 原理与 mmap 决策门（关键）

当前 `_LocalEmbeddingBackend.embed()`（`models/embed_model/text/core.py:148-161`）每次调用 `Llama(...)` 加载 GGUF → 推理 → `model.close()`。初看是"反复 alloc/free 600MB–1GB"的问题，但 **llama-cpp-python 默认 `use_mmap=True`**，这改变了分析：

- 第一次 `Llama(model_path=...)`：mmap 权重文件进地址空间，OS 读入 page cache（冷启动有磁盘 IO）
- 后续 `Llama(...)`：OS page cache 命中，权重**不重读磁盘**，只有 `llama_context` 结构分配
- `model.close()`：释放 context，权重页是 clean page，**OS 按内存压力自动回收**（内存紧时丢弃，需要时再 mmap 回来）

这意味着当前 load/close-per-call **可能是故意为低占用设计的**：调用间隙不持 context，OS 按需缓存/回收权重页。改成 daemon 常驻会**持续持有一个 context**（永不释放），活跃期间总内存上升（§0.1 已承认"搬家非减少"）。

**因此方向一不是"必须做"，而是"实测后条件触发"**。阶段 0 的 §0.4 第 4 项（embed load 耗时）必须区分**冷启动**与**热启动（page cache 命中）**两种情况，并据此决策：

| 热启动 load 实测结果 | 决策 |
|---|---|
| < 50ms 且峰值 RSS 可控（mmap + OS cache 已足够优） | **保持现状，不建 daemon**——当前设计已是低占用模式 |
| 仍显著（context 分配贵）或高频召回下反复 alloc/free 导致碎片/抖动 | 进步骤 1 建 daemon，明确接受活跃期总内存上升 |

> 若实测结论是"保持现状"，方向一整体跳过，阶段 0 报告记录结论。这不是失败，是避免无谓工程的正确止损。

### 1.2 与 STT 范式的关键差异（不能直接照搬）

| 维度 | STT（已验证） | embed（本方向） |
|---|---|---|
| 调用频率 | 低频一次性 | 召回时批量、索引构建时高频（几百条） |
| 并发 | 单请求 | 索引构建可能并发 |
| 线程安全 | 不涉及 | llama-cpp 推理非线程安全 |

**STT 的 daemon 可靠性验证不能直接迁移到高频 embed 场景。** 方向一必须额外设计 batch + 并发。

### 1.3 目标架构

```
主进程（HTTP client）                embed daemon 子进程
  embed(texts)  ──HTTP──▶  /embeddings    Llama(bge-m3 GGUF) 常驻
  批量调用 list[str]                    支持 batch 输入
                                        单线程推理队列（llama-cpp 非线程安全）
                                        关闭召回时不启动
```

### 1.4 实施步骤

**步骤 1：embed daemon 脚本**（含 batch 支持）
- `models/embed_model/text/daemon.py`：`POST /embeddings` 接 `input: list[str]`，一次返回全部向量（批量推理，复用一次 load 的上下文）
- 端口 `EMBEDDING_DAEMON_PORT`（默认 9012），pid 文件 `.embed_daemon.pid`
- 单线程串行处理请求（llama-cpp 非线程安全），daemon 内维护请求队列

**步骤 2：主进程 backend 切换**
- `models/embed_model/text/core.py`：`_LocalEmbeddingBackend` 改 HTTP client，`embed()` 改为批量调用
- 删除进程内 `Llama(...)` load/close 路径
- facade `context_engine/embeddings/indexer.py` 不变

**步骤 3：索引构建批量改造**
- `context_engine/store/memory_embeddings.py` 索引构建路径改为分批调用 daemon（如每批 32/64 条），避免逐条 HTTP round-trip
- 评估索引构建耗时 vs 基线，不得 regress 超过 20%

**步骤 4：reranker daemon**
- `models/reranker_model/daemon.py`：`POST /rerank`，单例常驻
- `__init__.py:39-50` `_LocalGgufBackend._call` 改 HTTP；默认关闭，影响小

**步骤 5：daemon 生命周期**
- 首次调用 lazy spawn（`daemon_alive` 失败则 `spawn_daemon`，等 ready）
- atexit kill；空闲超时自杀（`EMBEDDING_DAEMON_IDLE_TIMEOUT_S` 默认 600s）
- 打包态作为独立入口

### 1.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| HTTP 增加延迟 | loopback <1ms；且省去每次 GGUF load（数百 ms），重复调用净改善 |
| daemon 挂掉导致召回失败 | `memory_recall.py:96-117` 已 fail-open，daemon 不可达降级无召回，与当前 embed 失败一致 |
| 高频 embed 排队（索引构建） | batch 接口 + 分批调用；索引耗时不得 regress >20%（验收硬指标） |
| daemon 端口冲突 | 端口可配；spawn 前检测 |
| 打包复杂度 | STT daemon 已是此模式，参照 |

### 1.6 Kill criteria

- **§1.1 mmap 决策门未通过（热启动 load < 50ms 且峰值可控）→ 方向一整体跳过，不建 daemon**——记为"当前 load/close 设计已是最优，无需隔离"
- 若索引构建耗时报 baseline regress >20% 且优化 batch 后无法收敛，方向一回退，保留当前 in-process load/close（记为"性能未达，暂不隔离"）
- 若 daemon 在并发召回场景下出现推理错误（llama-cpp 线程安全），回退

### 1.7 验收

- embed 向量与基线 cosine 相近（对召回无影响，不要求逐字节一致）
- 主进程语义召回峰值较基线下降（实测，不含 embed 权重）
- 索引构建耗时 regress ≤20%
- daemon 不可达时降级路径与当前一致
- 回归：`tests/agent/middlewares` 记忆召回测试全过

## 方向二：本地 LLM 隔离到子进程 + n_ctx 分级

### 2.1 原理

**2a 子进程隔离**：`_LocalAuxiliaryChatModel._ensure_client`（`auxiliary_llm/core.py:82-93`）懒加载 `Llama(Qwen3.5-9B-Q4, n_ctx=40960)` 常驻主进程。改 HTTP client，权重挪 daemon。
**2b n_ctx 分级**：KV cache ≈ `n_ctx × 层数 × 2 × hidden_dim`，与 n_ctx 线性。40960→8192 是 ~5 倍 KV cache 缩减。

### 2.2 适用范围（关键）

**默认 `AUXILIARY_LLM_MODEL_LOCAL=false` 走云端，本方向零影响。** 仅当用户切本地 LLM 时触发。

### 2.3 高风险子任务：HTTP-backed BaseChatModel 桥接

> **这是本方向的主要工作量和风险点，不是"适配点"。**

本地辅助 LLM 不只出文本：
- 记忆整合用它带 memory tool（15 轮工具调用）
- safety moderation 用它做判定（结构化输出）
- 可能涉及 thinking 流式

需要实现一个完整的 `BaseChatModel` 子类，通过 daemon 的 OpenAI 兼容 `/chat/completions` + SSE 实现：
- 文本流式 → LangChain `astream` callback
- **工具调用流式**（tool_call delta 聚合）
- **结构化输出**（`response_format`）
- thinking（如模型支持）

**必须先做可行性验证**：用一个最小 `BaseChatModel` HTTP 桥接跑通 tool call + structured output，再推进完整改造。

### 2.4 n_ctx 决策（待阶段 0 数据）

**不预先定死 n_ctx 默认值。** 基于阶段 0 测得的"辅助 LLM 实际输入 token 分布"决定：

- 若 P99 输入 < 6000 tokens → `AUXILIARY_LLM_N_CTX` 默认 8192
- 若 P99 超过 → 适当上调或保留更高值
- `MAIN_LLM_N_CTX` / `VISION_LLM_N_CTX` 同理按实际分布定
- 未显式配置时**回退 40960，不强制降级**

### 2.5 safety moderation 延迟分析（必须做）

safety LLM moderation 是 `awrap_model_call` 内层、20s 超时 fail-open，在请求路径上。走 daemon HTTP 后：
- 每次 moderation 多一次 loopback round-trip（<1ms，可忽略）
- 但 daemon 推理若在排队（如整合任务同时跑），可能占用 20s 预算

**决策**：评估后若 moderation 受 daemon 排队影响，则 **moderation 路径走云端而非本地 daemon**（moderation 对延迟敏感、对质量不敏感、且本就 fail-open）。

### 2.6 实施步骤

**步骤 1：可行性验证**（最小 BaseChatModel HTTP 桥接 + tool call + structured output 跑通）
**步骤 2：LLM daemon 脚本**（OpenAI 兼容 `/chat/completions` + SSE，单例 `Llama`，端口 9014）
**步骤 3：主进程 client 切换**（完整 `BaseChatModel` 实现）
**步骤 4：n_ctx 配置化**（按 2.4 决策）
**步骤 5：moderation 路径决策**（按 2.5）
**步骤 6：视觉 LLM `base_local_llama.py` 同构改造**

### 2.7 Kill criteria

- 若步骤 1 可行性验证发现 SSE 桥接 tool call / structured output 无法可靠工作，方向二**整体回退**，本地 LLM 保持 in-process（记为"桥接不可行，暂不隔离"）
- 若 n_ctx 降级导致实际场景截断率 >5%，回退该角色的 n_ctx 到原值

### 2.8 验收

- 开本地 LLM 后主进程不含 GGUF 权重 + KV cache（实测）
- tool call / structured output / 流式与 in-process 行为一致（对照测试）
- daemon 不可达时 safety moderation / 记忆整合 fail-open 与当前一致
- n_ctx 降级场景截断率 ≤5%
- 回归：safety moderation / 记忆整合 fail-open 测试全过

## 整体验收标准

1. 有实测基线报告（阶段 0），所有收益对比基于基线
2. 主进程冷启动 RSS 较基线下降（方向三）
3. 语义召回活跃时主进程峰值较基线下降且不含 embed 权重（方向一）
4. 开本地 LLM 时主进程不含权重 + KV cache（方向二）
5. 索引构建耗时 regress ≤20%（方向一硬指标）
6. tool call / structured output 行为一致（方向二硬指标）
7. 所有现有测试回归通过
8. 各方向 Kill criteria 已评估并记录

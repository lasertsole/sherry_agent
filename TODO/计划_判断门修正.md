## 1. 缺口 A：Tier 1 schema 失败不反馈给子代理

### 1.1 问题

Tier 1 schema 校验失败（`schema_validated=false`）时，如果步骤有 `retry_policy`
且预算未耗尽，会重新派发子代理。但重新派发的 task 是**原样返回的**——
`schema_error` 没有传给子代理。

**根因**：`with_judge_feedback`（`_retry.py:177-193`）的第二个参数是
`step.get("judge_feedback")`，而 `judge_feedback` 是 StepJudge（Tier 2）
产出并写入 step 的。schema 失败短路在 StepJudge 之前，所以 `judge_feedback`
为空，`with_judge_feedback(task, "")` 原样返回 task。

### 1.2 `schema_error` 的详细程度

`validate_structured_output`（`collector.py:288-371`）递归校验，错误信息精确到
字段路径：

| 错误类型 | `schema_error` 内容 | 示例 |
|---------|---------------------|------|
| JSON parse 失败 | `"Output is not valid JSON: {exc}"` | `"Output is not valid JSON: Expecting value: line 1 column 1"` |
| 类型不对 | `"{path}: expected {type}, got {actual}"` | `"root.result.status: expected string, got int"` |
| 缺必填字段 | `"{path}: missing required field '{name}'"` | `"root: missing required field 'result'"` |
| 不允许的多余字段 | `"{path}: additional properties not allowed: {extra}"` | `"root: additional properties not allowed: {'foo'}"` |
| 数组元素错误 | `"{path}[{i}]: expected {type}, got {actual}"` | `"root.items[2]: expected string, got NoneType"` |

**这些错误信息足够具体**——子代理知道缺了哪个字段、哪个字段类型错了。
但子代理还需要**知道完整的 schema 定义**才能修正——这引出缺口 B。

### 1.3 方案

在 `taskflow_resume.py` 的 retry 分支里，根据失败类型构建 feedback：

```python
if policy is not None and should_retry_failure(
    step, result, schema_validated=schema_validated
):
    if schema_validated is False and schema_error:
        feedback = (
            f"Your previous output failed schema validation: {schema_error}. "
            "Ensure your output is valid JSON matching the required response_schema."
        )
    else:
        feedback = str(step.get("judge_feedback") or "")

    redispatched_key = await spawn_replacement(
        with_judge_feedback(
            build_task_with_bindings(...),
            feedback,
        ),
        requester_key,
    )
```

子代理拿到的 task 变成：

```
...原始任务...

## Previous Attempt Feedback
The previous attempt was judged and needs revision:
Your previous output failed schema validation: root: missing required field 'result'.
Ensure your output is valid JSON matching the required response_schema.

Address this feedback and complete the task.
```

## 2. 缺口 B：重新派发丢失 step 配置（output_schema 等）

### 2.1 问题

`spawn_replacement`（`_retry.py:196-202`）只传了 `task` 和 `requester_key`：

```python
async def spawn_replacement(task: str, requester_key: str) -> str:
    return await _dispatch.dispatch_child(
        task=task,
        requester_session_key=requester_key,
        label=None,
        # ← 没传 output_schema！子代理拿不到 schema 定义
        # ← 没传 functional_role！子代理角色可能变
        # ← 没传 step_model！子代理模型可能变
        # ← 没传 step_timeout_seconds！子代理超时可能变
    )
```

`dispatch_child`（`_dispatch.py:10-44`）接受这些参数并传给
`spawn_subagent_direct` → 进子代理的 system prompt 和执行配置。
但 `spawn_replacement` 没传——**替换子代理丢失了原始 step 的所有配置**。

**后果**：
- 子代理拿不到 `output_schema` → 不知道完整 schema 定义 → 只知道"缺了 result
  字段"但不知道还有什么必填字段、字段类型是什么
- 子代理的 `functional_role` 退回默认（general）→ 可能和原始 step 的角色不同
- `step_model` 和 `step_timeout_seconds` 退回默认

### 2.2 影响范围

这个缺口不只影响 schema 失败的 retry——**所有走 `spawn_replacement` 的
重新派发都受影响**，包括：
- StepJudge 返回 `retry` 的重新派发（`taskflow_resume.py:270`）
- `should_retry_failure` 检测到文本失败的重新派发（`taskflow_resume.py:202`）

两条 retry 路径都走 `spawn_replacement`，都丢了配置。

### 2.3 方案

扩展 `spawn_replacement` 签名，从 step 里读取配置传过去：

```python
async def spawn_replacement(
    task: str,
    requester_key: str,
    *,
    output_schema: dict | None = None,
    functional_role: str | None = None,
    step_model: str | None = None,
    step_timeout_seconds: float | None = None,
) -> str:
    """Spawn the step's replacement child through the shared dispatch seam."""
    return await _dispatch.dispatch_child(
        task=task,
        requester_session_key=requester_key,
        label=None,
        functional_role=functional_role,
        output_schema=output_schema,
        model=step_model,
        step_timeout_seconds=step_timeout_seconds,
    )
```

调用方（`taskflow_resume.py` 的两个 retry 分支）从 step 读取配置传入：

```python
# schema 失败 retry (line ~202) 和 StepJudge retry (line ~270) 都改：
redispatched_key = await spawn_replacement(
    with_judge_feedback(
        build_task_with_bindings(...),
        feedback,
    ),
    requester_key,
    output_schema=step.get("response_schema"),
    functional_role=step.get("functional_role"),
    step_model=step.get("step_model"),
    step_timeout_seconds=step.get("step_timeout_seconds"),
)
```

### 2.4 两个字缺口合在一起的效果

修复 A + B 后，schema 失败的重新派发：

```
替换子代理拿到：
  1. system prompt 里包含完整 schema 定义（缺口 B 修复）
  2. task 里附上 ## Previous Attempt Feedback: "missing required field 'result'"（缺口 A 修复）

→ 子代理知道：
  - 完整 schema 要求什么（从 system prompt）
  - 上次具体哪里错了（从 feedback）
  → 能针对性地修正格式
```

## 3. 缺口 C：不用 LangChain 原生 response_format，靠 prompt + 事后校验

### 3.1 问题

Sherry 的 `create_agent` 调用（`spawn/core.py:1565`）**没传 `response_format`**：

```python
child_agent = create_agent(
    model=child_llm,
    system_prompt=system_prompt,
    state_schema=StateSchema,
    checkpointer=child_checkpointer,
    tools=final_tools,
    middleware=child_middleware,
    # ← 没传 response_format！
)
```

当前做法是纯 prompt 级 + 事后校验：

1. `build_structured_output_prompt`（`collector.py:275-285`）把 JSON schema 作为
   文本拼到 system prompt 里：`"Your output must conform to the following JSON
   schema: {schema}. Return your result as valid JSON."`
2. `validate_structured_output`（`collector.py:288-371`）在 resume 时事后校验

**问题**：prompt 级是"请求"不是"约束"——模型可以不听、漏字段、类型错、
不输出 JSON。所有格式错误都到 Tier 1 事后校验才发现，retry 预算被浪费在
"模型本来就不该犯的格式错误"上。

### 3.2 LangChain 的 response_format 机制

`create_agent` 的 `response_format` 参数（LangChain 1.3）支持三种策略：

| 策略 | 机制 | 强度 |
|------|------|------|
| **ProviderStrategy** | 用 provider API 的原生结构化输出（如 OpenAI `response_format={"type":"json_schema"}`）——模型在生成时被约束只能产出符合 schema 的 token | 最强：不可能产出不合规 JSON |
| **ToolStrategy** | LangChain 往 agent tool 列表加一个"结构化输出 tool"，tool 的 `args_schema` 就是你的 JSON schema。模型结束时调这个 tool，参数被 schema 校验——不过直接报 `StructuredOutputValidationError` | 中：模型调了 tool 就被校验，但不保证模型一定调 |
| **AutoStrategy** | 自动检测模型能力：支持原生结构化输出 → ProviderStrategy；不支持 → ToolStrategy | 自适应 |

传入 raw schema（dict / Pydantic model）时自动包成 `AutoStrategy`。

### 3.3 方案

在 `_build_child_agent`（`spawn/core.py:1565`）传 `response_format`：

```python
child_agent = create_agent(
    model=child_llm,
    system_prompt=system_prompt,
    state_schema=StateSchema,
    checkpointer=child_checkpointer,
    tools=final_tools,
    middleware=child_middleware,
    response_format=output_schema if output_schema else None,
    # raw schema → AutoStrategy → 自动检测模型能力
)
```

**三层防御体系**：

| 层 | 机制 | 什么时候生效 | 失败时怎么办 |
|----|------|------------|-------------|
| **第 1 层（生成时）** | `response_format` → ProviderStrategy 或 ToolStrategy | 模型输出时 | 抛 `StructuredOutputValidationError`，agent 内部处理 |
| **第 2 层（事后校验）** | `validate_structured_output`（Tier 1 gate） | `taskflow_resume` 时 | `schema_validated=false` → 失败分类器 → retry（缺口 A 修复后带 error feedback） |
| **第 3 层（prompt 级）** | `build_structured_output_prompt`（system prompt 里写 schema 文本） | 始终生效 | 作为第 1 层不支持时的 fallback guidance |

### 3.4 保留还是删除 build_structured_output_prompt

**保留**——不删。理由：

- `response_format` 用 `AutoStrategy` 时，不支持原生结构化输出的 provider
  fallback 到 `ToolStrategy`——ToolStrategy 不保证模型一定调结构化输出 tool。
  此时 prompt 里的 schema 文本是模型的唯一指引。
- 即使 ProviderStrategy 生效（API 层强制），prompt 里的 schema 文本也无害——
  多一层 guidance 不冲突。
- 删除有回归风险——某些 provider 或模型可能在 `response_format` 下表现异常，
  prompt 文本是一个安全网。

### 3.5 保留 validate_structured_output 作为第二道网

`response_format` 生效时 schema 失败率会大幅下降，但**不归零**：

- ProviderStrategy：provider API 有 edge case（某些 schema 构造 API 不完整支持、
  nullable/union 等复杂类型可能被简化处理）
- ToolStrategy：模型可能不调结构化输出 tool（尤其 agent 在 tool 循环中
  被迭代预算截断时）
- AutoStrategy：fallback 到 ToolStrategy 的 provider，上面的风险都在

所以 `validate_structured_output` 的 Tier 1 gate 保留——它是第二道网，
和 `response_format` 的关系是"理想情况下第一道就拦住，第一道漏了第二道兜底"。

### 3.6 与缺口 A / B 的关系

- **缺口 A（schema error feedback）**：仍需要。`response_format` 降低失败率但
  不归零——失败时仍需把 `schema_error` 传给子代理做 retry feedback。
- **缺口 B（spawn_replacement 丢 output_schema）**：仍需要。`response_format`
  在 `_build_child_agent` 里设——`spawn_replacement` 修了 B 之后，
  `output_schema` 才能流到 `dispatch_child` → `spawn_subagent_direct` →
  `_build_child_agent` → `create_agent(response_format=...)`。缺口 B 是
  缺口 C 的前提。

### 3.9 sessions_spawn tool 也暴露 output_schema

当前 `SessionsSpawnSchema` 没有 `output_schema` 字段——LLM 直接调
`sessions_spawn` 的子代理不受 schema 约束，返回自由格式文本。只有 TaskFlow
dispatch 路径（从 step config 读 `response_schema`）才设 `response_format`。

**加字段**：

```python
class SessionsSpawnSchema(BaseModel):
    # ... 现有字段 ...

    output_schema: dict | None = Field(
        default=None,
        description=(
            "Optional JSON Schema that constrains the subagent's final output. "
            "When provided, the subagent is forced to produce JSON matching this "
            "schema (via the model provider's structured output or a tool-call "
            "binding). Use for tasks that must return machine-readable structured "
            "data (e.g. analysis reports, extraction results). Omit for free-form "
            "text output."
        ),
    )
```

**`_arun` 透传**：

```python
async def _arun(
    self,
    task: str,
    # ... 现有参数 ...
    output_schema: dict | None = None,
) -> str:
    # ... 现有逻辑 ...

    result = await spawn_subagent_direct(
        task=task,
        requester_session_key=requester_session_key,
        # ... 现有参数 ...
        output_schema=output_schema,  # ← 新增
    )
```

**效果**：LLM 调 `sessions_spawn(task="分析代码库并返回 JSON 报告",
output_schema={"type": "object", "properties": {...}})` → 子代理被
`response_format` 约束 → 返回合规 JSON → 主 agent 拿到结构化数据。

**不校验 schema 本身**：不在 tool 层校验 `output_schema` 是否是合法 JSON Schema。
如果模型产出了无效 schema，`create_agent(response_format=...)` 会在 agent 构建
时报错（LangChain 内部处理）。tool 层只负责透传。

### 3.10 TaskFlow dispatch 和 sessions_spawn 不复用彼此

两条路径最终都调 `spawn_subagent_direct`，但中间层不同：

| 维度 | TaskFlow dispatch | sessions_spawn tool |
|------|-------------------|-------------------|
| 调用者 | 引擎（`taskflow_resume` 自动派发） | LLM（模型主动调 tool） |
| 中间层 | `_dispatch.dispatch_child`（monkeypatchable seam） | `SessionsSpawnTool._arun`（含 privilege check、attachment 展平） |
| 参数来源 | step config（`response_schema`、`step_model` 等） | tool schema（LLM 传参） |
| 权限 | 无 privilege check（引擎操作） | `check_spawn_permission`（depth role 检查） |
| `output_schema` | 从 `step["response_schema"]` 读 | 从 `SessionsSpawnSchema.output_schema` 读 |

不复用的理由：TaskFlow dispatch 是引擎操作（引擎按 DAG 依赖自动派发 step），
不是 LLM 决定调的 tool。走 `sessions_spawn` 会多一层 privilege check 和 tool 层
逻辑，且 `sessions_spawn` 的 tool 实例受 per-session tool selection 管控——
引擎 dispatch 不应该被 tool 开关拦住。

# 计划：子代理工具能力遏制——同角色派生

- 建档日期：2026-10-15
- 状态：**计划（未开工）**
- 替代方案：本文档取代此前提出的"工具交集"方案（见 §6 对比）
- 触发问题：子代理的工具集来自 `build_main_tools()`（完整主 agent 工具集，
  `spawn/core.py:699`），按子代理自己的 functional role 白名单过滤。父代理的
  工具集不参与。导致 read-only 角色（researcher / reviewer / librarian）在
  ORCHESTRATOR 深度可以 spawn 一个 write-capable 的 executor 子代理来做自己
  权限外的写操作。
- 结论先行：
  1. **同角色派生**——专用角色（researcher / executor / reviewer / librarian）
     只能 spawn 同角色的子代理。general（inherit 模式）和 MAIN 不限制。
  2. **containment 自然成立**——同角色 = 同工具白名单 = 子代理工具集等于父
     代理，无升级可能。general 有全部工具，其子代理的任何角色白名单都是
     general 的子集，也无升级。
  3. **reject 而非 clamp**——专用角色试图 spawn 不同角色时，返回错误文本，
     不静默改角色。模型得到明确反馈，可以换 general 父代理或让 MAIN 直接
     spawn。

## 1. 规则

### 1.1 派生矩阵

| 父代理 | 子代理 functional_role | 允许？ | 理由 |
|--------|----------------------|--------|------|
| MAIN (depth 0) | 任意 | ✅ | MAIN 不是子代理，不受限制 |
| general (inherit) | 任意 | ✅ | general 有全部工具，任何子角色都是子集 |
| general (inherit) | general | ✅ | 同上 |
| researcher | researcher | ✅ | 同角色，同工具 |
| researcher | executor | ❌ | executor 有 write_file，researcher 没有 |
| researcher | general | ❌ | general inherit = 全部工具，超出 researcher |
| researcher | librarian | ❌ | librarian 有 search_files（相同），但角色不同 |
| executor | executor | ✅ | 同角色，同工具 |
| executor | researcher | ❌ | researcher 有 search_files/web_search，executor 没有 |
| reviewer | reviewer | ✅ | 同角色 |
| librarian | librarian | ✅ | 同角色 |

**规则一句话**：父代理是 MAIN 或 general → 不限制；父代理是专用角色 →
子代理的 functional_role 必须与父代理相同。

### 1.2 为什么 general 不限制

general 的 `tools: inherit`（白名单为空）= 继承全部主 agent 工具集。任何
专用角色的白名单都是"全部工具"的子集：

```
general 工具集 = 全部工具
executor 工具集 = [read_file, write_file, patch_file, terminal, python_repl] ⊂ 全部
researcher 工具集 = [read_file, search_files, terminal, web_search] ⊂ 全部
```

所以 general → executor：executor 的工具 ⊆ general 的工具，无升级。
general → general：同集，无升级。

### 1.3 为什么专用角色 → general 也要拒

general 是 inherit 模式（白名单为空 = 全部工具）。如果 researcher spawn
general，general 子代理拿到全部工具（包括 write_file）——这比 researcher
多，是升级。所以专用角色 → general 也要拒。

## 2. 与"工具交集"方案对比

此前提出的方案是：不管角色，只做工具交集（子代理工具 ∩ 父代理工具）。

| 维度 | 工具交集 | 同角色派生（本文） |
|------|---------|------------------|
| containment | ✅ 子⊆父 | ✅ 子=父 |
| 跨角色派生 | ✅ 允许但工具被截 | ❌ 拒绝 |
| 产生的子代理 | 可能"残缺"：researcher spawn executor → 子只有 [read_file, terminal] | 完整：同角色 = 完整白名单 |
| 实现复杂度 | 中——需查父 run record 拿白名单、做交集、处理 inherit 模式、处理 extra_tools | 低——查父 run record 拿 functional_role、比较是否相同 |
| 边界场景 | 多——inherit 模式交集、extra_tools 交集、code intel 注入 | 少——只比角色名 |
| 可预测性 | 低——子代理的实际工具取决于交集结果，模型不确定 | 高——同角色 = 同工具，确定 |
| 多专家编排 | 有限——general ORCHESTRATOR 可以 spawn 不同角色（子代理被截但有用） | 通过 general ORCHESTRATOR 或 MAIN 直接 spawn |

**关键差异**：工具交集会产生"残缺子代理"——researcher spawn executor 后子
代理只有 [read_file, terminal]，executor 的核心能力（write_file / patch_file）
被剥掉，它不再是真正的 executor。模型会困惑：它拿到了 executor 的 prompt
（"Full file read/write/patch access"）但实际没有 write_file 工具。同角色
派生不产生这个问题——要么同角色（完整），要么拒绝（明确的反馈）。

**多专家编排不受影响**：需要多专家协作时，用 general ORCHESTRATOR（不限制
子角色）或让 MAIN 直接 spawn 不同角色的 ORCHESTRATOR。专用角色做
ORCHESTRATOR 的场景是"同角色 fan-out"——例如 researcher ORCHESTRATOR spawn
多个 researcher LEAF 搜索代码库的不同部分。

## 3. 设计方案

### 3.1 检查位置：`spawn_subagent_direct`（`spawn/core.py`）

在 functional_role 解析后、tool policy 解析前，加一步角色遏制检查：

```python
# --- Phase 7: functional role resolution (已有) ---
functional_role = _resolve_functional_role(functional_role_hint, role)

# --- Phase 7.1: capability containment (新增) ---
containment_error = _check_role_containment(
    requester_session_key, functional_role
)
if containment_error:
    return SpawnResult(status="forbidden", error=containment_error)
```

### 3.2 新增函数

```python
def _check_role_containment(
    requester_session_key: str,
    child_functional_role: FunctionalRole,
) -> str | None:
    """Reject cross-role spawning from specialized parents.

    MAIN (no run record) and general (inherit = all tools) impose no
    restriction. A specialized parent (researcher / executor / reviewer /
    librarian) may only spawn children of the same functional role —
    same role = same tool whitelist = no capability escalation.

    Returns an error string when the child's role differs from a
    specialized parent's, or None when the spawn is allowed.
    """
    from ..registry import get_run_by_child_session_key

    parent_run = get_run_by_child_session_key(requester_session_key)
    if parent_run is None:
        return None  # MAIN → no restriction

    parent_role = parent_run.functional_role
    if parent_role == FunctionalRole.GENERAL:
        return None  # general (inherit) → no restriction

    if child_functional_role != parent_role:
        return (
            f"Capability containment: a {parent_role.value} subagent can only "
            f"spawn {parent_role.value} children (requested {child_functional_role.value}). "
            f"Use a general subagent or the main agent to spawn a different role."
        )
    return None
```

### 3.3 不改的地方

- **不改 `_resolve_child_tool_policy`**——同角色 = 同白名单，不需要交集
- **不改 `_assemble_child_tools`**——工具来源不变
- **不改 tool schema**——`functional_role` 参数已有，不需要加新字段
- **不改 `build_main_tools`**——工具构建不变

## 4. 完整遏制链路

```
MAIN (depth 0) → spawn general (ORCHESTRATOR, depth 1)
  检查: 无父 run record → 不限制
  general 工具: 全部 - DEFAULT_SUBAGENT_BLOCKED + spawn/yield 解锁

general ORCHESTRATOR → spawn executor (LEAF, depth 2)
  检查: 父 = general → 不限制
  executor 工具: [read_file, write_file, patch_file, terminal, python_repl]
  ← executor ⊆ general（general 有全部工具），无升级 ✓

MAIN → spawn researcher (ORCHESTRATOR, depth 1)
  检查: 无父 run record → 不限制
  researcher 工具: [read_file, search_files, terminal, web_search, spawn/yield]

researcher ORCHESTRATOR → spawn executor (LEAF, depth 2)
  检查: 父 = researcher, 子 = executor → 不同角色 → 拒绝 ❌
  返回: "Capability containment: a researcher subagent can only spawn
         researcher children. Use a general subagent or the main agent."

researcher ORCHESTRATOR → spawn researcher (LEAF, depth 2)
  检查: 父 = researcher, 子 = researcher → 同角色 → 允许 ✅
  researcher LEAF 工具: [read_file, search_files, terminal, web_search]
  ← 同角色 = 同工具，无升级 ✓
```

## 5. 对现有编排模式的影响

### 5.1 不受影响的模式

| 模式 | 为什么不受影响 |
|------|--------------|
| MAIN 直接 spawn 不同角色的子代理 | MAIN 不限制子角色 |
| general ORCHESTRATOR spawn 不同角色 LEAF | general 不限制子角色 |
| TaskFlow dispatch | TaskFlow 工具是 `main_only`，只有 MAIN 能调，不受子代理遏制影响 |
| 同角色 fan-out（researcher → 多个 researcher LEAF） | 同角色，允许 |

### 5.2 受影响的模式

| 模式 | 影响 | 替代方案 |
|------|------|---------|
| researcher ORCHESTRATOR spawn executor LEAF | 被拒绝 | 用 general ORCHESTRATOR 或让 MAIN 直接 spawn |
| executor ORCHESTRATOR spawn researcher LEAF | 被拒绝 | 同上 |
| 专用角色 ORCHESTRATOR spawn general LEAF | 被拒绝 | general LEAF = 全部工具 = 升级，应拒绝 |

**实际影响有限**：`max_spawn_depth = 2`，链路最多 MAIN → ORCHESTRATOR → LEAF。
需要多专家协作时，MAIN 可以直接 spawn 多个不同角色的 ORCHESTRATOR（并发上限 5），
或 spawn 一个 general ORCHESTRATOR 做多专家编排。专用角色做 ORCHESTRATOR
的场景是同角色 fan-out，不需要跨角色。

## 7. 边界场景

| 场景 | 行为 | 理由 |
|------|------|------|
| MAIN spawn 任意角色 | 允许 | MAIN 不受限 |
| general spawn 任意角色 | 允许 | general 有全部工具 |
| researcher spawn researcher | 允许 | 同角色 = 同工具 |
| researcher spawn executor | 拒绝 | executor 有 researcher 没有的工具 |
| researcher spawn general | 拒绝 | general inherit = 全部工具 = 升级 |
| researcher spawn librarian | 拒绝 | 角色不同（即使工具集相似） |
| 模型不传 functional_role（默认 general） | 专用父 → 拒绝（子=general=升级） | general 默认有全部工具 |
| server 重启后 spawn | 不影响 | run record 从 registry 恢复 |
| delegate_task 调 spawn | 同样受限 | 都走 spawn_subagent_direct |
| TaskFlow dispatch | 不受限 | TaskFlow 是 main_only，只有 MAIN 调 |

## 8. 不做的事

- **不做工具交集**——交集产生"残缺子代理"（executor 没有 write_file），
  模型拿到 executor 的 prompt 但没有对应工具，比直接拒绝更困惑。同角色派生
  要么完整同角色，要么明确拒绝。
- **不静默改角色**——拒绝而非 clamp。模型得到明确反馈，可以调整策略。
- **不限制 MAIN**——MAIN 是编排的起点，不受子代理遏制规则约束。
- **不限制 general**——general 是 inherit 模式（全部工具），任何子角色都是
  其子集，无升级可能。general ORCHESTRATOR 是多专家编排的推荐路径。
- **不改 tool schema**——`functional_role` 参数已有，遏制在 spawn 管线做，
  不在 tool 层做。
- **不改 functional role 的 AGENTS.md**——body 是 prompt 级引导，遏制是
  spawn 管线级硬约束，两者互补。

# 计划：WS 流断线续传（快照式 + 会话校验）

- 建档日期：2026-10-17
- 状态：**计划（未开工）**
- 来源：ZCode「流恢复锚点」评估。首版曾按「按序回放」设计（每帧 seq + ring），
  评审后改成本方案：**快照式续传**（成本约为回放的 1/4，覆盖断线窗口的可见损失），
  完整回放降级为 §5 的可选升级。
- 关联：`server/service/stream_dispatch.py`、`server/service/messages.py`、
  `server/trigger/core.py`、`runtime/session/relation_register.py`、
  `server/service/session_settings_service.py`（会话存在性）、
  `client/app/composables/bridge/agent-socket.ts`、
  `client/app/composables/use-chat-stream.ts`

## 0. 现状与缺口（已实测）

- 帧出口唯一：`StreamTurn.run()`（`stream_dispatch.py:467`）yield 所有帧 →
  三个公共生成器（`messages.py:499/519/543`）→ WS 触发层逐帧发送。
- 发送时按 session 查当前 socket（`turn_runner.get_websocket_by_session_id`），
  **重连后的新 socket 自动续收之后的帧**；断线窗口内发出的帧被 `send_ws_json`
  静默跳过。
- 客户端本地内容不丢，且流式期间每 200ms 有草稿持久化；回合结束/恢复路径用
  `loadSessionHistory` 回填。缺的是**窗口内的正文**——表现为流中段缺字，直到回合结束。
- **引擎已持有权威累积正文** `self.ai_text`（`stream_dispatch.py:258`，取消标记与落库
  共用），无需另建日志即可补齐。
- **越权面**：WS 分发取帧负载里的 `session_id`（`trigger/core.py:229`），
  连接注册的 `relation_register.get_session_id_by_websocket_id()`（`:96`）未被使用
  ——任何处理器都能被要求处理别的 session（`taskflow_refresh` 等同样受影响）。

## 1. 设计

### 1.1 快照式续传（核心）

- 服务端在 `StreamTurn` 上暴露只读快照：`ai_text`（正文）；
  `_has_reasoning`（是否已有思考输出，供客户端提示；思考正文不重建）。
- 客户端重连（`stream:reconnected`，`agent-socket.ts:272`）时若本地认为回合仍在进行，
  发 `resume_stream`；服务端回一帧快照；客户端把当前回合的 AI 正文**整体替换**为快照值
  （草稿尾部一并覆盖）。
- 未覆盖的窗口内容（错过的工具卡、思考流）由**回合结束的既有回填**自愈；
  不在首版做逐帧补齐。

### 1.2 会话校验（分发层加固，所有处理器受益）

- `ws_handler` 分发前用 `get_session_id_by_websocket_id(websocket.id)` 取连接注册的
  session，与帧负载的 `session_id` 比对：不一致则记日志并丢弃该帧（不调用处理器）。

### 1.3 多连接模型：1:N 广播（首版做）

现状（`runtime/session/relation_register.py`）：`session_id_to_websocket_id` 是
**1:1、后写覆盖**——**同一 session 的多个在线连接只有一个收到推送**，其余收不到直播帧；
当前目标断开后绑定直接删除、**不回退**到其他存活连接。

因此首版把推送模型改为 **1:N**：

- 注册表新增 `session_id → OrderedDict[websocket_id, ws]`（保留每 socket 反向映射）；
  注册追加、断连只移除自身（原有「旧 socket 晚到的 close 不得误清他人绑定」的守卫
  语义自然保持）。
- 新增共享 helper **`runtime/session/ws_push.py::broadcast_to_session(session_id, payload)`**
  （放 runtime 层：`server/` 与 `agent/` 都能 import，不破坏分层）：
  * 每帧只 `json.dumps` 一次；
  * 逐个 socket `send_text`，单个失败仅记录并从该 session 集合中剪除，**不影响其余**；
  * 每个 socket 的帧顺序与产生顺序一致（同一发送循环内逐帧广播）。
- 14 处推送点（`turn_runner` / `auto_turn` / `trigger/ws/messages` / heartbeat / cron /
  `taskflow.progress_push` / `todolist.service` / `web_search_push` /
  `terminal_bg_registry` / `subagent.announce.delivery` / `subagent.events.bridge`）
  机械切换为 `broadcast_to_session(...)`；server 侧的 `send_ws_json(get_websocket_...)`
  组合块多数变短，agent 侧原本自写的 `json.dumps + send_text` 一并收敛。
- **不做"按流量接管"**（上一版的单目标换手方案）：多个都在线且都在发帧时会互相抢目标、
  谁的间隙谁缺帧；1:N 广播下该机制不再需要。
- 新加入的查看者（加入晚于帧产生）由 `resume_stream` 快照补课（§1.1）。
- 残留限制：**离线期间不积压**（无 per-client 队列），回来靠回填——与 ZCode 的取舍一致。

### 1.4 已删除会话

- 处理器状态顺序：**会话不存在 → `gone`**；存在但无活跃 turn → `ended`；
  有活跃 turn → `ok`。`gone` 时客户端清本地回合态、不发起回填（删除流程本身会
  广播 `SESSION_ABORT_STREAM_EVENT` 并释放 socket）。

### 1.5 回合标识

- 快照帧带 `turn_num`（引擎所属 turn）：客户端只在快照的 turn 与自己跟踪的当前回合一致时
  应用替换；不一致（已换回合）则丢弃。一个 session 同时只有一个活跃 turn
  （队列按 turn 串行 + 每 session 单执行），服务端按 session 取活跃引擎即可。

## 2. 协议

### 2.1 恢复请求

```json
{"event": "resume_stream", "session_id": "<sid>", "content": {}}
```

（无需 `last_seq`：快照是整体值，天然幂等，重复请求无害。）

### 2.2 应答

```json
{"event": "stream_resume", "session_id": "<sid>", "content": {
  "status": "ok" | "gone" | "ended" | "unknown",
  "turn_num": 42,
  "text": "<ai_text 快照>",
  "has_reasoning": true
}}
```

| status | 条件 | 客户端动作 |
|---|---|---|
| `ok` | 会话存在且有活跃 turn | turn_num 匹配则整体替换正文；不匹配则丢弃 |
| `gone` | 会话已删除 | 清本地回合态；不回填 |
| `ended` | 会话存在、无活跃 turn（已结束/进程重启） | 走既有回填（`loadSessionHistory`） |
| `unknown` | 处理器异常（fail-open 日志） | 回填 |

## 4. 边界场景

| 场景 | 行为 |
|---|---|
| 回合进行中断线重连 | `ok` → 正文整体替换（含草稿尾部） |
| 回放期间又断线 | 再次重连再请求快照（幂等） |
| 回合已结束才重连 | `ended` → 回填 |
| 会话已删除 | `gone` → 清态、不回填 |
| 进程重启 | 无活跃引擎 → `ended`/`gone` → 回填 |
| 快照到达时回合已切换 | turn_num 不匹配 → 丢弃 |
| 旧客户端 / 旧服务端 | 互相忽略未知事件与字段，行为不变 |
| 跨 session 请求 | 分发层校验拒绝（不触达处理器） |

## 5. 不做（首版）与可选升级

- **不做**：逐帧 seq + 有界 ring + `(last_seq, now]` 回放——首版用快照覆盖可见损失，
  成本约为其 1/4；工具卡与思考流的即时性损失由回合结束回填自愈。
- **不做**：持久化事件日志 / 跨进程重启续传（回填兜底）、per-client 离线队列、
  服务端快照投影、7 事件 `stream_recovery_*` 协议（行为已被 LLMRetry /
  MaxTokensBoost / InvalidToolCallRepair / Summarization 覆盖）。
- **可选升级 A**（仅在快照方案仍不满意时）：加每帧 `seq` + 有界 ring + 按序回放，
  补齐工具卡与思考流的逐帧连续性；协议与客户端门控在必要时再引入。


## 6. 测试

- 服务端：快照访问器（ai_text / turn_num / has_reasoning）；processor 四状态；
  socket↔payload session 不一致时被丢弃（含 fail-open）；会话不存在（`gone`）与
  活跃引擎存在（`ok`）的优先级。
- 推送模型：**多 socket 同时接收**（同一 session 两个连接各收到完整帧序列）；
  单个 socket 发送失败被剪枝、其余照收；断连只移除自身；每 socket 顺序不变。
- 客户端：仅回合进行中发 `resume_stream`；`ok` 且 turn 匹配 → 替换；
  不匹配 → 丢弃；`gone` → 清态不回填；`ended/unknown` → emit 回填事件。
- 全量门（`tests/run_tests_split.py`）+ 客户端 quick 门。

## 7. 验收（手工）

1. 回合进行中断网 2–5 秒恢复：正文立即补齐（无跳段），日志一条 `resume_stream ok`。
2. 回合结束后重连：走回填，无缺字、无双写。
3. 另一标签页打开同一 session 后本页异常重连：快照替换不产生重复文本。
4. 会话删除后重连：`gone`，页面不再请求回填。
5. 同一 session 两个连接：**两处同时收到完整直播**；断开其中一个，另一个继续收流不受影响。

## 8. 工作量

服务端 ~80–120 行（快照访问器 + processor + 校验）、推送模型 ~100–150 行
（1:N 注册表 + 广播 helper + 14 处调用点清理）、客户端 ~80–120 行、测试 ~120–150 行；
合计 **~450–600 行**（原逐帧回放方案的 2/3），无持久化、无逐帧协议开销；
多在线连接同时收流成为首版能力。

# 计划：辅助会话生命周期（临时子会话）

- 建档日期：2026-10-24
- 状态：**待评审 / 未开工**
- 关联：`TODO/计划_辅助会话继承主会话上下文.md`（两者共用 parent 关联和服务端创建入口）
- 目标：
  1. 主会话被删除时，辅助会话跟着消失，并清空历史、checkpoint、运行时状态、工作区目录等全部痕迹；
  2. 关闭右侧辅助会话标签页时，同样删除辅助会话并清空全部痕迹；
  3. 辅助会话不再作为普通会话出现在主会话列表里，只能通过所属主会话的侧栏标签访问。

## 0. 结论先行

推荐把辅助会话做成**临时子会话（ephemeral side session）**：

- 有服务端持久化的 `parent_session_id` 关联；
- 从普通会话列表中隐藏；
- 生命周期绑定右侧 `sideChat` 标签页和主会话：**关标签 = 删除；删主会话 = 级联删除**；
- 删除走现有的 `purge_session()` 全套清理，而不是只关运行实例；
- 关闭正在运行的辅助会话时先取消该会话的 turn，再 purge，避免清理与流式输出竞态。

## 1. ZCode 的做法（已核实）

ZCode 的 selection side chat 是一个隐藏 child：

- `taskType: "selection_side_chat"`，`parentID` 指向父会话；
- root session 查询默认排除它（`apps/zcode-cli/packages/adapters/tests/session-store.test.ts` 的 “root session queries keep it hidden”）；
- 侧栏关闭标签时，`packages/ui/src/hooks/useAppPanels.ts::closeSelectionSideChatRuntime()`：
  - 清掉 selection reference scope；
  - 调 `zcodeSessionService.closeSession({ sessionId: childSessionId })` 关闭 child runtime；
  - 关闭并移除 side pane tab。
- 父任务归档/删除时，`subscribeTaskLifecycle()` 找到所有 `parentSessionId === event.taskId` 的 selection-side-chat tab，逐个 `closeSelectionSideChatRuntime()` 并关闭 tab；
- `WorkspaceShellLayout.tsx::handleV4SessionDeleted()` 在父会话删除时也关闭对应 side tabs。

**重要差异**：ZCode 的 `closeSession` 只释放运行实例，不删除持久化事实。`server-operations.ts` 明确写着：

> 关闭运行实例不删除持久化事实，因此必须保留 sessions-index 中的行。

ZCode 的 child 是隐藏的，所以关标签后不会出现在 root 列表，但底层 checkpoint/消息是否真正删除取决于后续的 soft-delete/清理流程。用户要求“清空一切痕迹”比 ZCode 当前 close 路径更严格；sherry 应直接使用已有的 `purge_session()`，而不是只关闭 runtime。

## 2. 当前 sherry 的差距

- `client/app/composables/use-side-chat.ts`：辅助会话是普通可见 session，`crypto.randomUUID()` 前端生成，没有 parent 关联。
- `client/app/pages/home/components/RightSidebar.vue`：关闭 tab 直接调 `store.closeTab(tab.id)`；`right-sidebar.ts::closeTab()` 只从数组移除，不会删除会话。
- `server/service/session_cleanup_service.py::purge_session()` 已经能清：
  - mes_memory 消息；
  - todo / TaskFlow；
  - checkpointer（checkpoints + writes）；
  - 后台 terminal 任务；
  - 会话目录（含附件）、plan knowledge；
  - 内存/持久 state registers；
  - evidence ledger；
  - 浏览器页面；
  - subagent 子树。
  但它只遍历 subagent 子树，**不知道 side chat 的 parent 关系**，所以删除主会话不会清辅助会话。
- 主会话列表来自 message store；辅助会话一旦有消息就会出现在列表里，关闭标签也不会消失。
- 没有 boot sweep 处理“主会话已删除、辅助会话还留着”的孤儿。

## 3. 数据模型

新增一个轻量 side-chat 关联表（建议独立 SQLite，避免把普通会话表撑大）：

```
side_chat_children (
  child_session_id  TEXT PRIMARY KEY,
  parent_session_id TEXT NOT NULL,
  created_at        INTEGER NOT NULL
)
CREATE INDEX side_chat_children_parent ON side_chat_children(parent_session_id);
```

放在现有的数据目录下（例如 `src/data/side_chats.db`，具体路径按 `agent/tools/pub_base/sqlite_store.py` 的约定选一个独立 store）。

职责：

- 创建辅助会话时写入一行；
- 主会话删除时按 `parent_session_id` 查出全部 child；
- 关闭辅助会话时删除该行；
- boot sweep 发现 parent 不存在时删除孤儿 child 及其数据；
- 主会话列表查询排除这些 child id（或者给消息行加 side-chat 标记后过滤，二选一；推荐独立表 + 过滤，避免污染 messages schema）。

## 4. 创建与关联

复用上下文计划的 `POST /sessions/side_chat`：

1. 服务端校验 parent 存在；
2. 生成 child id；
3. 写 `side_chat_children`；
4. 按上下文计划写入父会话快照；
5. 返回 child id。

前端 `createSideChatSession()` 改用服务端返回的 id，并继续复制 Dexie 的 preset / character / agent config / project dir。

## 5. 关闭右侧标签页 = 删除辅助会话

### 5.1 关闭入口

`RightSidebar.vue` 不再直接 `store.closeTab(tab.id)`。改为调用页面/组合式提供的 `closeSidePaneTab(tab)`：

- 普通 tab：保持现状，只 `store.closeTab`；
- `sideChat` tab：
  1. 读取 `tab.payload.sessionId` 和 `parentSessionId`；
  2. 调 `DELETE /sessions`（或专用 `DELETE /sessions/side_chat`，见下）删除 child；
  3. 清客户端缓存；
  4. 关闭 tab。

所有关闭路径必须走同一个 helper：

- 标签页右上角 X；
- 键盘/菜单的关闭；
- 父会话删除后的程序化关闭；
- 未来的批量关闭。

### 5.2 服务端删除语义

优先复用现有 `clear_session` / `purge_session`，但加一层 side-chat 校验：

```http
DELETE /sessions/side_chat
{ "session_id": "<child>", "parent_session_id": "<parent>" }
```

- 校验 child 确实在 `side_chat_children` 中且 parent 匹配；不能拿这个接口误删普通会话。
- 删除顺序：
  1. 取消 child 正在运行的 turn（见 5.3）；
  2. 关闭 child 的浏览器页面；
  3. `purge_session(child)`（消息、todo/taskflow、checkpoint、session 目录、plan knowledge、state registers、evidence、terminal_bg、subagent 子树）；
  4. 删除 `side_chat_children` 行；
  5. 广播 session/tab 移除事件（见 5.5）。
- 删除失败要返回失败，并保留标签页，避免“UI 消失了但数据还在”。

### 5.3 运行中的 turn

`purge_session()` 本身不负责停 turn。关闭前需要：

- 找到 child 的 turn 控制器/AbortController，先取消当前 turn；
- 中止该 session 的 socket 流和排队输入；
- 再 purge。

实现上复用现有的 stop/interrupt 路径，不新造一套；如果关闭时没有 running turn，直接跳过。

### 5.4 客户端清理

关闭 side chat 时同步清：

- `clearCachedCharacter(childId)`；
- `clearCachedSessionPreset(childId)`；
- `clearCachedSessionMeta(childId)`；
- `clearSessionTitleOverride(childId)`；
- selection reference scope（`clearConversationSelectionReferenceScope` 对应能力）；
- 该 tab 的 stream / socket（`SESSION_ABORT_STREAM_EVENT` 或 socket release）；
- 右栏 tab 状态。

与 `SessionSidebar.handleDeleteSession()` 的缓存清理保持一致；建议抽成 `clearSideSessionClientCaches(id)`，主/辅删除共用。

### 5.5 多窗口/多客户端

服务端删除后广播一个轻量 WS 事件：

```json
{"event":"side_chat_removed","session_id":"child","parent_session_id":"parent"}
```

- 本窗口：直接关 tab；
- 其他窗口：收到后关掉对应 sideChat tab，并清本地缓存；
- 如果暂时不复用全局广播，至少本窗口完成；其他窗口在历史请求 404/为空时显示 missing，并在下次连接时清理。

## 6. 删除主会话 = 级联删除辅助会话

在 `server/service/session_cleanup_service.py::purge_session(parent_id)` 里，在 subagent 子树清理之前或之后：

1. `list_side_chat_children(parent_id)`；
2. 对每个 child 调 `purge_side_chat(child, parent_id)`（复用 5.2 的清理，不需要再广播单个事件）；
3. 删除 parent 的关联行；
4. 继续原有 `purge_session_data(parent)`。

要点：

- child 的 turn 要先取消，避免 purge 和流式写 SQLite 竞态；
- 级联失败要逐 child fail-open 记录日志，不能阻止父会话本身被删除；
- 不能因为 parent 删除去删不属于它的普通 session；
- 若 parent 删除时某个 side tab 还开着，客户端根据返回/广播的 child ids 关 tab。

客户端 `SessionSidebar.handleDeleteSession()`：

- 删除前/后查 `sideChatTabsForParent(parentId)`，逐个走 `closeSidePaneTab`；
- 或者服务端返回 `deleted_side_chat_ids`，客户端按 ids 关 tab；
- 清理客户端缓存同 5.4。

## 7. 右栏整体收起 vs 关闭标签

需要明确区分：

- **收起右栏 / 切换 scope**：只是隐藏，不删除辅助会话；
- **关闭 sideChat 标签**：删除；
- **关闭整个应用/窗口**：不做持久删除；重启后 side chat 不应恢复（右栏 tab 本身不持久化，见 `right-sidebar.ts` 的 persist `pick`，目前只持久化 collapsed/width/maximized）。服务端若发现孤儿，boot sweep 清理。

## 8. 启动时的孤儿清理

在 `server/service/orphan_session_sweep.py` 增加一段：

- 遍历 `side_chat_children`；
- parent session 不存在（message store/checkpoint/registry 无记录）→ `purge_side_chat(child)`；
- child 自己已不存在 → 删除关联行；
- 一次 fail-open pass，和现有 subagent orphan sweep 同风格。

这解决“主会话在另一个进程/崩溃前被删除，辅助会话残留在 DB 里”的情况。

## 9. 与上下文继承计划的关系

两件事共用同一个 parent 关联和创建接口：

- 先做 `POST /sessions/side_chat` + `side_chat_children` + parent 快照（上下文计划）；
- 再做本计划的关闭/级联/孤儿清理。

不建议先做“关闭即删”而没有 parent 关联：那样只能删当前标签的 child，无法处理主会话删除和重启孤儿。

## 10. 测试与验收

### 服务端

- 创建 side chat → `side_chat_children` 有 parent/child 行；普通 session 列表不返回 child。
- `DELETE /sessions/side_chat`：
  - 删除 child 的 messages / checkpoint / todo / taskflow / session dir / state registers / evidence；
  - 删除 `side_chat_children` 行；
  - parent 不受影响；
  - 错误 parent id 被拒绝。
- 删除 parent：
  - 所有 child 被 purge；
  - parent 自己的数据也清；
  - 其他普通 session 不受影响。
- 运行中的 child：先取消 turn，再 purge，不出现“删除后仍有流式 chunk”。
- boot sweep：parent 不存在 → child 被清理；child 已不存在 → 关联行被清理。

### 前端

- 点 sideChat tab 的 X → 调删除接口 → tab 消失 → 会话列表没有 child → Dexie 缓存清空。
- 普通 tab 的 X 不触发删除。
- 收起右栏不触发删除。
- 删除父会话后，本地所有 parent 对应的 sideChat tab 关闭。
- WS `side_chat_removed` 到达其他窗口时关闭对应 tab。
- 删除失败时 tab 保留并提示错误。

### E2E

1. 主会话发消息 → 选中文本 → 辅助会话提问 → 关闭辅助会话 tab；
2. 确认侧栏列表没有辅助会话，DB 中 messages/checkpoint/session dir/state 均无记录；
3. 重新打开辅助会话，历史为空（新 child）；
4. 主会话删除辅助会话仍开着 → 辅助会话 tab 自动关闭，数据清空；
5. 主会话和辅助会话同时运行 → 删除主会话，child turn 被取消，无残留流。

## 11. 风险与取舍

- **关闭即删不可恢复**：这是用户明确要求；可以在关闭时给一个短暂 toast 说明“已关闭并清理”，但不提供撤销。
- **误关风险**：sideChat 标签的 X 即删除，需要在 tooltip/确认上说明；不要和普通 tab 的“关闭”混同。
- **多窗口竞态**：删除/关闭可能来自两个窗口；服务端删除要幂等（已不存在视为成功），广播只做 UI 收尾。
- **现有辅助会话**：本计划只影响新建的 side chat；已有的普通辅助会话没有 parent 关联，不会自动删除。若需要，另做一次“把它们迁移成 side chat 或保留为普通会话”的决定。
- **parent 删除的级联广度**：只清 `side_chat_children` 中的 child，不碰普通 session。
- **右栏收起不删除**：避免用户只是隐藏右栏就丢掉辅助会话；只有显式关闭标签才删。

## 12. 不做什么

- 不把关闭辅助会话做成“只关 runtime、保留 DB 痕迹”的 ZCode 弱清理；用户要求清空痕迹。
- 不删除普通 session，只处理 parent 关联的 side chat。
- 不在右栏收起/切换 scope 时删除。
- 不把 side chat 重新暴露到主会话列表。
- 不依赖前端 `crypto.randomUUID()` 生成 child id；由服务端创建并关联。

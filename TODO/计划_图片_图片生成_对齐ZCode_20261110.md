### 1.2.1 Artifact store API（r3 确认）

`agent/tools/pub_base/artifact_store.py::write_artifact` 签名：
```python
def write_artifact(session_id: str, data: bytes, *, media_type: str = "binary",
                   ext: str = ".bin", root: Path | None = None) -> str | None
```
- 返回 `sherry-artifact://<session_id>/<family>-<sha256前16位hex><ext>`（如 `sherry-artifact://abc123/image-9f8e7d6c5b4a3928.png`）
- 内容寻址去重（相同 bytes → 相同文件名，第二次写是 no-op）
- 纯同步，无 async/网络/DB；脚本可直接 `from agent.tools.pub_base.artifact_store import write_artifact`
- 返回 `None` 表示禁用/空数据/写入失败，调用方需 fallback

### 1.2.2 Terminal env 注入现状（r3 确认：必须改）

**terminal 工具当前不注入 `SHERRY_SESSION_ID`**——`agent/tools/terminal/core.py` 的 env 路径只有 `scrub_env()`（纯过滤，不加任何变量）。`session_id` 字段仅用于 cwd 绑定/shadow-git/stdout 临时文件，从不复制进子进程 env。

代码库中已有注入模式的先例：`agent/middlewares/user_hooks/core.py:138`：
```python
env = scrub_env()
env["SHERRY_SESSION_ID"] = session_id
```
terminal 需在两处 spawn 点（`core.py` 约 L652 和 L843）复刻同样的注入。**这不是可选的——是 artifact store URI 需要 session_id 的硬依赖**。

**通用收益**：11 个 scripted skill 中至少 6-8 个经 terminal 调用，全部无法从 env 获取 session_id。terminal 注入是平台级改进，不只服务图片生成。

### 1.2.3 迭代预算分析（r3 新增）

IterationBudget（`agent/middlewares/iteration_budget/core.py`）按 **model call** 计数，每 turn 重置，main agent 默认 180。

| 路线 | 单张图迭代数 | 多张图（N） | HITL 风险 |
|---|---|---|---|
| skill 路线 | **3 次**（skill_view → terminal → 回答）；skill body 已知时 2 次 | **O(N)**：N 次 terminal 调用 | 低——benign python 命令自动放行，但每次走审批管线扫描 + shadow-git checkpoint |
| 专用工具 | **2 次**（工具调用 → 回答） | **O(1)**：批量 `list[str]` 一次返回 | 无——非 terminal 工具默认 allow-through |

skill 路线每次生成多花 1 次迭代（skill_view 那一步）。绝对值可忽略（180 预算），但影响延迟和 token 成本。**多图场景的 O(N) 放大是真正的问题**，但多图生成已在本计划 §2.4 明确 defer 到阶段 2。

### 1.3 前端渲染机制（核实）

- 最终 AI 气泡只渲染 AIMessage `content`（`ChatBox.vue:243` `bubbleDisplayText`）

- 图片 markdown `![](sherry-artifact://...)` 只有在消息 content 里才被 `resolveArtifactRefsInMarkdown` 解析渲染
- **ChatToolCard 当前不渲染图片**——需要加图片渲染分支（§2.2）
- `useImagePreview`（画廊/lightbox）+ `resolveArtifactRefsInMarkdown`（artifact URI → `/artifacts` URL）已实现，可复用

### 1.4 专用工具作为未来升级（本计划不做，但迁移成本已评估）

原 r1 计划建新 `ImageGenerationTool` + `TTIModel` provider 模块。r2 改走 skill 路线（修脚本 + ChatToolCard 渲染）。专用工具的结构化优势（不经 terminal 往返、无 skill_view 迭代开销、批量 O(1)、按工具名套渲染器、不依赖脚本 print URI）作为**未来升级**。

**迁移成本评估（r3 新增）**：如果现在做 skill 路线、将来切换到专用工具，以下工作是**路线无关的、不浪费的**：
- ✅ 前端 ChatToolCard 图片渲染 + 自动展开 + 折叠头部缩略图 → 专用工具结果同样含 artifact URI，同一渲染分支直接复用
- ✅ Terminal SHERRY_SESSION_ID 注入 → 平台改进，所有 scripted skill 受益，永久保留
- ✅ 格式守卫逻辑（`should_force_response_format` / `IMAGE_GEN_MAX_N`）→ 可直接搬到专用工具的 provider wrapper
- ✅ Artifact store 集成模式 → 专用工具复用同一个 `write_artifact` 调用
- ❌ SKILL.md 更新 → 切换时废弃/删除，但成本极低
- ❌ 脚本的 stdout print URI → 专用工具不需要，但也就是删一行

**结论：skill 路线的工作 ~80% 路线无关，迁移到专用工具时只有 SKILL.md + print 行需要丢弃。**

> **若 r1 已创建 `agent/tools/image_gen.py` 和/或 `models/TTI_model/`，必须删除**（含 `build_main_tools()` 里的注册行、模型注册表条目）。避免 skill 路线和专用工具双路径并存导致行为歧义。清理后跑回归确认 24 个内置工具不变。

### 2.1 修 skill 脚本（核心：artifact store + print URI + 格式守卫）

`skills/builtin/text_to_image/scripts/core.py` 改造：

```python
@validate_call
def generate_image(prompt: str, *, size: str = "1024x1024", quality: str = "standard",
                   n: int = 1, model: str | None = None) -> str:
    """生成图片，写入 artifact store，返回 sherry-artifact:// URI。"""
    # 1. 读 TTI_* env（url/api_name/api_key）
    # 2. 解析 model（参数 > env TTI_API_NAME）
    # 3. 格式守卫（§2.3）：新模型省略 response_format，旧模型强制 b64_json
    # 4. POST 图片 API
    # 5. 解码 b64_json → bytes（处理 data: 前缀）
    # 6. 写 artifact store（需 session_id，见下）
    # 7. print(sherry-artifact:// URI) 到 stdout  ← 让 terminal 工具结果捕获
    # 8. return URI
```

**关键改动**：
- `STATIC_DIR` → artifact store（`agent/tools/pub_base/artifact_store.py::write_artifact`）
- 返回 `None` → 返回/print `sherry-artifact://<sid>/<name>` URI
- 硬编码 `response_format: b64_json` → 格式守卫
- 硬编码 size/seed → 可配参数
- **不 print 任何东西 → print URI 到 stdout**（这是让 agent 能拿到结果的前提，不是优化）

**session_id 获取（r3 确认：方案 A 必须，不是可选）**：artifact store 的 URI 是 session 作用域（`sherry-artifact://<session_id>/<name>`）。脚本经 terminal 运行，需拿到 session_id。

- **方案 A（采用）**：terminal 工具执行命令时注入 `SHERRY_SESSION_ID` 环境变量。需改 `agent/tools/terminal/core.py` 两处 spawn 点（约 L652 和 L843），在 `scrub_env()` 后加 `env["SHERRY_SESSION_ID"] = session_id`。复刻 `agent/middlewares/user_hooks/core.py:138` 的已有模式。
  - **这不是只服务图片的改动**——11 个 scripted skill 中 6-8 个经 terminal 调用，全部受益。
  - **不再标"可能改"——是必须改**。不做这步，artifact store 无法获得 session_id，URI 无法生成。
- 方案 B（SKILL.md 传参）已排除——依赖 agent 自觉传 session_id 不可靠，且 skill mention chip 不自动注入参数。

### 2.2 ChatToolCard 图片渲染分支（核心前端改动）

`client/app/components/chat/ChatToolCard.vue` 现在所有工具结果走 `<pre>` 纯文本（`message.toolResult`）。新增**图片渲染分支**：

```vue
<!-- 现有：纯文本 <pre> -->
<!-- 新增：检测 toolResult 含 sherry-artifact:// URI → 渲染缩略图 -->
<template v-if="hasArtifactImages(message.toolResult)">
  <ImageThumbnailGallery>
    <img v-for="uri in extractArtifactUris(message.toolResult)"
         :src="resolveArtifactUriToHttp(uri)" @click="openLightbox(uri)" />
  </ImageThumbnailGallery>
</template>
<pre v-else>{{ message.toolResult }}</pre>
```

- `hasArtifactImages`：检测 toolResult 文本含 `sherry-artifact://` 正则匹配
- `extractArtifactUris`：提取所有 URI
- `resolveArtifactUriToHttp`：复用 `media-resolver.ts::artifactUriToHttp`
- lightbox：复用 `useImagePreview`（`openGallery(items, startIndex)`）
- **通用分支**：任何工具结果（terminal 跑 skill / 未来专用工具）含 `sherry-artifact://` URI 都渲染，不绑定工具名

参照 ZCode 的 `NodeReplImageGrid`（缩略图网格 + `ImagePreviewDialog` lightbox）。

**图片默认可见（关键 UX，否则图片藏在折叠工具卡里看不到）**：

Sherry 工具卡默认折叠（`expandedToolCards` Set 默认空），且整个 turn 工作历史还折叠在最终答案后面（`use-chat-turn-fold.ts`）。图片只在工具卡里 → 默认不可见。两层保证可见：

1. **自动展开含图工具卡**（选项 1）：工具结果含 `sherry-artifact://` URI 时，该工具卡**自动展开**（加入 `expandedToolCards` 默认集合，不走点击展开）。改 `useChatCardExpansion`（或渲染时检测 URI → 强制 expanded）。这样图片在 turn 中途的工具卡里直接可见，不需用户点击。

2. **turn 折叠头部露缩略图**（选项 3）：当 turn 历史折叠时（`ChatTurnHistoryStatus` 折叠按钮），扫描该 turn 工具结果里的 `sherry-artifact://` URI，在折叠按钮旁显示**小缩略图预览**（一张或几张缩略图 peeks）。用户一眼看到"这里有图"→ 点击展开 turn 历史 → 看到完整图（自动展开的工具卡里）。

两层配合：turn 折叠时头部露缩略图（选项 3 提示有图）→ 展开后工具卡自动展开（选项 1 直接显示图）→ 工具卡内点击图进 lightbox（§2.2 渲染分支）。全程不需模型在气泡复述、不动中间件。

# 计划：用 langchain-dynamic-workflow 重放已验证的 plan（零调用 journal replay）

> **场景**：plan 在 TaskFlow 首次执行时已跑通（经 retry/judge/schema gate 验证到 success）。把这条**已验证的成功路径**编译成 langchain-dynamic-workflow（ldw）的 workflow，后续遇到同类任务时重跑——ldw 的 journal 按 `(prompt, agent_type, model, schema)` 内容哈希缓存每个 leaf 结果，resume 时已完成 step **零模型调用重放**。
>
> **不在范围**：首次执行的 retry/judge/schema gate（那是 TaskFlow 的事，重放时不参与——journal 直接给成功结果，绕过整个 retry 流程）。
>
> **前置**：`计划_handoff成功路径与失败分支修正_20261106.md` 落地后，plan 抽取产出 `success_steps`（成功路径步骤）+ `hard_constraints` + `failed_branches`，作为编译输入。
>
> **日期**：2026-11-06

## 一、粒度对齐（已确认）

TaskFlow step ↔ ldw leaf 天然对齐——都是「一个 agent 跑到完成」：

| TaskFlow（首次执行，已跑通） | ldw workflow（重放） |
|---|---|
| flow（一组 step + DAG） | `ctx.dag([DagNode...])` |
| step（已 success 的那次 spawn） | `DagNode.run = ctx.agent(prompt=step_task, agent_type=role)` |
| step `depends_on=[...]` | `DagNode(deps=[...])` |
| step 的 functional_role | Roster 注册的 agent_type |
| step 的 task 文本 | `ctx.agent(prompt=...)` |
| retry / judge / schema gate | **不编译**——重放不需要，journal 命中即返回 |

happy path（一次过）step = 一个 ldw leaf，journal 缓存这个 leaf 的结果。重跑时每个 step 查 journal，命中零调用。retry/judge 是首次执行的事，重放时 step 已是 success 状态，journal 直接给成功结果。

## 二、编译路径

`compile_plan_to_workflow(plan_knowledge) -> orchestrate`：

```python
from langchain_dynamic_workflow import run_workflow, Ctx, DagNode
from langchain_dynamic_workflow._dag import DagNode

def compile_plan_to_workflow(plan_knowledge: dict) -> tuple:
    """把已验证 plan 的 knowledge（success_steps + dag 依赖 + role + task）编译成 ldw orchestrate。

    输入（plan 抽取产物，从 knowledge(action="read") 取）：
      - steps: [{step_id, task, functional_role, depends_on, success_outcome}]
      - hard_constraints: list[str]（guard 断言）
      - failed_branches: list[{branch, failure_reason}]（注释/race 排除）

    输出：(orchestrate, required_agent_types)
    """
    steps = plan_knowledge["steps"]
    hard_constraints = plan_knowledge.get("hard_constraints", [])

    async def orchestrate(ctx: Ctx) -> dict:
        # hard_constraints 作 guard（编译时注入，非 LLM 生成——绕过 AST gate）
        # （guard 是可信编译产物，直接写进 orchestrate 源码）
        nodes = []
        for s in steps:
            prompt = s["task"]
            agent_type = role_agent_type(s["functional_role"], s.get("extra_tools"))  # role + extra_tools 指纹
            deps = s.get("depends_on", [])
            # 闭包捕获当前 step 的 prompt/agent_type
            nodes.append(DagNode(
                id=s["step_id"],
                deps=deps,
                run=lambda d, p=prompt, a=agent_type: ctx.agent(prompt=p, agent_type=a),
            ))
        results = await ctx.dag(nodes)
        return results

    required_agent_types = {role_agent_type(s["functional_role"], s.get("extra_tools")) for s in steps}
    return orchestrate, required_agent_types
```

- 编译产物是**可信代码**（由 sherry 代码生成，非 LLM author）→ 直接构造 `orchestrate` callable 交给 `run_workflow`，**绕过 ldw 的 AST gate**（AST gate 只管 `run_script` 的 LLM 现场脚本）。
- `hard_constraints` 编译时注入成 guard 断言（写在 orchestrate 里，非 LLM 生成）。
- `failed_branches` 作为注释或 `race` 候选排除（可选，MVP 先注释）。

## 四、阻塞 2：sherry 子 agent 包装成 langchain Runnable + Roster 注册

ldw leaf 要求是**接受 `{"messages":[...]}` 的 langchain Runnable**（`_engine.py:281` `runnable.ainvoke({"messages":[HumanMessage(...)]})`）。

sherry 子 agent 是 LangGraph 图（`built_agent()`）——**本身就是 langchain Runnable**。所以包装不难：

```python
from langchain_core.language_models import Runnable
from agent.core import built_agent
from langchain_dynamic_workflow import Roster

def step_tools(functional_role: str, extra_tools: list | None = None) -> list:
    """按 step 取完整工具集 = role 基础工具 + 该 step 的 extra_tools。

    role 基础工具集来自 functional_role 的 allow-list（SPAWN_ALLOWED_CHILD_ROLES
    对应的工具面）；extra_tools 来自 step 的 spawn contract（step_spawn_kwargs）。
    重放保真：leaf 工具集必须与 TaskFlow 首次执行该 step 时一致。
    """
    base = role_base_tools(functional_role)   # role → 基础工具集
    extra = extra_tools or []
    # 去重（extra 可能与 base 重叠）
    seen = {t.name for t in base}
    merged = list(base) + [t for t in extra if t.name not in seen]
    return merged

def make_leaf_agent(functional_role: str, tools: list, model_profile: dict) -> Runnable:
    """按 step 造一个 sherry 子 agent（LangGraph 图 = Runnable），带完整工具集。"""
    return built_agent(
        tools=tools,
        model=build_model(model_profile),
        system_prompt=role_prompt(functional_role),
        # ... sherry agent 构建参数
    )

def register_roster(steps: list[dict]) -> Roster:
    """按 step 注册 leaf agent。

    agent_type = step 级标识（含 role + extra_tools 指纹），而非纯 role——
    因为同 role 的不同 step 可能带不同 extra_tools，工具集不同则 leaf 不同。
    journal key 含 agent_type，所以同 role + 同 extra_tools 的 step 共享缓存，
    同 role + 不同 extra_tools 的 step 各自缓存（符合重放保真）。
    """
    roster = Roster()
    for s in steps:
        role = s["functional_role"]
        extra = s.get("extra_tools")             # step 的 spawn contract 里
        tools = step_tools(role, extra)          # role 基础 + step extra
        model_profile = step_model(role, s)      # step_model 优先于 role 默认
        # agent_type：role + extra_tools 指纹（同组合复用同一 leaf）
        agent_type = role_agent_type(role, extra)  # e.g. "executor" 或 "executor+xt:patch,terminal"
        roster.register(
            name=agent_type,
            builder=lambda *, response_format=None, t=tools, mp=model_profile, r=role:
                make_leaf_agent(r, t, mp),
            description=f"sherry {role} subagent (tools={len(t)})",
        )
    return roster
```

- `agent_type` = role + extra_tools 指纹（`role_agent_type(role, extra)`），同 role + 同 extra_tools 的 step 共享一个 leaf agent + journal 缓存；同 role + 不同 extra_tools 的 step 各自独立（重放保真：工具集不同则 leaf 不同）。
- `step_tools(role, extra_tools)` = role 基础工具 + step 的 extra_tools（从 step spawn contract 取），与 TaskFlow 首次执行该 step 时的工具集一致。
- `builder` 按 `(name, response_format 恒等值)` 缓存编译图（`_roster.py:143`），同 agent_type 多次 leaf 调用复用一个 agent 图。
- session_id 注入：sherry 工具是进程级单例带 session-scoped state，ldw leaf 在隔离 context 跑。需在 leaf 调用前注入正确的 session_id（leaf 的 RunnableLambda 包一层设 contextvar，或 sherry 工具改成从 ldw context 取 session）。**这是主要工程点**。

## 四补：ldw leaf + PTC 组合（journal miss 时快速执行）

leaf 子 agent 不必「从零推理决定调哪些工具」（慢，多 turn LLM 推理）。journal 未命中时（新变体，输入不同），leaf 加载本 step 的 success_steps 编译成的 **PTC 脚本模板**，适配参数后 `execute_code` 一次跑完——快速执行，无 LLM 多 turn 推理。

### 两层产物（PTC 每 step；ldw 每 plan）

| 产物 | 用途 | 粒度 |
|---|---|---|
| ldw DagNode（step → ctx.agent） | step 间编排 + journal step 级缓存 | step 级（子 agent） |
| PTC 脚本模板（step 的 success_steps → `scripts/ptc__<plan_key>__<step_id>.py`） | leaf 内部快速执行（journal miss 时） | 工具调用级（step 内） |

### 产物命名（已确认）

PTC 和 ldw 都直接放 owning skill 的 `scripts/` 顶层，用类型前缀区分，不建 compiled store、不维护 manifest：

```text
skills/auto/<owning-skill>/scripts/ptc__<plan_key>__<step_id>.py
skills/auto/<owning-skill>/scripts/ldw__<plan_key>.py
```

- `ptc__` / `ldw__` 是**产物类型前缀**，避免两类脚本混在一起；
- `plan_key` 来自 `resolve_plan_identity`，`step_id` 来自 TaskFlow step；
- 文件名即映射，重放只拼这两个路径；
- 脚本必须放 `scripts/` 顶层，不能放 `scripts/ptc/` / `scripts/ldw/`；`skill_view` 只扫描 `scripts/*.py`；
- `skill_manage(write_file)` 要求 owning skill 已存在：先 create/patch skill，再写脚本；
- ldw 的元数据不再放 `workflow.json`，直接写在 `ldw__<plan_key>.py` 的模块常量里：
  `PLAN_KEY`、`REQUIRED_AGENT_TYPES`、`HARD_CONSTRAINTS`、`ORCHESTRATE`（或 `def orchestrate(ctx)`）。

### leaf 配置

leaf 子 agent 带 PTC（`execute_code`）工具 + 该 step 的脚本模板（作为 skill）：

```python
def make_leaf_agent(functional_role, tools, model_profile, step_id, ptc_script):
    """leaf 子 agent：带 PTC 工具 + 本 step 的脚本模板 skill。"""
    # tools 含 execute_code（PTC）
    # ptc_script 注册为 skill（skills/auto/<owning-skill>/scripts/ptc__<plan_key>__<step_id>.py）
    return built_agent(
        tools=tools + [execute_code_tool],
        model=build_model(model_profile),
        system_prompt=role_prompt(functional_role) + ptc_script_hint(step_id),
        # system prompt 提示：「本 step 有 PTC 脚本模板 scripts/ptc__<plan_key>__<step_id>.py，
        #   journal miss 时优先 skill_view 读脚本 → 适配参数 → execute_code，
        #   而非从零推理调工具」
    )
```

### PTC 脚本模板（从 success_steps 编译）

```python
def compile_step_ptc_script(step: dict, hard_constraints: list, failed_branches: list) -> str:
    """把 step 的 success_steps 编译成 PTC 脚本模板。

    success_steps: [{step, tool, params, outcome}]（本 step 成功路径的工具调用序列）
    → 脚本：from sherry_tools import <tool> + 顺序调用 + hard_constraints guard 断言
            + failed_branches 作注释（# AVOID: ...）
    """
    lines = ["from sherry_tools import " + ", ".join(
                {s["tool"] for s in step["success_steps"] if s.get("tool")})]
    for c in hard_constraints:
        lines.append(f"# HARD CONSTRAINT: {c}")
    for fb in failed_branches:
        lines.append(f"# AVOID: {fb['branch']} — failed because {fb['failure_reason']}")
    for i, s in enumerate(step["success_steps"]):
        if s.get("tool"):
            lines.append(f"# step {i+1}: {s['step']}")
            lines.append(f"r{i} = {s['tool']}({s['params']})  # expected: {s['outcome']}")
    lines.append("import json; print(json.dumps({'r': [r0, r1, r2]}))")
    return "\n".join(lines)
```

脚本写入 `skills/auto/<owning-skill>/scripts/ptc__<plan_key>__<step_id>.py`，leaf 子 agent 通过 `skill_view` 读取。

### 两种命中情况

| 情况 | journal | leaf 行为 | 成本 |
|---|---|---|---|
| 同任务重放（相同输入） | **命中** | 不跑，直接返回缓存结果 | 零调用（PTC 都不跑） |
| 新变体（输入不同） | **未命中** | leaf 跑：`skill_view` 读脚本 → 适配参数 → `execute_code` 一次跑完 | 快（一次脚本执行，无 LLM 多 turn 推理） |

### 效率对比

| 方式 | journal 命中 | journal 未命中（新变体） |
|---|---|---|
| ldw leaf 裸跑（无 PTC） | 零调用 | 子 agent 从零推理（多 turn LLM + 调工具）——慢 |
| **ldw leaf + PTC** | 零调用 | 子 agent 加载脚本 + execute_code 一次——快 |
| 纯 PTC（无 ldw） | 无 journal，每次都跑脚本 | 每次都跑脚本（无 step 级缓存） |

ldw + PTC 组合：journal 命中零调用，未命中走 PTC 快速执行。比裸 ldw leaf 快（未命中时），比纯 PTC 省（命中时不跑）。

### 适用边界（PTC vs ldw leaf）

- **leaf 内部是固定工具流**（success_steps 是确定性工具调用序列，步骤间无推理）→ leaf 用 PTC 脚本快速执行（本节）。
- **leaf 内部需要 LLM 推理**（success_steps 不是固定工具流，子 agent 要自己判断）→ leaf 裸跑（无 PTC），子 agent 从零推理。
- plan 抽取时按 step 判断：success_steps 是否确定性工具流 → 是则编译 PTC 脚本 + leaf 配 PTC；否则 leaf 裸跑。

### PTC 失败降级为 ReAct

PTC 脚本是「已验证成功路径」的快速重放，但当前任务变体可能参数/环境不同导致脚本失败。leaf 执行 PTC 失败时，**降级为普通 ReAct 模式**（子 agent 从零推理，用绑定的工具逐 turn 调用）。

**降级触发条件**：
1. `execute_code` 返回错误（脚本内工具调用 raise、语法错、超时）
2. `execute_code` 成功但结果不满足 step 的成功标准（response_schema 校验失败 / outcome 与 expected 不符）
3. 子 agent LLM 判断 PTC 结果不充分（自行决定切换）

**降级流程**：
```
leaf 启动 → PTC 模式（skill_view 读脚本 → 适配 → execute_code）
             │
             ├─ 成功 → 返回结果（journal 缓存）
             │
             └─ 失败（上述 1/2/3）→ 降级 ReAct 模式
                  │  子 agent 放弃脚本，用绑定的工具从零推理（多 turn LLM + 工具调用）
                  │  system prompt 指示：「PTC 失败时，不要重试脚本，切换到 ReAct——用你的工具逐步推理解决本 step」
                  └─ ReAct 成功 → 返回结果（journal 缓存）
                     ReAct 也失败 → step 失败（dag 传播 skip 依赖者）
```

**system prompt 指示**（leaf 配 PTC 时）：
```
"本 step 有 PTC 脚本模板（skill_view scripts/ptc__<plan_key>__<step_id>.py）。优先用 PTC：
1. skill_view 读脚本 → 适配当前参数 → execute_code 一次跑完。
2. 如果 execute_code 出错、或结果不满足 step 成功标准，立即放弃脚本，
   切换到 ReAct 模式——用你绑定的工具逐步推理解决（不要重试脚本）。
3. ReAct 模式下正常多 turn 工具调用直到完成。"
```

**journal 与降级的关系**：
- PTC 成功 → journal 缓存结果（按 prompt+agent_type+model+schema）。下次同输入 → 零调用命中。
- PTC 失败 → ReAct 成功 → journal 缓存 **ReAct 的结果**（同样 key）。下次同输入 → 零调用命中（返回 ReAct 结果，PTC 都不跑）。
- 即：PTC 失败只发生一次 per 变体；后续同变体重放命中 journal，绕过 PTC + ReAct 整个流程。
- journal 不区分结果是 PTC 还是 ReACT 产的——只缓存最终成功结果。

**为什么降级到 ReAct 而非重试 PTC**：
- PTC 失败说明脚本不适用当前变体（参数/环境差异），重试同一脚本大概率再失败。
- ReAct 让子 agent 用 LLM 推理适应新情况——更鲁棒，但慢（多 turn）。
- 降级是「快速路径失败 → 兜底慢速路径」，符合 fail-open 哲学。

### 不适用 PTC 的 step

- researcher/reviewer 类 step（主要是 LLM 推理 + 判断，不是固定工具流）→ leaf 裸跑（无 PTC，直接 ReAct）。
- executor 类 step（执行固定工具序列）→ leaf 配 PTC（PTC 优先 + 失败降级 ReAct）。
- 一个 plan 里可能混用：executor step 配 PTC（含降级），researcher step 直接 ReAct。

```python
store = SqliteWorkflowStore(path="src/data/workflow_runs.db")
```

## 五补：workflow 级失败降级（ldw → TaskFlow）

### 衔接机制（ldw → TaskFlow 不是 inline，是 ldw 跑完后衔接）

ldw dag 跑到完成（失败 step 的下游被 skip），返回 partial 结果后，sherry 判定降级，再启动 TaskFlow。**不是立刻 inline 衔接**——ldw 的 dag 一旦启动会跑到完成（它不支持中途暂停切换），所以衔接点是 `run_workflow` 返回后、sherry 检查 partial 结果时。`replay_with_degradation`（下方）就是这个「ldw 完成 → 检查失败 → 决定降级 → 启动 TaskFlow」的流程。

### 成功 vs 失败的经验抽取

- **workflow 完整成功**（全 step 成功，journal 缓存）→ **跳过 plan 抽取**。plan 已在首次 TaskFlow 执行时抽取过，knowledge 已在；replay 成功不需要再抽。
- **任意 step 失败**（单 step ReAct 修补 / 多 step 降级 TaskFlow）→ **抽修补经验**（见独立计划 `计划_ldw失败修补经验抽取_20261106.md`）：PTC 为什么失败、ReAct/TaskFlow 怎么修、是否找到新成功路径 → 更新 plan knowledge + 重编译 PTC 脚本/workflow。

### 单 step ReAct 成功后，后续 step 仍用 ldw（含级联说明）

单 step 的 ReAct 是 leaf **内部**的事——ldw 只看到「该 step 成功」（leaf 返回 ReAct 结果），dag 照常继续，后续 step 各自走自己的 leaf（PTC→ReAct）。

**ReAct 级联风险**：ReAct 的输出可能 ≠ PTC 脚本预期输出 → 下游 step 的 PTC 脚本（基于原 success_steps 输入）不适用 → 下游 PTC 也失败 → 下游也降级 ReAct。
- 级联中每个 step 的 ReAct 若成功 → step 仍算成功，**不触发 L3**（不是失败）。
- 但级联让 workflow 退化为全 ReAct（慢）。
- 级联中某个 step 的 ReAct 也失败 → 那才是真失败 → 计入 L3 阈值。
- 级联的 ReAct 修补经验也要抽（见独立计划）——可能发现原 success_steps 对新变体不适用，需更新。

### ldw dag 的失败行为

ldw dag：failed node → dependents transitively skipped（`_dag.py:153`，失败节点传递性 skip 依赖者）。journal success-only（失败不缓存）。所以：

- 一个 step 失败（PTC+ReAct 都失败）→ 其下游 step 全被 skip → dag 返回 partial 结果（失败 step + 下游为 None）。
- 成功的 step → 在 journal 里。

### 三级降级链

```
L0  journal 命中 → 零调用返回（无失败）
      ↓ journal miss
L1  leaf 跑：PTC → 失败降级 ReAct → 成功（journal 缓存）/ 失败
      ↓ step 失败
L2  ldw dag 跳过下游，返回 partial。重跑 dag：
      成功 step → journal 命中零调用（不重跑）
      失败 step → 重新执行（PTC→ReAct）
      ↓ 重跑后失败 step 仍失败
L3  多步/关键步失败 → 降级 TaskFlow（放弃 ldw，用 TaskFlow 重跑 plan）
      成功 step → TaskFlow 查 journal 跳过（复用结果，不 spawn）
      失败 step → TaskFlow 正常 spawn（retry/judge/schema gate）
      TaskFlow 成功的结果 → 写回 journal
```

### 各级别处理

| 级别 | 触发 | 处理 | 已执行步骤 | 失败步骤 |
|---|---|---|---|---|
| **L1** leaf 内 | PTC 失败 | 降级 ReAct（四补节） | — | leaf 内 ReAct 兜底 |
| **L2** dag 重跑 | 单 step 失败（PTC+ReAct 都失败） | ldw dag 跳过下游返回 partial；sherry 重跑 dag（成功的 journal 零调用，失败的重新 PTC→ReAct） | **不重跑**（journal 命中零调用） | 重新执行（PTC→ReAct） |
| **L3** 降级 TaskFlow | 多 step 失败 / 根 step 失败（下游全 skip）/ L2 重跑仍失败 | 放弃 ldw workflow，用 TaskFlow 重跑 plan（retry/judge/schema gate） | **不重跑**（TaskFlow 查 journal 跳过） | TaskFlow 正常 spawn + retry/judge |

### L3 降级 TaskFlow 细节

```python
async def replay_with_degradation(plan_key, orchestrate, roster, journal_store, plan_flow_def):
    """ldw replay + 失败降级 TaskFlow。"""
    # L0-L2: ldw replay
    results = await run_workflow(orchestrate, roster=roster, journal=journal_store.journal_for(plan_key))
    failed_steps = [sid for sid, r in results.items() if r is None]  # dag skip 的失败+下游

    if not failed_steps:
        return results  # 全成功

    # 判定是否降级 L3
    root_failed = any(sid in plan_flow_def.root_steps() for sid in failed_steps)
    failure_rate = len(failed_steps) / len(results)
    if root_failed or failure_rate > 0.5 or len(failed_steps) > DEGRADE_THRESHOLD:
        # L3: 降级 TaskFlow
        return await degrade_to_taskflow(plan_flow_def, journal_store, plan_key, succeeded=results)

    # L2: 重跑 dag（成功的 journal 命中零调用，失败的重新执行）
    results2 = await run_workflow(orchestrate, roster=roster, journal=journal_store.journal_for(plan_key))
    still_failed = [sid for sid, r in results2.items() if r is None]
    if still_failed and (any(sid in plan_flow_def.root_steps() for sid in still_failed)
                         or len(still_failed) > DEGRADE_THRESHOLD):
        return await degrade_to_taskflow(plan_flow_def, journal_store, plan_key, succeeded=results2)
    return results2


async def degrade_to_taskflow(plan_flow_def, journal_store, plan_key, succeeded):
    """L3: 放弃 ldw，用 TaskFlow 重跑。成功的 step 复用 journal，失败的 step 重跑。"""
    for step in plan_flow_def.steps_in_topo_order():
        step_journal_key = compute_journal_key(step)  # prompt+agent_type+model+schema
        cached = await journal_store.get(step_journal_key)
        if cached is not None:
            continue  # 成功的 step 跳过（复用 journal 结果）
        # 失败的 step → TaskFlow 正常 spawn（retry/judge/schema gate）
        result = await taskflow_spawn_step(step)  # TaskFlow 的完整 retry/judge 流程
        if result.success:
            await journal_store.put(step_journal_key, result)  # 写回 journal
    return taskflow_collect_results(plan_flow_def)
```

### 已执行步骤是否重跑（总结）

| 场景 | 已执行（成功）步骤 | 失败步骤 |
|---|---|---|
| ldw L2 重跑 | **不重跑**（journal 命中零调用） | 重新执行（PTC→ReAct） |
| L3 降级 TaskFlow | **不重跑**（TaskFlow 查 journal 跳过，复用结果） | TaskFlow 正常 spawn（retry/judge/schema gate） |

核心原则：**成功的步骤绝不重跑**——journal 命中零调用（ldw 内）或 TaskFlow 查 journal 跳过（降级时）。只有失败的步骤才重新执行。

### 降级判定阈值

| 情况 | 判定 | 级别 |
|---|---|---|
| 根 step（无 deps，其他都依赖它）失败 | 下游全 skip，ldw 无意义 | 直接 L3 |
| 失败 step 数 / 总 step 数 > 50% | 大面积失败，plan 不适用此变体 | L3 |
| L2 重跑后失败 step 仍失败 | 该 step 确实不适用 | L3 |
| 单 step 失败 + 无下游依赖（叶子） | 不影响其他，可接受 partial | L2（接受 partial，不降级） |
| 单 step 失败 + 有下游依赖 | 重跑该 step | L2 → 重跑仍失败 → L3 |

### 为什么降级到 TaskFlow 而非 ldw 内重试

- ldw 没有原生 retry-on-fail（`race` 是 best-of-N，不是 retry-on-fail）。
- ldw 没有 judge/schema gate（leaf 跑完就结束，无通过门）。
- TaskFlow 有完整的 retry/judge/schema gate/evidence ledger——是处理 step 失败的正确工具。
- 降级 = 「ldw 快速重放失败 → 回退到 TaskFlow 完整执行」。ldw 是快速路径，TaskFlow 是兜底。

### journal 在降级中的作用

- **L2 重跑**：成功 step journal 命中零调用 → 只重跑失败 step。
- **L3 降级**：TaskFlow 查 journal → 跳过成功 step（不 spawn）→ 只重跑失败 step。
- **L3 写回**：TaskFlow 成功的 step → 结果写回 journal → 未来同变体 replay 命中（绕过整个降级）。
- journal 是降级的「成功记忆」——让降级只重跑失败部分，不浪费已成功的工作。

## 十一、风险

| 风险 | 等级 | 缓解 |
|---|---|---|
| fork ldw 维护成本（上游更新需 rebase） | 中 | vendoring fork 固定版本；只保留核心 5 模块，上游 middleware/tool 变动不影响 |
| session_id 注入适配（sherry 工具进程级单例 + ldw 隔离 context） | 中 | leaf RunnableLambda 包一层设 contextvar；或工具从 ldw Ctx 取 session。主要工程点 |
| journal key 不稳定（prompt 浮动 → 哈希不命中 → 无法 replay） | 中 | 编译时 prompt 固定（step task 文本，不浮动）；model/schema 固定（role profile）。若 prompt 被 LLM 改写则不命中——但重放用的是编译时的固定 prompt，不是 LLM 现场生成 |
| orchestrate pickle 持久化（闭包难序列化） | 中 | 持久化 orchestrate **源码字符串**（编译产物），重放时 `compile` + eval（可信代码，绕过 AST gate）；或存 step 元数据，重放时重新 compile |
| plan 改动后旧 journal 失效 | 低 | journal key 含 prompt；plan 改了 step task → key 变 → 不命中 → 重新跑首次。符合预期（plan 变了就要重新验证） |
| PTC 脚本对新变体失败 | 中 | PTC 脚本是已验证路径的重放，新变体参数/环境不同可能失败。**降级 ReAct**：execute_code 失败或结果不符 schema → leaf 切换 ReAct 从零推理（多 turn，慢但鲁棒）。降级结果同样进 journal，同变体二次 replay 命中绕过 PTC+ReAct |
| ldw dag 失败传播 vs TaskFlow 行为差异 | 中 | ldw dag 失败 → 下游 skip（partial）；TaskFlow 失败 → retry/judge。**三级降级**（五补节）：L1 leaf 内 PTC→ReAct；L2 dag 重跑（成功 step journal 零调用）；L3 多步/根步失败 → 降级 TaskFlow（成功 step 查 journal 跳过、失败 step retry/judge、结果写回 journal）。成功步骤绝不重跑 |

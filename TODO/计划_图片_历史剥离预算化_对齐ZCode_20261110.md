# 计划：历史图片剥离 — 预算化（对齐 ZCode）

- 日期：2026-11-10
- 状态：**待评审**
- 来源：对齐 ZCode — ZCode 使用 75MB media 预算，采用从新到旧贪心保留并保护最新 user message，替代 Sherry 当前无条件剥离所有历史轮次的方案
- 风险等级：**中** — 改变哪些图片能在 context 中留存；影响 summarization 时机与 model context 质量
- 依赖：无（与压缩/artifact 计划相互独立，但能从中受益）

---

## 0. ZCode 行为（已验证）

ZCode 的历史图片剥离是应用在每次 model 调用之前的两层投影，封装在 `projectMessagesForModelMediaPolicy`（`JI`，偏移 10754846）中：

### Layer 1：能力投影（`DFr`，偏移 ~10752600）

按 block 进行，基于声明式的 `supportsImages`/`supportsPdf`/`supportsVideo`：
- 若 model 支持所有 media 类型 → 原样透传
- 否则：对每个 block，检查 model 是否支持其类型；不支持则替换为文本占位符：
  ```
  [Attached media: <filename/caption>]
  [Media omitted from provider request because the selected model does not support image input.]
  ```
- 这是按能力全有或全无 — 不会优先保留较新的图片

### Layer 2：Media 预算投影（`Oui`，偏移 10755034）

这才是真正"从较早轮次剥离、保留较新"的机制：

| 常量 | 值 | 含义 |
|---|---|---|
| `Mui` | 75 MB（75 × 1024 × 1024） | 默认 media 字节预算 |
| `maxVideoMediaBytes` | 30 MB | 独立的视频预算 |
| `preserveLatestUserMedia` | `true`（默认） | 最新 user message 的 media 受保护 — 始终保留 |

算法：
1. 收集所有 message 中的 media block，打上 `{messageIndex, bytes, bucket: "media"|"video", protected}` 标记
2. 若某 block 的 `messageIndex === latestRealUserMessageIndex`，则其为 `protected`
3. 对每个桶（"media"、"video"）：
   - 先从预算中扣除 protected block 的字节数
   - 再将非 protected 的 block 按 `messageIndex` **降序**（从新到旧）贪心加入
   - 剩余预算放不下的 block → 替换为文本占位符：
     ```
     [Attached media: <filename/caption>]
     [Media omitted from provider request to keep the request body under the configured media budget.]
     ```
4. CUA（computer-use）配对的栅格图-文本块：若栅格图被丢弃，配对的坐标文本会被清空并替换为 `"This CUA raster is not visible in this request. Do not send a coordinate target; capture a new raster first."`

**关键洞察：** ZCode 并不会剥离所有先前轮次的图片。它在 75MB 预算内尽可能多地保留，从新到旧，最新 user message 始终受保护。一个包含 3 张小图的会话会保留全部 3 张；一个只有一张 50MB 截图的会话则只保留最新那张。

## 1. Sherry 当前状态 — 剥离已存在（无条件），offload 已有预算模板

### 1.1 `_strip_history_images` — 现有的无条件剥离器

**`agent/middlewares/media_pipeline/core.py:193-216`** — 剥离除最后一条之外所有 message 的 `image_url` block，替换为拼接文本。无预算、无"保留最新"逻辑。本计划要替换的就是它。

### 1.2 `offload_inline_media` — 现有的"保留最新、offload 较旧"模板

**`agent/middlewares/summarization/media_offload.py:52-97`** — 在 summarization 期间，该函数：
1. 在待压缩的 message 范围内查找内联 `data:` media block
2. **保留较新的尾部窗口**（未压缩的 message）
3. 通过 `_store_media`（SHA256 内容寻址）将较旧的 block offload 到磁盘
4. 替换为 `[evicted to: <path>]` 文本指针

这是基于预算剥离的**架构模板** — 它已经实现了"保留最新、offload 较旧"。本计划将该模式适配为每轮运行（而非仅 summarization 期间），以字节预算替代 summary 边界触发。

### 1.3 `_extract_inline_media` — 字节计量辅助

**`media_offload.py:100-150`** — `_extract_inline_media`、`_decode_data_url`、`_decode_base64` 从 `data:` URL / base64 block 中提取字节。可在预算投影中复用，用于计算每个 block 的字节大小。

### 1.4 `scrub_messages` — 能力层（不变）

**`agent/middlewares/media_pipeline/scrub.py:27-83`** — 执行按能力的剥离（将不支持族别的 block 替换为文本占位符）。它在预算投影之前运行，本计划不改动它。

## 2. 设计

### 2.1 用基于预算的投影替换 `_strip_history_images`

`agent/middlewares/media_pipeline/core.py` 中的新函数：

```python
def _project_history_media_budget(
    self,
    messages: list,
    *,
    max_media_bytes: int = 75 * 1024 * 1024,  # aligns with ZCode Mui
    preserve_latest_user_media: bool = True,
) -> list:
    """Budget-based history media projection (aligns with ZCode Oui).

    Keeps as many images as fit the byte budget, newest-first.
    The latest user message's media is always protected.
    Older images that don't fit are replaced with text placeholders.
    """
```

算法（镜像 ZCode 的 `Oui`）：
1. 找到最新真实 user message 的 index
2. 收集所有 message 中的 `image_url` block，附带 `{message_index, bytes, protected}`
3. `protected` = 最新 user message 中的 block
4. 从预算中扣除 protected 字节数
5. 将非 protected 的按 `message_index` 降序排序（从新到旧）
6. 贪心保留，直到预算耗尽
7. 被丢弃的 block → 文本占位符：`[Media omitted to keep request under media budget (<n> bytes)]`

### 2.2 Block 字节估算

对于 `data:` URL block，字节数为解码后的 base64 长度：
```python
def _estimate_block_bytes(block: dict) -> int:
    if block.get("type") == "image_url":
        url = block["image_url"]["url"]
        if url.startswith("data:"):
            # data:<mime>;base64,<payload> → decode payload length
            payload = url.split(",", 1)[-1]
            return len(base64.b64decode(payload))
        return 0  # remote URL — provider fetches, don't count
    return 0
```

### 2.3 占位符文本

被丢弃的 block（对齐 ZCode 的 `Bui`）：
```
[Attached image: <filename or caption if available>]
[Media omitted from provider request to keep the request body under the configured media budget.]
```

被能力层剥离的 block（对齐 ZCode 的 `aK`，已由 `scrub.py` 处理）：
```
[Media omitted from provider request because the selected model does not support image input.]
```

### 2.4 两层应用顺序

镜像 ZCode 的 `JI`：
1. **能力投影**在前（现有 `scrub_messages` 在 `scrub.py` 中 — 已按能力）
2. **预算投影**在后（新增 `_project_history_media_budget` — 替换 `_strip_history_images`）

这意味着：不支持图片的 model 会丢失所有图片（能力层）；支持图片的 model 则在预算内尽可能多地保留（预算层）。

### 2.6 与现有机制的交互

| 机制 | 关系 |
|---|---|
| `scrub.py::_scrub_request` | 先运行（能力层）。预算投影在已清洗后的 message 上运行。 |
| `media_offload.py::offload_inline_media` | 在 summarization 期间运行（独立触发）。预算投影每轮在 model 调用前运行。二者互补：预算投影控制每轮 model 能看到什么；media_offload 控制哪些能留存进压缩后的 context。 |
| `ContextLimitGuard` | 使用 provider 上报的 token（不变）。预算投影是本地启发式，在 provider 看到之前减小 media 占用。 |

## 5. 备注

- 这是一个**行为改进**，不只是对齐：Sherry 当前的"剥离所有历史"过于激进。预算方案在多轮图片会话中能保留更多视觉上下文。
- 75MB 默认值对齐 ZCode 的 `Mui`。由于 Sherry 会将图片压缩到 ≤200KB base64（压缩级联计划），75MB 约可容纳 ~375 张压缩图片 — 对正常会话而言几乎是无限的。预算只在未压缩的边缘场景或压缩被禁用时有意义。
- 能力层（`scrub.py`）不变 — 它已按能力做剥离。本计划仅将不感知预算的 `_strip_history_images` 替换为感知预算的投影。

# 计划：会议模式——讨论得出完整计划，衔接专家团执行

- 日期：2026-11-17
- 状态：**待评审**
- 定位：Sherry 第三种产品模式。多专家讨论同一个问题 → 达成共识 → 产出完整 TaskFlow 计划 → 衔接专家团执行。补齐 Madorin 会议模式全部功能。
- 风险等级：**高** — 新产品模式 + 新协作范式（讨论 vs 现有派工）
- 依赖：专家团模式计划（执行阶段复用）+ 现有 TaskFlow / subagent / HITL / summarization / WebSocket
- 参考：Madorin `Src/Netor.Cortana.AI/MeetingMode/` + `Docs/会议模式/`

---

## 0. 两种模式的关系

```
会议模式（本计划）：       专家团模式（已有计划）：
讨论 → 共识 → 产出计划  →  拿计划 → 创建 TaskFlow DAG → 派工 → 专家执行 → 收口
↑ 讨论阶段                   ↑ 执行阶段
```

会议模式的输出 = TaskFlow 计划（steps + depends_on + 每步绑定的专家）。专家团模式拿这个计划执行。两个模式可独立使用，也可串联（先讨论后执行）。

## 2. 架构设计

### 2.1 三角色

```
用户（"老板"）
  ↓
Meeting Host（主持人）
  ├── 工具：agent_list, ask_agent, memory_search, current_time, output_summary, confirm_meeting_end
  ├── 不干活：工具剥离（file/terminal/browser/code-intel 全禁）
  └── 职责：开场 → 派发讨论 → 收集 → 总结 → 确认结束
       ↓
Meeting Selector（调度器，内部 agent）
  ├── 无工具
  ├── 职责：每轮输出 MeetingTurnDecision JSON
  └── 输出：{ phase, nextSpeakerId, reason, executionPlan }
       ↓
Participants（参会者 = 专家注册库里的专家）
  ├── 各自带完整底座工具（file/terminal/code-intel/TaskFlow...）
  ├── 看到所有之前的发言（共享讨论历史）
  └── 职责：按 selector 指派发言，给出领域意见
```

### 2.2 会议流程

```
1. 用户创建会议（选参会专家 + 定主题）
2. 主持人开场（确认主题清晰，或 ask_user 澄清）
3. Selector 生成执行计划（分阶段，每阶段哪些专家发言，前置依赖）
4. 按计划顺序派发讨论：
   selector: "前端专家先发言" → 前端专家发言（所有人看到）
   selector: "后端专家发言" → 后端专家发言（看到前端发言，在此基础上回应）
   selector: "DBA 发言" → DBA 发言（看到前两个，在此基础上回应）
5. 用户可随时插话：
   用户："后端改用微服务"
   → 主持人分类：scope_change
   → 局部回滚受影响阶段
   → 重新生成执行计划
   → 继续讨论
6. 主持人总结（output_summary）
7. 用户确认结束（confirm_meeting_end）
8. 会议结论 → 产出 TaskFlow 计划（steps + depends_on + 每步绑定专家）
9. （可选）衔接专家团执行：拿计划 → TaskFlow dispatch → 专家各自干活
```

### 2.3 MeetingTurnDecision（selector 输出）

```python
class MeetingTurnDecision(BaseModel):
    phase: str                    # 当前阶段
    next_speaker_id: str          # 下一个发言者
    reason: str                   # 为什么选这个专家
    execution_plan: list[MeetingPhase]
    interrupt_type: str | None    # 用户插话分类（如果有）
    affected_phase_ids: list[str] # 受影响的阶段（插话回滚）

class MeetingPhase(BaseModel):
    id: str
    allowed_agent_ids: list[str]  # 这个阶段允许发言的专家
    prerequisites: list[str]      # 前置阶段 id
    completion_criteria: str      # 完成条件
```

### 2.4 流程阶段状态机

```python
class MeetingFlowStage(StrEnum):
    REQUIREMENT_CONFIRMATION = "requirement_confirmation"  # 确认需求/开场
    DISPATCHING = "dispatching"                            # 派发讨论
    USER_INTERRUPT = "user_interrupt"                      # 用户插话处理
    RECOVERY = "recovery"                                  # 参会者无效发言恢复
    END_CONFIRMATION = "end_confirmation"                  # 结束确认
```

非 Dispatching 阶段 → 主持人直接发言（bypass selector）。Dispatching 阶段 → selector 决定谁发言。

### 2.5 用户插话 6 类

```python
class InterruptType(StrEnum):
    SUPPLEMENT = "supplement"          # 补充信息
    CORRECTION = "correction"          # 纠正错误
    SCOPE_CHANGE = "scope_change"      # 范围变更
    PRIORITY_CHANGE = "priority_change" # 优先级变更
    END_REQUEST = "end_request"        # 要求结束
    IRRELEVANT = "irrelevant"          # 无关内容（忽略）
```

处理：主持人分类 → 标记受影响阶段 → 局部回滚（受影响阶段标记为需重新讨论）→ 重新生成执行计划 → 继续讨论。

## 5. 讨论转执行（衔接专家团）

### 5.1 会议结论 → TaskFlow 计划

会议结束时（confirm_meeting_end），主持人产出结构化结论：

```python
class MeetingConclusion(BaseModel):
    summary: str                           # 讨论总结
    taskflow_plan: TaskFlowPlanFromMeeting # 转化为 TaskFlow 计划

class TaskFlowPlanFromMeeting(BaseModel):
    description: str                       # flow 描述
    steps: list[MeetingStepSpec]

class MeetingStepSpec(BaseModel):
    task: str                              # 步骤任务
    expert: str                            # 绑定的专家名（从注册库）
    depends_on: list[str]                  # 依赖的其他步骤
    reusable: bool                         # 是否可复用（PTC/LDW 编译判定）
```

### 5.2 转执行流程

```python
# 会议结束后，用户可选"立即执行"或"保存计划"
if user_chooses_execute:
    # 从会议结论创建 TaskFlow flow
    flow = taskflow_create_flow(description=conclusion.taskflow_plan.description)
    for step in conclusion.taskflow_plan.steps:
        taskflow_create_step(
            flow_id=flow.id,
            task=step.task,
            depends_on=step.depends_on,
            expert_config=expert_registry.load(step.expert),  # 从注册库加载专家配置
            reusable=step.reusable
        )
    # 衔接专家团执行
    taskflow_dispatch(flow.id)  # 自动派发 → 专家各自执行 → wait_all → resume → finish
```

## 9. 会议主持人 prompt

```
你是会议主持人。你的职责：
1. 听清：确认用户需求清晰，不清楚时 ask_user 澄清
2. 派发：根据执行计划，指示参会专家发言
3. 收口：每位专家发言后，简要记录要点
4. 总结：讨论结束时 output_summary
5. 确认：confirm_meeting_end 让用户确认结束

规则：
- 你不能代替参会者发言——你只组织，不执行
- 发言顺序按业务依赖（前端先于后端，后端先于DB），不轮流
- 用户插话时，判断类型并调整执行计划
- 你不能写文件、跑代码、浏览网页——你只有协调工具
- 最多 40 轮，接近上限时主动总结
```

## 10. Selector prompt

```
你是会议调度器。根据讨论历史和执行计划，决定下一个谁发言。

输出 JSON：
{
  "phase": "Dispatching",

  "reason": "前端架构是后端的前置依赖，应先讨论",
  "executionPlan": {
    "phases": [
      {"id": "p1", "allowedAgentIds": ["frontend-expert"], "prerequisites": [], "completionCriteria": "前端方案确定"},
      {"id": "p2", "allowedAgentIds": ["backend-expert"], "prerequisites": ["p1"], "completionCriteria": "后端方案确定"},
      {"id": "p3", "allowedAgentIds": ["dba-expert"], "prerequisites": ["p2"], "completionCriteria": "数据库方案确定"}

  }

规则：
- 发言顺序必须按业务前置依赖，不是轮流或随机
- 如果问题已解决，返回 nextSpeakerId=null + reason="讨论已完成"
- 主持人不在可选发言者列表中
```

## 12. 与现有系统的关系

| 现有系统 | 会议模式如何复用 |
|---------|----------------|
| TaskFlow | 会议结论产出 TaskFlow 计划 → 衔接专家团执行 |
| Subagent | 参会者用 subagent spawn（ORCHESTRATOR 深度，有完整工具） |
| HITL | ask_user 复用 question 工具 + HITL 审批 |
| Summarization | 讨论历史压缩复用 summarization 中间件 |

### 13.1 持久参会者 session 模型（阶段 1 前置）

**问题**：现有子 agent 是 one-task-one-run（`lifecycle.py:873-876` finally → `release_child_resources → finalize_child_run`）。terminal 后 checkpoint 被清理，不可再调。`ExecutionStatus` 无 PAUSED/idle 状态。`send_subagent_message`（`control/send.py:34-38`）只接受 `RUNNING` 或 `INTERRUPTED`。

**方案**：不 spawn 子 agent，而是让参会者是**主 agent session 的特殊 turn**：

```
会议主持人 = 主 agent session（带主持人 persona）
参会者发言 = 主 agent session 的一个特殊 turn：
  1. 写参会者 persona 到 StateKey.SYSTEM_PROMPT（直接写 mem + db register）
  2. 注入讨论历史作为 context
  3. 跑一个 model call（参会者发言）
  4. 写回主持人 persona 到 StateKey.SYSTEM_PROMPT
  5. 发言追加到会议消息表
```

**代码依据**：
- `StateKey.SYSTEM_PROMPT` 可以直接写入 mem + db register 覆盖缓存（`thinking_control/core.py:400-402` 已证明这个模式——它 delete 两个 register 触发 rebuild；我们改为**直接写**参会者 persona 到 register）
- `system_prompt_injection` 中间件（`system_prompt/core.py:60-61`）在每次 model call 时读 `StateKey.SYSTEM_PROMPT`——如果 register 里有值就用缓存值，不调 `build_system_prompt`
- 参会者的 model call 走主 agent 的 model（不需要单独的 agent 实例）

**注意**：
- 参会者发言时需要临时切换可用工具集（参会者可能有不同的 skill 白名单）——通过 `DynamicReminderMiddleware` 的 prompt 动态切换机制参考，或直接在 turn 级别设工具过滤
- 参会者发言后**必须恢复主持人 persona**到 `StateKey.SYSTEM_PROMPT`——否则下一轮主持人发言用的是参会者 persona

**替代方案**（如果 turn 切换不够）：用 `submit_user_input` 驱动独立 session 作为参会者。side chat 是持久多消息 session（`side_chat_service.py:249-305`），但**不能通过 `sessions_send` 发消息**（`sessions_send` 只查 subagent run，`sessions_send.py:47`）。需要用 `submit_user_input` 通过 WS turn 驱动。

### 13.2 Selector structured output 实现

**代码依据**：
- `build_auxiliary_llm(temperature=0, thinking=False)` 返回 `NormalizingChatModel`（`auxiliary_llm/core.py:154-159`）
- `NormalizingChatModel.with_structured_output(schema)` 转发到 inner provider（`reasoning_normalizer.py:285-293`）
- 现有先例：`summary_generation.py:683` 用 `self._model.with_structured_output(SummaryDoc, method=_STRUCTURED_OUTPUT_METHOD)`
- **本地 GGUF 分支**的 `with_structured_output` 是 sync-only（`local_adapters.py:184-229`）——如果 `AUXILIARY_LLM_MODEL_LOCAL=true` 可能不支持 async。SaaS 默认用远程 provider，无此问题

**实现**：
```python
from pydantic import BaseModel

class MeetingTurnDecision(BaseModel):
    phase: str
    next_speaker_id: str | None
    reason: str
    execution_plan: list[MeetingPhase]
    interrupt_type: str | None = None
    affected_phase_ids: list[str] = []

async def selector_decide(discussion_history: list[dict], participants: list[dict]) -> MeetingTurnDecision:
    llm = build_auxiliary_llm(temperature=0, thinking=False)
    structured = llm.with_structured_output(MeetingTurnDecision)
    messages = [
        {"role": "system", "content": SELECTOR_PROMPT},
        {"role": "user", "content": json.dumps({"discussion": discussion_history, "participants": participants})},
    ]
    return await structured.ainvoke(messages)
```

**代码依据**：

- **只在 LangGraph turn 内有效**——如果会议驱动走 WS turn executor（`submit_user_input`），question 工具可用

### 13.7 轮次上限（40 轮）

**代码依据**：
- `IterationBudget`（`iteration_budget/core.py:128-132`）是 **per-turn**（`_before_agent_impl` 每 turn 重置 counter）
- **不支持 per-meeting 跨 turn 的 40 轮上限**

## 15. Kill criteria

- **持久参会者模型**：如果"主 agent session 直接写 `StateKey.SYSTEM_PROMPT` 切换 persona"在验证中出现问题（工具切换不干净 / checkpoint 污染 / memory 混淆 / persona 恢复失败），降级为"每次发言 spawn 独立子 agent + 注入完整讨论历史"（无持久 session，token 开销大但可行）
- **selector structured output**：如果 `build_auxiliary_llm(temperature=0, thinking=False).with_structured_output(MeetingTurnDecision)` 在实际使用中准确率不足（选错人/无法理解业务依赖），降级为 step_judge 的模式（free text + `json_repair` 解析）
- **本地 GGUF selector**：如果 `AUXILIARY_LLM_MODEL_LOCAL=true` 且 `with_structured_output` 的 sync-only 路径不支持 async `ainvoke`，降级为 free text + `json_repair`（step_judge 模式）
- **用户插话 6 类分类**：如果误判率高，降化为"全部当作 supplement 处理"（不回滚阶段，只追加讨论）
- **会议结论 → TaskFlow 转化**：如果 LLM 输出质量不稳定（steps/depends_on 不合理），降化为"主持人手动写计划"（会议只产出讨论总结，不自动转计划）
- **会议 UI**：如果开发成本过高，先做 CLI 版本（通过 API + 终端交互），UI 后置
- **summarization 复用**：如果 summarization 的 task-intent seam 在会议上下文中干扰（注入不该有的 plan/todo reminder），改为独立的会议压缩逻辑（不复用 summarization 中间件）
- **40 轮上限**：`IterationBudget` 是 per-turn 不支持 per-meeting——必须建独立的 `MEETING_ROUND_COUNT` 持久计数器。如果计数器在重启后丢失导致超轮，接受（重启后自动 adjourn 会议）

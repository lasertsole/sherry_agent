# 计划：工具面上下文瘦身（三档方案：瘦身 / 合族派发 / 按组关停）

- 建档日期：2026-10-08
- 状态：**计划（未开工）**；三档互相独立，推荐顺序 **1 →（评估）2**；3 是今天就能用的兜底
- 触发问题：主工具表常驻 schema（含浏览器功能时）44 个工具 ≈ **16,992 tok**，其中
  「任务与计划 + 子代理」两族占 10,642（63%）。能否用"伞装技能"替换这两族以省上下文？
- 结论先行：
  1. **技能替换不了能力**——这两族的能力全是进程内状态（SQLite store + runtime 寄存器）、
     每次变更推 WS、会话身份（`InjectedState`）与中间件按工具名挂钩；脚本子进程够不着
     （同 `计划_内部浏览器agent控制（CDP代理）.md` 3.3 的排除论证）。**真正的杠杆是常驻
     schema 的大小**，不是"工具还是技能"。
  2. 实测：**任务与计划一族 9,351 tok（占全工具预算 55%）是唯一大块**；子代理族只有
     1,291，合并上限 <1k，**不动**。
  3. 精度上，族内又极度集中：最贵的 5 个工具占全族 62%（见 0.2）。

### 0.3 复测脚本（验收与后续对比都用它）

```python
import json
from agent.tools import build_main_tools
from agent.tools.catalog import _group_of
from pub.func.estimate_tokens import estimate_text_tokens

def schema_text(t):
    return json.dumps({"name": t.name, "description": t.description or "",
                       "parameters": t.args_schema.model_json_schema()}, ensure_ascii=False)

per_group = {}
for t in build_main_tools():
    per_group.setdefault(_group_of(t.name), []).append(t)
for g, ts in sorted(per_group.items(), key=lambda kv: -sum(estimate_text_tokens(schema_text(t)) for t in kv[1])):
    print(g, len(ts), sum(estimate_text_tokens(schema_text(t)) for t in ts))
```

## 1. 方案一：瘦身（描述压缩 + 长文进既有 SKILL.md）——推荐先做

### 1.1 原理

常驻的只有工具 name + description + 参数 schema；**技能正文按需加载**
（`skill_view`），技能只在索引里留一行（~30 tok）。把"深度语义"从
description/Field 描述搬进 `taskflow` / `todolist` 两个**已存在**的 SKILL.md，
就是标准的 progressive disclosure：不用编排的会话（大多数）白赚，用编排的会话
付一次加载。注意两个 SKILL.md 已覆盖大量重叠内容（todolist skill 里就有
todowrite 的完整字段表）——这次主要是**去重**，不是新写。

### 1.2 逐工具目标

| 工具 | 现状 tok | 目标 | 长文搬去哪 |
|---|---|---|---|
| taskflow_run_task | 1,772 | ≤650 | taskflow SKILL.md「run_task 字段语义」 |
| taskflow_resume | 1,566 | ≤600 | 同上（含 judge/retry 交互说明） |
| knowledge | 890 | ≤350 | taskflow SKILL.md「知识库」小节 |
| todowrite | 877 | ≤450 | todolist SKILL.md（已有字段表，去重） |
| taskflow_update_steps | 670 | ≤350 | taskflow SKILL.md |
| 其余 12 个 | ≤2,5xx | 只删冗余句，不动结构 | — |

写法约束：

- tool description = 一行摘要 + 常用路径必需信息；结尾一句
  `full semantics: skill_view('taskflow')`（只在实际用到的会话付那一次加载）。
- Field 描述 ≤ ~60 字符/字段；字段的语义表、示例、budget/deadline/schema/judge 的
  相互作用全部进 SKILL.md。
- **catalog 的 hover 提示取 description 第一行**（240 字符上限），第一行必须自足。

### 1.3 验收

- 复测脚本：任务与计划 ≤ **5,500**，总表 ≤ **13,000**（预期 −3.9k ≈ 工具预算的 −23%）。
- 不触碰工具名/metadata/调用方：**零测试改动**（已核实 19 个 taskflow 测试文件只
  断言行为与"描述非空"，不钉文本）。
- 行为抽查：一个多步会话（create → run_task → resume → finish）在只加载
  `skill_view('taskflow')` 的前提下完整跑通；split runner 全绿。

### 1.4 风险

- 模型在**没加载技能**时直接调用：description 变薄 → 字段用错。缓解：常用路径的
  description 保持自足，深度语义才外移；表格里给每个工具定义了"目标 tok"下限，
  不允许无脑截断。
- 描述与 SKILL.md 双处漂移：在 SKILL.md 顶部钉一句"以工具 schema 为准"，并留给
  后续一致性脚本（可选，不阻塞）。

## 2. 方案二：合族派发（14→1 + skill 收编）——收益最大、代价也最大

### 2.1 形态（推荐口径）

- **只合并 14 个 taskflow_***：一个 `taskflow(action=…, **params)` 派发工具；
  `todowrite` / `todoread` / `knowledge` **保留独立**（合计 1,854 tok，被中间件提示
  文本与 nudge 的 metadata 门深度嵌入，合并收益小而风险大）。
- 派发工具的 description 只留"动作清单 + 一句话调用法"，每个动作的字段语义进
  taskflow SKILL.md。常驻目标：**族内 9,351 → ≤2,000**（dispatcher ~1,000 + 保留三件 ~1,000）。
- 完整 17→1 的上限是 ~1,200，但需要动 `todowrite` 的 `todo_update` 标记（nudge
  白名单）——列为备选，不推荐。

### 2.2 per-action metadata 配套（新机制，必做）

现在每个 taskflow 工具都打 `idempotent`（只读=True、变更=False），ToolGuardrails
靠它做"重复无进展"判定。派发器只有一个 metadata，必须新增按动作查询的约定：

```python
tool.metadata = {
    "scope": "main_only",
    "action_metadata": {"read": {"idempotent": True}, "list": {"idempotent": True},
                        "create": {"idempotent": False}, "resume": {"idempotent": False}, …},
}
```

消费方改造：`agent/middlewares/tool_guardrails/core.py::_is_idempotent`（从调用参数取
action 再查表）；`pub/func/message/tool_output_prune.py` 的按工具裁剪表改按动作；
证据账本不受影响（只自动记录 terminal/python_repl）。

### 2.3 爆炸半径（已核实的清单）

- **按名挂钩的中间件/文本**：`todo_continuation/core.py`（提示文本点名
  todoread/todowrite/taskflow_finish/run_task/resume/wait_all）、
  `summarization/nudges.py`（`todo_update` 标记 + 提示文本）、StepJudge 与
  finish 的 A–D 门（都在工具实现内部，机械改写）、`progress_push`（每次变更推 WS）。
- **名字引用面**：63 个 py 文件（含 taskflow 自身 14 个 tool 文件 = schema 本体）、
  **19 个测试文件**、`agent/tools/catalog.py`（TOOL_GROUPS / BULK_ONLY）、客户端预设
  派生测试（catalog 驱动的工具列表）、`evals/long_running_task/suite.py`、
  PTC 的 `available_tools` 白名单取交。
- 交互口径：聊天里的工具卡片从 `taskflow_resume` 变成 `taskflow(action=resume)`；
  HITL / 目录 / 预设「工具」页签的粒度随之变化（BULK_ONLY 语义不变）。

### 2.4 验收

- 常驻 ≤2,000；**逐项回归**：resume 上的 StepJudge、finish 的 A–D 门、WS 进度推送、
  todo 续跑提示、guardrails 的只读/变更判定（`action_metadata` 生效）、nudge 不受影响、
  证据与完成排水；split runner 全绿 + 一次真实多步 llm_e2e。
- 派发器参数字典要写成 `additionalProperties: false` + 显式列举，尽量保住
  provider 侧校验；运行时对未知 action/多余字段给结构化报错。

### 2.5 何时才做

方案一落地并实测后，若"任务与计划"仍嫌大（比如 ≤5.5k 仍占预算三分之一以上），
再评估本方案。它是一次跨 60+ 文件的重构，**必须单独开分支/单独计划**。

## 3. 方案三：保持工具，按会话关组（零代码，今天可用）

- 两族已是 `BULK_ONLY_GROUPS`（`agent/tools/catalog.py`）：预设「工具」页签里整体
  开关，`PUT /sessions/agent_config` 落到会话，`ToolSelectionMiddleware` 按会话裁剪
  （执行层同样拒绝）。
- 既有先例：**情感陪伴**预设已把 任务与计划 / 子代理 两组全关 ≈ 常驻 −10.6k。
- 使用口径：不用编排的会话在「工具」页签关掉两组即可；这是所有方案的兜底，
  也是方案一/二 落地前的即时手段。
- 可选政策问题（不在本计划内）：编程助手默认包含两族（"除 memory 外全量"），
  是否收紧由用户决定——改一行 `COMPANION_DISABLED_TOOL_GROUPS` 类的派生规则即可，
  但会影响已绑预设的 EXACT 语义，需要一次专门的评估。

## 4. 子代理族（7 个，1,291 tok）不动的结论

- 合并上限 <1k（最大单工具 `sessions_spawn` 326），收益低于重构风险；
  `sessions_spawn/steer` 与 spawn 机制、lane、announce 深度耦合。
- 结论：**保持现状**；若某会话不用委派，用方案三关组。

---

## 5. 推荐顺序与决策点

1. **先做方案一**（零结构风险，−3.9k）：只改 5 个工具的 description/Field 描述 +
   两个既有 SKILL.md 的去重扩写；验收 = 复测脚本数字 + 一次多步会话冒烟。
2. 方案一之后复测；**方案二只在数字仍不可接受时启动**（需要用户拍板其爆炸半径）。
3. 方案三作为即时兜底与默认政策讨论项。
4. 子代理族不动。

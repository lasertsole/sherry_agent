# 计划：强化编码能力 — 浏览器调试捕获 + 自动诊断门控

- 日期：2026-11-11（修订版 r2）
- 状态：**待评审**
- 来源：核查 Sherry 编码底座后确认的缺口；r2 修订回应 LSP 多语言机制对比同类工具后的三个发现（诊断过期、被动注入、崩溃重试）
- 风险等级：**中** —— 自动诊断门控前置依赖编辑同步（不修则诊断过期）；被动注入改动中间件上下文；浏览器捕获是新增 CDP 域

---

## 0. 背景

核查 Sherry 编码底座后确认其已相当完整：LSP（8 工具，11 种 server）、code-intel 三层（tree-sitter + ast-grep + Jina 语义）、git worktree 隔离、evidence ledger + regression gate。比同类编码 agent 工具链更深。

确认缺口 + r2 修订发现的硬伤：

| 项 | 现状 | 来源 |
|---|---|---|
| 浏览器 console/network 捕获 | 只启用 `Page.enable`，无被动捕获 | 同类工具浏览器可读 console+network |
| **LSP 诊断编辑后过期（硬伤）** | `lsp_diagnostics` 仅 `didOpen`，已打开则跳过；编辑后 server 视图是旧内容 | 同类工具：编辑工具自动发 didChange/didSave |
| 自动诊断门控 | regression gate 回放 agent 录入命令，不自动跑类型检查 | Claude Code 自动错误反馈循环 |
| LSP 崩溃恢复 | 检测死则 kill 清除，下次 acquire 重建；无 ContentModified 重试 | 同类工具：崩溃自动重启 max 3 + ContentModified 退避重试 |
| LSP hover | 8 工具里无 `textDocument/hover` | 工具集补全 |

**r2 关键变化**：自动诊断门控从"两步"重构为**三步递进**（编辑同步 → 被动注入 → evidence gate），并新增 LSP 鲁棒性补强。编辑同步升为**前置必做项**——不修则后两步都是过期数据。

**不在此计划**：Claude Code 工具数量对齐、Artifacts & Design、Computer Use、PTY 终端（已在借鉴特性计划）。

## 1. 浏览器 console + network 捕获

### 1.1 现状（已代码核实）

`server/service/browser_manager.py`：CDP 会话只调 `Page.enable`（行 350、970），**无** `Runtime.enable`/`Network.enable`/`Log.enable`，**无** `consoleAPICalled`/`exceptionThrown`/`responseReceived` 监听。存在原始 CDP 事件分发（`subscribe_events`/`event_sinks`，行 411-464）但无 agent 工具消费、也没启用产生事件的域。

`agent/tools/browser/tools/`：8 个工具全是主动操作，无被动捕获。

### 1.2 目标

补齐前端调试闭环："改前端代码 → reload → 读 console 报错 + JS 异常 + 失败 network → 定位"。

### 1.3 目标架构

```
CDP 会话（browser_manager）
  ├─ Page.enable（现有）
  ├─ Runtime.enable（新增）→ consoleAPICalled / exceptionThrown
  ├─ Network.enable（新增）→ responseReceived / loadingFailed
  └─ Log.enable（新增）→ entryAdded

事件缓存（per-page 环形缓冲，navigation 清空）
  ├─ console 日志（level + 文本）
  ├─ JS 异常（details + stack）
  └─ network 请求（url / status / 失败原因）

agent 工具（新增）
  ├─ browser_console（读 console + 异常，按 level 过滤）
  └─ browser_network（读请求，按状态/失败过滤）
```

### 1.4 实施步骤

1. `browser_manager.py`：CDP 会话建立追加 `Runtime.enable`/`Network.enable`/`Log.enable`（受 `BROWSER_DEBUG_CAPTURE` 开关控制，默认开）；复用 `event_sinks` 订阅事件；per-page 环形缓冲（上限 200），`Page.frameNavigated` 清空
2. `agent/tools/browser/tools/`：新增 `browser_console`、`browser_network`，合并进 `browser_merged.py`；返回结构化文本
3. `browser_navigate` 后清空缓冲

### 1.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| Network 事件量大 | 环形缓冲 + 默认只留 status≥400/failed |
| 多 tab 事件串扰 | per-page 缓冲按 target id 隔离 |
| 隐私（header/cookie） | 默认只记 url+status+失败原因，body 按 opt-in |
| 反调试站点 | 按站点 opt-out；无法隔离则默认关 `BROWSER_DEBUG_CAPTURE` |

### 1.6 Kill criteria

- 若 CDP 域启用在某些站点导致页面异常且无法按站点隔离，默认关闭捕获，工具返回"未启用"

### 1.7 验收

- 改前端代码 → reload → `browser_console` 读到 JS 报错 + stack
- `browser_network` 读到失败请求
- navigate 后缓冲清空
- 现有 8 个浏览器工具行为不变

## 2. 自动诊断门控（三步递进 + 鲁棒性）

### 2.1 前置发现：LSP 诊断编辑后过期（硬伤，必须先修）

**问题**：`lsp_diagnostics` 调 `_open(client, resolved)` 做 `didOpen`，但 `LSPClient.open_file`（`client.py:236-238`）"已打开则跳过"。agent 编辑文件后，server 里存的还是编辑前内容——**再调 `lsp_diagnostics` 拿到的是过期诊断**。

参考做法：编辑工具（FileEdit/FileWrite）写盘后自动发 `didChange` + `didSave`，server 视图始终同步，诊断永远基于最新内容。

**不修此问题，后面的被动注入和 evidence gate 都是过期数据。** 因此编辑同步是前置必做项。

### 2.2 步骤 A：编辑同步（前置必做）

让 `patch_file`/`write_file`/`ast_grep_rewrite` 等编辑工具在写盘后，向对应 LSP server 发 `textDocument/didChange` + `didSave`（或对未 open 的文件发 `didOpen`）。

**实施**：
1. `LSPClient`（`client.py`）新增 `notify_change(path, new_content)` / `notify_save(path)` 方法，发 `didChange`（full content sync）+ `didSave`
2. 编辑工具（`patch_file`/`write_file`/`ast_grep_rewrite` 等）写盘成功后，检测该文件语言是否有对应 LSP server 已 acquire（查 `LspServerManager` 的 `(language, cwd)` client 是否存在）；存在则发 `notify_change`，不存在则跳过（fail-open，不强迫启动 server）
3. **不阻塞编辑流**：`didChange` 是 notification（无响应等待），fire-and-forget；server 异步重算诊断

**关键约束**：
- 只对**已 acquire 的 server**发 didChange（不为了同步而启动 server）；这保持 LSP 惰性
- didChange 用 full content sync（`{"text": new_content}`），避免增量 range 计算复杂度
- 多个连续编辑合并（防抖短窗口内只发最后一次 didChange）

### 2.3 步骤 B：被动诊断注入（即时反馈）

参考做法不靠工具主动调 `lsp_diagnostics`——而是注册 `publishDiagnostics` 处理器，server 异步推过来的诊断存进诊断 registry，在后续 query 里**作为 attachment 自动注入对话**。FileEdit 发 didChange 触发重算，诊断自动流进下一轮上下文。

这比"编辑→调工具→写 ledger→finish 时 gate 回放"**更即时**：agent 在**下一轮**就看到错误并自己修，不必等到 finish gate。

**实施**：
1. `LSPClient` 已缓存 `publishDiagnostics` 通知（`client.py:361-365`，按 uri 缓存）。新增一个**进程级诊断 registry**：聚合所有 client 的诊断，按文件路径索引，记录 `delivered` 标志（是否已注入过上下文）
2. 注册一个 before_model 钩子（或复用 `DynamicReminderMiddleware` 的 source 机制）：每轮首次 model call 前，扫描 registry 中**有 error 且未 delivered**的诊断，组装成 `<system-reminder source="lsp_diagnostics">` 注入上下文
3. 注入后标记 `delivered=True`；该文件下次被编辑（didChange）触发新诊断时重新标记 `undelivered`
4. 容量限制：每轮注入上限 N 个文件的 M 条诊断（按 severity 排序保留最严重），超出截断
5. **fail-open**：registry/注入任何失败不阻塞 turn

**与 evidence ledger 的关系**：被动注入是**即时反馈**（让 agent 当场修），evidence gate 是**最终防线**（finish 时验证）。两者互补，都做。

### 2.4 步骤 C：evidence gate 串联（最终门控）

诊断结果同时写 evidence ledger，finish 时 regression gate 回放。

**实施**：
1. 新增 `agent/tools/pub_base/auto_diagnostics.py`：编辑事件（复用 evidence collector 的编辑钩子）触发后，对 `modified_files` 按语言分组，调 LSP diagnostics（**直接调 `LspServerManager.acquire` + `LSPClient`，不经角色门控的工具层**——因为自动诊断可能在 main agent 或任何编辑角色上下文运行，不能依赖 `lsp_diagnostics` 工具的角色注入）
2. 诊断结果写 evidence ledger：`command="lsp_diagnostics <path>"`，`status`=error 数 0→pass / >0→fail，`auto=true` 标注
3. finish 时现有 regression gate 回放 `status="passed"` 的命令（含自动诊断写入的）；fail 记录作为 `[broken]` 呈现
4. gate 仍 **fail-open**：不阻塞 finish，只报告
5. 配置：`AUTO_DIAGNOSTICS_ENABLED`（默认 true）、`AUTO_DIAGNASTICS_MAX_FILES`（如 20）、`AUTO_DIAGNASTICS_TIMEOUT_S`

**与 Code Intel 开放计划的交互**：另一份计划（`计划_CodeIntel开放到Executor与General角色`）把 LSP 工具开放给 EXECUTOR/GENERAL。步骤 C **不依赖**那个计划——自动诊断直接调底层 manager/client，不经角色注入的工具层。但开放计划落地后，EXECUTOR 也能主动调 `lsp_diagnostics` 工具自查，与自动诊断互补。

### 2.5 LSP 鲁棒性补强

| 项 | Sherry 现状 | 改进 |
|---|---|---|
| 崩溃恢复 | 检测死则 kill 清除，下次 acquire 重建 | 自动重启带上限（`lsp_max_restarts=3`），避免无限循环 |
| ContentModified（-32801） | 无重试 | 指数退避重试（500ms/1000ms/2000ms，max 3）——rust-analyzer reindex 期间常见 |

**实施**：
1. `LSPClient`/`LspServerManager`：client 进程 exit 且非主动停止时，标记可重启；下次 acquire 检测到死且重启次数 < max 则自动重启；超 max 则返回错误（fail-open 回退 tree-sitter/rg）
2. `LSPClient.request`：响应错误码 `-32801` 时退避重试

### 2.6 风险与缓解

| 风险 | 缓解 |
|---|---|
| 编辑同步 didChange 拖慢编辑流 | notification fire-and-forget + 防抖合并；只对已 acquire server 发 |
| 被动注入刷屏/噪声 | 容量上限 + severity 排序 + delivered 去重；只注入 error 级 |
| LSP 冷启动拖慢 | 惰性 acquire 已有；自动诊断 fail-open 不阻塞 |
| 无 server 的文件 | 跳过，fail-open |
| 自动诊断与 agent 录入验证重复 | `auto=true` 标注，gate 回放去重 |
| 崩溃重启循环 | max 3 上限 |
| ContentModified 重试累积延迟 | max 3 + 退避上限 2s |

### 2.7 Kill criteria

- **步骤 A（编辑同步）是硬前置**：不实现则步骤 B/C 不上线（过期数据无意义）
- 步骤 B：若被动注入导致上下文噪声（agent 被无关诊断干扰），降级为"只注入当前编辑文件的诊断"而非全局
- 步骤 C：若 LSP 冷启动延迟导致编辑后卡顿 >5s 且防抖/上限无法收敛，自动诊断改"finish 时一次性跑"而非"编辑后即时跑"
- 步骤 C：若自动诊断误报率高（与 agent 录入验证冲突频繁），降级为"仅报告不写 ledger"

### 2.8 验收

- 编辑后 LSP server 视图同步（didChange 发送验证）
- 编辑后下一轮上下文含 `<system-reminder source="lsp_diagnostics">` 注入的 error 诊断（被动注入）
- 自动诊断结果写入 evidence ledger（`auto=true`）
- finish 时 gate 回放自动诊断 pass 记录；类型错误作 `[broken]` 呈现
- 崩溃 server 自动重启（≤max 3）
- ContentModified 错误自动重试
- 无 server 文件跳过；gate fail-open 不阻塞
- 回归：现有 evidence ledger / regression gate / LSP 工具测试全过

## 实施顺序与里程碑（r2 修订）

| 阶段 | 内容 | 依赖 | Kill criteria |
|---|---|---|---|
| 阶段 1 | LSP hover（trivial） | 无 | — |
| 阶段 2 | LSP 鲁棒性补强（崩溃重启 + ContentModified 重试） | 无 | 崩溃循环无法收敛则保留 max 上限 |
| 阶段 3 | **步骤 A：编辑同步**（前置必做） | LSPClient | 不实现则 B/C 不上线 |
| 阶段 4 | 浏览器 console/network 捕获 | CDP event_sinks | 反调试无法隔离则默认关 |
| 阶段 5 | **步骤 B：被动诊断注入** | 步骤 A | 噪声则收窄到当前文件 |
| 阶段 6 | **步骤 C：evidence gate 串联** | 步骤 A + LSP diagnostics | 卡顿无法收敛则改 finish 时跑 |

**关键顺序约束**：步骤 A 必须先于 B/C（否则过期数据）。鲁棒性补强（阶段 2）建议在步骤 A 前做——编辑同步会触发 server reindex，ContentModified 在此期间高发，先补重试减少假失败。

## 整体验收标准

1. 编辑后 LSP server 视图同步（didChange）——**硬前置**
2. 编辑后下一轮上下文含 error 诊断注入（被动，即时反馈）
3. finish 时类型错误作 `[broken]` 呈现，gate fail-open 不阻塞
4. LSP 崩溃自动重启（≤max 3）+ ContentModified 自动重试
5. `lsp_hover` 返回符号类型签名
6. 浏览器 reload 后读到 console 报错 + 失败 network
7. 各条 Kill criteria 已评估并记录
8. 不破坏现有 LSP 工具、evidence ledger、regression gate、浏览器工具行为

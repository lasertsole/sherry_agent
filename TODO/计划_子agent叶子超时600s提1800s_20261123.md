# 计划：子 agent 叶子超时 600s→1800s

- 日期：2026-11-23
- 状态：**待评审**
- 来源：DeepSWE 测评发现 600s 叶子预算对真实编码任务（read + implement + run tests）过短，agent 还在产出就被超时杀掉。eval 自己用 3× 系数补偿到 1800s，产品默认没补偿。
- 风险等级：**低** — 一个默认值 + 同步注释/描述/测试
- 依赖：无
- 可独立执行：✅

---

## 0. 现状

```
max_spawn_depth = 2, run_timeout_seconds = 600, _DEPTH_BUDGET_MULTIPLIER = 3.0

depth-2 叶子:  600 × 3^0 = 600s   (10 分钟)
depth-1 父:    600 × 3^1 = 1800s  (30 分钟)
depth-0 MAIN:  排除（靠迭代数 180 刹车）
```

eval 自己补偿：`suite.py` 把 `run_timeout_seconds` 乘 3 → eval 叶子 = 1800s，depth-1 = 5400s。
**产品默认没有这个补偿**，叶子只有 600s。

DeepSWE task 1 实测：1800s turn budget 下 9/20，7200s 下 20/20——预算是瓶颈不是能力。

### 改后预算

**产品侧和 eval 侧统一**，同一套深度梯子：

```
叶子 (depth == max_spawn_depth):  1800 × 3^0 = 1800s  (30 分钟)
父   (depth-1):                   1800 × 3^1 = 5400s  (90 分钟)
MAIN (depth 0):                   排除（迭代数封顶）
```

### eval 影响

eval 不再额外乘 3。改前 eval 用 `_EVAL_CHILD_RUN_TIMEOUT_MULTIPLIER = 3.0` 把产品默认 600s 补偿到 1800s；现在产品默认已经是 1800s，eval 和产品保持一致，乘数改为 1.0（不再补偿）。

| | 改前 | 改后 |
|---|------|------|
| 产品叶子 | 600s | 1800s |
| 产品 depth-1 | 1800s | 5400s |
| eval 叶子 | 1800s（=600×3） | 1800s（=产品默认，不补偿） |
| eval depth-1 | 5400s（=1800×3） | 5400s（=1800×3） |

eval 的 `SHERRY_EVAL_CHILD_RUN_TIMEOUT_S` 环境变量仍保留——它是手动 escape hatch，不受乘数变化影响。

## 2. 不改的东西

| 项 | 值 | 理由 |
|----|----|------|
| `run_timeout_min_seconds` | 600s | 只 clamp 模型提供的值（sessions_spawn），低于默认 1800 是合理的——模型可以主动要求短超时 |
| `run_timeout_max_seconds` | 7200s | 硬上限 2h 不变 |
| `_DEPTH_BUDGET_MULTIPLIER` | 3.0 | 倍率不变，只改基础值 |
| `max_spawn_depth` | 2 | 深度不变 |
| clamp 逻辑 | `[600, 7200]` | 模型提供的值仍 clamp 到这个范围 |
| 子树预算约束 | 子不超父剩余 | 不变 |
| `SHERRY_EVAL_CHILD_RUN_TIMEOUT_S` | 保留 | 手动 escape hatch，不受乘数变化影响 |

## 4. 风险

| 风险 | 缓解 |
|------|------|
| 1800s 叶子让失控子 agent 跑更久才被杀 | depth-1 父 5400s 会级联杀子树；迭代数上限（executor 90）仍刹车；MAIN 无 wall-clock 但迭代数 180 封顶 |
| 用户觉得子 agent 跑太久 | sessions_spawn 仍接受模型提供的 timeout，clamp 到 [600, 7200]；用户/模型可以主动设短 |
| eval 和产品一致后叶子变短（5400→1800） | eval 的 `--timeout`（task 级 wall clock）仍杀整个 run；1800s 对单个 step（read+implement+test）已够用；`SHERRY_EVAL_CHILD_RUN_TIMEOUT_S` 可手动覆盖 |

### Kill criteria

- 若实测发现 1800s 叶子导致资源占用过高（SUBAGENT lane 8 个并发 × 1800s），回退到 1200s（2× 而非 3× 原值）
- 若 eval 1800s 叶子对某些 benchmark 不够，设 `SHERRY_EVAL_CHILD_RUN_TIMEOUT_S=3600` 手动覆盖（不改乘数）

---

## 5. 验收

- `get_config().run_timeout_seconds == 1800.0`
- 叶子 spawn（depth == max_spawn_depth）→ timeout = 1800s
- depth-1 spawn → timeout = 5400s
- 模型提供 `run_timeout_seconds=600` → clamp 后仍 600s（min 不变）
- 模型提供 `run_timeout_seconds=99999` → clamp 后 7200s（max 不变）
- 子树约束不变：父用了 4000s 后派子，子拿 min(1800, 5400-4000) = 1400s
- eval `_eval_child_run_timeout_s()` = 1800 × 1.0 = 1800s（和产品一致）
- eval bump 逻辑不触发（`1800 < 1800` → False）
- `SHERRY_EVAL_CHILD_RUN_TIMEOUT_S=3600` → eval 叶子 = 3600s（手动覆盖仍生效）
- 所有同步测试通过

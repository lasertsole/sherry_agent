# 计划：思考模式切换时刷新冻结快照（条件计划）

- 建档日期：2026-10-22
- 状态：**计划（未开工）**
- 触发问题：`MemoryStore` 的冻结快照（`_system_prompt_snapshot`）只在 session 初
  `load_from_disk()` 时捕获一次，此后 mid-session 写入（FACTS.md 被 plan extraction
  写、MEMORY.md / USER.md 被 agent 或 nudge 写）只落盘不更新快照，system prompt
  整个 session 字节不变——这是保护 prefix cache 的设计。但思考模式切换时
  `ThinkingControlMiddleware` 会换 model variant（`request.override(model=variant)`），
  如果 provider 的 prefix cache 键包含 model build（含 thinking 参数），切换后缓存
  本就冷了。既然缓存已经要冷，不如顺手 `load_from_disk()` 刷新快照——"免费"拿到
  mid-session 写入的最新记忆内容。
- 结论先行：
  1. **前置门控**：先实测切换思考模式是否真的把 prefix cache 命中率打到 0。会 → 执行
     主体；不会 → 放弃整个计划（缓存没破就不该额外破坏它）。
  2. **主体**：在 turn 开始时检测思考模式与上一轮不同 → `load_from_disk()` 刷新快照
     + 删除 `StateKey.SYSTEM_PROMPT` 失效三层缓存 → 首次模型调用重建 system prompt
     时拿到的是新快照。
  3. **触发条件**：仅在实际发送消息（turn 开始）且检测到思考模式与上一轮不同时触发；
     前端来回拨开关但不发送不触发。

---

## 0. 前置验证：切换思考模式是否破坏 prefix cache

### 0.1 验证逻辑

同一份 system prompt + 同一份消息前缀，连续发两次：

1. 请求 A：thinking OFF，建立缓存
2. 请求 B：thinking OFF，相同前缀 → **应命中**（baseline，证明缓存机制本身工作）
3. 请求 C：thinking ON，相同前缀 → **检查命中**

如果 C 的 cache_read = 0 而 B 的 cache_read > 0，则思考模式切换破坏了 prefix cache。

### 0.2 验证指标

不同 provider 的 response `usage_metadata` 携带不同字段：

| Provider | 字段 | 说明 |
|---|---|---|
| Anthropic | `cache_read_input_tokens` | 显式缓存命中 token 数 |
| OpenAI | `prompt_tokens_details.cached_tokens` | 显式缓存命中 token 数 |
| 其他 | 无标准字段 | 需要靠 `prompt_tokens` 与前缀 token 数的差值推断 |

代码参照：`nudges.py:890` 的 `_cache_hit_tokens(reply)` 已有从 response 提取缓存命中
token 的逻辑，可直接复用。

### 0.3 验证脚本草案

```python
"""
前置验证：思考模式切换是否破坏 prefix cache。
需要 .models 配置好主模型，且 provider 返回 cache hit 指标（Anthropic / OpenAI）。
"""
import asyncio
from models import build_main_llm
from langchain_core.messages import SystemMessage, HumanMessage

SYSTEM = SystemMessage(content="你是一个助手。" * 200)  # 足够长以触发缓存
USER = HumanMessage(content="说一句话。")

async def probe(thinking: bool | None) -> int:
    model = build_main_llm(thinking=thinking)
    resp = await model.ainvoke([SYSTEM, USER])
    meta = getattr(resp, "usage_metadata", None) or {}
    # Anthropic
    if "cache_read_input_tokens" in meta:
        return meta["cache_read_input_tokens"]
    # OpenAI
    details = meta.get("prompt_tokens_details") or {}
    return details.get("cached_tokens", 0) or details.get("cached_tokens", -1)

async def main():
    a = await probe(False)   # 建立缓存
    await asyncio.sleep(0.5)
    b = await probe(False)   # 相同 thinking → baseline 命中
    await asyncio.sleep(0.5)
    c = await probe(True)    # 切换 thinking → 检查命中
    print(f"A (OFF, cold)  cache_read={a}")
    print(f"B (OFF, warm)  cache_read={b}")
    print(f"C (ON,  swap)  cache_read={c}")
    if b > 0 and c == 0:
        print("结论：思考模式切换破坏 prefix cache → 执行主体计划")
    elif b > 0 and c > 0:
        print("结论：思考模式切换不破坏 prefix cache → 放弃计划")
    else:
        print("结论：无法判定（provider 可能不支持缓存或指标不可读）→ 需人工排查")

asyncio.run(main())
```

### 0.4 判定标准

| B cache_read | C cache_read | 结论 |
|---|---|---|
| > 0 | = 0 | **切换破坏缓存** → 执行主体 |
| > 0 | > 0 | 切换不破坏 → **放弃计划** |
| = 0 | — | provider 不支持缓存或指标不可读 → 需人工排查 |

## 1. 主体：思考模式切换时刷新冻结快照

> 仅在前置验证（§0）确认"切换思考模式破坏 prefix cache"后执行。

### 1.1 核心逻辑

在 turn 开始时（`before_model` 钩子，运行在 `system_prompt_injection` 的
`wrap_model_call` 之前），检测思考模式是否与上一轮不同：

1. 读当前 `LLM_THINKING_ENABLED`（已被 turn boundary 从 pending 提升）
2. 与上一轮的 applied thinking（`_last_applied` 或 `_applied_model_configs`）比较
3. **不同** → `memory_store.load_from_disk()` 刷新 `_system_prompt_snapshot` +
   删除 `state_register_mem` 和 `state_register_db` 中的 `StateKey.SYSTEM_PROMPT`
4. `system_prompt_injection` 的 `wrap_model_call` 随后运行 → 三层缓存全 miss →
   `build_system_prompt` 重建 → `format_for_system_prompt("facts")` 返回新快照

### 1.2 为什么放 before_model 而非 wrap_model_call

中间件链执行顺序（`agent/core.py`）：

```
before_model hooks → wrap_model_call hooks（外→内）→ LLM
```

- `system_prompt_injection` 是最外层 `wrap_model_call`（`@dynamic_prompt`）
- `ThinkingControlMiddleware` 是内层 `wrap_model_call`（`core.py:364`）

如果刷新逻辑放在 `ThinkingControlMiddleware.wrap_model_call` 里，它在
`system_prompt_injection` **之后**运行——当前调用的 system prompt 已经被外层用旧快照
解析完毕，刷新只对同一轮的后续模型调用（工具循环）生效。**首轮首次调用（最重要的一次）
仍然用旧快照。**

放在 `before_model` 里则保证：刷新在 `system_prompt_injection` 之前完成，首轮首次调用
就能拿到新快照。

参照先例：`DynamicReminderMiddleware` 就是 `before_model` 钩子（`abefore_model`），
注册位置在 `TaskIntentMiddleware` 之后（`core.py:357`）。

### 1.3 触发条件——"仅发送时，且模式不同时"

| 场景 | 触发？ | 原因 |
|---|---|---|
| 用户拨了开关但没发送 | **否** | 没有 turn，`before_model` 不运行 |
| 用户拨了开关→发送，模式和上一轮相同 | **否** | `_last_applied` 比较相同，跳过 |
| 用户拨了开关→发送，模式和上一轮不同 | **是** | 比较不同，刷新快照 + 失效缓存 |
| 用户没拨开关直接发送 | **否** | `_last_applied` 比较相同，跳过 |
| 首轮（无上一轮参考） | **否** | `_last_applied` 为空，视为相同（首轮的 `load_from_disk` 已在 agent 初始化时完成） |

park/promote 时序已经天然满足"仅发送时"的条件：用户拨开关 → `LLM_THINKING_ENABLED_PENDING`
（parked）→ 发送触发 turn → 上一轮的 `on_turn_finished` 提升 pending → 新 turn 的
`before_model` 读到提升后的值。

### 1.4 涉及的代码修改点

#### 1.4.1 ThinkingControlMiddleware 增加 before_model 钩子

文件：`agent/middlewares/thinking_control/core.py`

```python
async def abefore_model(self, state, runtime=None) -> dict[str, Any] | None:
    """思考模式切换时刷新冻结快照 + 失效 system prompt 缓存。

    在 system_prompt_injection 的 wrap_model_call 之前运行，保证首轮首次
    模型调用就能拿到新快照。
    """
    session_id = str((state or {}).get("session_id") or "")
    if not session_id:
        return None

    cache_key, override, custom_mapping = self._read_controls(session_id)
    applied = (cache_key, (override or {}).get("model"))
    last = self._last_applied.get(session_id)

    # 首轮或模式未变 → 不触发
    if last is None or last == applied:
        return None

    # 思考模式变化 → 刷新快照 + 失效缓存
    from agent.tools.memory import memory_store
    from runtime import StateKey, state_register_mem, state_register_db

    memory_store.load_from_disk()              # 刷新 _system_prompt_snapshot
    state_register_mem.del_state(session_id, StateKey.SYSTEM_PROMPT)
    state_register_db.del_state(session_id, StateKey.SYSTEM_PROMPT)

    logger.info(
        "ThinkingControlMiddleware: thinking changed {}→{}, "
        "refreshed memory snapshot + invalidated system prompt cache",
        last, applied,
    )
    return None
```

#### 1.4.2 需要确认的 API

- `state_register_mem.del_state` / `state_register_db.del_state` 是否存在——若不存在，
  用 `set_state(session_id, StateKey.SYSTEM_PROMPT, None)` 等效失效（`_get_and_reload_system_prompt`
  检查的是 `is None`）。
- `load_from_disk()` 是 process-level 单例方法，无 session 隔离——所有 session 共享同一份
  快照，调用一次即全局生效。这在当前设计下是安全的（冻结快照本就是全局的）。

### 1.5 为什么不直接在 HTTP 层（turn_runner）做

turn_runner 的 `on_turn_finished` 是提升 pending 值的地方。理论上可以在那里检测变化
并刷新。但：

- turn_runner 属于 `server/` 层，`MemoryStore` 属于 `agent/` 层——跨层调用增加耦合
- `before_model` 钩子在 agent 层内闭环，且执行时序（在 `system_prompt_injection` 之前）
  天然正确
- 已有先例（`DynamicReminderMiddleware` 的 `abefore_model` 就做类似的 per-turn 注入）

### 1.6 边界与风险

| 风险 | 评估 | 缓解 |
|---|---|---|
| `load_from_disk()` 有文件锁 I/O | 阻塞事件循环？ | 当前 `load_from_disk` 用 `flock_path`（`LOCK_SH`），非阻塞场景下毫秒级；且只在思考模式变化时触发，非每轮 |
| 全局快照影响其他 session | 两个 session 共享 `memory_store` 单例，A 切换会刷新 B 的快照 | 快照本就是全局的——B 的 system prompt 缓存未失效，B 仍用旧快照直到自己的下次 `load_from_disk`；且 B 的 mid-session 写入本就不影响 B 自己的 system prompt |
| 刷新后 system prompt 变化但 thinking 未变 | 不会——刷新只在 thinking 变化时触发；如果 thinking 变了但 memory 文件没变，`load_from_disk()` 读到相同内容，system prompt 字节不变，prefix cache 不额外受影响 | 设计自洽 |
| provider 不支持缓存指标（§0 无法判定） | 计划卡在前置验证 | 需要一个支持 cache hit 报告的 provider（Anthropic / OpenAI）来跑验证 |

### 1.7 测试要点

1. **前置验证测试**：`tests/agent/middlewares/test_thinking_control.py` 加一个 mark 为
   `llm_e2e` 的测试，跑 §0.3 脚本，断言 B 命中 > 0 且 C 命中 == 0（或 > 0 后放弃计划）。
2. **刷新触发测试**（mock，不需要真 LLM）：
   - 设 `_last_applied[session] = ("on", "gpt-4o")`
   - 设 `LLM_THINKING_ENABLED = False`（off）
   - 调 `abefore_model` → 断言 `StateKey.SYSTEM_PROMPT` 从 mem 和 db 中被删除
   - 断言 `memory_store._system_prompt_snapshot["facts"]` 被刷新
3. **不触发测试**：
   - thinking 模式不变 → `abefore_model` 返回 None，`StateKey.SYSTEM_PROMPT` 仍在
   - 首轮（`_last_applied` 为空）→ 同上
4. **端到端**：切换思考模式后首轮 system prompt 包含 mid-session 写入的 FACTS.md 新条目

## 2. 执行顺序

1. **§0 前置验证**——跑验证脚本，判定思考模式切换是否破坏 prefix cache

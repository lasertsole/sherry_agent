## 摘要

多代理系统可以通过并发执行来降低复杂任务的延迟。若干先行 harness 框架已经支持多代理系统,
但当前多代理 harness 的可扩展性往往受限于**中央编排者的任务分配与协调容量**。为突破这一限制,
我们提出 Agensh——一个**没有中央编排者**的可扩展自组织多代理 harness:并发 worker 各自执行一套
多代理协作循环,持续地 gathering context(收集上下文)、claim and self-assign sub-tasks(认领并
自分配子任务)、take action(采取行动)、share findings(分享发现)、verify results(验证结果)、
merge progress(合并进度),全程异步。循环由代理组织基础设施的三个组件支撑:**共享工作区**
(保存已提出、进行中、已完成的工作)、**消息接口**(供 worker 之间通信)、**共享上下文**
(沉淀可复用的发现与工作意图)。为测试可扩展性,我们在 ProgramBench 最难的五个任务上用
GPT-5.6-sol(high)评估:代理数从 1 扩到 128,平均最终测试通过率从 19.31% 升至 28.78%,相对
提升约 49%;更大的组织更早达到同等通过率。在 pandoc 上,1→1024 个代理把最终通过率从 33.89%
提升到 55.06%。worker 轨迹进一步显示:随着组织规模增长,不同形式的**自组织协作逐步涌现并
标准化**。这些结果揭示了**代理数量是多代理组织的一个新扩展维度**,为严苛延迟约束/时间预算下的
复杂任务提供了实用方案。

*(图 1:在 6 小时预算、无网络条件下从零构建 pandoc。)* **pandoc 的完整曲线(图上有、正文
没写)**:1→33.89%,8→**41.75%**,32→**43.11%**,128→**50.94%**,1024→55.06%。注意
8→32 只涨 1.36 分(平台区),32→128 涨 7.83 分,128→1024 再涨 4.12 分——**不是平滑线性**,
中间有一段明显的停滞。图右侧的「涌现协作」阶梯与横轴对位:Peer coordination 覆盖 1–8 区间,
Multi-worker integration 覆盖 8–32,Standardized workflows 覆盖 32–128,Specialized roles
覆盖 128–1024;**阶梯条带互相重叠**,表示形态是逐段叠加而不是到点切换。

## 1 引言

单代理系统让大模型感知上下文、通过工具行动、更新状态、迭代逼近目标,但其能力受限于
**一个上下文窗口、一条动作流、一条记忆流**;串行执行给复杂真实任务带来高延迟。要突破这些约束,
就要扩展多代理系统中代理的数量。

Codex sub-agent、Claude Code sub-agent 与 agent teams、Copilot fleet、Kimi Agent Swarm 等框架
普遍采用**编排者—工人**结构:主代理规划、分解、派发、管理。这种结构通常需要一个经过训练的
编排者才能有效规划分解,而且**系统整体的可扩展性从根本上受限于编排者管理和协调工人、整合
贡献的容量**。

Agensh 的答案:去掉中央编排者。自组织 worker 并发异步运行,通过轻量的**代理组织基础设施**
共享状态与进度:

- **共享工作区**:承载组织的进行中工作与已整合结果;
- **消息接口**:承载组织级公告与紧急直达消息;
- **共享上下文**:沉淀同伴的可复用发现与工作意图。

每个 worker 再配一套**异步协作循环**(第 2.1 节)。循环一轮:先围绕共享目标收集上下文、读同伴
进度,认领一个子任务;通过消息处理潜在重叠或冲突;用可用工具解决子任务;期间把可能有用的发现
写进共享上下文;工作完成并验证后,把进度合并进共享工作区,然后回到下一轮。

实验采用 ProgramBench——最具挑战性的智能体软件工程基准之一:无网络、6 小时预算内从零复现
参考软件的行为。我们选了五个最难的任务,参考仓库数千文件、源码数百万字节。1→128 个代理把五任务
平均最终通过率从 19.31% 提到 28.78%(相对 +49%);更大组织更早达到同等水平(并发降低延迟);
pandoc 上 1→1024 把通过率从 33.89% 提到 55.06%。轨迹还显示随规模增长,协作形式从同伴协调、
多工人集成,扩展到标准化工作流与组织级专业化角色。总体而言:**代理数量是多代理组织的新扩展
维度**——既是在硬延迟/时间预算下复杂任务的实用解法,也展示了扩展多代理组织能推开通用智能
的边界。

*(图 2:对比以往「编排者组织工人」与 Agensh「经基础设施自组织协作」。)* **看图才能发现的
一件事:两边的拓扑都是星形**——左侧中心是 `Orchestrator`(一个"节点"),右侧中心仍是同一个
位置的圆圈,只是标注换成了「lightweight infrastructure for shared workspace, message
interface, and shared context」。也就是说 Agensh 去掉的是**中心里的那个智能体**,不是
"中心"这个形状;它把中心降级为被动存储/传输。**这一点对"有编排者的系统能否借鉴"是关键:
可迁移的是"中心的基础设施化"这一半,不需要先砍掉编排者。**

## 2 多代理组织 harness

*(图 3:协作循环示意——worker 并发地 收集上下文→认领子任务→行动→验证→合并→重复,直到
目标达成;全员异步,经基础设施共享进度。)* **图上的箭头区分了每一步与基础设施的读/写关系,
这是正文散文里没有的信息:**

| 循环步骤 | 与基础设施的关系 |
| --- | --- |
| Gather context | **异步读**(绿色上箭头) |
| Claim sub-task | **并发写**(红色下箭头,写 `CLAIM`) |
| Take action | **同时读和写**(绿色 + 红色:读同伴进度,写 `OBSERVED`/`FACT`/`FAIL`) |
| Verify results | **异步读**(绿色:取验收标准与同伴证据) |
| Merge progress | **并发写**(红色:合入工作区 + 写 `PATCH_SUMMARY`) |

**推论**:论文把"读"点放在取上下文、行动中、验证时三个位置——这正是"mid-turn 高优先级
投递"该落地的位置;而"写"点是认领、行动中、合并三处,也是幂等/限流必须覆盖的三处。
Take action 是唯一读写兼备的步骤,即**协作信息最密集的一步**,也解释了为什么附录 B.2 的
mid-turn 注入包在"任意基础设施工具调用"外层。

### 2.1 多代理协作循环

harness 的核心抽象是它的循环。每个 worker 并发、异步地执行以下五步:

1. **收集上下文(Gather context)**:读共享的用户目标、当前状态、同伴进度与消息、累积发现,
   弄清已完成/待完成;并与环境交互,识别、规划下一步有用的动作。
2. **认领子任务(Claim sub-task)**:提出自己要做的子任务,把范围作为一条 `CLAIM` 追加到共享
   上下文。两个 worker 的 claim 重叠或冲突时,**鼓励通过直接消息自行解决**。
3. **采取行动(Take action)**:本地解决子任务,与环境交互;期间凡建立可能对同伴有用的发现,
   即时报到共享上下文。
4. **验证结果(Verify results)**:对照子任务的验收标准检查本地进度;不满足就修改方法,直到
   达标。
5. **合并进度(Merge progress)**:把贡献合并进共享工作区供同伴使用;发布一条更新,描述改了
   什么、背后思路、验证证据,让同伴可以在此基础上继续。**若合并被冲突挡住:吸收最新同伴进度、
   解决冲突、再次合并。**

第 5 步之后回到第 1 步,基于最新整合的工作与同伴更新开始下一轮。通过自提自领,worker 在整个
组织内**自组织地完成子任务的发现与分配**;彼此异步,谁都不用等同伴完成一轮。循环往复,发现与
已验证贡献经基础设施不断累积,推动组织逼近目标。

### 2.2 代理组织基础设施

*(图 4:三件套——共享上下文(观察/认领/失败尝试)、共享工作区(已完成/进行中/已提出的工作)、
消息接口(分享进度/解决冲突/避免重复)。)* **图上两个结构细节**:每个 worker 头顶各有一个
**自己的自环箭头**(`Loop`)——循环是 **per-worker 的私有周期**,不是全局流水线;而全部
worker 的上下箭头都汇入**同一个**基础设施盒子——拓扑上仍是单中心(见 2.2 与图 2 读解)。
三格里的条目就是各自的设计用途,其中两条值得单列:**"避免重复"被明确归给消息接口**
(而不是共享上下文),**"失败尝试"被明确列为共享上下文的一等类目**。

**共享工作区。** 一个承载组织工作的文件系统,要求支持**并发写、异步读**——worker 各自开发
各自贡献的同时能读同伴发布的成果;还要保留版本历史、支持合并,并**把合并冲突暴露出来**让
worker 回溯解决。Agensh 用 **Git 平台**(Gitea)实现:worker 改私有的 checkout 与分支,把贡献
整合进 main 分支;Git 记录改动来源(provenance)、检测**文本**合并冲突,并承载全部 issue 与
pull request。

**消息接口。** 让 worker 就进行中的工作沟通、处理归属重叠、解决依赖冲突。实现上(Mattermost):
一个共享任务频道承载团队公告;直接消息(DM)承载紧急的一对一沟通。**低优先级的频道消息在每轮
循环开始时投递;高优先级的直接消息在每次基础设施工具调用返回时投递(回合中途送达)。** 消息
接口保留会话历史、异步投递——worker 能及时解决重叠认领、协商依赖、请求协助,同时同伴继续干活。

**共享上下文。** 沉淀可跨组织复用的发现与工作认领(思想源自 DeLM)。worker 发布简短的、
**类型化**的条目:`OBSERVED`(观察到的行为)、`FACT`(已确认的事实)、`FAIL`(记录失败的
尝试)、`CLAIM`(进行中的认领)、`PATCH_SUMMARY`(已完成改动的摘要,格式
`files= | idea= | evidence=`)。服务端是一个只追加(append-only)数据库,保留近期记忆;为支撑
更长任务,提供 **context grep 工具**让 worker 检索近期记忆之外的完整历史。**新条目被视为高
优先级更新:每个其他 worker 的下一次基础设施工具调用返回时即被转发**,使同伴发现在全组织内
及时可见。

三者合力,把每个 worker 的本地活动连接到组织的共享状态:在自己的循环内,复用同伴发现、处理
子任务重叠、做出整合过的贡献。

### 2.3 实现

Agensh 是**架在单代理 harness 之上**的组织 harness,而非替代。每个 worker 的本地智能体循环
(会话状态、调模型、执行工具、产出下一条响应)由底层单代理 harness 负责;Agensh 在其外提供
组织级行为:worker 身份、协作协议、事件路由、稳健派发、共享工作区访问、消息、共享上下文、
恢复与活性机制。**单代理 harness 决定一个 worker 如何推理与行动;Agensh 决定多少个 worker
接收事件、共享状态、协调、持续为共享目标做贡献。**

两层之间的接口刻意保持最小、即插即用:**协作循环通过 worker prompt 里的工作流指令实现,
不硬编码进运行时**(附录 A 给出完整 worker prompt——除 worker id 外人人相同)。因此 Agensh
可以经轻量的 harness 适配器接入不同底层(如 Claude Code、Copilot),协作循环、共享服务、
底层智能体循环均不改动。实现选型:共享工作区 = Gitea,消息接口 = Mattermost,共享上下文沿
DeLM 核心思想改造工具格式与 worker 指令。

   increasing trend"在图上只对 3/5 个任务成立;均值的单调靠 pandoc(+17.05)与 ctags 的
   后期跃升拉动。**推论:小规模增加代理可能净负收益**(协调开销超过并行收益),不是"越多越好"。
2. **均值不能由图上两位小数逐项平均复现**(如 128 代理:5 项之和 ÷5 = 28.93,报告 28.78),
   说明均值用的是未取整的原始分数,图上数字是二次舍入。

*(图 6:五个任务 + 均值的"前 2 小时通过率-时间"曲线,每个面板四条线 = 1 / 8 / 32 / 128
代理。)* 正文只举了 pandoc 一个例子说明"更大组织更早达标";图 6 的全部面板显示这一结论
**同样不是全局的**:

- **pandoc、PHP-src、均值**:四条线顺序整齐(128 > 32 > 8 > 1),正文结论成立;
- **FFmpeg**:**32 代理线多数时间略高于 128 代理线**,两条末端几乎重合(对应最终 13.22 vs
  13.60)——"更多代理"在这个任务上的额外收益接近零;
- **gromacs**:面板标签自上而下是 **128 / 1 / 32 / 8**——**单代理全程压在 8 与 32 之上**,
  128 只在末段反超;
- **ctags**:**8 代理线全程垫底、且全程低于 1 代理**;32 代理线起步冲刺、早期一度贴近 128,
  末端被反超。

**这张图对"该不该加协调机制"最有价值的一条**:最难看的不是大组织,而是"不大不小"的
8 代理配置——它在两个任务上跑输单代理。协调成本与并发收益之间存在一个**净收益为负的中间区**。

固定代理模型(GPT-5.6-sol,high)、底层 harness(Copilot)与预算,**五任务平均分随组织
规模单调上升**:1→128 增益 9.47 个百分点,相对提升约 49%。作者据此认为持续增加协作 worker
能在长时域上提升复杂软件复现的质量——但**均值层面的这一结论不逐任务成立**(见上表:2/5 的
任务在低中规模上退化)。

延迟维度本身(pandoc 的具体读数):128 代理在 30 分钟检查点即越过 30%,32 与 8 代理分别在
60、90 分钟越过;单代理前两小时始终低于该阈值。**"更早达标"是确凿的,"每个任务都更快"不是**
(见上方图 6 读解)。

*(图 1,扩展。)* pandoc 上规模进一步扩到 1,024:33.89%(1)→ **41.75%(8)** →
**43.11%(32)** → 50.94%(128)→ **55.06%(1024)**;最大组织比 128 再增 4.12 个百分点,
比单代理高 21.17 个百分点。这证明 Agensh 的自组织协作能持续扩展到上千 worker。作者的结论
是**代理数量是多代理组织的新扩展维度**;更精确的读法应是"**在均值与足够大规模上**成立,
而 8~32 这个中间档在某些任务上并不划算"。

### 3.2 规模上的自组织协作涌现

所有 worker 同 prompt、同循环(仅 id 不同),但轨迹显示协作形式随规模逐级涌现:

- **8 个代理——与同伴协调实现**:worker 能谈定一个具体技术接口,然后各自独立实现符合该接口
  的组件(gromacs:公告模块接口,各自实现遵循它的命令模块);也能自行发现并解决认领重叠
  (FFmpeg:一名 worker 与同伴讨论重叠后改变范围、改做互补工作)。
- **32 个代理——跨多 worker 的集成管理**:多人共同参与一项技术贡献(PHP-src:数名同伴先批准
  一项贡献,另一 worker 找到具体反例,先前批准被撤回,作者修复问题,同伴复审,再由一名同伴
  合并);集成管理更活跃,更多同伴参与沟通。
- **128 个代理——自组织专业化与工作流标准化**:专业化出现——worker 按相关既往经验选择评审人,
  并长期复用这些评审关系;可以把集成的责任移交给一名同伴,由其解决冲突、验证合并后的工作并
  合并。能协商、遵循并复用标准化的自组织工作流(pandoc:两名 worker 建立标准集成协议——作者
  更新并测试分支,然后把 commit hash 发给同伴验证并合并;该协议随后被其他 worker 复用。若干
  失败之后,worker 又修订协议:授权同伴执行完整的「更新-测试-检查-合并」周期,同伴明确接受
  并对新 PR 执行该程序)。
- **1,024 个代理——组织级角色专业化**:多个 worker 承担同一专业角色或同一技术领域的专长。
  pandoc 中多名 worker 充当集成者:一名 worker 可以联系多个候选集成者,**选第一个有效响应的、
  取消其余请求,选定之后才交接代码**;同领域专长的 worker 还能在他人尝试失败后接手恢复工作,
  组织不再依赖任何个体 worker,健壮性增强。

这些观察与扩展结果互补:协作范围随规模从「协调实现」扩展到「管理集成」「标准化工作流」
「组织级角色专业化」。令人惊讶的是,这些形式**完全自组织**——worker 自己选合作者、分职责、
通过同伴交互建立并修订工作流。

## 4 相关工作

- **多代理组织与协作 harness**:Claude Code 支持持久 sub-agent 与异步 agent teams,但协作仍
  围绕固定的 lead 会话(spawn、管共享任务、代理间消息);Codex 的 sub-agent 由并行 worker
  完成并把结果路由回父级整合;Kimi Agent Swarm 训练一个编排者分解任务、并发调度 sub-agent,
  仍是编排者—工人并行方案。Agensh 研究的是**自组织 worker 在持久工作周期上共同承担任务发现、
  依赖协调、结果整合**的组织结构。
- **共享上下文与去中心化协调**:DeLM 组合异步 worker、任务队列与共享上下文,让代理在累积进度
  上构建而无需每个更新都过中央控制器;ChatCollab 把人类与 AI 作为 Slack 同侪协同;SlackAgents
  把 agent 嵌入 Slack 工作区做沟通与任务编排。共享工作区方面:Carlini 的编译器实验用 Git 仓库
  + 任务锁文件协调 16 个 Claude agent,无编排 agent,worker 自选任务、自行合并;STORM 把多代理
  编程重构为状态管理问题,用共享工作区替代隔离的多代理 worktree,在**写时**强制本地状态一致
  并检测过期/冲突编辑。

## 5 结论

Agensh = 多代理协作循环 × 轻量代理组织基础设施。自组织 worker 经共享工作区、消息接口、共享
上下文,发现并认领子任务、交换发现、整合贡献,全程并发异步——个体进展累积为共享工作与知识,
不依赖中央编排者分配任务、管理工人。固定模型与 6 小时预算:五任务 1→128 代理平均通过率
19.31%→28.78%(相对 +49%);更大组织更早达到同等水平(延迟维度);pandoc 1→1024 达 55.06%。
轨迹显示协作形式随规模拓宽:同伴协调 → 多工人集成 → 标准化工作流 → 组织级角色专业化。
**代理数量是多代理组织的新扩展维度**:扩展协作既是在硬延迟/时间预算下复杂任务的实用路径,
也是推开通用智能边界的途径。

### # Hello

你是 pbench-team1-worker1。

### ## 你在哪里

你和 1024 个同伴一起工作。工作记录在 **gitea**;你们在 **mattermost** 上交谈;在
**shared context board**(共享上下文板)上分享发现。

- **gitea**——issue #1 是总任务。你为自己负责的领域开自己的 issue,PR 承载工作。容器内一切
  操作(clone/fetch/push/curl/API)都用 **`http://gitea:3000`**。gitea 返回的
  `clone_url` / `html_url` 是外部地址(`http://gitea.localhost:<port>`),**容器内不可达**——
  见到就替换成 `http://gitea:3000`。
- **mattermost**——频道 `pbench-task` 是团队交流处。发言要简短具体。账号名是
  `pbench-team1-worker1..1024`;`@worker1` 匹配不到任何账号,要用全名。同服务器上的
  **直接消息**会在同伴**当前回合内**送达,是解决碰撞最快的方式——但它会打断对方正在做的事。
  两个人将要编辑同一处时发直接消息;其他一切用频道。
- **shared context board**——每个 agent 的简短、已验证笔记的只追加日志。每回合开头会以
  `==== SHARED CONTEXT ====` 渲染进你的 prompt;此后同伴写下的任何内容都会**回合中途**追加到
  你正在等待的工具结果上。一旦有所发现立刻用 `board_write` 发布:`OBSERVED` 记录参考程序的
  可注意行为,`FACT` 记录你确认的事实,`FAIL` 记录你证伪的假设(**价值最高的条目**:让同伴
  不再为此花预算),修复问题时发 `PATCH_SUMMARY`(`files= | idea= | evidence=`),开工时发
  `CLAIM` 让同伴选别的角度。条目有长度上限(100 字符,`PATCH_SUMMARY` 300);长内容放进
  `detail`,同伴可以 `board_unfold` 展开。**不要重新推导同伴的 `FACT`,不要重试已记录为
  `FAIL` 的做法。** `board_read` 返回近期完整板(截断到最新 2000 条),`board_grep` 在完整
  历史里按关键词检索;支持多关键词:`,` 是 OR,`&` 是 AND(大小写不敏感),所以 `a&b,c&d`
  表示 (a AND b) OR (c AND d)。

### ## 团队

1024 个 coder,人人平等。你认领要构建什么、构建它、合并它、再选下一件事。同伴在同时工作:
**把自己合并进 main 之前先同步最新 `main` 分支**,与同伴同步以避免重复工作。永远聚焦复现参考
程序;只有当你的信息会显著影响他人工作时才动用协调工具。

### # 当前任务:ProgramBench 逆向重建

#### 目标

给你一个**预编译的参考程序**(二进制),挂载在每个容器的 `/opt/pbench/executable`。
任务:**从零重建一个完整代码库,复现其行为**,使之可编译并通过隐藏测试。

- 你**可以运行**这个二进制来观察行为:`/opt/pbench/executable --help`、喂各种输入、检查输出、
  对比边界情况。这是理解目标行为的**唯一信息来源**(外加仓库里的文档/资产)。
- 你**不能读它的字节**:它是 `root:root 0111`,`cat` / `od` / `objdump` 都会 Permission
  denied。这是规则不是故障——**不要尝试反编译或 dump**;那是作弊,而且就算试也读不到。

#### 铁律(违反任何一条 = 整个任务作废)

1. **完全自主**:全队自行定义需求、自行分解、自行决策、自行收尾。没有任何外部输入;不要等待
   指示,不要在 mattermost 上问"接下来做什么"——答案永远是:**推进重建**。
2. **无网络**:整个集群离线。`git clone` 原项目源码、`pip install`、`npm i` 远程包**全部会
   失败**。不要浪费时间联网拉原始源码——既不可能也是作弊。只有容器内已有的工具链
   (gcc / make / python / node 等本地安装)可用。
3. **硬性交付约束**:仓库**根目录**必须有可执行的 `compile.sh`;运行它必须在**根目录**产出
   可执行文件 `./executable`。评测器会 tar 你的仓库 HEAD → 解包 → **删除任何已提交的
   `./executable`** → 运行 `./compile.sh` → 用产出的 `./executable` 跑隐藏测试。
   `compile.sh` 必须创建 `./executable`,而不只是 chmod。**根目录没有 compile.sh = 0 分。**

#### 第一步永远是

**运行 `/opt/pbench/executable`,观察它做什么。** 每次重建都从理解实际行为开始。

#### 使用工具

**事件。** 你是事件驱动的。有相关事情发生时,环境会给你一条消息:

```
[event]
event_id=...
source=... <- gitea / mattermost / ...
kind=...
observed_at=...
summary: ... <- 发生了什么、去哪里找
```

它只报告事实;怎么处理由你决定。**直接消息和同伴的新板条目会在回合中途送达**,追加到你正在
等待的工具结果上;其余排队,回合结束时到达。回合中途到达的板条目按类型处理:
`FAIL`——你正在做这件事就停;`FACT` / `OBSERVED`——拿去用;`CLAIM` 撞了你在建的东西——用
直接消息解决;别人的其他 `CLAIM`——继续做你手上的。

**工作循环。** 每一步由做它的人收尾:

1. 运行 `/opt/pbench/executable`,观察未探索的区域,确定要构建什么。
2. 把你要负责的区域作为 `CLAIM` 公告到共享上下文板。
3. 在 `ulimit -v 67108864` 下对该区域运行 `/opt/pbench/executable`,基于当前 `main` 写出复现
   观察行为的代码。实现期间**不需要**和别人同步代码。
4. 同样的输入分别喂参考程序和你的构建,对比输出,检查你的工作。
5. push、开 PR、合进 `main`。**合并被拒就把最新 `main` 合进你的分支,对照参考重新检查工作,
   再 push。**
6. 在板上用 `PATCH_SUMMARY`(`files= | idea= | evidence=`)说明你完成了什么,然后回到 1。

构建需要的一切都要提交:评分器从 `main` 的全新 clone 构建,不会调用你仓库根下的二进制,所以
数据路径要用 `dirname(realpath(argv[0]))` 解析。

**其余。** MCP、git CLI、shell、curl、写文件——手边有什么用什么。工具不够就找一个;没有就
造一个。

## 附录 B:实现细节

### B.1 事件驱动运行时

每个 worker 由事件驱动,而非中央调度的步骤序列。它的配对 router 监听 Gitea 的仓库活动与
Mattermost 的消息:Gitea 走 server-sent event,触发一次"拉取比上次处理更新的通知";Mattermost
走长连接投递,断线重连后补拉错过的消息。新活动到达时,listener 把事件写入 worker 的**持久
队列**并唤醒派发器。**每个事件带唯一标识用于去重。**

每次派发器被唤醒,从排队事件出发:排序、合并成下一个 prompt,投递给 worker 的持久会话;
**回合完成时**才把事件标记为已发送。回合期间到达的事件留在队列等下一回合。投递失败按逐步
加长的间隔重试;router 重启后,未完成事件回到队列,worker 的先前会话尽可能恢复。若 worker
空闲 10 分钟,**空闲探测器**发一条 prompt 请它继续工作;若一个完成的回合没有产生任何共享
上下文条目,跟进 prompt 提醒它发布有用的发现。

### B.2 共享上下文投递

共享上下文经两条路径到达 worker:(1) 新回合开始时,router 把排队的工作区通知、到达的消息、
近期共享上下文追加进 prompt;(2) 回合进行中,**包在每次基础设施工具调用外层的包装器**把
待处理的直接消息与新的共享上下文条目追加到返回的工具结果上。该路径作用于 MCP 工具返回,
**不会打断任意正在运行的进程**。

## 附录 C:实验细节

- **任务选择**:按 ProgramBench 官方扩展结果(programbench.com/extended)中 SOTA 模型的平均
  通过率选最难五任务。
- **代理配置**:全部配置用 gpt-5.6-sol、high 推理档、相同 harness/worker 协议/评测配置;底层
  单代理 harness 为 Copilot,最大输入 272,000 token、最大输出 128,000 token。
- **实验设置**:按 ProgramBench 准备容器,总预算 6 小时,跑官方评测,报告 canonical-kept
  通过率。
- **大规模部署**:所有实验错峰启动以减少范围争抢——**第一小时每 30 秒启动一个 agent,之后每
  3 秒一个**。设首个 agent 激活时刻为 t;T = t+6h 时全部终止并导出提交。**T−45 分钟**发提醒:
  "停止派发新功能。确保根构建可用、已有工作已合并。落掉 open 的 PR;合不掉的,说明情况然后
  继续。" **T−5 分钟**再发:"能合的合掉,然后停下。确认默认分支上 bash compile.sh &&
  ./executable 可用,公布最终状态。" 1,024-worker 实验跨 16 个节点,每节点 64 个 agent。
- **单代理基线**:单代理实际很少能撑满 6 小时,故加一个 stop hook:"永远有新工作——不要被
  先前计划的范围困住:拿起 /opt/pbench/executable,对没试过的输入运行它,从交互中派生新任务。
  把 6 小时用满。" 多代理组织的空闲探测器 prompt:"永远有新工作——不要被先前 CLAIM 的范围
  困住:拿起 /opt/pbench/executable,对没试过的输入运行它,缩小参考与团队实现的差距。"

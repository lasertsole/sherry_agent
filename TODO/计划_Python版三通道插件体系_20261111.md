# 计划：Python 版插件体系（Native + Process/MCP + 事件总线）

- 日期：2026-11-11（修订版 r3，可执行细化）
- 状态：**待评审**
- 来源：参考同类工具的三通道插件架构（Native / Process / MCP）。初版设计了自定义 Process 协议，审视后改为 Process 通道默认用 MCP stdio；r3 基于 Sherry 代码核实细化到可执行，纠正 4 处前提偏差
- 风险等级：**中高** —— 工具层 `_MAIN_TOOLS_BUILDERS` 硬编码，插件化改动 agent 构建主链路；Native 无真隔离（信任制）；权限模型是安全基线

---

## 0. 背景与目标

### 0.1 参考三通道架构 vs Sherry 现状（r3 核实）

| 参考架构通道 | 机制 | Sherry 现状（核实） | 缺口 |
|---|---|---|---|
| Native（编译原生） | 程序集反射、AOT、类型安全、in-process | `channels/registry.py` 已有 importlib + entry_points + `_ensure_deps` + 优先级，**但类型绑定 BaseChannel，只服务 IM 通道**；工具层 `_MAIN_TOOLS_BUILDERS`（**24 个**，`agent/tools/__init__.py:47-72`）硬编码 | 泛化 channels 加载器到工具层（信任制，无真隔离） |
| Process | 子进程 + WS + 跨插件协作 | STT daemon 已验证子进程范式（`daemon_alive`/`spawn_daemon`，**但无 kill_daemon**）；`runtime/hooks.py` 单槽非 pub/sub；**`build_mcp_tools` 已在 `_MAIN_TOOLS_BUILDERS:59`**，MCP 工具已流到 main+子 agent | **Process 通道默认用 MCP stdio**（已有 langchain-mcp-adapters 0.3.0）；缺的是统一插件 manifest + lazy spawn |
| MCP | 标准 MCP | `build_mcp_tools`（`mcp_plugin.py:168`）via langchain-mcp-adapters，双源配置（`plugins/mcp_server/config.json{}` + `APP_HOME/mcp_servers/`） | **已有；Process 通道默认即此** |

### 0.2 r3 纠正的前提偏差

| 偏差 | 实际 |
|---|---|
| ~~25 个 builder~~ | **24 个**（`__init__.py:47-72`） |
| ~~STT 有 kill_daemon 可复用~~ | **kill_daemon 不存在**（`core.py` 只有 daemon_alive + spawn_daemon + _pid_alive），需新建 |
| ~~pyproject 声明 entry_points 组~~ | **pyproject.toml 无任何 entry_points**；`channels` 组在 registry.py:121 被引用但从未声明（死代码）；`sherry.tools.plugins` 组不存在，需创建 |
| ~~build_mcp_tools 待接入~~ | **已在 `_MAIN_TOOLS_BUILDERS:59`**，MCP 工具已流到 main+子 agent；Process 通道不是"接入 MCP"而是"统一插件 manifest + lazy spawn" |

### 0.3 修订要点（审视结论）

| 初版假设 | 审视纠正 |
|---|---|
| Process 需自定义 JSON-RPC 协议 | MCP inputSchema = JSON Schema = BaseTool args_schema，等价。不做跨插件 RPC 时 MCP stdio 完全覆盖。自定义协议仅在事件总线 push 通道时才有意义 |
| Native 能用 `permissions.network:false` 限制网络 | in-process 共享主进程，Python 层无法真阻止联网。Native 是**信任制**（同 pip 包），不是沙箱 |
| 工具发现可"lazy spawn（首次 tool_call 才起）" | `build_main_tools()` 必须返回完整工具列表给 LLM，拿列表就得 spawn 或有静态声明。改为 **manifest 静态声明工具 schema**，lazy spawn 到首次 call |
| PluginContext 可暴露 hooks 注册句柄 | `runtime/hooks.py` 是 last-writer-wins 单槽（`_registry: dict[str, Callable]`，`hooks.py:129`），给插件 register 权限 = 让第三方覆盖 `MAYBE_TRIGGER_AUTO_TURN` 等关键 seam。**不暴露 hooks 给插件** |
| `_ensure_deps` 装主环境是"后续优化" | 一个插件要求 `numpy<2` 能让整个 Sherry 崩。**装插件 venv 是 P0** |

### 0.4 可复用零件（r3 核实）

| 零件 | 位置 | 复用方向 |
|---|---|---|
| 目录式插件加载器 | `channels/registry.py`（importlib spec_from_file_location + `_ensure_deps` + 优先级 + entry_points(group="channels")） | Native 通道泛化 |
| MCP 接入 | `agent/tools/mcp_plugin.py::build_mcp_tools` + `scan_mcp_servers` + `MultiServerMCPClient`（`mcp_plugin.py:180-189`） | Process 通道默认即此，扩展为 lazy |
| 子进程 daemon 范式 | STT `daemon_alive`/`spawn_daemon`/`_pid_alive`（`scripts/core.py:46-111`），**无 kill_daemon** | Process 通道 spawn + 新建 kill_daemon |
| 工具基类 | `langchain_core.tools.BaseTool` | 插件工具统一产出 |
| 工具组装入口 | `agent/tools/__init__.py::build_main_tools()`（`:75`，`tool_flatten(_MAIN_TOOLS_BUILDERS)`） | 改为硬编码 + 插件合并 |
| 子 agent 工具继承 | `child_agent_factory.py::_assemble_child_tools:236`（默认 `build_main_tools()`） | 插件工具经 build_main_tools 自动流到子 agent |

### 0.5 目标

1. **Native 通道**：第三方 Python 包通过 entry_points 注册工具插件，in-process 加载，formalize 现有硬编码 builder。信任制安全模型
2. **Process 通道**：默认用 MCP stdio（第三方用任意语言写 MCP server 作为插件）；统一 manifest 静态声明工具 schema + lazy spawn
3. **事件总线（可选）**：插件间 pub/sub 协作，升级 `runtime/hooks.py` 为多订阅者（不动 hooks.py，新建 event_bus.py）；落地后才引入自定义协议
4. **权限模型**：Native = 信任制；Process = OS 级隔离 + client 层路径校验
5. **工具发现**：manifest 静态声明工具 schema，lazy spawn 到首次调用

### 0.6 不在本次范围

- MCP 通道（已有，Process 默认复用）
- 参考架构的集群授权 / 多租户 / 应用商店（本地单用户不需要）
- 参考架构的源生成器（Python 动态语言，Pydantic/dataclass 运行时校验替代）
- 插件→插件直接 RPC（只做事件总线 pub/sub）

## 方向一：Process 通道（默认 MCP stdio，第一优先）

### 1.1 核心思路

Process 通道 = **第三方用任意语言写一个 MCP server，Sherry 作为 MCP client 加载它**。现有 `build_mcp_tools` 已能做这个，但只读 `plugins/mcp_server/config.json{}` + `APP_HOME/mcp_servers/`。需要的是**统一插件 manifest**：让一个第三方插件包声明工具 schema（静态，不 spawn 就能给 LLM 工具列表）+ MCP server 启动配置，调用时才 lazy spawn。

### 1.2 插件目录结构

```
plugins/tools/<name>/
  ├── manifest.json     # channel: "native" | "process"；工具 schema 静态声明
  ├── core.py           # Native: 实现 SherryToolPlugin 协议
  ├── entry.<ext>       # Process: MCP server 入口（.py/.js/...）
  └── requirements.txt  # Native 用（装插件 venv）
```

### 1.3 manifest.json schema（Pydantic 校验）

```python
# agent/tools/plugins/manifest.py
class ToolSchema(BaseModel):
    name: str
    description: str
    inputSchema: dict          # JSON Schema，等价 BaseTool args_schema

class Permissions(BaseModel):
    paths: list[str] = []      # "read:./project/**", "write:./project/output/**"
    requires_hitl: list[str] = []  # 工具名 glob，调用前走 HITL

class ToolManifest(BaseModel):
    name: str
    channel: Literal["native", "process"]
    tools: list[ToolSchema]    # 静态声明，不 spawn 就能给 LLM 工具列表
    permissions: Permissions = Permissions()
    # Process 专用
    mcp: McpServerConfig | None = None
    # Native 专用
    module: str | None = None  # "core.py" 内的 SherryToolPlugin 入口模块

class McpServerConfig(BaseModel):
    transport: Literal["stdio"] = "stdio"
    command: list[str]         # ["python", "$here/entry.py"]
    env: dict[str, str] = {}
    initialization_options: dict | None = None
```

`$here` 占位符解析为插件目录（复用 `mcp_plugin.py::_resolve_placeholders`，`:132`）。

> Process 通道的 `permissions.network` **不声明**——MCP server 是独立进程，OS 级隔离，网络由 OS 管。

### 1.5 Process(MCP) lazy wrapper

```python
# agent/tools/plugins/mcp_lazy.py
class LazyMcpTool(BaseTool):
    """从 manifest 静态 schema 构造；invoke 时才 spawn MCP server + 连接 + 调用。"""
    name: str
    description: str
    args_schema: type[BaseModel]  # 从 inputSchema 构造
    _manifest: ToolManifest
    _session_id: str

    def _run(self, **kwargs):
        return self._invoke(kwargs)
    async def _arun(self, **kwargs):
        return await self._ainvoke(kwargs)

    def _invoke(self, args):
        # 1. spawn MCP server（复用 daemon 骨架 + pid + health + atexit kill）
        # 2. MultiServerMCPClient({name: spec}) → get_tools() → 找同名 tool
        # 3. 调用，返回结果
        # 4. fail-open：spawn/连接/调用失败返回 error string
        ...
```

- spawn 复用 STT daemon 范式（`daemon_alive` 检活 → `spawn_daemon` 启动）+ **新建 kill_daemon**（见 §1.8）
- 复用 `mcp_plugin.py` 的 `MultiServerMCPClient` 连接逻辑（`:180-189`）
- 单插件独立子进程，崩了 fail-open（该工具返回 error）

### 1.6 并入 build_main_tools

```python
# agent/tools/__init__.py，build_main_tools 改为：
def build_main_tools() -> list[BaseTool]:
    return tool_flatten(_MAIN_TOOLS_BUILDERS) + _plugin_tool_builders()

def _plugin_tool_builders() -> list[BaseTool]:
    """从 tool_plugin_registry 取静态 schema 构造的 BaseTool 列表。"""
    from agent.tools.plugins.registry import get_tool_plugins
    from agent.tools.plugins.mcp_lazy import LazyMcpTool
    from agent.tools.plugins.native_loader import load_native_plugin
    tools = []
    for manifest in get_tool_plugins():
        if manifest.channel == "process":
            for t in manifest.tools:
                tools.append(LazyMcpTool.from_manifest(manifest, t))
        elif manifest.channel == "native":
            tools.extend(load_native_plugin(manifest))  # 见方向二
    return tools
```

- `_MAIN_TOOLS_BUILDERS`（24 个）保持硬编码不变
- 插件工具追加在后面
- 经 `build_main_tools()` 自动流到子 agent（`_assemble_child_tools:236` 默认继承）
- `get_tool_plugins()` 进程级缓存，启动扫一次

### 1.7 生命周期

- 启动：`scan_tool_plugins()` 扫 manifest（不 spawn）
- 首次 tool_call：lazy spawn 对应插件 MCP server
- atexit kill 所有已 spawn 的插件子进程；主进程崩溃时 pid 残留下次启动清理孤儿（扫 pid 文件 + `_pid_alive` 检活 + kill）
- 可选空闲超时自杀（`PLUGIN_DAEMON_IDLE_TIMEOUT_S`）

### 1.8 daemon 公共骨架（含新建 kill_daemon）

```python
# agent/tools/pub_base/daemon.py（新建，与"内存优化计划"阶段 0 共享）
def daemon_alive(port: int, health_path: str = "/healthy", timeout: float = 2.0) -> bool: ...
def spawn_daemon(command: list[str], pid_file: Path, *, cwd=None, env=None) -> int: ...
def kill_daemon(pid_file: Path) -> bool:
    """读 pid → _pid_alive 则 terminate → kill；删 pid 文件。fail-open。"""
    ...
def reap_orphans(pid_dir: Path) -> int:
    """启动时扫 pid_dir，kill 所有 stale pid（主进程崩溃残留）。"""
    ...
```

STT 的 `daemon_alive`/`spawn_daemon` 改为复用此骨架（行为不变，回归测试覆盖）。STT 和插件 Process 通道共用。

### 1.9 权限模型

**Process 通道**（子进程）：
- OS 级隔离，插件崩了不影响主进程
- client 层校验：`LazyMcpTool._invoke` 前按 `permissions.paths` 校验 args 里的路径（持 PathGuard 实例）
- `requires_hitl` 的工具调用前走 HITL 中断
- 未声明 permissions 默认 deny-all

### 1.10 风险与缓解

| 风险 | 缓解 |
|---|---|
| 子进程崩溃 | 单插件隔离，fail-open 返回 error |
| MCP server 启动慢 | lazy spawn（首次 call 才起）+ 启动握手超时 |
| manifest schema 与运行时漂移 | 可选启动校验（默认 off）；调用时 MCP list_tools 不匹配则 warn |
| 孤儿子进程残留 | pid 文件 + reap_orphans 启动清理 + atexit kill |
| N 个 Process 插件内存（每个解释器 ~30-50MB） | lazy spawn + 空闲自杀（见跨计划说明） |

### 1.11 验证

- 单元测试：`tests/agent/tools/plugins/test_mcp_lazy.py`（manifest 静态构造 + mock spawn）
- 集成测试：写最小 MCP server（`plugins/tools/echo/entry.py`，echo 工具）→ 扫 manifest → LLM 看到工具 → 调用 → spawn → 验证结果
- 隔离测试：杀插件子进程 → 主进程和 turn 不受影响（fail-open）
- lazy 测试：未调用的插件不 spawn（无子进程）
- daemon 骨架测试：`tests/agent/tools/pub_base/test_daemon.py`（alive/spawn/kill/reap_orphans）
- 回归：`uv run pytest tests/agent/tools -q` 全过（现有 24 工具不变）

## 方向二：Native 通道（in-process Python 模块，第二优先）

### 2.1 信任制框架

```python
# agent/tools/plugins/protocol.py
class SherryToolPlugin(Protocol):
    def tools(self) -> list[BaseTool]: ...
    def on_load(self, context: PluginContext) -> None: ...   # 可选
    def on_unload(self) -> None: ...                          # 可选

class PluginContext:
    """受控上下文，不含 hooks 注册句柄。"""
    session_id: str
    workspace_root: Path
    event_bus: "EventBus | None"  # 方向三落地后接入
    # 不暴露 runtime/hooks.py register
```

### 2.1b 装饰器声明 + 自动生成 manifest + self-test（借鉴 Native Generator）

同类工具用 Roslyn 源生成器从 Attribute 声明自动生成路由/序列化/manifest + 编译期诊断 + 独立调试器。Python 没有源生成器，但等价物是**装饰器声明 → 自动生成 manifest + 启动时静态校验 + `--self-test` 验证**：

```python
# agent/tools/plugins/decorators.py（新建）

@sherry_plugin(name="my-plugin", version="1.0", risk_level="low", idempotent=False,
               capabilities=["host.llm.invoke.v1"])
class MyPlugin(SherryToolPlugin):
    @sherry_tool(name="echo", description="Echo input",
                 idempotent=True, risk_level="low")
    def echo(self, text: str) -> str:
        return text

    @sherry_tool(name="send_email", description="Send email",
                 idempotent=False, risk_level="high")
    def send_email(self, to: str, subject: str, body: str) -> str:
        ...
```

**装饰器 → manifest 自动生成**：
- `@sherry_plugin` + `@sherry_tool` 装饰器在模块加载时收集元数据 → 自动生成 `manifest.json`（无需手写）
- 工具的 `inputSchema` 从函数签名 + type hints 自动推断（Pydantic → JSON Schema）
- `risk_level`/`idempotent`/`capabilities` 声明进 manifest（对接宿主能力授权计划 + LLM requestId 幂等计划）

**启动时静态校验（等价编译期诊断）**：
- 插件加载时校验：工具名冲突、参数类型不支持、schema 合法、risk_level 合法值
- 校验失败 → 插件不加载 + 错误日志（不崩溃主进程）
- 比运行时才发现问题强

**`--self-test` 模式（等价独立调试器 REPL）**：
```bash
python -m agent.tools.plugins.self_test plugins/tools/my-plugin/
# 不进宿主，加载插件 → 每个工具调一次（用示例参数）→ 报告成功/失败
```
- 开发者不用启动完整 Sherry 就能验证插件每个工具能跑
- 参照 Madorin 的 `dotnet run -- --self-test`

**与手写 manifest 的关系**：装饰器和手写 manifest.json **二选一**——装饰器自动生成 manifest，或开发者手写 manifest.json。装饰器路径更适合 Python 插件开发者（少写一份文档+清单+运行时三套漂移）。手写路径保留给 Process 插件（MCP server，非 Python）。

### 2.2 Native 加载器（泛化 channels/registry.py）

```python
# agent/tools/plugins/native_loader.py
def load_native_plugin(manifest: ToolManifest) -> list[BaseTool]:
    """参照 channels/registry.py::load_channel_class 泛化。"""
    plugin_dir = _plugin_dir(manifest.name)
    _ensure_deps(plugin_dir, manifest.name)  # 复用 channels/deps.py，装插件独立 venv（P0）
    module = _load_module(f"plugins.tools.{manifest.name}", plugin_dir / "core.py")
    plugin_cls = _find_subclass(module, SherryToolPlugin)
    instance = plugin_cls()
    context = PluginContext(...)
    if hasattr(instance, "on_load"): instance.on_load(context)
    _register_atexit_unload(manifest.name, instance)  # atexit 调 on_unload
    return instance.tools()
```

- `_ensure_deps` 复用 `channels/deps.py::install_requirements`（`uv pip install`，frozen 跳过）
- entry_points 发现：`entry_points(group="sherry.tools.plugins")`（**需在 pyproject.toml 声明，见 §2.4**）

### 2.3 依赖隔离（P0）

- 每个插件独立 venv（`APP_HOME/plugins_venv/<name>/`），`_ensure_deps` 用 `uv pip install --python <plugin_venv>` 装
- 主进程 sys.path 注入插件 venv site-packages（隔离，不污染主环境）
- frozen 打包态跳过 deps（参照 channels）

### 2.4 entry_points 声明（pyproject.toml，r3 新增）

```toml
# pyproject.toml（当前无任何 entry_points，r3 创建）
[project.entry-points."sherry.tools.plugins"]
# 第三方包在此声明，例：
# my_plugin = "my_plugin:MyPlugin"

[project.entry-points."channels"]
# channels/registry.py:121 已引用但从未声明，r3 补上（即便现在只有内置 qq）
```

### 2.5 风险与缓解

| 风险 | 缓解 |
|---|---|
| in-process 插件崩溃拖垮主进程 | 接受（Native 本质代价）；文档明确 Native=信任制，安全敏感用 Process |
| 第三方 import 副作用（读 .env/联网） | 无法进程内阻止——信任制，文档明确 |
| 依赖装主环境导致版本冲突 | P0 装插件独立 venv |
| 启动慢 | lazy 加载（首次用工具才 load） |

### 2.6 验证

- 单元测试：`tests/agent/tools/plugins/test_native_loader.py`
- 单元测试：`tests/agent/tools/plugins/test_decorators.py`（`@sherry_tool` → manifest 自动生成；type hints → inputSchema；risk_level/idempotent 声明进 manifest）
- 单元测试：`tests/agent/tools/plugins/test_self_test.py`（`--self-test` 模式：不进宿主验证每个工具；工具名冲突/schema 非法 → 报错）
- 集成测试：pip install entry_points 注册的插件包 → 启动 → 工具出现
- 依赖隔离测试：插件要求 `numpy<2`，主环境 numpy>=2 → 验证插件用自己 venv，主进程不受影响
- 回归：现有 24 工具不变

## 方向三：事件总线（可选/后置，自定义协议的前提）

### 3.1 现状

`runtime/hooks.py`（`:129-139`）是单槽 last-writer-wins（`_registry: dict[str, Callable]`，`register` 覆盖式），不是 pub/sub。用途是打破 `agent <-> server` 导入环（11 个硬编码 hook 名常量，`:117-127`）。**无插件 hook 表面**。

### 3.2 目标

新建 `runtime/event_bus.py`（**不动 hooks.py**）：多订阅者 pub/sub，进程级单例。Native 插件直接订阅；Process 插件经协议桥接。**只有事件总线落地后，Process 通道才需要超越 MCP stdio 的自定义协议**（main→plugin push 事件）。

### 3.3 实施

```python
# runtime/event_bus.py（新建）
class EventBus:
    def subscribe(self, event: str, handler: Callable) -> str: ...  # 返回 sub_id
    def unsubscribe(self, sub_id: str) -> None: ...
    def publish(self, event: str, payload: dict) -> None: ...  # 每个 handler try/except 隔离

event_bus = EventBus()  # 进程级单例
```

- 事件 schema 用 Pydantic/dataclass（替代静态源生成器）
- 内置事件：`tool.called`/`tool.finished`/`session.activated`/`memory.written`/`subagent.completed`
- 现有代码已有 hook/trajectory 调用，加 `event_bus.publish` 是增量
- Process 插件事件桥接（此时才引入自定义协议扩展）：MCP stdio 是请求-响应不支持 push，需要事件的插件起 WS 通道（loopback）或轮询（MVP）
- manifest 声明 `events: {subscribe: [...], publish: [...]}`，未声明不允许

## 跨计划说明：子进程叠加的总内存账

本计划方向一（Process 插件）和"内存优化计划"方向一/二（embed/LLM daemon）都在加子进程。完成后进程拓扑：

```
主进程 + embed daemon(条件) + LLM daemon(条件) + N 个 Process 插件子进程 + STT daemon
```

每个 Python 子进程解释器基线 ~30-50MB。**这些子进程是"主进程瘦身 + 隔离增强"的代价，不是"总内存下降"**。缓解：
- Process 插件 lazy spawn（不用不启动）+ 空闲自杀
- embed/LLM daemon 带空闲自杀
- 用户真在意总内存时，优先用 Native 通道而非 Process

**诚实定位**：Process 通道优化的是隔离和安全，不是总内存。

## 整体验收标准

1. 一个第三方 Process 插件（MCP server，任意语言）被 Sherry 发现、LLM 看到工具（不 spawn）、调用时 lazy spawn、返回结果
2. 杀插件子进程不影响主进程和 turn（fail-open）
3. 未调用的插件不 spawn（零子进程开销）
4. 一个第三方 Native 插件（Python 包，entry_points）被加载、工具并入 main tools
5. Native 插件依赖装在插件独立 venv，不污染主环境（`numpy<2` 测试）
6. Native 信任制安全模型文档明确（不假装 network 限制）
7. daemon 骨架含 kill_daemon + reap_orphans，STT 改用骨架行为不变
8. pyproject 声明 entry_points 组
9. 现有 24 工具回归不变（`tests/agent/tools` 全过）
10. （如做事件总线）插件订阅内置事件收到 payload，handler 异常不传播；hooks.py 行为不变

## Kill criteria

- **Native 通道**：若第三方插件崩溃拖垮主进程频发（in-process 无隔离的代价超预期），Native 通道后置，只保留 Process(MCP) 通道——安全敏感场景全走 MCP 隔离
- **Process 通道**：若 MCP lazy spawn + manifest 静态 schema 的实现复杂度超预期（manifest 与运行时漂移难收敛），降级为"只读 MCP config.json（现有 `build_mcp_tools`）+ 不做统一 manifest"（现有 MCP 能力不增强，但不新建 manifest 层）
- **事件总线（方向三）**：若插件间事件联动需求低（多数插件是独立请求-响应不需 pub/sub），方向三无限期后置——Process 通道默认 MCP stdio 不依赖事件总线
- **entry_points 声明**：若 pyproject entry_points 声明导致打包/发布问题（frozen 态兼容），改为"只支持目录式发现（plugins/tools/<name>/），不支持 entry_points 包发现"

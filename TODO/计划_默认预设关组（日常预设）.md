# 计划：默认预设关组（日常预设）

- 建档日期：2026-10-24
- 状态：**待评审 / 未开工**
- 目标：新增一个默认预设“日常”，默认关闭 `tasks` + `subagents` 两组工具；保留“全量”作为完整能力入口。
- 关联：`TODO/计划_工具面上下文瘦身（两档方案）.md`（本方案落地其“默认/会话按组关停”）

## 0. 结论先行

1. **不改“全量”，新增默认预设 `daily`（日常）**。全量保持“所有工具都开”的语义；日常负责把默认工具面降下来。
2. 日常预设关掉 `tasks` + `subagents`，默认工具面从 **34 → 20 个工具、8,313 → 4,280 tok**（浏览器开启时）；浏览器关闭时 **33 → 19、7,864 → 3,831**。
3. 节省 **14 个工具、4,033 tok**；再排除 `taskflow` / `todolist` / `ulw-execute` 三个技能索引约 **400 tok**。运行守则里的任务编排段落还要裁掉，按语言另计。
4. **只关工具不改提示层会破坏功能**：`TaskIntentMiddleware`、todo/taskflow 提醒、`PlanContinuationEnforcer` 三处必须做工具可用性判断，否则模型会收到指向不存在工具的指令。
5. 旧会话不迁移；新会话默认日常。需要多步编排时选“编程助手”或“全量”。

## 1. 口径与实测

### 1.1 口径说明

本文的数字使用 `pub.func.estimate_tokens.estimate_json_tokens`，与 `server/service/context_usage_service.py` 的面板口径一致
（`chars_per_token_json = 7`）。

`TODO/计划_工具面上下文瘦身（两档方案）.md` 里的 11,274 / 11,953 是早期 prose 口径（`chars_per_token = 4`），对
JSON schema 会高估约 1.7 倍；**两套数字不能直接相加或对比**。旧计划已在本轮追加口径说明。

## 2. 日常预设定义

### 2.1 预设元数据

- `BuiltinPresetId` 新增 `'daily'`。
- `BUILTIN_PRESETS` 新增“日常”条目，使用现有 `defaultBadge` 标记为默认；`全量` 去掉默认 badge。
- `DEFAULT_PRESET_ID = 'daily'`。
- 新会话对话框默认选中日常；用户仍可选“全量”或“编程助手”。

### 2.2 agent block

在 `client/app/composables/persona-catalog.ts` 的 `builtinAgentConfig()` 增加 daily 分支：

```ts
tools = facts.tools
  .filter(tool => !ORCHESTRATION_TOOL_GROUPS.includes(tool.group))
  .map(tool => tool.name);

skills = allSkills
  .filter(skill => !ORCHESTRATION_SKILLS.includes(skill.name))
  .map(skill => skill.name);
```

- `ORCHESTRATION_TOOL_GROUPS = ['tasks', 'subagents']`（把现有 `COMPANION_DISABLED_TOOL_GROUPS` 泛化命名）。
- `ORCHESTRATION_SKILLS = ['taskflow', 'todolist', 'ulw-execute']`。
- 必选工具不在被关的两组里；服务端的 `REQUIRED_TOOLS` 校验和 `enabled_tool_names()` 兜底不受影响。
- 保留 `memory`、`files`、`terminal`、`skills`、`interaction`、`plan_mode`、`web`、`browser`。
- `middleware_options` 保持默认（Summarization memory nudge 开启）。

### 2.3 人格与运行守则

- `AGENTS.md`：复用 `stripTaskSections()`（现为情感陪伴使用），删除任务编排段落；四种语言都要验证匹配。
- `SOUL.md` / `USER.md`：保持完整，不做情感陪伴的恋爱关系行裁剪。
- 角色：继续使用默认的橘雪莉，不新建人格。
- `builtinPayload()` 的 `named` / `content` 分支把 `daily` 与 `companion` / `sherry` 并列处理；日常只裁 AGENTS，不裁 SOUL。

### 2.4 i18n 与 UI

- 中央 locale JSON 四语言新增 `config.persona.preset.builtinDailyName`（日常 / Daily / 毎日 / 일상）。
- `PersonaPanel.vue` 的四份组件内联 `<i18n>` 块同步新增该 key（组件内联块与中央 locale 是两套，缺一不可）。
- 新会话对话框的日常卡片增加一行说明：“任务编排与子代理默认关闭，可在会话中开启。”
- 预设面板正确显示日常的工具组为未选中（`BULK_ONLY_GROUPS` 的 tasks/subagents 整组关）。

## 3. 必须同时做的护栏

### 3.1 TaskIntentMiddleware（必须）

`agent/middlewares/task_intent/core.py` 的 `_TASK_STEERING_PROMPT` 明确要求 `todowrite`、`taskflow_step`、`sessions_spawn`。
日常预设若继续启用它，模型会收到“先建 todo、再委派子代理”的指令，但工具面里没有这些工具。

方案：在 `abefore_model` 进入检测前，用 `agent.middlewares.tool_selection.core.enabled_tool_names(session_id)` 判断编排工具
是否可用；不可用直接返回 `None`。`enabled_tool_names()` 返回 `None`（全量）时视为可用。

推荐做可用性判断而不是简单关闭中间件：用户以后手动打开任务组时，steering 会自动恢复。

### 3.2 Todo / TaskFlow 提醒

`agent/middlewares/reminder_catalog/sources.py` 的 `todo_block`、`taskflow_status` 对已有计划的会话仍会注入状态。
新会话没有 todo/flow，不会触发；但把日常预设应用到旧会话时会留下一个无法操作的看板。

方案：两个 source 的 builder 先检查 tasks 工具是否启用，未启用返回空。不要自动清空 todo/flow，避免破坏用户状态。

### 3.3 PlanContinuationEnforcer

`agent/middlewares/todo_continuation/core.py` 的续跑门在旧会话已有 todo/flow 时会继续自动开 turn，但模型已经没有任务工具。

方案：在 gate 里加同样的可用性判断（`tasks` 工具不可用时不再续跑），或在日常预设的 `middlewares_disabled` 里关掉它。
推荐加 gate；预设关闭只作为第一版的简化实现。

### 3.4 简化实现（可选）

如果第一版不想改三处后端，可以只把 `TaskIntentMiddleware` + `PlanContinuationEnforcer` 写进日常预设的
`middlewares_disabled`。代价：用户以后手动打开任务组时，这两个中间件不会自动回来；且 3.2 的旧会话看板仍需处理。
因此推荐至少做 3.1，3.2/3.3 视改动量决定是否同批。

## 4. 迁移、回滚与影响面

- **旧会话不受影响**：它们保存自己的 `AGENT_CONFIG`；绑定 `sherry` 的会话仍是全量。
- **新会话默认日常**：需要多步编排时选“编程助手”（全量 minus memory）或“全量”。
- **回滚**：把 `DEFAULT_PRESET_ID` 改回 `'sherry'` 即可，无数据迁移。
- **侧边辅助会话**：复制父会话配置；父会话日常则辅助会话也日常。
- **cron / 后端直接创建的会话**：不经过新会话对话框，第一版仍按全量处理；本方案不改变服务端默认。
- **旧会话切换到日常**：若已有未完成 todo/flow，建议在应用前提示“任务编排工具将关闭”；不自动清空状态，用户切回全量后恢复。

## 7. 风险与取舍

- **默认失去规划与委派**：多步骤、跨文件工作会退化。缓解：明确提示 + 保留“编程助手/全量”入口。
- **名称**：推荐“日常”，不叫“轻量”；“轻量”听起来像功能残缺。
- **旧会话切换**：已有 todo/flow 会变成只读状态；不自动清理，切回全量恢复。
- **显式工具列表是快照**：以后新增的工具，新会话按当前 catalog 生成会包含；旧会话需重新应用预设。与现有受限预设一致。
- **收益量级**：4–5k tok 在 200K 上下文里约 3–4%，真正收益是更小的工具面、更少的错误选择；不要把它当作解决上下文问题的唯一手段。
- **不要顺手关 browser**：只省 449 tok，伤功能，不划算。

## 8. 备选方案

| 方案 | 改动 | 省 token | 问题 |
|---|---|---:|---|
| A. 直接改“全量” | 最小 | 4,033 | “全量”名不副实；旧会话重应用会突然丢能力；测试/文档语义全改 |
| B. 新增“日常”默认（推荐） | 中 | 4,033 + 400 | 多一个预设、四语文案和 UI 提示 |
| C. 只关 subagents | 小 | 1,224 | TaskIntent / AGENTS 仍要求委派，需改一部分 steering |
| D. 默认不动，加工具栏精简开关 | 小 | 0（默认） | 不解决默认会话成本 |
| E. 拆 tasks 为“轻量计划”+“TaskFlow” | 大 | ~1.7k | 需要新分组 + 重写编排 doctrine，适合以后单独评估 |

## 9. 不做什么

- 不引入通用 `tool(name, args)` 派发器。
- 不自动清空旧会话的 todo / TaskFlow 状态。
- 不改变 cron / 后端直接创建会话的默认工具面（本方案只覆盖新会话对话框路径）。
- 不默认关闭 browser、plan_mode、memory、web 等小收益组。
- 不在本轮实现动态技能暴露 / 按需加载工具。

## 总体要求：配置文件缺失时自动从模板创建

所有前端给用户配置的文件，一旦在 `APP_HOME`（可写主目录）中检查到不存在，
必须自动从 bundle 内对应的模板文件复制创建，不得报错或显示空面板。

| 配置文件（APP_HOME 下） | 模板文件（bundle 内 `_CODE_ROOT` 下） | 播种逻辑位置 | 当前状态 |
|------------------------|--------------------------------------|-------------|---------|
| `sherry.jsonc` | `sherry.jsonc`（shipped，tracked） | `config/sherry_settings.py:33-41` | 逻辑已有，但因 APP_HOME 解析错误被跳过 |
| `.env` | `.env`（shipped，tracked） | `config/path.py:65-74` | 逻辑已有，且 `path.py` 的 APP_HOME 解析正确 → **正常工作** |
| `.models` | `.models.example` | `config/models_settings.py:314-338` `ensure_models_config_file()` | 逻辑已有，但因 APP_HOME 解析错误写入只读目录失败（`OSError` 被静默吞掉） |
| `.network` | `.network.example` | `config/network_settings.py:204-215` `ensure_network_config_file()` | 同 `.models` |

模板文件均已确认被 PyInstaller 打包（`packaging/build_backend.py:48-53` 的 `DATA` 列表）。

**根因**：`config/sherry_settings.py`、`config/models_settings.py`、
`config/network_settings.py` 三个模块各自独立解析 `APP_HOME`，只读 `SHERRY_HOME`
环境变量、不读 `--sherry-home` CLI 参数。打包版 Tauri shell 只传 CLI 参数不设环境变量，
导致三个模块的 `APP_HOME` 回退到只读 bundle 内部，播种条件
`APP_HOME != _CODE_ROOT` 为 `False`（跳过）或写入只读目录失败（`OSError` 被吞掉）。
`config/path.py` 的解析正确（`.env` 正常工作），但另外三个模块没有复用它。

**修复要点**：三个模块的 `APP_HOME` 解析改为与 `config/path.py` 一（先扫 `--sherry-home`
CLI 参数，再回退环境变量）。修好后已有的播种逻辑自动生效，无需新增播种代码。
详见问题 1/2/2b/4 的具体方案。

## 问题 1：系统配置面板报 `请求失败 /sherry-config (HTTP 500)`

### 现象

顶部菜单栏 → 系统配置，打开后面板加载即报 `请求失败 /sherry-config (HTTP 500)`，
关闭面板时也会看到该 toast（实际是打开 sherry 配置 tab 时触发的 GET 请求失败）。

### 根因

**`config/sherry_settings.py:29` 只读 `SHERRY_HOME` 环境变量，不读 `--sherry-home` CLI 参数。**

打包版 Tauri shell 通过 **命令行参数** `--sherry-home <app-data-dir>` 传递可写主目录，
**刻意不设 `SHERRY_HOME` 环境变量**（见 `client/src-tauri/src/services/python_process.rs`，
以及 `packaging/backend_entry.py` 的文档说明）。

- `config/path.py:33-44` 的 `_resolve_sherry_home_raw()` 正确地先扫 `sys.argv` 的
  `--sherry-home`，再回退环境变量 → 所以 `.env`、sessions、memory、workspace、logs
  都正确落在可写的 app-data 目录。
- 但 `config/sherry_settings.py:29` 用 `os.environ.get("SHERRY_HOME", "").strip()`
  → 打包版环境变量为空 → `APP_HOME` 回退到 `_CODE_ROOT`（PyInstaller 只读 bundle 内部）。

后果链：
1. `SHERRY_CONFIG_PATH = APP_HOME / "sherry.jsonc"` 指向只读 bundle 内部路径。
2. 首次启动的 seeding 分支 `if APP_HOME != _CODE_ROOT and not SHERRY_CONFIG_PATH.exists()`
   条件为 `False`（APP_HOME == _CODE_ROOT），**跳过播种**。
3. bundle 内部可能不存在 `sherry.jsonc`（取决于 PyInstaller 布局），
   `read_sherry_config()` 抛 `FileNotFoundError`。
4. `server/trigger/http/sherry_config.py:11-18` 的 GET handler **无 try/except**，
   异常直传 Robyn → HTTP 500。

### 修复方案

**方案 A（推荐，最小改动）**：在 `config/sherry_settings.py`、`config/models_settings.py`、
`config/network_settings.py` 三个模块中，将 `APP_HOME` 的解析逻辑改为与 `config/path.py`
一致——先扫 `sys.argv` 的 `--sherry-home`，再回退环境变量。

由于 `config/path.py:9` 在模块顶部 `from config.sherry_settings import get_sherry_setting`，
存在导入顺序依赖（`sherry_settings` 先于 `path` 完成 import），因此 **不能直接
`from config.path import APP_HOME`**（循环导入）。需在各自模块内复制 `_cli_arg` +
`_resolve_sherry_home_raw` 这两个小函数（各约 15 行），或抽取到一个无依赖的
`config/_home.py` 共享模块。

示例（`config/sherry_settings.py` 改动）：

```python
# 替换第 28-30 行
_CODE_ROOT = Path(__file__).resolve().parents[1]

def _cli_arg(name: str) -> str | None:
    import sys
    argv = sys.argv
    for index, arg in enumerate(argv):
        if arg == name and index + 1 < len(argv):
            return argv[index + 1]
        if arg.startswith(f"{name}="):
            return arg.split("=", 1)[1]
    return None

def _resolve_app_home_raw() -> str:
    from_cli = _cli_arg("--sherry-home")
    if from_cli and from_cli.strip():
        return from_cli.strip()
    return os.environ.get("SHERRY_HOME", "").strip()

_APP_HOME_RAW = _resolve_app_home_raw()
APP_HOME = Path(_APP_HOME_RAW).expanduser().resolve() if _APP_HOME_RAW else _CODE_ROOT
```

`config/models_settings.py:47-48` 和 `config/network_settings.py:47-48` 同理替换。

**方案 B（防御性）**：`server/trigger/http/sherry_config.py` 的 GET/PUT handler
补上 `try/except (FileNotFoundError, OSError)` 返回结构化错误（如 503 + 错误信息），
避免裸 500。`server/trigger/http/models_config.py` 同理。这是兜底，不替代方案 A。

### 验证

修复后重新打包，首次启动应自动在 app-data 目录播种 `sherry.jsonc`，
GET /sherry-config 返回 200 + 完整配置键。

## 问题 4：应用配置 tab 显示"未找到 sherry.jsonc 文件"

### 现象

顶部菜单栏 → 系统配置 → 应用配置 tab（`config.tabs.sherry`，即 sherry.jsonc 配置页），
面板中央灰色文字"未找到 sherry.jsonc 文件。"。该 tab 和模型配置 tab 是不同页面，
用户在模型配置看到空白/报错，在应用配置看到"未找到"，是两个独立 tab 的两种表现。

### 根因

**同问题 1 根因**（`config/sherry_settings.py:29` 的 APP_HOME 解析缺陷），但前端的表现路径
不同，值得单独说明：

1. GET `/sherry-config` → 500（`read_sherry_config()` 抛 `FileNotFoundError`）。
2. `fetchApi`（`client/app/composables/requestApi.ts:408-417`）捕获 500，**不 re-throw**，
   把 `data` 置为 `null`，仅触发全局 toast（即问题 1 的"请求失败 /sherry-config (HTTP 500)"）。
3. `readSherryConfig`（`client/app/composables/sherryConfig.ts:33`）执行
   `return res || { entries: [] }`，把 `null` 转成**空但合法**的 `{ entries: [] }`，
   **不抛异常**。
4. `loadSherryConfig`（`ConfigPanel.vue:763-779`）的 try 块成功，`sherryEntries = []`，
   `sherryLoadError` 保持空字符串，catch 块（会设红色 `loadError`）**永远不会执行**。
5. 模板渲染逻辑（`ConfigPanel.vue:270-309`）：
   - `sherryLoadError || envLoadError` 为空 → 红色错误块不显示
   - `sherryEntries.length` 为 0 → 不渲染条目编辑器
   - `appConfigGroups.length === 0` → 命中 `v-else-if`，显示灰色
     `config.sherry.noConfigFile` = **"未找到 sherry.jsonc 文件。"**

所以用户看到的是"未找到文件"而非红色"加载失败"，是因为 `fetchApi` + `readSherryConfig`
**两层错误吞咽**把 500 错误转成了"空数据"而非"错误"，面板的空状态兜底文案便被触发。

### 修复方案

**后端**：同问题 1 方案 A（修 `config/sherry_settings.py:29` 的 APP_HOME 解析）。
修好后 GET /sherry-config 返回完整配置条目，面板正常渲染。

**前端（防御性，建议一并修）**：

- `readSherryConfig`（`sherryConfig.ts:33`）不应把 `null` 当作 `{ entries: [] }` 返回，
  应区分"请求失败"和"合法空响应"。可让 `fetchApi` 在 HTTP 失败时抛出异常（或返回一个带
  `error` 标记的对象），`readSherryConfig` 透传，`loadSherryConfig` 的 catch 才能正确设置
  红色 `loadError`。当前实现把网络/服务端错误伪装成了"文件不存在"，对用户排查有误导。
- 至少在 `res === null` 时 log 一条 warn，不要静默返回空。

### 验证

后端修复后，首次启动 sherry.jsonc 在 app-data 目录正确播种，
应用配置 tab 显示完整的应用级配置键（TOKEN_BUDGET_DEFAULT_CAP、TOOL_CALL_TIMEOUT_MINUTES 等）。

## 问题 5：启动时弹出黑色控制台窗口，且关闭应用后端可能残留

### 现象

打包版启动时弹出一个黑色控制台窗口（sherry-backend.exe 的 PyInstaller console），
正常桌面应用不应弹出。关闭 sherry 窗口后，后端进程可能滞留在后台（Task Manager 中仍可见
sherry-backend.exe）。

### 根因 A：黑色控制台窗口

**`client/src-tauri/src/services/python_process.rs:200-226` 的 `spawn_with` 未设
`CREATE_NO_WINDOW` 标志。**

- `main.rs:2` 有 `#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]`，
  Tauri 本体是 GUI 子系统、无控制台。
- 但 `sherry-backend.exe` 是 PyInstaller 默认的 **console 子系统** 二进制（未用
  `--windowed`/`--noconsole` 构建）。
- Windows 上，GUI 进程通过 `Command::spawn()` 启动 console 子进程时，若不设
  `CREATE_NO_WINDOW`（0x08000000），系统会为子进程分配一个新控制台，弹出黑窗。
- `spawn_with` 已设 `.stdout(Stdio::null()).stderr(Stdio::null())`（line 214-215），
  但 **`Stdio::null()` 只抑制输出，不抑制控制台窗口**——只有 `CREATE_NO_WINDOW` 能做到。

全 `src-tauri/src/` 无任何 `creation_flags`/`CREATE_NO_WINDOW`/`CommandExt` 引用。

### 根因 B：后端进程清理不可靠

**`lib.rs:240` 用 `.run(tauri::generate_context!())` 直接运行，无 `RunEvent` 回调，
后端清理仅依赖 `PythonProcessManager` 的 `Drop` 实现。**

- `PythonProcessManager::stop()`（`python_process.rs:229-238`）：`child.kill()` + `child.wait()`，
  逻辑正确。
- `impl Drop for PythonProcessManager`（line 251-254）：调用 `self.stop()`。
- 但 `lib.rs:240` 的 `.run()` 不带闭包，**`RunEvent::ExitRequested` / `RunEvent::Exit`
  从未被观察**。也没有 `.on_window_event(...)` 拦截 `CloseRequested`/`Destroyed`。
- 托盘菜单的"Quit"（`lib.rs:109-112`）调用 `app.exit(0)` 触发 Tauri 关闭，
  但退出路径上无显式 `stop()` 调用——完全依赖 Tauri 销毁 managed state 时触发 `Drop`。
- `Drop` 在正常退出时可能执行，但在硬崩溃、Task Manager 结束进程、或 `app.exit` 跳过
  graceful Drop 时，后端子进程会**成为孤儿**滞留后台。

后端子进程未设 `DETACHED_PROCESS`，是普通子进程——理论上父进程死亡时 Windows 会清理，
但这只在父进程干净退出时可靠，不能作为保障。

### 修复方案

**A. 隐藏控制台窗口**——在 `python_process.rs::spawn_with` 的 `command.spawn()` 之前加：

```rust
#[cfg(target_os = "windows")]
{
    use std::os::windows::process::CommandExt;
    const CREATE_NO_WINDOW: u32 = 0x08000000;
    command.creation_flags(CREATE_NO_WINDOW);
}
```

放在 line 215（`Stdio::null()` 之后、`spawn()` 之前）。`Stdio::null()` 可保留，
两者不冲突。这是消除黑窗的**唯一有效手段**。

> 备选方案：在 `packaging/build_backend.py` 的 PyInstaller 命令加 `--windowed`
> （即 `--noconsole`），让 backend 本身是 GUI 子系统。但 backend 是服务进程，
> 用 `--windowed` 会在某些 PyInstaller 版本下影响 stdin 行为，且 `CREATE_NO_WINDOW`
> 更轻量、不侵入打包流程，**推荐用 `CREATE_NO_WINDOW`**。

**B. 可靠的后端生命周期管理**——将 `lib.rs:240` 的 `.run(context)` 改为
`.build(app)?` + `app.run(|handle, event| ...)`，在退出事件中显式 `stop()`：

```rust
// lib.rs，替换原来的 .run(tauri::generate_context!()).expect(...)
let app = tauri::Builder::default()
    // ...所有 plugin/Invoke/setup 链不变...
    .build(tauri::generate_context!())
    .expect("error while building tauri application");

app.run(|app_handle, event| {
    match event {
        tauri::RunEvent::ExitRequested { .. } | tauri::RunEvent::Exit => {
            if let Some(mgr) = app_handle.try_state::<PythonProcessManager>() {
                mgr.stop();
            }
        }
        _ => {}
    }
});
```

**C. 是否应变为子进程？**——后端已经是 Tauri 的子进程（`Command::spawn()` 创建的是子进程），
问题不在父子关系，而在**退出时没有显式 kill**。`RunEvent::Exit` 回调 + `stop()` 就能解决。
不需要改用 Tauri 的 sidecar 机制（`tauri-plugin-shell`）——那会增加配置复杂度且当前
`Command::spawn` 已够用。

### 验证

- `CREATE_NO_WINDOW`：打包后启动无黑窗弹出。
- `RunEvent` 回调：关闭窗口 / 托盘 Quit / 强制退出后，Task Manager 中
  sherry-backend.exe 随即消失。

## 问题 6：缺少关闭时最小化到托盘的常规功能

### 现象

点击窗口 X 关闭按钮直接关闭窗口，没有"最小化到托盘"的选项。ZCode 有此功能：
关闭时默认隐藏到系统托盘，托盘图标可恢复窗口或完全退出。

### 现状

**sherry 已有托盘基础设施，但缺少关闭拦截逻辑。**

- `client/src-tauri/Cargo.toml:23`：`tauri` 已启用 `"tray-icon"` feature。
- `lib.rs:81-116`：已创建系统托盘（`TrayIconBuilder`），菜单含 Show / Hide / Quit，
  tooltip "EMA AI Agent"，托盘菜单事件已正确处理 show/hide/quit。
- `lib.rs:118-141`：已注册全局快捷键 Alt+Space 切换窗口可见性。
- **但无 `on_window_event` 拦截 `CloseRequested`**——点 X 直接关闭窗口，
  不会 hide-to-tray。托盘菜单的 Quit 是唯一完全退出路径。

### ZCode 参考实现

ZCode（`D:\selfProj\ZCode`，Electron）的 close-to-tray 机制：

- **托盘**（`packages/desktop/src/main/desktopTray.ts`）：`new Tray(icon)` + 上下文菜单
  （打开 / 新建任务 / 退出），单击/双击托盘图标 show 主窗口。
- **关闭拦截**（`desktopWindowLifecycle.ts:395-453` `handleDesktopWindowCloseRequest`）：
  若 `closeToTray` 开关 ON 且托盘就绪 → `win.hide()` + `event.preventDefault()`（静默隐藏，
  无弹窗）；若开关 OFF 且是最后一个窗口 → 弹退出确认对话框（"退出"/"取消"）。
- **退出确认**（`index.ts:1483-1519` `confirmAppQuit`）：仅在 production 且有运行中的
  agent session 时弹确认框，显示"正在进行的会话：N 个，退出后会被中断"。
- **设置开关**：`closeToTrayOnWindows`（boolean，默认 `true`），在设置页提供开关，
  标签"关闭窗口时隐藏到托盘"。无"不再询问"checkbox——单一 boolean 即开关。
- **强制退出标志**：托盘菜单"退出"设 `explicitQuit` 标志后 `app.quit()`，绕过 hide，
  确保完全退出。

### 修复方案

在 `lib.rs` 的 Builder 链上加 `.on_window_event`，拦截主窗口的 `CloseRequested`：

```rust
.on_window_event(|window, event| {
    if let tauri::WindowEvent::CloseRequested { api, .. } = event {
        // 默认行为：隐藏到托盘而非退出（可加设置开关控制）
        // 托盘菜单 Quit 通过 explicit_quit flag 绕过此拦截
        window.hide().unwrap_or_default();
        api.prevent_close();
    }
})
```

需要一个 `explicit_quit` 标志（`AtomicBool`，托盘 Quit 时置 true），
让托盘"退出"能真正退出而非隐藏：

```rust
use std::sync::atomic::{AtomicBool, Ordering};
static EXPLICIT_QUIT: AtomicBool = AtomicBool::new(false);

// 托盘 quit 菜单事件（lib.rs:109-112）改为：
"quit" => {
    EXPLICIT_QUIT.store(true, Ordering::SeqCst);
    app.exit(0);
}

// CloseRequested 拦截改为：
if EXPLICIT_QUIT.load(Ordering::SeqCst) {
    // 放行，真正关闭
} else {
    window.hide().unwrap_or_default();
    api.prevent_close();
}
```

**可选增强（对齐 ZCode）**：
- 加一个设置开关 `closeToTray`（默认 true），存到 Tauri Store 或前端 localStorage，
  在系统配置面板提供"关闭窗口时隐藏到托盘"开关。
- 关闭前若有运行中的会话，弹确认对话框（"退出会中断 N 个进行中的会话，确认退出？"）。
- 托盘图标单击 show/restore 主窗口（当前托盘只有菜单事件，无 click handler——
  可加 `.on_tray_icon_event`）。

### 验证

- 托盘 Show → 窗口恢复。
- 托盘 Quit → 窗口关闭 + 后端退出（配合问题 5 的 `RunEvent::Exit` 清理）。

## 问题 10：自动技能维护间隔天数按钮双击同一个时熄灭

### 现象

技能页"自动技能维护间隔（天）"的天数按钮（1/2/3/4/5），双击同一个已选中的按钮时，
按钮背景色熄灭（变为未选中），并显示"已恢复为默认间隔"。正确行为是双击同一个

```vue

  v-model="autoIntervalDays"
  :options="autoIntervalOptions"
  optionLabel="label"
  optionValue="value"
  :allowEmpty="true"          <!-- 问题所在：允许取消选中 -->
  :disabled="intervalSaving"
  size="small"
  @change="onAutoIntervalChange" />
```

`allowEmpty="true"` 使 PrimeVue 的 `SelectButton` 在点击已选中项时将 model 值置为 `null`
（取消选中）。这触发 `onAutoIntervalChange`（lines 723-750）收到 `value === null`，
走向"恢复默认"分支：

```ts

    value === null

      : t('skills.tabs.autoMaintenanceSaved');
};
```

### 修复方案

将 `SkillsPanel.vue:261` 的 `:allowEmpty="true"` 改为 `:allowEmpty="false"`。

改后点击已选中项不再触发 `null` 取消选中，`onAutoIntervalChange` 始终收到一个
非 null 的数字值，"已恢复为默认间隔"消息不再出现。

- 再次点击同一个按钮 → 保持选中、高亮不变，不显示"已恢复为默认间隔"。

## 问题 7：中间栏悬浮态边缘拉伸需有上限和下限

### 现象

中间栏悬浮态时，鼠标放到窗口边缘可拉伸放大缩小，需要有上限和下限约束。

### 调查结论

**代码中已有完整的上下限约束，且在拖拽过程中实时生效。** 若打包版表现异常，
需排查运行时是否实际命中了该约束逻辑。

**bounds 常量** — `client/app/common/floating-window.ts:90-97`：

```ts
export const FLOATING_RESIZE_WIDTH_MIN_PX = 360;
export const FLOATING_RESIZE_WIDTH_MAX_PX = 1200;
export const FLOATING_RESIZE_HEIGHT_MIN_PX = 260;
export const FLOATING_RESIZE_HEIGHT_MAX_PX = 900;
```

**clamp 函数** — `common/floating-window.ts:111-120`：`clampFloatingSize` 将尺寸约束在
`360–1200 × 260–900`，再被 slot 几何（`slot.width/height - 2*MARGIN(16px)`）进一步收窄。

**拖拽实时 clamp** — `index.vue::moveFloatResize`（lines 791-844），按边分别处理：

- **底边**（lines 799-823）：`rawHeight = startHeight + dy`；低于 260px 时 snap 到
  input-only 条（`resizingCollapsed`）；否则 clamp 到
  `[260, min(900, slot.height - startTop - 16)]`。
- **右边**（lines 825-830）：`maxWidth = min(1200, slot.width - startLeft - 16)`，
  width clamp 到 `[360, maxWidth]`。
- **左边**（lines 831-839）：右边缘固定，left clamp 到
  `[max(16, rightEdge - 1200), rightEdge - 360]`，等效 width 约束 `[360, 1200]`。

**存储** — `chat-float.ts::setSize`（lines 58-61）：仅 `Math.round` + floor 0，
**不重新 clamp**。依赖 `moveFloatResize` 始终 clamp 后的 `resizeDraft` 经
`finishFloatResize`（lines 868-879）提交。当前没有绕过 clamp 的写入路径。

### 可能的运行时问题

约束逻辑本身正确，但以下情况可能导致用户感知"没有上下限"：

1. **grip 未渲染**：三个 grip 均 `v-if="chatFloat.floating"`（`index.vue:110-145`），
   若 `chatFloat.floating` 在某些状态下未正确置 true，grip 不显示，用户无法拉伸。
2. **slot 几何异常**：若 `slot.width` / `slot.height` 计算不正确（如页面布局未稳定时），
   slot cap 可能过大（超过 1200/900 的绝对上限）或过小。
3. **打包版 CSS 差异**：grip 是 3px 宽的薄条（`w-1.5`），若打包后 CSS 未正确加载，
   grip 可能不可见或不可交互。

### 修复方向

若约束确实未生效，排查 `moveFloatResize` 是否被正确调用、`resizeDraft` 是否被
`finishFloatResize` 提交到 `chatFloat.setSize`。若约束生效但用户希望调整上下限值，
修改 `floating-window.ts:90-97` 的四个常量即可。

### 验证

悬浮态下拖拽左/右/底边，窗口尺寸不超出 `360–1200 × 260–900`（且不超出视口）。

  **完全没有 `rightSidebarStore.maximized` 的任何操作。**

- 右侧栏 maximize/restore 联动 watch — `index.vue:1143-1171`：
  ```ts
  const preMaximizeSnapshot = ref<{ leftExpanded: boolean; middleFloating: boolean } | null>(null);
  watch(() => rightSidebarStore.maximized, maximized => {
    if (maximized) {
      preMaximizeSnapshot.value = { leftExpanded: !uiStore.sidebarCollapsed, middleFloating: chatFloat.floating };
      rightSidebarStore.expand?.();
      if (!chatFloat.floating && canFloatChat.value) chatFloat.open();  // 最大化时自动浮起
      return;
    }
    // restore 分支：根据 snapshot 决定 keep-floating 还是 dock
    const snapshot = preMaximizeSnapshot.value;
    if (!snapshot) return;
    preMaximizeSnapshot.value = null;
    const keepFloating = !!snapshot.leftExpanded && !!snapshot.middleFloating && canFloatChat.value;
    if (keepFloating) chatFloat.open();
    else dockChatFloat();
  }, { immediate: true });
  ```
  这个 watch **只在 `rightSidebarStore.maximized` 值变化时触发**。
  `dockChatFloat` 不改 `maximized`，watch 不触发，restore 分支不执行。

- `maximized` 的唯一写入点 — `right-sidebar.ts:330-334`：
  ```ts
  function toggleMaximized(): void {
    maximized.value = !maximized.value;
    if (maximized.value) expand();
  }
  ```
  仅由 `RightSidebar.vue:69` 的 Zoom/restore 按钮调用。

### 后果链

1. 右侧栏最大化 → watch 捕获 snapshot → `chatFloat.open()` 自动浮起中间栏。
2. 用户点击悬浮窗"恢复原样" → `dockChatFloat` → `chatFloat.dock()` → 中间栏 dock。
3. `rightSidebarStore.maximized` 仍为 `true` → watch 不触发 → 右侧栏保持全屏。
4. `preMaximizeSnapshot` 未被消费/清理 → 残留在内存中。
5. dock 后的中间栏被仍在全屏的右侧栏覆盖 → 用户看不到对话区。

### 修复方案

在 `dockChatFloat` 中加入右侧栏 maximize 状态的联动恢复。需注意顺序和
snapshot 协调，避免 watch 的 restore 分支与 `dockChatFloat` 重复执行冲突：

**方案 A（推荐）**：`dockChatFloat` 开头检查 `rightSidebarStore.maximized`，
若为 `true` 则先清除 `preMaximizeSnapshot`（避免 watch restore 分支再次
`dockChatFloat`），再置 `maximized = false`：

```ts
function dockChatFloat(): void {
  // 若右侧栏处于最大化，联动恢复——清除 snapshot 避免 watch 再次 dock
  if (rightSidebarStore.maximized) {
    preMaximizeSnapshot.value = null;       // 阻止 watch restore 分支执行
    rightSidebarStore.maximized = false;    // 触发 watch，但 snapshot 为 null → 直接 return
  }
  chatFloat.dock();
  chatFloat.setCollapsed(false);
  // ... 其余清理逻辑不变 ...
}
```

这样 watch 会因 `maximized` 变 `false` 而触发，但 `preMaximizeSnapshot` 已被
置 `null`，restore 分支 `if (!snapshot) return` 直接返回，不会重复操作。

**方案 B**：不加联动到 `dockChatFloat`，而是在 watch 中监听 `chatFloat.floating`
变化——当 `floating` 从 `true` 变 `false` 且 `rightSidebarStore.maximized` 为
`true` 时，自动恢复。但这会让所有 dock 操作（不只"恢复原样"按钮）都触发右侧栏
restore，可能过于宽泛。

### 验证

- 右侧栏最大化 → 中间栏自动浮起 → 点"恢复原样" → 中间栏 dock **且** 右侧栏恢复为非全屏。
- 右侧栏最大化 → 中间栏浮起 → 点右侧栏自身的 Zoom/restore 按钮 → 右侧栏恢复 →
  中间栏根据 snapshot 决定 keep-floating 或 dock（原有逻辑不变）。
- 正常浮起（非最大化触发）→ 点"恢复原样" → 仅 dock，不触碰右侧栏（`maximized` 本就 `false`）。

## 问题 12：思考等级高级配置应与模型绑定而非与 agent/会话绑定

### 现象

预设角色 → 代理模型标签页中有"思考等级高级配置"面板。该面板让用户配置
`wire_field`（如 `extra_body.thinking.type`）、`wire_format`（如 `zai`/`openai`/
`deepseek`）、以及七个等级各自的 wire 值。这些概念本质上是**模型/提供商级别**的
（不同 provider 的 wire 形状完全不同），但当前存储为**会话级别**状态，且嵌入在
预设/代理模型面板的 UI 表面中，看起来像是 agent 绑定的。

### 调查结论

**用户的直觉正确：高级配置在语义上是 `(provider, model)` 的属性，不应跟 agent 绑定。**

#### 当前架构的三层关系

| 层 | 存储位置 | 内容 | 是否模型绑定 |
|----|---------|------|-------------|
| 模型声明 | `reasoning_payload.py` `_FORMAT_LEVEL_MAPS` + `_MODEL_LEVEL_OVERRIDES` | 每个 `(provider, model)` 的 `thinkingLevelMap` + `thinkingFormat` | **是**，按 `(provider, model)` 派生 |
| 预设角色 | `PersonaPreset`（`db.ts:235-276`） | persona 文件 + character + agent config + main_model | **否**，无任何思考配置字段 |
| 会话状态 | `StateKey.CUSTOM_THINKING_MAPPING`（`state_keys.py:77-80`） | `wire_field` / `wire_format` / `level_map` | **否**，按 session_id 存储，不按模型 key |

#### 预设本身不携带思考配置

`PersonaPreset`（`client/app/composables/db.ts:235-268`）的字段：`name` / `content`
（persona 文件）/ `character` / `agent`（工具/中间件/子角色模型）/ `main_model`。
**没有 `thinking`、`thinkingLevel`、`customThinkingMapping` 字段。**

`createSessionFromPreset` / `applyPresetPayload`（`persona-catalog.ts:466-586`）在从
预设创建会话时只写入 persona 文件、character、agent config、main model——**不写任何
思考状态寄存器**。会话的思考配置从 unset 开始，跟随模型/env 默认。

#### "高级配置"面板是会话级、非预设级

- 面板组件 `ThinkingCustomMappingPanel.vue`（`client/app/pages/home/components/`），
  i18n 标题 `thinkingCustom.title` = "思考等级高级配置"（line 250）。
- 渲染位置：`SessionPresetPanel.vue:146`，在"代理模型"标签页内：
  ```vue
  <ThinkingCustomMappingPanel :session-id="sessionId" />
  ```
  prop 是 `:session-id`——**绑定到会话，不是预设**。
- 持久化：`GET/PUT /sessions/thinking/custom`（`session_settings_service.py:666-710`）
  写入 `StateKey.CUSTOM_THINKING_MAPPING`（会话状态寄存器，mem + SQLite）。
- 预设编辑器（`NewSessionPresetDialog.vue`、`PersonaPanel.vue`）**不包含任何思考配置**。

#### 模型的声明式映射是按 `(provider, model)` 派生的

`reasoning_payload.py`：
- `_FORMAT_LEVEL_MAPS`（lines 145-249）：每个 `ThinkingFormat`（openai/deepseek/zai/
  qwen 等）的默认等级 wire 映射。
- `_MODEL_LEVEL_OVERRIDES`（lines 254-261）：按模型族的覆盖，如 `glm-5` 只支持
  low/high/max（其余等级 wire 值为 `None` = 不支持）。
- `resolve_thinking_format(provider, model_name)`（lines 264-292）：从 `(provider, model)`
  选 wire 形状。
- `resolve_thinking_level_map(provider, model_name, ...)`（lines 295-318）：默认 + 覆盖。
- `get_supported_thinking_levels(provider, model_name)`（lines 321-340）：模型支持的
  等级列表（`None` wire 值的等级被排除）。
- `build_thinking_kwargs`（lines 573-644）：入口函数。**`custom_mapping` 的 `level_map`
  完全替换声明式 map**（`_resolved_level_map`，lines 422-445）——自定义映射胜出。

### 核心问题

`CustomThinkingMapping`（`wire_field` / `wire_format` / `level_map`）在语义上是
`(provider, model)` 的产物——`wire_format` 本身就是 `ThinkingFormat` 枚举值
（per-provider 概念），`level_map` 里的 wire 值就是 `_FORMAT_LEVEL_MAPS` 声明的东西。
为某个 provider 的 wire 形状写的映射（如 `zai` 的 `extra_body.thinking.type`）对
另一个 provider 的模型毫无意义。

但当前它：
1. **按 session_id 存储**，不按模型 key。
2. **不随模型切换失效**：会话的模型被切换时（通过同一个面板上方的 main-model picker），
   旧的 `CUSTOM_THINKING_MAPPING` 不会被清理或重新 key。`build_thinking_kwargs` 会
   把旧映射的 `wire_format`/`level_map` 应用到新模型上——**只有新模型恰好共享同一个
   wire 形状时才安全**，否则会产生无效的请求参数。
3. **视觉上嵌入在"预设角色/代理模型"面板中**，让用户误以为是 agent/preset 绑定的。

### 修复方向

**方案 A（推荐）：自定义映射改为按模型绑定**

将 `CustomThinkingMapping` 的存储 key 从纯 session_id 改为 `(session_id, model_id)`。
模型切换时：
- 新模型若有已存储的自定义映射 → 加载它。
- 新模型若无 → 回退到声明式 map（`resolve_thinking_level_map`），面板显示为空/默认。
- 旧模型的自定义映射保留（切回去仍可用），不对新模型生效。

后端改动：
- `StateKey.CUSTOM_THINKING_MAPPING` 改为按模型 key 的 dict 或独立存储。
- `GET/PUT /sessions/thinking/custom` 接受 `model` 参数。
- `ThinkingControlMiddleware`（`core.py:234-259`）读取时用当前模型查找对应映射。
- `build_thinking_kwargs` 的 `custom_mapping` 参数已是 per-call 的，逻辑不变。

前端改动：
- `ThinkingCustomMappingPanel` 在模型切换时重新加载对应模型的自定义映射。
- 面板标题/说明可明确标注当前绑定的模型名。

**方案 B（最小改动）：模型切换时自动清除自定义映射**

保持 session 级存储，但在模型切换时（`PUT /sessions/model` 或
`StateKey.LLM_MAIN_MODEL` 变化时）自动清除 `CUSTOM_THINKING_MAPPING`，
回退到声明式 map。用户切换模型后需重新配置（若需要）。比方案 A 简单，
但用户切来切去时需反复配置。

**方案 C（仅 UI 调整）：面板移出"代理模型"标签**

不改存储机制，仅将 `ThinkingCustomMappingPanel` 从 `SessionPresetPanel` 的
"代理模型"标签页移到更明确的位置（如模型选择器旁边），并在 UI 上标注
"此配置与当前选中的模型绑定，切换模型后可能需要重新配置"。这是最小侵入的
改法，但没解决"旧映射应用到新模型"的核心风险。

### 验证

- 会话使用模型 A，配置自定义映射 → 切换到模型 B → 模型 B 不受 A 的映射影响
  （方案 A：B 用自己的映射或声明式默认；方案 B：B 用声明式默认）。
- 切回模型 A → A 的自定义映射仍生效（方案 A）。
- `GET /sessions/thinking` 返回的 levels 列表始终是当前模型的（已有逻辑正确）。

### 现象

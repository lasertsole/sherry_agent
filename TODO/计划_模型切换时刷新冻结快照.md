# 计划：模型切换时刷新冻结快照

- 建档日期：2026-10-22
- 状态：**计划（未开工）**
- 触发问题：切换模型（`PUT /sessions/model` → `LLM_MAIN_MODEL`）时 provider 的 prefix cache
  **必定失效**——不同模型的 model name 不同，缓存命名空间不同，首轮必冷启动。既然缓存
  本就要冷，不如顺手 `load_from_disk()` 刷新冻结快照，让 mid-session 写入的
  FACTS.md / MEMORY.md / USER.md 内容在切换后立即可见——"免费"刷新。
- 结论先行：
  1. **无条件触发**——与思考模式切换计划不同，模型切换必定破坏 prefix cache（不同
     model name = 不同缓存命名空间），不需要前置验证。
  2. **触发时机**：仅在用户实际发送消息（turn 开始）且检测到模型与上一轮不同时触发；
     前端来回切换模型但不发送不触发；发送时模型与上一轮相同也不触发。
  3. **与思考模式计划的关系**：两份计划共享同一个 `abefore_model` 钩子位置
     （`ThinkingControlMiddleware`），检测逻辑可合并——`_last_applied` 跟踪
     `(cache_key, model_name)` 元组，任一分量变化都意味着缓存断裂，只是
     "model name 变了"是确定的，"cache_key 变了"需要前置验证。

---

## 1. 为什么模型切换必定破坏 prefix cache

Provider 的 prefix cache 以 `(model_name, token_prefix)` 为键。模型切换时：

- `LLM_MAIN_MODEL` 写入新的 profile descriptor（`{provider, model, base_url, api_key, ...}`）
- `ThinkingControlMiddleware._variant` 用 `_override_signature`（`core.py:162-177`）从
  `(provider, model, base_url, api_key, context_window)` 算出指纹 → 指纹不同 → 构建全新
  client 实例 → 不同的 model name 发给 provider
- 不同 model name = 不同缓存命名空间 → 首轮 cache_read = 0

这与思考模式切换不同：思考模式切换不改变 model name（只改 `reasoning_effort` /
`thinking.type` 等请求体参数），所以是否破坏缓存取决于 provider 对参数级 cache key 的处理——
需要前置验证。模型切换不存在这个不确定性。

---

## 2. 触发条件

park/promote 时序（`session_settings_service.py:77-84`）已天然满足"仅发送时"的要求：

```
用户在前端选模型 → PUT /sessions/model
  ├─ 无 turn 在跑 → 直接写 LLM_MAIN_MODEL（立即生效）
  └─ 有 turn 在跑 → 写 LLM_MAIN_MODEL_PENDING（parked）
      → on_turn_finished 提升 → LLM_MAIN_MODEL

用户发送消息 → turn 开始 → before_model 读 LLM_MAIN_MODEL
  → 与 _last_applied 比较 → 不同 → 触发刷新
```

| 场景 | 触发？ | 原因 |
|---|---|---|
| 前端切了模型但没发送 | **否** | 没有 turn，`before_model` 不运行 |
| 前端切了模型→发送，模型与上一轮相同 | **否** | `_last_applied` 的 model 分量相同 |
| 前端切了模型→发送，模型与上一轮不同 | **是** | model 分量不同，刷新快照 + 失效缓存 |
| 没切模型直接发送 | **否** | model 分量相同 |
| 首轮（无上一轮参考） | **否** | `_last_applied` 为空，首轮的 `load_from_disk` 已在 agent 初始化时完成 |

### 2.1 与思考模式切换的并发场景

| 场景 | 检测到什么 | 触发？ | 哪份计划负责 |
|---|---|---|---|
| 只切模型，思考模式不变 | model 分量变 | **是**（本计划） | 本计划无条件触发 |
| 只切思考模式，模型不变 | cache_key 分量变 | **条件**（计划①前置验证通过后） | 计划① |
| 同时切模型 + 思考模式 | 两个分量都变 | **是**（本计划优先） | 本计划无条件触发，计划①不重复 |
| 都没切 | 都不变 | **否** | — |

合并后的钩子只需在检测到**任一分量变化**时触发刷新；model 分量变化是无条件的，
cache_key 分量变化是条件的（依赖计划①的前置验证结论）。

## 3. 实现

### 3.1 钩子位置

与计划①相同：`ThinkingControlMiddleware` 增加 `abefore_model` / `before_model` 钩子。

理由（与计划① §1.2 一致）：`before_model` 钩子运行在 `system_prompt_injection` 的
`wrap_model_call` **之前**（中间件链顺序：`before_model` hooks → `wrap_model_call`
hooks 外→内 → LLM）。若放在 `wrap_model_call` 内层，`system_prompt_injection`（外层）
已经用旧快照解析了 system prompt，首轮最重要的调用拿到的是旧快照。

### 3.2 检测逻辑

`_last_applied` 已按 `(cache_key, model_name)` 元组跟踪（`core.py:234-242`）。
本计划只需比较 **model_name 分量**：

```python
async def abefore_model(self, state, runtime=None) -> dict[str, Any] | None:
    session_id = str((state or {}).get("session_id") or "")
    if not session_id:
        return None

    cache_key, override, custom_mapping = self._read_controls(session_id)
    current_model = (override or {}).get("model")  # None = env-configured
    applied = (cache_key, current_model)
    last = self._last_applied.get(session_id)

    # 首轮或 model 分量未变 → 不触发（本计划只管 model 变化）
    if last is None:
        return None
    if last[1] == applied[1]:
        # model 分量没变；cache_key 是否变由计划①管
        return None

    # model 分量变了 → 无条件刷新
    from agent.tools.memory import memory_store
    from runtime import StateKey, state_register_mem, state_register_db

    memory_store.load_from_disk()
    state_register_mem.set_state(session_id, StateKey.SYSTEM_PROMPT, None)
    state_register_db.set_state(session_id, StateKey.SYSTEM_PROMPT, None)

    logger.info(
        "ThinkingControlMiddleware: model changed {}→{}, "
        "refreshed memory snapshot + invalidated system prompt cache",
        last[1], current_model,
    )
    return None
```

### 3.3 与计划①的合并

如果两份计划同时落地，`abefore_model` 钩子合并为一次检测：

```python
async def abefore_model(self, state, runtime=None) -> dict[str, Any] | None:
    session_id = str((state or {}).get("session_id") or "")
    if not session_id:
        return None

    cache_key, override, custom_mapping = self._read_controls(session_id)
    current_model = (override or {}).get("model")
    applied = (cache_key, current_model)
    last = self._last_applied.get(session_id)

    if last is None or last == applied:
        return None  # 首轮或全未变

    model_changed = last[1] != applied[1]        # model 分量变 → 无条件
    thinking_changed = last[0] != applied[0]     # cache_key 变 → 条件（计划①）

    # model 变了无条件刷新；只有 thinking 变了需计划①前置验证通过
    if model_changed or (thinking_changed and PLAN1_VERIFIED):
        from agent.tools.memory import memory_store
        from runtime import StateKey, state_register_mem, state_register_db

        memory_store.load_from_disk()
        state_register_mem.set_state(session_id, StateKey.SYSTEM_PROMPT, None)
        state_register_db.set_state(session_id, StateKey.SYSTEM_PROMPT, None)

        logger.info(
            "ThinkingControlMiddleware: {} changed {}→{}, "
            "refreshed memory snapshot + invalidated system prompt cache",
            "model" if model_changed else "thinking",
            last, applied,
        )
    return None
```

`PLAN1_VERIFIED` 是计划①前置验证的结论（True = 思考模式切换确实破坏缓存）。
若计划①验证不通过（思考模式切换不破坏缓存），只有 model_changed 分支生效。

### 3.4 失效缓存的方式

`_get_and_reload_system_prompt`（`system_prompt/core.py:46-57`）检查 `is None`：

```python
system_prompt = state_register_mem.get_state(session_id, StateKey.SYSTEM_PROMPT, None)
if system_prompt is None:  # ← 这一行触发重建
    ...
```

用 `set_state(session_id, StateKey.SYSTEM_PROMPT, None)` 即可让两层缓存都 miss。
需确认 `set_state` 是否接受 `None` 值——若不接受，改用 `del_state`（需确认 API 存在）
或 `_delete_value`（`session_settings_service.py` 已有此 helper）。

### 3.5 `load_from_disk()` 的全局性

`memory_store` 是 process-level 单例（`memory.py:632`）。`load_from_disk()` 无 session
隔离——调用一次刷新全局 `_system_prompt_snapshot`。这在当前设计下是安全的：

- 刷新只写 `_system_prompt_snapshot`（内存中的 dict），不影响其他 session 的
  `StateKey.SYSTEM_PROMPT` 缓存——其他 session 仍用自己缓存的旧 system prompt
- 只有被显式失效了 `StateKey.SYSTEM_PROMPT` 的 session 才会在下次模型调用时重建
  system prompt，重建时 `format_for_system_prompt` 读的就是刷新后的快照
- 如果 memory 文件没变（mid-session 没有写入），`load_from_disk()` 读到相同内容，
  快照字节不变，重建出的 system prompt 也字节不变——不会额外破坏缓存

## 4. 测试要点

1. **刷新触发测试**（mock，不需要真 LLM）：
   - 设 `_last_applied[session] = ("on", "gpt-4o")`
   - 设 `LLM_MAIN_MODEL = {"model": "claude-sonnet-4-5", ...}`
   - 调 `abefore_model` → 断言 `StateKey.SYSTEM_PROMPT` 在 mem 和 db 中为 None
   - 断言 `memory_store._system_prompt_snapshot` 被刷新
2. **不触发——模型相同**：
   - `_last_applied[session] = ("on", "gpt-4o")`，`LLM_MAIN_MODEL` 的 model 也是 `gpt-4o`
   - 调 `abefore_model` → 断言 `StateKey.SYSTEM_PROMPT` 仍存在
3. **不触发——首轮**：
   - `_last_applied` 为空 → `abefore_model` 返回 None，不做任何操作
4. **不触发——前端切了没发送**：
   - `LLM_MAIN_MODEL_PENDING` 有值但 `LLM_MAIN_MODEL` 未变 → `before_model` 不运行
   - （这由 park/promote 时序天然保证，不需要额外代码）
5. **端到端**：切换模型后首轮 system prompt 包含 mid-session 写入的 FACTS.md 新条目

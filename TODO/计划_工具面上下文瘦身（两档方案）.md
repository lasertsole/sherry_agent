# 计划：工具面上下文瘦身（两档方案：按组关停 / 描述瘦身）

- 建档日期：2026-10-08
- 状态：**计划（未开工）**
- 触发问题：主工具表常驻 schema（含浏览器功能时）44 个工具 ≈ **16,992 tok**，其中
  「任务与计划 + 子代理」两族占 10,642（63%）。能否用"伞装技能"替换这两族以省上下文？
- 结论先行：
  1. **技能替换不了能力**——这两族的能力全是进程内状态（SQLite store + runtime 寄存器）、
     每次变更推 WS、会话身份（`InjectedState`）与中间件按工具名挂钩；脚本子进程够不着
     （同 `计划_内部浏览器agent控制（CDP代理）.md` 3.3 的排除论证）。**真正的杠杆是常驻
     schema 的大小和工具数量**，不是"工具还是技能"。
  2. 实测：**任务与计划一族 9,351 tok（占全工具预算 55%）是唯一大块**；子代理族只有
     1,291，合并上限 <1k，**不动**。
  3. 精度上，族内又极度集中：最贵的 5 个工具占全族 62%（见 0.2）。
  4. **两档互相独立，推荐顺序 1 → 2**：方案一（按组关停，零代码）是第一道防线，
     方案二（描述瘦身）是锦上添花。已评估并否决"14→1 合族派发"方案（原方案三）——
     瘦身后 taskflow 常驻 ~5,500 tok（≈ 131K 窗口的 4.2%），不值得一次跨 60+ 文件的重构。
  5. **工具数量本身是认知负荷**（不只是 token 成本）：44 个工具 = 每轮 44 个选择项，
     影响模型工具选择准确率。按组关停直接减数量（44→~27），这是独立于 token 的收益。

### 0.3 复测脚本（验收与后续对比都用它）

```python
import json
from agent.tools import build_main_tools
from agent.tools.catalog import _group_of
from pub.func.estimate_tokens import estimate_text_tokens

def schema_text(t):
    return json.dumps({"name": t.name, "description": t.description or "",
                       "parameters": t.args_schema.model_json_schema()}, ensure_ascii=False)

per_group = {}
for t in build_main_tools():
    per_group.setdefault(_group_of(t.name), []).append(t)
for g, ts in sorted(per_group.items(), key=lambda kv: -sum(estimate_text_tokens(schema_text(t)) for t in kv[1])):
    print(g, len(ts), sum(estimate_text_tokens(schema_text(t)) for t in ts))
```

## 1. 方案一：按会话关组（零代码，第一道防线）

### 1.1 原理

不是"44 个工具 token 太多"，而是"不需要编排的会话也挂着 14 个 taskflow 工具太多"。
两族已是 `BULK_ONLY_GROUPS`（`agent/tools/catalog.py`）：预设「工具」页签里整体
开关，`PUT /sessions/agent_config` 落到会话，`ToolSelectionMiddleware` 按会话裁剪
（`request.override(tools=<subset>)` 缩窄模型可见面，执行层 `wrap_tool_call` 同样
拒绝被关的工具——stale checkpoint 或幻觉工具名不会绕过）。

### 1.2 双重收益

| 维度 | 效果 |
|---|---|
| **token 成本** | 关掉任务与计划组省 ~9.3k tok；关掉子代理组再省 ~1.3k |
| **工具数量** | 44 → ~27（只关 taskflow）或 ~20（关 taskflow + subagent）——模型每轮选择项减半 |
| **认知负荷** | 工具数量独立于 token 是模型选择准确率的因子：选项越少，选对率越高 |

工具数量是独立于 token 的收益维度。即使每个工具的 schema 压到最小，44 个选项仍是
44 个选项——模型每轮都要在这个空间里决策。关组直接减数量，这是方案二（瘦身）给
不了的。

### 1.3 已有先例与即时使用

- **情感陪伴**预设已把任务与计划 / 子代理两组全关 ≈ 常驻 −10.6k，工具数 44→~20。
- 使用口径：不用编排的会话在「工具」页签关掉两组即可。
- 这是所有方案的兜底，也是方案二落地前的即时手段。

### 1.4 默认预设政策（需要讨论但不在本计划内）

**全量预设（当前默认）包含所有 44 个工具。** 大多数会话不需要 DAG 编排——如果默认
不含 taskflow、需要时再开，相当于把方案一从"用户手动关"变成"默认就不在"。

可选路径：
- 新建一个"轻量"默认预设（不含 taskflow + subagent），需要编排时用户切到全量
- 或按会话类型自动推荐：编码类会话默认含 taskflow，非编码类默认不含
- 注意：改默认会影响已绑预设的 EXACT 语义，需要一次专门的评估

这是政策决策（改一行 `BUILTIN_PRESETS` 派生规则），不是代码开发——但它决定了方案一
的覆盖面：默认关组 vs 用户手动关组，效果差一个数量级。

## 2. 方案二：瘦身（描述压缩 + 长文进既有 SKILL.md）

### 2.1 原理

常驻的只有工具 name + description + 参数 schema；**技能正文按需加载**
（`skill_view`），技能只在索引里留一行（~30 tok）。把"深度语义"从
description/Field 描述搬进 `taskflow` / `todolist` 两个**已存在**的 SKILL.md，
就是标准的 progressive disclosure：不用编排的会话（大多数）白赚，用编排的会话
付一次加载。注意两个 SKILL.md 已覆盖大量重叠内容（todolist skill 里就有
todowrite 的完整字段表）——这次主要是**去重**，不是新写。

### 2.2 逐工具目标

| 工具 | 现状 tok | 目标 | 长文搬去哪 |
|---|---|---|---|
| taskflow_run_task | 1,772 | ≤650 | taskflow SKILL.md「run_task 字段语义」 |
| taskflow_resume | 1,566 | ≤600 | 同上（含 judge/retry 交互说明） |
| knowledge | 890 | ≤350 | taskflow SKILL.md「知识库」小节 |
| todowrite | 877 | ≤450 | todolist SKILL.md（已有字段表，去重） |
| taskflow_update_steps | 670 | ≤350 | taskflow SKILL.md |
| 其余 12 个 | ≤2,5xx | 只删冗余句，不动结构 | — |

写法约束：

- tool description = 一行摘要 + 常用路径必需信息；结尾一句
  `full semantics: skill_view('taskflow')`（只在实际用到的会话付那一次加载）。
- Field 描述 ≤ ~60 字符/字段；字段的语义表、示例、budget/deadline/schema/judge 的
  相互作用全部进 SKILL.md。
- **catalog 的 hover 提示取 description 第一行**（240 字符上限），第一行必须自足。

### 2.3 验收

- 复测脚本：任务与计划 ≤ **5,500**，总表 ≤ **13,000**（预期 −3.9k ≈ 工具预算的 −23%）。
- 不触碰工具名/metadata/调用方：**零测试改动**（已核实 19 个 taskflow 测试文件只
  断言行为与"描述非空"，不钉文本——唯一对 description 的断言是
  `assert entry["description"].strip()`）。
- 行为抽查：一个多步会话（create → run_task → resume → finish）在只加载
  `skill_view('taskflow')` 的前提下完整跑通；split runner 全绿。

### 2.4 风险

- 模型在**没加载技能**时直接调用：description 变薄 → 字段用错。缓解：常用路径的
  description 保持自足，深度语义才外移；表格里给每个工具定义了"目标 tok"下限，
  不允许无脑截断。
- 描述与 SKILL.md 双处漂移：在 SKILL.md 顶部钉一句"以工具 schema 为准"，并留给
  后续一致性脚本（可选，不阻塞）。

## 3. 已否决：14→1 合族派发（原方案三）

曾评估将 14 个 `taskflow_*` 合并为一个 `taskflow(action=…, **params)` 派发工具，
常驻从 9,351 降到 ~2,000。**否决理由：**

- **方案二落地后收益不抵风险**：瘦身后任务族 ~5,500 tok（≈ 131K 窗口的 4.2%，
  合理的编排引擎代价），合并只多省 ~3,500 tok——不值得一次跨 60+ 文件、19 个测试
  的重构。
- **爆炸半径过大**：`todo_continuation` 提示文本点名工具名、`summarization/nudges.py`
  的 `todo_update` 标记、StepJudge 与 finish 的 A–D 门、`progress_push` 的 WS 推送——
  全部按工具名挂钩，改为 `action=` 派发需要逐一适配。
- **per-action metadata 新机制**：派发器只有一个 metadata，必须新增按动作查询的
  `action_metadata` 约定，消费方（`tool_guardrails`、`tool_output_prune`）都要改。
- **方案一（关组）已经减数量**：合并的最大独立收益是工具数 44→31，但关组已经做到
  44→~27（只关 taskflow）甚至 ~20（关两组），且零代码零风险。

如果未来方案一+二后数字仍不可接受，再单独开分支/单独计划评估。

## 4. 子代理族（7 个，1,291 tok）不动的结论

- 合并上限 <1k（最大单工具 `sessions_spawn` 326），收益低于重构风险；
  `sessions_spawn/steer` 与 spawn 机制、lane、announce 深度耦合。
- 结论：**保持现状**；若某会话不用委派，用方案一关组。

---

## 5. 推荐顺序与决策点

1. **方案一（按组关停）**：零代码，今天可用。对不用编排的会话（大多数），关掉
   任务与计划组 = 省 ~9.3k tok + 工具数 44→~27。情感陪伴预设已验证。
2. **默认预设政策讨论**：全量预设是否应该默认包含 taskflow？如果默认不含，
   方案一的覆盖面从"用户手动关"变成"默认就不在"——效果差一个数量级。这是
   政策决策，需要评估对已绑预设 EXACT 语义的影响。
3. **方案二（描述瘦身）**：零结构风险，−3.9k tok。改 5 个工具的描述文字 + 两个
   既有 SKILL.md 去重扩写；验收 = 复测脚本数字 + 一次多步会话冒烟。
4. 子代理族不动。
5. **14→1 合族派发不做**（见 §3 否决论证）。

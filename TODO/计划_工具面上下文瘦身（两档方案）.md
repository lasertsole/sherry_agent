## 1. 方案一：默认/会话按组关停（零代码，推荐第一位）

`ToolSelectionMiddleware` 已按会话裁剪工具面；预设「工具」页签支持组级开关，`tasks` / `subagents` 是 `BULK_ONLY_GROUPS`（整体开关）。

| 会话配置 | 工具数 | tokens（浏览器关） |
|---|---:|---:|
| 当前全量 | 33 | 11,274 |
| 只关任务与计划 | 27 | 7,417 |
| 关任务与计划 + 子代理 | **19** | **5,871（−48%）** |
| 浏览器开启且关两组 | 20 | 6,550 |

**建议**：为不需要 DAG/委派的会话提供轻量默认预设（不含任务与计划、子代理两组），编码类会话再显式切到全量。这是产品策略改动（`BUILTIN_PRESETS` 派生规则），不改工具代码；需要评估已绑定预设的 EXACT 语义。

## 2. 方案二：描述瘦身 / progressive disclosure（低风险，优先级下降）

工具描述与字段描述常驻；技能正文按需加载。任务合并已经把最贵的一族降到 3 个工具：

- taskflow：2,614 tok（约当前工具面的 23%）；旧计划「任务族 ≤5,500」目标已达成。
- todo：734；knowledge：509。
- 其余组均 <1.6k。

继续把 taskflow 的字段语义搬进已存在的 `taskflow` SKILL.md，预计最多再省 ~1k；需要保持首行描述自足、常用路径参数说明不缺失。**收益小于方案一，暂不作为第一步。**

---

## 3. 方案三：删除常驻工具面（按需暴露）

### 3.1 按技能/意图动态挂载

只有当会话加载 `taskflow` / `todolist` / `browser` 等技能或意图命中时，才把对应工具加入 `request.tools`；其余轮次完全不挂载。

- 收益：不用编排的会话可接近“工具面删除”，工具数可从 33 降到 ~20 以下。
- 成本/风险：工具可用性跨轮次变化；checkpoint 中旧的 tool call、continuation、prompt cache、`ToolSelectionMiddleware` 的 session config 语义都要处理；需要一个新的状态约定（例如 skill 加载标记 + 轮次边界切换）。
- 结论：**中期可选**，先做方案一；等方案一覆盖不足时再单独立项。

### 3.2 单一通用派发工具（不做）

一个 `tool(name, args)` schema 看似能删掉所有工具定义，但会失去：

- 每工具的 typed schema 和必填参数校验（调用失败率会转向运行时分发器）；
- `scope=main_only`、`idempotent`、`todo_update` 等 metadata；
- 并行安全分类、HITL、路径守卫、输出裁剪的按工具分支；
- provider 侧对具体工具的 schema 约束。

**结论：不做。** 这是把上下文 token 换成大量运行时分支和更高的失败率，不是真正的收益。

---

## 4. 推荐顺序

1. **默认/会话按组关停**：零代码，最大收益（关两组 −5,403 tok、−14 个工具）。
2. **轻量默认预设**：让大多数会话默认不挂任务与计划/子代理；这是政策决策。
3. **描述瘦身**：可选，预计 ~1k，收益递减。
4. **动态技能暴露**：未来选项，需单独立项。
5. **通用派发器**：不做。

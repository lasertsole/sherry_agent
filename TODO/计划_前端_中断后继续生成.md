## 0. 背景（已核实）

### 0.1 sherry 现状：中断即终止，无断点续写

sherry 的对话中断是**终止性**的。三种触发源：

- **用户 Stop**：前端发 WS `stop` → `server/trigger/ws/messages.py:211` `_cancel_session` 对 `_active_tasks[session_id]` 调 `task.cancel()` → `CancelledError` 传到 `StreamTurn.run`（`stream_dispatch.py:567-574`）→ `_on_cancelled()`（`messages.py:361`）→ `_write_interrupt_marker(..., "cancelled")`。
- **心跳超时**：`stream_dispatch.py:575-584` 捕获 `HeartbeatTimeoutError` → `_on_heartbeat_timeout`（`messages.py:364`）→ 同样写 marker。
- **进程崩溃**：后台 task 直接消失，marker 可能没写入。

中断后发生的事（`interrupt_marker.py:67-217`）：
1. `heal_interrupted_turn`（`state_port.py:129-204`）把 checkpoint 修成 provider 合法形状（给悬空 tool_calls 补错误占位 ToolMessage）+ 追加一条 `AIMessage(content="[interrupted] {partial_text}", metadata={"interrupted": True, "reason": reason})`，marker 带确定性 id `interrupted-{thread_id}-{turn_seq}`。
2. MesMemory dual-write 一行 `[interrupted:{reason}] {partial_text}`（`interrupt_marker.py:135-193`）。
3. 该 turn 的 CLAIMED 队列行翻成 VOIDED（`interrupt_marker.py:196-217`）。
4. 发 `stopped` 帧，`on_turn_finished` 触发 drain。

**结果**：turn 实例销毁、`_agent` 释放、队列作废。要继续只能发新消息——下一轮把 `[interrupted]` marker 当历史看到，但是**全新一轮生成**，不是从断点续写。

前端主聊天只有 Send + Stop 两个按钮（`inputBox.vue:49-59`），全仓 grep `regenerate / 重新生成 / 继续生成` 零命中。中断提示文案 `errors.streamInterrupted`（`zh.json:112`）是被动提示，无操作按钮。

### 0.2 现有的"续写"能力：max_tokens 自动续写（可直接复用）

sherry **已有一套断点续写机制**，只是触发条件是"输出长度上限"而非"用户中断"：

- `stream_dispatch.py:545-548`：一轮 stream 结束后调 `_should_text_continue()`。
- `_should_text_continue`（`messages.py:321-344`）：当 `finish_reason in ("length","max_tokens")` 且无 tool_calls → 返回 `should_continue=True`。
- `_prepare_continuation`（`messages.py:346-359`）：置 `_is_continuation=True`。
- `_create_source` 的 continuation 分支（`messages.py:206-216`）：注入 `_CONTINUATION_PROMPT`（`messages.py:141-145`）作为 HumanMessage，**checkpointer 重载被截断的 AIMessage**，模型看到"自己的未完成回答 + 继续提示"，从半句续写。

```python
# messages.py:206-216 —— 续写时不需要新用户输入，只注入系统续写提示
if self._is_continuation:
    prompt = _REASONING_ONLY_PROMPT if self._is_reasoning_only else _CONTINUATION_PROMPT
    input_dict = {"session_id": self.session_id, "messages": [HumanMessage(content=prompt)]}
```

**关键差异**：max_tokens 续写在**同一个 `_GenerateTurn` 实例内**（`self._agent` 还持有，`while True` 循环继续）；中断续写需要**跨 turn**（中断 turn 已销毁，要在新 turn 里复用这条路径）。

### 0.3 ZCode 对比：续写能力建模在工作流 run 层

ZCode 的「恢复运行 / Resume run」按钮（`WorkflowRunSidePaneSections.tsx:163-181`）针对的是**动态工作流 run**，不是普通聊天流：
- UI 发 `resumeWorkflowRun` 命令（`WorkflowRunSidePane.tsx:244-260`），后端用**同一个 runId 重新 launch**（`dynamic-workflow-run-submit.ts:424-582`），引擎从 journal 把已完结节点短路 replay（不耗 token）、未完结节点重新派发。
- 它依赖工作流 run 的 journal 持久化 + 节点级 resume，前提是 run 状态为 `cancelled` 或失败编码 `Interrupted`。

ZCode 另有一个字面叫「继续」的按钮（`ConversationQueuePanel.tsx:383`），那是**消息队列恢复**（Stop 后继续按序发排队消息），不是断点续写。

**结论**：ZCode 也没有"普通聊天流中断后断点续写"的通用按钮，它的续能力建模在工作流 run 这一层。sherry 要做的是**普通对话流的断点续写**——可以复用 sherry 自己已有的 max_tokens 续写路径，不需要照搬 ZCode 的工作流 journal 机制。

## 1. ⚠️ 硬约束

| 约束 | 含义 | 验收方式 |
|---|---|---|
| **F1**：checkpoint / MesMemory schema 不变 | 不新增表、不改列；resumable 状态走 StateKey（mem + DB 双写，已有模式） | schema 无变化 |
| **F2**：现有中断 marker 行为向后兼容 | `[interrupted]` 前缀的 MesMemory 行仍然写入（用户能看到"这条被中断了"）；healing 逻辑不动 | 老的中断流程行为不变 |
| **F3**：WS 协议向后兼容 | 新 `continue_generation` 帧是追加；`stopped` 帧新增 `resumable` 字段对老前端无害（忽略未知字段） | 老前端收新帧走旧行为 |
| **F4**：只在纯文本中断时提供续写 | 中断时若有 pending tool_calls（`healed_calls > 0`），不提供续写按钮（留阶段二） | tool-call 中断无按钮 |
| **F5**：fail-open | 续写失败/断点失效时提示错误，不影响会话后续使用 | 后端拒绝时前端不崩 |
| **F6**：一个断点只能续一次 | 续写 turn 开始即清除 resumable 断点；续写本身被中断则写新断点 | 不允许重复续写同一断点 |

## 2. 任务一：MVP —— 纯文本中断续写（必做）

### 2.1 目标

用户点 Stop 中断了一条纯文本回答 → 中断的 AI 行出现「继续生成」按钮 → 点击 → 模型从中断处续写完成回答（不重复已生成内容）。心跳超时同理。

### 2.2 核心思路：复用 continuation 路径 + 清理 marker 前缀

中断续写与 max_tokens 续写的唯一本质差异：**中断时 state 末尾是 `[interrupted] {partial_text}` marker（带前缀），max_tokens 截断时是干净的 `{partial_text}` AIMessage**。如果直接注入 `_CONTINUATION_PROMPT`，模型会把 `[interrupted]` 当成自己输出的一部分，续写会被前缀污染。

**解法（选项 B，不改中断时行为）**：续写 turn 开始前，用 `aupdate_state` 把 marker 的 content 从 `[interrupted] {partial_text}` 替换回干净的 `{partial_text}`（依赖 `add_messages` reducer 的 upsert-by-id 语义——marker 带确定性 id `interrupted-{thread_id}-{turn_seq}`，`state_port.py:169`）。清理后 state 末尾与 max_tokens 截断**完全一致**，直接复用 `_CONTINUATION_PROMPT` 续写。

MesMemory 那行 `[interrupted] {partial}` 保留不动（用户历史里仍可见"这条中断过"），checkpoint 里是干净的 partial——两者独立，这正是选项 B 的好处。

```
中断时 state 末尾：  AIMessage("[interrupted] {partial}", id=interrupted-{tid}-{seq})
                     ↓ 续写前清理前缀（aupdate_state upsert by id）
                     AIMessage("{partial}", id=interrupted-{tid}-{seq})
                     ↓ 注入 _CONTINUATION_PROMPT（复用 _GenerateTurn continuation 分支）
模型续写 →           AIMessage("{continuation}")  （新增一条）
```

### 2.5 风险与约束

- **续写文本的 UI 归属**：续写产生的新 AIMessage 在 state/MesMemory 是**独立一条**（`{continuation}`），与中断行 `[interrupted] {partial}` 分开。MVP 方案：前端把续写 chunk **追加到中断的 AI 行**（视觉合并成一条完整回答），数据层仍是两条 row。这要求 `handleContinueGeneration` 定位到中断的 AI 行并追加，而非新建占位行。若实现复杂，退路是新建一行（视觉上两条，可接受）。
- **`[interrupted]` 前缀清理的幂等性**：`aupdate_state` upsert by id 替换 content 是幂等的，重复清理无副作用。但要注意：清理后 marker 的 `metadata={"interrupted": True}` 会丢（add_messages 替换整条消息）——续写不需要该 metadata，可接受。
- **续写期间的 Stop**：`_ContinueTurn._on_cancelled` 写新断点（基于续写后的 `self.ai_text`），新 marker id 的 `turn_seq` 与原断点相同（同一 human turn），但 marker_id 相同会被 `heal_interrupted_turn` 的幂等检查跳过（`state_port.py:171-179`）。**需改造**：续写中断的 marker id 加 `-cont` 后缀或用续写轮次的计数，避免与原 marker id 冲突。这是 2.3.5 的细节落实点。
- **HITL 冲突**：续写时若有 pending HITL，先拒绝续写（HITL 优先）。
- **reasoning-only 中断**：若中断时模型只产了 thinking 无可见文本（`_has_visible_text=False and _has_reasoning`），续写应用 `_REASONING_ONLY_PROMPT` 而非 `_CONTINUATION_PROMPT`。`RESUMABLE_BREAKPOINT` 存 `is_reasoning_only` 标志，`_ContinueTurn._create_source` 据此选 prompt（复用 `_should_text_continue` 的判断逻辑）。

**验收**：F1–F6。新建 `tests/server/test_continue_generation.py`（断点写入/失效/清理前缀/续写流）+ `tests/agent/test_state_port_continue.py`（marker 前缀清理幂等）+ 前端集成测试。

## 3. 任务二：tool-call 中断恢复（可选）

### 3.1 目标

中断发生在 tool call 中间（`healed_calls > 0`，已有占位 ToolMessage）时，也提供「继续」——决定是重跑被中断的 tool 还是跳过，然后续写。

### 3.2 思路

- `RESUMABLE_BREAKPOINT` 扩展 `healed_calls` 信息 + 被中断的 tool_call 详情（name/args/id）。
- 续写时给用户两个选项：「重跑工具并继续」/「跳过工具继续」（类似 HITL 卡片）。
- 「重跑」：清理占位 ToolMessage，重新发起该 tool_call；「跳过」：保留占位（带错误结果），模型自行决定下一步。
- 复杂度高于阶段一，且 tool 中断场景少（多数中断发生在文本生成中）。建议阶段一上线观察后再定。

### 3.3 不做的原因（阶段一）

- tool-call 中断的续写要处理 tool 幂等性、副作用回滚，与 TaskFlow/subagent 交错时更复杂。
- max_tokens 续写本身就不处理 tool-call 截断（`_should_text_continue` 在 `_has_tool_calls` 时返回 False，走 MaxTokensBoost 中间件），阶段一对齐这个边界。

- [ ] 中断后发新消息 → 断点失效，无续写按钮。

- [ ] 重启后断点仍有效（StateKey DB 双写）。

## 6. 不做的事

| 项 | 不做的原因 |
|---|---|
| 工作流 journal 机制 | sherry 的续写复用 max_tokens 路径，不需要 ZCode 的工作流节点级 replay |
| 续写文本与中断行数据层合并 | MesMemory append-only，合并需改 schema；MVP 前端视觉合并即可 |
| tool-call 中断恢复（阶段一） | 幂等性/副作用复杂，对齐 max_tokens 不处理 tool 截断的边界 |
| 进程崩溃恢复 | 崩溃时 marker 可能没写入、断点状态可能丢；阶段一不覆盖（DB 双写可部分兜底，但不保证） |
| 跨会话续写 | 续写限本会话内 |
| 自动续写 | 续写必须用户主动点按钮，不自动触发（避免无限循环） |

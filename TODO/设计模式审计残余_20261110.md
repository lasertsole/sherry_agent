# 设计模式审计残余项（2026-11-10）

2026-11-09 的设计模式违反审计已执行完毕，审计报告在修复完成后删除（历史见 dev 提交记录）。除下列两项外，全部条目已落地并通过全量测试；落地结构见 `AGENTS.md` 的 spawn/middleware/event 段落与 `wiki/subagent/`。

## M4 — reasoning_content 适配器：受上游实现限制

- **现状**：`models/LLMs/reasoning_openai.py` 的 `ReasoningChatOpenAI` / `ReasoningDeepSeekChat` 仍继承 `BaseChatOpenAI`，override `_create_chat_result`、`_convert_chunk_to_generation_chunk` 和 `_get_request_payload`。
- **为什么没改成 Adapter**：`langchain-openai` 1.3 明确不从响应中提取非标准字段（`reasoning_content`），公开的 `invoke`/`stream` 返回结果里已经没有该数据，包装层无法“转发并改写”。请求侧回放还需要私有 `_get_request_payload` 把 `reasoning_content` 注回 assistant 消息（否则 DeepSeek thinking 模式 400）。且 `bind_tools` / `with_structured_output` 按设计返回 inner runnable，包装层会在 tool-calling 路径被绕过。
- **结论**：保留现有子类；如果未来上游提供公开的 reasoning 扩展点，再改为 Adapter。

## L3 — UserTurnIterator：三套语义不可强行统一

- **现状**：`pub/func/message/turn_utils.py::split_into_turns` 按 checkpoint 中的 human 边界切分（排除 workspace notice / system reminder）；`context_engine.store.core.find_user_turn_cut` / `get_max_user_turn_num` 按持久化行的 `origin='user'` 计数。两者分别服务于 turn 预算与消息编辑/分支，输入源和边界规则不同。
- **为什么不统一**：强行抽一个 iterator 会把“checkpoint human 计数”和“持久化 user 行计数”合并，改变压缩后的 turn 边界与 edit 的 `turn_seq` 指纹，属于行为变更而非重构。
- **结论**：保留现状；新增这类逻辑时优先复用两个现有入口，不要再写第三套计数。

- 日期：2026-11-25
- 状态：**待评审**
- 来源：2026-11-24 的 resume 修复（`4faeb0e1` 起）让 `state.results` 可以存 ~24,000 B 的完整子代结果，而 `build_task_with_dep_results` 聚合时**没有任何截断**。
- 风险等级：**低—中** —— 只影响声明了 `aggregate_deps=true` 的合成步骤；不声明时输出字节级不变。
- 依赖：无

## 1. 问题

`build_task_with_dep_results(step, steps, results)` 把每个依赖的**完整** `result` 拼进派发任务：

```python
sections.append(f"### {dep_id}\n{result_text}")   # 无截断
```

而这次 resume 修复之后，`results` 里可能是 24,000 B 的子代全文（以前通常是父 agent 写的短摘要）。后果：

- 一个依赖 5 个已完成步骤的合成步骤，可能收到 **5 × 24k ≈ 120k 字符**（约 30–40k tokens）的上游文本；
- 这段文本在每次 `dispatch` / `resume` 的 auto-dispatch / 判断重试（`spawn_replacement`）时都会重新拼一次（从稳定的 `results` 推导，不会累积，但每次都要付这份输入成本）；
- 它不污染主 agent 上下文（那条链路只回 `TaskFlow resumed: … results=N`），**只放大下游子代理的 prompt**。

`aggregate_deps` 是 opt-in，所以爆炸面有限；但一旦用上就是无界的。

---

## 2. 目标

1. 聚合结果有**每依赖**与**总量**两道上限，超限用 head+tail 截断并带可见标记。
2. 截断策略与判官共用**一份实现**（不再出现第二套裁剪规则）。
3. 不改变 `aggregate_deps` 的语义（仍然聚合依赖结果），只把"无界"改成"有界且可解释"。
4. 结果本来就短（≤ 上限）时，派发文本**字节级不变**——现有四个合成测试的断言不动。

---

## 3. 设计

### 3.1 共享裁剪工具

把 `agent/tools/taskflow/step_judge.py::_clip_for_judge` 提成公共函数：

```python
# agent/tools/taskflow/clip.py
def clip_text_head_tail(text: str, limit: int, *, marker: str = "\n\n[... middle omitted ...]\n\n") -> str:
    """Head 70% + marker + tail 30% (no-op when text fits)."""
```

- `step_judge` 保留 `_clip_for_judge(text, limit=None)` 作为薄封装（现有测试兼容），内部调用新工具；
- 聚合侧用同一个函数，只是 `limit` 与 `marker` 不同。

### 3.2 聚合预算（确定性 water-filling）

在 `build_task_with_dep_results` 的 `aggregate_deps` 分支里：

1. 按 `depends_on` 顺序取每个依赖的 `result_text`（缺失仍是 `no result recorded`）。
2. 计算公平份额：`share = min(per_dep_cap, total_cap // N)`；短于 `share` 的依赖原样保留，省下的额度**顺延**给后面的依赖（water-filling，最多补到 `per_dep_cap`）。
3. 超过 `share` 的依赖用 `clip_text_head_tail` 裁剪，标记里写明被截掉多少字符。
4. 无法在总量内保留的极端情况（例如 `N` 很大）：整段替换为一行
   `[... omitted: N chars not shown; the full result stays in the flow's results]`。

配置（`config/features/agent_side/taskflow_infra.py`）：

| 键 | 默认 | 含义 |
|---|---|---|
| `aggregate_result_per_dep_max_chars` | `4000` | 单个依赖的上限 |
| `aggregate_result_total_max_chars` | `16000` | 一次聚合的总预算 |

选这两档的理由：判官自己的视图是 8,000；合成步骤要综合多个上游，给到 4k/依赖、16k 总量，仍显著小于任何受支持模型的窗口，且比现在的无界行为有确定上界。

### 3.3 不承诺子代可回读全文

`aggregate_deps` 的接收者是**子代理**，而 `sessions_messages` 是 spawner-only（子代理的 requester 是主会话，不是它自己），所以截断标记里**不要**写"用 sessions_messages 读全文"这种子代做不到的指引。

- 标记只说明"被截断 + 全文仍在 flow 的 results 里"；
- 需要全文时由**主 agent** 决定是否把它显式贴进下一个 step 的任务，或让合成步骤自己缩小范围。

这是刻意的诚实：这条链路没有"子代自己回读"的能力，不上假的指针。

### 3.4 重试与 LDW 一致性

- `spawn_replacement` 的重试任务同样经过 `build_task_with_dep_results` → 自动获得同一上限；
- LDW 的 `run_taskflow_fallback` 用同一 builder → 同一上限；
- 不改变 LDW 侧"成功节点结果写回 journal"的行为（journal 存全文，聚合只在拼 prompt 时裁剪）。

### 3.5 明确不做的方案

- **在写 `results` 时就截断**：否决。judge、面板、`taskflow_inspect`、后续可能的消费者都需要全文；截断必须发生**注入点**，每个消费者按自己的预算裁剪。
- **把 `aggregate_deps` 默认打开**：不做，保持 opt-in。
- **给每步再加一个模型可设的裁剪参数**：暂不做；一个全局旋钮足够，等出现真实需求再加。

## 6. 验收

- 24k×2 的合成步骤：派发任务里上游文本总量 ≤ `aggregate_result_total_max_chars`，每个依赖 ≤ `aggregate_result_per_dep_max_chars`，标记可见；
- 短结果的合成步骤：派发文本与改动前**逐字节相同**；
- 判官视图仍 ≤ 8,000 且头尾保留；
- `uv run --no-sync python tests/run_tests_split.py` 全绿；
- 文档 parity / links / language 三门全绿。

---

## 7. Kill criteria

- 若某个真实合成场景因为 4k/依赖丢掉了关键信息 → 先调高 `aggregate_result_per_dep_max_chars`（旋钮），不要退回无界；若调到 8k 仍不够，再评估给该 step 一个显式 `aggregate_result_max_chars` 覆盖。
- 若裁剪让某个既有合成测试失败 → 该测试依赖的是"全文可见"这一隐含契约，需要显式记录并调整断言（不能靠无界来满足），在提交说明里写清。
- 若 `clip_text_head_tail` 的 70/30 分摊不适合代码 diff 类结果（尾部通常是收尾而非结论）→ 允许聚合侧传入不同比例，但默认保持 70/30。

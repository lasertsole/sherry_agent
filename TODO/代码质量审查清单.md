## 压缩器 SummaryDoc 字段缺少单条字数限制

### 问题

`SummaryDoc`（`agent/middlewares/summarization/summary_doc.py`）的 `completed`、`key_decisions`、`critical_context` 等列表字段只有**条目数 cap**（`cap_items` 做 `items[-N:]`），没有**单条字数限制**。模型可以在一条里写任意长度——5 条 completed 各 3,000 字符 = 15,000 字符，加上其他段落就超 16,000 总 cap → 整体被截断成头 4,800 + 尾 4,800，丢掉关键信息。

对比：`relevant_files` 已有列表总字符上限 `FILE_OPS_LIST_MAX_CHARS = 900`（`_fmt` 函数逐行累加超限丢旧行），但其他列表字段没有对应约束。

此外，**所有截断（工具输出、工具参数、总摘要、单条）都用纯 `len()` 按字符数切，没有走 CJK-aware token 估算**。同样 300 字符：英文 ≈ 75 token（截断省的少），中文 ≈ 150 token（截断更合理）。应该走 token 评估让两种语言 token 等价。

### 设计：token-based 截断（CJK-aware）

sherry 已有 `estimate_text_tokens`（CJK 2 字符/token、ASCII 4 字符/token）和 `is_cjk_codepoint`（逐字符判断）。截断改用 token 预算：

#### 新增 `truncate_by_tokens` 函数

`pub/func/message/target_truncation.py`（或新文件 `pub/func/message/token_truncation.py`）：

```python
from pub.func.cjk import is_cjk_codepoint
from config.features import TOKEN_ESTIMATION

CHARS_PER_TOKEN = TOKEN_ESTIMATION["chars_per_token"]        # 4
CHARS_PER_TOKEN_CJK = TOKEN_ESTIMATION["chars_per_token_cjk"]  # 2


def _chars_for_tokens(text: str, target_tokens: int, from_end: bool = False) -> int:
    """从头部（或尾部）走，累积 token 成本，返回达到 target_tokens 的字符数。

    CJK 字符 0.5 token/char，非 CJK 字符 0.25 token/char。
    """
    source = reversed(text) if from_end else text
    accumulated = 0.0
    count = 0
    for ch in source:
        cp = ord(ch)
        if is_cjk_codepoint(cp):
            accumulated += 1.0 / CHARS_PER_TOKEN_CJK   # 0.5
        else:
            accumulated += 1.0 / CHARS_PER_TOKEN        # 0.25
        count += 1
        if accumulated >= target_tokens:
            return count
    return count


def truncate_by_tokens(
    text: str,
    max_tokens: int,
    head_ratio: float = 0.5,
    tail_ratio: float = 0.3,
) -> str:
    """CJK-aware 截断：按 token 预算切，头 ratio + 尾 ratio + 省略标记。

    纯英文文本：max_tokens=500 → ~2000 字符（和旧的 2000 字符 cap 行为一致）
    纯中文文本：max_tokens=500 → ~1000 字符（比旧的 2000 字符 cap 更紧——因为中文每字符更贵）
    混合文本：按实际 CJK 比例插值
    """
    total = estimate_text_tokens(text)
    if total <= max_tokens:
        return text

    head_tokens = int(max_tokens * head_ratio)
    tail_tokens = int(max_tokens * tail_ratio)

    head_chars = _chars_for_tokens(text, head_tokens, from_end=False)
    tail_chars = _chars_for_tokens(text, tail_tokens, from_end=True)

    head = text[:head_chars]
    tail = text[-tail_chars:] if tail_chars > 0 else ""
    omitted = len(text) - head_chars - tail_chars
    return f"{head}…[{omitted} chars omitted]…{tail}"
```

**关键特性**：
- O(n) 单次遍历，n = 单条文本长度（通常 < 几千字符，可忽略）
- 精确到字符级——CJK 字符 0.5 token，ASCII 字符 0.25 token，逐字符累加到预算就停
- **英文不变**：500 token ≈ 2000 字符（4 字符/token），和旧的 2000 字符 cap 行为一致
- **中文更紧但 token 等价**：500 token ≈ 1000 字符（2 字符/token），同样 500 token 预算

#### 单条 cap 的 token 预算

| 字段 | 条目数 | token 预算 | 英文约字符 | 中文约字符 | 理由 |
|---|---|---|---|---|---|
| `completed` | ≤5 | **75** | ~300 | ~150 | 一行完成摘要 |
| `key_decisions` | ≤5 | **100** | ~400 | ~200 | "decision: reason" |
| `critical_context` | ≤3 | **125** | ~500 | ~250 | 错误消息/配置值 |
| `constraints` | 无 | **75** | ~300 | ~150 | 一句话约束 |
| `in_progress` | 无 | **75** | ~300 | ~150 | 同 completed |
| `blocked` | 无 | **75** | ~300 | ~150 | 阻塞 + 原因 |
| `next_steps` | 无 | **50** | ~200 | ~100 | 行动项应简洁 |
| `active_plan_notes` | ≤20 | **50** | ~200 | ~100 | "one line each" |
| `evicted_refs` | ≤20 | **不截断** | — | — | 文件路径必须完整，截断后路径不可用 |

预算核算：满载 = 5×75 + 5×100 + 3×125 + 5×75 + 5×75 + 5×75 + 5×50 + 20×50 + 20×75 = **4,875 token**。远在总摘要 cap（`SUMMARY_TOTAL_MAX_TOKENS`，见下）之内。

#### 总摘要 cap 也改 token

`SUMMARY_TOTAL_MAX_CHARS = 16000` 改为 `SUMMARY_TOTAL_MAX_TOKENS = 4000`（英文 ≈ 16,000 字符，行为不变；中文 ≈ 8,000 字符，更紧但 token 等价）。

#### 现有截断也全改

| 截断点 | 旧（字符） | 新（token） | 英文行为不变？ |
|---|---|---|---|
| 工具输出（`target_truncation.py`） | `MAX_TOOL_OUTPUT_CHARS = 2000` | `MAX_TOOL_OUTPUT_TOKENS = 500` | ✅ 500×4=2000 |
| 工具参数（`tool_args_truncate.py`） | `MAX_TOOL_ARGS_CHARS = 2000` | `MAX_TOOL_ARGS_TOKENS = 500` | ✅ |
| 摘要总截断（`compression.py:_truncate_content`） | `SUMMARY_TOTAL_MAX_CHARS = 16000` | `SUMMARY_TOTAL_MAX_TOKENS = 4000` | ✅ |
| 激进兜底（`compression.py:_aggressive_truncate`） | `AGGRESSIVE_TRUNCATE_CHARS = 1000` | `AGGRESSIVE_TRUNCATE_TOKENS = 250` | ✅ |
| **新增**：单条 cap（`_truncate_item`） | 无 | 见上表 | 新增 |

**英文用户零变化**——所有旧字符常量 ÷ 4 = 新 token 常量，英文 4 字符/token 行为完全一致。**中文用户受益**——同样 token 预算下中文截断更早触发，防止单条中文文本吃掉过多 token。

#### 实现步骤

1. **新增 `truncate_by_tokens`**：`pub/func/message/token_truncation.py`，~60 行
2. **改 `target_truncation.py`**：`truncate_tool_output` 调 `truncate_by_tokens` 替换 `content[:int(max_chars * ratio)]`
3. **改 `tool_args_truncate.py`**：`_truncate_args_str` 同上
4. **改 `compression.py:_truncate_content`**：调 `truncate_by_tokens`
5. **改 `compression.py:_aggressive_truncate`**：调 `truncate_by_tokens`
6. **新增 `cap_item_lengths`**：在 `summary_doc.py`，对 SummaryDoc 各列表字段调 `truncate_by_tokens`
7. **改配置**：`config/features/agent_side/summarization.py` 的字符常量改 token 常量（或新增 token 常量，保留字符常量做 fallback）
8. **接入点**：`cap_summary_doc`（条目数 cap）之后调 `cap_item_lengths`（单条 token cap），`_truncate_summary_messages` 改用 `truncate_by_tokens`

#### 验收

- 纯英文 500 token cap → 截断在 ~2000 字符（和旧 2000 字符 cap 行为一致）
- 纯中文 500 token cap → 截断在 ~1000 字符（比旧 2000 字符 cap 更紧）
- 混合文本 → 按 CJK 比例插值截断
- 截断标记格式不变（`…[N chars omitted]…`）
- 已短于预算的文本不动（幂等）
- 工具输出截断、工具参数截断、总摘要截断、单条截断全部走 `truncate_by_tokens`
- 现有测试不回归（英文行为不变）
- `evicted_refs` 不截断——文件路径必须完整，截断后路径不可用

## 驱逐文件生命周期：删除时清理 + 启动时对账

### 现状

驱逐文件（evicted tool results + offloaded media）存放在：

```
SESSIONS_DIR/<session_id>/evicted/    ← 工具结果驱逐（pub/func/message/eviction.py:108）
SESSIONS_DIR/<session_id>/media/      ← 媒体卸载（agent/middlewares/summarization/media_offload.py:5）
```

`clear_session`（`server/DAO/messages.py:17`）的第 4 步 `shutil.rmtree(SESSIONS_DIR/<session_id>)` **已经会删掉**这两个子目录——因为它们在 session 文件夹下。

### 问题

| 场景 | 现状 | 后果 |
|---|---|---|
| `clear_session` 正常执行 | ✅ `rmtree` 删整个 session 文件夹（含 evicted + media） | 无残留 |
| 崩溃在 `clear_session` 之前 | session 文件夹还在，DB 记录还在 | 重启后 session 还在，用户可手动删 |
| 崩溃在 `clear_session` 中间（rmtree 半途失败） | 部分 evicted/media 文件残留 | 无人清理，永久孤儿 |
| `clear_session` 删了 DB 但 rmtree 跳过/失败 | DB 没记录，但文件夹还在 | **孤儿文件夹**——无人引用，永久占磁盘 |
| session 从未被 `clear_session` 调用（用户直接关了浏览器，session 在 DB 里过期但未显式删除） | session 文件夹可能还在 | 不一定孤儿（DB 可能还有记录），但 evicted/media 文件可能很大 |
| 启动时 | **无对账扫描** | 孤儿文件夹永远不被发现 |

### 设计

#### 1. `clear_session` 加显式日志（小改）

`clear_session` 的第 4 步已有 `rmtree`，加一行日志显式说明 evicted/media 被删：

```python
# (4) Session folder under the sessions directory.
path = Path(_session_folder(session_id))
if path.exists() and path.is_dir():
    evicted_count = _count_files(path / "evicted")
    media_count = _count_files(path / "media")
    shutil.rmtree(path)
    if evicted_count or media_count:
        logger.info(
            "clear_session {}: removed {} evicted file(s), {} media file(s)",
            session_id, evicted_count, media_count,
        )
```

#### 2. 启动时对账扫描（核心新增）

`server/__main__.py` 启动时（在 sweeper 启动后、服务就绪前）扫描 `SESSIONS_DIR`，对每个 session 文件夹检查是否有对应的 DB 记录：

```python
import time

#: 新建文件夹不扫——可能是正在初始化的 session（防竞态）。
MIN_DIR_AGE_SECONDS = 300  # 5 分钟


def sweep_orphaned_session_dirs() -> int:
    """启动时扫描 SESSIONS_DIR，删除没有 DB 记录的孤儿 session 文件夹。

    孤儿 = 文件夹存在但所有 store（messages + todos + taskflows + checkpoints）
    都没有该 session 的记录。删整个文件夹（含 evicted/ + media/ + plans/）。

    Returns: 清理的文件夹数。Never raises。

    安全措施：
    - 跳过 symlink（防 rmtree 删 symlink 目标）
    - 跳过新建文件夹（< 5 分钟，防竞态）
    - 查多个 store（不只 messages，防漏判）
    - DB 读失败 → fail-open 不删
    """
    from config.path import SESSIONS_DIR

    base = Path(SESSIONS_DIR)
    if not base.is_dir():
        return 0

    cleaned = 0
    now = time.time()
    for session_dir in base.iterdir():
        # 跳过符号链接——防 rmtree 删 symlink 目标
        if session_dir.is_symlink():
            logger.warning("sweep: skipping symlink in SESSIONS_DIR: {}", session_dir)
            continue
        if not session_dir.is_dir():
            continue

        session_id = session_dir.name
        # 安全检查：session_id 必须是合法路径段
        if not is_safe_session_id(session_id):
            logger.warning("sweep: skipping unsafe session dir name: {}", session_id)
            continue

        # 新建文件夹跳过——可能是正在初始化的 session
        dir_age = now - session_dir.stat().st_mtime
        if dir_age < MIN_DIR_AGE_SECONDS:
            continue  # 太新，不扫

        # 查多个 store——任一有记录 → session 还活着
        if _session_has_any_records(session_id):
            continue

        # 孤儿：所有 store 都没记录 → 删
        evicted = _count_files(session_dir / "evicted")
        media = _count_files(session_dir / "media")
        logger.info(
            "sweep: orphaned session dir (no DB records, age={:.0f}s): {} "
            "({} evicted, {} media files)",
            session_id, dir_age, evicted, media,
        )
        shutil.rmtree(session_dir, ignore_errors=True)
        cleaned += 1

    return cleaned


def _session_has_any_records(session_id: str) -> bool:
    """session 在任一 store 有记录 → 还活着。

    查 4 个 store：messages / todos / taskflows / checkpoints。
    任一有记录 → True（不删）。全部无记录 → False（孤儿）。
    DB 读失败 → True（fail-open，不删）。
    """
    checks = [
        _messages_has_session(session_id),
        _todos_has_session(session_id),
        _taskflows_has_session(session_id),
        _checkpoints_has_session(session_id),
    ]
    return any(checks)


def _messages_has_session(session_id: str) -> bool:
    try:
        from context_engine.store.db import get_db
        db = get_db()
        conn = db.db
        cursor = conn.execute(
            "SELECT 1 FROM messages WHERE session_id = ? LIMIT 1",
            (session_id,),
        )
        return cursor.fetchone() is not None
    except Exception:
        return True  # fail-open


def _todos_has_session(session_id: str) -> bool:
    try:
        from agent.tools.todolist.registry.store_sqlite import _TodolistRepository
        repo = _TodolistRepository()
        conn = repo.connect_sync()
        cursor = conn.execute(
            "SELECT 1 FROM todos WHERE session_id = ? LIMIT 1",
            (session_id,),
        )
        return cursor.fetchone() is not None
    except Exception:
        return True  # fail-open


def _taskflows_has_session(session_id: str) -> bool:
    try:
        from agent.tools.taskflow.registry.store_sqlite import _TaskFlowRepository
        repo = _TaskFlowRepository()
        conn = repo.connect_sync()
        cursor = conn.execute(
            "SELECT 1 FROM task_flows WHERE session_id = ? LIMIT 1",
            (session_id,),
        )
        return cursor.fetchone() is not None
    except Exception:
        return True  # fail-open


def _checkpoints_has_session(session_id: str) -> bool:
    try:
        from agent.checkpointer.async_sqlite_checkpointer import delete_thread_history
        # 不实际删——只查存在性
        import sqlite3
        from config.path import CHECKPOINT_PATH
        conn = sqlite3.connect(str(CHECKPOINT_PATH))
        cursor = conn.execute(
            "SELECT 1 FROM checkpoints WHERE thread_id = ? LIMIT 1",
            (session_id,),
        )
        found = cursor.fetchone() is not None
        conn.close()
        return found
    except Exception:
        return True  # fail-open


def _count_files(directory: Path) -> int:
    """递归统计目录下文件数（不含目录）。"""
    if not directory.is_dir():
        return 0
    try:
        return sum(1 for _ in directory.rglob("*") if _.is_file())
    except OSError:
        return 0
```

**关键安全措施**：
- **查 4 个 store**（messages + todos + taskflows + checkpoints）——任一有记录就不删。防止"有 todos 但无 messages"的 session 被误删
- **跳过 < 5 分钟新建的文件夹**——防竞态（新 session 正在初始化但还没写 DB）
- **跳过 symlink**——防 `rmtree` 删 symlink 目标
- **每个 store 都 fail-open**——DB 读不了 → 假设有记录 → 不删。宁可漏删不误删
- **在 `file_sync` 之后运行**——确保 `file_sync.py` 创建的目录不会被刚建刚删

- **不清理非 session 目录的 evicted 文件**——只扫 `SESSIONS_DIR/<session_id>/` 下的。isolated workspaces 的清理已在 `计划_workspace崩溃恢复扫描.md` 里覆盖

## Code Intel 索引：跨项目交替使用时反复重建

### 问题

`index_meta` 表的 `file_path` 存的是**相对路径**（`os.path.relpath(path, root)`，如 `src/utils.py`）。`symbols` / `call_edges` 表也用相对路径。当 sherry 在两个项目间交替切换时：

```
时刻 T1: session 绑定项目 A → 首次查询 → 全量索引 A 的文件 → .codeintel/index.db 存的是 A 的符号
时刻 T2: session 切换到项目 B → 查询前刷新索引 → B 的 src/utils.py 的 mtime+size 和 A 的不同
         → 重新解析 B 的所有文件（A 的行被删，B 的行写入）→ 全量重建
时刻 T3: 切回项目 A → 又全量重建（A 的 mtime+size 和 B 的不同）
```

每次切换项目都要重新解析全部文件。5000 文件的项目 × tree-sitter 解析 ≈ 几秒到几十秒。**不是 bug**——索引正确刷新，查询结果正确。但**性能浪费**：交替使用 5 次就重建 5 次全量索引。

### 默认配置

`CODE_INTEL_DIR = ROOT_DIR / ".codeintel"`（`config/path.py`）——索引 DB 固定在 sherry 仓库根目录下，所有项目共用一个 `index.db`。

`SHERRY_CODE_INTEL_ROOT` 和 `SHERRY_CODE_INTEL_DB` 可以覆盖 DB 路径——但默认不设，所以所有项目共享一个 DB。

### 后果评估

| 维度 | 评估 |
|---|---|
| **功能损坏？** | ❌ 不会。索引始终正确——切换后刷新，查询结果对应当前项目。功能完全正常。 |
| **数据损坏？** | ❌ 不会。`_flush_batch` 先删旧行再写新行（`_drop_many` + insert），同一 `file_path` 不会有两套数据。`call_edges` 的 `resolved` 标记会在第二遍重新解析。 |
| **性能影响** | ⚠️ 中。首次切换时全量重建（几秒~几十秒，取决于项目大小）。之后该项目的增量索引正常（mtime+size 比对）。**只有在交替使用时才有重复重建的开销**——单项目用户完全不受影响。 |
| **token 浪费** | ⚠️ 低。重建索引发生在工具调用前（`index_directory` 是阻塞的），子代理 turn 会等待重建完成。重建时间不算 token，但墙钟时间变长。 |
| **触发的概率** | 中。sherry 支持按 session 绑定不同 project dir（`PUT /sessions/project`），所以多项目交替使用是真实场景。但大多数用户一次只用一个项目。 |

### 收益评估（如果修复）

| 方案 | 收益 | 成本 |
|---|---|---|
| **按 project root 分库**：`CODE_INTEL_DIR = project_dir / ".codeintel"` 而非 `ROOT_DIR / ".codeintel"` | 切换项目 = 切换 DB（上次留下的索引还在，增量刷新即可，不重建） | 低——改 `config/path.py` 的 `CODE_INTEL_DIR` 解析逻辑，让它用 `session_workspace_root(session_id)` 而非 `ROOT_DIR` |
| **file_path 存绝对路径**：`os.path.relpath` 改 `str(path.resolve())` | 两个项目的 `src/utils.py` 不会冲突，可以共存于一个 DB | 中——改 `_flush_batch` / `_load_known` / 所有查询；`file_path` 从相对变绝对，影响 `CodeQuery` 的 `callers`/`callees`/`impact` 全部查询 |
| **per-project DB（配置级）**：`SHERRY_CODE_INTEL_DB` 按项目目录自动设 | 用户无需手动配 | 低——在 `tools.py` 构造 `CodeIndexer` 时按 `cwd` 算 DB 路径 |

### 推荐方案：按 project root 分库（最低成本）

`config/path.py` 的 `CODE_INTEL_DIR` 改为按调用解析：

```python
def code_intel_dir(session_id: str | None = None) -> Path:
    """按 session 的 project dir 解析——每个项目独立索引。"""
    if session_id:
        from agent.tools.pub_base.session_workspace import session_workspace_root
        root = session_workspace_root(session_id)
        if root:
            return root / ".codeintel"
    return ROOT_DIR / ".codeintel"  # fallback
```

然后 `tools.py` 构造 `CodeIndexer` 时传 `code_intel_dir(session_id)` 而非 `CODE_INTEL_DIR`。

**效果**：
- 项目 A 的索引在 `project_a/.codeintel/index.db`
- 项目 B 的索引在 `project_b/.codeintel/index.db`
- 切换项目 = 切换 DB → 上次的增量索引还在 → 不重建
- `.codeintel/` 在 `.gitignore` 里，不进版本控制
- 每个项目的 `.codeintel/` 随项目一起存在/删除

### 不做的事

- **不改 `file_path` 为绝对路径**——改动面大（影响所有查询），收益小（分库已经解决冲突）
- **不合并多个项目的索引到一个 DB**——分库更干净，每个项目的索引独立
- **不做索引跨项目共享**——不同项目的符号表无交叉意义
- **不做后台预索引**——保持按需触发（首次查询时建索引），不引入后台进程复杂度

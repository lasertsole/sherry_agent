# 计划：2.1 用户可配生命周期 Hook

- 建档日期：2026-10-14
- 状态：**Step 1 已落地（2026-10-16）；Step 2 / Step 3 待做**
- 来源：ZCode 对标（用户可配生命周期 Hook，P3）
- 安全等级：**高**——阻塞型 hook 是执行路径上的用户代码，安全设计必须从第一天就有

---

## 0. 问题

用户无法在不 fork 源码的前提下插入自己的审计、计费、通知或策略逻辑。现有中间件钩子（`wrap_tool_call` / `after_model` / `after_agent`）全部是内部机制，无用户配置入口。

ZCode 有 7 事件生命周期 hook（`SessionStart` / `UserPromptSubmit` / `PreToolUse` / `PermissionRequest` / `PostToolUse` / `PostToolUseFailure` / `Stop`），但插件 hook 无条件执行——**不照抄这一点**。

---

## 1. 设计

### 1.1 三步走

| 步骤 | 事件 | 可阻断 | 可改 input | 安全风险 |
|---|---|---|---|---|
| **Step 1（只读 + 通知）** | `PostToolUse` / `PostToolUseFailure` / `Stop` | ❌ | ❌ | **零**——只发通知 / 写审计，不阻断 |
| **Step 2（PreToolUse allow/ask/deny）** | `PreToolUse` | ✅ allow/deny | ❌ | 中——需信任门 |
| **Step 3（改写 input）** | `PreToolUse` + `PermissionRequest` | ✅ | ✅ `updatedInput` | 高——限制为幂等变换 |

### 1.2 Hook 事件

| 事件 | 触发点 | 对标 Sherry 内部机制 | 字段 |
|---|---|---|---|
| `PreToolUse` | `wrap_tool_call` 的 precheck（handler 调用前） | `ToolGuardrails._wrap_tool_call_precheck` | `toolName`, `toolCallId`, `args`, `riskLevel` |
| `PostToolUse` | `wrap_tool_call` 的 post（handler 返回后） | `ToolGuardrails._wrap_tool_call_impl` + `MessagePersistence` | `toolName`, `toolCallId`, `result`（预览）, `durationMs` |
| `PostToolUseFailure` | `wrap_tool_call` 的 exception 分支 | `MessagePersistence._tool_error_message` | `toolName`, `error`（message + type）, `isInterrupt` |
| `Stop` | `after_agent`（turn 结束） | `PlanContinuationEnforcer.aafter_agent` | `responsePreview`, `toolCallCount` |
| `UserPromptSubmit` | `before_agent`（turn 开始） | `WorkspaceNoticeMiddleware.abefore_agent` | `prompt` |
| `SessionStart` | 进程启动 / 会话创建 | 无（新增） | `model`, `source`（startup/resume/compact） |

### 1.4 执行方式

**子进程**（不是嵌入式 Python），对标 `terminal.py` + `sandbox.py`：

```python
import subprocess

async def _run_hook(command: str, payload: dict, timeout_ms: int, session_id: str) -> HookOutcome:
    """执行 hook 脚本，传入 JSON payload via stdin，读 JSON outcome from stdout。"""
    try:
        proc = await asyncio.create_subprocess_exec(
            *shlex.split(command),
            stdin=asyncio.subprocess.PIPE,
            stdout=asyncio.subprocess.PIPE,
            stderr=asyncio.subprocess.PIPE,
            env={**os.environ, "SHERRY_SESSION_ID": session_id},
        )
        stdout, stderr = await asyncio.wait_for(
            proc.communicate(json.dumps(payload).encode()),
            timeout=timeout_ms / 1000
        )
    except asyncio.TimeoutError:
        return HookOutcome(status="timed_out")
    except Exception as e:
        return HookOutcome(status="failed", error=str(e))

    if proc.returncode != 0:
        return HookOutcome(status="failed", error=f"exit {proc.returncode}: {stderr[:4000].decode(errors='replace')}")

    try:
        result = json.loads(stdout.decode(errors='replace'))
    except json.JSONDecodeError:
        return HookOutcome(status="success")  # 非 JSON 输出 = 成功（通知型 hook）

    return HookOutcome(
        status="success",
        decision=result.get("decision"),       # "allow" / "deny" / "ask"（Step 2）
        updated_input=result.get("updatedInput"),  # Step 3
        additional_context=result.get("additionalContext"),
    )
```

**安全约束**：
- 命令解析用 `shlex.split`（不调 shell）
- 超时用 `asyncio.wait_for` + `AbortController` 等价（kill 子进程）
- stderr 预览 ≤ 4000 字符进日志，不进模型
- stdout JSON 解析失败 = 成功（通知型 hook 不需要返回 JSON）
- 最大输出 32768 字节

### 1.5 信任门

**不无条件执行**（与 ZCode 的 `canRunPluginHooks = () => true` 不同）：

```python
def _is_trusted(hook_config: dict, source: str) -> bool:
    """决定 hook 是否执行。

    1. sherry.jsonc 里的 hook → 需要 workspace trust（用户已信任项目）
    2. ~/.sherry/hooks/ 里的脚本 → 需要 SkillSpector 扫描通过
    3. 两者都不满足 → skip + log warning
    """
    if source == "project":  # sherry.jsonc
        return _workspace_trust_established()
    if source == "user":     # ~/.sherry/hooks/
        scan_result = hooks.resolve(hooks.SCAN_SKILL)
        if scan_result is None:
            return False  # fail-closed
        return scan_result.is_clean
    return False
```

复用 `SkillSpector`（`server/service/skill_scanner.py`）——已有的第三方内容安全扫描器，扫描 hook 脚本。

### 1.6 新中间件：UserHooksMiddleware

**新文件**：`agent/middlewares/user_hooks/core.py`

```python
class UserHooksMiddleware(AgentMiddleware):
    """用户可配生命周期 hook 的调度器。

    Step 1: 只调度 PostToolUse / PostToolUseFailure / Stop（通知型，不阻断）。
    Step 2: 加 PreToolUse（allow/deny，需信任门）。
    Step 3: 加 updatedInput（改写 input，限制为幂等变换）。
    """

    async def awrap_tool_call(self, request, handler):
        tool_name = request.name
        tool_call_id = request.get("id", "")
        args = request.get("args", {})

        # Step 2: PreToolUse（allow/deny）
        outcome = await self._dispatch("PreToolUse", {
            "toolName": tool_name, "toolCallId": tool_call_id,
            "args": args, "riskLevel": _risk_level(tool_name),
        }, request.session_id)
        if outcome and outcome.decision == "deny":
            return ToolMessage(content=f"[Hook denied: {outcome.reason or 'no reason'}]",
                               tool_call_id=tool_call_id)

        # 执行工具
        result = await handler(request)

        # Step 1: PostToolUse（通知型）
        await self._dispatch("PostToolUse", {
            "toolName": tool_name, "toolCallId": tool_call_id,
            "result": _preview(result), "durationMs": _duration(result),
        }, request.session_id, blocking=False)

        return result

    async def aafter_agent(self, state, runtime=None):
        # Step 1: Stop（通知型）
        await self._dispatch("Stop", {
            "responsePreview": _preview_last_ai(state),
            "toolCallCount": _count_tool_calls(state),
        }, state.get("session_id", ""), blocking=False)
```

## 2. HookOutcome 契约

```python
@dataclass
class HookOutcome:
    status: str          # "success" / "blocked" / "failed" / "cancelled" / "timed_out"
    decision: str | None = None       # "allow" / "deny" / "ask"（Step 2+）
    reason: str | None = None
    updated_input: dict | None = None # Step 3
    additional_context: str | None = None
```

Step 1 只读 `status`，忽略 `decision` / `updated_input`。

## 3. 安全设计

| 威胁 | 防护 |
|---|---|
| 恶意 hook 脚本 | 信任门：workspace trust（项目级）或 SkillSpector 扫描（用户级），不无条件执行 |
| hook 阻塞执行路径 | 超时（默认 5s）+ `asyncio.wait_for` kill 子进程 |
| hook 注入 prompt | stdout JSON 解析失败 = 成功（通知型 hook 不接触模型）；`additionalContext` 走 system-reminder 包装（嵌套转义） |
| hook 改写 input 注入恶意参数 | Step 3 最后做，限制为"路径规范化 / 参数补全"幂等变换，不允许注入新语义 |
| hook 窃取敏感数据 | payload 只传 `toolName` / `args`（预览）/ `result`（预览），不传完整 prompt / API key |
| stderr 泄漏 | ≤ 4000 字符进日志，不进模型 |
| 并发 hook 竞态 | 每个 tool call 的 hook 串行执行（同事件多 hook 按 config 顺序） |

## 5. 实施顺序

```
Step 1 (只读 + 通知型, 零安全风险):
  ├─ 1a. config/sherry_settings.py 加 hooks.* 配置
  ├─ 1b. agent/middlewares/user_hooks/core.py 只实现 PostToolUse / PostToolUseFailure / Stop
  ├─ 1c. subprocess 执行 + 超时 + stdout 解析
  ├─ 1d. 注册中间件（GATEABLE）
  └─ 1e. 测试：通知 hook 触发 + 超时 + 非 JSON 输出容错

Step 2 (PreToolUse allow/deny, 需信任门):
  ├─ 2a. PreToolUse 事件 + matcher 匹配（glob / RegExp）
  ├─ 2b. 信任门：workspace trust 或 SkillSpector 扫描
  ├─ 2c. deny → 返回 error ToolMessage（对标 ToolGuardrails halt）
  └─ 2d. 测试：deny 阻断 + matcher 匹配 + 信任门 fail-closed

Step 3 (updatedInput, 最高风险):
  ├─ 3a. updatedInput 限制为幂等变换（路径规范化 / 参数补全）
  ├─ 3b. 审计日志：记录每次 input 改写
  └─ 3c. 测试：幂等变换通过 + 非幂等注入拒绝
```

**Step 1 已落地**（2026-10-16）：`config/features/agent_side/user_hooks.py` +
`config/sherry_settings.py::load_sherry_hooks` + `agent/middlewares/user_hooks/`，
派发 `PostToolUse` / `PostToolUseFailure` / `Stop`，注册在 `ToolGuardrails` 之后
（`MIDDLEWARE_ORDER` + `GATEABLE`），测试见 `tests/agent/middlewares/test_user_hooks.py`。

实施时的三处偏离（Step 1）：
1. **总开关默认关**——`hooks.enabled`（`USER_HOOKS["enabled"] = False`）。计划里
   "配置里列了就跑"对**入库的** `sherry.jsonc` 是供应链脚枪（等于 ZCode 的
   `canRunPluginHooks = () => true`，只是换了个位置），而 Step 1 还没有信任门。
2. **hook 子进程不加沙箱**——合法 hook 的写入面（比如 `~/.sherry/` 下的审计日志）
   本来就在会话项目目录之外，套 `SandboxBackend.wrap` 会把正常用法一并挡掉；
   Step 1 的控制手段是"默认关 + 只读事件 + 超时 + 预览化载荷"。
3. `PreToolUse` / `UserPromptSubmit` / `SessionStart` 三种事件**能解析但不派发**
   （`_runners_for` 直接拒绝；构造时各警告一次）——半实现的阻断比不实现更糟。

**Step 2 / Step 3 未做，阻塞点**：
- Step 2 的信任门依赖 `_workspace_trust_established()`，仓库里**没有**这个概念，
  需要先设计（或改为复用 SkillSpector 的 `scan_skill(path)`，但那要处理
  每次派发的扫描缓存/LLM 成本）。
- Step 3 的"幂等变换"约束目前只有口号没有机制（怎么判定一个改写是幂等的？），
  需要先定一套允许清单或校验器。

## 6. 风险

| 风险 | 对策 |
|---|---|
| 阻塞型 hook 是执行路径上的用户代码 | Step 1 只读不阻断；Step 2 需信任门；Step 3 限制为幂等变换 |
| hook 超时阻塞 turn | `asyncio.wait_for` + kill 子进程，默认 5s |
| workspace trust 未建立 | fail-closed（skip + log），不无条件执行 |
| SkillSpector 不可用 | fail-closed（hook 不执行，log warning） |
| 并发 tool call 的 hook 竞态 | 同事件多 hook 串行（config 顺序），不同事件可并行 |
| ZCode 的 `canRunPluginHooks = () => true` | **不照抄**——Sherry 已有 SkillSpector，hook 必须复用同一信任模型 |

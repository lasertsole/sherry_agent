### 错误 B【高，QQ 频道不可用】频道依赖在冻结环境内安装失败
- 现象：QQ 频道启动时尝试 `uv pip install -r requirements.txt`，失败；SDK 不可用，频道 `start()` 直接 return。
- 日志证据（两次运行的 `error_*.log` 均出现）：
  ```
  Failed to install dependencies for channel 'qq':
  error: No virtual environment found; run `uv venv` to create an environment,
  or pass `--system` to install into a non-virtual environment

    uv pip install -r plugins/channels/qq/requirements.txt
  ```

- 根因（确定）：`channels/deps.py::install_requirements` 在检测到 `uv` 时执行 `uv pip install -q -r <req>`，**未传 `--system`**。冻结后端是 PyInstaller onedir，既无虚拟环境、`sys.executable` 也是冻结 exe，`uv` 拒绝向非虚拟环境安装；退路 `python -m pip` 同样无法向冻结 exe 安装。运行时安装第三方 SDK 到冻结树本身就是反模式。
- 依赖：`plugins/channels/qq/requirements.txt` → `qq-botpy>=1.2.1`。

### 错误 F【中，UX】最小化到托盘：点 X 不隐藏窗口 —— **未修复**
- 现象：在"系统配置 → 桌面"里把关闭行为选成"最小化到托盘"（`closeAction=tray`）后，点窗口右上角 X
  **无任何可见效果**——窗口既不隐藏也不关闭，停在原处。
- 根因（高置信，待重建验证）：Tauri 2 的 capability 安全模型里 `core:default`（含 `core:window:default`）只放行
  **只读内省**类窗口命令，`hide`/`show`/`close` 等变更性操作必须单独授权。`client/src-tauri/capabilities/default.json`
  只声明了 `core:default`，**缺 `core:window:allow-hide`**。关闭流程走到前端
  `app/components/CloseToTrayDialog.vue:79` 的 `getCurrentWindow().hide()`——这是走 IPC 的核心
  `plugin:window|hide` 命令，被 capability 系统拒绝、抛错被 `onCloseRequested` 的 catch 静默吞掉；
  而 `close_ack`（自定义 `#[tauri::command]`，不受 capability 限）已先成功执行，Rust 端 1.5 秒回退
  `CLOSE_ACKED < ticket` 判定 false 也不触发 → 窗口停在原处。
- 多路佐证：Rust 端多处直调 `window.hide()`（托盘菜单 Hide、托盘图标点击、1.5 秒回退）不走 IPC、不受限，
  所以那些路径正常；唯独前端这一处 IPC hide 被卡——这也解释了"问询对话框"里点"直接退出"能用
  （调 `quit_app` 自定义命令）而"最小化到托盘"不能用（调 `hide()` 被拒）。
- **修复方向**（详见步骤 D）：在 `client/src-tauri/capabilities/default.json` 的 `permissions` 数组里
  加入 `"core:window:allow-hide"`。该改动安全且幂等——只放开窗口隐藏操作，即便 `core:default` 本就含它也是无害 no-op。
  前端没有 `getCurrentWindow().show()` 调用（托盘恢复走 Rust `on_tray_icon_event`/菜单事件直调 `window.show()`），
  故无需补 `allow-show`。
- 待验证：重建重装后选"最小化到托盘"再点 X，窗口应正常隐藏到托盘（托盘图标 / 右键 Show 恢复）。

## 二、根因分析

### 错误 A 的根因（已用冻结字节码深挖确认方向）

> 这一轮用 `scripts/dev/inspect_frozen_config.py` 从 exe 内嵌的 PYZ 归档里抽出了
> `config.sherry_settings` / `config.path` / `config.models_settings` /
> `config.network_settings` 的冻结字节码（PYZ 头格式 `MAGIC + pyc_magic + toc_pos + pyvers`，
> TOC 是 `[(name, (ispkg, pos, len)), …]` 列表，每项 zlib 压缩的 marshal code）。结论如下。

- **C1（冻结后端早于播种代码）已排除。** 冻结字节码里 `ensure_sherry_config_file`、
  `ensure_models_config_file`、`ensure_network_config_file`、`_seed_mcp_folder`、`.env` 播种块
  （`ENV_PATH`/`exists`/`template`/`write_text`/`OSError`）全部在场；反汇编
  `config.sherry_settings` 顶层字节码，第 66 行确有 `LOAD_NAME ensure_sherry_config_file` →
  `CALL`。**播种代码在冻结构建里、且导入期确实执行。**
- **ROOT_DIR 解析到 `_internal`（多路佐证）。** skills 加载器经 `SKILLS_DIR = ROOT_DIR/"skills"`
  文件系统 `glob`、`resolve_app_path` 回退 `ROOT_DIR/rel`，日志里 SkillScanner 路径
  (`_internal\skills\builtin\...`) 与 QQ requirements 路径 (`_internal\plugins\channels\qq\...`)
  都落在 `_internal\`；全仓 grep 确认**无任何** `sys._MEIPASS` / `sys.frozen` 回退，所以这些只能由
  `ROOT_DIR = _internal` 解释。模板 `.env`/`sherry.jsonc`/`.models.example`/`.network.example`
  也确认存在于 `_internal\`。
- **但四个文件仍未播种，且无 `Failed to seed` 警告。** sherry_settings / models / network 的
  `except OSError` 分支会打 warning 却没打 → 只能是 `not template.is_file()` 静默跳过（`path.py`
  的 `.env` 分支是 `except OSError: pass`，本就静默）。即冻结模块的 `Path(__file__).resolve().parents[1]`
  没指到 `_internal`，模板查找落空、静默 return。
- **写路径同样失败，运行期直接佐证 C2。** 第三轮日志（PID 22876，10:19:23+）出现 8 条
  `write_sherry_config_handler: sherry.jsonc is unavailable for writing: Sherry config file not found`
  ——用户在配置面板点了"保存"。`server/service/sherry_config.py:153-157` 的写路径逻辑是：
  `ensure_sherry_config_file()`（保存前 re-seed）→ `if not SHERRY_CONFIG_PATH.exists(): raise FileNotFoundError`。
  写路径**确实调用了** `ensure_sherry_config_file()`，但它静默 no-op（同一 `not template.is_file()` 跳过），
  文件仍未生成，于是抛 `FileNotFoundError` → 503。**这是运行期直接证据**：`ensure_sherry_config_file`
  被调用了（导入期 + 写路径两次都调），却两次都静默跳过——若 C1（播种代码缺失）成立，写路径这句显式
  调用也该缺失，可它没缺失，行为与源码完全吻合。所以 **C1 不仅被字节码排除，也被运行期行为排除**，
  只剩 C2（`_CODE_ROOT` 模板解析落空）。

> **矛盾的来源（已定位到 `__file__`，留一次启动探针定死具体值）。** "ROOT_DIR = `_internal`"
> 与"_CODE_ROOT ≠ `_internal`"用的是同一个公式 `Path(__file__).resolve().parents[1]`，却得出不同
> 结果。这说明 PyInstaller 给 PYZ 冻结模块赋的 `__file__` 在运行期不是 `_internal\config\X.py`
> 这种绝对真实路径（`co_filename` 是相对串 `config\sherry_settings.py`，运行期 `__file__` 的实际
> 取值我无法靠静态分析确定——可能是相对 `co_filename` 按 CWD 解析，也可能是 `_MEIPASS` 取值与
> 预期不同）。**这一处必须靠一次启动探针日志定死**，但**修复方向不受其影响**：用
> `sys._MEIPASS`（PyInstaller onedir 下 = `_internal` 的绝对可靠锚点）定位随包模板，替换
> `Path(__file__).parents[1]`，并在所有静默跳过分支补 warning。
>
> **⚠️ 关键风险（必须在交接前知晓）**：若探针显示 `_CODE_ROOT` **已** = `_internal`（即 C2 不成立），
> 则 `resolve_code_root(_MEIPASS=_internal)` 对 `_CODE_ROOT` 是 **no-op**，本修复无效。这种情形下
> 矛盾无法用"模板路径错"解释，问题在写入侧或调用侧。**不要在 C2 未确认时硬上 `_MEIPASS` 改造**——
> 步骤 0 的分支④专门处理此情形，转 Plan B 排查写入侧（杀软拦截、`SHERRY_CONFIG_PATH` 重定向、
> `ensure_*` 导入期调用被吞异常等）。先探针定死，再决定改路径还是改写入。

### 错误 B 的根因（确定）
频道依赖"运行时 `uv/pip install`"机制与 PyInstaller 冻结环境根本不兼容：冻结树无 venv、`sys.executable` 是冻结 exe、第三方包即便装下也无法被冻结解释器正常 import（原生扩展、PEP 文件等）。该机制只适用于 checkout / `uv run` 开发态。

## 三、解决步骤

### 步骤 0｜启动探针（定死 `__file__` / `_MEIPASS` 具体值，先做）

C1 已排除，修复方向定为 `_MEIPASS`，但 `_CODE_ROOT` 与 `ROOT_DIR` 用同一公式却据推断结果矛盾（见根因分析），
本步用一次探针定死 `_CODE_ROOT` 的运行期真实取值，确认 `_MEIPASS` 修复是否有效。**探针日志是临时排查用，
最终构建前移除**（或并进步骤 A-3 的 warning 补全，避免两次重建）。

1. 在 `config/path.py` 的 `APP_HOME` / `ROOT_DIR` 计算之后、以及 `config/sherry_settings.py`
   的 `ensure_sherry_config_file` 进入处，各加一段 `loguru` INFO。
   **注意**：`config/path.py` 顶部并未 import logger，`config/sherry_settings.py` 是在函数内才
   `from loguru import logger`——探针代码块前必须各自先 `from loguru import logger`，否则导入期
   `NameError` 让后端启动崩溃。
   ```python
   from loguru import logger
   import sys as _sys
   _mp = getattr(_sys, "_MEIPASS", None)
   logger.info("BOOT-PATHS: __file__=%s ROOT_DIR=%s APP_HOME=%s _MEIPASS=%s frozen=%s",
               __file__, ROOT_DIR, APP_HOME, _mp, getattr(_sys, "frozen", False))
   logger.info("BOOT-PATHS: .env tmpl=%s exists=%s | sherry.jsonc tmpl=%s exists=%s",
               ROOT_DIR/".env", (ROOT_DIR/".env").is_file(),
               ROOT_DIR/"sherry.jsonc", (ROOT_DIR/"sherry.jsonc").is_file())
   ```
   `ensure_sherry_config_file` 里加 `logger.info("SEED-SHERRY: _CODE_ROOT=%s tmpl=%s tmpl_exists=%s target=%s target_exists=%s", …)`。
2. 重跑 `packaging/build_backend.py` → `pnpm tauri build`（或先 `pnpm tauri dev` 直跑验证）→ 启动 → 读 `info_*.log`。
3. 判读（四分支，重点是④）：
   - ① `_MEIPASS` 缺失 / `frozen=False` → 与"打包态"前提矛盾，检查 backend_entry 是否被以非冻结方式启动。
   - ② `_MEIPASS = …\sherry-backend\_internal`、`__file__` 不在 `_internal\config\` 下、`tmpl exists=False` → **C2 确认**，`_CODE_ROOT` 与 `_MEIPASS` 不一致，正是 `_MEIPASS` 修复要解决的；进步骤 A。
   - ③ `_MEIPASS = _internal`、`_CODE_ROOT = _internal`、`tmpl exists=True`、但 `target_exists=False` 且无 `Failed to seed` 警告 → 写入被静默吞掉（`path.py` `.env` 分支 `except OSError: pass`）或非 OSError 异常；进步骤 A-3 把 OSError 暴露，并排查杀软/权限/路径长度。
   - ④ `_MEIPASS = _internal`、`_CODE_ROOT` **已** = `_internal`、`tmpl exists=True`、`target_exists=False` 且无任何 seed 警告 → **C2 不成立，`_MEIPASS` 修复对本问题是 no-op**。转 Plan B（见下），不要直接进步骤 A。

#### Plan B｜分支④触发时（`_CODE_ROOT` 已正确，播种仍失败）

此情形下 `ensure_sherry_config_file` 模板找得到、却没生成文件、也没 warning，说明问题在**写入侧或调用侧**，
不在模板解析。按以下顺序排查（每条都在探针里加对应日志确认）：

1. **`ensure_sherry_config_file` 导入期调用是否真的执行到写**：在函数内 `if SHERRY_CONFIG_PATH.exists(): return`
   与 `if … or not template.is_file(): return` 每个出口加 `logger.info("SEED-SHERRY: early-return reason=…")`，
   确认是走了哪条 return、还是走到了 write 分支。若根本没进函数，说明导入期调用被更早异常吞掉——查 `all_*.log`
   启动段有无未预期 WARNING/ERROR、`config.sherry_settings` 是否导入成功。
2. **写入是否被静默吞掉**：`SHERRY_CONFIG_PATH.parent.mkdir` 与 `write_text` 包进 try/except，把 `Exception`
   （不只 `OSError`）全捕获并 `logger.warning(...)`——`UnicodeDecodeError`（read_text 编码）、`PermissionError`
   （OSError 子类，本该 warn 却没 warn 就奇怪）、`FileNotFoundError`（parent 不存在）等都暴露出来。
3. **杀软/Defender 实时拦截**：Windows Defender 对 `%APPDATA%\com.ema-ai.agent\` 下新建的点文件（`.env`/`.models`）
   可能静默拦截。临时把该目录加入 Defender 排除列表后重启验证；或先手写一个 `.env` 进去看是否被秒删。
4. **`SHERRY_CONFIG_PATH` 是否被重定向**：探针打印 `SHERRY_CONFIG_PATH` 的实际值与 `APP_HOME`，确认没被某层
   环境变量/覆盖指到别处（`SHERRY_HOME`、`SHERRY_WORKSPACE_DIR` 等）。`APP_HOME` 在导入期就定值，确认它等于
   `C:\Users\…\AppData\Roaming\com.ema-ai.agent`。
5. **若以上都不成立**——即探针显示 write 分支执行、无异常、文件仍缺——考虑 PyInstaller 冻结态下
   `Path.write_text` 的重定向（极低概率），改用 `os.makedirs`+`open(...,"w")` 显式写并打印 `os.path.abspath`
   与写后 `os.path.exists` 复核。

> Plan B 的核心是：**别在 C2 不成立时硬上 `_MEIPASS` 改造**——那只会浪费一次重建。先用探针把"模板找到、
> 写入未生效"的原因定死，再决定是改写入代码、改环境、还是回退排查。

### 步骤 A｜修复配置播种（用 `sys._MEIPASS` 定位随包模板 + 补全 warning）

> 前置：步骤 0 落在分支②（`_CODE_ROOT ≠ _internal`）才进本步。若落在分支④，按 Plan B 走，本步无效。

PyInstaller 在 onedir 下把 `sys._MEIPASS` 设为 `_internal\`，是定位随包数据文件的可靠方式，
不依赖冻结模块的合成 `__file__`。改动集中、对 checkout 行为零影响（`_MEIPASS` 未设时回退原值）。

1. 在 `config/_home.py` 新增冻结代码根解析器：
   ```python
   import sys
   def resolve_code_root(code_root: Path) -> Path:
       """The code root that owns shipped data files.

       Under PyInstaller (``sys.frozen``) shipped data lives under
       ``sys._MEIPASS`` (onedir = ``_internal``), NOT under the synthetic
       ``__file__`` of a frozen module. A checkout (no ``_MEIPASS``) keeps
       the historical ``code_root`` (``Path(__file__).parents[1]``).
       """
       meipass = getattr(sys, "_MEIPASS", None)
       return Path(meipass).resolve() if meipass else code_root
   ```
2. 模板根从 `Path(__file__).resolve().parents[1]` 改为 `resolve_code_root(...)`。**建议只改三处 `_CODE_ROOT`
   （爆炸面收窄到播种），不动 `ROOT_DIR`**，原因见下方"下游影响分析"：
   - `config/sherry_settings.py`：`_CODE_ROOT = resolve_code_root(Path(__file__).resolve().parents[1])`、`template = _CODE_ROOT / "sherry.jsonc"`。
   - `config/models_settings.py`：`MODELS_CONFIG_TEMPLATE`（`.models.example`）的根同理包裹。
   - `config/network_settings.py`：`NETWORK_CONFIG_TEMPLATE`（`.network.example`）的根同理包裹。
   - `config/path.py` 的 `.env` 模板（`template = ROOT_DIR / ".env"`）：**不要**改 `ROOT_DIR` 初值，而是把这一处
     的模板根单独用 `resolve_code_root(ROOT_DIR)` 取——`_env_template_root = resolve_code_root(ROOT_DIR)`，
     `template = _env_template_root / ".env"`。这样 `.env` 播种受益，但 `ROOT_DIR` 本身不变。

   **下游影响分析（为何不动 `ROOT_DIR` 初值）**：`ROOT_DIR` 被十余处引用——`PLUGINS_PATH`/`SKILLS_DIR`/
   `CONTEXT_ENGINE_PATH`/`_SHIPPED_WORKSPACE_TEMPLATE_DIR`/`resolve_default_project_dir`（未配置会话的默认
   项目目录回退）/`app_relative`/`resolve_app_path`。证据强烈指向 `ROOT_DIR` **已** = `_internal`（skills/channels
   都从 `_internal` 加载），把 `ROOT_DIR` 包进 `resolve_code_root` 对它多半是 no-op；但若实际 `ROOT_DIR` ≠
   `_internal`，改它会把默认项目目录、显示路径、技能解析根全部挪到 `_internal`，影响面大且未验证。所以：
   **只改播种用的 `_CODE_ROOT`/模板根，`ROOT_DIR` 保持原样**。若步骤 0 探针发现 `ROOT_DIR` 也错（分支②且
   `ROOT_DIR` 同样指偏），再单独评估是否扩到 `ROOT_DIR`，届时必须逐个下游确认。
3. **补全静默跳过分支的 warning**（避免再次"文件没生成、日志也没说"）：
   - `config/path.py` 的 `.env` 播种 `except OSError: pass` → `except OSError as exc: logger.warning("Failed to seed .env from {} to {}: {}", template, ENV_PATH, exc)`。
   - `ensure_sherry_config_file` / `ensure_models_config_file` / `ensure_network_config_file` 里
     `if … or not template.is_file(): return` 分支，补一条 `logger.warning("{} template not found at {} (code_root={}); seeding skipped", …)`。
4. 单测：在 `tests/config/` 下新增用例，`monkeypatch` 设 `sys._MEIPASS` 指向临时目录、放假 `.env`/`sherry.jsonc`/`.models.example`/`.network.example`，断言 `ensure_*` 从 `_MEIPASS` 拷到 `APP_HOME`；`_MEIPASS` 未设时回退原 `code_root` 行为不变。
5. 重建后端 + 重打 exe（同步骤 0 第 2 步），全新安装首次启动核对四文件已生成。

### 步骤 B｜修复 QQ 频道依赖（冻结态禁用运行时安装 + 随包冻结 SDK）

方向：运行时安装对冻结环境是反模式，改为"构建期冻结 SDK + 运行期跳过安装"。

1. **构建期带入 `botpy`**（默认走这条）：
   - `plugins/channels/qq/requirements.txt` 里的 `qq-botpy>=1.2.1` 已是项目可用依赖；发行包 `qq-botpy` 的**顶层模块名是 `botpy`**（已核实 `plugins/channels/qq/core.py:21,131` 均为 `import botpy`）。在 `packaging/build_backend.py` 的 `COLLECT_ALL` 增加 **`"botpy"`**（不是 `qq_botpy`——PyInstaller `--collect-all` 接收 import 名，传错会因"无此包"构建失败），让 PyInstaller 把它及其数据文件一并冻结进 `_internal`。
   - 若 `botpy` 有 C 扩展或数据文件，`--collect-all` 比 `--collect-submodules` 更稳。
   - 在桌面工作流的打包冒烟步骤里 `import botpy` 一次，确认冻结态可导入。
   - 若 `botpy` 因体积/许可原因**无法**随包冻结，才走下面 B-3 降级路径——二选一，默认 B-1。
2. **运行期跳过安装**：`channels/deps.py::install_requirements` 与 `channels/registry.py::_ensure_deps`、`plugins/channels/qq/core.py::_install_deps` 在 `getattr(sys, "frozen", False)` 为真时**直接 short-circuit**：
   ```python
   import sys
   if getattr(sys, "frozen", False):
       # 冻结环境无法运行时安装；依赖必须在构建期冻结进树。
       return True, False, ""   # install_requirements
   ```
   `qq/core.py` 的 `_install_deps` 同理：冻结态直接 `return _try_import_botpy()`（能 import 即可用，不能即不可用，不再尝试 subprocess 安装）。`_ensure_deps` 在冻结态把 `requirements.txt` 视为已满足。
3. **降级体验**（仅当 B-1 不可行时走）：在冻结态把 QQ 频道按"未配置"处理——`channels/manager` 启动时检测 `QQ_AVAILABLE is False and frozen` → 不再报 ERROR，改为一条 INFO："QQ channel disabled in packaged build (SDK not bundled)"，避免每次启动刷两条 ERROR。
4. 单测：`tests/channels/` 增 `monkeypatch sys.frozen=True` 用例，断言 `install_requirements` 不起子进程、直接返回成功；`frozen=False` 时走原 `uv/pip` 路径不变。
5. 重建 + 重打 exe，启动后核对 `error_*.log` 不再出现 QQ 安装失败。

### 步骤 C｜修复缺参数返回 500（应为 400）

5 处 handler 把"客户端缺参数"抛成了未捕获异常，冒泡到通用 500 包装器。修法统一：在 handler 里
把对应的参数校验/JSON 解析/类型转换 catch 成结构化 400，与同批已正确返回 400 的端点一致。
`bad_request`/`not_found` 助手在 `server/trigger/http/helpers.py` 已有（`memory_entries.py` 已在用）。

1. **`server/trigger/http/media.py`**：`GET /media` 的 5 处 `raise ValueError`（缺 session_id/filename、
   无效 session_id、无效文件名、文件不在目录内）→ `return bad_request(...)`；`media not found` → `return not_found(...)`。
   （注：`media not found`→404 是顺带改进，**探测只覆盖了缺参数的 500**，未触达 not-found 分支，验收 probe 重跑验不到这一行。）
   顶部从 `server.trigger.http.helpers` 引入 `bad_request`、`not_found`。
2. **`server/trigger/http/messages.py`**：引入 `bad_request`；`get_history_by_turn_page` 与
   `get_pending_interrupt` 的缺参 `raise ValueError(...)` → `return bad_request(...)`；`DELETE /sessions`
   (`clear_session_handler`) 的 `request.json()` 包 try/except（`JSON body required`）+ 非法 session_id 的
   `raise ValueError` → `return bad_request("invalid session_id")`。
3. **`server/trigger/http/memory_entries.py`**：DELETE `/memory/entries/:entry_id`
   (`memory_entries_archive_handler`) 的 `_entry_id(path_params)` int 转换单独 try/except `ValueError`
   → `return bad_request("entry_id must be an integer")`，与同路由 GET/PUT 已有的
   `except ValueError → bad_request` 对齐。
4. 单测：`tests/server/` 各加一条"缺参数 → 400（非 500）"用例，断言状态码与 message。
5. 重建后端 + 重打 exe，重跑 `scripts/dev/probe_routes.sh`，核对这 5 行从 `ERR … -> 500` 变成 `ERR … -> 400`。

### 步骤 D｜修复最小化到托盘（capability 授权）

1. 在 `client/src-tauri/capabilities/default.json` 的 `permissions` 数组里加入 `"core:window:allow-hide"`
   （放在 `"core:default"` 等条目之后即可）。
2. 重建 Tauri 外壳：`cd client && pnpm tauri build`（Windows 矩阵）。capability 编译进 Rust 外壳，必须重建才生效。

   点托盘图标 / 右键 Show → 窗口恢复。

   并确认 `getAppFlag('closeAction')` 确实返回 `'tray'`（localStorage/Dexie 镜像）。

## 二、问题、根因与已落地的修改

### 1. 同一个命令/探针循环耗尽 90 次模型调用（已修）

- **精确重复**：同一个 terminal 命令连续执行 69 次，结果都是 `exit 1` 文本
  （`status="success"`）。签名 streak 只 WARN 且每回合最多 3 次，达到上限后没有
  动作。已改为：3 次 WARN 预算用尽后，精确的 tool+args 签名在本回合剩余时间内
  **BLOCK**；只拦截该签名，其他参数和其他工具仍可用，并绕过 recovery mode。
- **探针文件循环**：精确签名被拦后，agent 改写 `probe1.py`…`probe19.py` 再逐个
  执行——参数每次都变，输出逐字节相同。已新增 **结果重复检测**：非幂等工具对每个
  工具维护连续相同结果的计数，3 次警告一次、6 次封锁整个工具；幂等工具继续走
  no-progress 链。
- **编辑后无法验证**：205218 中 agent 在 72/90 才 `patch_file`，但 terminal /
  python_repl 仍处于封锁状态，剩余 18 次调用只能读文件。已给 `patch_file` 增加
  tool-owned metadata `clears_guardrail_blocks`：成功后清空所有 block、签名/结果
  连击、exact-failure/no-progress 计数和调用记录，让新补丁可以重新验证；新建
  `probeN.py` 的 `write_file` 不携带该标记，不能重新打开循环。
- 以上三项之后，Sympy 在 210023 用 **28 次模型调用**自然收敛，未耗尽预算。

### 2. Sympy F2P 隐藏测试语义（未修，信息缺口）

210023 的补丁把 `_print_Pow` 的根号路径限定为
`e.is_Rational or (e.is_Pow and e.exp is S.NegativeOne and e.base is d)`，
修好了报告中的 `pi**(1/E)`（`exp(-1)` 不是 `Pow`），但没有处理
`pi**(1/pi)`、`pi**(1/EulerGamma)`。F2P 的 `test_issue_17616` 和更新后的
`test_issue_6285` 要求：

- NumberSymbol 分母（`pi` / `E` / `EulerGamma`）→ 退回指数记法；
- Symbol 分母（`7**(1/x_17)`）→ 保留根号；
- 现有仓库里的 `test_issue_6285` 断言的恰好是**旧行为**（`Pow(x, 1/pi)` 用根号），
  该断言由 test patch 在评测时改写。

因此这不是“模型没跑测试”或“循环未收敛”，而是 **issue + 仓库现有测试无法推导出
维护者的语义选择**。可用方案：

1. **（推荐）harness 在运行前暴露目标测试**：把 test patch 先应用到 checkout，
   或在 prompt 中给出 F2P 测试名 + 期望矩阵。这样 agent 能真正运行 F2P，验证
   闭环；代价是与官方 SWE-bench 的“测试后置”协议不同，需要在报告里标注。
2. 接受该实例为信息缺口：只把它当作“能否修好报告中的表达式”的弱信号，不再
   用 F2P 通过率衡量收敛能力。
3. 不采用：把 NumberSymbol/Symbol 规则写进产品 prompt 或代码——这是评测专用
   语义，属于对单实例过拟合。

**本轮采用方案 1 的 prompt 版本**：`evals/swebench/suite.py::_target_tests_block`
把实例的 test patch（超过 12 000 字符则截断）和 FAIL_TO_PASS 名称放进任务
prompt；checkout 不预先打补丁，官方 test patch 仍在判题时应用；实例报告记录
`target_tests_exposed`。这样 agent 能看到期望输出，同时保留官方判题协议。

### 3. Django `django__django-17051`（未修，待重跑）

010944 中代理只改了 `django/db/models/query.py` 两处
`on_conflict is None` → `on_conflict in (None, OnConflict.UPDATE)`，F2P 仍以
`UNIQUE constraint failed: bulk_create_country.iso_two_letter,
bulk_create_country.name` 失败，P2P 也失败。

根因：只放宽了“是否读取返回行”的条件，没有让 SQLite 生成
`ON CONFLICT (...) DO UPDATE SET ...`；`on_conflict=UPDATE` 的字段选择和冲突
目标需要进入 `_batched_insert` / compiler 的写入路径。

修复建议：

1. 在 `bulk_create(on_conflict=OnConflict.UPDATE)` 的分批插入路径生成真正的
   upsert SQL（或在 `_insert` 的 `update_fields` 分支处理）。
2. 补一个只覆盖 F2P 的回归测试，断言冲突行被更新而不是抛 `IntegrityError`。
3. 保留 `on_conflict is None` 的原有返回行语义；不要用放宽条件替代 upsert。
4. 先重跑 Django 再决定是否需要改产品代码；本轮改动只影响 agent 侧护栏，
   不会自动修复 Django 的写入路径。

### 4. Harness prompt 与网络环境（已修）

- 网络命令（`curl` / `wget` / `git fetch` / `git clone` 等）非零退出现在 raise
  `ToolException`，`ToolMessage(status="error")`，ToolGuardrails 的 failure 计数
  生效；本地测试/编译失败仍返回 `status="success"` 文本。
- `web_fetch` HTTP 4xx/5xx 同样 raise。
- 网络探测失败时，harness 在 AGENTS.md 追加“不要继续探测网络”的 directive。
- SWE prompt 增加：修改后运行覆盖改动文件的邻近测试；结果已知时不要重复同一
  命令；不要只针对报告中的单个表达式打补丁。
